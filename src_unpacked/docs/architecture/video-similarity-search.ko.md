# 동영상 유사도·중복 탐색 아키텍처

> **설계 상태: PROPOSED / NOT IMPLEMENTED / NOT VALIDATED**
>
> 기준일: 2026-10-31  
> 목적: 영상 길이와 구조에 맞춰 적은 수의 대표 프레임 및 시간축 정보를 선택하고, 전체 영상 중복과 부분 클립 탐색을 분리하는 알고리즘 설계.  
> 이 문서는 CPU/GPU 디코더 구현이나 하드웨어 가속 경로를 결정하지 않는다.

> 2026-10-31 보강: §16은 Probe/Kept/Decoded 수량, 130분 예산, 본편 가중, Node E decoder 경계를 구체화하는 최신 기준이다.

## 1. 문서의 역할과 목표

이 문서는 MediaSimilarityFinder의 **동영상 콘텐츠 중복 판정 의미론**을 설명한다. 디코더가 어떤 CPU/GPU 경로로 프레임을 가져오는지, CUDA/NVDEC/D3D11VA를 어떻게 연결하는지와는 별개의 계층이다.

핵심 목표는 모든 시간 지점의 화면을 촘촘히 저장하는 것이 아니라, 영상 유형에 맞는 소수의 대표 프레임과 시간 구간 특징으로 동일 콘텐츠 여부를 높은 신뢰도로 판정하는 것이다.

설계 원칙:

1. 이미지처럼 단일 프레임의 여러 방향 변형을 과도하게 비교하지 않는다. 동영상은 프레임의 **시간 순서, 연속성, 장면 변화**를 주요 증거로 사용한다.
2. 전체 영상 중복 검색과 부분 클립 검색은 별도 작업·색인·판정 유형으로 분리한다.
3. 길이만으로 장르를 단정하지 않되, 재생 시간은 첫 번째 후보 분류 축으로 사용한다.
4. 시작부와 종료부를 지능적으로 탐색한다. 장편은 정방향 시작부와 역방향 엔딩 탐색을 모두 사용한다.
5. 검은 화면, 로고, 인트로, 크레디트는 불필요한 이미지로 저장하지 않고 구조적 구간 정보로 기록할 수 있다.
6. 후보가 발견된 경우에만 해당 구간을 추가로 촘촘하게 분석한다.
7. 제안된 프레임 개수는 초기 실험 목표이지 검증된 최적값이나 하드 제한이 아니다.

## 2. 현재 구현과 제안 설계의 경계

현재 저장소에는 다음과 같은 동영상 처리 요소가 이미 존재한다.

- `video_sampling.*`: 재생 시간 기반의 샘플 시간 계획.
- `video_fingerprint.*`: timestamp와 frame hash, mirror 특징, crop 특징, 저분산 프레임 필터 및 장면 변화 처리.
- `video_similarity`: DTW, scene bonus 및 dyadic-grid 정렬을 포함한 시간적 비교.
- `video-gpu-hash.{ko,en}.md`: 32×32 pHash의 CUDA batch 처리와 CPU fallback.
- `video-ssim-gpu.{ko,en}.md`: temporal MSSIM의 GPU 처리와 CPU fallback.

위 항목은 현재 코드와 구현 경로를 설명한다. 이 문서는 그 위에 놓이는 **목표 탐색 정책 및 판정 설계**다. 여기 적힌 길이별 프로파일, 구조 분류, 희소 샘플링 및 후보 라우팅이 이미 production에 구현되었다는 뜻은 아니다.

특히 Node E의 adaptive video decode planner 실험은 디코더의 sparse seek 정확성과 비용에 관한 별도 주제다. Node E는 production sparse seek를 채택하지 않고 순차 경로를 유지하는 것으로 종결되었다. 이 문서는 해당 결론을 변경하거나 random seek 도입을 승인하지 않는다.

## 3. 먼저 비교 대상 모집단을 분리한다

### 3.1 전역 파일 동일성

파일 바이트가 완전히 같은지는 영상 길이 그룹과 관계없이 파일 해시로 확인한다. 이것은 영상 디코딩이나 시각 지문 비교보다 먼저 수행할 수 있다.

### 3.2 전체 영상 중복 검색

전체 콘텐츠가 동일하거나 시작·끝의 광고, 인트로, 크레디트가 달라진 영상의 탐색은 재생 시간 그룹과 구조 특성이 비슷한 후보끼리 수행한다.

예를 들어 10초짜리 영상과 2시간 영화를 일반적인 **전체 영상 중복 후보**로 서로 비교하지 않는다. 길이가 크게 다른 쌍은 전체 중복 검색에서 제외하고, 사용자가 부분 클립 검색을 요청하거나 해당 기능이 별도로 활성화된 경우에만 다른 경로로 보낸다.

재생 시간 그룹은 후보를 줄이는 용도이며 장르 분류나 절대 배제의 근거가 아니다. 그룹 경계의 누락을 막기 위해 동일 그룹 및 인접 그룹을 후보로 고려하되, 실제 비교 전에는 재생 시간 비율과 구조 특징을 다시 확인한다.

\[
R = \frac{\min(T_A,T_B)}{\max(T_A,T_B)}
\]

`R`은 길이 차이를 나타내는 후보 필터다. 0.95, 0.80, 0.70 같은 경계는 초기 실험 가설로만 취급한다. 광고·인트로·엔딩의 삽입·삭제 허용 범위가 검증되기 전에는 production의 고정 임계값으로 사용하지 않는다. 길이 비율만으로 동일성을 확정하거나 배제하지 않는다.

### 3.3 부분 클립 검색

10~60초 숏폼이 2시간 영화의 특정 구간에서 추출되었는지 찾는 일은 전체 영상 중복 검색과 다른 문제다.

- 기본 전체 중복 검색에서는 극단적으로 길이가 다른 쌍을 제외한다.
- 부분 클립 검색은 별도 선택 기능과 별도 후보 색인을 사용한다.
- 부분 클립 검색은 긴 영상 전체에 걸친 시간축 구간 지문을 필요로 할 수 있지만, 모든 프레임의 스크린샷을 저장할 필요는 없다.
- 장편 대표 프레임 10~14개만으로 영화의 임의 위치에서 추출된 모든 짧은 클립을 놓치지 않고 찾을 수 있다고 가정하지 않는다.

## 4. 길이별 기본 분류 및 초기 프레임 예산

아래 그룹은 탐색 정책을 선택하기 위한 **재생 시간 cohort**다. 영상의 실제 종류는 인트로 반복성, 장면 전환 밀도, 본편·크레디트 구조 등 저비용 특징을 함께 보고 판단한다.

| 그룹 | 재생 시간 | 일반적인 예 | 대표 프레임 목표 |
|---|---:|---|---:|
| G1 | 15초 이하 | 매우 짧은 SNS 클립 | 4~6장 |
| G2 | 15초 초과~60초 | X/SNS 숏폼 | 6~10장 |
| G3 | 1~3분 | 짧은 클립 | 8~10장 |
| G4 | 3~10분 | 예고편·중단편·유튜브 영상 | 10~14장 |
| G5 | 10~25분 | 중간 길이 콘텐츠 | 9~13장 |
| G6 | 25~60분 | 드라마·TV 프로그램 가능성이 높은 영상 | 9~12장 |
| G7 | 60~150분 | 장편 영화 가능성이 높은 영상 | 10~14장 |
| G8 | 150분 초과 | 장편 영화·공연·긴 방송 | 12~16장 |

수치는 대표 프레임 지문을 보관하는 초기 목표다. 샘플 수를 채우기 위해 중복되거나 정보량이 낮은 프레임을 억지로 저장하지 않는다. 특징적인 장면이 적은 영상은 더 적게 저장할 수 있고, 컷이 매우 빠르거나 구조가 불명확한 경우에만 추가한다.

### 4.1 60초 이하 숏폼

- 시작부터 종료까지 전체 시간축을 비교한다. 영화식 엔딩 역방향 탐색은 기본적으로 사용하지 않는다.
- 시간축을 여러 구간으로 나누되, 일정 간격 프레임을 모두 저장하지 않는다.
- 장면 전환 및 화면 변화가 뚜렷한 대표 프레임을 선택하고, 이어지는 프레임의 순서와 시간 간격을 지문에 포함한다.
- 기본 목표는 6~10장이다. 단일 촬영·단일 장면이면 더 적을 수 있고, 컷이 매우 빠르면 더 필요할 수 있다.
- 1분짜리 영상은 전체 구간이 짧으므로 앞부분 몇 프레임만 비교하고 종료하지 않는다.

### 4.2 1~10분 중단편

- 시작·끝만 보지 않고 전체 구간을 분산해 확인한다.
- 6~8개 정도의 시간 구간을 저비용으로 관찰하고, 구간마다 대표 장면을 선택한다.
- 장면 전환이 적은 인터뷰·단일 촬영은 샘플을 줄인다.
- 예고편·빠른 몽타주·다중 클립 편집은 구간별 장면 다양성을 반영해 늘릴 수 있다.
- 기본 목표는 8~14장 범위이며, 영상 구조에 따라 조절한다.

### 4.3 10~25분 영상

- 전체 구간의 대표성을 유지한다. 시작·끝 집중도를 장편 영화만큼 높이지 않는다.
- 시작, 중간 여러 지점, 끝을 분산해서 선택한다.
- 기본 목표는 9~13장이다.
- 구조가 드라마형인지 단일 촬영인지에 따라 반복 인트로·아웃트로 가중치를 다르게 적용한다.

### 4.4 25~60분 드라마·TV형 영상

길이만으로 드라마라고 단정하지 않는다. 반복 오프닝, 타이틀, 회차 요약, 엔딩 크레디트가 탐지되면 episode-like 프로파일을 적용한다.

- 오프닝·요약·공통 타이틀·반복 크레디트는 여러 파일에서 반복될수록 식별 가중치를 낮춘다.
- 본편의 고유 장면을 가장 중요한 증거로 사용한다.
- 본편 시작, 전반, 중반, 후반, 엔딩 직전에서 대표 프레임을 고른다.
- 기본 목표는 9~12장이다.
- 다른 회차가 같은 오프닝·엔딩을 공유한다는 이유만으로 중복 판정하지 않는다.

### 4.5 60~150분 장편 영화

- 정방향 시작부 탐색과 역방향 종료부 탐색을 모두 사용한다.
- 본편 시작 예상 지점을 고정된 1분으로 가정하지 않는다.
- 본편 중간은 1~3개의 고유 장면으로 보강하되 모든 부분을 균일하게 촘촘히 저장하지 않는다.
- 엔딩 크레디트 직전의 마지막 본편 장면을 찾고, 인접한 본편 장면도 보조 증거로 선택한다.
- 130분 영화의 초기 저장 목표는 약 10~14장, 중심 목표 약 12장이다. 이 수치는 실측 최적값이 아니다.

### 4.6 150분 초과

장편 영화 프로파일을 유지하되 본편 중간의 시간 분포와 구조 복잡도에 따라 대표 프레임 예산을 12~16장 수준에서 시작한다. 길이가 늘었다고 이미지 수를 길이에 정비례시켜 늘리지 않는다.

## 5. 시작부: 인트로와 본편 시작을 지능적으로 찾는다

### 5.1 저비용 구조 탐색

처음부터 모든 후보 프레임을 영구 지문으로 만들지 않는다. 먼저 저해상도·비저장 관찰(probe)을 수행하며 다음 신호를 기록한다.

- 평균 밝기 및 어두운 픽셀 비율
- 색상 분포와 엔트로피
- 에지 밀도 및 화면 복잡도
- 급격한 화면 변화와 장면 전환 후보
- 페이드인·페이드아웃 같은 점진적 변화
- 한 화면 특성이 일정 시간 지속되는지 여부

시작 30초를 예로 들면 약 5초 간격 관찰을 시작점으로 사용할 수 있지만, 이 모든 관찰 프레임을 비교용 이미지로 저장하지 않는다. 인트로가 길거나 경계가 모호하면 관찰 위치를 추가하고 의심 구간만 좁혀 재검사한다.

### 5.2 본편 시작 추정

- 30초, 60초, 90초, 120초, 180초 등은 초기 탐색 기준점의 예이며 고정 규칙이 아니다.
- 화면이 어두워졌다가 정상 장면으로 전환되거나 장면 전환이 연속해서 나타나면 해당 구간을 본편 시작 후보로 삼는다.
- 단일 검은 프레임이나 단일 컷만으로 인트로 종료를 판정하지 않는다. 전환 뒤에도 일반 장면이 지속되는지 확인한다.
- 본편 시작이 추정되면 주변을 더 세밀하게 관찰하고, 식별력이 높은 프레임 1~2개를 선택한다.
- 동일한 배급사 로고·타이틀이 여러 파일에서 반복되면 낮은 가중치를 준다.

## 6. 종료부: 역방향으로 엔딩과 크레디트 경계를 탐색한다

장편에서는 마지막 프레임만 비교하지 않는다. 종료 시각에서 과거 방향으로 이동하면서 크레디트 구간과 본편 마지막 장면의 위치를 추정한다.

### 6.1 점진적 역방향 probe

종료 시각을 \(T\)라고 하면 다음은 초기 탐색 위치의 예다.

| 종료 시각으로부터 | 목적 |
|---:|---|
| 15초 전 | 최종 화면·암전·크레디트 확인 |
| 30초 전 | 종료 직전 구조 확인 |
| 1분 전 | 크레디트 및 추가 장면 확인 |
| 2분 전 | 크레디트 지속 여부 |
| 4분 전 | 본편 경계 후보 |
| 8분 전 | 본편 마지막 장면 후보 |
| 12분 전 | 긴 크레디트 대응 |
| 20분 전 | 크레디트가 매우 길거나 종료 편집이 다른 경우 |

이 위치는 검색 probe이며 모두 스크린샷으로 보관하는 위치가 아니다. 크레디트가 이미 확인되면 경계 후보 주변만 좁혀 검사한다. 반대로 본편이 아직 계속되면 더 과거로 확장한다.

### 6.2 크레디트와 본편 경계

크레디트 판단에 사용할 수 있는 신호는 다음과 같다.

- 화면 내 작은 텍스트의 밀도와 수직 이동
- 배경 영상의 유무와 움직임
- 장시간 유지되는 어두운 배경
- 본편에서 크레디트로 넘어가는 장면 전환
- 오디오가 있다면 음악·음성의 구간 변화

이 신호는 확률적 구조 단서다. 본편도 검은 화면이나 자막을 포함할 수 있고, 크레디트 중에도 영상·쿠키 장면이 나타날 수 있으므로 단일 신호만으로 구간을 확정하지 않는다.

크레디트로 분류된 구간은 이미지 대신 시작·끝 시각과 구간 특징을 저장한다. 크레디트 직전의 마지막 본편 장면과 필요하면 그 앞의 장면을 대표 프레임으로 남긴다. 크레디트 뒤의 쿠키 영상·후속 장면은 별도 구간으로 계속 탐색한다.

실제 디코딩은 역재생을 요구하지 않는다. 알고리즘은 역방향 시간 위치를 선택하고, 디코더는 지원되는 seek/decode 방식으로 프레임을 가져온 뒤 timestamp에 따라 역순으로 정렬할 수 있다. 이것은 decoder random-access 정확성의 검증이나 sparse-seek production 채택을 뜻하지 않는다.

## 7. 검은 화면·인트로·크레디트는 구조 지문으로 기록한다

이미지 정보량이 거의 없는 구간을 대표 프레임으로 반복 저장하지 않는다. 대신 다음과 같은 시간 구간 메타데이터를 남길 수 있다.

- 구간 시작·끝 시각 및 길이
- 완전 암전 또는 저밝기 구간 여부
- 로고·타이틀 후보
- 페이드인·페이드아웃 여부
- 장면 전환 위치
- 크레디트 후보 및 스크롤 특성
- 본편 시작·종료 추정 지점
- 크레디트 이후 별도 장면 유무

구조 지문은 후보 비교를 보조하고 추가 프레임을 어느 위치에서 뽑을지 결정하는 데 사용한다. 검은 화면 길이, 로고 또는 크레디트 구조가 비슷하다는 사실만으로 같은 영상이라고 판정하지 않는다.

## 8. 대표 프레임 특징: 공간 변형보다 시간 연속성을 우선한다

### 8.1 허용할 방향 변형

- 정상 방향 프레임을 기본으로 한다.
- 좌우 반전은 현실적인 변형으로 보고 보조 지문을 만든다.
- **상하 반전은 비교하지 않는다.**
- 사진과 같이 모든 방향을 조합해 다각도로 비교하지 않는다.
- crop은 기존 지문 경로와의 호환을 고려해 보조 특징으로만 사용한다. 기본 비교의 중심은 crop 조합 수가 아니라 프레임 순서와 연속성이다.

좌우 반전 지문은 동일하게 디코딩한 프레임에서 파생하므로 별도 스크린샷이나 별도 디코딩을 요구하지 않는 방향을 우선한다.

### 8.2 프레임별 특징

대표 프레임에서 전체 화면 pHash, 좌우 반전 pHash 및 필요한 보조 지역 특징을 만들 수 있다. 다만 한 프레임에서 파생한 여러 특징은 독립적인 일치 증거 여러 개로 중복 집계하지 않는다.

저분산·검은 화면·공통 로고·크레디트는 지문을 만들지 않거나 낮은 가중치를 사용한다. 식별력이 있는 본편 장면에 더 큰 가중치를 부여한다.

### 8.3 시간 연속성

주요 증거는 개별 프레임이 우연히 닮았는지가 아니라 다음 항목이다.

- 유사 프레임이 같은 시간 순서로 나타나는지
- 프레임 사이 시간 간격이 합리적으로 대응하는지
- 장면 전환과 움직임 변화가 연속적으로 대응하는지
- 일치 장면이 영상의 여러 시간대에 분포하는지
- 삽입 광고·인트로 변경·잘라내기 이후에도 순서가 유지되는지

## 9. 후보 간 시간축 정렬과 판정

두 영상에서 발견한 프레임 대응 쌍은 각자의 timestamp와 함께 기록한다. 대응 관계는 단조 증가해야 한다. 같은 장면이 여러 번 반복될 경우 하나의 프레임 일치만으로 선택하지 않고 주변 시퀀스와 함께 판별한다.

단순한 시작 오프셋은 다음 관계로 설명할 수 있다.

\[
t_B \approx a t_A + b
\]

- \(b\): 시작 시점 차이 또는 앞부분 광고·인트로 차이
- \(a\): 재생 속도·시간축 변화의 근사치

동일 속도 재인코딩본은 일반적으로 \(a\)가 1에 가깝다. 삽입·삭제된 구간이 있으면 전체를 하나의 선형 관계로 설명할 수 없으므로, 구간별 정렬 또는 DTW 계열의 단조 시퀀스 정렬을 사용한다.

한 프레임 불일치만으로 즉시 중단하지 않는다. 그러나 짧은 공통 로고나 우연히 유사한 장면만으로 전체 동일성을 인정해서도 안 된다. 일치 구간의 길이, 고유 장면의 정보량, 순서 일관성, 시간 분포 및 전체 콘텐츠 커버리지를 함께 평가한다.

반복되는 제작사 로고·프로그램 오프닝·회차 요약·크레디트는 여러 파일에서 자주 나타날수록 판별 가중치를 낮춘다. 드물게 나타나는 본편 장면은 더 높은 검색 가치를 갖는다.

## 10. 영상당 이미지 수와 실제 디코드 수를 구분한다

130분 영화의 대표 프레임 저장 목표는 약 10~14장(중심 목표 약 12장)이다. 이는 모든 탐색 probe 수나 실제 디코더가 처리한 프레임 수와 같지 않다.

다음 수치는 별도로 계측해야 한다.

- **Probe count**: 구조 경계·밝기·장면 전환을 알아보기 위해 저비용으로 관찰한 위치 수
- **Sampled frames**: 샘플 계획이 요청한 프레임 수
- **Kept/representative frames**: 유효성·중복 제거를 통과해 비교 지문으로 보관한 프레임 수
- **Decoded frames**: 실제 디코더가 성공적으로 출력한 프레임 수. 중간에 디코드했지만 버린 프레임도 포함한다.

현재 instrumentation의 `decodedFrames`, `sampledFrames`, `keptFrames` 의미를 유지한다. 대표 이미지 12장을 선택했다고 실제 디코드도 12프레임뿐이었다고 보고해서는 안 된다. 현재 sequential decode 경로는 희소한 timestamp만 요청해도 중간 프레임을 처리할 수 있다.

## 11. 후보 검색 흐름

1. 파일 전체 해시 및 기본 메타데이터를 확인한다.
2. 영상 길이 cohort를 결정하고 저비용 구조 probe를 수행한다.
3. 전체 중복 검색의 비교 가능 후보군을 만든다. 극단적으로 길이가 다른 영상은 부분 클립 경로와 분리한다.
4. 길이·구조에 맞는 희소 대표 프레임과 구조 지문을 만든다.
5. 희귀한 본편 특징에 높은 가중치를 주어 후보를 좁힌다.
6. 후보 쌍에서 프레임 대응과 시간 순서를 정렬한다.
7. 필요한 주변 구간만 추가 probe/frame을 추출한다.
8. 전체 영상 중복·편집된 동일 콘텐츠·부분 클립·유사 장면·판정 보류로 구분한다.

## 13. 검증 계획과 채택 조건

실제 최적 프레임 수와 임계값은 추정으로 확정하지 않는다. 길이 cohort별로 다음 시험 자료를 구성한다.

- 완전 동일 복사본과 재인코딩본
- 해상도·비트레이트·프레임률이 달라진 영상
- 좌우 반전본
- 화면 크롭, 자막, 워터마크가 추가된 영상
- 시작 광고·인트로·엔딩·크레디트 길이가 달라진 영상
- 앞뒤 잘라내기 및 중간 광고 삽입
- 같은 시리즈의 서로 다른 드라마 회차
- 같은 로고·음악·크레디트를 공유하는 별개 영상
- 장편에서 추출한 부분 숏폼
- 장면 전환이 빠른 예고편 및 다중 클립 편집본

각 cohort에서 후보 검색 재현율, 최종 precision/recall, 오탐·누락 사례, 평균/상위 프레임 수, probe 수, 실제 decodedFrames, 인덱스 크기 및 처리 시간을 기록한다. 6~10장·8~14장 등의 초기 목표와 더 촘촘한 기준선을 비교해 정확도 손실을 허용 가능한지 판정한다.

채택 순서는 다음과 같다.

1. 오프라인 평가용 데이터와 기준 결과를 준비한다.
2. 기존 production 경로와 제안 정책을 병렬 비교한다.
3. cohort별 정확도와 비용을 측정한다.
4. 실패 유형을 분석해 샘플 정책·가중치·시간 정렬을 보정한다.
5. 정확성 및 회귀 Gate를 통과한 범위만 production에 제안한다.

이 문서는 구현·측정 결과를 기록하지 않는다. 실제 채택 시에는 해당 구현 범위의 brief, build-history 및 worklog를 별도로 갱신해야 한다. 검색 판정 의미를 바꾸는 경우 engine version 및 캐시 호환성 영향도 따로 검토한다.

## 16. 2026-10-31 설계 보강 — Probe / Kept / Decoded 분리와 적응형 비교

이 절은 앞선 설계를 구현 가능한 계약으로 구체화한다. 이전 절과 해석이 충돌하면 이 절의 수량 분리, 본편 중심 가중, 적응형 추가 검증, decoder 경계를 우선한다.

### 16.1 세 가지 수량은 서로 다르다

| 수량 | 의미 | 보관 |
|---|---|---|
| Probe observation | 밝기·색상·화면 변화·전환 구조를 관찰한 시간 위치 | 보통 이미지로 저장하지 않음 |
| Kept representative frame | 비교 지문으로 남긴 식별력 있는 대표 프레임 | 저장 |
| Decoded frame | 디코더가 실제 출력한 프레임. 중간에 디코드한 뒤 버린 프레임 포함 | 계측 |

**대표 프레임 12장을 보관하는 것은 디코더가 12프레임만 처리했다는 뜻이 아니다.**

현재 make_sample_plan()은 3,840초 초과 영상에 32초 간격을 적용한다. 130분(7,800초) 영상은 종료 지점을 포함해 약 245개 timestamp를 요청한다. 그러나 VideoDecoder::framesAt()은 첫 target으로 한 번 seek하고 마지막 target까지 순차 디코드한다. 25fps CFR을 가정하면 약 195,000프레임 규모의 디코드가 발생할 수 있다. 이는 **산술 예시이지 실측값이 아니며**, 실제 값은 0.9.4.155의 decodedFrames로 확인한다.

따라서 새 설계의 첫 목표는 **보관 프레임과 비교량 감소**다. 실제 디코드량까지 줄었다고 주장하려면 별도 decoder 접근법이 정확성·성능 Gate를 통과해야 한다.

### 16.2 3단계 관찰

1. **Probe:** 가능한 한 한 번의 순차 스트림에서 평균 밝기/dark ratio, 저해상도 색상 변화, 에지 밀도, 장면 변화, fade, 저정보량 구간을 계산한다. Probe는 보관 이미지가 아니지만 현재 sequential decoder에서는 계산을 위해 중간 프레임이 실제로 디코드될 수 있다.
2. **Keep:** 구간 내에서 가장 식별력 높은 프레임만 보관한다. 같은 화면의 연속 프레임, 암전, 공통 로고/타이틀/크레디트는 일반 quota에서 제외하거나 가중치를 낮춘다.
3. **Refine:** 초기 후보가 애매할 때만 식별 정보가 부족한 본편 구간에 1~2개 프레임을 추가한다. 모든 영상에 균일하게 간격을 좁히지 않는다.

### 16.3 130분 영화의 초기 프레임 예산

| 역할 | Probe 계획 | 보관 목표 |
|---|---|---:|
| 오프닝 | 0~30초, 약 5초 간격(약 6회) | 1~2장 |
| 본편 시작 경계 | 30초~3분에서 30/45/60/90/120/180초 등을 시작점으로 적응 탐색 | 1~2장 |
| 본편 초반 | 본편 시작 후 고유 장면 | 1장 |
| 본편 중간 | 1~3개 분산 구간 | 2~3장 |
| 본편 후반/엔딩 직전 | 종료 시점에서 역방향으로 크레디트 경계 탐색 | 1~3장 |
| 종료/크레디트 | T-15초, T-30초, T-1/2/4/8/12/20분. 마지막 30초 관찰과 중복 제거 | 보통 0장 |

중심 목표는 약 12장, 초기 범위는 10~14장이다. 암전/크레디트가 길면 보관 수는 줄어든다. T-20분에서 무조건 멈추지 말고 크레디트가 계속되면 과거로 확장한다. 12장은 quota가 아니다.

### 16.4 길이별 운용

- 60초 이하: 첫 30초만 보지 않고 전체 구간을 약 5초 간격으로 관찰한 뒤 장면 변화에 따라 보완. 6~10장.
- 1~10분: 전체를 6~8개 관찰 구간으로 분할. 8~14장.
- 10~25분: 시작/중간/끝 분산. 9~13장.
- 25~60분: 반복 인트로·요약·크레디트 신호가 있을 때 episode-like 가중, 본편 중심. 9~12장.
- 60~150분: 10~14장.
- 150분 초과: 12~16장부터 구조 복잡도에 따라 조정.

길이 cohort는 후보·샘플 정책을 결정하는 축이며 장르 판정은 별도 구조 분석이다.

### 16.5 본편 중심 후보 필터와 가중

introInterval, mainContentInterval, creditsInterval, postCreditsInterval을 구분한다. 본편 경계를 신뢰성 있게 찾지 못하면 전체 duration을 본편 duration인 것처럼 취급하지 않고 경계 불확실성을 점수에 반영한다.

전체 길이 비율 R_total은 거친 후보 필터다. 본편 경계가 유효하면 R_core=min(coreA,coreB)/max(coreA,coreB)를 후보 ranking에 보조 사용한다. 둘 다 검증 전 고정 임계값으로 쓰지 않는다.

라이브러리에서 자주 등장하는 제작사/방송사 로고, 프로그램 오프닝, 회차 요약, 크레디트는 낮은 가중치를 준다. 드물고 본편에 속한 장면은 높은 가중치를 준다. 장편은 opening+ending만 맞아서는 승인하지 않고, 서로 떨어진 본편 구간에도 독립 증거가 있어야 한다.

### 16.6 시간 연속성 및 적응형 종료

후보 대응 timestamp는 단조 증가해야 한다. 먼저 affine offset/scale을 확인하고, 삽입/삭제 구간이 있으면 piecewise monotonic alignment 또는 DTW를 사용한다. 프레임 점수뿐 아니라 시간 간격, 본편 coverage, 고유 장면 수, 일치가 오프닝/크레디트에 편중되는지 함께 평가한다.

후보가 명확해지면 중단한다. 공통 인트로만 일치하거나 점수 차이가 작으면 본편 구간에서만 1~2장씩 보강한다. 예산 내에서도 판정이 안정되지 않으면 Uncertain으로 남기며 무한히 추출하지 않는다.

### 16.7 Node E / decoder 경계

Node E는 exactness 문제로 production sparse seek를 채택하지 않았고 ExactnessPolicy::RefuseAll을 유지한다. 역방향 timestamp 선택은 역재생 디코드나 random seek 정확성 보장이 아니다.

- 첫 prototype은 현행 sequential decoder를 기준으로 한다.
- timestamp 주변 seek, keyframe jump, window decode는 별도 prototype/계측 경로에서만 시험한다.
- Probe/Kept 수 감소를 decodedFrames 감소로 표현하지 않는다.
- 실제 decoder 절감 주장은 decodedFrames, sampledFrames, keptFrames, seek/landing, decode time, end-to-end time이 모두 확인될 때만 허용한다.
- production random access는 별도 codec/profile/exactness/fallback Gate와 명시적 로드맵 변경 전까지 금지다.

### 16.8 Cache / Engine 버전 경계

초기 단계는 scratch 결과로 검증한다. 대표 프레임·interval payload 및 verdict semantics가 확정되기 전에는 cache format, DB schema, engine version을 올리지 않는다. production 판정 의미가 실제 변경될 때에만 재생성/재검증 및 호환성 비용을 분석한다.

### 16.9 연구 참고

- IEEE Access 2026, A Review of Partial Video Copy Detection: Technical Advances, Evaluation Frameworks, and Future Trends, DOI 10.1109/ACCESS.2026.3707321: whole-video near-duplicate와 partial-copy localization의 목적을 구분하고, keyframe retrieval 후 temporal consistency/sequence alignment로 검증하는 coarse-to-fine 구조를 정리한다.
- Luo et al., IEEE TPAMI 2025, FiGVCL: Fine-Grained Benchmark and Method for Video Copy Localization, DOI 10.1109/TPAMI.2025.3595625: 부분 복사 구간의 temporal correspondence를 보존하는 평가·localization을 다룬다.

참고 연구는 설계·평가 근거일 뿐, deep model·데이터셋·외부 의존성 도입을 승인하지 않는다.

## 17. GUI 설정 — 동영상 탭과 사용자 조정 프로파일

> **설계 상태: PROPOSED / NOT IMPLEMENTED / NOT VALIDATED.** 아래 항목은 V Workstream에 추가할 GUI 설정 계약이다. 현재 GUI에 동영상 탭이 구현되어 있다는 뜻은 아니다.

### 17.1 설정 화면 구조

설정 대화상자에 **[동영상] 탭**을 추가한다. 기본 선택은 **자동(권장)**이며, 기존 내부 G1~G8 duration cohort 및 구조 판정을 그대로 사용한다. 자동 모드에서는 파일마다 길이·장면 변화·인트로/크레디트 구조를 보고 샘플링 정책을 선택한다. 사용자가 파일을 숏폼/영화로 강제 분류하는 방식이 기본이 되어서는 안 된다.

**사용자 지정**을 선택하면 프로파일별 세부 값을 편집할 수 있다. UI에서는 이해하기 쉬운 3개 그룹(숏폼 / 중간 길이 / 롱폼)으로 보여주되, 내부에서는 기존 세부 duration cohort를 유지한다.

### 17.2 권장 기본값과 편집 항목

| GUI 프로파일 / 설정 | 권장 기본값 | 적용 범위 및 의미 |
|---|---:|---|
| 숏폼(최대 60초) — 전체 구간 프레임 확인 간격 | **5초** | 시작부터 끝까지 전체 시간축의 Probe 위치 간격. 장면 전환 이벤트는 추가 관찰할 수 있다. |
| 숏폼 — 대표 프레임 목표 | 자동: G1 **5장**(4~6장), G2 **8장**(6~10장) | 사용자 지정은 해당 cohort의 제안 범위 내에서 정수 목표를 선택한다. 중복·저정보량 프레임은 제외한다. |
| 중간 길이(60초 초과~25분) — 비교 정책 | 자동(권장) | 1~10분은 전체 6~8 관찰 구간, 10~25분은 시작·중간·끝 분산 정책을 유지한다. 일률적 고정 간격보다 구조 기반 관찰을 우선한다. |

| 롱폼 — 본편 기본 anchor 수 | 자동, **1~3개 분산 구간** | 전체 길이에 비례해 모든 구간을 균일하게 늘리지 않는다. 서로 떨어진 본편 구간의 독립 증거를 확보한다. |

Custom 대표 프레임 목표는 cohort별 표의 권장 중심값을 기본으로 하며, 사용자가 해당 cohort의 제안 범위 내에서 정수 목표를 조정할 수 있다. 이 값은 **soft target**이지 quota가 아니다. 실제 보관 수는 중복·정보량에 따라 더 적을 수 있고, 모호한 후보에서만 별도 추가 보강 예산을 사용한다. 위 중심값은 초기 UI 권장값이며 실측 최적값이 아니다.

사용자 지정 간격은 양의 초 단위 값으로 입력하며, 초기 UI 제안 범위는 **1~60초**다. 최종 입력 상한·총 Probe 예산은 실제 데이터의 처리량/정확도 측정으로 확정한다. 간격을 촘촘하게 설정하더라도 파일당 Probe 수와 대표 프레임 수에는 별도 상한/예산이 있어야 하며, 무제한 확장은 허용하지 않는다.

### 17.3 권장 기본 프로파일의 핵심 해석

- **숏폼:** 예를 들어 1분 영상에서 5초 간격은 전체 시간축의 약 12개 기본 관찰 위치를 뜻한다. 이는 12장을 모두 보관한다는 뜻이 아니며, 최종 대표 프레임은 보통 6~10장 목표에서 정보량과 중복도를 보고 고른다.
- **롱폼:** 영화 전체를 5초 또는 3초 간격으로 균일하게 샘플링하지 않는다. 시작부/본편 경계/종료부를 먼저 적응적으로 찾고, 본편 중간 anchor를 분산 배치한다. 5초→3초 사용자 설정은 자동 선택된 **국소 상세 탐색 창**에만 적용한다.
- **정밀도와 비용:** 간격을 짧게 하면 Probe/후보 위치 및 특징 계산량이 증가할 수 있다. 대표 프레임 목표를 올리면 fingerprint/비교/캐시 비용이 증가할 수 있다. 정확도 개선을 보장하거나 추출량에 정비례한 정확도 상승을 약속하지 않는다.
- 자동 모드는 모든 기존 G1~G8 cohort를 보존한다. 60초~25분 구간을 숏폼 또는 롱폼 어느 한쪽으로 강제 합치지 않는다. 25~60분 콘텐츠는 반복 오프닝/요약/크레디트 구조가 탐지될 때만 episode-like 가중치를 적용한다.

### 17.4 설정 저장과 실행 수명주기

1. 설정 대화상자의 자동/사용자 지정 및 프로파일 값은 기존 사용자 설정 저장 계층을 사용한다. 새 설정 파일·DB·schema를 성급히 추가하지 않는다.
2. 검색 시작 시 유효 설정을 **run snapshot**으로 고정한다. 검색 중 UI 값 변경은 현재 실행에 소급 적용하지 않고 다음 검색부터 적용한다.
3. 샘플 간격/대표 프레임 예산처럼 fingerprint 결과를 바꾸는 설정은 비교 판정만 바꾸는 threshold 설정과 구분한다. 전자는 video fingerprint cache의 재사용 적합성에 영향을 주므로 정책 ID/hash 또는 동등한 cache-freshness 검사가 필요하다.
4. 설정 변경으로 기존 캐시를 조용히 새 결과와 혼합하지 않는다. 기존 결과 보존, stale 표시, 명시적 재생성/재검증 경로를 설계하고 실제 migration 필요성은 구현 전 현재 cache contract를 확인한다.
5. 초기 구현만을 위해 engine version, cache format, DB schema를 올리지 않는다. 저장 payload 또는 production verdict semantics가 실제 변경되고 호환성 근거가 생겼을 때 별도 Gate로 결정한다.

### 17.5 UI 용어와 정직한 계측

사용자에게 보이는 레이블은 **프레임 확인 간격**으로 하고, 도움말에 “비교 후보 시간 위치(Probe)의 간격이며, 실제 보관 프레임 수나 디코더 출력 프레임 수를 뜻하지 않습니다”라고 명시한다.

현행 VideoDecoder::framesAt()의 단일 seek 후 순차 디코드 경로에서는 timestamp 요청 간격을 줄여도 중간 프레임 decode가 그대로 발생할 수 있다. 따라서 5초에서 3초로 바꾼 사실만으로 실제 디코드 프레임이나 전체 실행 시간이 줄었다고 표시해서는 안 된다. run telemetry는 적용된 프로파일/간격, probeCount, sampledFrames, keptFrames, decodedFrames, fingerprint/compare 시간과 최종 판정 근거를 각각 기록한다.

### 17.6 GUI 설정 Acceptance Gate

- 설정 창에 동영상 탭이 있고 첫 실행 기본값이 자동(권장)인지 확인한다.
- 자동 모드가 G1~G8의 duration/구조 정책을 그대로 사용하고, 사용자 파일 유형 강제 지정 없이 경계 cohort를 올바르게 처리하는지 확인한다.
- 사용자 지정 5초→3초 변경의 실제 적용 범위가 숏폼 전체 구간 또는 롱폼의 선택된 국소 상세 창으로 제한되는지 검증한다.
- 설정 저장/재시작 round-trip, 잘못된 값 거부·상한 적용, 현재 검색 중 변경 미적용/다음 검색 반영을 검증한다.
- 프로파일 변경 후 기존 video fingerprint cache가 잘못 재사용되거나 서로 다른 정책의 결과가 혼합되지 않는지 검증한다.
- 간격/프레임 예산별 candidate recall, precision/recall, probe/kept/decoded 수, fingerprint/compare/end-to-end 시간을 실제 숏폼·드라마·영화 데이터셋으로 비교한다.
- UI가 decoder savings를 주장하지 않으며 CPU/GPU/fallback 모두 같은 판정 의미를 유지하는지 검증한다.

이 GUI 범위는 V의 알고리즘/정확도 Gate를 통과한 정책만 노출한다. 현재 상태는 설계 제안이며, 구현·수동 GUI acceptance·성능 수치는 아직 없다.
