## 1. 변경 필요성

GUI 에서 "검색 업데이트" 를 누르면 `검색 오류` 다이얼로그가 떴다.

```
No mapping for the Unicode character exists in the target multi-byte code page.
```

`%TEMP%\msf_scan.log` 에 실패가 기록되었다. 대상은 `G:\Downloads\ss_twit`
(272,714 항목, 한국어·일본어 파일명 다수) 였고, **시작 1초 만에 `lastPath` 없이
실패**했다. 같은 폴더가 9월 25~26일에는 정상 스캔됐고 9월 28일부터 매번 실패했다.

**"검색 엔진 개발 중"이라서 나는 문제가 아니다. 제품 코드 버그다.**

## 2. 기존 구조

다이얼로그 본문은 `ScanWorker::run()` 의 `catch (const std::exception&)` 가 잡은
`e.what()` 이다(`gui/mainwindow.cpp:566-571`). 즉 엔진 스캔에서 C++ 예외가
탈출했다는 뜻이다.

메시지는 **MSVC 표준 라이브러리**가 던진다. Qt6 DLL, MSVC 헤더, System32/SysWOW64
DLL 6,240개를 전수 검색했으나 이 문자열은 **어느 바이너리에도 존재하지 않는다.**
직접 프로브로 확정한 결과는 다음과 같다.

```cpp
std::filesystem::u8path(유효한 UTF-8)       → ok
std::filesystem::u8path(CP949 바이트)      → THROW: No mapping ...
std::filesystem::u8path(단절된 UTF-8)      → THROW
std::filesystem::path(UTF-8 한국어 narrow) → THREW (같은 메시지)
```

`fs::u8path()` 와 narrow `fs::path(string)` 생성자는 입력을 UTF-8 이 아니라
**ANSI 코드 페이지(949)** 로 해석하므로, 비ASCII 이름에서 던진다.

## 3. 변경 구조

### 원인

`src/dataset_fingerprint.cpp:118` 의 `canonicalRelativePath()` 가 문제였다.

```cpp
// before
fs::path rel = fs::relative(fs::path(file), fs::path(root), ec);
// after
fs::path rel = fs::relative(path_from_utf8(file), path_from_utf8(root), ec);
```

`file` 과 `root` 는 제품 규약상 UTF-8 문자열이다. narrow `fs::path(string)` 으로
만들면 ACP 로 재해석되어 비ASCII 이름에서 던진다. 이 함수는 S6 측정 게이트용
dataset fingerprint(D8a/D8b) 에서 들어왔고, `engine.scan()` 시작 단계
(telemetry 설정, 파일 처리 전)에서 매번 호출된다. 그래서 "1초 만에, 파일 처리
없이" 실패했다.

시점도 일치한다. dataset fingerprint 가 9월 26~28일경 들어오기 전에는 같은 폴더가
정상 스캔됐고, 들어온 뒤부터 비ASCII 폴더 스캔이 전부 실패했다.

### 동일 패턴 전수 조사

제품 소스 전체에서 `fs::path(narrow string)` 생성을 조사했다.

| 위치 | 판정 |
|---|---|
| `dataset_fingerprint.cpp:118` | **수정** (유일한 위험 지점) |
| `monitor.cpp:129,130,240` | 안전 (`fs::path("..")`, `fs::path(".")` ASCII 리터럴) |
| `monitor.cpp:226` | 안전 (`std::wstring` wide 생성) |
| 나머지 `path_from_utf8` 경유 | 안전 (명시적 UTF-8) |

### 제외한 후보들 (검증으로 배제)

- Qt6 `QString::toStdString()` / `fromStdString()` 은 UTF-8 기반임을 헤더와
  프로브로 확인. `toLocal8Bit()` 은 조용히 `?` 로 대체할 뿐 던지지 않음
- `path_from_utf8` (`fs::u8path`) 경유 경로는 전부 유효 UTF-8 을 받음
- `Scanner().count/scan`, `MediaPipeline.image/imageBatch`, `db_.upsert`,
  `compareFingerprint`, GPU getter, `detectCpuModel`, `ProfileStore` 는
  단계별 프로브로 전부 정상 확인
- DB 인덱스의 손상 경로는 읽기 전용 검사기로 전수 조사해 없음 확인

## 4. 해결된 상황

- 비ASCII 1개 파일 스캔: `exit=-1073740791` (0xC0000409, 무출력) →
  `exit=0, analyzed=1`
- 한국어·일본어·악상트·ASCII 4개 혼합: `scanned=4 analyzed=4 candidates=6 groups=6`
- CLI 무출력 크래시와 GUI `검색 오류` 다이얼로그는 같은 예외의 두 얼굴이었다.
  CLI `runHeadlessScan` 에는 `catch` 가 없어 terminate → abort → fail-fast 로
  죽었고, GUI 는 `ScanWorker` 가 잡아 다이얼로그로 보여줬다.

## 6. 향후 영향

- 스캔 시작 단계의 dataset fingerprint 가 비ASCII 폴더에서도 동작한다.
  `G:\Downloads\ss_twit` (272k 항목) 의 전체 스캔은 규모가 커서 이번 빌드에서
  끝까지 실행하지 않았고, 단일·소규모 비ASCII 재현으로 검증했다.
- narrow `fs::path(string)` 생성은 제품에서 금지 패턴이다. UTF-8 문자열은
  반드시 `path_from_utf8()` 으로 만든다. 이번에 전수 조사로 다른 사례는 없음을
  확인했다.
- `image_decoder.cpp:161` 의 `std::mbstowcs` (C locale 의존, XMP `VT_LPSTR` 경로)
  와 `mainwindow.cpp` 의 ffprobe용 `toLocal8Bit`/`fromLocal8Bit` 은 ACP 의존이
  남아 있으나 이번 실패 경로가 아니므로 손대지 않았다. 별도 과제로 남긴다.
