# 0.9.2.27 — Video Fingerprint Persistent Cache Hardening


## Important Change
이번 버전은 영상 fingerprint 자체의 유사도 알고리즘을 변경하지 않고, **영속 video fingerprint cache의 신뢰성·재사용 효율·동시 접근 안정성**을 강화한다.

## Why the Change Was Needed
0.9.2.26까지 persistent video cache는 path + size + modified와 payload 크기 검증으로 캐시 유효성을 판단했다. payload 구조가 바뀌면 크기 불일치로 무효화할 수 있지만, **fingerprint 알고리즘의 의미가 바뀌었는데 payload 형식과 크기는 동일한 경우**에는 오래된 fingerprint가 조용히 재사용될 가능성이 있었다. 또한 cache DB는 매 load/save마다 SQLite statement를 prepare/finalize하고 있어 반복적인 영상 분석/Monitor 환경에서 불필요한 DB 작업이 발생했다.

## Previous Structure
- SQLite cache table에 path/size/modified/payload 저장
- payload 크기로 mirror/crop 확장 형식 검증
- load/save 때마다 SQL statement 생성 및 종료
- SQLite 기본 설정 사용

## Design Change
### 1. Cache Format/Version Discriminator
`cache_version` 컬럼을 추가하고 현재 cache format을 버전 `3`으로 정의했다. 기존 cache에는 version이 없으므로 자동으로 컬럼을 추가하며, 현재 버전과 일치하지 않는 기존 row는 삭제한다. 따라서 알고리즘/캐시 의미가 변경될 때 payload 크기만으로 판단하지 않고 명시적인 버전으로 무효화할 수 있다.

### 2. Prepared Statement Reuse
engine 수명 동안 load/save statement를 준비하고 재사용한다. 각 사용 전에 `sqlite3_reset()`과 `sqlite3_clear_bindings()`를 수행해 이전 바인딩 상태가 다음 요청으로 누출되지 않도록 한다. close 시 statement를 먼저 finalize한다.

### 3. SQLite Operational Settings
cache DB에 `busy_timeout=5000`, WAL, `synchronous=NORMAL`, `temp_store=MEMORY`를 적용했다. 이는 Resident Monitor에서 반복적인 cache 접근이 발생하는 상황을 고려한 것이다.

## Resolved
- fingerprint 의미가 바뀌어도 cache version 증가만으로 오래된 결과를 명시적으로 폐기할 수 있다.
- 반복적인 cache load/save에서 prepare/finalize 비용을 줄였다.
- SQLite lock 상황에서 즉시 실패하기보다 제한된 시간 동안 대기할 수 있다.
- WAL을 통해 cache DB의 resident 접근 패턴에 맞는 동작 기반을 마련했다.
- 기존 `VideoFingerprint`, mirror, crop, temporal similarity 알고리즘과 최종 유사도 판정은 변경하지 않았다.

## Scope
이번 변경은 persistent video fingerprint cache 계층에 한정된다. CandidateIndex, SimilarityEngine, Mirror/Crop semantics, Monitor Load Protection 정책은 변경하지 않는다.

## Future Impact
향후 fingerprint 알고리즘이나 payload 의미가 바뀌는 경우 **cache format version을 반드시 증가**시키는 것을 규칙으로 한다. 이를 통해 알고리즘 변경 후 구버전 fingerprint가 조용히 재사용되는 문제를 방지한다.
