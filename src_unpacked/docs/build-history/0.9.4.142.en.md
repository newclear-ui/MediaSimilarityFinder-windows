# MediaSimilarityFinder v0.9.4.142 — Freeze the loaded view during a scan (apply once on completion; no thumbnail rebuild churn)

Baseline `0.9.4.141` → this build `0.9.4.142`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged (display only).

## 1. Why

- Field checks (S-1 retest): after Load populated the list and previews, starting a scan meant:
  - pages visited before the scan kept their thumbnails,
  - pages scrolled to **after the scan started never filled**,
  - selecting a group during the scan showed **only the representative** image in the right file list.
- As the user observed, thumbnail filling appears to stop when the scan starts.
- Cause: while scanning, every quick-load/streamed batch made `refreshStreaming()` rebuild the list and file panes; the newly created rows' thumbnail requests queued behind the busy backend, leaving placeholders. At the 9,070-group scale the rebuild churn itself was significant.

## 2. Previous structure

- `refreshStreaming()` ran `rebuildGroups()` + `refreshGroupList()` + `refreshFileViews()` on every data change (`groupsDirty_`/`matchSeq_`), including during scans.
- New rows created while the backend scanned could not get their thumbnails, so scrolled-in pages stayed blank.

## 3. New structure

- New `holdViewDuringScan_`: when a scan starts **while a result set is on screen** (`!groups_.isEmpty()`), the view is frozen until the scan ends.
  - `refreshStreaming()` then skips rebuilds/refills, applies only cached thumbnails to visible rows (`thumbCatchUpVisible`) and updates the status counts.
  - Data still accumulates in the maps (quick-load/live); `onResults()` applies it **once** to the list/selection/preview.
  - The flag clears in `onResults`, `scanFinished` and `scanFailed`.
- `beginScan` logs `viewHold=1/0` to `msf_scan.log` for field diagnosis.
- The 0.9.4.141 rules stay: keep selection/preview, reset match accumulators at start, and invalidate thumbnails/metadata only when `analyzed>0`.

## 4. Result

- Starting a scan no longer churns the loaded list, selection or preview.
- Cached pages scrolled during the scan appear immediately.
- Completion applies the new result once; changed content refreshes the visible thumbnails.

## 5. Verification


- `ui_scroll_regression_test` (checks=100): Load -> select -> unchanged rescan keeps the selection/group thumbnails/file preview, with the existing scroll/catch-up checks.
- `backend_e2e_test` (checks=86): the same scenario through the real IPC backend (Test 1f).
- Field check: on the large dataset, pages scrolled during a scan appear immediately when cached and refresh after completion.

## 6. Impact and limits

- Display only (verdicts, storage, protocol, engine/DB/schema/cache unchanged).
- **Pages first seen during a scan** still need the backend to generate their thumbnails. While the scan uses the disk, generation can be slow; those fill after completion (cached pages are immediate). Backend thumbnail priority/prefetch is a follow-up candidate.
- A first scan with no result set on screen still streams live as before (not frozen).
