# MediaSimilarityFinder v0.9.4.46 — DEFECT-A / DEFECT-B fix

Baseline `0.9.4.45` / `619f74a` -> this build `0.9.4.46`.
Bumped only from a verified state. CPU CTest **103/103**, GPU CTest **104/104**
(previous 102/103 plus one new test). Engine verdict version stays `1.5.0`,
benchmark schema stays `9`, video cache stays `9`. Only the DB schema moves
`1.0.3` -> `1.0.4` (additive column, old code still reads it).

## 1. Why the change was needed

The `0.9.4.45` Search / Index / Comparison acceptance audit registered two
reproducible product defects on a real dataset scan. The originating file was
`images/format/tiff/ycbcr_lzw_bt709.tif`, but the cause is not that file's
format. It is the **absence of a product state model for analysis failure**.

Observed before the fix:
```
run1: scanned=1 added=1     analyzed=0   no stderr/stdout output, exit=0
run2: scanned=1 modified=1 analyzed=0
run3: scanned=1 modified=1 analyzed=0   <- repeats forever
```

## 2. Previous structure

`processOne()` inside `MediaSearchEngine::scan()` owned the per-file state
transition.

- **Decision**: `changed = (new) || size/modified/quickHash mismatch || fingerprint==0 || (video && videoRegrid)`
- **Counters**: immediately after `if(!changed){ ++unchanged; return; }`,
  `if(new) ++added; else ++modified;` — counted at **intent**, before analysis
- **Skeleton row**: a `fingerprint=0` row is written by `db_.upsert()` before
  analysis, deliberately, so an interrupted walk keeps its file list
- **Analysis outcome**: `processImageBatch()` / `processVideoRange()` write the
  fingerprint, upsert, and `++analyzed` only under `if(ok)`

So `fingerprint==0` was expressing two different situations at once —
"analysis not completed (retry)" and "analysis failed (do not retry)" — and no
field distinguished them.

## 3. New structure

### Common cause (DEFECT-A and DEFECT-B are two symptoms of one missing state)

- **DEFECT-A**: `added`/`modified` were counted before analysis, so a file with
  no fingerprint at all was reported as successfully indexed. The skeleton row
  stayed in `files`, yet the file cannot take part in search (fingerprint 0).
  No warning, no error, exit 0.
- **DEFECT-B**: `fingerprint==0` made `changed` unconditionally true, so a failed
  file was re-queued on every scan and reported as `modified=1` forever. No
  reanalysis actually happened (`analyzed=0`), so the state never converged.

-> **Fixed as one state transition.**

### New state: `analysis_failed`

`files.analysis_failed INTEGER NOT NULL DEFAULT 0`, added through the existing
additive-column migration path.

| fingerprint | analysis_failed | meaning | retry |
|---|---|---|---|
| != 0 | 0 | analysis completed | not needed |
| 0 | 0 | analysis not completed (skeleton: cancel/crash/not reached) | **needed** |
| 0 | 1 | analysis attempted and produced no fingerprint | **not needed** while content is unchanged |

### Decision change

```cpp
// before
changed = (... || it->second.fingerprint==0 || ...);
// after
const bool pendingAnalysis = (it!=oldByPath.end() && it->second.fingerprint==0 && !it->second.analysisFailed);
changed = (... || pendingAnalysis || ...);
```

### Counters moved to outcome time

`added`/`modified` now increment only when analysis succeeds and a fingerprint is
actually recorded. A new `failed` counter increments only when analysis was
attempted and failed.

### Failure state persisted

On failure the skeleton row is kept with `analysisFailed=true`, so the next scan
recognises a settled failure for identical content and does not re-queue it.

### Visibility

- CLI `--scan`: adds `failed=` to the result line and prints a stderr warning
- GUI completion message: appends `, N could not be analyzed` conditionally
- telemetry `pending`: now `scanned - analyzed - failed`, so failed files are not
  misread as outstanding work
- benchmark journal: additive `summary.failed` (absent in old journals, reads 0)

## 4. Resolved situation

```
after the fix (the real file alone, CPU and GPU identical):
run1: scanned=1 added=0 modified=0 unchanged=0 analyzed=0 failed=1
run2: scanned=1 added=0 modified=0 unchanged=1 analyzed=0 failed=0
run3: identical to run2  <- converged
```

- A failed file is no longer reported as `added`/`modified`
- The `modified` infinite repetition is gone
- The failed file still has no fingerprint and therefore still takes no part in
  search or comparison (that part was already correct and is preserved)
- If the file genuinely becomes readable (content changes) it is re-analyzed

## 5. Verification

### Regression gate (does the new test actually catch the defect?)

With `&& !analysisFailed` removed from the `pendingAnalysis` decision so the
DEFECT-B behaviour is restored, the new test **exits 1**: `scan2 unchanged=2`,
`scan2 no new failure is invented`, and `normal file converges` all FAIL. After
restoring, all pass.

> Learned while measuring: `Copy-Item` preserves the source `LastWriteTime`, so
> make skips recompilation. After restoring a source file its mtime must be
> raised to force a rebuild.

### New regression test `analysis_failure_state_test` (28 checks, PASS on CPU and GPU)

It drives the **production path** `MediaSearchEngine::openIndexForRoot()` +
`scan()`. It does not disable the GPU and does not depend on a helper-only path.

Fixtures are generated deterministically with no external file:
- `good.bmp` — a valid 8x8 24-bit BMP
- `broken.bmp` — a structurally valid BMP header declaring 64x64 pixels with no
  pixel data whatsoever, so `GetFrame(0)` cannot yield a frame and decoding
  fails by construction

Whether the real TIFF is strictly required was judged first: it is **not**. The
defect is a state transition, not a format, so a deterministic fixture
reproduces it. Nothing hardcodes a file name or a TIFF subtype.

Verified invariants:
- A failure is never reported as a successful `added` or `modified`
- A failed file does not repeat as `modified + analyzed=0` on the next scan
- The third and fourth scans report identical state, with identical
  candidate/group results
- A normal file keeps its existing rescan convergence semantics (`unchanged`, no
  reanalysis)
- The **accounting identity** `scanned == added + modified + unchanged + failed`
  holds on every scan
- Failed file `fingerprint==0` with `analysis_failed==1`; analyzed file
  `fingerprint!=0` with `analysis_failed==0`
- Changing the content re-analyzes and recovers the file

Persisted state is read with the same read-only direct sqlite3 pattern as
`video_cache_test`, so no test-only accessor was added to a product class.

### Real dataset reproduction path (measured after the fix)

Fresh index, 14 files in `images/format/tiff`:

`candidates=3 groups=3` is **preserved exactly**, which is the measured proof
that Search/Index/Comparison verdict semantics are unchanged. `added` moving
14->13 plus the new `failed=1` is the intended change.

Full dataset, 694 files:
```

GPU run1: scanned=694 unchanged=693 analyzed=0 failed=1 candidates=174 groups=169  <- identical
CPU run2: scanned=694 unchanged=694 analyzed=0 failed=0 candidates=174 groups=169
CPU run3: identical to run2  <- converged
```
The file that repeated as `modified=1` during acceptance is now reported once as
`failed=1` and then settles. `candidates=174 groups=169` matches the pre-fix
baseline.

## 6. Future impact

- **DB `1.0.4`**: adds `files.analysis_failed`. An existing index without the
  column is migrated automatically, and old code ignores the new column, so an
  index produced by a previous build is still readable. Note that such an index
  carries no failure marking, so DEFECT-B can appear once more (the first scan
  reports `modified`, then it settles as `failed`).
- **Engine verdict version unchanged**: for normal files the meaning of
  `added`/`modified`/`analyzed`/`fingerprint`/`groups` is exactly as before. Only
  the accounting for failed files was corrected, so `kEngineVersion` was not
  raised.
- **Unsupported-extension transparency is still unresolved** (12 `.ico` files are
  silently skipped). It is outside this build's scope and stays a separate task.
- **Next gate**: S4 GUI Detailed Logs final functional acceptance, which requires
  a real screen.
- `color_thumb` R1, XMP coverage validation, and the S5 benchmark are **not**
  included in this build and remain the following tasks.
