# MediaSimilarityFinder v0.9.4.87 — remove the backend shell-thumbnail path (IThumbnailCache crash fix)

Baseline `0.9.4.86` -> this build `0.9.4.87`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.5` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — all unchanged. No verdict/schema/decode semantic change.

## 1. Why it was needed

User report: during a large scan (`G:\Downloads\ss_twit`) the **backend crashed
repeatedly** (`backend process exited unexpectedly — scan aborted`, exit code
62097 / -1073741819) and re-crashed 2-3 s after every restart with the same signature.

Dump + event log pinned the cause:
- A dump (`%LOCALAPPDATA%\CrashDumps\MediaSimilarityFinderBackend.exe.*.dmp`)
  symbolized with the 0.9.4.86 PDB shows **`0xC0000005`** with the fault IP in an
  **unloaded shell DLL** (`Windows.FileExplorer.Common.dll+0x2395e`); the crash
  thread's stack is full of addresses of that unloaded module plus `combase`/registry
  frames -> **code from a shell module was executing when the module was unloaded**
  (`FAILURE_BUCKET ... INVALID_POINTER_EXECUTE`).
- Event Viewer ID 1000: faulting module is each time an **unloaded shell/URL DLL**
  (`Windows.FileExplorer.Common.dll_unloaded`, `urlmon.dll_unloaded`, `ntdll`), all `0xc0000005`.
- The backend's only shell use is `ThumbnailStore::shellArt` (`src/thumbnail_store.cpp`):
  `SHCreateItemFromParsingName` + `CoCreateInstance(CLSID_ThumbnailCache)` = the
  **Windows shell thumbnail cache (`IThumbnailCache`)**, which loads exactly those shell DLLs.
- It is called when the disk cache misses and the engine has no in-memory art ->
  **many calls while the user views groups/thumbnails during the scan**.

## 2. Previous structure

`ThumbnailStore::fetch` order:
disk cache -> engine art -> **shellArt (shell IThumbnailCache)** -> WIC (images) / FFmpeg (videos).

## 3. Change

- **`shellArt` removed.** `fetch` order: disk -> engine art -> **WIC
  (`decodeColorAspect`)** (images) / **FFmpeg (`frameAtColor`)** (videos).
- `shobjidl.h`/`thumbcache.h`/`windows.h` dependency removed; `CLSID_ThumbnailCache`
  usage deleted.
- The backend thumbnail path now has **no COM/shell dependency** (image WIC manages
  its own COM lifetime inside `decodeColorAspect`).

## 4. Result

- The shell thumbnail COM path is gone, removing the crash class (executing in an
  unloaded shell DLL).
- Image/video thumbnails are still produced by WIC/FFmpeg as before.

## 6. Diagnostic record (experiment, AGENTS rule 9)

- **Experiment**: P-0.9.4.86-shell-thumbnail-crash
- **Symptom**: repeated backend crash (`0xC0000005`) during large scans.
- **Method**: WER LocalDumps (backend exe, full) + WinDbg (`!analyze -v`, `dps`) + Event 1000.
- **Evidence**: fault IP in an unloaded shell DLL; the stack is full of that DLL's
  addresses; code path = `ThumbnailStore::shellArt` (IThumbnailCache).
- **Verdict**: cause identified (shell thumbnail COM module-lifetime UAF). Fix: remove
  the shell path.
- **Revisit**: if shell-only codec thumbnails are ever required (e.g. some heic/webp
  shell extensions), use an out-of-process helper or WIC/FFmpeg instead of shell COM.

## 7. Impact and limits

- Formats decodable only by shell codecs may show a placeholder thumbnail (thumbnails
  are display-only; verdicts/index/results are unaffected). Such files already settle
  as `analysis_failed` when WIC decode fails.
- The GUI's `SHCreateItemFromParsingName` ("reveal in Explorer") stays (a user-initiated
  path, unrelated to the backend crash).
- Dumps/analysis preserved in `D:\Temp\OpenCodeWork\dumps\` (`analyze-433372.txt`, `dps-433372.txt`).
