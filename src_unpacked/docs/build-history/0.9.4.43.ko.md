## 1. 변경 필요성

F preflight에서 NVDEC이 RTX 3080 Ti에서 실제로 동작함을 확인했고(`Runtime PASS` /
`Decode PASS`), 4K H.264 fixture에서 `Pixel-exact FAIL`을 얻었다. 이번 단계는 NVDEC
구현이 아니라 **"NVDEC을 쓰기 전에 만족해야 하는 안전성 계약"** 을 세우는 단계다.

핵심 원칙(지시 §44):

> **GPU decode가 가능하다는 사실과 GPU decode를 사용해도 정확하다는 사실을 분리하십시오.**

## 2. 기존 구조

- production video decode는 전부 software FFmpeg. NVDEC/CUDA 경로 없음.
- Node E는 **sampling strategy**(Sequential/Sparse)를 다루며, **decode backend**는 다루지 않는다.
- E-3B에서 sparse seek는 exactness 미증명으로 기각되었고 `ExactnessPolicy::RefuseAll`이 기본값이다.

## 3. 변경 구조

추가된 것은 **probe/test뿐**이다. production decode decision은 바뀌지 않았다.

- `tests/f_random_access_safety_test.cpp` — 계약 정의 + selfcheck 20 checks, CTest 등록.
  `msf_core`가 include하지 않으며 어떤 production 경로도 읽지 않는다.
- `CMakeLists.txt` — version `0.9.4.43`, test 등록.

### 3-1. 계약 구조 (지시 §6, §28)

```text
Video → Codec capability → Decoder availability
      → Random-access safety → Exactness compatibility → NVDEC candidate
하나라도 확인 불가 → CPU software fallback
```

목표 이중 안전장치:

```text
E Planner → Sparse/Sequential → F Backend Selector
                               → Random-Access Safety
                                  ├─ SAFE → NVDEC
                                  └─ UNSAFE/UNKNOWN → CPU
```

### 3-2. 3상태와 정책 (지시 §7, §24, §25)

```text
RandomAccessSafe / RandomAccessUnsafe / RandomAccessUnknown
Unsafe → CPU,  Unknown → CPU
```

`Unsafe`와 `Unknown`은 **의도적으로 collapse** 된다. 안전성이 "증명되지 않은" stream을
hardware로 보내서는 안 되므로 optimistic 분기가 어디에도 없다.

### 3-3. 판정 순서 (재정렬 금지)

```text
1. hardwareCapability 없으면 → Unknown (moot, CPU 취급)
2. startIsKeyFrame 아니면  → Unsafe
3. firstDecodedPts > request → Unsafe
4. predicate 재현 불가      → Unknown
5. exactnessVerified 없으면 → Unknown   ← 측정 강제
6. 그 외                    → Safe
```

## 4. 해결된 상황

### 4-1. 핵심 반전 — "IDR로 시작하면 안전"은 거짓이다

F-1 착수 시 가정은 `mid-GOP 시작 = unsafe`였다. dataset 전체를 조사한 결과 이 가정은
**부족**했다.

| 파일 | file-start | mismatch | exact |
|---|---|---|---|
| h264_0648x1080_30fps_030s | IDR(0) | 0/20 | YES |
| h264_1080x1920_30fps_030s | IDR(0) | **1/20** | **NO** |
| h264_1360x0808_30fps_030s | IDR(0) | **20/20** | **NO** |
| h264_1920x1080_30fps_300s | IDR(0) | 0/20 | YES |
| h264_3840x2160_30fps_020s | **P(23)** | 20/20 | NO |

dataset 14개 중 **13개는 file-start가 IDR**(key=1 at index 0). mid-GOP은 4K 파일 하나뿐이다.

그러나 **1360x0808는 IDR-start인데도 20/20 mismatch**이며, **확인된 IDR에서 재시작해도
(ss 2.0) 20/20 mismatch**였다. 즉 mid-GOP은 실패 모드 **중 하나일 뿐**이고, NVDEC
exactness는 4K에서도, IDR-start에서도 성립하지 않는다.

→ 그래서 계약에 **`exactnessVerified`가 `Safe`의 필수조건**으로 들어갔다. structure는
필요조건일 뿐 충분조건이 아니다.

### 4-2. 1360x0808 규명 (INCIDENT-F1-1)

- 98.6 % of bytes differ, `maxAbs=185`, `meanSigned=0`
- 양쪽을 nv12에서 멈춰도 잔존(Y maxAbs 143, chroma maxAbs 169) → **format conversion 아님**
- luma보다 **chroma가 더 심하게** 영향
- 1360x808은 **높이 808이 16 정렬이 아님** (chroma plane 높이 404). 비정렬 chroma
  배치에서의 decode 불일치로 보이지만, **이 단계에서 root cause 로 확정하지 않는다**
  (parser 금지, 신규 fixture 생성 금지)

### 4-3. 제외된 가설

| 가설 | 근거 | 상태 |
|---|---|---|
| 4K 해상도 자체 | 4K인데 IDR 이후면 exact | 약화 |
| mid-GOP 시작 | 1360x808는 IDR-start인데도 mismatch | **부분만 설명** |
| format conversion | nv12 정렬 비교에서도 잔존 | 약화 |
| software threading | default == `-threads 1` | 제외 |
| corrupted decode | 양쪽 경로 warning 0건 | 지지되지 않음 |
| frame-rate 불일치 | r=60 vs avg=59.95이나 frame identity 일치 | 약화 |

## 5. 검증

### 5-1. Exactness matrix (지시 §10, §11)

| Input condition | Software | NVDEC | Exact | Policy |
|---|---|---|---|---|
| mid-GOP start (4K) | baseline | differ | **NO** | CPU fallback |
| Confirmed IDR 이후 (4K) | baseline | same | YES | NVDEC candidate |
| **File-start IDR fixture (1360x808)** | baseline | differ | **NO** | **CPU fallback** |
| **File-start IDR fixture (1080x1920)** | baseline | 1/20 differ | **NO** | **CPU fallback** |
| File-start IDR fixture (0648x1080) | baseline | same | YES | NVDEC candidate |
| File-start IDR fixture (1920x1080 300s) | baseline | same | YES | NVDEC candidate |
| Unknown safety | baseline | n/a | n/a | CPU fallback |

control: software A vs A = byte-identical(전 파일), `default == -threads 1` = byte-identical.

### 5-2. Fallback (Gate C)

계약상 mid-GOP **및 exactness 미증명 IDR-start** 모두 `CPU fallback`이다. fallback은
CPU baseline을 그대로 쓰므로 결과가 달라질 수 없으며, selfcheck에서
`Unsafe`/`Unknown` 양쪽이 hardware를 사용하지 않음을 검증한다.

### 5-3. Performance preflight (Gate D)

**확정 exact 조건 파일**(`real_h264_1920x1080_30fps_300s.mp4`, 0/20 exact)에서 측정.
3회, median. `bench: total` 필드가 이 빌드에 없어 PowerShell wall clock을 사용했다.

| case | 100 frames | full 870 frames |
|---|---|---|
| CPU software decode + output | **0.112 s** | **4.438 s** |
| NVDEC + transfer + output | 0.337 s | 9.397 s |
| NVDEC decode only (GPU-resident) | 0.342 s | — |

한계비(770 frame 추가분): CPU ≈ 5.62 ms/frame, NVDEC ≈ 11.77 ms/frame.
**NVDEC이 frame당 2.1배 느리다.** 고정비 story가 아니라 per-frame 비용이다.

**측정 한계(정직하게 기록)**: 이 측정은 NVDEC output을 `hwdownload`로 **전 프레임
내려받는** 조건이다. production은 약 12개 frame만 샘플링하므로 실제 transfer 비용은 이보다
작을 수 있다. 그럼에도 production 사용 패턴(sparse decode 불가 → 전량 decode + 선택적
download)에서는 **NVDEC의 성능 이득 근거가 없다.** 100 frame에서도 NVDEC이 3배 느리다.

## 6. 향후 영향

- **PRODUCTION ADOPTION = NO.** F-2 production integration은 **금지**(지시 §41).
- **NVDEC exactness가 H.264에서 일반적으로 성립한다는 근거가 없다.** 4개 IDR-start
  H.264 중 2개가 mismatch였다.
- 계약의 핵심 규칙은 "structure는 필요조건, exactness 증명이 충분조건"이다.
- **추가 fixture 필요(지시 §42)**
  - Reason: dataset에 4K IDR-start H.264가 없고, 1360x808의 비정렬 chroma 문제가
    root cause인지 4K가 아닌 크기 문제인지 구분할 수 없다.
  - Expected information gain: (a) 4K IDR-start에서 exactness 성립 여부
    (b) 비정렬 높이(16 미배수) H.264에서의 재현 여부 → 1360x808이 구조 문제인지 판정
  - **이번에는 생성하지 않았다**(지시 §16/§13/§42). 별도 지시 대기.
- §4-2의 1360x808 root cause는 미확정(`INCONCLUSIVE`). parser 금지 조건상 SPS/PPS
  직접 파싱으로 좁히는 것은 허용되지 않는다.
