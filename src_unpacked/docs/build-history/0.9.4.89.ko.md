기준선 `0.9.4.88` → 본 빌드 `0.9.4.89`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` 불변.
**`kDatabaseVersion 1.0.5 → 1.0.6`** (가산 테이블 `content_hash`; 구코드 무시).

## 1. 변경 필요성

0.9.4.86의 dataset fingerprint 캐시는 파일셋 키가 **완전히 같을 때만** 재사용한다.
0.9.4.87 실측(`detailed-log-2026-10-11T013805`)에서 **20개 파일만 변경**되었는데도:
- fingerprint **1533.2s(총 2495.5s의 61.4%)**, `bytesRead=68.9GB` = **전체 재해시**.
- 즉 "파일 하나라도 바뀌면 25분 전체 재해시" 한계가 그대로 드러났다.

## 2. 기존 구조

- `computeDatasetFingerprint`가 in-scope 모든 파일을 전체 읽어 SHA-256 → 매니페스트.
- 캐시는 **전체 지문 단위**(파일셋 키가 같을 때만).

## 3. 변경 구조

- **DB `content_hash` 테이블**(1.0.6, 가산): `rel TEXT PRIMARY KEY, size, modified, sha256`.
  `Database::contentHashGet/Put`.
- **`computeDatasetFingerprint`에 `DatasetHashCache`(get/put) 훅**: 파일별로
  `(rel,size,modified)`가 일치하면 **저장된 SHA-256 재사용**(읽지 않음), 아니면 읽어 해시 후 저장.
  `DatasetFingerprint.cachedFiles`(재사용 수) 계측 추가, `bytesRead`는 이번에 실제 읽은 바이트.
- 엔진이 `db_` 기반 콜백을 전달.

## 4. 해결된 상황

- 파일 몇 개만 바뀐 재스캔은 **변경/신규 파일만 재해시** → 25분 → 초 단위.
- 완전 무변경이면 종전의 전체 지문 캐시가 그대로 즉시 반환(0 읽기).

## 6. 성능 실험 기록 (AGENTS 9항)

- **Experiment**: P-0.9.4.89-incremental-fingerprint
- **Baseline**: 0.9.4.87 (20파일 변경 시 fingerprint 1533s / 68.9GB 전체 재해시).
- **Hypothesis**: 파일별 전체 해시를 저장하면 변경분만 재해시할 수 있다.
- **Method**: `content_hash` 테이블 + `DatasetHashCache`; `dataset_e2e_test` 3차 스캔.
- **Result**: 1개 변경 시 59/60 파일 재사용(`cachedFiles=59`), 지문 정확.
- **Status**: PASS (fixture). 실제 대규모 재측정은 사용자 실행으로 확인.
- **Known limitation**: `(size,modified)`가 같고 내용만 바뀌는 드문 경우는 재사용(전체 지문 캐시와 동일 한계).

## 7. 향후 영향 및 한계

- DB 버전 1.0.6(가산 테이블). 기존 DB는 open 시 `CREATE TABLE IF NOT EXISTS`로 자동 생성.
- `content_hash` 행은 스캔마다 해당 파일에 대해 갱신되며, 삭제 파일의 고아 행은 남을 수 있다
  (무해; 필요 시 prune 후보).
- 파일별 해시는 최초 스캔에서 한 번 계산된다(그 이후 재사용).
