### 0.1 Process Note — Pre-register Ordering Deviation (Recorded Honestly)

The pre-register document (`E-exact-sparse-seek.*.md`) was committed **after**
the implementation: commit `d8bb2b3` contains the brief and the probe change
together. The brief was therefore written after the code was built and tested,
rather than before. This is a **procedural deviation** from directive §39 and
from this project's pre-register convention. It does not affect the substance
of the result, but the ordering was wrong, and it is recorded here.

## 1. Why the Change Was Needed

E-2A established that sparse seek is fast but **selects different frames than
production** (pixel parity 4/14, `tsLater` present). Following the directive's
§1 order, exactness is resolved **first**. The production predicate, the
tolerance and the target are **not changed at all.** Only the candidate's seek
target changes.

## 2. The Exactness Cause

The product predicate is at `video_decoder.cpp:127`:

```text
ft + 0.05 >= target     ⇔  the first frame with pts >= target - 0.05
```

The E-2A candidate sought to `target`:

```text
landing keyframe K <= target
if K > target - 0.05 then
  the frame the product chose lies BEFORE K → unreachable → tsLater
```

## 3. The Fix — seek to `target - 0.05`

```text
before  av_seek_frame(fmt, s, pts(target),         BACKWARD)
after   av_seek_frame(fmt, s, pts(target - 0.05),  BACKWARD)
```

The landing keyframe `K'` then satisfies `K' <= target - 0.05`. The frame the
product selects satisfies `pts >= target - 0.05 >= K'`, so it **always exists at
or after the landing point**, and the identical predicate selects the
**identical frame**.

```text
In the common case where no keyframe lies in (target-0.05, target]:
  → K' == K, no cost change
In the rare case where one does:
  → we step one keyframe further back. That is a legitimate cost of exactness.
```

**The predicate, the tolerance and the target were not changed.** The selfcheck
asserts `kProductPredicateToleranceSec == 0.05`.

## 5. The Remaining Failure — HEVC 1080p, and How It Is Detected

In `real_hevc_1920x1080`, 2 of 17 samples are still late (`tsLater=2`).

The **decoder-state-after-seek verification** required by directive §8 found the
cause:

```text
Necessary condition for exact reproduction:
  the frame the product picks satisfies pts >= target - 0.05
  therefore the FIRST DECODED FRAME must be at or before the REQUESTED seek point
  firstDecodedPts > seekRequestPts  →  the product's frame is unreachable
```

The number of targets violating this was measured as
`landingAfterSeekRequest`. **It fired on this file, which is exactly the file
whose pixel parity failed.**

Per directive §34 no resolution is forced; it is classified
`SequentialPreferred`. HEVC uses CRA pictures in addition to IDR, so
`av_seek_frame` may land later than requested. That is structural.

```text
has_b_frames   = 2

```

The packet-pts and frame-`best_effort_timestamp` sequences are offset as a

| C planner | **PASS** — three states decided reproducibly, inputs recorded |
| D E/F boundary | **PASS** — the planner only classifies, the executor only executes, no hardware |

**Why production is not adopted**

1. An exactness failure remains (HEVC 1080p). §35's "no unexplained pixel
   mismatch" is not yet fully satisfied. The cause is explained (seek landing)
   but **not resolved**.
2. The planner detecting that failure at runtime and falling back is
   **detection and avoidance, not an exactness fix**.
3. §2 forbids changing the production default in this version.
