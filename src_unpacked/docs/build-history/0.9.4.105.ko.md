`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` 불변.

## 1. 변경 필요성

사용자 보고(0.9.4.104 실기): 삭제/이동 후 미리보기 소실이 일괄 처리 빌드 이후에도 지속. "로딩 시간은 약간 줄었지만 같은 문제" → **근본 원인 해소** + 유예된 남은 항목(D·E·F·C·상세정보) 전부 수정 지시.

원인 분석(0.9.4.104 보고에서 구조로 확정):

1. **썸네일 요청 폭풍(D)**: `prunePaths()`가 중간 목록을 전체 재구축하고, 재구축의 모든 행(`addGroupItems`)이 `fileThumb()`을 호출해 그룹 수(수천)만큼 백엔드 요청이 나간다. pending 상한 2000의 `erase(begin())`이 진행 중 요청 추적을 버려, 늦게 도착한 응답이 unknown으로 드롭되고 해당 셀은 영구 placeholder로 남았다. `thumbCache_`(3000)와 결합해 "기준 파일만 남는다"는 증상(중간 목록이 기준 파일 썸네일을 같은 크기 키로 캐시해 우측에서 적중)이 된다.
2. **상세정보 텍스트 소실(유예분)**: `requestFileMeta`가 in-flight일 때만 dedup했다. 답이 duration 없이 도착하면(모든 이미지 파일) `refreshDetail`이 duration 미확인으로 **다시 요청** → 응답 → 재구축 → 재요청의 무한 핑퐁. 회전마다 폼 행 삭제/재생성(+EXIF 재파싱)이 반복되어 텍스트가 "떴다 사라지는" 표시가 된다. 0.9.4.102의 `activate()`(지오메트리 확정)로는 잡히지 않는 별개 원인이다.
3. **인덱스 미반영(F)**: 삭제/이동 후 저장 인덱스(files 행·matches 쌍·thumbs 행)는 다음 스캔까지 그대로 남았다. 이후 "불러오기"·리포트에 유령 행/쌍이 보인다.
4. **GUI 블로킹(C)**: 파일 조작 자체가 GUI 스레드에서 실행되어 대량 체크 휴지통/이동 중 창이 멈추고 진행 표시가 없었다(0.9.4.104 유예 C).

## 2. 기존 구조

- `fileThumb()`은 cache miss마다 (dedup loop → 상한 처리 → 요청) 순서로 백엔드 요청을 넣었다. 상한 초과 시 **가장 오래된 항목 삭제** = 진행 중 요청의 추적 상실.
- `addGroupItems()`는 모든 행에서 `fileThumb(rep, grid->iconSize())`을 호출했다. 호출자가 전체 재구축/append 어느 쪽이어도 동일.
- `onBackendConnection(false)`는 UI 상태만 바꿨다. 진행 중 썸네일/메타 요청 추적은 남아 재연결 후 유령 id가 된다.
- `requestFileMeta()`의 dedup은 `fileMetaPending_`(in-flight) 기준. 답 후 재요청을 막는 장치가 없었다. `onFileMetaReady`는 ok면 무조건 `refreshDetail()`.
- `BackendSession`에는 인덱스 행 삭제 경로가 없었다(`loadIndex`/`startScan`만). Database에도 다중 경로 삭제 API가 없었다.
- `deleteSelected`/`moveSelected`는 배치 셸 호출/파일 루프를 GUI 스레드에서 동기 실행했다.

## 3. 변경 구조

- **(D) 요청 폭풍 근본 수정** (`gui/mainwindow.cpp`, `gui/mainwindow.h`):
  - `thumbBulkFill_` 플래그: 대량 채우기(`addGroupItems`) 중 `fileThumb`은 캐시 적중/placeholder만 반환하고 요청하지 않는다. 채우기가 끝나면 `fillPair`(append/전체 재구축 양쪽)가 `thumbCatchUpVisible()`을 호출해 **가시 항목만** 요청한다. 유휴 틱 펌프는 그대로 유지된다.
  - pending 상한: **초과 시 새 요청 거부**(erase-oldest 제거). 거부된 셀은 여전히 cache miss이므로 백로그가 빠지면 다음 가시 펌프가 재시도한다. 도착 응답이 unknown으로 드롭되는 경로 자체가 사라진다.
  - `onBackendConnection(false)`: `thumbPendingReq_`/`fileMetaPending_`/`fileMetaAsked_`를 비운다. 재시작 후 응답이 stale id와 매칭되지 않고, READY 후 가시 펌프가 재요청한다.
- **(상세정보) 메타 요청 핑퐁 제거**:
  - `fileMetaAsked_`(경로별 1회)·`fileMetaRequestCount_`(계측) 추가. 스캔/로드 시작 시 `resCache_`와 같이 초기화된다.
  - `onFileMetaReady`는 **표시 내용이 실제로 바뀐 경우에만** `refreshDetail()`(치수가 새로 캐시됨/길이가 새로 확인됨). 목록 행은 기존대로 in-place 갱신(`refreshFileMetaRow`).
- **(E) 백엔드 중복 흡수 확대**: `ThumbnailStore::kMemMax` 256→1024. 디스크 테이블이 권위이고 메모리 LRU는 반복 요청(중간 대표·우측·미리보기)을 SQLite 이전에 흡수한다. 최악 ~40 MB.
- **(F) 인덱스 즉시 반영**: `Database::forget(paths)` 신설(files + matches 양방향 + thumbs, 1 트랜잭션, 실패 시 롤백). IPC `FORGET_PATHS` + `BackendSession::forgetPaths`(스캔 중 거부 — 스캔이 인덱스를 소유; 다음 스캔이 정합성 복구) + supervisor/loopback 배선. GUI는 삭제/이동/이름변경/붙여넣기(잘라내기 소스) 후 실제 사라진 경로만 전달한다. `prunePaths` 공용 경로(예: 무시 목록)에는 걸지 않는다(행 삭제 오적용 방지).
- **(C) 파일 I/O 백그라운드화 + 진행 표시**: 휴지통은 워커 스레드에서 일괄 `SHFileOperationW`(+`CoInitializeEx(APARTMENTTHREADED)`, COM 정리), 이동은 워커 스레드의 파일별 rename/복사 루프(교차 볼륨 폴백 포함) + 취소(파일 사이) 지원. 진행 다이얼로그는 공용 헬퍼(`newFileOpDialog`: 총계 0이면 무한 진행, 취소 버튼 옵션). 결과(실제 이동분)만 GUI 스레드로 돌아와 `prunePaths` + `forgetPaths` + 타이밍 로그를 수행한다. 이동 로그에 `cancelled=` 추가.
- **회귀 테스트**: `ui_scroll_regression_test` phase 17(대량 재구축이 전 행을 요청하지 않음: `pending=2 items=120`, 가시분 채움) + phase 18(선택 후 메타 요청이 정지: `m1=240 m2=240`, 상세 텍스트 안정). `database_test` forget 섹션(files/matches/thumbs 삭제 + 무관 행 보존 + 빈 입력 no-op). 신규 테스트 훅 `testRefreshGroupList`/`testFileMetaRequestCount`.

## 4. 해결된 상황

- 전체 재구축 1회의 백엔드 요청이 행 수(수천) → **가시 항목 수(수십)** 로 줄어든다. pending 상한이 응답 추적을 훼손할 수 없게 되어(거부 방식) 지연 도착 응답이 유실되지 않는다.
- 이미지 파일 선택 시 메타 요청 1회 + 표시 갱신 1회로 끝난다(무한 재구축 제거). 상세정보 텍스트가 안정된다.
- 삭제/이동/이름변경 직후 인덱스에서 파일·쌍·썸네일 행이 사라져 이후 "불러오기"/리포트가 실물과 일치한다(스캔 중 조작은 다음 스캔이 복구).
- 대량 휴지통/이동 중 GUI가 응답하고, 진행 상황(무한/결정 바 + 취소)이 보인다.

## 6. 향후 영향 및 한계

- `kProtocol` 불변(새 명령 `FORGET_PATHS` 추가). 포터블은 GUI/백엔드를 동일 버전으로 동봉하므로 혼용이 없다.
- engine/DB/schema/cache 불변. `forget()`은 기존 테이블의 행 삭제라 스키마 변경이 아니다.
- FORGET_PATHS는 스캔 진행 중 거부된다(워커가 인덱스 소유). 이동된 파일의 **새 위치**는 다음 스캔에서 인덱싱된다(즉시 재분석은 비용상 범위 밖).
- 백그라운드 파일 조작은 앱 종료와 겹치면 중단될 수 있다(기존 블로킹 동작과 동등 이상; 워커 스레드는 종료 시 프로세스 종료로 정리).
- E 메모리 LRU 증가는 최악 ~40 MB(1024×평균 JPEG).
- **Future revisit condition**: 실측에서 `rebuildMs`가 여전히 지배적이면 진짜 증분(행 단위) 갱신으로 전환. `recycleMs` 지배가 지속되면 `IFileOperation`+진행률 전환. 상세 핑퐁이 다른 경로(예: 폼 외 갱신)에서 재발하면 요청 추적에 상태 기계 도입.
