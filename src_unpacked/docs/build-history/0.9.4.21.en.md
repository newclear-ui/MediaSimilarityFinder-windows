D8 entry. **This is not a performance optimization.** It builds the
foundation that was missing: the ability to compare two states under
identical conditions. Engine 1.5.0, DB 1.0.3, cache v9 unchanged;
benchmark schema 7 → 8.

> This document was written **before fixture / code changes** so the ordering

## 1. Why D8a is needed

By the end of D4a the backend-internal timing boundary existed, but there
was still **no comparison baseline.** The phrase "compare two states under
identical conditions" was not expressible. This is not a code problem; it
is missing evidence.

## 2. Current fixture absence

- `test_sample_img_vid/` exists but is **completely empty** (0 entries).
- `Scanner::isMediaPath` does not recognize `.pgm`, so a PGM-based fixture
  must still carry a scannable extension.

## 3. Why D4b / Full D3 / D8 were all blocked

All three branches require the **same dataset**, and it did not exist:

- **D4b overlap decision** — needs the distribution of `gpuSyncHostMs` /
  `gpuKernelDeviceMs` over a representative scan. D4a's synthetic 16/256
  image probe is not a representative dataset.
- **Full D3** — needs real `walker.maxDepth` / `blockedTicks` /
  `starvedTicks` behavior.
- **D8** — needs repeated measurement of one dataset plus parity comparison.

Every subsequent optimization was blocked by the same evidence gap. D8a
is that evidence.

## 4. Dataset composition method (based on the investigation)

### Investigation conclusion: use a generation script

The repo's firm convention is **"no committed binary assets"** (all 495
tracked files are text). So the dataset is not committed; it is produced by
a **deterministic generation script**. `test_sample_img_vid/` stays a
placeholder and the script determines the actual output.

Why this choice:

- Hand-rolled BMP output is fully deterministic (no encoder nondeterminism)
- 66 tests already follow a generate-at-runtime convention
- Keeps binary files out of git history for the first time
- Regeneration and validation are fully documented

### Fixture composition (v1, image only)

Following the existing test convention (`bmp()` 8x8 24-bit), but carrying
**two structures** so the fixture is meaningful for end-to-end measurement:

```
images/exact/dupNN.bmp      identical-content duplicate groups (dedup path)
images/varied/vNN.bmp       per-seed small variations (classification path)
```

- Extension `.bmp` — WIC reads it through the real production path (not the
  PGM fallback), and the scanner recognizes it.
- Each file is a 54-byte header plus pixels. Pixel values come from pure
  integer determinism such as `(x*2 + y*3 + seed) % 256`.
- File sizes, names, and relative paths are fixed.

### Video is excluded at this stage (documented as separate work)

The investigation found every video fixture depends on
`std::system("ffmpeg ... lavfi testsrc")`, and **ffmpeg output is not byte
reproducible** (encoder / creation-time metadata are muxed into the
container). No current test passes `-fflags +bitexact` / `-map_metadata -1`.

So the documents clearly separate:

```
D8a dataset foundation        = image fixture + fingerprint (this version)
future video fixture expansion = a later stage, once bitexact is guaranteed
```

Forcing video in now would make the fingerprint drift between runs and
**directly defeat the purpose of reproducibility.**

## 5. Fingerprint definition

Dataset identity is **content**, not location:

```
manifest entry = canonical relative path + file size + content hash
sort entries by canonical relative path
canonical string = entries joined by '|' with ';' inside an entry
hash canonical string -> dataset fingerprint
```

### Never included

```
absolute path, timestamp, process id, GPU/CPU name, run id
```

`root` already exists in the JSON, but it is a **location**, not a dataset
identity. `C:\project\test_sample_img_vid` and `D:\other\test_sample_img_vid`
must produce the same fingerprint when their content matches.

### Relative path rule

Following the `IndexManager::canonicalRoot` convention: `\` → `/`,
`lexically_normal`, trailing separators stripped. **No case folding** — that
would break case-sensitive filesystems.

## 6. Canonicalization

- every path boundary goes through `msf::path_from_utf8` / `path_to_utf8`
  (mandatory on Windows)
- `fs::relative(root, file)` then the rule above
- entries sorted by byte order (locale independent)
- the content hash reads the **whole file** — the existing
  `scanner.cpp` `quick()` reads only the first 64 KiB, but that serves file
  identity, so it is not reused for dataset identity

## 7. Hash algorithm choice

The investigation found `msf_core` has **no cryptographic hash:**
- SHA-256 exists only as `QCryptographicHash` inside
  `gui/mainwindow.cpp`, it needs Qt, and it is not exposed in any header
- `msf_core` does not link Qt
- vcpkg has no openssl
- only FNV-1a style hashes exist, as file-local `static` copies

Therefore a new `src/dataset_fingerprint.h/.cpp` implements **SHA-256
directly**. Requirements:

- pure C++ (no Qt, no external library)
- compiles in both the CPU and GPU trees
- deterministic

Precedent: `ProfileStore::deriveId` uses "version constant + `|`-delimited
canonical string → fixed-width hex", so the fingerprint follows the same
shape.

## 8. Fingerprint version

`datasetFingerprintVersion` = 1 — an **algorithm identifier**, separate
from the dataset content. It is raised when the algorithm changes.
Precedent: `PerformanceProfile::kProfileVersion`.

## 9. Benchmark JSON change (schema v8)

Dataset identity is added next to `root` (the location) in the `meta`
block. This is an additive extension; no existing key is removed.

```json
"dataset":{
  "fingerprint":"<64 hex>",
  "fingerprintVersion":1,
  "fileCount":N,
  "totalBytes":M,
  "state":"measured"
}
```

`fileCount` / `totalBytes` are convenience metadata (already inside the
fingerprint, exposed separately for readability).

## 10. Measurement state

| Situation | state |
| --- | --- |
| computed successfully | `measured` |
| root missing / fixture not installed | `not_available` |
| read error | `failed` |

**Never disguise a missing value as `fingerprint: 0`.** When nothing was
computed, the fingerprint is recorded as `null`.

## 11. Test requirements (A–F)

- **A** same fixture twice → identical fingerprint
- **B** change one file's content → fingerprint changes
- **C** same dataset under a different absolute root → identical fingerprint
- **D** enumeration order independence → canonical sort yields one fingerprint
- **E** empty / missing dataset → correct state (`not_available`)
- **F** BenchmarkRecorder JSON records the fingerprint with a correct state

B compares against a **copied** dataset with one file altered (the original
stays intact). C compares a **copy moved to a different root**.

## 12. Compatibility impact

- identical on Windows and Linux (pure C++, via `path_utils`)
- no impact on CPU-only builds (no CUDA use)
- unrelated to search verdicts: the dataset fingerprint is benchmark
  telemetry only and never reaches the engine, DB, or cache
- fingerprint computation **does not affect scan results**

## 16. Generated dataset fingerprint

fixture: `test_sample_img_vid/` (a placeholder — the files are generated)

```
fingerprint          f01d5c77ccd777057494cefc5ad817caea567b40341fa1925f53bb04ec5b2d7c
fingerprintVersion   1
fileCount            60
totalBytes           14760
state                measured
media type           images 100% (BMP 8x8 24-bit, 246 B each)
structure            images/exact 48 (12 groups x 4 identical) + images/varied 12
```

**Reproducibility confirmed**: `msf_dataset_report` was run twice at
different times and produced the identical fingerprint.
`prepare_dataset.ps1` reads no clock, environment, or random source; every
byte is a pure function of `(seed, x, y)`.

### A trap found during the work (dataset root self-reference)

The dataset document was first placed at
`test_sample_img_vid/README.md`, and it turned out to be **a problem.** The
manifest covers *every* file under the root, so:

```
before README:  60 files, 14760 bytes, f01d5c77ccd77705...
after  README:  61 files, 18895 bytes, 8654f69bab23b13e...
```

A document inside the dataset changes the fingerprint. That is not a bug, it
is **correct behavior** — dataset identity includes everything inside it. So:

- the dataset document moved outside the root to
  `src_unpacked/docs/test_sample_img_vid.md`
- `prepare_dataset.ps1` clears a stale identity file when it regenerates
  the root
- the trap is named in both the tests and the documentation

The dataset root must contain **media files only**.

## 17. How D4b / Full D3 / D8 will use it

Against the same dataset fingerprint:

```
D4b    → gpuH2dDeviceMs / gpuKernelDeviceMs / gpuD2hDeviceMs /
          gpuSyncHostMs / gpuHostTotalMs distributions + end-to-end wall time
Full D3 → walker.maxDepth / blockedTicks / starvedTicks / memory / wall time
D8     → repeated performance / stability / correctness / parity on one dataset
```

Procedure:

1. `.\scripts\prepare_dataset.ps1 -Root ..\test_sample_img_vid`
2. Confirm the fingerprint with `msf_dataset_report <root>`
3. Run the scan and compare it to `meta.dataset.fingerprint` in the JSON
4. If the values differ, **the input conditions were not identical, so the
   comparison is void**

**D4b overlap implementation and Full D3 topology implementation are still
not done.**
