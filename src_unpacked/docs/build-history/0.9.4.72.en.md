# MediaSimilarityFinder v0.9.4.72 — Scan stall fix (walk/analyze parallelization) + display/ETR defects

Baseline `0.9.4.71` → this build `0.9.4.72`.
CPU CTest **116/116**, GPU CTest **117/117**.
`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.4` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — all unchanged. No change to search verdicts or behavior.

## 1. Why this change

User report: during a scan the frontend/backend CPU stayed **<1%**, the ETR read
**7000+ minutes**, and the screen sat at **0%** with "read complete" frozen. They
suspected "scheduler CPU allocation".

`--scan` (headless) **reproduced the real stall** (it is not a display problem):

- dataset A (`G:\Downloads\ss_twit`, 273k files, high-latency drive): the walk
  phase ran at ~105–166 files/s with `done=0` and CPU ~6%, never reaching the
  analyze phase within 150 s.
- dataset B (`D:`, 20,000 near-duplicate 16×16 images, SSD): the walk was fast
  (6.3 s) but **analyze took 126.5 s** (breakdown: `cand=199,990,000`,
  `scanMs=101.7s`, `verifyMs=4.9s`).

Both stalls are **single-threaded (~1 core)** regions. `CpuGpuScheduler` only
splits image hashing CPU/GPU in the batch stage, so the scheduler looks healthy.
Two display/formula defects (backend CPU/RSS overwritten with 0; naive linear
ETR) are fixed in the same build.

## 2. Prior structure

- **walk**: `Scanner::scan_stream` computed `quick()` (an FNV hash of the first
  64 KB) for every media file on a **single thread** (since the initial commit
  `3b3e096`). Per-file open/read latency dominates, so on a slow or large tree
  the whole walk serializes onto one core.
- **analyze**: `ScanPipeline::analyze`'s candidate-pair loop (`consume`→`process`)
  is **single-threaded**. On candidate-heavy (near-duplicate) data, recomputing
  `bestMatch` lands on one core. Only the video temporal stage (flushVideo) was
  already parallel.
- **display**: `BackendSupervisor::dispatchEvent`'s `kStatus` (~5 Hz, on match
  arrival) built a fresh `BackendStatus st;`, zeroing `backendCpu/backendRssMB`.
  Real CPU/RSS arrive only on `kHealth` (1 Hz), so the readout mostly showed 0%.
- **ETR**: `MainWindow::scanStatusText` used a naive linear extrapolation
  `elapsedMs*(total-done)/done`, yielding 7000-minute values while `done` was tiny.

## 3. New structure

- **walk parallelization (`src/scanner.cpp`)**: `scan_stream` keeps enumeration
  and metadata on its thread but fans the 64 KB `quick()` reads out over a
  **bounded pool (≤8)** in batches (256). Batches flush **in enumeration order**,
  so emission order (hence results, progress and determinism) is unchanged.
  Workers never terminate the walk (a failed read becomes an empty hash).
- **analyze parallelization (`src/scan_pipeline.cpp`, `src/candidate_index.*`)**:
  added `CandidateIndex::groupBoundaries()` and `forEachCandidatePairInRange()`
  to shard the outer-entry range at **group (file) boundaries**. Each unordered
  pair is emitted once by its smaller entry, so boundary-aligned shards partition
  the pair set with no overlap and no miss. Workers keep thread-local counters,
  telemetry and match buffers; shards are merged **in order**, so the emitted
  match sequence, counters and telemetry sums match the sequential pass
  (verdict parity, deterministic order).
- **telemetry merge (`src/analyze_telemetry.h`, `src/image_decoder.h`)**: added
  additive `addAnalyzeTelemetry`/`addDecodeTelemetry`. To preserve the D9a
  invariant (`index+scan+verify+video == total`), the parallel verify wall-time
  sum is **capped** at the remaining budget (scan becomes 0 on saturation).
- **display fix (`gui/backend_supervisor.cpp`)**: the `kStatus` branch carries
  the Health-sampled CPU/RSS forward via `BackendStatus st = lastStatus_;`.
- **loopback display (`gui/backend_loopback.cpp`)**: the statusSnapshot lambda
  fills GUI-process CPU/RSS via `msf::sampleOwnProcess` (loopback has no Health
  ticker).
- **ETR guard (`gui/mainwindow.cpp`)**: hide the ETR while
  `elapsedMs<3000 || done==0 || total<=done` or `done < max(20, total/50)`.

## 4. What is fixed

- The walk no longer serializes onto one core on a high-latency/large tree.
  Measured: G: read throughput **~10.6 MB/s → ~55 MB/s (~5×)**, ~166 → ~880 files/s.
- On near-duplicate data the analyze `bestMatch`/verify work spreads across
  cores. Measured (ds2, 200M pairs): analyze 101.7 s → 87.9 s (this case is
  dominated by match emission). The gain is larger on real data with many
  candidates but few matches.
- The CPU/RAM readout holds the real working-process values during a scan (no 0%
  flicker).
- The early ETR explosion (7000-minute values) is gone.

## 5. Verification

### Reproduction measurements (0.9.4.72)

- dataset A (G:, high-latency drive, image-only repeat scan): walk read
  throughput ~10.6 MB/s before → ~55 MB/s after. Process CPU stays low (I/O
  bound) but completion time drops sharply.
- dataset B (D:, 20,000 near-duplicate 16×16 images): phase log shows walk
  0.1→1.0 s and analyze 1.1→89.0 s (was 101.7 s), `cand=199,990,000`.
- D9a invariant: verify is capped so `index+scan+verify+video` never exceeds the
  analyze total. `analyze_telemetry_test`'s `substage sum <= analyzeMs` check passes.

### Performance experiment index (AGENTS item 9)

- **Experiment ID**: P-0.9.4.72-walk-parallel, P-0.9.4.72-analyze-parallel
- **Version**: 0.9.4.72. **Date**: 2026-10-08.
- **Purpose**: identify and mitigate the scan stall (low CPU, long runtime).
- **Hypothesis**: the walk's per-file 64 KB read and the analyze candidate loop
  are single-threaded, leaving cores idle and delaying completion.
- **Baseline**: unmodified 0.9.4.72 (= 0.9.4.71 walk/analyze paths).
- **Dataset**: A `G:\Downloads\ss_twit` (273k files, flat), B
  `D:\Temp\OpenCodeWork\ds2` (20,000 near-duplicate 16×16 images).
- **Hardware/OS**: Windows, local. Build configuration: CPU/GPU Release.
- **Run count**: repeated 3 s sampling; one representative run per condition.
- **Raw measured**: A walk read ~10.6 MB/s (unmodified, 166 files/s) → ~55 MB/s
  (fixed, 880 files/s). B analyze 101.7 s (unmodified) → 87.9 s (fixed).
- **Verdict / Status**: PASS (walk), PASS (analyze; the pathological match-flood
  case has a limited gain). Accuracy/verdict parity: confirmed by the full CTest.
- **Known limitation**: the parallel wall-time sum is capped in verifyMs, so the
  D9c decomposition is approximate under saturation. On an HDD the 8-way parallel
  read can lose ground to seek cost (this targets SSD/NVMe).
- **Future revisit condition**: retune walk parallelism for HDD/network shares;
  parallelize the match-emission path (engine onMatch) if it becomes the bottleneck.

## 6. Future impact

- Real GUI visual acceptance is still required (preview, selection, Tiles/List,
  large-dataset traversal).
- The analyze parallelization applies to every `ScanPipeline::analyze` caller
  (revalidate, monitor compare). CTest guarantees identical verdicts and order
  versus the sequential path.
- Headless `--scan` keeps `retainMatches` at its default and can balloon memory
  on pathological data (200M matches); the GUI `ScanWorker` sets
  `retainMatches=false`. Tracked separately.
- HDD walk parallelism remains a revisit condition.
- `ExactnessPolicy::RefuseAll` stays; Node E terminal state unchanged.
