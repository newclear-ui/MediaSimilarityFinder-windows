## 1. Why the change

- P1 declared the BackendCore boundary and raised the entry point. P2 routes
  the GUI through the Backend API while running real BackendCore in the same
  process (Loopback is not a fake).
- Of the P0 inventory's 19 junctions, the MainWindow side moves.
  The `ScanWorker` class itself is untouched.

## 2. Previous structure

- `MainWindow` directly owned `QThread` + `ScanWorker` + `MediaMonitor`.
  Matches travelled via the `matchesArrived` signal plus a `takePending()`
  pull. Ticks read `scanEngine()` / `monitor_->status()` directly.

## 3. New structure

- New `gui/backend_client.h`: fire-and-forget commands only (no synchronous
  wait API, G3). Tick values are pushed snapshots; thumbnails/detail are
  Type B with requestId. All types are plain value structs (no QObject,
  widget, or native handle).
- New `gui/backend_loopback.*`: owns QThread + ScanWorker + MediaMonitor.
  Forwards worker signals, and on every `matchesArrived` drains
  `takePending()` into a `matchesBatch` push. Drains synchronously inside
  pause() too, keeping pause-time completeness. Presentation caches such as
  `thumbDb_` stay GUI-side.
- `MainWindow`: `worker_`/`thread_`/`monitor_` gone, one `backend_`.
  The fileThumb engine branches go through `requestThumb`, ticks read the
  snapshot cache, the monitor goes through
  `startMonitor`/`stopMonitor`/`refreshMonitor` plus snapshots.
  onResults takes `BackendFile`. The loopback drains stragglers first at
  terminal transitions (finished/failed/results).
- GUI decode fallbacks, `thumbDb_` persistence, and the `VideoDecoder`
  duration probe stay as-is in-process and are recorded P3 items (final
  G1.3 is P3).

## 4. Resolved state

- The GUI no longer owns or calls `MediaSearchEngine`/`ScanWorker`/
  `MediaMonitor` directly. Everything crosses `BackendClient`. Same process,
  so behavior is unchanged. P3 only swaps the transport.
