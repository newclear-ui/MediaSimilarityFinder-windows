# 0.9.2.26 — CandidateIndex Large-Scale Performance and Memory Optimization

## IMPORTANT CHANGE
The previous CandidateIndex used a BK-tree with separately allocated heap nodes and per-node `unique_ptr`/`unordered_map` children. As the index grew, pointer/heap fragmentation and BK-tree traversal caused poor large-scale scaling.

0.9.2.26 replaces the normal Hamming-distance `D <= 8` candidate stage with an **exact 9-part multi-index hash**.

The 64-bit hash is split into `8 + 7×8` bits across nine partitions. Candidates sharing any exact partition bucket are collected, then verified with the complete 64-bit Hamming distance. By the pigeonhole principle, two hashes at Hamming distance <=8 must share at least one unchanged partition, so this candidate stage cannot miss a valid result.

Requests with `D > 8` conservatively use an exact full-entry scan. This preserves correctness for arbitrary distances supported by the public API.

## Implementation
- Replaced per-node heap BK-tree storage with a contiguous hash-entry array plus nine partition bucket indexes.
- Buckets store entry positions, eliminating per-node child-object allocation.
- `reserve()` now reserves entry and bucket capacity.
- Added `CandidateIndex::Stats`:
  - nodeCount
  - edgeCount/storedRefs
  - maxDepth
  - bucketCount
- Preserved candidate-pair ordering semantics.
- Added a regression covering an 8-bit difference distributed across partition boundaries.
- Added an exact fallback regression for `D > 8`.
- Added optional 100,000-entry benchmarking via `MSF_LARGE_BENCH=1`. Normal CTest runs 6k/25k/50k to avoid making the regression suite unnecessarily long.

## Benchmark
Measured in the current development environment:

| N | Index build | Indexed query | Linear query | Speedup | Hits |
|---:|---:|---:|---:|---:|---:|
| 6,000 | 1.03 ms | 64.45 ms | 103.61 ms | 1.61x | 6,000 |
| 25,000 | 3.06 ms | 1,092.83 ms | — | — | 25,000 |
| 50,000 | 7.07 ms | 4,617.82 ms | — | — | 50,000 |
| 100,000 | 10.92 ms | 19,609.30 ms | — | — | 100,006 |

The 100k result of `hits=100006` occurs because the random 64-bit hashes contain a few accidental pairs within distance <=8. The benchmark intentionally counts all valid matches, not only self-matches.

Maximum RSS during the 100k benchmark was approximately **17.9 MB**.

The 0.9.2.25 BK-tree measured about 275 ms for the 6k indexed-query workload in the same development environment, while 0.9.2.26 measured about 64 ms. More importantly, the previous BK-tree scaled poorly beyond 25k entries, making it unsuitable as the sole large-index candidate structure.

## Scope / Compatibility
This release changes **CandidateIndex candidate generation only**. Similarity thresholds, final SimilarityEngine semantics, mirror semantics, crop-aware semantics, and video temporal second-stage rules are unchanged.

The Monitor user-workload protection policy is also unchanged. This optimization primarily affects index build/query paths and does not relax the CPU/GPU load protection used by resident monitoring.

## Verification limitation
Qt6 and a physical NVIDIA CUDA runtime are not available in the current environment, so Windows GUI execution and physical NVIDIA GPU execution were not verified here.
