# 0.9.2.28 — CandidateIndex candidatePairs 대규모 후보 생성 최적화

## 중요 변경
0.9.2.26에서 9-part Multi-Index Hash로 후보 검색 자체는 최적화했지만 `candidatePairs()`는 여전히 각 entry마다 `query()`를 호출하는 구조였다. 대규모 인덱스에서는 같은 bucket을 반복 조회하고, 동일 후보를 여러 partition에서 중복 수집한 뒤 매 entry마다 정렬/중복 제거하는 비용이 발생한다.

0.9.2.28에서는 `D <= 8`의 정확성을 유지하면서 `candidatePairs()`를 **bucket 직접 pair generation** 방식으로 변경했다.

## 이전 구조
- 각 entry마다 `query(entry.hash, D)` 실행
- 9개 partition bucket 조회
- 후보 위치 정렬/중복 제거
- 전체 Hamming distance 검증
- 다음 entry에서 같은 작업 반복

## 새 구조
- 각 entry에서 필요한 9-part bucket을 직접 조회
- bucket 안의 후보 entry를 generation-stamp 배열로 중복 제거
- 별도의 후보-position vector 정렬/unique를 제거
- 최종 64-bit Hamming distance로 정확히 검증
- `D=0`은 partition 0 하나만 사용하여 동일 hash pair 중복 생성을 방지
- `D>8`은 기존 exact fallback semantics 유지

## 설계 이유
`D <= 8`에서는 pigeonhole 보장에 의해 실제 후보 pair가 적어도 하나의 partition을 공유한다. 따라서 `query()`의 후보 vector 생성·정렬 비용을 제거하면서 bucket 후보를 직접 순회하면 후보 생성 단계의 반복 비용을 줄일 수 있다. 최종 Hamming 검증을 유지하므로 SimilarityEngine의 판정 규칙은 변경하지 않는다.

## 추가 변경
- `query(D=0)`도 partition 0 하나만 조회하도록 최적화.
- candidatePairs regression에서 planted D=8 근접 pair와 exhaustive linear 결과를 직접 비교.
- `D=0`, `D=8`, `D=9` exact semantics 검증.
- 10k/25k/선택적 50k candidatePairs benchmark 추가.
- 선택적 `MSF_HEAVY_BENCH=1`로 bucket-heavy 데이터 검증 가능.

## 해결된 상황
`candidatePairs()`가 인덱스 크기에 비례해 동일한 query 작업을 반복하던 구조를 제거했다. 특히 bucket 충돌이 많은 데이터에서 실제 후보 pair 생성량과 필요한 검증량에 가까운 형태로 동작하도록 개선했다.

## 정확성/호환성 영향
- 공개 CandidateIndex API 유지.
- `candidatePairs()`의 pair ordering과 `distance` 의미 유지.
- `D <= 8`에서 pigeonhole 기반 후보 누락 없음.
- `D > 8` exact fallback 유지.
- SimilarityEngine, mirror/crop/video temporal 알고리즘 및 Monitor load-protection 정책은 변경하지 않음.

## Benchmark

동일한 0.9.2.26 CandidateIndex 소스와 새 benchmark를 별도 빌드해 비교했다.

| N | 기존 0.9.2.27 계열 candidatePairs | 0.9.2.28 | 개선 |
|---:|---:|---:|---:|
| 10,000 | 약 171 ms | 약 23 ms | 약 7.3배 |
| 25,000 | 약 1,091 ms | 약 147 ms | 약 7.4배 |

추가로 50,000개에서는 약 640 ms가 측정되었다. Bucket-heavy 5,000개 테스트에서는 12,497,500개의 실제 pair가 생성되며 약 1.20초가 걸렸다. 이 경우 메모리 사용량 약 398 MB는 결과 vector 자체의 크기에 크게 좌우된다.

## 검증
- Release build 수행.
- 전체 CTest 수행.
- candidatePairs 결과를 exhaustive linear 결과와 직접 비교.
- candidatePairs 10k/25k benchmark 수행.
- Windows Qt6 및 실제 NVIDIA CUDA 런타임은 기존과 동일하게 현재 환경에서 검증 불가.

## 향후
다음 후보는 실제 수십만~수백만 entry에서 bucket-heavy/worst-case 메모리 및 pair-output 비용을 측정하고, 필요하면 pair generation의 추가 메모리 사용량과 병렬화를 검토한다.
