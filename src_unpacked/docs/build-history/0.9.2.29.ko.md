# 0.9.2.29 — ScanPipeline 후보쌍 스트리밍 및 완전 커버리지 단락 최적화

## 중요 변경
**중요 변경:** `candidatePairs()`의 결과를 ScanPipeline에서 대량 `vector`로 보관하지 않고 스트리밍 소비하도록 변경했다.

### 변경 필요성
0.9.2.28에서 `CandidateIndex::candidatePairs()` 자체는 내부 후보 vector를 없애고 스트리밍 API를 추가할 기반을 만들었지만, `ScanPipeline`은 여전히 8개 인덱스의 `candidatePairs()` 결과를 모두 메모리에 만든 뒤 다시 합치는 구조였다. bucket-heavy 데이터에서는 후보쌍 자체가 수백만~천만 개가 될 수 있어 transient memory가 매우 커질 수 있었다.

### 이전 구조
- 8개 CandidateIndex 각각에서 `candidatePairs()` 호출
- 각 결과 vector를 동시에 보관
- 모든 결과를 `seen` set으로 중복 제거
- 최종 pair vector를 다시 생성

### 새 구조
- `CandidateIndex::forEachCandidatePair()` 추가
- ScanPipeline이 각 인덱스의 후보쌍을 callback으로 즉시 소비
- 후보 pair 전체 vector를 만들지 않음
- full index가 해당 media kind의 가능한 모든 pair를 이미 발견하면 crop index 처리를 생략
- full index가 완전하지 않은 경우에만 crop 중복 제거용 set을 활성화

### 선택 이유
결과 pair가 실제로 필요해질 때만 처리하도록 하여 후보쌍의 transient memory를 줄이고, 동일한 hash가 대량 존재하는 worst-case에서는 crop index의 중복 후보 생성을 아예 피할 수 있다.

### 해결된 상황
대규모 후보 생성 경로에서 `candidatePairs()` 결과 vector와 ScanPipeline의 최종 pair vector가 동시에 존재하던 구조를 제거했다. 특히 full index가 모든 가능한 pair를 커버하는 데이터에서는 추가 index의 중복 후보를 생성하지 않는다.

## 정확성 / 호환성
- CandidateIndex의 기존 `candidatePairs()` API와 정렬 결과는 유지.
- 새 `forEachCandidatePair()`는 동일한 exact Hamming semantics를 사용.
- ScanPipeline의 후보 중복 제거 semantics 유지.
- 이미지/영상 kind 분리 유지.
- SimilarityEngine, mirror/crop similarity, video temporal second stage는 변경하지 않음.

## 향후 영향
후속 단계에서는 `ScanStats::matches` 자체가 매우 큰 결과를 반환하는 경우를 포함해, 대규모 검색 결과의 메모리/소비자 API를 검토할 수 있다. 또한 Windows 실사용 환경에서 수십만 파일 규모의 peak RSS와 scheduler 영향을 측정해야 한다.
