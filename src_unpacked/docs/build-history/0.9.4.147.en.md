# MediaSimilarityFinder v0.9.4.147 — "None" remembers the loaded/scan order

Baseline `0.9.4.146` → this build `0.9.4.147`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged (display only).

## 1. Why

- Field: the "None" order right after Load/search was not remembered. After switching to Name/Similarity and back to None, the **last sorted order** appeared.
- Request: None must always restore the original loaded/scan list order.

## 2. Previous structure

- `rebuildGroups()` overwrote `noneOrder_` (the None baseline) with the current `groups_` order on **every** fill, including sorted fills.
  - The comment even said a sorted fill preserved the visible order for a later None switch.

## 3. New structure

- `noneOrder_` is refreshed **only when the sort mode is None**.
  - Name/Similarity/Group-size fills leave the baseline untouched.
  - Switching to None restores the stored loaded/scan order; new roots are still appended per the existing rule.
- Load/re-verify still create a new baseline, and the scan's None sections (including the 0.9.4.146 start/end reorders) record the new result's order.

## 4. Result

- Name/Similarity -> None returns to the original loaded list order.
- After a scan, its None order becomes the baseline.

## 6. Impact and limits

- The baseline updates on Load/re-verify/scan None sections; a user-sorted view does not change it.
