# MediaSimilarityFinder v0.9.4.46 — DEFECT-A / DEFECT-B 수정

기준선 `0.9.4.45` / `619f74a` → 본 빌드 `0.9.4.46`.
검증된 상태로만 bump. CPU CTest **103/103**, GPU CTest **104/104** (기존 102/103 + 신규 1).
엔진 판정 버전 `1.5.0` 유지, benchmark schema `9` 유지, video cache `9` 유지.
DB 스키마만 `1.0.3` → `1.0.4` (부가적 컬럼 추가, 구코드 읽기 가능).

## 1. 변경 필요성

`0.9.4.45` Search / Index / Comparison acceptance audit 가 real dataset 스캔에서
재현 가능한 제품 결함 2건을 등록했다. 원본 파일은
`images/format/tiff/ycbcr_lzw_bt709.tif` 였으나, 원인은 그 파일의 포맷이 아니라
**분석 실패에 대한 제품 상태 모델 부재**였다.

관측(수정 전):
```
run1: scanned=1 added=1     analyzed=0   stderr/stdout 무출력, exit=0
run2: scanned=1 modified=1 analyzed=0
run3: scanned=1 modified=1 analyzed=0   ← 영구 반복
```

## 2. 기존 구조

`MediaSearchEngine::scan()` 의 `processOne()` 이 파일 단위 상태 전이를 소유했다.

- **판정**: `changed = (신규) || size/​modified/quickHash 불일치 || fingerprint==0 || (video && videoRegrid)`
- **카운터**: `if(!changed){ ++unchanged; return; }` 다음 줄에서 곧바로
  `if(신규) ++added; else ++modified;` — **분석 이전의 의도(intent) 시점에 계수**
- **스켈레톤 행**: 분석 전에 `fingerprint=0` 행을 `db_.upsert()` 로 선기록
  (cancel/crash 시 파일 목록 보존 목적, 주석에 명시)
- **분석 결과 반영**: `processImageBatch()` / `processVideoRange()` 가
  `if(ok)` 일 때만 `fingerprint` 기록 + `db_.upsert()` + `++analyzed`

즉 `fingerprint==0` 이 **"분석 미완료(재시도 필요)"** 와
**"분석 실패(재시도 불필요)"** 를 동시에 표현하고 있었고, 두 상태를 구분할
필드가 존재하지 않았다.

## 3. 변경 구조

### 공통 원인 (DEFECT-A·B 는 독립 버그가 아니라 같은 실패 상태 모델의 두 증상)

- **DEFECT-A**: `added`/`modified` 를 분석 이전에 계수하므로, fingerprint 가 하나도
  없는 파일이 성공적으로 인덱싱된 것처럼 보고됨. 스켈레톤 행이 그대로 남아
  `files` 에 등록되지만 검색에는 참여하지 못함(fingerprint 0). 경고·에러 0, exit 0.
- **DEFECT-B**: `fingerprint==0` 이 무조건 `changed` 를 만들므로, 분석 실패 파일이
  다음 스캔마다 다시 큐에 올라 `modified=1` 로 영구 보고됨. 재분석은 일어나지
  않으므로(`analyzed=0`) 상태가 수렴하지 않음.

→ **하나의 상태 전이로 함께 수정**

### 새 상태: `analysis_failed`

`files.analysis_failed INTEGER NOT NULL DEFAULT 0` (기존 컬럼 추가 마이그레이션 경로 사용).

| fingerprint | analysis_failed | 의미 | 재분석 |
|---|---|---|---|
| != 0 | 0 | 분석 완료 | 불필요 |
| 0 | 0 | 분석 미완료(skeleton: cancel/crash/미도달) | **필요** |
| 0 | 1 | 분석 시도했으나 fingerprint 산출 실패 | **불필요**(내용 불변 시) |

### 판정 변경

```cpp
// before
changed = (... || it->second.fingerprint==0 || ...);
// after
const bool pendingAnalysis = (it!=oldByPath.end() && it->second.fingerprint==0 && !it->second.analysisFailed);
changed = (... || pendingAnalysis || ...);
```

### 카운터 결정 시점 변경 (outcome 시점)

`added`/`modified` 를 분석 **결과** 시점으로 이동. 성공으로 fingerprint 가 기록될
때만 계수한다. 신규 `failed` 카운터는 분석을 시도했고 실패한 경우만 계수한다.

### 실패 상태 영속화

분석 실패 시 스켈레톤 행에 `analysisFailed=true` 를 기록해 남긴다. 따라서 다음
스캔은 "내용이 동일한 확정 실패" 로 인식하고 재분석하지 않는다.

### 가시화

- CLI `--scan`: 결과 라인에 `failed=` 추가, 실패가 있으면 stderr 경고 출력
- GUI 완료 메시지: `, N could not be analyzed` 를 조건부로 추가
- telemetry `pending`: `scanned - analyzed - failed` 로 변경. 실패 파일을
  "미처리 작업"으로 오해하지 않게 함
- benchmark journal `summary.failed` additive 필드 (구 journal 에는 없으며 0 으로 읽힘)

## 4. 해결된 상황

```
수정 후 (실파일 단독, CPU / GPU 동일):
run1: scanned=1 added=0 modified=0 unchanged=0 analyzed=0 failed=1
run2: scanned=1 added=0 modified=0 unchanged=1 analyzed=0 failed=0
run3: run2 와 동일  ← 수렴
```

- 실패 파일이 `added`/`modified` 로 보고되지 않음
- `modified` 무한 반복이 사라짐
- 실패 파일은 fingerprint 가 없어 검색·비교에 여전히 참여하지 않음(의도된 동작)
- 파일이 실제로 복구되면(내용 변경) 자동 재분석됨

## 5. 검증

### 회귀 게이트 (새 테스트가 실제로 결함을 잡는가)

`pendingAnalysis` 판정에서 `&& !analysisFailed` 를 제거해 DEFECT-B 동작을 되살린
경우, 신규 테스트가 **exit=1** 로 실패했다(`scan2 unchanged=2`, `scan2 no new
failure`, `normal file converges` 3개 check FAIL). 복원 후 전부 PASS.

> 측정 중 배운 것: `Copy-Item` 은 원본 `LastWriteTime` 을 보존하므로 make 가
> 재컴파일을 건너뛴다. 소스 복원 후에는 mtime 을 올려 강제 재컴파일해야 한다.

### 신규 회귀 테스트 `analysis_failure_state_test` (28 checks, CPU·GPU 양쪽 PASS)

`MediaSearchEngine::openIndexForRoot()` + `scan()` **production 경로**로 구동한다.
GPU 를 비활성화하지 않으며 보조 경로에 의존하지 않는다.

fixture 는 외부 파일 없이 결정적으로 생성한다.
- `good.bmp` — 유효한 8x8 24-bit BMP
- `broken.bmp` — 유효한 BMP 헤더가 64x64 픽셀을 선언하나 픽셀 데이터가 전혀 없는
  파일. `GetFrame(0)` 이 프레임을 만들 수 없으므로 구성상 디코드 실패

실파일(`ycbcr_lzw_bt709.tif`)이 반드시 필요한지 먼저 판단했고, **필요하지 않다**.
결함은 포맷이 아니라 상태 전이이므로 결정적 fixture 로 동일하게 재현된다. 파일명이나
TIFF subtype 을 하드코딩한 부분은 없다.

검증 불변식:
- 실패가 성공적 `added`/`modified` 로 보고되지 않음
- 실패 파일이 `modified + analyzed=0` 으로 영구 반복되지 않음
- 3·4차 스캔 리포트가 완전 동일하고 candidate/group 결과도 동일
- 정상 파일의 재스캔 수렴 semantics 불변(`unchanged`, 재분석 없음)
- **회계 등식** `scanned == added + modified + unchanged + failed` 가 모든 스캔에서 성립
- 실패 파일 `fingerprint==0` + `analysis_failed==1`, 정상 파일 `fingerprint!=0` + `analysis_failed==0`
- 내용을 바꾸면 재분석되어 복구됨

영속 상태는 `video_cache_test` 와 동일한 read-only sqlite3 직접 읽기 방식으로
확인하며, 제품 클래스에 test 전용 accessor 를 추가하지 않았다.

### real dataset 재현 경로 (수정 후 실측)

신규 인덱스, `images/format/tiff` 14개:
```
CPU run1: scanned=14 added=13 analyzed=13 failed=1 candidates=3 groups=3
GPU run2: scanned=14 added=13 analyzed=13 failed=1 candidates=3 groups=3   ← CPU/GPU 동일
CPU run3: scanned=14 unchanged=14 analyzed=0 failed=0 candidates=3 groups=3
수정 전  : scanned=14 added=14 analyzed=13 candidates=3 groups=3
```
`candidates=3 groups=3` 이 **그대로 보존**되어 Search/Index/Comparison 판정
semantics 가 변하지 않았음을 실측으로 확인했다. `added` 가 14→13, `failed` 1 이
신규로 나타난 것이 의도된 변화다.

전체 dataset 694개:
```
CPU run1: scanned=694 unchanged=693 analyzed=0 failed=1 candidates=174 groups=169
GPU run1: scanned=694 unchanged=693 analyzed=0 failed=1 candidates=174 groups=169  ← 동일
CPU run2: scanned=694 unchanged=694 analyzed=0 failed=0 candidates=174 groups=169
CPU run3: run2 와 동일  ← 수렴
```
acceptance 때 `modified=1` 로 반복되던 파일이 이제 `failed=1` 로 1회 보고되고
수렴한다. `candidates=174 groups=169` 는 수정 전 baseline 과 동일하다.

## 6. 향후 영향

- **DB `1.0.4`**: `files.analysis_failed` 추가. 기존 인덱스는 열이 없어도 자동
  마이그레이션된다. 구코드는 새 컬럼을 무시하므로 이전 빌드가 만든 인덱스를
  그대로 읽는다(단, 그 인덱스에는 실패 표시가 없으므로 DEFECT-B 가 한 번 더
  나타날 수 있다 — 최초 스캔이 `modified` 로 보고한 뒤 `failed` 로 settles).
- **engine 판정 버전 불변**: `added`/`modified`/`analyzed`/`fingerprint`/`groups`
  의 의미는 정상 파일에 대해 그대로다. 실패 파일의 계수만 정정되었으므로
  `kEngineVersion` 을 올리지 않았다.
- **미지원 확장자 투명성**은 여전히 미해결이다(`.ico` 12개가 조용히 건너뜀).
  이번 빌드 범위 밖이며 별도 과제로 남긴다.
- **다음 Gate**: S4 GUI Detailed Logs 최종 functional acceptance (실제 화면 필요).
- `color_thumb` R1, XMP coverage validation, S5 benchmark 는 이번 빌드에
  포함되지 않았고 다음 작업으로 유지된다.
