# MediaSimilarityFinder v0.9.4.129 — Hybrid(AB) 라이브 매치 유실 수정 (라이브 인덱스 off-by-one)

기준선 `0.9.4.128` → 본 빌드 `0.9.4.129`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` 불변 (판정 불변, CTest 등록 수 불변).

## 1. 변경 필요성

- 실기 보고: 검색 방법 `자동(혼합 검증)`(AB) 스캔에서 **유사 그룹 0 / 중복 파일 0**. 상세 로그는 `candidates 19187, pairs 0, groups 0, reduction 100.0%`로 "후보는 찾았는데 확정 쌍이 0"인 서명을 남겼다. B(안정)·A(빠른) 모드는 정상.
- 프로브 재현(18건 실파일 세트, 신규 인덱스): AB만 `pairs=0, liveBatches=0, verifyCalls=0, candidates=8`. Sequential은 `pairs=8`. AB의 최종 패스는 "양쪽 다 changed인 이미지 쌍은 라이브 스트리밍 패스가 이미 방출했다"는 전제(0.9.4.81)로 그 쌍들을 스킵하는데, 라이브가 0건이므로 신규/전체 재스캔 AB 결과는 구조적으로 항상 0이었다.
- 원인 확정(코드 추적 + 격리 프로브): `ScanPipeline::addAndMatch`가 매치를 방출하는 시점에 신규 파일이 아직 `files_`에 push되지 않아, 매치의 right index가 `files_.size()`와 같았다. 소비자 `liveEmit`의 범위 검사 `if(m.left>=lf.size()||m.right>=lf.size()) return;`이 이를 전부 거부 → **라이브 스트림은 0.9.4.81 도입 이후 단 한 건도 전달된 적이 없다.**
- 2차 결함: 텔레메트리/상세 로그의 `pairs`·`groups`는 최종 analyze 패스의 onMatch만 집계한다. 라이브가 고쳐져도 AB의 상세 로그는 여전히 0으로 남는 구조였다.

## 2. 기존 구조

- 라이브 패스: `processImageBatch`/`processVideoRange`가 파일을 `files_`에 넣으면서 `livePipe.addAndMatch(mf, maxDistance, liveEmit)`를 호출. `addAndMatch`는 consider 루프 안에서 `onMatch(match)`를 부르고, `files_.push_back(f)`는 그 뒤에 실행됐다.
- AB 최종 패스: `included()`가 `skipBothChangedImages=(analyzeMode==Hybrid)&&liveMatch`일 때 양쪽 changed 이미지 쌍을 스킵(라이브 소유).
- 텔레메트리: `telemetry_.addStreamedMatch()`와 그룹 union-find(`clusterParent`/`clusterTouched`)는 최종 패스 onMatch에서만 갱신. 라이브 방출은 `control->onMatch`만 호출하고 계정에 들어가지 않았다.
- 라이브 파이프는 모든 모드에서 feed됐다(Sequential 포함).

## 3. 변경 구조

- `scan_pipeline.cpp::addAndMatch`: 매치를 로컬 벡터에 모은 뒤 `files_.push_back` + `indexFile`로 파일을 완전히 등록한 다음 방출한다. 콜백은 이제 배치 `analyze()` 계약과 동일하게 "완전히 등록된 파일"을 관측한다.
- `media_search_engine.cpp`:
  - AB에서 라이브가 소유한 양쪽-changed 이미지 쌍을 리포트/텔레메트리에 합산: `nLiveImgPairs`(r.groups = st.groups + nLiveImgPairs, r.imgPairs 포함), 경로 키 union-find(`tlParent`/`tlKind`)가 라이브(AB)와 최종 패스 두 스트림을 GUI와 같은 방식으로 병합. `streamedMatches`는 AB의 라이브에 대해서만 가산 — A/B는 최종 패스가 전 쌍을 세므로 이중 계수를 피한다.
  - 라이브 파이프 feed를 A/AB로 한정(`liveStreamActive`). Sequential(B)는 "walk 완료 후 검증"이 계약(analyze_mode.h)이고 최종 패스가 전 쌍을 방출하므로, B에서 feed하면 `takePending()`/`matchesBatch`에 동일 쌍이 이중 방출된다(walker_queue_test가 pending 집합을 정확 수로 고정).
- `gui/mainwindow.cpp` 검색 요약의 CPU 행: 프로세스(avg/max/std)와 **시스템 평균(cpuSysMean)**을 함께 표기. 신규 키 `detailLogCpuProc`/`detailLogCpuSys`. 배경: 프로세스 지표는 논리 CPU 수로 정규화되어 16스레드가 꽉 차도 ~2~6%로 보이므로("CPU 2%만 표시" 실기 지적), JSON에 이미 있던 시스템 평균을 노출한다.

## 4. 해결된 상황

- AB 신규/전체 재스캔에서 유사그룹·중복파일이 정상 산출된다. 썸네일 미표시 증상은 그룹 0의 직결 결과(표시할 행 없음)였으며 별도 코드 결함이 아니다(백엔드 썸네일 경로는 0.9.4.125 keep-as-is 판정 + 프로브 검증에서 정상).
- 상세 로그가 모드와 무관하게 동일한 수치를 기록한다: 18건 세트에서 B/A/AB 모두 `pairs=8, candidates=8, imgGroups=3, imgDupFiles=8, groups=3`.
- "CPU 2%" 문의에 대한 정정: 요약에 프로세스/시스템이 분리 표기되어 실사용량이 보인다.

## 6. 향후 영향 및 한계

- 판정·저장·프로토콜·engine/DB/schema/cache·journal schema 불변. CTest 등록 수 불변(125/126).
- Live(A) 모드는 설계대로 최종 패스가 양쪽-changed 쌍을 재검증·재방출한다(중복 방출은 GUI union-find가 동일 결과로 흡수, 텔레메트리는 최종 패스 단일 집계). AB는 라이브(양쪽 changed)와 최종(exactly-one changed)이 상호 배타라 중복이 없다.
- 라이브 스트림이 0.9.4.81 이후 처음으로 실제 동작한다. A/AB 스캔에서 walk 중 라이브 검증 비용이 추가되며, 최종 재검증분은 verify 캐시 히트로 저렴하다. B 모드는 관측 동작(라이브 미가동)과 결과가 동일하다.
- 남은 육안 확인(사용자): AB 자동 모드 실기 스캔에서 그룹/중복 파일 수·썸네일 표시, 상세 로그 수치 일치.
