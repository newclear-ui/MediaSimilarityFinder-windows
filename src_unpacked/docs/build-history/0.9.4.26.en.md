## 2. What this overturns

D9b assumed the cost sat in the scoring path and removed buffer recomputation
there. That stage is now measured at **0.55 % of the total** — about 0.047 ms
out of 8.564 ms. D9b's change was a correct, results-neutral cleanup of a stage
that was never the bottleneck, which is exactly why it moved nothing.

The proportional relationship is worth stating plainly: decode is roughly
**173×** the cost of `frame_ssim` in this path. Any candidate that does not
touch decode cannot address more than the remaining 5.1 %.

## 3. What was measured, and what was not

Measured boundaries, all disjoint code regions:

- **key** — `file_size` + `last_write_time` + 64 KiB read + the FNV loop, in
  `verifyBuffersFor` before the cache lookup. Runs on **every** buffer lookup,
  cache hit or miss.
- **decode** — `ImageDecoder::decode` ×2 + the dimension validation.
- **cache store** — the map insert and LRU eviction.
- **cache copy** — the two `GrayImage` copies out of the cache on a hit.
- **crop/aspect** — the 8 `centerCropResize` calls. `resize` is **not** split out
  of `crop`: `centerCropResize` does both in one function, and separating them
  would have meant changing the code under measurement.
- **mirror flip** — the 10 `flipBuf` calls.
- **frame_ssim** — the 20 `frame_ssim` calls, timed around the calls.
- **other** — remainder of `verifyMs`, mirroring how D9a defined `scanMs`.

**Not measured, and not estimated:**

- `frame_ssim` internals (preparation / window / accumulation). It is a single
  function (`src/video_fingerprint.cpp:398`) with no separable sub-stage short of
  putting a timer inside the 4,096-iteration loop, which is forbidden. Reported
  as unmeasured.
- The split of `decode` between file open, EXIF read, WIC scale, format
  conversion, and pixel copy. D9c timed the decode call as one region. This is
  the obvious next level of decomposition, and it is where the next candidate
  has to look.

## 5. Timing semantics

**Exclusive, non-overlapping.** The seven measured stages are disjoint code
regions and `other` is the remainder, so the list reconstructs `verifyMs`
exactly. `verifySumMs` and `verifyBreakdownOverMs` are published so a consumer
can check that identity rather than trust it; on this run the overflow is
0.0000 ms.

Timer overhead: roughly 48 reads per *expensive* verify (~20 per
`verifyBuffersFor` × 2, 1 for crop, 4 per `ssimBuf` × 10), about 660,000 over the
run. No timer is inside the inner loop. Because the build pays for its own
timers, **these numbers are a relative distribution, not a production
performance claim.** Note `verifyMs` here (117,614.6 ms) sits inside the D9a/D9b
run-to-run spread (109,142–117,291 ms), which is consistent with that
qualification.

## 7. Stage counters

```text
verifyBufferLookups    27,468   (= misses 12,949 + hits 14,519)
verifyQuickHashReads   27,468   one per lookup, hit or miss
verifyQuickHashBytes   380,999,408  (363.3 MB; 27,741 B/verify average)
verifyDecodes          25,898   (= 2 x 12,949 misses)
verifyCacheCopies      14,519   (= hits)
verifyCropCalls       109,872   (= 8 x 13,734)
verifyFlipCalls       137,340   (= 10 x 13,734)
```

Two structural facts fall out of these counters:

1. **Every cache hit still reads 64 KiB and hashes it.** 27,468 quick-hash
   reads for 12,949 real decodes means the key is rebuilt on hits too. 363 MB
   read and hashed to serve 14,519 cache hits. This is 3.76 % of the cost, so it
   is real but not the bottleneck.
2. **Each miss decodes the same file twice.** `verifyDecodes` is 25,898 = 2 ×
   12,949, because `verifyBuffersFor` calls both `decode(path, 64, 64, f)` and
   `decodePreserveAspect(path, 64, a)` on the same path. 4.31 ms per decode call
   × 2 is the 8.127 ms.

## 8. Why decode costs 4.31 ms

Read from `src/image_decoder.cpp` during the D9c investigation (reported, not
changed):

- `decodeWicFile` / `decodeWicFileAspect` each `CoCreateInstance`
  `CLSID_WICImagingFactory2` and `CreateDecoderFromFilename` **per call**, so the
  file is opened and the image decoded from scratch every time. No factory, no
  decoder, and no decoded frame is reused between the two calls for the same
  file.
- The scaler uses `WICBitmapInterpolationModeFant` (line 143, and the same in
  `decodeWicFileAspect`), the high-quality downsampling mode.
- EXIF orientation is queried on every decode (lines 120, 168).
- `IWICBitmapFormatConverter` then converts to 8 bpp gray, followed by
  `CopyPixels`.

Producing a 64×64 grayscale thumbnail this way costs 4.31 ms, and it is done
twice per file. None of this was measured at a finer grain in D9c; it is code
reading that identifies where the next measurement should go.

The real call path, read from source rather than inferred from names:

```text
ImageDecoder::decode(path,w,h,out)                     (image_decoder.cpp:241)
```

Boundaries to be measured, per the actual code above:

```text
decodeTotalMs / decodeCount                      (decode)
decodePreserveAspectTotalMs / ...Count           (decodePreserveAspect)
  ├─ comInitMs         CoInitializeEx
  ├─ factoryMs         CoCreateInstance(WIC factory)
  ├─ openMs            CreateDecoderFromFilename
  ├─ metadataMs        GetFrame + GetMetadataQueryReader + GetMetadataByName
  ├─ orientMs          CreateBitmapFlipRotator + Initialize
```

`decode` and `decodePreserveAspect` are **always** reported separately, even
though the two WIC bodies are near-identical.

during `CopyPixels`, so "decode" and "copy" cannot be separated without changing
the code under measurement. The `copyMs` bucket therefore contains the actual
image decode. This is recorded so the numbers are not misread.

The PGM fallbacks are counted but not decomposed; they only run when WIC fails.

## 7. Secondary Measurement Target — cache mutex

```text
cacheMutexAcquires

```

Both measured at the two existing lock sites in `verifyBuffersFor`

## 13. Timer Semantics

Exclusive and non-overlapping, as in D9c:

```text
decodeTotal = comInit + factory + open + metadata + orient
            + resize + convert + copy + other
```

`otherMs` is the remainder inside the WIC function, mirroring how D9a defined
`scanMs` and D9c defined `verifyOtherMs`. A mis-scoped timer shows up as a
negative or oversized remainder rather than a plausible wrong split.

Mutex wait and hold are **not** part of the decode sum; they are reported
alongside, because the lock is held across a map lookup, not across decoding.

No timer is placed inside any inner loop. `frame_ssim`'s 4,096-iteration body
is untouched.

## 14. Noise Consideration

D9a observed ~7.5% run-to-run spread. D9d therefore:

- uses >= 5 runs and reports median/min/max/range;
- does not rank two stages whose medians are within the observed range of each
  other; ties are reported as ties;
- prefers per-call shares over absolute milliseconds, since call counts are
  deterministic and therefore a cleaner signal than wall time.

## 2. What this overturns

Two plausible-sounding optimization targets are now measured and dropped:

- **`WICBitmapInterpolationModeFant` downscaling: 0.32 %.** Fant is the
  high-quality interpolation mode and looks expensive by name. It is 369.0 ms
  out of 115,628.4. Switching it to a cheaper filter would buy nothing, and it
  would change resize quality, which is a verdict-relevant property.
- **EXIF metadata: 0.17 %.** Skipping or deferring the orientation query would
  buy 194.0 ms.

And the target that is *not* obvious from the name is the one that matters:

- **File open and decoder construction: 89.55 %.** `CreateDecoderFromFilename`
  and the per-call `CoCreateInstance` of the WIC factory. Together 3.99 ms of
  every 4.47 ms decode.

`copy` at 5.15 % is the actual image decompression, and it is where a
"decode is expensive" intuition would have looked. It is a twentieth of the cost.

## 3. Cache mutex: not a bottleneck

| Metric | Value |
|---|---:|
| acquires | 40,417 |
| waitMs | 8.4 (0.0002 ms/acquire) |
| holdMs | 72.4 (0.0018 ms/acquire) |
| wait share of lock time | 10.38 % |
| hold share of lock time | 89.62 % |

40,417 acquisitions = 27,468 lookups + 12,949 stores. Total lock time is 80.8 ms
against 115,628.4 ms of decode — **0.07 %**. Wait is ten percent of the lock
time but both quantities are microscopic, so the lock serializes almost nothing
in practice.

**This closes the question D9c could not answer.** The mutex is explicitly
deprioritised, with a measurement behind it, rather than left ambiguous. Note
that D9c's `other` bucket (0.42 %) therefore does **not** contain hidden
contention: there is none to hide.

## 4. Timing Semantics

Exclusive and non-overlapping. Each WIC step is timed by a pair of
`steady_clock` reads around exactly that call, and `decode` /
`decodePreserveAspect` are reported separately even though their bodies are
near-identical.

`decodeSubSumMs` vs `decodeTotalMs` is published so the identity can be checked
rather than trusted. On this run: **sub-sum 110,879.4 vs total 115,628.4** — a
4.1 % gap. That gap is honest and is *not* a mis-scoped timer: it is the
unmeasured code between the instrumented calls (the `FAILED(hr)` checks,
`GetSize`, the aspect arithmetic, and `out.pixels.resize()`, which is a heap
allocation and zero-fill). It is reported rather than folded into a stage.

`cacheMutexWaitMs` and `cacheMutexHoldMs` are never summed. The verdict depends
on their ratio, and a single combined number would hide exactly the distinction
that matters.

No timer is inside any inner loop. The D9c instrumentation was kept in place, and
its exclusive identity still holds (§5).

## 10. Limitations

- Instrumented build: absolute times carry timer overhead. Use the shares.
- 4.1 % of decode time sits between the instrumented calls (allocation,
  `GetSize`, HRESULT checks) and is not attributed to any stage.
- The image decompression itself cannot be separated from `CopyPixels`; WIC does
  it lazily. `copy` is the real decode cost and is labelled as such everywhere.
- `open` and `factory` are not split further. `CreateDecoderFromFilename` does
  file open, format probing, and decoder instantiation together, and separating
  them would mean changing the code under measurement.
- Single host, single dataset, one configuration. 5 runs, one machine.
- D9c's own "resize is inside crop/aspect" limitation still stands: `crop` and
  `resize` remain one bucket in the verify breakdown, separate from the
  decoder's own resize stage.

## 11. Next Candidate

**Not implemented here.** Seeing that file open and factory construction dominate
does not authorise changing them. The evidence supports:

> **Candidate D1 — image decoder construction and file open.** The next
> pre-register should first decompose the 2.77 ms `open` (file open vs format
> probe vs decoder instantiation) and confirm how much of the 1.22 ms `factory`
> is the `CLSID_WICImagingFactory2` probe failing before falling back to
> `CLSID_WICImagingFactory`, because that fallback would mean the fast path is
> not being taken at all.

Three observations to carry in, all from measured counters or source, none of
them proposals:

1. 89.55 % of decode — 84.9 % of the whole expensive verify — is two COM
   construction calls, and both are constructed per call with no reuse.
2. The same file is decoded **twice** per miss (25,898 decodes for 12,949 files),
   so the 2.77 ms open is paid twice for one file.
3. `copy` (the real decompression) is only 5.15 %; `Fant` is 0.32 %; EXIF is
   0.17 %. All three are dead ends and should not be proposed again.

Explicitly deprioritised with evidence: cache mutex contention (0.07 % of decode),
`WICBitmapInterpolationModeFant` (0.32 %), EXIF skip (0.17 %), and
`frame_ssim` (0.53 % of the verify).

Candidate A (candidate arrival reduction) stays deferred: it touches candidate
recall, false positive/negative risk, and verdict semantics.
