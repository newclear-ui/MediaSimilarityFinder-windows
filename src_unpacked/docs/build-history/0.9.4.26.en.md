# MediaSimilarityFinder v0.9.4.26 — D9c Expensive Verify Internal Cost Accounting

Status: **PRE-REGISTERED** (this document is committed *before* any code change)

This is an **instrumentation / profiling build**. Performance improvement is
explicitly not the goal.

---

## 1. Change Need

v0.9.4.25 D9b tested Candidate B (reduce the cost of one expensive verify) and
was rejected:

```text
v0.9.4.25 D9b
Candidate B
expensive verify per-call cost reduction
→ NOT ACCEPTED
```

Correctness and compatibility were preserved, but the performance objective was
not met. D9b therefore cannot be promoted to a performance baseline, and the
D9a baseline (0.9.4.24) remains the reference for all future comparison.

The open question D9b left unanswered is the actual subject of D9c:

> Where do the roughly 8.5 ms per expensive verify actually go?

**Structural fact D9b established, recorded here so it is not repeated:**
the duplication it hypothesised did not exist. The original code already
computed the aspect buffers (`rA`, `rB`) once outside the loop. D9b moved an
already-reused value into a wider scope. This does **not** generalise to "the
original was optimally written" — it only invalidates that one hypothesis.

## 4. D9c Hypothesis

No optimization hypothesis. D9c assumes nothing about which stage dominates
and measures each stage separately. The reason is D9b's lesson:

```text
observed operation count ≠ actual bottleneck
```

D9b removed ~2,048 pixel operations (a 2.3% proxy) and measured no change,
while a different stage in the same function was never considered at all.

## 5. Measurement Scope

The stages to be separated, per the real call path traced in
`src/image_verify.cpp` (`verifyImagePair` → `verifyBuffersFor` ×2 →
`verifyScorePlan` → `verifyScorePlanImpl` → `ssimBuf` ×10 → `frame_ssim` ×20):

| Stage | Code site | How it is bounded |
|---|---|---|
| buffer key / stat / quick-hash read | `verifyBuffersFor` prologue | timer around `file_size` + `last_write_time` + 64 KB read + FNV loop |
| decode | `verifyBuffersFor` | timer around `ImageDecoder::decode` ×2 + dimension validation |
| cache store / copy out | `verifyBuffersFor` | timer around the map insert/evict, and separately around the buffer copy on a hit |
| crop / aspect preparation | `verifyScorePlan` | timer around the 8 `centerCropResize` calls |
| mirror flip | `ssimBuf` | timer around `flipBuf` |
| frame_ssim | `ssimBuf` | timer around the two `frame_ssim` calls |
| other | — | remainder of the verify total |

`resize` is not separated from `crop` when the code does not separate them.
The report must state the actual boundary measured, per the directive.

**`frame_ssim` internals are not instrumented.** It is a single function
(`src/video_fingerprint.cpp:398`) with no separable sub-stages short of adding
timers inside the inner loop, which is forbidden (see Non-goals). Its
preparation/window/accumulation split is therefore **not measured** and must
be reported as such rather than estimated.

## 6. Instrumentation Scope

Only these are allowed in D9c:

```text
timing instrumentation
counter instrumentation
profiling telemetry
benchmark reporting
test coverage needed to validate the instrumentation
```

Existing structures are extended rather than duplicated:

- `src/analyze_telemetry.h` — the existing plain data carrier. It deliberately
  has no dependency on `BenchmarkRecorder` or `ScanPipeline`, and no recorder
  pointer is ever passed into verification code. D9c must preserve that
  property: `image_verify` only fills the struct.
- `src/benchmark.cpp` — renders the analyze telemetry (currently `verifyMs`,
  `verifyCalls`, `msPerVerifyCall`). The new fields are rendered alongside.
- schema version — the analyze telemetry block is schema v9. Adding fields is
  additive; the schema version is bumped only if the existing additive-read
  contract requires it, and that decision is recorded explicitly.

## 7. Non-goals

Not done in D9c, under any circumstances:

```text
SSIM formula, window size, or precision changes
early-exit additions
SSIM evaluation count changes
frame sampling, threshold, candidate filtering,
candidate semantics, grouping, or verdict semantics changes
cache semantics changes
decode, resize, crop, or mirror semantics changes
CPU fallback semantics changes
CUDA correctness changes
any optimization, however small, "while the timer is in there"
vcpkg restructuring
```

Window size, precision, and early-exit are deferred candidates for a separate
pre-register.

## 8. Accuracy / Verdict Risk

The risk is not numerical; it is behavioural. Instrumentation must not change:

```text
verify result
verdict
group count and membership
similarity decision
```

Mitigations:

- The instrumented path must be covered by the existing
  `verify_parity_test`, which compares `verifyScorePlan` against the preserved
  pre-D9b `verifyScorePlanReference` for double equality.
- A new assertion compares an instrumented run against an uninstrumented run
  of the same inputs (`tel == nullptr`) and requires identical results.
- A new assertion requires the sub-stage timings to sum to less than or equal
  to the measured verify total, so an overlapping or mis-scoped timer fails
  loudly instead of producing a plausible-looking but wrong distribution.
- `groups` must equal 156,152 on the same dataset.

## 9. Compatibility Risk

None expected. The struct is additive and is filled by the core, not by the Qt
layer. CPU fallback and the GPU path are untouched because verification is
shared CPU code. If any of this turns out to be false, that is a stop
condition, not something to work around.

## 10. Measurement Plan

- Same dataset, same hardware, same GPU, same configuration, same cold-index
  condition as D9a. Fingerprint is asserted before measuring.
- The existing `msf_dataset_baseline` harness, 3 runs. Single-run conclusions
  are not valid.
- Report stage times as totals and as per-expensive-verify averages, plus
  percentage shares.
- Because instrumentation itself costs time, the D9c timing result is **not** a
  production performance claim. Only the relative internal distribution is in
  scope.

## 11. Timer Semantics and Non-overlap

Timings are **exclusive** and constructed to be mutually exclusive:

```text
verifyTotal = keyMs + decodeMs + cacheStoreMs + cacheCopyMs
            + cropMs + flipMs + frameSsimMs + otherMs
```

`otherMs` is the remainder of the D9a `verifyMs` total after the measured
stages, mirroring how D9a defined `scanMs`. Because the stages are disjoint
code regions, their sum can never exceed the total; the test asserts this.

Nested/inclusive time is never added on top. The report states which semantic
applies per field.

Overhead budget: roughly 48 timer reads per *expensive* verify (about 20 per
`verifyBuffersFor`, 1 for crop, 4 per `ssimBuf` × 10), i.e. order 660,000
timer reads over the whole run. Timers are never placed inside the 4,096-iteration
inner loop. The measured overhead is reported rather than assumed away.

## 12. Stop Conditions

Reduce scope or stop, and record the problem instead of patching around it, if:

```text
1. instrumentation changes a verdict
2. instrumentation changes candidate semantics
3. CPU/GPU parity breaks
4. an existing test fails
5. timer overhead is excessive
6. stage timings overlap and cannot be interpreted
7. the real expensive verify path cannot be measured accurately
8. an existing test is deleted or its conditions relaxed
9. a measurement would have to be estimated rather than measured
```

## 13. Pre-register Baseline Decision

The working tree contains the D9b code (103 added lines in
`src/image_verify.cpp` / `.h` relative to the D9a commit `f46658e`). It is
**not** reverted, because:

- Reverting is not required: D9b was measured to leave every counter and the
  group count identical to D9a, and `verify_parity_test` proves the scoring
  path is double-identical to the pre-D9b reference. The tree is therefore
  behaviourally equivalent to D9a even though the code differs.
- `git reset --hard`, `git clean -fd`, and `git restore .` are forbidden, and
  there are no local user modifications to preserve (the tree was clean at
  HEAD `0f75c2d`).

D9c instruments the current tree and the report states this equivalence
explicitly, so the numbers remain comparable to D9a.

## 14. Expected Outcome

Success means, and does not mean:

```text
SUCCESS:
  stable internal timing of the expensive verify path
  verdict, grouping, candidate behaviour preserved
  CPU/GPU parity held
  all existing tests pass
  telemetry comparable against the D9a baseline
  evidence sufficient to choose the next candidate

NOT SUCCESS (performance is not the criterion):
  any wall-clock improvement
  a larger ms/verify number than D9a
```

The delivered artifact is a measured cost distribution of the 8.5 ms, plus the
evidence needed to pick the next candidate. The next candidate is **not**
implemented here; it gets its own pre-register, version, hypothesis, accuracy
risk, and measurement plan.
