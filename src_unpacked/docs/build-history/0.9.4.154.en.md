Baseline `0.9.4.153` → this build `0.9.4.154`.
CPU CTest **128/128**, GPU CTest **129/129** (no new CTest registrations; §7 is a new section inside the existing binary).
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` / `kProtocol 1` unchanged (no judgement/schema/version bumps).

## 1. Why the change was needed

- In-scan match checkpoints (5 s, analyze-slice) are written with SAVEPOINT inside the scan transaction. A forced kill rolls back every uncommitted transaction, so checkpoints after the last engine commit are lost.
- With a still-valid baseline, the next A/AB skips full verification and the lost matches stay lost forever (`unchanged` verdicts, since the file rows survived and change detection never fires).

## 2. Previous structure

- `.151` SAVEPOINT: nested saves are consistent but prove nothing about kills (declared unproven).
- `.152`/`.153`: baseline invalidation on settled exits (complete/cancel/reported failure).

## 3. New structure

- New `meta.scan_dirty` key (scalar upsert/delete, no schema change).
- `ScanWorker::run()` writes `'1'` in its own autocommit right after the index opens; a function-scope RAII guard (`SettledExit`, noexcept with internal try/catch) deletes it on EVERY settled exit (complete, cancel, reported failure, including exception unwinds). Only a forced kill skips destructors, leaving the key set.
- `MediaSearchEngine::scan()` runs one forced full verification when the key survives, regardless of the baseline (`dirty=1` in the log), then restamps. A clean exit clears the key, so one crash costs exactly one full pass.
- Regression pin: new `crash_diagnostics_test` §7 (15 checks): no marker after a clean scan → plant the marker manually (exact post-kill DB state) → next A/AB logs `forceFullPass dirty=1` → restamped, marker gone, changed pair dropped, untouched pair kept.
- `ui_cancel_consistency_test` finalized (fixed-sleep tail race replaced with progress-signal gating — deterministic cancel).
- Test-read hardening: busy_timeout(10s) on the e2e sqlite handles. The intermittent Test 1e failure (3 early failures, then 10 consecutive passes; DBG showed rowBefore="" at failure) is attributed to transient SQLITE_BUSY "" reads as the prime suspect. Genuine mismatches still fail. INSUFFICIENT EVIDENCE held, no speculative product change.
- Test Mode adoption unaffected (a completed scratch never carries the marker, so there is nothing to upsert; partial adoption never touches meta).

## 4. Resolved state

- After a forced kill, the next A/AB no longer trusts the stored set as complete.
- The marker survives only a forced kill (every settled path clears it via the guard or an explicit delete).
