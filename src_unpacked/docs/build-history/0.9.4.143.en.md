# MediaSimilarityFinder v0.9.4.143 — Drop stale pairs of changed files + auto re-apply the index after a changed scan + configurable recent-folder count

Baseline `0.9.4.142` → this build `0.9.4.143`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged.
This is a **verdict-persistence correctness fix**, not display-only (schema/protocol/engine version unchanged).

## 1. Why

- Field (S-4): after confirming two files as one group, one file was deleted and replaced by a **different image with the same name and a very similar size**. A Fast (A) search kept the old group and reported the different files as duplicates; Test Mode (a fresh scratch index) judged correctly and offered an index update.
- Cause: the scan persisted the quick-loaded stored pairs plus newly found pairs as one set, so **stale pairs of re-analyzed files were never removed**. Test Mode was correct because it analyzed from an empty index.
- Additional request: Favorites showed only 2 recent folders. Make it 3 by default and configurable from 1 to 20.

## 2. Previous structure

- `ScanWorker` merged quick-loaded stored pairs and this scan's emitted pairs in `allMatches_` and saved them wholesale. The save deletes rows absent from the set, but the set itself still contained the old pairs.
- The GUI union-find (`pathParent_`) also kept the old edges from the scan-start quick-load and only added new pairs, so the old group stayed visible.
- Recent folders were capped at 2 in `beginScan` (`while (recent.size() > 2)`).

## 3. New structure

- **Engine**: new `ScanControl::onChangedFile` callback. Every path re-analyzed this scan (new/modified/pending/regrid) is reported to the worker.
- **Worker**: stored pairs (`storedPairs_`) are separated from this scan's emissions (`storedCount_` = stored prefix length). Persistence now:
  - drops stored pairs touching a re-analyzed path,
  - keeps every pair emitted this scan (emitted wins on a duplicate key).
  - Checkpoints and the final save use the same set, and the detailed-log counters count that set.
- **GUI**: when a scan that started with a result set on screen re-analyzed files (`analyzed>0`, Test Mode excluded), the stored index is **silently reloaded** after completion, rebuilding the list/previews from the corrected DB.
  - The scan summary/status (analyzed/unchanged/verify) is kept, and the sort/selection (representative path/selected file) is restored.
  - No load popup (`silentReload_`). A scan with no analyzed files (analyzed=0) leaves the view untouched as before.
- **Recent folders**: new `ui/recentFolderLimit` (default 3, range 1-20). The MRU cap in `beginScan` follows it; saving Settings trims the existing list immediately and refreshes Favorites. A "Recent folder count" spin box is added to Settings > General.

## 4. Result

- Replacing one file no longer leaves the old group after a Fast search; both the DB and the view reflect the new verdict.
- Test Mode and normal scans agree on verdicts/index results (schema/protocol unchanged).
- Favorites can show 3 recent folders by default and up to 20 via Settings.

## 6. Impact and limits

- Schema/protocol/engine version unchanged. Invalid pairs no longer survive in the DB.
- A changed scan re-reads the stored set once after completion, adding a small completion cost on large datasets (unchanged scans are unaffected).
- Test Mode is excluded from the re-apply (the scratch result stays on screen; the existing Yes/No decides adoption).
- Lowering the recent-folder count trims the list immediately; raising it fills from later scans.
