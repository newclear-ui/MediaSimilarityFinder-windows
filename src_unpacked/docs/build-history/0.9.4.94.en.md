# MediaSimilarityFinder v0.9.4.94 — Completion-path dedup + scroll-jump fix

Baseline `0.9.4.93` -> this build `0.9.4.94`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged.

## 1. Why

Two user reports:

1. **Log generation never completes after a search finishes.** Completion is reported, but the "writing report" phase looks stuck for a long time, or a damaged detailed-log record vanishes with no dialog at all.
2. **Scrolling down past a level with keyboard/mouse jumps the view back to the top.** Same as the scroll jump deferred to "next build" in 0.9.4.93.

## 2. Previous structure

- **Double rebuild on the completion path**: on a normal finish the `ScanWorker` emits `results → telemetryReady → finished`, and the GUI ran the **same full rebuild** (`rebuildGroups + refreshGroupList + refreshFileViews + refreshDetail`) twice — once in `onResults()`, once in `scanFinished()`. With thousands of groups the GUI thread is pinned twice, so the report popup shows twice at length with the detailed-log modal in between, reading as "the report never finishes".
- **Silent detailed-log parse failure**: `showDetailedLogDialog()` ended with a bare `return` on JSON parse failure. No dialog, no message, so a damaged record is indistinguishable from "no log generated".
- **Batched layout clamp**: the middle `imgGrid_/vidGrid_` used `QListView::Batched`. A `doItemsLayout()` call restarts batching from row 0, so the scrollbar maximum **collapses** to the first batch and regrows as later batches land. A deep offset restored against the small maximum stays clamped after the maximum recovers, leaving the view near the top. Shallow scrolls fit inside the then-maximum and restore fine, hence "only past a depth". Measured (regression test, 120 groups): 30x `scrollToBottom → doItemsLayout` never converged (value 14461 vs maximum 17491).
- **Anchorless right-pane rebuild**: `refreshFileViews()` ran `grid_->clear(); list_->clear();` with no scroll save/restore, so every refill (streaming, finish, zoom) sent the file list to 0.

## 3. New structure

- **Completion dedup** (`gui/mainwindow.cpp`, `gui/mainwindow.h`): the scan branch of `onResults()` sets `resultsApplied_ = true` after rebuilding (the load branch does not). `scanFinished()` skips the four rebuilds when `resultsApplied_ && !CANCELLED` and only updates summary/status. Cancelled scans never pass through `onResults`, so they always rebuild. The flag is cleared at scan start (`setRunning(true)`) and at load start.
- **Detailed-log failure reporting**: on parse failure the status bar shows `detailLogParseFail` ("상세 로그 열기 실패 (기록 손상)" / "Could not open the detailed log (record damaged)") and `msf_scan.log` records the offset and reason. Added the key to the translation table and the `ui_translation_keys_test` key list.
- **SinglePass switch**: both middle grids moved from `Batched` to `SinglePass`. Uniform-cell layout is cheap, so one synchronous full pass is reasonable, and every explicit `doItemsLayout()` (append, rebuild, thumbnail flush, delegate switch) now observes the final geometry. Spontaneous relayouts (resize etc.) no longer disturb the value either. The `fillPair` anchor-restore logic itself is unchanged (it now sees the exact maximum).
- **Right-pane scroll preservation** (`refreshFileViews()`): both scrollbar values are saved before recreating rows and restored after `doItemsLayout()` when the signature (`currentGroup_|file count|first path|last path`) matches. A newly selected group changes the signature and still starts at the top.

## 4. Result

- A normal finish now rebuilds once for the "writing report" phase; one popup plus the summary update remain. Cancel/failure/load paths behave as before.
- Damaged detailed logs are reported via status message and scan log. Saving stays manual (the dialog's Save button), as before.
- Deep scroll survives full rebuilds, streaming refills, and zoom. Switching groups still shows the right pane from the top.

## 6. Impact and limits

- The scan completion signal order (`results → telemetryReady → finished`) and IPC are unchanged. `kProtocol` unchanged.
- `resultsApplied_` is a one-shot mark valid for one scan only. Backend restarts/auto-resumes are new scans, so the flag resets.
- The SinglePass switch concentrates per-refill synchronous layout cost into one tick instead of spreading it across batches. Item creation dominates (recorded ~1s at 11k groups), so this is within budget; the scroll gate and append paths are unchanged.
- The trailing completion fingerprint (long on cache miss) stays as designed. Its progress display (`fingerprintProgress` → status-bar files/GB) already prevents a freeze misread.
- The CUDA-unavailable cause is still handled in the next build.
