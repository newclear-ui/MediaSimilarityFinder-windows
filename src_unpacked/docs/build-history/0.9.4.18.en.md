# MediaSimilarityFinder v0.9.4.18 — D2 Barrier Review (video completion order)

D2 validation baseline. Nominates barrier candidates citing D1a/D1b
evidence and executes in pre-register order (measure → quantify →
change → parity → gate). Engine 1.5.0, DB 1.0.3, cache v9 unchanged;
schema 4 → 5.

## Why the change was needed
- Index-ordered joins in video ranges stall finished results behind a
  slow head file (head-of-line). Structural waiting under real-world
  file-time variance.

## Pre-register (recorded before code changes)
- Measured bottleneck: one slow file dominates range walls; completions
  wait. `maxRangeFileMs` quantifies it from JSON alone.
- Expected gain: up to (max−min) per high-variance range, ~0 when
  uniform.
- Rollback criterion: parity break or measured regression → revert the
  join hunk (telemetry stays).

## Previous structure
- `for(f:futs) f.get()` ordered join. Same thread count and topology.

## New structure
- Completion-order harvest (same threads, same joins; only the harvest
  sequence changes). 5 ms idle bound per range, negligible against
  seconds-long builds. Cancel semantics preserved (post-stop completions
  still joined and discarded).
- `recordVideoRange(files, maxFileMs)` plus `maxRangeFileMs` (range
  maximum). Failed ranges stay unrecorded (documented).
- Schema v5 (new-key rule followed).

## Why this shape
- Dependency check: DB upserts, progress, and files accumulation are
  order-independent; only live order changes (not a correctness
  contract). Image phase joins, walker poll, and DB serialization carry
  real dependencies and were excluded (analysis on record).

## Resolved state
- Straggler-wait structure removed. Next is D3 queues (on D1b depth
  evidence).

## Accuracy impact
- Parity suites green on both trees prove order-independence.
  Identical `scan_workflow_test` on both.

## Compatibility impact
- Benchmark JSON additive extension (schema 5). Existing keys kept.
