# MediaSimilarityFinder v0.9.4.28 — D2 CreateDecoderFromFilename 내부 비용 / WIC Decoder 진입경로 비교

Status: **PRE-REGISTERED** (D2 코드 변경 전에 커밋된다)

D2 는 **measurement** 빌드다. 최적화하지 않는다.

---

## 1. 변경 필요성

D1 은 두 질문에 답하고 하나를 남겼다.

```text
D9d: decode ≈ 4.4654 ms/call
D1:  CreateDecoderFromFilename ≈ 2.6257 ms/call
     OS CreateFileW reference   ≈ 0.0576 ms/call
     Factory2 25,898 attempts / 25,898 successes / 0 fallbacks
```

D1 은 `open` 버킷의 97.8 % 가 WIC 고유임을 확인했고, Factory2 fallback 이나
raw OS file I/O 로는 설명되지 않는다는 것을 보였다. 더 나아갈 수 없었던 이유는
`CreateDecoderFromFilename` 가 단일 불투명 호출이기 때문이다.

따라서 D2 는 **다른 WIC 진입점이 더 빠를 것이라고 가정하지 않는다.** 대안을
측정한다.

이 빌드가 막으려는 위험한 추론:

> "`CreateDecoderFromFilename` 가 느리니 `CreateDecoderFromFileHandle` 나
> `CreateDecoderFromStream` 이 더 빠를 것이다."

이는 추측이다. D2 는 이것을 수치로 바꾸거나 기각된 상태로 남긴다.

## 3. dataset 변경 — 본질적 이탈이며 그 사실로 기록한다

**지시는 형식별 분석(§15, §16)을 요구하면서 D8b fingerprint 유지를 요구한다
(§27). 두 요구는 충돌하며, 충돌은 형식 분석을 우선하는 쪽으로 해결했고
dataset 변경은 사용자가 명시적으로 승인했다.**

D8b dataset 은 **BMP 100 %** 다 — 확장자가 아니라 2,700개 전부 매직 바이트를
읽어 확인했다. 단일 형식 dataset 으로는 지시가 요구하는 "JPEG ≠ BMP ≠ PNG"
분석이 불가능하며, BMP 만으로 "WIC decoder 가 2.6257 ms 다"라고 일반화하는
것은 이 지시가 경고하는 바로 그 오류다.

사용자 지시에 따라 `G:\Downloads\ss_twit` 에서 샘플을 선별하되, 확장자가
아니라 **매직 바이트로 검증**하고, 편향을 피하기 위해 **크기 계층별로
분층**하여 `C:\project\test_sample_img_vid\images\format\` 에 복사했다.

| 형식 | 파일 수 | 선별 방식 |
|---|---:|---|
| BMP (기존) | 2,700 | 변경 없음 |
| JPEG | 200 | 크기 분층, ≤ 1 MB |
| PNG | 200 | 크기 분층, ≤ 1 MB |
| WEBP | 200 | 크기 분층, ≤ 1 MB |
| GIF | 20 | 크기 분층, ≤ 4 MB |

복사 후 추가된 620개 전부를 매직 바이트로 재검증했다(불일치 0).

**결과를 먼저 밝힌다.**

```text

total bytes  36,007,560     ->  100,579,845 (95.9 MB)
```

즉 **D2 의 합계는 D9a…D1 의 절대 합계와 직접 비교할 수 없다.** 그 baseline 은
모두 2,700개 BMP dataset 에서 측정됐기 때문이다. per-call 과 per-format 수치는
비교 가능하지만 dataset 전체 집계는 그렇지 않다. 보고서는 이를 명시하고,
dataset 이 그대로인 것처럼 D1-D2 합계 차이를 제시하지 않는다.

첫 시도는 최대 크기까지 800개를 뽑아 2.16 GB 를 추가했고 dataset 을 잠식했다.
이는 폐기하고 위 크기 상한으로 재선별했다. "적당히"는 36 MB dataset 을 수 GB 로
만들어서는 안 되기 때문이다.

## 4. D2 가설

최적화 관점의 가설은 없다. 세 가지 가능성이 모두 열려 있고, 이 빌드는
구분할 수 있도록 설계된다.

- **경우 A** — handle 또는 stream 진입점이 체감상 빠르다면, WIC 내부의
  filename 경로 특화 오버헤드를 시사한다.
- **경우 B** — 셋이 비슷하다면 decoder 활성화 또는 codec 초기화가 지배적이고
  진입점이 레버가 아니다.
- **경우 C** — 경로 차이가 주로 파일 형식에 따른다면, codec 특화 decoder
  초기화 문제다.

## 5. 비교 경로

코드를 쓰기 전에 Windows SDK 헤더(`wincodec.h`, SDK 10.0.26100.0)에서 세
진입점의 **존재를 확인**했다.

```text
IWICImagingFactory::CreateDecoderFromFilename(LPCWSTR, GUID*, DWORD, IWICBitmapDecoder**)
IWICImagingFactory::CreateDecoderFromFileHandle(ULONG_PTR, GUID*, DWORD, IWICBitmapDecoder**)
IWICImagingFactory::CreateDecoderFromStream(IStream*, GUID*, DWORD, IWICBitmapDecoder**)
IWICImagingFactory::CreateStream(IWICStream**)
```

`IWICStream` 은 `IStream` 을 상속하므로 `CreateDecoderFromStream` 에 직접
넘길 수 있다.

| Path | 단계 | 역할 |
|---|---|---|
| **A** | `CreateDecoderFromFilename` | production baseline |
| **B** | `CreateFileW` → `CreateDecoderFromFileHandle` | 측정 전용 |
| **C** | `CreateFileW` → `IStream` 어댑터 → `CreateDecoderFromStream` | 측정 전용 |

Path A 는 production 과 **동일한** `metadataOptions`, desired access,
vendor GUID 를 사용하므로 수치가 D1 과 직접 비교 가능하다.

Path B/C 는 **측정 전용**이며 `decode()` 에 연결하지 않고, 이 빌드에서 제품
경로로 채택하지 않는다.

### 사전 등록 대비 Path C 정정 (구현 단계에서 확인)

사전 등록은 Path C 를 `CreateFileW` → `CreateStream`(IWICStream) →
`InitializeFromFilename` → `CreateDecoderFromStream` 으로 적었다. 구현 시
다음을 확인해 **pre-register 커밋(`3a494e7`)의 내용을 정정한다.**

1. **`IWICStream` 에 `InitializeFromHandle` 이 없다.** SDK `wincodec.h` 의
   `IWICStream` 은 `InitializeFromFilename` 과 `InitializeFromIStream` 만
   제공한다. 그래서 `InitializeFromFilename` 을 쓰면 우리가 연 `CreateFileW`
   핸들이 **stream 에 연결되지 않고 버려진다.** 그러면 Path C 는 "버려진
   `CreateFileW` + WIC 내부의 두 번째 open" 을 재는 것이라 비교 대상이 아니다.
2. **`CreateStreamOnHANDLE` 은 존재하지 않는다.** `ole32.lib` 과 `ole32.dll`
   양쪽에 symbol 이 없다(추측이 아니라 실제 확인함). HANDLE → IStream 을
   만들어 주는 OS API 가 없으므로, 직접 어댑터(`HandleStream`)를 구현한다.

따라서 Path C 는 `CreateFileW` → `HandleStream`(직접 구현한 IStream) →
`CreateDecoderFromStream` 으로 변경했다. 이 경로는 디코더가 실제로 우리가 연
핸들로 읽게 되므로, 진입 경로의 비용을 의도대로 측정한다.
**대안 설계 절충**: 이 어댑터는 우리가 유지·정비해야 하는 코드가 되며, 측정된
수치에는 이 어댑터 비용이 포함된다. 이 점을 다음 단계 판단에 반드시 반영한다.

## 6. 계측 경계

각 metric 은 정확히 한 호출만 측정하며, 다른 metric 안에 중첩되지 않는다.

```text
fileOpenMs          CreateFileW                          (B·C 전용, A 는 N/A)
streamCreateMs      사용하지 않음 (Path C 정정으로 제거) → 리포트에 미기록
streamInitMs        HandleStream 생성 (직접 구현한 IStream) (C 전용)
decoderFilenameMs   CreateDecoderFromFilename          (A)
decoderFileHandleMs CreateDecoderFromFileHandle        (B)
decoderStreamMs     CreateDecoderFromStream            (C)
combinedPathMs      A: decoderFilenameMs
                    B: fileOpenMs + decoderFileHandleMs
                    C: fileOpenMs + streamInitMs + decoderStreamMs
```

`combinedPathMs` 는 자기 구성요소의 합이며 함께 보고할 뿐 더하지 않는다.
어떤 시간도 두 번 세지 않는다.

## 7. Scope

timer, counter, HRESULT 기록, 단계 counter, profiling telemetry,
instrumentation 을 검증하는 test. D9d 의 `DecodeTelemetry` 를 **재사용·확장**
하며 두 번째 telemetry 체계를 만들지 않는다.

측정 helper 는 `image_decoder.h/.cpp` 에 명시적으로 호출되는 probe 로 둔다.
`ImageDecoder::decode` 와 `decodePreserveAspect` 에 **모드 스위치를 추가하지
않으며** 동작도 바꾸지 않는다.

## 8. Non-goals

지시에 따라 D2 에서 하지 않는다.

```text
제품 경로를 FileHandle 또는 Stream 으로 교체
factory / decoder / stream / file-handle 재사용
중복 decode 제거
cache 변경
EXIF, metadata option, resize, format conversion, copy 변경
threading 또는 parallelization 변경
candidate, threshold, grouping, verdict 변경
확장자로 decoder CLSID 를 직접 선택 (형식 탐색 동작을 바꾸므로)
기존 test 완화 또는 삭제
```

지시 §17 을 직접 지킨다. 확장자로 decoder 를 고르지 **않는다.** 세 경로 모두
production 과 동일하게 WIC 가 형식을 탐색하게 하므로, 비교는 진입점만을
고립하고 형식 탐색 변경을 섞지 않는다.

Factory2 fallback 은 후보로 다시 올리지 않는다(D1: fallback 0회), cache mutex
도 다시 올리지 않는다(D1: 총 71.5 ms). 두 항목 모두 회귀 확인만 한다.

## 9. 정확성 위험

instrumentation 은 decoder **생성**만 다룬다. 디코딩은 다루지 않는다.

- `verifyCalls`, `verifyDecodeMisses`, `verifyCacheHits`, `ssimEvals`,
  `frameSsimEvals`, `groups`, 최종 verdict 불변.
- probe 는 production decode 결과를 바꾸지 않아야 한다. 별도 진입점이며
  benchmark 드라이버에서만 호출된다.
- Path B/C 는 "호출이 성공했다" 만으로 검증하지 않는다. 각각 `GetFrame(0)` 과
  합리적인 픽셀 크기를 얻어야 한다. decoder 를 만들지만 frame 을 내지 못하는
  경로는 실패로 세고 보고한다. 성공 샘플만 골라 평균내지 않는다.

## 10. 호환성 위험

Path B/C 는 측정 전용이며 Windows 로 compile-guard 하므로 CPU 전용 빌드와
non-WIC 빌드에 영향이 없다. `image_decoder.cpp` 에 이미 non-WIC 분기가 있으므로,
probe 는 거기서 0 을 만들지 않고 `not_available` 로 보고한다.

Path C 는 일부 입력에서 정당한 실패가 가능하다(파일명으로 초기화된 WIC stream 은
seek 의미가 다르다). 실패는 HRESULT 과 함께 기록하며, 성공 샘플만 골라 평균내는
방식으로 **숨기지 않는다.**

## 11. 측정 계획

- 동일 하드웨어, OS, GPU, build configuration, cold-index 조건.
- **최소 5회**, 경로별·형식별 mean/median/min/max/range.
- 세 경로는 같은 실행 안에서 같은 파일에 대해 시간 측정하므로 비교가 **쌍짜리**
  이고 run 간 편차가 세 경로에 동일하게 작용한다.
- 3.7~7.5 % 편차 환경에서 1~2 % 차이는 개선이 아니다.
- 경로 순서를 `A < B < C` 단순 순위로 읽지 않는다. 경로마다 내부 작업이
  다르고, 보고서는 **차이가 어디서 발생할 수 있는가**를 해석한다(§13).

## 12. noise 고려

각 경로의 첫 호출은 일회성 비용(DLL 해석, codec 로드)을 치를 수 있고 이후
호출은 치르지 않는다. 경로별·형식별로 **warm-up 호출 1회를 수행하고 제외**하며,
이는 추정하지 않고 보고서에 명시한다.

범위를 줄이거나 중단하고, 고쳐 돌리지 않고 기록한다.

### 해석상 반드시 함께 봐야 하는 사항

1. **tiff A 의 mean(5.41) 은 쓰지 않는다.** median 0.1974 인데 max 가
   73.2 ms 였다. 단일 파일 이상치(tiff 컨테이너의 특정 변형)이며 형식 전체
   비용을 대표하지 않는다. tiff 는 median 으로만 판단한다.
2. **첫 호출의 cold-start 는 별개 비용이다.** warm-up 없이 단일 파일을 재면
   A 가 2.3~4.1 ms 로 측정되었다. 이건 코덱 DLL 최초 로드이며 경로와 무관하게
   프로세스당 한 번만 발생하는 비용이다. production 스캔에서는 이미 감산되므로
   **warm-up 후 수치가 production 해당 비용에 가깝다.** 반대로 D1 의
   `CreateDecoderFromFilename ≈ 2.6 ms` 는 이 cold-start 가 섞인 값이므로,
   D1 과 D2 를 **동일 조건으로 비교할 수 없다.** 이 차이는 성능 변화가 아니라
   측정 조건 차이다.
3. **성공/실패는 세 경로가 완전히 동일하다.** ico 4개 / tiff 1개 는
   `0x88982F60` (`WINCODEC_ERR_COMPONENTNOTFOUND`) 로 A·B·C 가 똑같이 실패한다.
   의도적으로 넣은 비정상 픽스처(`truncated_mask_32bpp.ico`,
   `cmyk_u8_*_case.tif` 등) 이며, 진입 경로를 바꿔도 판정 가능성은 달라지지
   않는다. 견고성 관점에서 유지한다.
4. **Path C 수치에는 우리 구현한 `HandleStream` 비용이 포함된다.**
   `streamInitMs` 는 0.0003 ms 로 사실상 무시 가능했지만, 채택 시 유지보수
   부담이 따라온다.
5. **절약 규모는 작다.** 파일당 약 0.02 ms. D1 스캔 규모(25,898 파일)로는
   총 0.5 s 수준이므로, D1 이 open 97.8% 라고 결론 내린 근거와 함께 봐야 한다.

|---|---:|---:|---|
| bmp  | 0.0748 → 0.2479 | 0.0539 → 0.0646 | A > B > C 유지 |
| jpg  | 0.0816 → 0.2773 | 0.0582 → 0.0724 | A > B > C 유지 |
| png  | 0.0985 → 0.2697 | 0.0686 → 0.0734 | A > B > C 유지 |
| webp | 0.1198 → 0.3439 | 0.0993 → 0.1288 | A > B > C 유지 |
| gif  | 0.0957 → 0.3891 | 0.0808 → 0.1054 | A > B > C 유지 |

| ico  | 0.0996 → 0.3452 | 0.0753 → 0.1139 | A > B > C 유지 |

- **경우의 순서는 7개 형식 전부에서 두 실행이 동일하다.** 결론( C 가
  decoder 단계에서 최단)은 재현된다.
- 성공/실패 parity 도 동일하다 (ico 8/4, tiff 13/1, 동일 HRESULT).
- **절대값은 머신 부하에 의존한다.** 따라서 위 표의 16~30 % 라는 숫자는
  특정 실행 조건의 값이지 고정 상수가 아니다. 두 번째 실행에서는 상대 격차가
  오히려 더 크게 나타났다(63~74 %).
- **이것은 §19 의 판단을 강화한다.** "파일당 약 0.02 ms" 도 부하에 따라 달라지는
  값이므로, 이를 근거로 제품 채택을 정당화할 수 없다.
- tiff A 의 max 는 두 실행 모두 극단적(73.2 ms → 100.1 ms)으로, **mean
  폐기 판단이 재확인**되었다.

### 상태

`PASS` — 비용 구조가 충분히 측정되었다. **성능 개선은 아직 주장하지 않는다.**
D2 는 measurement-only 이므로 production 경로는 그대로다.

## 15. D2 구현 중 발견한 실제 버그 3건 (영구 보존)

D2 는 측정 전용 코드였지만, 구현 과정에서 **실제로 동작하지 않는 3가지 결함**이
발견됐다. 성공 여부와 무관하게 장기 기록한다.

### Bug 1 — Path B handle lifetime (use-after-close)

- **원인**: `CreateDecoderFromFileHandle` 로 만든 decoder 를 `GetFrame(0)` 으로
  검증하기 **전에** `CloseHandle` 을 호출했다.
- **문제**: decoder 는 해당 handle 을 계속 참조하며 `GetFrame` 안에서 읽을 수
  있으므로, 닫힌 handle 을 읽는 use-after-close 가 된다. 실제로 access
  violation 으로 이어졌다.
- **수정**: `validateFrame()` 이 끝난 뒤 decoder 를 해제하고 그 다음에
  `CloseHandle` 하도록 순서를 바꿨다.
- **확장 규칙**: 진입 경로를 교체할 때 caller 가 연 handle 의 수명은
  "디코더 생성" 이 아니라 "디코더 사용이 끝날 때까지" 다.

### Bug 2 — Path C 가 잘못된 stream 을 연결

- **원인**: 초기 구현이 `IWICStream::InitializeFromFilename` 을 썼다.
- **문제**: `IWICStream` 에는 `InitializeFromHandle` 이 없어, 우리가 직접 연
  `CreateFileW` handle 이 **decoder 입력에 연결되지 않고 버려졌다.** 결과적으로
  "버려진 `CreateFileW` + WIC 내부의 두 번째 filename open" 을 측정하게 되어
  비교 자체가 무의미했다.
- **수정**: §5 의 Path C 정정대로 HANDLE→IStream 어댑터(`HandleStream`)를 직접
  구현해 디코더가 실제로 우리가 연 핸들로 읽게 했다.
- **확장 규칙**: "진입 경로"를 비교할 때, 각 경로가 **동일한 자원을 읽는지**
  먼저 확인한다. 다르면 그 비교는 버린다.

### Bug 3 — COM lifetime

- **원인**: probe 가 `CoUninitialize()` 를 직접 수행했다.
- **문제**: scope 종료 시 access violation. `CoUninitialize` 가 apartment 를
  정리하는 과정에서 마지막 참조를 잃은 코덱 DLL 이 정리되는데, 그 위에 남아
  있던 스택이 사용 불가 상태가 된다.
- **수정**: probe 는 COM 을 **초기화만 하고 해제하지 않는다.** 수명은 소유
  프로세스가 갖는다.
- **해결 근거**: `src/image_decoder.cpp` 150~153 행에 **이미 같은 사례가
  문서화**돼 있었다("helpers must never touch COM lifetime themselves").
  규칙은 이미 존재했고 probe 가 이를 따르지 않은 것이 문제였다.
- **확장 규칙**: **COM 수명은 caller ownership 을 따른다.**

## 16. `CreateStreamOnHANDLE` 오판과 정정 (방법론 기록)

- **초기 추측**: Bug 2 를 해결하려고 `CreateStreamOnHANDLE` 을 사용했다.
- **실제 확인 결과**: `ole32.lib` 과 `ole32.dll` **양쪽에 symbol 이 없다.**
  추측이 아니라 실제 확인으로 무효임을 확정했다.
- **정정**: Windows 는 HANDLE→IStream 어댑터를 제공하지 않으므로 직접
  구현했다(`HandleStream`).
- **기록 이유**: 이 과정은 `pre-register` 와 Build History 에 **투명하게
  남겼다**(§5). 성공한 수정만 남기고 실패한 추측을 지우면, 같은 착각을 다음
  작업이 반복한다.
- **확장 규칙**: **존재 여부를 확인하지 않고 Windows API 를 추측하지 않는다.**

## 17. parity / 동일성 확인

- 세 경로의 **성공/실패 패턴은 완전히 동일**했다.
- 실패는 ICO 4개, TIFF 1개이며 모두 `0x88982F60`
  (`WINCODEC_ERR_COMPONENTNOTFOUND`) 로 A·B·C 가 **똑같이** 실패한다.
- 따라서 Path C 가 특정 입력을 선택적으로 성공시켜 수치를 유리하게 만든
  결과가 **아님**을 확인했다.
- 성공한 파일에서는 세 경로 모두 같은 frame(0) 과 같은 dimension 을 반환했다.
  예) `fax4.tiff` → 460x307, `smile.ico` → 16x16 (경로 3종 모두 동일).
- **의도적 비정상 fixture**(`truncated_mask_32bpp.ico`, `cmyk_u8_*_case.tif` 등)는
  삭제하지 않고 유지한다. 견고성 관점에서 가치가 있다.

## 18. Path C 최종 결정 = `DEFERRED`

`CreateDecoderFromStream` + `HandleStream` 을 **지금 제품에 채택하지 않는다.**

1. **절대적 기대 이득이 작다.** decoder 단계 개선은 있으나 현재 병목 대비
   규모가 작다.
2. **유지보수 비용이 증가한다.** 직접 구현한 `HandleStream` 을 장기 관리해야
   한다: HANDLE lifetime, IStream semantics, Read/Seek/Stat/Clone, close
   semantics, COM 상호작용, Windows 호환성.
3. **production full-path 검증이 아직 없다.** D2 는 decoder entry timing
   비교이지 전체 production scan benchmark 가 아니다.
4. **절대값이 머신 부하에 의존한다.** 재현 확인에서 동일 코드가 머신 부하에
   따라 약 3배 다른 절대값을 냈고(§14), 상대 격차도 16~30 % 와 63~74 % 로
   갈렸다. 이 정도로 변동하는 수치를 근거로 제품 채택을 정당화할 수 없다.

**`REJECTED` 가 아니라 `DEFERRED` 다.** 영구 폐기가 아니다. 재검토 조건:

```text
1. WIC decoder 경로가 다시 전체 bottleneck 의 큰 비중을 차지할 때
2. full production benchmark 에서 의미 있는 절감이 확인될 때
3. HandleStream 이 다른 기능에서도 재사용될 때
4. decoder architecture 가 변경될 때
5. Windows/WIC runtime 환경이 달라질 때
```

## 19. 기대 효과의 정확한 표현

- 파일당 약 0.02 ms 의 decoder 단계 절감이 예상된다.
- D1 과 유사한 25,898 calls 를 단순 환산하면 약 0.5 수준이지만, **이 값은
  production full-path 측정값이 아니다.**
- 따라서 **"전체 scan 에서 약 0.5초가 확정적으로 줄어든다"** 라고 기록하지
  않는다. 정확히는 **"decoder-only timing 을 단순 환산하면 약 0.5초 수준의
  잠재적 절감량이지만, production full-path 에서는 아직 검증되지 않았다."**
- 전체 스캔 약 120초 기준 대략 0.4 % 규모로 환산되나, 이것도 **단순 추정치**다.
  production 경로에서는 file open / decoder / GetFrame / CopyPixels /
  conversion / resize / cache / verify 와 함께 발생하므로 전체 성능 개선으로
  간주하지 않는다.

## 20. D1 과의 직접 비교 금지 (재확인)

```text
D1        CreateDecoderFromFilename ≈ 2.6257 ms/call
D2 warm-up 약 0.07~0.12 ms
```

이 차이는 **성능 개선이 아니다.** D1 에는 코덱 DLL 최초 로드 등이 포함되고,
D2 측정은 warm state 에서 이루어졌기 때문이다. **측정 조건이 달라 직접 비교할
수 없으며, warm-up 이후 decoder call 비용을 새롭게 확인했다.** `95 % 향상`
으로 계산하지 않는다.

## 22. 다음 후보 — D3 (v0.9.4.29)

다음 성능 조사 후보를 **D3 = decode / decodePreserveAspect 중복 비용 계측**으로
정의한다. 이번 작업에서 D3 source implementation 은 하지 않는다.

- 목적: miss 1건당 두 번 수행되는 `decode` 와 `decodePreserveAspect` 가 실제로
  얼마나 많은 wall-clock 비용을 발생시키는가.
- 최소 계측: `decodeCount` / `decodeTotalMs`,
  `decodePreserveAspectCount` / `decodePreserveAspectTotalMs`. 가능하면
  open / factory / decoder / frame acquisition / pixel decode / resize /
  format conversion / copy 의 기존 telemetry 연결.
- D3 에서는 **중복 decode 를 제거하지 않는다.** cache / merge / dedup /
  HandleStream 채택 / factory·stream·decoder reuse 는 하지 않는다. 숫자를
  먼저 얻는다.
- 핵심 질문: `decodePreserveAspect` 가 동일 파일을 두 번째로 읽으며 발생시키는
  추가 비용은 expensive verify 전체에서 몇 %인가.
- 판단은 D3 수치를 얻은 뒤에만 한다. (예: second decode 가 0.02 ms 면 우선순위
  낮음, 4 ms 면 강력한 후보)
- D3 pre-register 는 별도 작업으로 `docs/build-history/0.9.4.29.ko.md` +
  `.en.md` 에 만든다.

## 24. 기대 결과

성공은 측정된 비용 구조이지 속도 개선이 아니다.

```text
1. 동일 metadata 옵션과 동일 파일로 세 진입점 비용 비교

```

최종 상태는 PASS / PARTIAL / INCONCLUSIVE / FAIL 중 하나이며, 비용 구조가
