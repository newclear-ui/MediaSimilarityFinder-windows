# MediaSimilarityFinder v0.9.4.20 — D4a Backend Internal Timing

D4a 진입. **D4 전체가 아니라 계측(measure) 단계만** 수행한다.
엔진 1.5.0·DB 1.0.3·캐시 v9 불변, benchmark schema 6→7.

> 이 문서는 **코드 변경 전에** 작성되어 커밋 순서로 감사 가능하다.
> build/test 결과는 구현·검증 후에만 채운다 (PENDING 상태에서는 PASS를
> 기록하지 않는다).

**D4a does not implement transfer/compute overlap. It only establishes
backend-internal timing evidence required before evaluating D4b overlap.**

---

## Pre-register (코드 변경 전 기록)

### 예상 효과

```
- 현재 GPU hashBatch 내부의 H2D / kernel / D2H device timing을
  분리 관측 가능하게 만든다.
- 기존 cudaStreamSynchronize()가 host wall time에 미치는 영향을
  host 측 직접 측정으로 확인할 수 있다.
- "transfer가 느린가"가 아니라 "H2D / kernel / D2H / synchronization 중
  현재 wall time을 지배하는 요소가 무엇인가"를 실측으로 판정한다.
- 향후 D4b overlap 여부를 실측 근거로 결정할 수 있다.
```

### 기대하지 않는 것

```
- 이번 버전 자체의 성능 향상 (계측만 한다)
- transfer/compute overlap 구현
- double / triple buffering
- pinned-memory 최적화
- 새로운 CUDA stream topology 또는 stream pool
- producer/consumer CUDA overlap
- transfer bandwidth 최적화
- GPU throughput 향상
- CPU/GPU pipeline 재설계
- 새 GPU queue
- Scheduler 변경 / CPU-GPU share formula 변경
- D5 batching, D6 starvation, D7 allocation-proportional dispatch
- NVDEC, 새 GPU backend
```

### 롤백 기준 (하나라도 해당하면 timing 훅 revert)

```
- GPU correctness regression
- CPU fallback regression
- CUDA build regression
- 기존 CTest regression
- 측정 코드가 GPU 처리 semantics에 영향을 줌
- benchmark overhead가 비정상적으로 증가
```

## 1. D4a 진입 필요성

D1a에서 `addImageTransferMs()` / `addImageExecMs()` / `addImageGpuQueueMs()`
가 telemetry 필드로 **정의만 존재**하고 호출자가 0개인 상태가 확인되었다.
그래서 현재 JSON의 `gpuTransferState` / `gpuExecState` /
`gpuQueueWaitState`는 `not_measured`가 정상이며, 0 위장이 아니다.

원인은 추상화 경계에 있다. CUDA device-side 타이머가 backend 내부에
전혀 없고, 상위 계층이 backend 호출을 감싸면 전송과 커널 실행이
한 덩어리로 측정된다. D4 brief §D4가 요구하는 평가 항목
(transfer time / GPU execution time / synchronization time 분리)은
**내부 타이밍 지점이 없이는 측정 자체가 불가능**하다.

D4a는 그래서 "최적화"가 아니라 "측정 가능 상태"를 만드는 게이트다.

## 2. 현재 hashBatch 구조

`src/cuda_backend.cu` `msf_cuda_backend_hash_batch()`:

```
ensure_capacity
    ↓
cudaMemcpyAsync(H2D)
    ↓
msf_phash_kernel<<<>>>
    ↓
cudaMemcpyAsync(D2H)
    ↓
cudaStreamSynchronize
```

`src/media_pipeline.cpp` 는 이 전체를 `addGpuBatchMs()` 한 줄로 기록한다.
따라서 현재 `gpuBatchMs` = H2D + kernel + D2H + synchronization의 합이고
어느 지배 요소인지 알 수 없다.

`cudaEvent_t` 는 파일 전체에 존재하지 않는다.

## 3. 기존 telemetry의 한계

- `gpuBatchMs` : 경계 미분리 단일 값
- `gpuTransferMs` / `gpuExecMs` / `gpuQueueWaitMs` : 정의만 있고 호출자 없음
  (state = `not_measured`)
- 측정 실패를 0으로 기록하지 않는 규칙은 지켜지고 있으나,
  **측정 자체가 불가능**하므로 D4 판단에 쓸 근거가 없다.
- B5 과거 기록의 ≈86 ns/장 transfer는 당시 조건의 값일 뿐,
  현재 workload의 지배 요소를 대신하지 않는다.

## 4. CUDA internal timing 도입 이유

D4 brief §D1b transfer observability 조항이 명시한 조건 —
"backend abstraction 아래에서 구현된 내부 timing point" — 을
`cuda_backend.cu` 안에서만 만족시킨다.

`GpuBackend`가 상위 계층과 `.cu` 사이의 유일 경계이므로,
backend 내부에 두면 CUDA 타입이 엔진 / 파이프라인 / recorder로
퍼지지 않는다. 상위에는 POD 값만 올라온다.

## 5. timing point 정의

같은 CUDA stream에 순서대로 기록한다 (실제 실행 순서 반영).

```
event  h2dStart   기록
        cudaMemcpyAsync(H2D)
event  h2dEnd     기록
event  kernelStart 기록
        kernel launch
event  kernelEnd   기록
event  d2hStart   기록
        cudaMemcpyAsync(D2H)
event  d2hEnd     기록
        cudaStreamSynchronize   ← host 대기 지점
```

이벤트는 backend 생성 시 1회 생성하고 재사용한다
(호출마다 생성하면 per-call overhead가 측정값을 오염시킨다).

## 6. 각 metric의 의미

| metric | 정의 |
| --- | --- |
| `h2dDeviceMs` | device event 간격. stream 위 H2D 복사의 **device 실행 시간** |
| `kernelDeviceMs` | device event 간격. pHash kernel의 **device 실행 시간** |
| `d2hDeviceMs` | device event 간격. stream 위 D2H 복사의 **device 실행 시간** |
| `syncHostMs` | backend 내부 `cudaStreamSynchronize()` 호출에 머문 **host wall time** |
| `hostTotalMs` | backend 호출 전체의 **host wall time** |

`sync = hostTotal - h2d - kernel - d2h` 로 **계산하지 않는다.**
그 값은 host enqueue overhead와 host scheduling 영향을 섞으므로
정확한 CUDA synchronization time이라고 주장할 수 없다.
`syncHostMs` 는 host 측에서 **직접 측정한 값**이며, 위와 다른 정의다.

## 7. 미측정 상태 처리

- event 생성 실패 / 기록 실패 / elapsed 실패 → `measured = false`
- 이 경우 해시 결과 자체는 기존과 **완전히 동일**하게 반환한다.
  `measurement failure != GPU processing failure`
- 상위 호출자는 `measured == false`이면 recorder를 **호출하지 않는다.**
  → JSON은 `not_measured`로 남고 0이 되지 않는다.

## 8. 기존 GPU / CPU semantics 보호

- `hashBatch()` 기존 인자 동작·반환값·해시 결과 불변
- `addGpuBatchMs()` 기존 키와 의미 유지 (파이프라인 측 host elapsed)
- CPU build / GPU OFF / GPU unavailable / GPU fallback 전부 기존 동작
- CUDA 미컴파일 빌드에서 새 계측 코드는 컴파일 대상이 아니다
- CUDA runtime 오류 시 계측을 끄고 **기존 오류 처리 경로를 그대로 사용**

## 9. D4a가 변경하지 않는 D4b 항목

```
double buffering / triple buffering
pinned memory
새 stream topology / stream pool
producer-consumer overlap
D5 batching, D6 starvation, D7 dispatch
Scheduler / share formula
```

## 10. 정확성 영향

계측 전용. 해시 산술·임계값·판정 로직을 건드리지 않는다.
검증은 CPU↔GPU 해시 parity로 확인한다.

## 11. Windows / GPU / Linux 호환성 영향

- `cudaEvent_t` 는 CUDA 런타임 표준 API. Windows / Linux 동일
- CPU-only 빌드 영향 없음
- 다른 백엔드(HIP/Level Zero 등)는 아직 없으므로 "계측 불가 →
  not_measured" 경로를 그대로 사용한다

## 14. 향후 D4b 판단 방법

실측 JSON에서 다음을 확인한다.

- `gpuKernelMs` 가 `gpuH2dMs + gpuD2hMs + gpuSyncHostMs` 를 크게
  상회하면 kernel 지배 → overlap 이득 후보 아님
- kernel 은 짧은데 `gpuSyncHostMs` / host enqueue 비중이 크면
  host 대기 구조가 wall time을 지배 → D4b overlap 실험 설계 대상
- 어느 경우든 판단은 **실측 후에만** 내린다
