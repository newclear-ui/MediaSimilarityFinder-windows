# 0.9.2.31 — Large-result Match Streaming and Memory Bounds

## IMPORTANT CHANGE
Large match sets no longer have to be fully materialized in `SearchReport.matches`.

## Why
0.9.2.29 removed transient candidate-pair vectors and 0.9.2.30 reduced duplicate match storage, but millions of genuine matches could still make the final result vector dominate memory.

## Previous Structure
`ScanPipeline` → `MediaSearchEngine::scan()` → materialize all matches in `SearchReport.matches`.

## New Structure
`ScanPipeline` → `ScanControl::onMatch` immediate delivery → retain results only when requested.

`retainMatches=false` disables report-owned full-result storage. `maxRetainedMatches` can bound the report vector. The streaming callback still receives every match regardless of the retention limit.

## Rationale
Preserve the existing default API while establishing a safe boundary for future GUI pagination/virtualisation and monitor/database-backed result consumption.

## Resolved Situation
A caller can now process very large result sets without requiring the complete match list to remain in `SearchReport` memory. Existing callers retain previous behavior by default.

## Verification
- `search_report_test`: default retention, full streaming, and bounded retention.
- Full CTest regression verification follows.

## Future Impact
The next stage can connect Qt result virtualisation/page queries and monitor notification storage to the streaming boundary.
