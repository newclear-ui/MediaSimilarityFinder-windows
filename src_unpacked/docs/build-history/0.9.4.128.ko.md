# MediaSimilarityFinder v0.9.4.128 — 이미지 디코드 공유 소스 통합 (파일당 3 open → 1 open)

기준선 `0.9.4.127` → 본 빌드 `0.9.4.128`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` 불변 (판정·지문 bytes 불변).

## 1. 변경 필요성

- 실측 로그(사용자 dataset 177,880 files, wall 6362.6초)에서 walk 4634.1초와 img 3668.0초가 지배적이고, 프로세스 총 읽기 466.2GB가 dataset 68.9GB의 약 6.8배였다.
- 코드 추적 결과 이미지 1장당 WIC factory+decoder를 3회 생성했다: `decode()`(고정), `decodePreserveAspect()`(aspect), `decodeWicFileAspectColor()`(컬러, raw 경로). D9d 실측에서 open+factory가 decode의 89.54%를 차지하므로, 파일당 open 3회는 그대로 3배의 디스크 읽기와 CPU 대기로 이어진다. 저지연 드라이브에서는 워커가 I/O에 막혀 CPU가 놀았다(평균 25.3%).
- `Maximum` 90퍼센트는 스케줄러 배분용이며 디코드 fan-out(`decodeWorkerCount`, 하드웨어 clamp 4~32)과 무관하므로, 정책 조정으로는 해결되지 않는 구조적 문제였다.

## 2. 기존 구조

- `MediaPipeline::imageBatch`가 고정 디코드 → pack/hash → aspect+color 재디코드의 3단계로 동작했고, 각 파일마다 decoder가 3번 열렸다.
- I-2 공유 소스(`decodeWicBranches`)는 고정+aspect까지만 묶었고, 컬러 lane은 별도 raw 경로였다. `decodeBoth()`는 verify 전용이라 스캔 경로는 사용하지 않았다.

## 3. 변경 구조

- `decodeWicBranches`에 branch C(컬러, BGRA)를 추가했다. scaler math와 Fant와 BGRA converter와 trailing orientation이 기존과 byte-identical하며, 달라지는 것은 공유 factory/decoder/frame뿐이다.
- 신규 `ImageDecoder::decodeTriple()`이 고정+aspect+컬러를 1 open으로 생산한다. per-branch 유효성은 기존 3회 호출과 동일하게 유지한다(고정 실패 → 파일 skip, aspect 실패 → crops만 비움, 컬러 실패 → 썸네일만 없음). gray lane PGM fallback은 `decodeBoth`와 동일 계약, 컬러 lane은 기존처럼 PGM fallback이 없다.
- `imageBatch`가 `decodeTriple()` 1회 호출로 바꾸고 aspect/crop/color를 메모리 내 버퍼에서 처리한다. batch당 메모리 상한은 유지된다.
- `decodeColorAspect()`은 공유 경로로 재구현했고, 사용처가 없어진 raw `decodeWicFileAspectColor()`는 삭제했다(주석 dead code 금지 규칙에 따라 snapshot 없이 제거 — 로직은 branch C에 보존됨).
- 부수 수정: Release 빌드가 debug sqlite3/ffmpeg import lib를 링크하던 잠재 결함을 수정했다. `FindSQLite3`/pkg-config가 debug 경로를 가리켰고, vcpkg debug 트리 삭제 후 링크가 깨지며 드러났다. `unofficial-sqlite3 CONFIG` 우선 + Windows에서는 pkg-config 대신 release HINTS를 사용한다. 동작 코드 변경이 아니라 빌드 계약 정정이며, 바이너리 동작은 동일해야 한다(아래 검증).

## 4. 해결된 상황

- 파일당 WIC open 3회 → 1회. 디코드 2회분(메타데이터+open+재읽기)이 사라졌다.
- 동일 실파일 A/B: 구 빌드(0.9.4.127 포터블) 대비 신 빌드 wall 5.12초 → 3.02초(약 41% 단축, 4개 저속 파일 코호트, cold 1회차). 판정은 양쪽 동일(scanned=4 analyzed=4 failed=0 candidates=0 groups=0). warm run은 양쪽 1.0초로 동일(인덱스 재사용 경로 불변).
- 단, cold/warm cache 교란이 있어 41%를 일반 성능 수치로 주장하지 않는다. 방향성 증거이며, 구조적 근거(3 open → 1 open)가 본질이다.

## 5. 검증

```text
CPU Release CTest 100% tests passed out of 125
GPU CTest 100% tests passed out of 126
GUI/Backend --version 0.9.4.128
```

- 기존 스위트 전체 PASS가 byte 동등성을 보증한다: `xmp_orientation_test` 38 checks + WIC 98/98, `color_thumb_test`(생산 디코딩 함수 직접 가드), `image_verify_test`, `test_mode_xmp_test` 14 checks, `search_engine_test` 필드 규모 회귀.
- FAIL-first 성격: 공유 전에는 b1/c1 같은 회전 쌍 검증이 decode 단위에서만 가능했고, 스캔 경로 3-open 구조는 관측만 가능했다. 이번 변경 후 스캔 경로 자체가 공유 소스를 쓰므로 기존 회귀 테스트가 곧 공유 경로의 증거가 된다.
- 엔진/DB 버전 불변: 지문 bytes가 동일하므로 저장 쌍 재검증이 발생하지 않는다.

## 6. 향후 영향 및 한계

- 판정·저장·프로토콜·engine/DB/schema/cache·journal schema 불변. CTest 등록 수 불변(125/126).
- Telemetry 의미 변경 1건: `addImage`의 cropMs에 더 이상 재디코드 시간이 포함되지 않고 CPU fingerprint 시간만 남는다. JSON 키는 그대로이며 값의 정의만 좁아졌다. D9d per-stage bucket에는 영향이 없다(imageBatch 경로는 per-stage telemetry를 전달하지 않았다).
- 메모리: batch당 aspect+color 버퍼를 유지하므로 batch 상한 안에서 수십 MB 증가한다. batch 크기는 그대로다.
- 55건 `.jpg` 이름 MP4 파일의 analysis_failed settled 처리는 불변이다(디코드 실패 경로 미접촉).
- 다음 후보: dataset fingerprint 자체는 단일 스레드 순차 해시로 남는다. wipe 후 첫 스캔의 전체 재해시는 별도 후보이며 이번 범위 밖이다.
