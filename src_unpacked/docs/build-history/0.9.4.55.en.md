## 1. Why the change was needed

Two symptoms were reported:

1. The read-complete counter rises, resets to 0, then resumes
2. After Stop the counter shows a final 0

## 2. Cause 1: phase-handoff reset

Fingerprint and walk count different sequences with no shared denominator.
`onFingerprintProgress` wrote the hashed count to `sumValDone_`, then the walk
start had `updateStatusCounts` overwrite it with `lastTotalN_` restarting at 0.
It looked like a reset.

## 3. Cause 2: post-cancel zero display

The `scanFinished` CANCELLED branch never updates `lastStats_`. The following
`refreshSummary()` blanked every row (`"-"`), and `updateStatusCounts()` wrote
`lastTotalN_=0`. Hashing 4519 files showed as final 0.

## 4. New structure

- New `lastReadN_` member. Reset at scan start, max-updated by fingerprint and
  walk. Monotonic across phases so no visible reset. Honest as "files touched
  so far" (fingerprint and walk process the same dataset sequentially).
- `refreshSummary` no-report branch preserves live values when `lastReadN_ > 0`
  instead of blanking. Real zeros still show `"-"`.
- `indexed` row keeps its existing live-analyzed path (0.9.4.54).

## 6. Why indexing did not happen (no code change, explanation)

The attached log is a run cancelled during fingerprint
(`cancelledDuring=fingerprint`, 71s, 11GB, scanned=0). It stopped before
walk/analysis/indexing began, so no indexing is correct behavior, not a bug.
The fingerprint hashes everything first by architecture, so this phase is long
on huge datasets (separate task: streaming fingerprint review).
