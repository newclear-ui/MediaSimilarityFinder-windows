# MediaSimilarityFinder v0.9.4.65 — 스캔 실패 핸들러 무throw 확정

기준선 `0.9.4.64` → 본 빌드 `0.9.4.65`.
CPU CTest **111/111**, GPU CTest **112/112** (crash_diagnostics 5→7 checks).
`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.4` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — 전부 불변.
`src/media_search_engine.cpp`·scheduler·color_thumb·NVDEC·sparse 미접촉.

## 1. 변경 필요성

- 2026-10-07 04:30 세 번째 `0xC0000409` 크래시. 이번에는 WER LocalDumps의
  mini 덤프(`MediaSimilarityFinder.exe.11104.dmp`)를 확보해 fault 스레드·
  스택을 특정했다 (분석 방법은 `docs/architecture/crash-response-runbook.ko.md`).
- 확정된 사실: 예외 코드 `0xC0000409` + 파라미터 `0x7` = ucrtbase `abort()`
  내부의 `int 29h` fail-fast (`abort+0x4E`). Qt fatal 아님
  (`msf_qt.log` 없음). 힙 손상(`0xC0000005`) 아님.
- fault 스레드는 스캔 worker. 스택 최상단이 `ScanWorker::run`의
  `catch (std::exception&)` 핸들러 영역(`persistMatchesSnapshot` 호출 +
  `e.what()` 가상 호출 + `emit failed`, PDB-less 역조회로 함수 특정).
- 구조적 결함: `run()`은 Qt 슬롯(`QThread::started` 직결)이라 핸들러 밖으로
  예외가 나가면 Qt 내부를 거쳐 `terminate()` → `abort()`로 직행한다.
  0.9.4.62의 catch-all은 첫 예외를 잡지만, 핸들러 안의 `persist`·`emit`이
  다시 던지면 같은 서명으로 사망한다. 덤프가 바로 그 경로를 가리킨다.

## 2. 기존 구조

```cpp
} catch (const std::exception& e) {
  persistMatchesSnapshot();   // 던지면 핸들러 밖으로 탈출
  emit failed(e.what());
} catch (...) {
  persistMatchesSnapshot();   // 동일
  emit failed("unhandled non-standard exception in scan worker");
}
```

## 3. 변경 구조

- 두 핸들러의 `persist`와 `emit`을 각각 독립 `try/catch(...)`로 감싼다.
  persist가 실패해도 `failed` 보고는 시도하고, 반대로 보고가 실패해도
  persist 시도는 유지한다.
  핸들러 밖으로 예외가 나가는 경로가 없다.
- 회귀용 seam 추가: `MSF_TEST_THROW_PERSIST`가 있으면
  `persistMatchesSnapshot()` 진입 시 throw (테스트 전용, 제품 미사용).
  기존 `MSF_TEST_THROW_NONSTD`와 조합하면 "핸들러 안에서 persist가
  던지는" 덤프 사슬을 결정적으로 재현한다.

## 4. 해결된 상황

- 스캔 실패는 이제 어떤 경우에도 기록된 `failed`로 끝나고 프로세스가
  살아남는다. SEH 액세스 위반은 그대로 fail-fast (마스킹 없음, 0.9.4.62
  원칙 유지).
- 첫 예외의 원인은 덤프로 알 수 없다 (이미 잡힌 뒤 사망했으므로).
  핸들러가 살았으므로 다음 발생 시에는 `failed` 메시지가 남는다.
