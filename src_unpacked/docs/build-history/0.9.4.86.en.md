Baseline `0.9.4.85` -> this build `0.9.4.86`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.5` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — all unchanged. No verdict, schema or decode change.
(One additive key `dataset_fp_cache` in the DB `meta` table; old code ignores it.)

## 1. Why it was needed

Analysis of two user full-scan logs:
- run1 (08:27): of 2047.5 s total, **dataset fingerprint 1387.7 s (67.8 %)**, a 68.9 GB
  full re-hash.
- run2 (09:13): of 2199.8 s total, **dataset fingerprint 1436.6 s (65.3 %)**, the same
  68.9 GB re-hashed.
- Both runs produced the **same** dataset fingerprint (`1bf86a74…`): the dataset is
  unchanged, yet every scan re-reads it entirely.
- This stage is **telemetry-only** (the JSON's dataset identity); it never affects the
  results (groups/pairs).
- Also: same fingerprint but run1 groups 1976 vs run2 4734 -> a determinism question.

## 2. Previous structure

- `computeDatasetFingerprint` (`dataset_fingerprint.cpp`) reads every in-scope file
  **fully and SHA-256s it**, building a manifest hash.
- Called when `telemetryOn && walkCompleted && !cancelled` (every scan while detailed
  logging is on).
- No cache, so every scan re-hashes everything -> 23 min on a large corpus.

## 3. Change

**(1) File-set key cache (core)**
- After the scan, build a sorted manifest of the DB rows' `(path,size,modified,quickHash)`
  (the exact triple the walk uses to detect change) and SHA-256 it -> **file-set key**.
- Store the fingerprint, fileCount and totalBytes as
  `keyHash|fingerprint|fileCount|totalBytes` in DB `meta` (`dataset_fp_cache`).
- On the next scan, if the key matches, **skip the re-read and reuse the stored value**
  (`bytesRead=0`). If it differs (change/add/delete), recompute and update.
- The fingerprintVersion and scope (images/videos) are part of the key, so algorithm or
  scope changes invalidate it.

**(2) Candidate determinism diagnostic**
- `ScanPipeline::analyze` logs one line `scanIndex files= indexed= withCrops= imageIdx=
  c4= c1= c916=`. The candidate set is a **pure function of `files_`** (fingerprints +
  crops), so different numbers across runs mean the DB crop columns differ, not a code
  nondeterminism.

## 4. Result

- An unchanged rescan: dataset fingerprint 23 min -> **0 (cache hit)**.
- Verdicts, results, index and thumbnails unchanged (the cache only reuses a telemetry value).

## 6. Impact and limits

- **Any changed file still forces a full re-hash** (same as before). A true incremental
  cache storing per-file full hashes is a follow-up candidate.
- The key is based on size/mtime/quickHash (first 64 KiB), so a rare change that keeps
  mtime while altering bytes beyond 64 KiB is not detected (telemetry value only; results
  unaffected).
- **The determinism anomaly (run1 1976 vs run2 4734) is not yet resolved**: the candidate
  set is deterministic in code, so the two runs likely had different DB crop data. The
  new `scanIndex … withCrops= …` log will confirm it on the next runs.
