## 1. Why the change was needed

- External review P2: cache identity centers on `path + size + mtime + quick_hash(first 64KB)`. Whether the front-64KB hash and size/mtime gates actually work — and where the residual risk ends — was never pinned by a product test.

## 2. Previous structure

- `quickIdentity()`: FNV-1a over the first 64KB. `memoryLookup`/`loadPersistent` query a 6-part key (path, size, mtime, quick, version, policy). A tail-only-changed file (same front 64KB, size, mtime) hits the stale row.

## 3. New structure

- No product-code change. Regression pin: new `video_cache_identity_test` — same path with isolated DBs per case, forced mtime restore so only the intended key component varies:
  - control: identical-file rebuild hits + hash stability.
  - (A) front-byte change (same size+mtime): must miss. A stale true would fail, proving the quick-hash gate is bypassed.
  - (B) mtime bump (identical content): must miss.
  - (D) tail-only change past 64KB (same size+mtime): stale hit pinned as documented residual risk. A decodable offset is probed first with a cacheless engine, so the pin does not depend on decoder error tolerance.
- Full-content hashing stays rejected: re-reading multi-GB videos every scan is not justified by the current cost/risk balance. Revisit if field evidence shows tail-only mutations matter.

## 4. Resolved state

- Three identity gates (front, mtime, control) are test-pinned; one residual risk (tail-only) is documented as intended behavior.
