## 1. Purpose

I-1 shared an intermediate 8-bit GrayImage, which created a two-step Fant chain
and broke f/a byte parity. This candidate creates **no intermediate
GrayImage.** Only the factory, decoder, frame and EXIF-orientation source are
shared; the final scaler/converter/`CopyPixels` pairs are created independently.

The core question was **exact output parity, not speed.**

## 2. Candidate Structure

```text
file
 ↓  CoInitializeEx                      once
 ↓  WIC factory                         once
 ↓  CreateDecoderFromFilename           once
 ↓  GetFrame(0)                         once
 ↓  EXIF orientation (FlipRotator)      once
 ↓  shared src (IWICBitmapSource)
      ├── scaler A -> 64x64    -> converter A -> CopyPixels A -> f
      └── scaler B -> aspect64 -> converter B -> CopyPixels B -> a
 ↓  release all COM objects
 ↓  CoUninitialize                      once
```

The product path (`decodeWicFile` / `decodeWicFileAspect`,
`src/image_decoder.cpp:154` / `:238`) performs factory, decoder, frame,
metadata and orientation twice. The candidate does that prefix once.

**No production code was changed.** All measurement ran in a separate
executable, `tests/shared_wic_source_probe.cpp`, with its own WIC pipeline; the
baseline was obtained by **calling** the product functions.

### 3.1 Two Real Defects Found While Verifying (not caught by self-consistency)

1. **COM lifetime order violation → access violation.** The `(C)` verification
   block called `CoUninitialize()` while the factory, decoder, frame, rotator and
   converters were **still alive**, and the process died with an access
   violation (0xC0000005) on scope exit. This is exactly the failure the
   product source warns about (`src/image_decoder.cpp:150-153`).
   → Fix: all WIC objects are now **owned by a helper function**, and the
   caller runs `CoUninitialize` only **after** the helper returns. That is
   automatically correct on every return path, including failures. The
   candidate body uses the same structure.
2. **Failure counts were being masked.** The measurement loop put
   `if (!okCand) continue;` before the `if (!okBase)` check, so a baseline
   failure was never counted for the 5 files where the candidate failed.
   `baseFail=0` therefore looked like "the baseline decoded all 5 and only the
   candidate failed".
   → Fix: both sides are recorded independently, plus a `candOnlyFail` count
   for the dangerous class (baseline succeeds, candidate fails). In fact
   **both sides fail on the same 5 files** (§5).

## 4. Final COM Lifetime Structure

```text
candidateSharedSource()
  CoInitializeEx
  runSharedPipeline()      <- owns every WIC ComPtr
  CoUninitialize           <- only after the helper returned, so nothing is live
```

When `runSharedPipeline` returns, factory, decoder, frame, rotator, scalers A/B
and converters A/B are all released, and only then does `CoUninitialize` run.
This holds on every return path.

### 6.3 What "adjusted baseline" Means

When a telemetry sink is present, the product decoder additionally runs a
`CreateFileW`+`CloseHandle` **reference probe** whose cost lands inside
`totalMs` (`src/image_decoder.cpp:69-79`). The candidate has no such probe. Both
baseline numbers are recorded so the comparison stays honest. The difference is
under 0.11 ms.

## 7. Q4 — Does WIC Share the Actual Decode Work?

**It does.** This is the substance of the candidate. CPU run 1 (n=849):

| CopyPixels | baseline mean | candidate mean | ratio |
|---|---:|---:|---:|
| f (first) | 3.9224 ms | 3.8801 ms | 1.01× |
| a (second) | 3.8833 ms | **1.0917 ms** | **0.28×** |

- The baseline runs two pipelines, so **both** pay the full decode.
- The candidate's first `CopyPixels` pays the full decode and the second drops
  to roughly 1/3.6 of that.
- If only factory/decoder/frame creation were saved while `CopyPixels` stayed
  equally expensive, the cost would not have dropped. It dropped, so H3 is
  confirmed and the opposing hypothesis H4 is **refuted**.

## 8. EXIF — PARTIAL / not_measured

```text
exif_status = not_measured
```

- The standard dataset reports `orient_applied_files = 0`, so the EXIF branch
  did not run in this measurement. That is a pre-existing fact carried from I-1.
- The standard dataset was **not** modified. Eight fixtures were generated in a
  separate directory by inserting an EXIF APP1 orientation (1–8) into a dataset
  JPEG (`f0000.jpg`, 209×248) after SOI (and after any leading APP0/JFIF), then
  baseline/candidate byte parity was compared. **8/8 byte identical.**
- However **the product applied orientation 0 times**, so the fixtures never
  exercised the EXIF branch. WIC's metadata reader returned
  `WINCODEC_ERR_PROPERTYNOTFOUND (0x88982F41)` for all four query paths tried:

```text
/app1/ifd/exif/{ushort=274}    (the path the product uses)
/app1/ifd0/exif/{ushort=274}
/app1/ifd/{ushort=274}
/app1/exif/{ushort=274}
```

- Diagnosing why is **outside this experiment's scope.** Baseline and candidate
  read the orientation tag with **the same code**. What is established is that
  the EXIF fixture is invisible to WIC in this environment, which also suggests
  that the **product's own EXIF path may never have executed** against this
  dataset. That is registered as a separate follow-up (§12).
- Therefore **A5 (EXIF parity) is not recorded as PASS.** The candidate's EXIF
  risk is structurally low: the FlipRotator-shared-by-two-scalers path passed
  byte-identically in the selfcheck (§3 C), and the metadata detection code is
  identical on both sides. The end-to-end check is nonetheless **not measured**.
