## 1. 변경 필요성

v0.9.4.36 은 I-2 를 production 에 통합하고 decoder 수준에서 36.72 % 감소를
확인했다. 그러나 그 값은 decoder microbenchmark 값이며, 실제 MediaSimilarityFinder
전체 scan 에 얼마나 반영되는지는 측정되지 않았다. decode 는 scan 전체의 일부일
뿐이며 cache hit 시에는 아예 실행되지 않기 때문이다. 지시대로 이 수치를
production full scan 으로 검증해 I 노드를 닫을 근거를 확보한다.

## 2. 기존 구조

product executable `MediaSimilarityFinder.exe` 는 GUI 서브시스템이며
`--version` / `--help` / `--smoke` 만 받는다. **scan 을 시작하는 CLI 플래그가
없다.** scan 은 GUI 의 Scan 버튼(`ScanWorker::run`)으로만 도달 가능하다.

그러나 이미 목적에 정확히 맞는 측정 드라이버가 존재한다.

```text
tests/dataset_baseline.cpp
  msf_dataset_baseline <dataset-root> <app-dir> [runs]
```

이 도구는 `MediaSearchEngine::scan(root, 8, &control)` 을 호출하므로 GUI 와
**동일한** `scan_pipeline.cpp` + `image_verify.cpp` + `MediaPipeline` 경로다.
호스트 wall clock(`run=N wall_ms=`), D9a/D9c/D9d/D1/D3 telemetry 전문,
그리고 `MSF_DUMP_JSON` env var 로 원본 JSON 을 모두 제공한다.

**필요한 telemetry 가 이미 전부 존재했다.** 지시가 허용한 최소 telemetry 추가도
**필요하지 않았고, production 코드는 한 줄도 변경하지 않았다.** 커밋 내용은
버전 bump, 측정 하네스 스크립트, 문서뿐이다.

### 3.2 조건 A — decode-active (cold process)

`verifyCacheList` 은 `image_verify.cpp` 의 **프로세스 전역** 32-entry LRU 다
(`constexpr std::size_t kVerifyCacheMax = 32;` 파일 스태틱). 이를 리셋하는 API
가 없다. 따라서 **프로세스당 1회 스캔**이 cold verify cache 를 유일하게 보장한다.
이는 앱을 새로 실행해 스캔하는 실제 production 동작이기도 하다.

```text
msf_dataset_baseline <root> <appdir> 1     # 측정 1회 = 프로세스 1회
```

baseline / candidate 를 **BCBCBCBCBC** 로 교차 실행해 시간축 편향을 제거했다.
양쪽 binary 로 한 번씩 예열 실행 후 버렸다.

## 5. 결과 — 조건 B (warm / repeat scan)

GPU, 프로세스 3개 × repeat run 4개 = 버전당 12 rows.

```text
baseline  median  31,005.3 ms  [23,797.1 – 31,136.3]
candidate median  22,718.9 ms  [16,643.0 – 24,231.3]
delta            -8,286.4 ms   (-26.73 %)
```

작업량은 24회 실행 전부에서 동일하다 (`scanned=3334`, `analyzed=3333`,
`groups=156211`, `verifyDecodeMisses=12962`, `verifyCacheHits=14524`).
candidate 는 24/24회 더 빠르다.

그러나 **이 조건의 절대 시간이 비정상적**이다. 프로세스 내 run 1은 빠르고
run 2부터 두 버전 모두 크게 느려진다.

```text
v0.9.4.35  run1 23,930 → run2 31,036 → run3 31,136 → run4 31,058
v0.9.4.36  run1 16,643 → run2 23,082 → run3 22,745 → run4 24,231
```

원인을 telemetry 로 분리했다. decode 1회당 비용을 cold / warm 으로 비교하면:

```text
v0.9.4.35  cold 0.7203 ms/miss  →  warm 1.1546 ms/miss   (+60 %)
v0.9.4.36  cold 0.5522 ms/miss  →  warm 0.6196 ms/miss   (+12 %)
```

즉 **v0.9.4.35 의 decode 가 반복 스캔에서 60 % 느려지고, v0.9.4.36 은 12 % 만
느려진다.** `openMs` 는 두 버전 모두 거의 변하지 않아(CPU/GPU cold 값과 동일),
차이는 `copyMs` 쪽에 있다. WIC 의 lazy decode 가 decoder instance 구조에 따라
다르게 캐시되는 것이 유력하지만, **이것은 가설이며 확정된 결론이 아니다.**

`MSF_DUMP_JSON` 은 마지막 run 의 JSON 만 기록하므로 repeat run 별 telemetry 를
모두 확보하지 못했다. 이것이 조건 B 를 headline 근거로 쓰지 않는 이유다.

### 반드시 명시해야 할 사실

절감의 **약 28–30 %가 계측 오버헤드 제거**다.

```text
GPU  1,960.8 → 2,177.9 ms 절감 중 642.4 ms (29.5 %)
CPU                            551.0 ms (28.1 %)
```

`probeOsFileOpen` 은 `src/image_decoder.cpp:69` 에 있으며 소스 주석이 명시한다.

> Opens and immediately closes a handle; it does not touch the decode path, the
> image bytes, or any result, and its outcome never gates the decode.

즉 **순수한 계측 전용 비용**이며 `tel == nullptr` 이면 즉시 반환한다. v0.9.4.35 에서는
스캔당 25,924 회, v0.9.4.36 에서는 12,962 회 실행되었다. v0.9.4.36 이 줄인 642 ms
중 일부는 product 성능이 아니라 **중복 계측을 없앴기 때문**이다. v0.9.4.36 의
36.72 % microbenchmark 역시 telemetry 가 켜진 빌드에서 측정된 값이므로 같은
보정 대상이다.

### 실제 product 이득의 주원인

가장 큰 **실제** 절감은 `open` 버킷이다. WIC decoder 객체 생성이 25,924 회 →
12,962 회로 정확히 절반이 되었다. 이것이 I-2 통합의 본질이다.

반면 `copy` 버킷(실제 픽셀 decompression)은 -95 ms(GPU)로 거의 변하지 않았다.
이는 WIC 가 이미 내부적으로 decode 를 공유하고 있었다는 뜻이며, 중복이 expensive
decompression 이 아니라 **객체 생성/setup 에 있었다**는 것을 보여준다.

## 7. 전체 scan 과 decoder 수치의 정합성

```text
GPU 조건 A:
  decode share of baseline wall   9,335.9 / 18,399.7 = 50.7 %
  decode stage reduction                       22.3 %
  50.7 % × 22.3 %                                = 11.3 %
  관측된 paired full-scan reduction              11.13 %
```

예측과 관측이 0.2 %p 로 일치한다. full-scan 개선은 decode 단계 절감이
scan 전체에 그대로 전파된 결과이며, 다른 stage 에서 새로 비용이 생긴 것이 아니다.

decoder microbenchmark 36.72 % 와 full-scan 10–11 % 가 다른 이유는 단순하다.

```text
1. decode 는 scan wall 의 약 50 % 뿐이다
2. 절감의 28–30 % 가 계측 오버헤드다
3. 나머지 stage(walk, image stage, verify key/hash, DB)는 그대로다
```

## 10. 한계와 남은 항목

### 미해명 (I 노드를 막지는 않음)

1. **조건 B 의 process-level slowdown.** 동일 프로세스 내 2회째 스캔부터 양 버전
   모두 30~60 % 느려진다. v36 은 여기서도 24/24회 더 빠르므로 **I-2 가 만든
   회귀가 아니다.** 원인은 decode 의 `copyMs` 에 있으며 WIC lazy decode 캐시가
   decoder instance 구조에 따라 다르게 동작할 가능성이 있으나 **가설 단계다.**
2. **조건 B 의 per-run telemetry 부재.** `MSF_DUMP_JSON` 이 마지막 run 만 기록해
   repeat run 별 counter 를 확보하지 못했다. 이 때문에 조건 B 는 headline 근거로
   쓰지 않았다.
3. **CPU 전체 벽시계 잡음.** run 3·5·6 이 크게 흔들려 범위가 겹친다. GPU 측정이
   신뢰할 만한 대표값이다.

### 기타

- `vcpkg.json` 의 `version-string` 이 `0.9.4.35` 에서 멈춰 있다(v0.9.4.36 도
  올리지 않음). 이를 바꾸면 manifest 해시가 바뀌어 2.2 GB vcpkg 의존성 전체
  재빌드가 발생하므로 measurement-only 버전에서는 **의도적으로 건드리지 않았다.**
  별도 유지보수 버전에서 다룰 항목이다.
- product executable 에 scan CLI 플래그가 없다는 사실이 재확인되었다. 이번
  검증은 기존 `msf_dataset_baseline` 드라이버로 수행했고, 이는 production
  `MediaSearchEngine::scan()` 을 그대로 호출한다. **추가 코드 변경이 필요하지
  않았다.**
