## 1. Why the change was needed

- `VideoBuildStats.decodedFrames` is documented as "frames actually decoded", but `VideoFingerprintEngine::build()` set it to `frames32.size()` (the kept samples).
- `VideoDecoder::framesAt()` stores only selected samples in the result array, so the old value said nothing about how many frames the decoder actually processed in between.
- With that, GPU-decode CPU replacement and frame-download savings cannot be measured accurately.

## 2. Previous structure

- A decode count existed only on the ExactSparse path (`SparseSeekStats.decoded/emitted` split). The production sequential sweep had none.
- `video_decode_planner_probe` recorded this gap in writing ("decodedFrames is frames32.size(), not what FFmpeg produced").

## 3. New structure

- Optional `decodedOut` on `VideoDecoder::framesAt()`/`framesAt96Plus32()`: counts every successful `avcodec_receive_frame`, kept or discarded. The no-FFmpeg fallback counts one per successful push. The 32px derive decodes nothing, so it forwards the 96px sweep count.
- `VideoFingerprintEngine::build()`: sequential path uses the sweep count, sparse path uses `SparseSeekStats.decoded` (same receive_frame basis). `sampledFrames` (plan target count) and `keptFrames` (final hashes) unchanged.
- Regression pin: `video_real_test` asserts `decodedFrames >= keptFrames && decodedFrames >= sampledFrames`. Measured on the 8 s fixture: kept=8, decoded=80, sampled=9 (identical on both trees; GPU path with `gpuUsed=yes`).
- Comment alignment: `VideoBuildStats` now names discarded intermediates; the probe's gap note updated to "closed in 0.9.4.155".

## 4. Resolved state

- `decodedFrames` now reports the true decode count. Telemetry/benchmark JSON shape unchanged (only the values became honest).
- The denominator for GPU-decode replacement/download-savings measurement is secured.
