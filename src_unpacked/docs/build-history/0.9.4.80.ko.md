# MediaSimilarityFinder v0.9.4.80 — analyze 병렬 구조 개선 (UNVERIFIED)

기준선 `0.9.4.79` → 본 빌드 `0.9.4.80`.
**이 버전은 미검증이다.** 실행 중인 제품 스캔이 머신을 점유하고 있어
사용자 지시로 컴파일·CTest를 수행하지 않았다. CPU CTest / GPU CTest 모두
미실행이며, 다음 빌드에서 parity 재검증이 선행 Gate다.

`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.5` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — 전부 불변(의도). 판정 변경 없음(의도).

## 1. 변경 필요성

- 파일별 스캔이 끝난 뒤 후보 쌍 검증이 매우 오래 걸리고, 그 구간에 CPU
  사용률이 떨어진다. 코드 확정 원인 3건:
  1. analyze image pass worker가 16개로 고정
     (`src/scan_pipeline.cpp`, 구 284행). 코어 많은 머신에서 남는 코어가 놈.
  2. 샤드 불균형: 그룹 연속 구간 균등 분할이라 쌍이 한 그룹에 몰리면 한
     worker만 수십 분 갈고 나머지는 idle (straggler).
  3. 리포트 작성 단계(`scanFinished`/`onResults`)가 GUI 단일 스레드다.
     Backend는 이미 끝난 상태라 CPU를 끌어올 구조가 아니다.

## 2. 기존 구조

- `consumeImageParallel`: `min(hw, groups)` worker, 단 연속 구간 분할,
  part 순서 병합. 16-cap.
- `flushVideo`: 동일 16-cap.

## 3. 변경 구조

- **16-cap 해제**: 양쪽 다 `hardware_concurrency` 그대로 사용.
- **동적 그룹 디스펜서**: worker가 atomic `nextGroup`으로 whole group을
  가져간다. 병합은 그룹 인덱스 순으로 재배열하므로 출력 순서는 sequential
  pass와 동일하게 유지된다 (verdict parity, deterministic order).
- **샤드 계측**: job/active/쌍수/샤드 최대·평균 벽시계를 `analyzeShards ...`
  한 줄로 backend 로그에 남긴다. 프로파일러 없이 straggler 해소 여부를
  로그만으로 판정한다.
- 판정·매칭·취소 의미 변경 없음. `stop`/cancel 경로, `LocalCancel`,
  telemetry 합산 방식 그대로.

## 4. 해결된 상황 (예상, 미검증)

- 코어 전부 사용 + straggler 해소로 analyze wall 단축.
- `analyzeShards` 라인으로 샤드 균형을 실측 가능.

## 5. 검증

```text
CPU CTest: 미실행 (사용자 지시: 실행 중 스캔 보호를 위해 컴파일 금지)
GPU CTest: 미실행 (동일)
GUI/Backend --version: 미확인 (동일)
```

**다음 Gate (순서 고정): 컴파일 → CTest 전수 → parity(기존 결과와 쌍 집합
동일) → 위 5 검증란 갱신 후에만 본 버전 인용.**

## 6. 향후 영향 및 제외 항목

- 제외(의도): 리포트 단계 GUI 스레드 분리 — 스레딩 변경이라 미검증 상태로
  넣지 않았다. 컴파일 가능해지면 별도 버전으로 진행.
- 제외(의도): video `consume()` 직렬 열거 병렬화, decode-once, GPU SSIM —
  측정 후 별도 버전.
- 비동기 전송(논블로킹 IPC)은 범위 밖이다.
