# MediaSimilarityFinder v0.9.4.7 — Node B6: Resource Mode Integration

Validation baseline for B6: the brief §10 per-mode policies wired into
the scheduler. Engine 1.5.0, DB 1.0.3, cache v9, schema 1 unchanged.

## Why the change was needed
- Through B5 the scheduler never read Resource Mode. Maximum and Gaming
  behaved identically, so the mode choice never reached scheduling.

## Previous structure
- `SchedulerHardware` had no mode input; hold, floor, and band were
  global constants.

## New structure
- `SchedulerHardware.mode` plus `paramsForMode()`: per-mode (cpuFloor,
  holdMs, killAt, relieveAbove). Maximum (0.10/5 s/standard band), High
  (0.07/10 s/standard), Balanced and Custom (0.05/10 s/standard = the
  B4-validated values), Gaming (0.02/30 s/kill-95/relieve-90). Light is
  the Gaming alias (same enum value).
- An explicit `setHoldMs()` wins over the mode default (tests,
  diagnostics). Unset (-1) takes the mode default. Existing tests use
  the Balanced default or explicit holds, so all pass unchanged.
- The engine connects with one line per scan: `schedHw.mode =
  policy_.mode`. Manual's CPU cap stays enforced upstream by worker
  counts, so scheduler-side Manual == Balanced is stated and tested.
- Modes tune stability/responsiveness only; the proportional share rule
  is untouched.

## Why this shape
- Instead of reinterpreting existing policy numbers (cpuPercent), the
  four parameters the scheduler actually consumes are declared per mode
  in one place, easy to tune after long-run observation.
- Gaming's deep cut, long hold, and early yield define "conservative"
  behaviorally; Maximum is nimble and self-prioritizing. The doc is the
  spec.

## Resolved state
- Mode selection reaches scheduler behavior. B7's per-mode gate scenarios
  are now executable.

## Accuracy impact
- None. Gates and verdict paths untouched. Balanced defaults equal B4.
  Identical `scan_workflow_test` on both trees.

## Compatibility impact
