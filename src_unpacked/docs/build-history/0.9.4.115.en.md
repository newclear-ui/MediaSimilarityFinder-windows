# MediaSimilarityFinder v0.9.4.115 — Hotfix 2: Load/Start-Scan 62097 crash loop (event-thread block + stale kill timer)

Baseline `0.9.4.114` -> this build `0.9.4.115`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged.

## 1. Why it was needed

Field re-report: the **same backend crash 62097 persisted in 0.9.4.114**. Analyzing the user log (`%TEMP%\msf_scan.log`) identified what code 62097 actually is:
- Qt 6.11 `qprocess_win.cpp:32` — `KillProcessExitCode = 0xf291` (**62097**) — i.e. this is **not a self-crash but the code set by the supervisor's `QProcess::kill()`**. The number was evidence that OUR code killed the backend.

The log chain (0.9.4.114):
```text
01:01:09 backend hello_ack version=0.9.4.114
01:01:24 backend health quiet 1/3   (the backend went silent ~5 s in)
01:01:26 backend health timeout
01:01:26 backend watchdog: backend health timeout   (terminate + 3 s grace)
01:01:29 backend unexpected exit: ... (crash exit, code 62097)  (kill after the grace)
-> restart -> the new backend is killed ~3 s later the same way -> endless loop
```

## 2. Previous structure and defects (two causes + one leftover)

- **D1 (trigger, a 0.9.4.113 regression)**: `BackendSession::loadIndex()` runs **synchronously on the IPC event thread**. Since .113, `loadMatches()` performs the badge full-content confirmation (SHA-256) over candidate files (user index: ~5,296 files, ~1.5 GiB), so during a Load the event thread went **silent for well over 10 s** -> supervisor health timeout (quiet 1/3 -> 3/3) -> `terminateAndRespawn` -> `terminate()` (ineffective on a console app) -> `kill()` after the 3 s grace (62097).
- **D2 (amplifier, pre-existing latent)**: `spawn()` **never stops `escTimer_`**. Only `escStage_` was reset to 0, so when a stale escalation timer from a previous round fired it took the stage-0 branch and **KILLED the freshly spawned backend ~killWait after spawn** (with no reason logged) -> restart -> killed again -> a **self-sustaining kill loop**. The 0.9.4.78 comment ("a stale armed timer from a previous round must never kill this backend") was not actually enforced by the code.
- **Leftover (badge contract)**: the Load row builder (`backend_session.cpp`) **recomputed the badge flag from the quick hash only**, ignoring the engine's `contentIdentical` — the .113/.114 full-content contract was not reflected in the Load display.

## 3. New structure

- **D1 — Load made asynchronous**: `loadIndex()` runs `runLoadIndex()` on a `QThread` worker (signals cross threads queued, the same contract scan answers use). `teardownWorker()` waits via `stopLoad()`, so scan start/teardown serialize safely with a pending load. Test seam `MSF_TEST_SLOW_LOAD_MS` (set before the backend spawns).
- **D2 — `escTimer_.stop()` in `spawn()`**: the .78 intent is now enforced by code. No fresh backend can be killed by a stale timer.
- **Badge leftover**: Load rows now use the engine-computed `m.contentIdentical` (the redundant recompute is gone).
- **Regression tests** (backend_e2e_test, checks 39 -> 45):
  - **Test 1b (D1)**: the seam stretches the load to 12 s (test health window 5 s) and verifies event-thread survival, no restart, and load completion. **Pre-fix FAIL reproduced** (synchronous load -> health kill -> load never completed + restarts).
  - **Test 3c (D2)**: a silent backend drives repeated escalations and checks the invariant **"every unexpected exit must be accompanied, since its own spawn, by its own logged escalation reason (timeout/watchdog/FAILED/refuses)"**. **Pre-fix `exits=4 reasonless=3` FAIL -> post-fix `reasonless=0` PASS**.
  - **Test adjustment**: `ui_scroll_regression_test` phase 11 (load lists the stored groups) now waits boundedly for the asynchronous Load answer (the synchronous assumption was removed — without it CTest fails immediately).

## 4. What is fixed

- Both causes of the 62097 kill loop seen on Load/Start Scan are removed (event-thread blocking + stale kill timer). The event thread keeps sending HEALTH during loads/scans, and no restarted backend is killed by a stale timer.
- The Load badge now follows the full-content contract (Load and Scan displays agree).
- The user's index DB is undamaged (SQLite crash safety; the kills did not interrupt a write transaction).

## 6. Future impact and limits

- Verdicts/storage/protocol/engine/DB/schema/cache unchanged. The change is execution structure (threading) and supervisor lifecycle.
- The health rule (10 s silence, 3 strikes) stays as the backstop — the fix's core is that the event thread is never blocked by design.
- Revisit condition: if the user's Load feel is bad (e.g., minutes), consider progress reporting / a partial cap for the badge confirmation (keeping "no false positives"). `MSF_TEST_SLOW_LOAD_MS` is test-only.
