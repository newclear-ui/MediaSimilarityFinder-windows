# MediaSimilarityFinder v0.9.4.144 — 상세 로그에 실패 파일 목록과 사유 추가

기준선 `0.9.4.143` → 본 빌드 `0.9.4.144`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` 불변 (텔레메트리 additive key).

## 1. 변경 필요성

- S-3 실기에서 `broken.jpg`(텍스트를 확장자만 변경)가 분석 실패로 집계되는 것은 확인됐지만, 상세 로그에는 **실패 건수만** 보이고 어떤 파일이 왜 실패했는지는 알 수 없었다.
- 느린 파일 목록처럼 **실패한 파일의 이름과 사유**를 상세 로그에 출력하자는 요청.

## 2. 기존 구조

- 엔진은 분석 실패 시 `analysis_failed` 상태만 기록하고 `failed` 카운트를 올렸다.
- 텔레메트리 JSON에는 `images/videos.slowest`만 있었고, 상세 로그 다이얼로그는 그 목록만 표시했다.

## 3. 변경 구조

- `TelemetryRecorder`에 `FailedFile{path, reason, ms}` 목록 추가(이미지/비디오 각 최대 **50건**).
- 엔진의 이미지/비디오 실패 분기에서 사유를 기록:
  - 파일 읽기 실패 → `read failed`
  - 0바이트 → `empty file`
  - 그 외 → `decode/analysis failed`
  - 비디오는 `decode/analysis failed` + 해당 범위 처리 시간(ms).
- 텔레메트리 JSON(추가 키, 스키마 v9 유지):
  - `images.failedFiles[] = {path, reason, ms}`
  - `videos.failedFiles[] = {path, reason, ms}`
- 상세 로그 다이얼로그에 **"실패한 파일 (img/vid)"** 섹션 추가. 종류별 최대 10건을 `사유 — 경로` 형식으로 표시(JSON 저장에는 최대 50건 유지).

## 4. 해결된 상황

- 상세 로그만으로 어떤 파일이 왜 인덱싱되지 않았는지 확인할 수 있다(예: `empty file — D:\...\broken.jpg`).
- CLI/JSON 소비자는 `failedFiles` 배열로 동일 정보를 얻는다.

## 6. 향후 영향 및 한계

- 실패 사유는 휴리스틱이다(읽기/0바이트/일반 디코드 실패). 디코더별 세부 HRESULT/FFmpeg 오류 코드는 기록하지 않는다.
- 목록은 이미지/비디오 각 50건으로 제한한다(대량 실패 시 로그 크기 보호).
- 텔레메트리 스키마 버전은 additive 규칙에 따라 9를 유지한다.
