# 0.9.2.25 — SQLite/Index Performance Optimization and Migration Hardening

## IMPORTANT CHANGE

This release reduces repeated work in the SQLite and Index management layers as the persistent media index grows, while making existing database schema migration more robust.

### Why the change was needed

The previous implementation could repeatedly prepare SQL statements for file upsert/remove/unchanged checks, and SQLite busy behavior needed an explicit wait policy. Crop-fingerprint schema migration also performed separate schema checks for each missing column.

### Design changes

- Reuse prepared SQLite statements for `upsert`, `remove`, and `containsUnchanged` within the Database connection.
- Explicitly reset/clear statement bindings before reuse.
- Configure SQLite with WAL, `synchronous=NORMAL`, `busy_timeout=5000`, and `temp_store=MEMORY`.
- Replace six separate crop-schema checks with one schema scan that identifies all missing columns.
- Correct `IndexManager` application-version metadata to 0.9.2.25.
- Synchronize portable packaging version to 0.9.2.25.

### Resolved state

Database operations no longer depend on repeatedly preparing the same statements, and schema migration performs one metadata scan instead of six. SQLite busy conditions can wait briefly rather than failing immediately.

### Caution

The current Database prepared statements assume connection ownership. If the same Database connection is later accessed concurrently, a mutex or explicit connection-ownership policy will be required.
