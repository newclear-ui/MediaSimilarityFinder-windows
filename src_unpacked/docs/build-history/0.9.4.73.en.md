# MediaSimilarityFinder v0.9.4.73 — Backend crash hardening + PDB enablement + scan auto-resume

Baseline `0.9.4.72` → this build `0.9.4.73`.
CPU CTest **116/116**, GPU CTest **117/117**.
`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.4` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — all unchanged. No change to search verdicts or behavior.

## 1. Why this change

User report (running 0.9.4.72, `G:\Downloads\ss_twit`):

- Heavy disk I/O but GUI/backend CPU at 1%/2%; indexed files pass quickly, yet the
  "read complete" count does not advance for new files.
- Mid-scan a **"backend process exited unexpectedly — scan aborted"** dialog
  appears and the process dies. The supervisor restarts the backend but does
  **not resume** the search, so the user must press Start again.

We collected `%TEMP%\msf_scan.log` and the two backend dumps in
`%LOCALAPPDATA%\CrashDumps` (`MediaSimilarityFinderBackend.exe.{51136,11660}.dmp`,
2026-10-08 07:33/07:28) and analyzed them.

- Exit code **`-1073740791` = `0xC0000409`**, parameter **`0x7` =
  `FAST_FAIL_FATAL_APP_EXIT`**: an `abort()` / `std::terminate` fail-fast.
- The dump's fault-thread RIP is `ucrtbase.dll+0xA527E` (inside `abort`, `int 29h`).
  This matches the **same offset recorded in runbook 3-1/3-2** (a deterministic
  abort path).
- The heartbeat before the crash read `walked=7340` (run 1) / `walked=0` (run 2)
  with `lastPct=0`: the walk never completed, then the process died ~5 min later.
- **The Release build produces no PDBs** (no PDB settings in CMakeLists), so the
  fault function could not be resolved. The runbook requires a fault stack, so
  this is an analysis gap.

## 2. Prior structure

- The walker runs on a separate `std::thread walker([&]{ ... s.scan_stream(...) })`
  with **no try/catch**. In 0.9.4.72 `scan_stream` began calling `std::async`
  (a bounded pool); if scheduling fails, the exception escaping this thread goes
  straight to `std::terminate -> abort`.
- `ScanWorker::run` is wrapped in `catch(std::exception)` / `catch(...)`, but the
  walker thread sits outside that protection.
- The Release build emits no PDB, so WER/dumps keep only module+offset.
- When the backend dies mid-scan the supervisor only restarts it; the GUI
  `onBackendConnection(false)` ends with `scanFailed` (popup + idle). The
  reconnect (`backendConnection(true,"ready")`) merely re-enables the Start button.

## 3. New structure

- **Walker exception safety (`src/media_search_engine.cpp`)**: the walker body is
  wrapped in `try{...}catch(...){ walkError.store(true); }`, and after the
  consumer loop `walkError` promotes to `failed=true`. An exception leaving the
  walker now becomes a **recorded scan failure** instead of terminating the
  process (same principle as runbook item 4).
- **Parallel-hash fallback (`src/scanner.cpp`)**: `flushBatch`'s `std::async`
  fan-out is wrapped in try/catch and **falls back to a serial `quick()` pass** on
  failure, removing the path by which a scheduling failure could escape the
  walker (always progresses, zero exceptions).
- **PDB enablement (`CMakeLists.txt`)**: Release adds `/Zi` for CXX and `/DEBUG`
  for the linker, producing GUI/Backend PDBs (`MediaSimilarityFinder.pdb` etc.).
  `/Zi` is restricted to CXX so it is not passed to nvcc (which fails with
  MSB3721 otherwise). Codegen is unchanged.
- **Scan auto-resume (`gui/mainwindow.{h,cpp}`)**: split `startScan()`
  (user-initiated) from `beginScan()` (the body). When a backend crash aborts a
  scan, `scanCrashed_=true` is recorded, and when the supervisor reports a READY
  reconnect the GUI calls `beginScan()` **once** to continue the search. The
  engine checkpoints progress, so the re-walk skips indexed files and continues
  the update. A fresh user start resets the budget.

## 4. What is fixed

- The process-termination path from an unhandled walker-thread exception is
  removed (degraded to a recorded failure).
- Even if `std::async` scheduling fails, the walk continues in serial mode.
- A future crash can now be symbolized with PDBs (satisfies the runbook).
- After a backend crash the search resumes once automatically; the user no longer
  has to press Start again.

## 5. Verification

- CPU Release CTest 116/116, GPU Release CTest 117/117. Both exes --version 0.9.4.73.
- PDBs generated: `MediaSimilarityFinder.pdb` (GUI) / `MediaSimilarityFinderBackend.pdb`.
- The walker-exception / `async`-failure paths are covered by the existing scan
  regression tests (scan_streaming, walker_queue, backend_e2e, ...) all passing.
  No new deterministic seam was added.
- Auto-resume is a MainWindow path and requires a backend process, so it is not a
  unit CTest target. The supervisor restart remains covered by
  `backend_e2e_test` (passing).

## 6. Future impact

- **The crash root cause is unconfirmed.** This build (a) degrades an unhandled
  exception to a graceful failure, (b) enables PDBs so the next crash is
  symbolizable, and (c) provides auto-resume. To pin the fault function, a fresh
  reproduction dump must be captured with the 0.9.4.73 PDBs present (runbook).
- The stall (low CPU, no progress) on the new-file segment needs separate
  tracking. The 0.9.4.72 walk parallelization measured 5x on a high-latency drive
  but did not fully resolve the user's stall. Next candidates: a slow/hanging
  `quick()` 64 KB read on a specific file, or a stall in the new-file analysis.
- HDD/network walk parallelism remains a revisit condition.
- `ExactnessPolicy::RefuseAll` stays; Node E terminal state unchanged.
