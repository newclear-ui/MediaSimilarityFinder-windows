# 0.9.2.28 — CandidateIndex candidatePairs Large-Scale Candidate Generation Optimization

## IMPORTANT CHANGE
In 0.9.2.26 the 9-part Multi-Index Hash optimized candidate lookup, but `candidatePairs()` still called `query()` once per entry. At large index sizes this repeated bucket lookup, duplicate collection, sorting, and verification work.

0.9.2.28 changes `candidatePairs()` to **direct bucket pair generation** for `D <= 8` while preserving exact semantics.

## Previous structure
- Call `query(entry.hash, D)` for every entry.
- Look up all 9 partition buckets.
- Sort and deduplicate candidate positions.
- Verify full Hamming distance.
- Repeat for the next entry.

## New structure
- Look up the required 9-part buckets directly for each entry.
- Deduplicate bucket candidates with a reusable generation-stamp array.
- Remove the per-query candidate-position vector sort/unique overhead.
- Verify final 64-bit Hamming distance.
- For `D=0`, use only partition 0 because equal hashes share every partition.
- Preserve the exact fallback semantics for `D>8`.

## Design rationale
For `D <= 8`, the pigeonhole guarantee means every true candidate pair shares at least one partition. Direct bucket scanning removes the repeated candidate-vector construction/sort overhead while retaining final full-hash verification. SimilarityEngine decision rules are unchanged.

## Additional changes
- `query(D=0)` now uses a single partition lookup.
- Added exhaustive-linear regression coverage with planted D=8 neighbors.
- Added exact D=0, D=8, and D=9 checks.
- Added 10k/25k/optional 50k candidatePairs benchmarks.
- Added optional `MSF_HEAVY_BENCH=1` for bucket-heavy validation.

## Resolved situation
The repeated per-entry candidate query path in `candidatePairs()` has been removed for the normal `D <= 8` range. The implementation now operates closer to the actual bucket candidate-pair workload, particularly when bucket collisions are high.

## Accuracy / compatibility impact
- Public CandidateIndex API unchanged.
- Existing candidatePairs ordering and distance semantics preserved.
- No candidate omission for `D <= 8` under the existing partition guarantee.
- Exact fallback retained for `D > 8`.
- SimilarityEngine, mirror/crop/video-temporal algorithms, and Monitor load protection are unchanged.

## Benchmark

The same benchmark was built separately against the 0.9.2.26 CandidateIndex implementation for comparison.

| N | Previous candidatePairs | 0.9.2.28 | Improvement |
|---:|---:|---:|---:|
| 10,000 | ~171 ms | ~23 ms | ~7.3x |
| 25,000 | ~1,091 ms | ~147 ms | ~7.4x |

At 50,000 entries the new path measured ~640 ms. A bucket-heavy 5,000-entry case produced 12,497,500 actual pairs in ~1.20 s; its ~398 MB RSS is dominated by the result vector.
