# MediaSimilarityFinder v0.9.2.47 — Checkpointed Scans (Interruption Keeps Progress)

## Need for change
Interrupted (cancelled) scans rolled back the whole transaction, discarding even the walked file list. Hours of work on huge folders evaporated on one interruption. Requested: interruptions must keep the log index, especially the file-name list. Rules for post-listing add/delete updates were also requested.

## Previous structure
One transaction per scan. Cancel/failure rolled back everything; `SearchReport` had no completion flag. Unanalyzed files had no DB rows at all.

## New structure
- Checkpoint commits: commit + reopen every 500 analyzed files and every 1000 walked files. Cancel/crash keeps everything up to the last checkpoint
- Skeleton rows first: changed files get an upserted fingerprint-0 row before analysis. Matching and candidate indexes already exclude fp==0 rows (existing guards verified), so results stay clean. fp==0 with unchanged stamps qualifies for analysis, guaranteeing crash resume
- Deleted-file cleanup runs only on fully walked scans (complete seen set). Ignored rows retained
- On cancel: commit the open chunk and return a partial report (`completed=false`) instead of rolling back. DB errors keep committed chunks too (documented reversal of old semantics)
- `SearchReport::completed` added. GUI cancel message shows scanned/analyzed counts ("partially saved")
- New `scan_cancel_test` → 40 tests total. Verifies incomplete flag, surviving DB rows, and resume-to-completion (fails on the old rollback behavior)

## Resolved situation
- Interruption keeps the file list and checkpoints; the next scan completes the work. Deletion cleanup only on complete scans, so partial states lose nothing

## Validation
- Core Release build: PASS, **CTest 40/40 PASS** (including new `scan_cancel_test`)
- All existing scan-path suites green = counters and matching semantics preserved. `--smoke` exit 0, `--version` 0.9.2.47
- Debugging lesson: checkpoint's re-BEGIN left a trailing open transaction that failed the *next* scan's BEGIN and returned an empty report. Fixed with a final commit; rescans verified healthy (scan2: scanned=2 analyzed=0 unchanged=2). Undiscovered, this would have looked like "search does nothing at all"

## Future impact
- Cancel-semantics change (full discard → partial keep) belongs in release notes. Callers distinguish via `completed`
- Checkpoint intervals (500/1000) are constants. Tune if commit cost shows on slow disks (tens of ms under WAL)
- ETA display is the next candidate: remaining work is estimable from checkpoint statistics
