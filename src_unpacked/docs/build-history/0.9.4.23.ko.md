# MediaSimilarityFinder v0.9.4.23 — D9a Analyze Internal Observability

D9a 진입. **새 노드의 첫 단계는 관측(measure)이며 최적화가 아니다.**
D8b 가 실측으로 확인했듯이 엔진 wall 의 98.7 % 를 차지하는
`analyze` 내부에 stage 분해가 전혀 없다. 그래서 어떤 최적화도 근거를
가질 수 없다. 엔진 1.5.0·DB 1.0.3·캐시 v9 불변.

> 이 문서는 **코드 변경 전에** 작성되어 커밋 순서로 감사 가능하다.

**D9a does not optimize anything. It makes the stage that consumes 98.7 % of
a scan observable, so a later step can decide on evidence.**

---

## Pre-register (코드 변경 전 기록)

### 예상 효과

```
- analyze 내부 stage 분해를 가능하게 하여 98.7 % 를 구성 요소를 분리
- verifyImagePair 호출 수 / SSIM 계산 수 / 캐시 적중률을 실측
- "후보 쌍이 많은지", "SSIM 검증이 느린지", "캐시가 동작하는지"를 구분
- 이후 최적화 후보의 우선순위를 근거로 정할 수 있게 됨
```

### 기대하지 않는 것

```
- 어떤 성능 향상도 (계측만)
- verifyImagePair 최적화 / 캐시 확대 / 병렬화
- 후보 쌍 생성 알고리즘 변경
- SSIM 알고리즘 변경
- 판정 임계값 변경
- search verdict semantic 변경
```

### 롤백 기준

```
- 계측이 scan 결과를 변경함
- 기존 CTest / 빌드 regression
- parity 회귀 (동일 dataset 에서 그룹/판정 변화)
- 계측 overhead 가 비정상적으로 증가
```

## 1. 왜 새 노드가 필요한가

D8b(0.9.4.22) 실측:

```
engine wall 109,737 ms
  analyze            108,225.6   98.62 %   ← 대부분
  walk                 1,536.5    1.40 %
  image stage             642.3    0.59 %
  gpu batch                 48.3    0.04 %
```

Node D 는 queue / transfer / overlap 을 소유한다. `analyze` 는
최종 매칭/그룹화 단계(`media_search_engine.cpp:702-703` 의
`pipe.analyze`)이므로 **D brief 범위 밖**이다.

그래서 D 를 아무리 진행해도 이 workload 에서 의미 있는 이득이 없다.
**진짜 병목의 소유 노드가 없었다.** 이것이 D9a 를 여는 이유다.

## 2. 현재 관측 불가능한 이유

`analyze` 는 **단일 지표**로만 기록된다:

```cpp
// media_search_engine.cpp:702-703
const auto benchAT0=...;
st=pipe.analyze(maxDistance, ...);
bench_.addAnalyzeMs(...);
```

benchmark JSON 의 `matches` 섹션이 주는 것은:

```
candidates   후보 쌍 개수
pairs        스트리밍된 매치 수
retainedPairs 유지된 쌍 수
groups       그룹 수
reductionPct 후보 감소율
```

하지만 **시간이 어디에 쓰이는지에 대한 내부 분해가 전혀 없다.**
그래서 "후보 쌍이 너무 많은가"와 "각 쌍의 검증이 느린가"와
"캐시가 작동하는가"를 구분할 수 없다.

## 3. 코드 조사로 확인한 의존 관계

`src/scan_pipeline.cpp` `analyze()` 의 실제 작업은 4단계다:

```
(A) index build        for each file → 8 indexes 에 삽입
(B) candidate scan     forEachCandidatePair → 각 쌍에 bestMatch(Hamming)
(C) image verify       gray-zone 쌍마다 verifyImagePair (SSIM 재디코드)
(D) video temporal     video 쌍마다 재디코드 + DTW + crop SSIM
```

### (C) 가 유력한 원인 — 근거 있는 가설

`src/image_verify.cpp` `verifyImagePair()`:

```
kFast = 97.0        hammingSim >= 97 이면 즉시 반환 (검증 없음)
gray zone 쌍마다:
  verifyBuffersFor(pathA) → decode 64x64 full + decodePreserveAspect 64x64
  verifyBuffersFor(pathB) → 동일 2회
  ssimBuf 1회 + 3 aspect × 3 비교 = 총 10회 호출
  ssimBuf 는 frame_ssim 을 normal + flipped 2회 계산
  → 쌍당 frame_ssim 최대 20회, 이미지 재디코드 최대 4회
```

그리고 `kVerifyCacheMax = 32`:

```
verifyCacheList 이 32 entry 로 hard cap 된다.
```

**2,700 파일 대비 캐시가 32 entry** 라면, 쌍마다 두 파일을 재디코드하는
것이 사실상 정상이다. 이것이 98.7 % 의 유력한 원인이지만, **아직 가설이며
계측이 없다.** 그래서 이번 단계는 가설을 검증하는 계측이다.

> 이 가설이 사실이어도 **바로 손대지 않는다.** 먼저 stage 별 시간을
> 재야, SSIM 이 지배적인지 캐시 미스가 지배적인지 알 수 있다.

## 4. 측정할 것 (telemetry 설계)

`analyze` 내부에 다음을 기록한다. **모두 measurement state 를 가진다.**

### 시간 분해

| 키 | 의미 |
| --- | --- |
| `analyzeIndexMs` | (A) candidate index build |
| `analyzeScanMs` | (B) 후보 쌍 열거 + Hamming 판정 |
| `analyzeVerifyMs` | (C) image verifyImagePair 총 소요 |
| `analyzeVideoMs` | (D) video temporal 총 소요 |

### 카운터

| 키 | 의미 |
| --- | --- |
| `verifyCalls` | verifyImagePair 호출 횟수 |
| `verifyDecodeMisses` | 그중 실제 디코드가 수행된 횟수 (캐시 미스) |
| `verifyCacheHits` | 캐시 적중 횟수 |
| `ssimEvals` | ssimBuf 호출 횟수 |
| `frameSsimEvals` | frame_ssim 호출 횟수 |
| `videoTemporalPairs` | temporal 재디코드 대상 쌍 수 |

### 반드시 함께 기록할 것

- `verifyHitRate` = verifyCacheHits / (verifyCacheHits + verifyDecodeMisses)
  — 이 값이 0 에 가까우면 캐시 용량 문제가 맞고, 높다면 디코드 자체가 비용이다.
- `msPerVerifyCall` = analyzeVerifyMs / verifyCalls
  — 1 건당 비용을 분리해야 "쌍이 많다"와 "쌍 하나가 느리다"를 구분할 수 있다.

## 5. 왜 이런 키가 필요한가 (사전 논증)

```
verifyCalls 이 크고 msPerVerifyCall 이 작다  → 후보 쌍 수가 원인
verifyCalls 이 작고 msPerVerifyCall 이 크다  → 쌍 하나의 검증이 원인 (decode/SSIM)
verifyHitRate 가 0 에 가깝다                → 캐시 용량(32)이 원인
ssimEvals 가 verifyCalls 의 10배에 가깝다    → aspect loop 가 비용을 증폭
analyzeScanMs 가 크다                        → 후보 열거 자체가 원인 (index 구조)
analyzeVideoMs 가 크다                       → video temporal (dataset 에 video 없으면 0)
```

**지금으로는 위 중 어느 것인지 전혀 알 수 없다.** 그래서 계측이 선행이다.

## 6. 테스트 요구사항

- A. telemetry 키 6종이 JSON 에 존재
- B. `analyze` 를 실행한 recorder 에서 각 state 가 올바름
- C. 미실행 시 `not_measured` (0 위장 금지)
- D. 합계 정합성: 각 sub-stage ms 합이 `analyzeMs` 를 **초과하지 않음**
  (계측이 시간을 만들어내면 안 됨 — 단언은 `<=` 이며 정확 일치를 요구하지 않음)
- E. 기존 판정 회귀: 동일 dataset 에서 groups / candidates / verdict 불변
- F. 계측 overhead 기록 (verify 카운터 수집 자체의 비용은 별도 기록하지 않고,
  전체 wall time 회귀 여부로 판단)

## 7. 이 단계의 성공 기준

계측이 **실제 병목 후보를 식별해낼 수 있으면** 성공이다. 병목이 무엇이든
상관없다. "측정했더니 SSIM 이 지배적이었다" 도 성공이고,
"후보 열거가 지배적이었다" 도 성공이다.

**미측정 상태로 최적화를 시작하는 것보다 항상 낫다.**

## 9. 실제 결과

### 9.1 구현한 것 (계측 전용)

- `src/analyze_telemetry.h` (신규, Qt-free): 순수 데이터 캐리어.
  `BenchmarkRecorder` / `ScanPipeline` / `image_verify` 에 의존하지
  **않으므로**, verification 코드가 engine telemetry upwards 로 새
  의존성을 갖지 않는다. `image_verify` 와 `scan_pipeline` 은 이 구조체를
  채우고, 엔진이 복사해 recorder 에 넣는다. **recorder 포인터는 아래로
  절대 내려가지 않는다** (프롬프트 §16/§17 요구사항).
- `image_verify.h/.cpp`: optional `AnalyzeTelemetry*` (기본 nullptr —
  기존 호출부는 그대로 동작). 계측 지점은 정확히 3곳:
  `verifyImagePair` 의 isImage 통과 직후(호출), `verifyBuffersFor` 의
  cache hit/miss 분기, `ssimBuf` 의 실제 `frame_ssim` 실행부.
- `scan_pipeline.h/.cpp`: `ScanStats` 에 `AnalyzeTelemetry analyze` 추가
  (additive). stage 시간은 **4개 슬라이스가 analyze 총합의 부분집합**이 되도록
  설계: index 는 자기 루프, verify 는 각 호출부 누적, video 는 flush 누적,
  **scan 은 총합의 나머지(remainder)**.
- `benchmark.h/.cpp`: `"analyze"` 섹션 추가, **schema v8 → v9**.
- `media_search_engine.cpp`: `bench_.setAnalyzeTelemetry(st.analyze)`.

#### Stage 합이 analyzeMs 를 넘지 않는 구조 (프롬프트 §20/§21)

`flushVideo()` 는 candidate loop **안에서도** 호출되므로 naive 한 겹
타이머로는 겹칩니다. 그래서 video 시간을 누적해 scan 나머지에서 제외하고:

```
scanMs = totalMs - indexMs - verifyMs - videoMs   (음수면 0 으로 클램프)
```

결과적으로 `index+scan+verify+video == total` 이 **구조적으로 보장**되어
합이 analyzeMs 를 넘을 수 없다. 그리고 scan 은 attribution 되지 않은 제어
오버헤드(poll, callback, bookkeeping)를 **정직하게 흡수**한다 — 그 오버헤드가
실제로 측정되지 않은 stage 소속인 것처럼 꾸미지 않는다.

#### 카운터 의미 (모두 "추정"이 아니라 "실측 이벤트 수")

| 카운터 | 정의 |
| --- | --- |
| `verifyCalls` | `isImage == true` 로 실제 image verification 에 진입한 호출. video 쌍은 위에서 즉시 반환하므로 **세지 않는다** |
| `verifyDecodeMisses` | `verifyBuffersFor` 조회 중 실제 디코드를 수행한 **조회 수** (호출 수가 아님 — 한 호출은 최대 2 조회) |
| `verifyCacheHits` | 동일 조회 중 캐시로 처리된 수 |
| `ssimEvals` | `ssimBuf` **호출** 수 |
| `frameSsimEvals` | 실제 실행된 `frame_ssim` 수 (guard 로 거부된 경우 ssimEvals 보다 작아진다 — 이 차이 자체가 측정값) |
| `videoTemporalPairs` | temporal 큐에 들어간 쌍 수 |

derived 는 분모가 실재할 때만 계산하고, 아니면 `null` + `not_measured`.
**0 으로 나눠 0.0 을 만들어내지 않는다.**

### 9.2 실제 측정 결과

조건: RTX 3080 Ti, GPU 트리, D8b 표준 dataset
(`9b113848…4253c`, 2700 files, 36,007,560 B, 95 dirs, version 1),
**cold index**, `msf_dataset_baseline` 반복 실행.

#### Stage 분해 (2회 반복, 카운터는 완전히 동일)

```
                     run 0        run 1
  indexMs              3.2          3.7      state=measured
  scanMs             350.8        399.3      state=measured
  verifyMs        109,142.3    117,290.7      state=measured
  videoMs              0.0          0.0      state=not_measured
  --------------------------------------------
  substage sum    109,496.3    117,693.7
  analyzeMs       109,501.9    117,699.8     -> 합 <= 총합 OK
```

analyze 내부 비중:

```
  index     0.00 %
  scan      0.32 %
  verify   99.67 %    ← 지배
  video     0.00 %    (dataset 에 video 없음 -> not_measured, 0 위장 아님)
```

#### Verify 카운터 (2회 반복 완전 동일 = 결정론적)

```
  verifyCalls          158,020
  verifyDecodeMisses    12,949
  verifyCacheHits       14,519
  verifyHitRate          0.528579    (state=measured)
  msPerVerifyCall        0.69 ~ 0.74 ms
  ssimEvals            137,340
  frameSsimEvals       274,680
  videoTemporalPairs         0
  ssimEvals/verifyCall     0.87
```

**카운터 내부 정합성 검증** (계측이 신뢰할 만하다는 증거):

```
  ssimEvals / 10          = 137,340 / 10 = 13,734  (SSIM loop 를 끝까지 돈 호출)
  (misses + hits) / 2     =  27,468 / 2 = 13,734  (buffer 조회 2회씩)
```

두 값이 **정확히 일치**한다. 즉 실제로 비싼 검증을 수행한 호출이 13,734
개이고, 각 호출이 buffer 조회 2회 + `ssimBuf` 10회를 했다는 뜻이다.
계측이 서로 모순되지 않는다는 직접 증거다.

## 10. Hypothesis 별 판단 (프롬프트 §14 / §30)

### 가설 A — "verifyImagePair 가 병목" → **확인**

```
verifyMs = 99.67 % of analyze
```

stage (C) 가 지배적이라는 사전 가설이 **실측으로 확인**되었다.

### 가설 C — "kVerifyCacheMax = 32 가 재디코드 원인" → **기각**

```
verifyHitRate = 0.5286   (≈ 0 이 아니다)
```

이것이 이번 단계의 가장 중요한 결과다. **코드만 읽고 세운 가설이
측정으로 기각되었다.** 32-entry 캐시라 해도 후보 쌍이 인덱스 순으로
집중 접근되어 실제 적중률이 52.9 % 다. 즉 "캐시 용량 확대"는
99.67 % 를 설명하지 못한다.

### 실제 지배 구조 (측정으로 확정)

```
verifyCalls 158,020  (가능 쌍 3,641,700 의 4.3 % 만 verify 게이트까지 도달)
  ├─ 약 144,286 건 (91.3 %) : kFast(>=97) 단축 → 거의 무비용
  └─ 약  13,734 건 ( 8.7 %) : buffer 조회 2회 + ssimBuf 10회 (frame_ssim 20회)
       117,290 ms / 13,734 ≈ 8.5 ms per expensive verification
```

즉 **병목은 "비싼 검증 1건의 비용"이 아니라 "verify 게이트까지 도달하는
후보 쌍의 수"** 이다. 게이트에 들어온 158,020 건 중 8.7 % 가 각각 ~8.5 ms
를 쓰고, 그것이 117 초를 만든다.

### 나머지 판단

- `analyzeScanMs` 는 0.32 % — 후보 열거/index 구조는 병목이 **아님**
- `analyzeVideoMs` 는 dataset 에 video 가 없어 `not_measured`
  (0 으로 위장하지 않음). video 경로 판단은 video dataset 확보 후 필요
- `ssimEvals/verifyCalls = 0.87` — SSIM loop 는 10배 증폭되지만
  전체 호출의 8.7 % 에서만 도는 것이므로, "SSIM 이 모든 호출을
  증폭한다"는 예상과 다르다

```
D4b overlap / Full D3 topology   없음 (0.9.4.22 에서 근거로 보류 상태 유지)
```

## 14. 다음 optimization 후보 (판단만, 구현하지 않음)

측정 결과가 가리키는 방향:

1. **후보 쌍 도착률 4.3 % 를 낮추는 방향** — verify 게이트까지 오는 쌍을
   줄이는 것은 판정 의미를 건드릴 수 있으므로 신중해야 한다.
2. **비싼 검증 1건의 8.5 ms 를 낮추는 방향** — 4회 디코드(동일 파일을
   aspect 별로 중복 디코드)와 20회 `frame_ssim` 이 그 안에서 지배적이다.
   `ssimBuf` 10회 중 9회가 aspect 조합이며, 동일 GrayImage 를 반복
   재사용하지 않는다.
3. **`ssimEvals` 를 verify 게이트에 더 가까운 곳으로 당기는 방향** —
   aspect 비교를 full SSIM 이후로 미루면 불필요한 계산을 건너뛸 수 있다.

**어느 것도 이번 단계에서 구현하지 않았다.** 어느 방향이 옳은지는
다음 substep의 pre-register 를 먼저 써야 결정할 수 있다.

단, 주의: dataset 의 fingerprint 분포가 **합성 deterministic 패턴**이므로
실사용 라이브러리에서 후보 쌍 비율은 다를 수 있다. 이 결론은
"이 dataset 에서" 의 결론이다.
