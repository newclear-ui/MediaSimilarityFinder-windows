# MediaSimilarityFinder v0.9.4.116 — Phantom group members from external deletes fixed + GUI auto-repair (stale index rows)

Baseline `0.9.4.115` -> this build `0.9.4.116`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged.

## 1. Why it was needed

Field report: indexDB group 275 (representative `Keren1286444-2080011532100890711-01.jpg`) — the user had previously deleted all similar files in testing, yet the group remained listed, with **two non-existent members still shown**. The detail pane showed the cached name/path/format/similarity, but the actual file size was 0 byte and the resolution etc. were blank. Additional request: when such residual issues are detected in the GUI, resolve them automatically in the interface.

## 2. Previous structure and defect

- **Root cause**: the scan's deleted-file reconciliation (`media_search_engine.cpp`, the walkCompleted loop) used `Database::remove()`, which deletes **only the files row** and leaves the **matches and thumbs rows** referencing that path (database.cpp:137).
- Result: an externally deleted file survived forever as a **phantom group member** — no files row (so size 0 / blank detail) while its match rows kept listing it, and **even a rescan did not remove the matches**.
- `Database::forget()` (added in .105: files+matches+thumbs in one transaction) was the correct cleanup, but the scan path never used it — the scan runs inside its own outer transaction (`tx`), so calling `forget()` (which opens its own `BEGIN`) was not possible directly.
- The same defect existed on the **realtime-monitor path** (`MediaSearchEngine::removePath()` called from monitor.cpp:297 on observed deletions).
- **Load and scan quick-load displayed DB rows with no validation** — there was no existence check or auto-repair (the user's request item).

## 3. New structure

- **`Database` refactor**: the row deletes are extracted into `forgetRows()`, and `forgetNoTransaction()` (caller owns the transaction) was added. The public `forget()` keeps its existing contract (owns its transaction).
- **Scan reconciliation**: removed paths are collected and `db_.forgetNoTransaction(removedPaths)` runs inside the scan's transaction — files + matches + thumbs together. The `removed` count semantics are unchanged.
- **Monitor path**: `removePath()` now uses `db_.forget({path})`.
- **Auto-repair API** `MediaSearchEngine::cleanupMissingOnDisk(root)`:
  - Runs only when `root` is a directory (an offline drive is a no-op — never wipe the index).
  - Validates the **stored match endpoints** against the filesystem, forgets the vanished ones, and logs `diskCleanup missing=N`.
- **GUI auto-resolution wiring**: **Load** (`BackendSession::runLoadIndex`) and the **scan quick-load** (`scan_worker`) call `cleanupMissingOnDisk` before building the list — phantom members are removed before they can be displayed (visible in the backend log).
- **Regression tests** (`search_engine_test`): (1) external delete + rescan removes the match rows — **pre-fix exit 29 FAIL reproduced** -> post-fix PASS; (2) `cleanupMissingOnDisk` forgets vanished endpoints and is a **no-op on an offline root** (exit 30-33).

## 4. What is fixed

- An externally deleted file can no longer linger as a phantom member through any path (rescan / Load / scan start / monitor).
- Already-accumulated stale rows are **auto-cleaned on the next Load or scan start** (no user action; the `diskCleanup missing=N` log records it).
- The 0-byte / blank detail symptom disappears with its cause (the phantom entries).

## 6. Future impact and limits

- Verdicts/storage schema/protocol/engine/DB/schema/cache unchanged. Display/cleanup behavior only.
- Cost: Load / scan start performs one existence check (stat) per stored match endpoint — a few hundred ms at the user's index scale.
- Limit (same authority semantics as the scan): if a root directory exists but its contents are wholesale different/empty (e.g., a remount), everything is forgotten — the same judgment the scan's deletion detection makes, and rescanning that root rebuilds it.
- `Database::remove()` (files-row only) remains correctly used on the changed-file re-analysis path (row replacement before re-analysis).
