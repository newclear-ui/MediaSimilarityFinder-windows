## 1. Why it was needed

Two process-split release gates from Active Build Queue priorities 2-3 sat at `OPENCODE REVIEW REQUIRED / DEFECT NOT CONFIRMED (not validated)`.

- **G4 (IPC backpressure)**: no evidence for the `send/flush` blocking paths, a bounded outgoing queue, or lossless/coalesced/bounded behavior under a slow consumer.
- **G6 (Job Object / GUI exit)**: no review of Win32 return-value handling and no E2E evidence that the backend PID dies when the GUI parent dies.

## 2. Previous structure and review outcome

**G4 (no defect confirmed — design review plus a stress test were missing)**
- GUI->Backend commands are few and small; request volume is bounded by the GUI pending cap (0.9.4.105 D). `QProcess::write`'s buffer is theoretically unbounded but the producer is bounded, so there is no practical risk.
- Backend->GUI MATCHES are chunked in 500s and lossless (never dropped); progress events coalesce by arrival (latest wins). With a slow consumer the pipe fills, the backend event thread blocks in `flush()`, and its event queue grows — bounded by the scan's total output (= the result itself).
- The supervisor's stdout parser is bounded (64 MiB line cap + runaway guard); sequence-gap logs detect any loss.
- **No defect confirmed**: the design looked sound but had no proof of losslessness/no-deadlock/boundedness, so a stress test was added.

**G6 (two real defects confirmed)**
- **Defect 1 — fixed 3 s exit delay**: `BackendSupervisor::shutdown()` polled `proc_->state()` while waiting for exit. Qt processes `QWinEventNotifier`'s `WinEventAct` **only during event-loop dispatch** (qwineventnotifier.cpp), so a polling loop without an event loop can never observe the exit. Result: even when the backend exits in 50 ms, **every app exit burned the full `shutdownWaitMs` (default 3 s)**. Measured (pre-fix): `shutdown elapsed=3049 ms`.
- **Defect 2 — three unchecked Win32 returns**: `assignJobObject()` ignored the returns of `SetInformationJobObject` (failure = KILL_ON_JOB_CLOSE never set), `OpenProcess`, and `AssignProcessToJobObject` (failure = silent orphan-protection loss with no log evidence). `CreateJobObjectW` failure was also unlogged.
- Pre-assignment window: the small interval between `QProcess::started` and assignment is covered by the backend's stdin-EOF self-exit (documented).

## 3. New structure

- **`BackendSupervisor::shutdown()`** (gui/backend_supervisor.cpp): instead of polling, `proc_->disconnect(this)` then `waitForFinished(shutdownWaitMs)` — a **direct wait on the process handle**. The disconnect prevents the blocking drain from emitting readyRead synchronously and re-entering GUI handlers mid-teardown (the "no event pumping" guarantee is kept). `terminate()` only on timeout; repeat calls return immediately (no double wait). The Job Object KILL_ON_JOB_CLOSE stays as the final backstop.
- **`assignJobObject()`**: all four Win32 calls are return-checked and log `GetLastError`. `PROCESS_ALL_ACCESS` -> `PROCESS_SET_QUOTA|PROCESS_TERMINATE|PROCESS_QUERY_LIMITED_INFORMATION` (the documented rights). On failure a prominent log states "orphan protection = channel-loss self-exit only". Test-only `SupervisorOptions::jobObjectEnabled` (default true).
- **`src/backend_main.cpp`**: test seam `MSF_TEST_BACKEND_WEDGE` — the stdin reader starts but the event loop is never entered, so both SHUTDOWN and the stdin-EOF self-exit are blocked (only the Job Object can kill it; G6 E2E control).
- **`tests/backend_e2e_test.cpp`** (37 checks, dataset 30 -> 300 groups):
  - Test 4 (G4): a 3 s consumer stall mid-scan (no event pumping -> pipe fills -> backend blocks in flush) then drain — 0 sequence gaps, 600 match entries delivered, same group count, no deadlock, RSS bound.
  - Test 5 (G6): graceful shutdown is bounded AND prompt — `delete supervisor` timing (pre-fix 3049 ms FAIL reproduced; post-fix 6 ms PASS) plus PID-gone after exit.
  - Test 6 (G6): parent (GUI) crash E2E — a helper process spawns a wedged backend, reports its PID, and the parent `TerminateProcess`es the helper (crash simulation). The job must reap the backend; the `--no-job` control must show the orphan surviving (proving the job is the actual killer) and is then cleaned up explicitly.

## 4. What is fixed

- **G4**: the slow-consumer stress proves losslessness (0 gaps, 600 delivered), no deadlock, and bounded memory (RSS 20/20/21 MB). Review conclusion: GUI->Backend is bounded by the pending cap; Backend->GUI is lossless with a backlog bounded by the scan output.
- **G6**: the app-exit latency is gone (3049 ms -> 6 ms). Win32 failures now leave log evidence (no more silent degradation). Parent-crash reaping of even a wedged backend is proven E2E, and the control proves the job is load-bearing.

## 6. Future impact and limits

- Verdicts, storage, protocol (`kProtocol`), engine/DB/schema/cache unchanged. No interface change beyond `--backend`.
- **Known limitation (documented)**: if the consumer stalls permanently, the backend event-queue backlog grows up to the scan's output size (the inherent cost of lossless delivery). GUI modals run nested event loops, so QProcess keeps draining — no real path hits this. **Revisit condition**: if a new consumer path that halts the event loop appears (non-modal synchronous blocking), consider coalescing/bounded queues.
- On job-assignment failure, orphan protection degrades to the stdin-EOF self-exit and says so in the log. `MSF_TEST_BACKEND_WEDGE` is test-only (production paths untouched).
