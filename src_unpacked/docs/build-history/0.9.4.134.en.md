# MediaSimilarityFinder v0.9.4.134 — Fast-rescan mode (setting) + forced re-verification (duplicate members only)

Baseline `0.9.4.133` -> this build `0.9.4.134`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged (verdicts unchanged; CTest registration count unchanged).

## 1. Why the change was needed

- Measured on 0.9.4.133: a no-change rescan spends ~5 min in the walk (177,887 files, 21.2 GB read) while the app itself uses 1.66% CPU -- **file-open I/O dominates** and antivirus (Defender 31%) follows every open. Re-reading the 64 KiB quick hash per file is most of that cost.
- User decision: apply (1) a strict/fast rescan integrity setting and (2) forced re-verification on Load (duplicate members only). (3) Test Mode difference report + Yes/No adoption is deferred to the next build (design agreed, out of scope here).

## 2. Previous structure

- The walk always computed the 64 KiB hash and `processOne` decided change with a 3-way `(size, mtime, quickHash)` comparison (media_search_engine.cpp:964). Stored pairs were only refreshed by the engine-bump revalidation; users had no way to re-check duplicate members on demand.

## 3. Changed structure

### (1) Fast rescan (Settings -> General -> "Fast rescan (compare size/mtime only)", default OFF = strict)

- `ScanControl.fastRescan` wired through `ScanWorker` / `BackendScanConfig` / supervisor START_SCAN payload / backend_main. Provenance is recorded in the detailed log as `config.fastRescan` (additive JSON key).
- Walk: new `Scanner::ScanCallbacks.skipQuickHash` predicate. The engine skips the hash only for files with a stored row whose `(size, mtime)` matches and that will not be re-analyzed; files that will be analyzed (pendingAnalysis), stat mismatches and video regrids still hash, so fresh rows keep the badge/fingerprint-cache inputs. One hash implementation via `Scanner::quickHash64k`.
- Change detection: fast mode drops the quick-hash term from the `changed` test; an empty hash is never treated as a mismatch (strict mode unchanged).
- Per the user's request, the default stays **strict** (no behavior/verdict change), and the tooltip states the residual risk (a size+mtime-preserving edit is not detected) and recommends the re-verification.

### (2) Forced re-verification (toolbar "Re-verify", duplicate members only)

- `MediaSearchEngine::reverifyStoredDuplicates`: re-reads stat + 64 KiB hash of **member paths only** (no walk), re-analyzes just the members that changed (images batched, videos single), then re-verifies/rediscovers only the pairs touching a changed file through the same targeted pipeline pass A/AB uses (d=8). Stored pairs unrelated to a change keep their verdict.
- Atomicity: row updates, pair saving and match-set replacement run in **one transaction** (new `Database::saveMatchesNoTransaction`; `saveMatches` keeps its own BEGIN and now shares one core). Cancel/failure rolls everything back -- never a partial set.
- IPC `REVERIFY_INDEX` (additive command) -> backend worker thread (same rule as Load) -> `results()` repopulates the view + `REVERIFY_FINISHED` counter event. GUI: toolbar "Re-verify" button, Load-style flow (notice popup/summary), status `Re-verification complete — checked N, changed M, re-analyzed K, pairs A -> B`.
- Limits (documented): only stored duplicate members are checked; newly forming duplicates remain the job of a normal scan. Images verify at distance 8 (same as GUI scans).

## 4. What was resolved

- No-change rescans: the open-per-file cost disappears, so walk time converges to enumeration and antivirus involvement drops sharply (removes the measured Defender 31% path on the user's machine).
- The fast mode blind spot (size+mtime-preserving edits) is cheaply checkable via "Re-verify" (members only). Measured: 6 identical files (15 pairs), one altered with size/mtime preserved -> re-verify detects it (changed 1, re-analyzed 1), pairs 15 -> 10, persisted.

## 6. Impact and limitations

- Verdicts, storage, protocol (kProtocol 1), engine/DB/schema/cache and the journal schema unchanged. One additive JSON key (`config.fastRescan`).
- Fast mode is explicit opt-in; strict stays the default. Even when enabled, re-verification (duplicate members) and strict scans are the safety net.
- Next-build candidate (awaiting user confirmation): (3) after a Test Mode run, report the differences against the main index and offer a Yes/No adoption (apply the scratch result through the normal transaction machinery; the Test Mode isolation contract stays "unchanged unless explicitly confirmed").
- Build note (recorded): after a version bump, the GUI exe's main.obj was not relinked because the generated header (`msf_build_version.h`) is not a tracked dependency of that target, leaving the previous version string (0.9.4.133) in the binary. Retouched main.cpp mtime + rebuild fixed it; the release routine's `--version` check detects and blocks this (verified 0.9.4.134 on both trees).
