# MediaSimilarityFinder v0.9.2.46 — 스캔 파이프라이닝 (워킹‖분석)

## 변경 필요성
스캔은 디렉토리 워킹 완료 후 분석을 시작하는 완전 순차 구조라, 27만 파일 폴더에서 23분간 CPU/GPU가 놀고 진행했다. 워킹 중 취소도 23분간 무시됐다. 목록 작성과 비교의 동시 실행 요청에 따라 2단계 오버랩(워킹‖분석, 매칭 불변)으로 개조했다.

## 기존 구조
`Scanner::scan`이 전체 `vector<FileState>`를 반환한 뒤에야 분류·분석·매칭이 시작. `MediaSearchEngine::scan`은 단일 스레드 수집 → 이미지 배치 → 비디오 배치 → 커밋 → 매칭.

## 변경 구조
- `Scanner::ScanCallbacks{onProgress, onFile, cancel, pause}` + `scan_stream()` 신설. `onFile`이 있으면 이동 전달(벡터 미보관), 취소/일시정지를 엔트리 단위로 확인. 기존 `scan()`은 콜백 없이 위임하므로 동작·시그니처 호환
- `MediaSearchEngine::scan()`: 워커 스레드가 `scan_stream`으로 큐에 흘리고, 메인 스레드가 꺼내며 분류→이미지 배치/GPU→비디오 async→upsert를 그 자리에서 수행. DB 단일 연결 원칙 유지(워커는 DB를 만지지 않음). 무제한 큐라 교착 없음(27만개≈수십MB)
- 분류 카운터(added/modified/unchanged/scanned)와 삭제 감지(seen 집합)를 스트리밍에 맞게 재구성. 트랜잭션 1회·커밋 위치·매칭 단계·무시 필터 의미 모두 기존과 동일
- `msf::IndexedFile`로 개명 (`incremental_index.h`가 `database.h`와 충돌하는 두 번째 `FileState`를 정의하고 있었음. 현재 빌드되던 것은 우연 — 어느 TU도 양쪽을 함께 include하지 않았기 때문)
- 버전 표기 통일 → 0.9.2.46

## 해결된 상황
- 분석이 워킹 완료를 기다리지 않고 시작. 워킹 중 취소가 즉시 반영 (이전: 최대 23분 무시)
- 일시정지는 워커·분석 양쪽에서 확인. 매칭 결과·리포트 의미 불변

## 검증
- Core Release 빌드 PASS, **CTest 39/39 PASS** (스캔 경로를 쓰는 search/integration/ignore/report/database 전부 녹색 = 의미 보존 증거)
- 워커 재현 프로브 3000개: 순차 버전과 **완전 동일**(scanned/analyzed/groups/candidates 641,358) + 시간 단축(46.6초→37.9초)
- pause/cancel 프로브: 정지·재개·조기종료 정상. cancel이 워킹 단계에서 즉시 종료됨을 확인
- 컴파일 과정에서 `ScanCallbacks`를 클래스 밖(네임스페이스 scope)에 잘못 두어 `Scanner::` 한정 실패 — 클래스 안으로 이동해 해결 (기록용 교훈: MSVC C2039+C3409 연쇄는 스코프 오지정 의심)

## 향후 영향
- 전체 파이프라이닝(매칭까지 점진적)은 이번에 제외. 필요하면 `pipe.analyze`를 증분 인덱스 조회형으로 교체 (별도 버전, 정확도 회귀 필수)
- `Scanner::scan()` 구 시그니처 유지. 신규 코드는 `scan_stream` 사용
- `IndexedFile` 개명으로 향후 ODR 위반 원천 차단
