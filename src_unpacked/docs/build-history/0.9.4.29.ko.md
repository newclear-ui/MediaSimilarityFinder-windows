# MediaSimilarityFinder v0.9.4.29 — D3 `decode` / `decodePreserveAspect` 중복 비용 계측

Status: **PRE-REGISTERED** (D3 instrumentation 코드보다 먼저 커밋된다)

D3 는 **measurement** 빌드다. 최적화하지 않는다.

---

## 1. 기준점

```text
base version : v0.9.4.28
base commit  : 256c41a
D2 status    : PASS
Path C       : DEFERRED (제품 채택 안 함)
```

D2 의 `CreateDecoderFromStream` + `HandleStream` 경로는 **현재 제품 경로에
채택하지 않는다.** D3 는 그 결론을 변경하지도, 재평가하지도 않는다.

## 2. 변경 필요성

D9c 는 `expensive verify` 안에서 decode 가 **94.90 %** 라고 측정했다. 그러나 그
94.90 % 는 **두 개의 서로 다른 decode 호출이 합쳐진 값**이다. 지금까지 두 호출을
분리한 적이 없다.

D2 는 decoder **진입 경로**의 비용 구조를 좁혔고, 그 결과는 "이득이 작아 채택
하지 않음"으로 끝났다. 그 판단 자체는 건드리지 않는다. 다만 D2 를 통해 두 가지가
확정되었다.

```text
1. decoder 생성 자체는 호출당 수십~수백 µs 규모이며, 이것만으로는
   verify 전체를 좌우하지 않는다.
2. 그러면 남은 큰 질문은 "decode 가 몇 번 호출되는가" 이다.
   호출 횟수가 그대로 비용이다.
```

현재 구조상 verify miss 1건마다 **같은 파일을 두 번 decode** 한다. 이 중 두 번째
호출이 실제 비용에서 얼마나 차지하는지 **아직 아무도 측정하지 않았다.**

## 3. 핵심 질문

> `decodePreserveAspect()` 가 동일 파일을 다시 decode 하면서 발생시키는 실제
> wall-clock 비용은 얼마이며, 그것은 `expensive verify` / `verify` / 전체 scan
> 시간 중 각각 몇 % 인가?

이 질문에 답하기 전까지 **어떤 최적화도 채택하지 않는다.**

## 4. D2 결과의 경계 — D3 의 baseline 으로 쓰지 않는다

```text
D1  CreateDecoderFromFilename ≈ 2.6257 ms/call   (cold, 코덱 DLL 최초 로드 포함)
D2  decoder call ≈ 0.07~0.12 ms                  (warm, 형식별 warm-up 제외)
D3  decode / decodePreserveAspect 분리 비용
```

D1 과 D2 는 측정 조건(cold / warm)이 달라 **직접 비교할 수 없고**, 그 차이는
성능 개선이 아니다. D3 도 마찬가지로 D2 나 D1 과 자동으로 비교하거나 차이를
성능 향상으로 표현하지 않는다. **측정 조건이 명확히 동일할 때만** 직접 비교한다.

## 5. 코드 구조 사전 조사 — 계측 전에 확인한 사실

계측 계획은 아래 실제 코드에서 나왔다. 추측이 아니다.

### 5.1 두 호출이 같은 telemetry 에 합쳐진다 (D3 의 정확한 공백)

`src/image_verify.cpp:78`

```cpp
if(!dec.decode(path, kDim, kDim, f, tel? &tel->decode : nullptr)
   || !dec.decodePreserveAspect(path, kDim, a, tel? &tel->decode : nullptr)) { ... }
```

**두 호출 모두 동일한 `&tel->decode` 를 넘긴다.** 그래서 `AnalyzeTelemetry::decode`
(D9d 가 만든 단일 `DecodeTelemetry`) 안의 모든 **타이머**와 성공/실패 카운터가
두 호출의 **합**이다.

```text
합쳐져 있던 것 (타이머 · 결과 카운터)
DecodeTelemetry::totalMs     두 호출의 합
DecodeTelemetry::openMs      두 호출의 합
DecodeTelemetry::copyMs      두 호출의 합
DecodeTelemetry::comInitMs / factoryMs / metadataMs / orientMs
                     / resizeMs / convertMs / otherMs / pgmFallbackMs  두 호출의 합
DecodeTelemetry::wicSucceeded / pgmFallbacks / orientApplied / failures  두 호출의 합
D1 항목(factory2Attempts·Successes·Fallbacks·factory2Ms·factoryFallbackMs
        ·osFileOpenProbe*·openHrFailCount)                                두 호출의 합
```

즉 **이미 존재하는 카운터는 두 호출을 구분하지 못한다.** D3 는 개념을 새로 만드는
것이 아니라, **이미 존재하는 누산기를 호출별로 분리**하는 작업이다.

### 5.1.1 정정 — `calls` / `aspectCalls` 는 원래부터 분리돼 있었다

> **정정 기록.** 이 pre-register 의 초안에 `calls` 와 `aspectCalls` 도 두 호출의
> 합이라고 적었으나, **틀렸다.** 구현 중 실제 코드를 다시 읽어 확인한 결과
> `decode()` 는 `calls` 만, `decodePreserveAspect()` 는 `aspectCalls` 만
> 증가시킨다(`src/image_decoder.cpp:355` / `:374`).
>
> ```text
> 원래 기록: calls 와 aspectCalls 도 두 호출의 합이다        ← 오류
> 오류 원인: 타이머 누적 구조만 보고 카운터의 증가 지점을 확인하지 않았다
> 수정된 값: 두 타이머 계열과 결과 카운터만 합쳐져 있었다.
>           calls = decode() 횟수, aspectCalls = decodePreserveAspect() 횟수
>           로 원래부터 분리되어 있었다.
> 수정 이유: D9d 리포트가 decodeCalls / decodeAspectCalls 를 서로 다른 값으로
>           이미 출력하고 있었다. 합쳐져 있었다면 그 두 키는 같은 값이었을
>           것이므로, 기존 리포트가 어느 정도 분리돼 있었다는 뜻이다.
> ```
>
> 이 정정은 D3 의 결론을 바꾸지 않는다. D3 가 측정하는 대상은 **합쳐져 있던
> 타이머**(`totalMs`, `openMs`, `copyMs` 등)이며, 이것이 D9c 의 "decode 94.90 %"
> 를 구성하던 것이기 때문이다. 다만 D3 리포트에서 두 번째 호출의 횟수를
> `.calls` 가 아니라 **`.aspectCalls`** 로 읽어야 하며, 그렇게 구현했다.

### 5.2 호출 횟수 카운터는 이미 2회 증가로 되어 있다

`src/image_verify.cpp:79`

```cpp
if(tel){ tel->verifyDecodes += 2; }
```

따라서 `verifyDecodes == 2 × verifyDecodeMisses` 가 **구조적으로 이미 성립**한다.
D3 는 이 의미를 바꾸지 않는다.

### 5.3 decode 호출 지점은 총 3곳이며, telemetry 를 넘기는 곳은 1곳뿐이다

| 호출 지점 | 호출 | telemetry 전달 | D3 대상 |
|---|---|---|---|
| `image_verify.cpp:78` | `decode()` 32×32 + `decodePreserveAspect()` 32×32 | `&tel->decode` (공유) | **O** |
| `media_pipeline.cpp:45` | `decode()` 32×32 (지문용) | **없음** | X |
| `media_pipeline.cpp:110` | `decodePreserveAspect()` 128 (crop 지문용) | **없음** | X |

이것이 §9 의 count consistency 예지를 **미리 깨뜨리는 요인**이다.
`decodePreserveAspect` 는 verify miss 경로 밖에서도 호출되므로, **전역 카운트는
`verifyDecodeMisses` 와 같지 않다.** D3 는 이 사실을 숨기지 않고 사전에 기록한다.

```text

decodePreserveAspectCount    decodePreserveAspect() 호출 횟수
```

가능하면 기존 하위 단계를 각 호출에 개별 귀속시킨다.

```text
open / factory / metadata / orient / resize / convert / copy / pgmFallback
```

**새 telemetry 시스템을 만들지 않는다.** 기존 `DecodeTelemetry` 의 필드와 의미를

분모로 쓸 실제 필드:

```text

verifyKeyMs / verifyCacheStoreMs / verifyCacheCopyMs
```

## 8. 반드시 산출할 값

각 measured run 에서 최소한:

```text
decodeCount                       decodeTotalMs
decodePreserveAspectCount         decodePreserveAspectTotalMs
verifyMs                          verifyDecodeMs
analyzeMs                         groups
```

그리고 아래 비율을 계산한다. 핵심 지표는 `ms/call` 하나가 아니라 **두 번째
decode 가 실제 production 비용에서 차지하는 비율**이다.

```text
decodePreserveAspectTotalMs / decodeTotalMs
decodePreserveAspectTotalMs / verifyDecodeMs
decodePreserveAspectTotalMs / verifyMs
decodePreserveAspectTotalMs / analyzeMs
(decodeTotalMs + decodePreserveAspectTotalMs) / verifyDecodeMs
(decodeTotalMs + decodePreserveAspectTotalMs) / verifyMs
```

`verifyDecodeMs` 를 "expensive verify" 기준으로 쓰는 이유는 D9c 의 정의와 같다.
D9c 는 D9c stage 합이 `verifyMs` 와 정확히 일치함을 확인했고, 그 합을 호출당
정규화해 "expensive verify 1건당" 수치를 냈다. D3 도 **같은 분모**를 쓴다.

## 9. Count consistency — 사전 예측과 실제 차이의 예상

```text
예상 (verify miss 경로 한정)          근거
decodeCount                  == verifyDecodeMisses   §5.3, miss 1건당 decode 1회
decodePreserveAspectCount    == verifyDecodeMisses   §5.3, miss 1건당 1회
verifyDecodes                == 2 × verifyDecodeMisses  §5.2 이미 성립
```

**단, 이것을 사전 사실로 간주하지 않는다.** 예상과 다르면 아래를 기록한다.

```text
expected count
actual count
delta
reason
```

**예측된 차이 1건 (이미 알고 있는 구조적 이유)**

전역 호출을 세면 `decodePreserveAspectCount > verifyDecodeMisses` 가 된다. §5.3
의 `media_pipeline.cpp:110` 이 crop 지문 생성으로 verify 경로 밖에서
`decodePreserveAspect` 를 호출하고, 그쪽은 telemetry 를 넘기지 않기 때문이다.

D3 의 대응: 두 개수를 **분리해서 보고**한다.

```text
verify 경로 기준 decodePreserveAspectCount     (D3 의 주 지표)
verify 경로 밖 호출                             N/A 로 명시, 추정 금지
```

계측 결과를 맞추기 위해 **호출 경로를 변경하지 않는다.** 개수를 맞추려고 코드를
고치는 것은 D3 가 아니다.

## 10. Timing 조건

D3 는 **실제 production decode 경로**를 계측한다. 한 run 안에서 동일 dataset 과
동일 파일 집합을 사용한다.

```text
warm-up run   : 1회, 결과에서 제외
measured runs : 최소 5회
```

각 measured run 에서 `mean / median / min / max / range` 를 기록한다.

첫 호출의 DLL/codec 초기화 등 **cold-start 비용은 duplicate decode 비용으로
해석하지 않는다.** cold-start 가 발생하면 별도 기록하고 warm measurement 와
혼합하지 않는다. (D2 에서 이미 cold/warm 차이가 수치를 뒤집을 만큼 크다는 것을
확인했다.)

## 11. Production behavior 보존

D3 는 아래 결과를 변경해서는 안 된다.

```text
verifyCalls            verifyDecodeMisses       verifyCacheHits
verifyDecodes          ssimEvals                frameSsimEvals
groups                 final verdict            CPU/GPU parity
```

동일 입력에서 decode 결과, 이미지 크기, 픽셀 결과가 기존 baseline 과 달라져서는
안 된다. instrumentation 때문에 scan 결과나 grouping/verdict 가 달라지면
**측정을 중단하고 원인을 기록한다.**

## 12. Telemetry correctness

D1 의 누적값 double-counting 을 재발시키지 않는다.

### 12.1 기존 identity 가 유지되어야 한다 (D9c)

```text
verifyKeyMs + verifyDecodeMs + verifyCacheStoreMs + verifyCacheCopyMs
  + verifyCropMs + verifyFlipMs + verifyFrameSsimMs + verifyOtherMs
    == verifyMs
```

### 12.2 D3 가 추가하는 identity

```text
decodeTotalMs + decodePreserveAspectTotalMs == verifyDecodeMs 의 decode 성분
```

이 identity 가 깨지면 **timing 결과를 사용하지 않는다.** 어느 timer 가
mis-scoped 인지 드러나기 때문이다. 깨졌을 때의 기본 대응은 계측 철회가 아니라
**원인 기록 + `INCONCLUSIVE`** 다.

### 12.3 값 취급 규칙

```text
N/A / Not measured / unknown
```

을 임의 숫자로 대체하지 않는다. 상태값(`measured` / `not_measured` /
`not_available`)을 JSON 과 함께 보존한다. instrumentation overhead 도
**측정하지 않은 상태에서 "무시 가능"** 이라고 표현하지 않는다.

## 13. Instrumentation 범위

**허용**

```text
counter 추가                elapsed-time 측정
기존 telemetry 확장         benchmark output 의 additive field 추가
schema validation           telemetry analysis
measurement-only test
```

**금지**

```text
decode deduplication        decode result cache
decode cache 구조 변경      decodePreserveAspect 제거
decode 호출 병합            factory reuse
decoder reuse               stream reuse
HandleStream production 채택
CreateDecoderFromStream production 채택
threading 변경              parallelism 변경
algorithm 변경              threshold 변경
grouping 변경               verdict 변경
```

D3 의 코드 변경은 **측정을 가능하게 하기 위한 instrumentation 에 한정**한다.

## 14. 계측 전에 하지 않는 판단

다음 판단을 결과 보기 전에 하지 않는다.

```text
"두 번째 decode 니까 제거하자."
"같은 파일이니까 cache 하면 된다."
"decode 결과를 재사용하자."
"decoder 를 재사용하면 빨라질 것이다."
```

D3 결과가 큰 비용을 보여주더라도 해당 optimization 은 **D3 에 포함하지 않는다.**
결과를 확인한 후 **별도 optimization pre-register** 를 작성한다.

## 16. 핵심 계산 — 반드시 기록

```text
A. 두 번째 decode 자체의 비용
   decodePreserveAspectTotalMs / decodePreserveAspectCount

B. 첫 번째 decode 대비 두 번째 decode
   decodePreserveAspectTotalMs / decodeTotalMs

C. expensive verify 내 비중
   decodePreserveAspectTotalMs / verifyDecodeMs

D. verify 전체 내 비중
   decodePreserveAspectTotalMs / verifyMs

E. 전체 scan 내 비중
   decodePreserveAspectTotalMs / analyzeMs

F. 두 decode 합계
   (decodeTotalMs + decodePreserveAspectTotalMs) / verifyDecodeMs
```

**단순 extrapolation 은 실제 production speedup 으로 기록하지 않는다.**

## 17. 성공 조건 — "빨라졌다" 가 아니다

아래가 모두 충족되면 `D3 = PASS` 다.

```text
1. decode / decodePreserveAspect 호출 횟수가 측정됨
2. 두 경로의 wall-clock 비용이 측정됨
3. verifyDecodeMs / verifyMs / analyzeMs 대비 비율이 계산됨
4. 최소 5회 이상의 반복 측정이 완료됨
5. mean / median / min / max / range 가 기록됨
6. §12.1 과 §12.2 의 stage identity 가 성립함
7. 기존 scan 결과와 parity 가 유지됨
8. 기존 테스트가 모두 유지됨
9. 측정값을 추정값으로 대체한 부분이 없음
```

## 18. INCONCLUSIVE 조건

아래 경우 억지로 결론을 만들지 않고 `INCONCLUSIVE` 로 기록하며, 측정 실패
원인과 재검토 조건을 남긴다.

```text
1. 두 decode 호출의 비용을 분리할 수 없음
2. instrumentation 때문에 stage totals 가 재구성되지 않음
3. run-to-run variation 이 측정을 해석할 수 없을 정도로 큼
4. 호출 count 와 verifyDecodeMisses 관계가 설명되지 않음
5. production result 가 instrumentation 때문에 변경됨
6. 필요한 denominator 가 실제로 측정되지 않음
```

## 19. 다음 optimization 연결 규칙

D3 자체는 optimization 을 결정하지 않는다.

```text
0.x ms 수준        → low-priority 후보가 될 수 있음
수 ms 또는
expensive verify 의 의미 있는 비율  → 후속 optimization 후보가 "열린" 것일 뿐
```

후속 단계의 별도 pre-register 에서 다시 정의한다.

```text
candidate / expected mechanism / baseline / dataset / measurement method
accuracy risk / rollback condition / acceptance criteria
```

## 6. 해석 — 그리고 반드시 함께 봐야 하는 사실

D3 가 답한 질문: **두 번째 decode 는 verifyDecodeMs 의 49.60 %,
verifyMs 의 39.19 %, analyzeMs 의 38.47 % 를 차지한다.**

이 숫자만 보면 중복 decode 제거가 아주 강한 후보처럼 보인다. **그러나
"중복" 이라는 표현은 정확하지 않다.** 계측 전 코드 확인에서 이미 확인했고
결과가 그랬다.

```text
src/image_verify.cpp:82-83
  decode(path, kDim, kDim, f, ...)                 → f : 고정 kDim × kDim
  decodePreserveAspect(path, kDim, a, ...)         → a : aspect 보존 축소

src/image_verify.cpp:229
  verifyScorePlan(fA, aA, fB, aB, hammingSim, tel) → 둘 다 사용된다
```

**두 호출은 같은 결과를 두 번 계산하는 것이 아니라, 같은 파일의 서로 다른
지오메트리 두 벌을 만든다.** `f` 와 `a` 는 `VerifyBuffers{f, a}` 로 캐시되고
scoring plan 이 둘 다 소비한다. 따라서:

- 두 번째 decode 를 단순히 제거하면 **`a` 가 사라지고 similarity / verdict 가
  바뀐다.** 이는 최적화가 아니라 정확성 회귀다.
- 두 비용이 거의 같다는 사실은 "한 번만 하면 된다"는 근거가 **아니다.**
  대신 "두 번의 WIC decode 파스를 **한 번의 고해상도 decode + 두 번의
  리사이즈** 로 대체할 수 있는가" 라는 **별도의 질문**을 연다.
- 이것은 §11 이 금지한 "결과를 보기 전에 제거하자" 와 정면으로 반대되는
  방향이다. 그래서 **D3 에서 구현하지 않는다.**

## 11. 구현 중 발견한 실제 결함 — 영구 기록

### 11.1 pre-register §5.1 의 오류 (counters)

pre-register 초안이 `calls` / `aspectCalls` 도 두 호출의 합이라고 적었으나
**틀렸다.** 구현 중 실제 코드를 다시 읽어 `decode()` 는 `calls` 만,
`decodePreserveAspect()` 는 `aspectCalls` 만 증가시킴을 확인했다.

```text
원래 기록: calls 와 aspectCalls 도 두 호출의 합   ← 오류
오류 원인: 타이머 누적 구조에서 카운터 증가 지점을 확인하지 않았다
수정된 값: 타이머 계열과 결과 카운터만 합쳐져 있었다. calls / aspectCalls 는
           원래부터 분리돼 있었다.
수정 이유: D9d 리포트가 두 키를 이미 서로 다른 값으로 출력하고 있었다.
```

정리는 §5.1.1 에 투명하게 남겼다. D3 의 결론은 바뀌지 않는다 — 측정 대상은
합쳐져 있던 **타이머**이며, 이것이 D9c 의 "decode 94.90 %" 를 구성했기 때문이다.
실제로 D3 리포트에서 두 번째 호출의 횟수를 `.calls` 가 아니라 **`.aspectCalls`**
로 읽어야 했고, 그렇게 구현했다.

### 11.2 telemetry 전사 누락 (실측값이 0 으로 나옴)

첫 D3 실행에서 `decodeFullTotalMs` / `decodeAspectOnlyTotalMs` 가 **0** 으로
나왔다. `verifyDecodeMs`(17,787.9 ms) 와 combined `decodeTotalMs`(17,780.0 ms) 는
정상이었으므로 타이머는 동작하는데 새 필드만 비어 있었다.

원인은 `src/scan_pipeline.cpp` 의 `analyze()` 가 telemetry 를 **필드 하나씩**
`s.analyze` 로 복사하는데(`s.analyze.decode=tel.decode;` 등) D3 필드 2개를
복사하지 않았기 때문이다. verify 경로는 값을 채웠는데 리포트에 닿지 않았다.

```text
해결: s.analyze.decodeFull / s.analyze.decodeAspect 전사 2줄 추가
결과: decodeSplitOverMs = 0.000000 으로 identity 성립 확인
```

**일반화 규칙**: 필드를 추가할 때 "구조체에 넣었다"만으로는 부족하고,
**값이 소비자에게 전달되는 경로까지** 확인해야 한다. 멤버 단위 복사 구조에서는
특히 그렇다. 이 결함은 측정값이 조용히 0 이 되는 형태로 나타났으므로,
`not_measured` / 0 구분 원칙이 실제로 위험을 막았다.
