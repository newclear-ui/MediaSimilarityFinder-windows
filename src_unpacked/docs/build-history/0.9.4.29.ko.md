# MediaSimilarityFinder v0.9.4.29 — D3 `decode` / `decodePreserveAspect` 중복 비용 계측

Status: **PRE-REGISTERED** (D3 instrumentation 코드보다 먼저 커밋된다)

D3 는 **measurement** 빌드다. 최적화하지 않는다.

---

## 1. 기준점

```text
base version : v0.9.4.28
base commit  : 256c41a
D2 status    : PASS
Path C       : DEFERRED (제품 채택 안 함)
```

D2 의 `CreateDecoderFromStream` + `HandleStream` 경로는 **현재 제품 경로에
채택하지 않는다.** D3 는 그 결론을 변경하지도, 재평가하지도 않는다.

## 2. 변경 필요성

D9c 는 `expensive verify` 안에서 decode 가 **94.90 %** 라고 측정했다. 그러나 그
94.90 % 는 **두 개의 서로 다른 decode 호출이 합쳐진 값**이다. 지금까지 두 호출을
분리한 적이 없다.

D2 는 decoder **진입 경로**의 비용 구조를 좁혔고, 그 결과는 "이득이 작아 채택
하지 않음"으로 끝났다. 그 판단 자체는 건드리지 않는다. 다만 D2 를 통해 두 가지가
확정되었다.

```text
1. decoder 생성 자체는 호출당 수십~수백 µs 규모이며, 이것만으로는
   verify 전체를 좌우하지 않는다.
2. 그러면 남은 큰 질문은 "decode 가 몇 번 호출되는가" 이다.
   호출 횟수가 그대로 비용이다.
```

현재 구조상 verify miss 1건마다 **같은 파일을 두 번 decode** 한다. 이 중 두 번째
호출이 실제 비용에서 얼마나 차지하는지 **아직 아무도 측정하지 않았다.**

## 3. 핵심 질문

> `decodePreserveAspect()` 가 동일 파일을 다시 decode 하면서 발생시키는 실제
> wall-clock 비용은 얼마이며, 그것은 `expensive verify` / `verify` / 전체 scan
> 시간 중 각각 몇 % 인가?

이 질문에 답하기 전까지 **어떤 최적화도 채택하지 않는다.**

## 4. D2 결과의 경계 — D3 의 baseline 으로 쓰지 않는다

```text
D1  CreateDecoderFromFilename ≈ 2.6257 ms/call   (cold, 코덱 DLL 최초 로드 포함)
D2  decoder call ≈ 0.07~0.12 ms                  (warm, 형식별 warm-up 제외)
D3  decode / decodePreserveAspect 분리 비용
```

D1 과 D2 는 측정 조건(cold / warm)이 달라 **직접 비교할 수 없고**, 그 차이는
성능 개선이 아니다. D3 도 마찬가지로 D2 나 D1 과 자동으로 비교하거나 차이를
성능 향상으로 표현하지 않는다. **측정 조건이 명확히 동일할 때만** 직접 비교한다.

## 5. 코드 구조 사전 조사 — 계측 전에 확인한 사실

계측 계획은 아래 실제 코드에서 나왔다. 추측이 아니다.

### 5.1 두 호출이 같은 telemetry 에 합쳐진다 (D3 의 정확한 공백)

`src/image_verify.cpp:78`

```cpp
if(!dec.decode(path, kDim, kDim, f, tel? &tel->decode : nullptr)
   || !dec.decodePreserveAspect(path, kDim, a, tel? &tel->decode : nullptr)) { ... }
```

**두 호출 모두 동일한 `&tel->decode` 를 넘긴다.** 그래서 `AnalyzeTelemetry::decode`
(D9d 가 만든 단일 `DecodeTelemetry`) 안의 모든 타이머와 카운터가 두 호출의
**합**이다.

```text
DecodeTelemetry::calls       → decode() + decodePreserveAspect() 합계
DecodeTelemetry::aspectCalls → 위와 동일한 버킷에 누적됨
DecodeTelemetry::totalMs     → 두 호출의 합
DecodeTelemetry::openMs      → 두 호출의 합
DecodeTelemetry::copyMs      → 두 호출의 합
```

즉 **이미 존재하는 카운터는 두 호출을 구분하지 못한다.** D3 는 개념을 새로 만드는
것이 아니라, **이미 존재하는 누산기를 호출별로 분리**하는 작업이다.

### 5.2 호출 횟수 카운터는 이미 2회 증가로 되어 있다

`src/image_verify.cpp:79`

```cpp
if(tel){ tel->verifyDecodes += 2; }
```

따라서 `verifyDecodes == 2 × verifyDecodeMisses` 가 **구조적으로 이미 성립**한다.
D3 는 이 의미를 바꾸지 않는다.

### 5.3 decode 호출 지점은 총 3곳이며, telemetry 를 넘기는 곳은 1곳뿐이다

| 호출 지점 | 호출 | telemetry 전달 | D3 대상 |
|---|---|---|---|
| `image_verify.cpp:78` | `decode()` 32×32 + `decodePreserveAspect()` 32×32 | `&tel->decode` (공유) | **O** |
| `media_pipeline.cpp:45` | `decode()` 32×32 (지문용) | **없음** | X |
| `media_pipeline.cpp:110` | `decodePreserveAspect()` 128 (crop 지문용) | **없음** | X |

이것이 §9 의 count consistency 예지를 **미리 깨뜨리는 요인**이다.
`decodePreserveAspect` 는 verify miss 경로 밖에서도 호출되므로, **전역 카운트는
`verifyDecodeMisses` 와 같지 않다.** D3 는 이 사실을 숨기지 않고 사전에 기록한다.

## 7. 측정 대상

최소 telemetry:

```text
decodeCount                  decode() 호출 횟수
decodeTotalMs                decode() wall-clock 합계

decodePreserveAspectCount    decodePreserveAspect() 호출 횟수
decodePreserveAspectTotalMs  decodePreserveAspect() wall-clock 합계
```

가능하면 기존 하위 단계를 각 호출에 개별 귀속시킨다.

```text
open / factory / metadata / orient / resize / convert / copy / pgmFallback
```

**새 telemetry 시스템을 만들지 않는다.** 기존 `DecodeTelemetry` 의 필드와 의미를
우선 재사용하고, §5.1 의 공유 누산기를 호출별로 **분리**하는 것이 전제다.
분모로 쓸 실제 필드:

```text
verifyMs                 AnalyzeTelemetry::verifyMs  (verify 전체)
verifyDecodeMs           D9c miss-only decode 버킷
verifyKeyMs / verifyCacheStoreMs / verifyCacheCopyMs
verifyCropMs / verifyFlipMs / verifyFrameSsimMs / verifyOtherMs
analyzeMs                BenchmarkRecorder::analyzeMs_  (scan 수준 총계)
```

## 8. 반드시 산출할 값

각 measured run 에서 최소한:

```text
decodeCount                       decodeTotalMs
decodePreserveAspectCount         decodePreserveAspectTotalMs
verifyMs                          verifyDecodeMs
analyzeMs                         groups
```

그리고 아래 비율을 계산한다. 핵심 지표는 `ms/call` 하나가 아니라 **두 번째
decode 가 실제 production 비용에서 차지하는 비율**이다.

```text
decodePreserveAspectTotalMs / decodeTotalMs
decodePreserveAspectTotalMs / verifyDecodeMs
decodePreserveAspectTotalMs / verifyMs
decodePreserveAspectTotalMs / analyzeMs
(decodeTotalMs + decodePreserveAspectTotalMs) / verifyDecodeMs
(decodeTotalMs + decodePreserveAspectTotalMs) / verifyMs
```

`verifyDecodeMs` 를 "expensive verify" 기준으로 쓰는 이유는 D9c 의 정의와 같다.
D9c 는 D9c stage 합이 `verifyMs` 와 정확히 일치함을 확인했고, 그 합을 호출당
정규화해 "expensive verify 1건당" 수치를 냈다. D3 도 **같은 분모**를 쓴다.

## 9. Count consistency — 사전 예측과 실제 차이의 예상

```text
예상 (verify miss 경로 한정)          근거
decodeCount                  == verifyDecodeMisses   §5.3, miss 1건당 decode 1회
decodePreserveAspectCount    == verifyDecodeMisses   §5.3, miss 1건당 1회
verifyDecodes                == 2 × verifyDecodeMisses  §5.2 이미 성립
```

**단, 이것을 사전 사실로 간주하지 않는다.** 예상과 다르면 아래를 기록한다.

```text
expected count
actual count
delta
reason
```

**예측된 차이 1건 (이미 알고 있는 구조적 이유)**

전역 호출을 세면 `decodePreserveAspectCount > verifyDecodeMisses` 가 된다. §5.3
의 `media_pipeline.cpp:110` 이 crop 지문 생성으로 verify 경로 밖에서
`decodePreserveAspect` 를 호출하고, 그쪽은 telemetry 를 넘기지 않기 때문이다.

D3 의 대응: 두 개수를 **분리해서 보고**한다.

```text
verify 경로 기준 decodePreserveAspectCount     (D3 의 주 지표)
verify 경로 밖 호출                             N/A 로 명시, 추정 금지
```

계측 결과를 맞추기 위해 **호출 경로를 변경하지 않는다.** 개수를 맞추려고 코드를
고치는 것은 D3 가 아니다.

## 10. Timing 조건

D3 는 **실제 production decode 경로**를 계측한다. 한 run 안에서 동일 dataset 과
동일 파일 집합을 사용한다.

```text
warm-up run   : 1회, 결과에서 제외
measured runs : 최소 5회
```

각 measured run 에서 `mean / median / min / max / range` 를 기록한다.

첫 호출의 DLL/codec 초기화 등 **cold-start 비용은 duplicate decode 비용으로
해석하지 않는다.** cold-start 가 발생하면 별도 기록하고 warm measurement 와
혼합하지 않는다. (D2 에서 이미 cold/warm 차이가 수치를 뒤집을 만큼 크다는 것을
확인했다.)

## 11. Production behavior 보존

D3 는 아래 결과를 변경해서는 안 된다.

```text
verifyCalls            verifyDecodeMisses       verifyCacheHits
verifyDecodes          ssimEvals                frameSsimEvals
groups                 final verdict            CPU/GPU parity
```

동일 입력에서 decode 결과, 이미지 크기, 픽셀 결과가 기존 baseline 과 달라져서는
안 된다. instrumentation 때문에 scan 결과나 grouping/verdict 가 달라지면
**측정을 중단하고 원인을 기록한다.**

## 12. Telemetry correctness

D1 의 누적값 double-counting 을 재발시키지 않는다.

### 12.1 기존 identity 가 유지되어야 한다 (D9c)

```text
verifyKeyMs + verifyDecodeMs + verifyCacheStoreMs + verifyCacheCopyMs
  + verifyCropMs + verifyFlipMs + verifyFrameSsimMs + verifyOtherMs
    == verifyMs
```

### 12.2 D3 가 추가하는 identity

```text
decodeTotalMs + decodePreserveAspectTotalMs == verifyDecodeMs 의 decode 성분
```

이 identity 가 깨지면 **timing 결과를 사용하지 않는다.** 어느 timer 가
mis-scoped 인지 드러나기 때문이다. 깨졌을 때의 기본 대응은 계측 철회가 아니라
**원인 기록 + `INCONCLUSIVE`** 다.

### 12.3 값 취급 규칙

```text
N/A / Not measured / unknown
```

을 임의 숫자로 대체하지 않는다. 상태값(`measured` / `not_measured` /
`not_available`)을 JSON 과 함께 보존한다. instrumentation overhead 도
**측정하지 않은 상태에서 "무시 가능"** 이라고 표현하지 않는다.

## 13. Instrumentation 범위

**허용**

```text

기존 telemetry 확장         benchmark output 의 additive field 추가

```

**금지**

```text

```

D3 의 코드 변경은 **측정을 가능하게 하기 위한 instrumentation 에 한정**한다.

## 18. INCONCLUSIVE 조건

원인과 재검토 조건을 남긴다.

```text

3. run-to-run variation 이 측정을 해석할 수 없을 정도로 큼

5. verdict, grouping, parity 가 보존된다
6. 다음 후보가 증거로 선정 가능해진다
```

최종 상태는 `PASS` / `INCONCLUSIVE` 중 하나로 판정하고, 비용 구조가 충분히
측정되었는지로 판단한다. **성능 개선은 주장하지 않는다.**
