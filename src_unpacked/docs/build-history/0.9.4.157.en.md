# MediaSimilarityFinder v0.9.4.157 — Video Thumbnail Fix + AV1 Software Decode

Baseline `0.9.4.156` → this build `0.9.4.157`.
CPU CTest **131/131**, GPU CTest **132/132** (1 new CTest: video_thumb_e2e_test).
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` / `kProtocol 1` unchanged.

## 1. Why the change was needed

- No video previews were shown at all. Root cause: `ThumbnailStore`'s JPEG compressor used hardcoded `TJSAMP_420` even for gray input, so `tjCompress2` failed. Every analyzed video (served from engine art, 48×48 gray) failed thumbnail issuance. (Images use the BGRA path and were unaffected.)
- An AV1 file failed analysis. The vcpkg FFmpeg had no AV1 software decoder (no dav1d), and the GPU at hand (RTX 3080 Ti) has no AV1 hardware decoder to fall back to.

## 2. Previous structure

- `backend_thumb.cpp::compress()` hardcoded `TJSAMP_420` regardless of pixel format.
- vcpkg FFmpeg features: ffprobe + ffmpeg CLI only. AV1 decoders: native `av1` only, no dav1d.

## 3. New structure

- `compress()` uses `TJSAMP_GRAY` for gray input (a gray JPEG has no chroma planes to subsample).
- vcpkg `ffmpeg` gains the `dav1d` feature → AV1 software decoding secured (not the NVDEC path; independent of the post-Vulkan order).
- Regression pin: new `video_thumb_e2e_test` — after a real scan, `getVideoThumb` (engine) → `ThumbnailStore::fetch` (the exact backend path) → disk round-trip without the engine. Verified to fail at step 2 on the old code.

## 4. Resolved state

- Analyzed videos get thumbnails again through the engine-art path.
- AV1 files analyze via software decode regardless of missing HW support.

- Judgement, storage, protocol unchanged. No DB version bump.

The fundamental fix (device-resident decode) stays a HW-phase task (post Vulkan); the D3D11VA path was verified open by measurement.
