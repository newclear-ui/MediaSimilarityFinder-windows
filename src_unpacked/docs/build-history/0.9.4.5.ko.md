# MediaSimilarityFinder v0.9.4.5 — Node B4: Stability Control

B4 검증 기준점. brief §8의 3요소(moving average·hysteresis·minimum
hold)를 스케줄러 내부에 구현한다. 엔진·파이프라인 변경 없음.
엔진 1.5.0·DB 1.0.3·캐시 v9·schema 1 불변.

## 변경 필요성
- B3까지 관측이 바뀌면 2초마다 판단이 그대로 바뀌었다. 시스템 노이즈가
  그대로 adjustment 카운터와 shares에 타면서, 경계 부근에서는 GPU
  kill/relief가 매 틱 뒤집힐 수 있었다.

## 기존 구조
- `evaluate()`는 원시 입력을 직접 쓰고 즉시 발표했다.

## 변경 구조
- SMA-4: 관측 rate·부하를 고정 윈도우 평균으로平滑한다. known일 때만
  feed, unknown이면 레인 clear(오래된 값이 새 값 행세 금지).
  baseline은 정적이라 대상 아님.
- kill-band hysteresis: 가용도 0.02 이하(부하 98 이상)에서 kill,
  0.05 초과(부하 95 미만)에서 relief, 사이는 이전 발표 상태 유지.
  정수 nvidia-smi 판독이 포화 구간에서 딱 이 밴드를 오가므로, 밴드
  없이는 kill이 매 주기 뒤집힌다.
- minimum hold(기본 10초, 설정 가능, 0이면 해제): 발표된 판단 전체가
  hold 만료 후에만 바뀐다. telemetry 입력(`lastHw_`)은 최신 유지,
  정책만 유지 — 관측 진실과 정책 안정을 분리한다.
- `decide()` 직후 첫 변경은 hold 면제(B1 호환). adjustments는 발표
  기준이라 시스템 노이즈에 더는 요동치지 않는다.
- 엔진 변경 없음: 게이트가 읽는 `lastDecision()`이 곧 발표된 판단이라
  실행 안정화가 자동 상속된다.

## 선택 이유
- 세 기제가 한 목표(방향 전환 희박화)를 분담한다: SMA는 입력 노이즈,
  밴드는 경계 dithering, hold는 발표 빈도. 어느 하나만으로는
  정수 부하 판독+2초 주기의 뒤집힘을 못 막는다.
- hold 기본값 10초는 주기(2초)의 5배 — 한두 번의 튐은 흡수하고 실제
  전환은 최대 10초 지연되는 수준이다. B6 정책에서 모드별 조정 가능.

## 해결된 문제
- 판단 발표가 안정됐다. B5는 비용 입력만 얹으면 된다.

## 정확성 영향
- 없음. 게이트 위치·판정 경로 무변경. hold는 발표 시점만 늦춘다.
  양쪽 `scan_workflow_test` 동일 결과(스캔이 주기보다 짧아 hold와
  무관).
