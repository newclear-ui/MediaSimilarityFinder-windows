# MediaSimilarityFinder v0.9.4.129 — Hybrid (AB) live-match loss fixed (live-index off-by-one)

Baseline `0.9.4.128` -> this build `0.9.4.129`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged (verdicts unchanged; CTest registration count unchanged).

## 1. Why the change was needed

- Field report: in `Auto (mixed verification)` (AB) scans, **similar groups 0 / duplicate files 0**. The detailed log carried the signature `candidates 19187, pairs 0, groups 0, reduction 100.0%` -- candidates were found, but zero pairs survived. B (Stable) and A (Fast) modes were normal.
- Probe reproduction (18-file real set, fresh index): only AB showed `pairs=0, liveBatches=0, verifyCalls=0, candidates=8`; Sequential showed `pairs=8`. The AB final pass skips both-changed image pairs on the 0.9.4.81 premise that "the live streaming pass already emitted them" -- but live delivered nothing, so fresh/rescan AB results were structurally always 0.
- Root cause (code trace + isolated probe): `ScanPipeline::addAndMatch` emitted matches before the new file was pushed into `files_`, so a match's right index equaled `files_.size()`. The consumer `liveEmit`'s bounds check `if(m.left>=lf.size()||m.right>=lf.size()) return;` rejected every one of them: **the live stream never delivered a single match since it was introduced in 0.9.4.81.**
- Second defect: telemetry/detailed-log `pairs`/`groups` count only final-analyze-pass onMatch callbacks. Even with live fixed, AB's log would still read 0.

## 2. Previous structure

- Live pass: `processImageBatch`/`processVideoRange` called `livePipe.addAndMatch(mf, maxDistance, liveEmit)` while pushing the file into `files_`. `addAndMatch` invoked `onMatch(match)` inside the consider loop, and `files_.push_back(f)` ran afterwards.
- AB final pass: `included()` skips both-changed image pairs when `skipBothChangedImages=(analyzeMode==Hybrid)&&liveMatch` (live owns them).
- Telemetry: `telemetry_.addStreamedMatch()` and the group union-find (`clusterParent`/`clusterTouched`) were updated only from the final pass. Live emissions called `control->onMatch` only and never entered the accounting.
- The live pipe was fed in every mode (including Sequential).

## 3. Changed structure

- `scan_pipeline.cpp::addAndMatch`: matches are collected into a local vector; the file is fully registered (`files_.push_back` + `indexFile`) and only then are the matches emitted. The callback now observes a fully registered file, matching the batch `analyze()` contract.
- `media_search_engine.cpp`:
  - In AB, live-owned both-changed image pairs are added to the report/telemetry: `nLiveImgPairs` (r.groups = st.groups + nLiveImgPairs, included in r.imgPairs), and a path-keyed union-find (`tlParent`/`tlKind`) merges the live (AB) and final streams the same way the GUI does. `streamedMatches` is incremented for AB live only -- A/B count every pair in the final pass, so this avoids double counting.
  - Live pipe feeding is limited to A/AB (`liveStreamActive`). Sequential (B) is contracted to "verify after the walk" (analyze_mode.h) and its final pass emits every pair; feeding it there would double-emit pairs into `takePending()`/`matchesBatch` (walker_queue_test pins the exact pending set).
- `gui/mainwindow.cpp` search-summary CPU row: now shows process (avg/max/std) and **system average (cpuSysMean)** side by side. New keys `detailLogCpuProc`/`detailLogCpuSys`. Background: the process metric is normalized by logical CPU count, so 16 busy threads read as ~2-6% (the field report "CPU shows only 2%"); the system mean was already in the JSON but never displayed.

## 4. What was resolved

- AB fresh/rescan scans produce groups and duplicate files normally again. The missing-thumbnails symptom was a direct consequence of groups 0 (no rows to show) and is not a separate code defect (the backend thumbnail path was found healthy by the 0.9.4.125 keep-as-is ruling and probe verification).
- The detailed log now records the same numbers in every mode: on the 18-file set, B/A/AB all report `pairs=8, candidates=8, imgGroups=3, imgDupFiles=8, groups=3`.
- The "CPU 2%" question is answered: the summary shows process and system values separately.

## 6. Impact and limitations

- Verdicts, storage, protocol, engine/DB/schema/cache and the journal schema are unchanged. CTest registration count unchanged (125/126).
- Live (A) mode still re-verifies and re-emits both-changed pairs in its final pass by design (the GUI union-find absorbs duplicates into the same result; telemetry counts the final pass once). AB's live (both changed) and final (exactly one changed) sets are mutually exclusive, so there are no duplicates there.
- The live stream works for the first time since 0.9.4.81. A/AB scans pay live verification during the walk; the final re-verification portion is cheap through verify-cache hits. B mode keeps its observed behavior and results exactly.
- Remaining visual check (user): AB Auto-mode field scan -- group/duplicate counts, thumbnail display, and detailed-log numbers agreeing.
