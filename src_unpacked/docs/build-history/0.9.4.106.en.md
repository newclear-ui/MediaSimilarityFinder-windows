# MediaSimilarityFinder v0.9.4.106 — What 100.0% means (identical content / perceptual badge)

Baseline `0.9.4.105` -> this build `0.9.4.106`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged.

## 1. Why the change was needed

User report: three derivatives of one photo (original / watermark+crop / sticker, `D:\Temp\OpenCodeWork\100`) all displayed 100%, reading as "identical files". Audit findings:

- 100.0% appears only at **hash distance 0** (one of the full/mirror/crop variant pairs is bit-identical; the blend can reach at most 99.2), and at that moment the `verifyImagePair` fast path (>=97) **skips SSIM**. Probe measurement: all three pairs distance 0; forcing the SSIM blend gives 99.34/99.82/99.69%.
- User data (ss_twit index, 177,594 files / 15,187 pairs): of 11,817 displayed-100.0% pairs, **3,511 are content-identical (size+quick_hash)** and **8,306 are derivatives**. Verifying all 8,306 with option A (always blend) would cost, on the G: drive (decodeBoth(64) measured: median 43 ms, mean 66 ms; C: baseline 4.1 ms), **+8.0-12.3 min serial** (+80-125% on top of the recorded 592 s verify) -> **option A is expensive**.
- Decision: **option B first (make the display honest)** — no verdict, number, or verification-cost change; show WHAT the 100 means next to it. Option A (honest numeric value) is deferred with measured cost and revisit conditions.

## 2. Previous structure

- The GUI received only the match percent (`matchRows` 3 fields `left\tright\tpercent`, `BackendMatch` 4 fields). The file quick_hash stayed inside the index DB and never reached the GUI.
- The group reference file shows "100% · reference" by convention; other files showed the raw percent (including 100.0%).
- The engine's `MediaFile` carried no quick_hash, and the final analyze pass rebuilt `files_` from the DB (size/modified/fingerprints/crops only).

## 3. New structure

- **Engine**: `MediaFile.quickHash` added (filled on all four paths: live analysis, video, revalidation toMedia, final DB rebuild). `MediaMatch.contentIdentical` / `SearchMatch.contentIdentical` added; `ScanPipeline::sameContent()` (equal size && non-empty quick_hash && equal) decides. Set in the parallel image pass, the sequential pass, the video pass, and the `addAndMatch` live pass.
- **Final-pass rebuild fix**: `scan()` rebuilds `files_` from the DB (line 1015-1021) and was missing the quickHash transfer -> without this fix every 100.0% would be mislabeled "perceptual" (caught by the test).
- **Transport**: `LiveMatch` -> `BackendMatch` (identical field) -> IPC `matchJson(identical)` / supervisor decode -> `matchRows` 4th field (`0/1`; 3-field rows still accepted). `loadMatches()` and `BackendSession::loadIndex` compute identity from the stored quick_hash with no extra I/O (loadIndex reuses the states it already read; loadMatches reuses the open-time `candidateStates_` snapshot).
- **GUI**: `contentFlag_` (bit1 = a content-identical 100% pair exists, bit2 = only perceptual 100% pairs). `pctText()` appends the badge at 100.0%: `100.0% · 동일 내용` / `100.0% · 지각 동일` (EN: identical content / perceptual match), on the grid, the list, and the detail similarity row. The reference-file "100% · reference" convention is unchanged.
- **Cost**: display-only — no added decodes/SSIM, no verdict/group/percent/stored-pair change. Identity is a memory string comparison.
- Two translation keys added (`identicalContent`/`perceptualMatch`); tr-keys 69 -> **71**.

## 4. Resolved state

- 100.0% now says whether it means byte-identical (size+quick_hash) or perceptually identical (watermark/sticker/re-encode/crop derivative). The user's issue (three files all 100% read as identical) is solved at zero added verification time.
- Verdicts, groups, numbers, DB, and protocol semantics are all unchanged (additive fields only).

## 6. Future impact and limits

- `kProtocol` unchanged (additive field). engine/DB/schema/cache unchanged. The flag is not persisted per stored pair but recomputed from quick_hash at load, so no schema change.
- quick_hash covers the 64 KiB head + length, so in theory a same-size, same-head, different-tail file could read as "identical content" (practically negligible; full byte comparison is out of scope).
- **Why option A is deferred, with revisit conditions**: A requires extra decodes for 8,306 pairs / 11,995 files on the user's data; measured +8-12 min on the G: drive (+80-125% of verify). Revisit: (1) a secondary signature computed at analysis time (e.g. 16x16 DCT) that separates derivatives without verify decodes, (2) a one-time refined-percent cache (skip re-verification when file identities are unchanged; the 0.9.4.86 dataset-fingerprint-cache pattern), (3) faster storage (SSD -> about +50 s).
