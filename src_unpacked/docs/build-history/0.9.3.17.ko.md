# MediaSimilarityFinder v0.9.3.17 — 영상 단일 스윕 디코드·재생시간 폴백

## 변경 필요성
- 실측 벤치마크(2439개 영상, 15GB, wall 17분)에서 영상 분석이 전체 시간의 97%를 차지했다. 최느림 파일(4K 2160x3840, 182초)은 1개당 175초가 걸렸고, 직접 계측 결과 32px 스윕 83.6초 + 96px 스윕 84.0초로 두 스윕이 동일했다. 즉 디코드 바운드이며 해싱 비용은 0에 가깝다.
- 상세정보 창의 재생시간이 라이브·취소 스캔에서는 항상 "-"였다. `fileDur_`가 최종 `onResults`에서만 채워지기 때문이다.
- 결론적으로 알고리즘 전체 재설계가 아니라 디코드 패스 축소가 정답이다. 파이프라인 구조(캐시 기반 temporal, 스트리밍, GPU 마이크로 배치)는 건전하다.

## 기존 구조
- `build()`/`buildFull()`이 32x32와 96x96 두 번의 전체 파일 스위프를 수행했다.
- 상세정보 재생시간이 `fileDur_`에만 의존했다.

## 변경 구조
- `VideoDecoder::framesAt96Plus32()`를 추가했다. 96x96 단일 스위프로 디코드하고 32x32는 정확한 3x3 박스 평균으로 소프트웨어 유도한다(타임스탬프 동일, 1:1 정렬).
- `build()`/`buildFull()`(96 모드)이 단일 스윕을 사용한다. 96 외 크기 요청 시에만 기존 2-스윕 경로를 유지한다(현재 호출자는 전부 96).
- 32px 유도값이 직접 디코드값과 달라질 수 있으므로 캐시 포맷을 v8 → v9로 올렸다(旧 캐시 무효화, 1회 재지문). 엔진 판정 버전은 1.4.0 → 1.5.0으로 상향했고 저장 쌍은 자동 재검증된다.
- 상세정보 재생시간이 비어 있으면 엔진 파일 목록에서 찾아 표시하고 캐시한다.
- `tests/video_decode_parity_test`를 추가했다. 실제 재인코딩 클립에서 직접-32 대 유도-32의 프레임별 pHash 거리와 `video_similarity`를 검증한다.

## 해결된 상황
- 영상 지문 빌드의 전체 파일 디코드가 절반으로 줄었다(해싱·crop·thumb 로직 불변).
- 라이브·취소 스캔에서도 재생시간이 표시된다.
- 동일 full 해시·temporal 의미는 그대로라 판정 체계가 바뀌지 않는다.

## 검증
- 저속 실물 파일(4K 2160x3840): 스위프 83.6초+84.0초 → 단일 스위프 구조로 절반 예상. parity 테스트 실측: 프레임 6개, 최대 드리프트 4비트, 유사도 96.875.
- `video_decode_parity_test` 신규 PASS(드리프트 4비트 이하, 유사도 95 이상).
- CUDA Release 빌드 PASS, **CTest 63/63 PASS**.
- CPU-only Release 빌드 PASS, **CTest 62/62 PASS**.
- Portable v0.9.3.17 생성 및 smoke PASS, `--version` 0.9.3.17.

## 향후 영향
- 첫 스캔 1회에 한해 v9 캐시 무효화로 전체 재지문이 발생한다. 이후 스캔은 빨라진다.
- 그래도 4K 소프트웨어 디코딩 1회는 남는다. 다음 후보는 NVDEC 하드웨어 디코드 검토다(AV1·코덱 커버리지와 의존성 검토 필요).
- 벤치마크 분석: GPU duty 0.2%는 정상이다. 영상당 GPU 2.5ms 대 빌드 1183ms라 nvidia-smi에 잡히지 않는다. CPU 평균 17%는 G: 드라이브 I/O·디코더 직렬 대기 때문이며 스레드 기아가 아니다. 분석 단계 이전에 멈춘 스캔에서는 analyze 0이 정상이다.
