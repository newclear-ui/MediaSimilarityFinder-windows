# MediaSimilarityFinder v0.9.4.128 — Shared image-decode source (3 file opens -> 1 per image)

Baseline `0.9.4.127` -> this build `0.9.4.128`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged (verdict/fingerprint bytes unchanged).

## 1. Why the change was needed

- A field log (user dataset, 177,880 files, wall 6362.6 s) is dominated by walk 4634.1 s and image decode 3668.0 s, with process total reads of 466.2 GB against a 68.9 GB dataset (~6.8x).
- Code tracing showed 3 WIC factory+decoder creations per image: `decode()` (fixed), `decodePreserveAspect()` (aspect), `decodeWicFileAspectColor()` (color, raw path). D9d measured open+factory at 89.54 % of decode, so 3 opens per file mean triple disk reads and CPU stalls. On a high-latency drive workers block on I/O while the CPU idles (avg 25.3 %).
- `Maximum` at 90 % is a scheduler-allocation policy and unrelated to the decode fan-out (`decodeWorkerCount`, hardware clamp 4-32), so no policy setting could fix this structural cost.

## 2. Previous structure

- `MediaPipeline::imageBatch` ran fixed decode -> pack/hash -> aspect+color re-decode in three phases, opening the decoder 3 times per file.
- The I-2 shared source (`decodeWicBranches`) covered fixed+aspect only; the color lane stayed on a separate raw path. `decodeBoth()` is verify-only, so the scan path never used it.

## 3. Changed structure

- Added branch C (color, BGRA) to `decodeWicBranches`. Scaler math, Fant, the BGRA converter and the trailing orientation pass are byte-identical to the old code; only the factory/decoder/frame is shared.
- New `ImageDecoder::decodeTriple()` produces fixed+aspect+color from 1 open. Per-branch validity matches the three separate calls (fixed failure -> skip the file; aspect failure -> empty crops but color still attempted; color failure -> no thumbnail). Gray-lane PGM fallback follows the `decodeBoth` contract; the color lane has no PGM fallback, as before.
- `imageBatch` calls one `decodeTriple()` and processes aspect/crop/color from in-memory buffers. The per-batch memory bound is kept.
- `decodeColorAspect()` is reimplemented on the shared path; the now-unused raw `decodeWicFileAspectColor()` is deleted (no dead commented code per the rule — its logic survives in branch C).
- Side fix: Release builds linked debug sqlite3/ffmpeg import libs. `FindSQLite3`/pkg-config resolved to debug paths, exposed when the vcpkg debug tree went missing. `unofficial-sqlite3 CONFIG` first + release HINTS on Windows instead of pkg-config. A build-contract correction, not a behaviour change (verified below).

## 4. Resolved state

- Per-image WIC opens 3 -> 1. Two opens' worth of metadata/open/re-read cost is gone.
- Same-file A/B: old build (0.9.4.127 portable) vs new build wall 5.12 s -> 3.02 s (~41 % faster, 4-file slow cohort, first cold pass). Verdicts identical on both sides (scanned=4 analyzed=4 failed=0 candidates=0 groups=0). Warm passes match at ~1.0 s on both (index-reuse path unchanged).
- The 41 % is directional, not a general performance claim, given cold/warm cache confounding. The structural argument (3 opens -> 1 open) is the substance.

## 5. Verification

- The full existing suite passing guarantees byte equality: `xmp_orientation_test` 38 checks + WIC 98/98, `color_thumb_test` (guards the exact production decode functions), `image_verify_test`, `test_mode_xmp_test` 14 checks, field-scale `search_engine_test`.
- FAIL-first character: before sharing, rotation-pair verification lived only at decode level while the 3-open scan path was observable only. After the change the scan path itself uses the shared source, so the existing regression tests are the shared path's evidence.
- Engine/DB versions unchanged: fingerprint bytes are identical, so no stored-pair revalidation occurs.

## 6. Future impact and limits

- Verdicts, storage, protocol, engine/DB/schema/cache and journal schema unchanged. CTest registration counts unchanged (125/126).
- One telemetry meaning change: `addImage`'s cropMs no longer contains re-decode time, only CPU fingerprint time. JSON keys are unchanged, only the value's definition narrowed. No effect on D9d per-stage buckets (the imageBatch path never passed per-stage telemetry).
- Memory: aspect+color buffers are held per batch, tens of MB within the unchanged batch cap.
- The 55 `.jpg`-named MP4 files' analysis_failed settled handling is unchanged (decode failure path untouched).
- Next candidate: the dataset fingerprint itself stays single-threaded sequential. Full rehash after an index wipe is a separate candidate, out of this scope.
