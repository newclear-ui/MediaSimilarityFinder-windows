# MediaSimilarityFinder v0.9.4.152 — 지시 재검토 결함 수정 (P0 content_hash 키·P1 meta·저장 실패· 체크포인트)

기준선 `0.9.4.151` → 본 빌드 `0.9.4.152`.
CPU CTest **127/127**, GPU CTest **128/128** (신규 `ui_persist_fail_test` 1건).
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` / `kProtocol 1` 불변 (판정·스키마 불변).

## 1. 변경 필요성

- 외부 재검토 지시: `.151` 채택 코드가 `content_hash` 삭제에 존재하지 않는 `path` 컬럼을 사용한다(P0). 삭제 대상 행이 있을 때 SQL이 실패해 채택 전체가 롤백된다(삭제 대상이 없던 1h는 통과해서 잡지 못했다).
- P1 세 건 재검토: (a) scratch `meta` 전체 복사가 부분 범위에서 `match_baseline` 등 전역 상태를 오염시키는가. (b) 최종 저장 실패 시 GUI가 스트리밍된 미저장 매치를 보여주는가. (c) SAVEPOINT가 크래시 내구성을 보장하는가.

## 2. 기존 구조

- `.151`의 범위별 삭제는 4개 테이블에 `WHERE path IN ...`을 썼다. `content_hash`의 PK는 `rel`이다.
- meta는 범위와 무관하게 전체 upsert됐다. 부분 범위 scratch의 `match_baseline`은 범위 밖을 검증하지 않았는데도 본 인덱스에 복사됐다.
- 최종 저장 실패 시 `failed`만 내보내고 화면은 스트리밍 누산기 그대로였다(DB는 구 집합).
- 스캔 중 체크포인트는 트랜잭션 안에서 성공하지만(SAVEPOINT), 바깥 트랜잭션 커밋 전 강제 종료되면 함께 사라진다.

## 3. 변경 구조

- **P0**: 테이블 키 명시 매핑. `content_hash` 삭제는 `canonicalRelativePath(root, path)`로 계산한 `rel`을 사용한다(매핑 불가 행은 유지 — stale 캐시 행은 무해, 실패한 DELETE는 전체 롤백이므로). 매핑 함수는 작성자와 동일한 함수다.
- **P1 meta**: `meta`는 전체 범위에서만 채택하고 부분 범위에서는 본 인덱스의 것을 유지한다. 부분 채택 후 다음 A/AB 검색은 `match_baseline` 부재로 강제 전체 검증을 1회 수행한다(안전 방향).
- **P1 저장 실패**: 실패 메시지에 `|msfChanged=N`을 싣고, N>0이면 저장된 구 집합으로 조용히 재적용한다(임시 스트리밍 결과 폐기 = 이전 확정 화면 복구). 동시에 baseline을 무효화해 다음 A/AB 검색이 전체 재검증으로 파일 행/매치 불일치를 치유한다(메타 키 삭제 1개, 데이터 삭제 없음).
- **P1 체크포인트**: 코드는 유지(SAVEPOINT = silent 실패 제거 + 트랜잭션 내 가시성). 킬 내구성 주장은 철회한다: 바깥 커밋 전 강제 종료 시 매치는 사라진다. 파일 행 체크포인트(엔진 커밋)는 기존대로 유효하다. 광범위 트랜잭션 리팩터링은 별도 설계로 분리한다.
- 회귀: e2e `Test 1h` 확장(삭제 파일의 content_hash rel 제거+채택 성공, ignored 보존, baseline 유지, 생산 검색 `forceFullPass` 실측). e2e `Test 1h2`(신규: 쓰기 잠금 하 채택 → 실패+전체 롤백 검증 → 해제 후 재시도로 성공+전체 범위 baseline 채택). `crash_diagnostics_test` §4 유지. `ui_persist_fail_test`(신규): 루프백 인프로세스에서 저장 실패 → 실패 전달+화면==DB(구 집합)+재시도 성공. `database_test` savepoint 절(nested 저장 성공·롤백 시 사라짐·기존 데이터 유지).

## 4. 해결된 상황

- 삭제 대상이 있는 채택이 `content_hash` 때문에 롤백되지 않는다.
- 부분 채택이 전역 baseline을 오염시키지 않는다. 다음 검색이 실제로 전체 검증을 수행함을 로그(`matchBaseline=forceFullPass`)로 확인했다.
- 저장 실패 후 화면은 DB와 일치하고(재적용), 재시도하면 정상 검색된다.
- 스캔 중 체크포인트 실패는 더 이상 조용하지 않다(로그). 킬 내구성은 미입증으로 보고한다.

## 6. 향후 영향 및 한계

- 판정·저장·프로토콜·engine/DB/schema/cache 불변. DB 버전 상향 없음.
- 스캔 중 매치 체크포인트의 강제 종료 내구성은 미입증(별도 설계 필요). 파일 행 체크포인트는 유효하다.
- `finished`/`failed` 메시지 필드 추가는 append-only이며 기존 위치 인덱스를 유지한다.
