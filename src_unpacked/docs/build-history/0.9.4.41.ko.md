## 1. 변경 필요성

v0.9.4.40 의 잔여 실패는 HEVC 1080p 한 건이었다.


질문은 하나였다. **이것이 현재 seek API / decoder interaction 으로 해결 가능한가?**
해결 가능하면 승격 근거를 얻고, 불가능하면 **HEVC = SequentialPreferred 를 최종
확정한다.** HEVC 를 반드시 살리는 것이 목표가 아니었다.

## 3. 세 가지 확인된 사실

### 3.1 `AVSEEK_FLAG_ANY` 는 문제를 해결하지 못하고 **악화**시킨다

```text
HEVC 1080p:  A viol=2   →   C viol=14
H.264 270s :  A viol=0   →   C viol=33
H.264 1080x1920: A viol=0 → C viol=12
```

진단 전용이라는 지시 §7 의 예 자격 심사가 정당화되었다. non-keyframe seek 는
landing 을 정확하게 만드는 대신 **더 뒤의 프레임에 착지**해 위반을 키운다.
진단 전용 후보로 남는 것이 옳다.

### 3.2 `avformat_flush()` 는 아무 영향이 없다

```text
A 와 D 가 모든 8개 파일에서 viol·decoded·tsLater 가 동일
```

demuxer 내부 버퍼 폐기는 원인이 아니다. `avcodec_flush_buffers` 만으로 충분하다.

### 3.3 유일하게 안전한 primitive 는 `av_seek_frame(..., BACKWARD)` 뿐이다

`avformat_seek_file` 의 좁은 window 와 `AVSEEK_FLAG_ANY` 는 모두 non-keyframe
착지를 허용하므로 exactness 를 깨뜨린다. **사용 가능한 API 안에서 HEVC 1080p 의
2건 위반을 없앨 방법은 없다.**

## 6. 절차상 고친 것 두 가지

작업 중 발견·수정한 실제 결함 두 건을 기록한다.

### 6.1 verdict 로직 버그 (중요)

첫 구현은 모든 파일의 exact 결과를 합산해 `VERIFIED` 를 보고했다.
**H.264 smoke 그룹이 HEVC 실패를 가리는 잘못**이었다. HEVC 만으로 판정하도록
고쳤고, 그 결과가 `NOT VERIFIED` 다. **잘못된 결론을 보고할 뻔했다.**

### 6.2 use-after-free 크래시

`avformat_close_input(&fmt)` 이후 dangling `st` 를 printf 에서 참조해
access violation(0xC0000005)이 발생했다. close 전에 width/height 를 복사하도록
수정했다.

부수적으로 FFmpeg 9 에서 `has_b_frames` 와 `FF_PROFILE_*` 상수가 제거/변경되어
있음을 확인했고, 존재하지 않는 필드를 읽지 않도록 profile 정수값만 기록한다.

## 9. 미해명으로 남기는 것

1. **HEVC 1080p 의 2건 위반 원인 자체는 여전히 미규명이다.** 어떤 API 로도
   재현·해결되지 않았다는 것이 이번 버전의 결론이지, 왜 그런지는 모른다.
   지시 §19 에 따라 여기서 더 깊이 들어가지 않는다.
2. **HEVC 1360x808 은 exact 인데 1080p 는 아니다.** 같은 codec 안에서의
   차이 원인은 조사하지 않았다.
3. **HEVC 파일이 2편뿐이다.** 결론의 표본이 작다.
4. E-2B 의 4K GOP mismatch 11 과 AV1 은 정책 그대로 유지한다(지시 §20·21).
5. planner calibration 은 하지 않았다(지시 §22). E-3B 몫이다.
