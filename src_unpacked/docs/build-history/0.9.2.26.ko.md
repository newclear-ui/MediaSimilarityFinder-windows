# 0.9.2.26 — CandidateIndex 대규모 성능·메모리 최적화

## 중요 변경
기존 CandidateIndex의 BK-tree는 해시 노드마다 별도 heap 객체와 `unique_ptr`/`unordered_map` 구조를 사용했다. 파일 수가 증가하면 노드 및 포인터 분산 비용이 커지고 검색 시간이 급격히 증가하는 문제가 확인되었다.

0.9.2.26에서는 기본 검색 범위인 Hamming distance `D <= 8`에 대해 **정확성을 유지하는 9-part multi-index hash** 구조로 변경했다.

64-bit hash를 `8 + 7×8` bit의 9개 partition으로 나누고, 각 partition의 동일한 bucket을 후보로 수집한다. 두 hash의 Hamming distance가 8 이하라면 9개 partition 중 적어도 하나는 완전히 동일해야 하므로 후보 누락이 없다. 이후 전체 64-bit Hamming distance를 다시 계산해 최종 후보를 검증한다.

`D > 8` 요청은 보수적으로 전체 hash를 정확히 검사하는 fallback을 사용한다. 따라서 기존 API의 임의 distance 요청에 대한 정확성은 유지된다.

## 구현
- `CandidateIndex` 저장 구조를 단일 hash-entry 배열 + 9개 partition bucket index로 변경.
- bucket에는 entry 위치를 저장해 node별 heap allocation을 제거.
- `reserve()`가 실제 entry/bucket capacity를 예약하도록 변경.
- `Stats` 추가:
  - nodeCount
  - edgeCount/storedRefs
  - maxDepth
  - bucketCount
- candidate pair 생성은 기존 결과 정렬 규칙을 유지.
- 8-bit/7-bit partition 경계에 걸친 8-bit 변형 regression 추가.
- `D > 8` exact fallback regression 추가.
- 100,000개 대규모 benchmark를 선택적으로 실행할 수 있도록 `MSF_LARGE_BENCH=1` 환경 변수를 추가했다. 일반 CTest에서는 6k/25k/50k만 실행해 전체 회귀 테스트 시간이 과도하게 늘어나지 않도록 했다.

## Benchmark
현재 개발 환경에서 측정한 값:

| N | Index build | Indexed query | Linear query | Speedup | Hits |
|---:|---:|---:|---:|---:|---:|
| 6,000 | 1.03 ms | 64.45 ms | 103.61 ms | 1.61x | 6,000 |
| 25,000 | 3.06 ms | 1,092.83 ms | — | — | 25,000 |
| 50,000 | 7.07 ms | 4,617.82 ms | — | — | 50,000 |
| 100,000 | 10.92 ms | 19,609.30 ms | — | — | 100,006 |

100k에서 `hits=100006`인 것은 무작위 64-bit hash 사이에 distance <=8인 우연한 근접 항목이 일부 존재하기 때문이다. 자기 자신만 반환하도록 제한한 benchmark가 아니다.

100k benchmark의 최대 RSS는 약 **17.9 MB**로 측정되었다.

0.9.2.25에서 사용하던 BK-tree의 6k indexed query는 동일 계열 환경에서 약 275 ms 수준이었으며, 0.9.2.26에서는 약 64 ms로 감소했다. 특히 기존 BK-tree는 25k 이상에서 검색 시간이 급격히 증가했기 때문에 대규모 인덱스 확장에 불리했다.

## 검증
- Core Release build: PASS
- CTest: **35/35 PASS**
- 6k / 25k / 50k benchmark: PASS
- 100k large benchmark: PASS
- 100k benchmark max RSS: 약 17.9 MB

## 영향 범위
이번 버전은 **CandidateIndex 후보 생성 구조만 최적화**하며, 최종 SimilarityEngine의 similarity threshold, mirror semantics, crop-aware semantics, video temporal second stage의 알고리즘과 결과 판정 규칙은 변경하지 않는다.

또한 Monitor의 사용자 작업 보호 정책은 그대로 유지한다. 이번 변경은 주로 인덱스 구축/검색 경로의 성능 개선이며, 실시간 Monitor가 사용자 작업 중 CPU/GPU 부하를 급격히 올리지 않도록 하는 Load Protection 정책을 완화하지 않는다.

## 검증 한계
현재 환경에는 Qt6 및 실제 NVIDIA CUDA 런타임이 없으므로 Windows GUI 및 물리 NVIDIA GPU 실행은 검증하지 않았다.
