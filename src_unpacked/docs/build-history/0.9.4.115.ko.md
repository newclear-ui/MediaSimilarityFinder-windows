# MediaSimilarityFinder v0.9.4.115 — 핫픽스 2: 불러오기/검색 시작 62097 크래시 루프 (이벤트 스레드 차단 + 잔존 킬 타이머)

기준선 `0.9.4.114` → 본 빌드 `0.9.4.115`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` 불변.

## 1. 변경 필요성

사용자 재보고: 0.9.4.114에서도 **동일한 백엔드 크래시 62097이 지속**. 사용자 로그(`%TEMP%\msf_scan.log`) 분석으로 코드 62097의 정체를 확정:
- Qt 6.11 `qprocess_win.cpp:32` — `KillProcessExitCode = 0xf291`(**62097**) — 이는 **자체 크래시가 아니라 슈퍼바이저가 `QProcess::kill()`로 종료한 코드**다. 즉 62097은 증상이 아니라 "우리 코드가 백엔드를 죽였다"는 증거였다.

로그가 보여준 실제 체인(0.9.4.114):
```text
01:01:09 backend hello_ack version=0.9.4.114
01:01:24 backend health quiet 1/3   (백엔드가 ~5초 만에 이벤트를 멈춤)
01:01:26 backend health timeout
01:01:26 backend watchdog: backend health timeout   (terminate + 3초 유예)
01:01:29 backend unexpected exit: ... (crash exit, code 62097)  (3초 후 kill)
→ 재시작 → 새 백엔드도 ~3초 후 동일 킬 → 무한 루프
```

## 2. 기존 구조와 결함 (원인 2건 + 잔존 1건)

- **D1 (방아쇠, 0.9.4.113 회귀)**: `BackendSession::loadIndex()`가 **IPC 이벤트 스레드에서 동기 실행**된다. .113부터 `loadMatches()`가 배지 전체 내용 확인(SHA-256)으로 후보 파일(사용자 인덱스 기준 ~5,296파일·약 1.5 GiB)을 읽게 되어, 불러오기 동안 이벤트 스레드가 **10초 이상 침묵** → 슈퍼바이저 health timeout(quiet 1/3→3/3) → `terminateAndRespawn` → `terminate()`(콘솔 앱에는 무효) → 3초 유예 후 `kill()`(62097).
- **D2 (증폭, 기존 잠복)**: `spawn()`이 **`escTimer_`를 중지하지 않는다**. `escStage_`만 0으로 리셋되어, 이전 라운드의 잔존 escalation 타이머가 발화하면 stage-0 분기로 **새로 뜬 백엔드를 ~killWait 후 킬**(사유 로그 없음) → 재시작 → 다시 킬 → **자기 유지 킬 루프**. 0.9.4.78 주석의 의도("a stale armed timer from a previous round must never kill this backend")를 코드가 실제로는 지키지 못했다.
- **잔존(배지 계약)**: Load 경로의 행 생성(`backend_session.cpp`)이 배지 플래그를 **quick-hash만으로 재계산**하고 있었다 — .113/.114의 전체 내용 계약이 Load 표시에 반영되지 않던 잔존 지점(엔진 `loadMatches`의 `contentIdentical` 무시).

## 3. 변경 구조

- **D1 — Load 비동기화**: `loadIndex()`가 `QThread` 워커에서 `runLoadIndex()`를 실행(신호는 queued — 스캔 응답과 동일 계약). `teardownWorker()`가 `stopLoad()`로 대기하므로 스캔 시작/종료와 안전하게 직렬화된다. 테스트 시임 `MSF_TEST_SLOW_LOAD_MS`(스폰 전 설정) 추가.
- **D2 — `spawn()`에서 `escTimer_.stop()`**: .78 주석의 의도를 코드로 강제. 새 백엔드는 어떤 잔존 타이머로도 죽지 않는다.
- **배지 잔존**: Load 행이 엔진 계산값(`m.contentIdentical`)을 그대로 사용(중복 재계산 제거).
- **회귀 테스트**(backend_e2e_test, checks 39→45):
  - **Test 1b (D1)**: 시임으로 load를 12초로 늘려(테스트 health window 5초) 이벤트 스레드 생존·재시작 없음·load 완료를 검증. **수정 전 FAIL 재현**(동기 load → health kill → load 미완료 + 재시작 발생).
  - **Test 3c (D2)**: silent 백엔드로 반복 escalation을 유도하고, **"모든 unexpected exit는 자신의 spawn 이후 기록된 사유 로그(timeout/watchdog/FAILED/refuses)를 반드시 동반한다"** 불변식을 검증. **수정 전 `exits=4 reasonless=3` FAIL → 수정 후 `reasonless=0` PASS**.
  - **테스트 보정**: `ui_scroll_regression_test` phase 11(불러오기 목록 표시)은 Load 응답이 비동기화된 것에 맞춰 유계 대기로 바꿨다(동기 가정 제거 — 수정 없이는 CTest에서 즉시 FAIL).

## 4. 해결된 상황

- 불러오기·검색 시작에서 나타나던 62097 킬 루프의 **두 원인(이벤트 스레드 차단 + 잔존 킬 타이머)이 모두 제거**되었다. 이벤트 스레드는 load/스캔 동안 계속 HEALTH를 보내며, 어떤 재시작 백엔드도 잔존 타이머로 죽지 않는다.
- Load 배지도 이제 전체 내용 계약을 따른다(Load와 스캔 표시 일치).
- 사용자 인덱스 DB는 무손상(SQLite 크래시 안전; kill은 쓰기 트랜잭션 중이 아니었음).

## 6. 향후 영향 및 한계

- 판정·저장·프로토콜·engine/DB/schema/cache 불변. 변경은 실행 구조(스레딩)와 슈퍼바이저 수명주기.
