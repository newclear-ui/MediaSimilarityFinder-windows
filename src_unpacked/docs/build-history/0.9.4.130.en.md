# MediaSimilarityFinder v0.9.4.130 — Match-set completeness baseline (A/AB self-heal)

Baseline `0.9.4.129` -> this build `0.9.4.130`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged (verdicts unchanged; CTest registration count unchanged).

## 1. Why the change was needed

- After upgrading to 0.9.4.129, the field log (`detailed-log-2026-10-19T053207.json`) shows an Auto (AB) scan with `scanned 177887, analyzed 0, unchanged 177887` and `candidates 0, pairs 0, groups 0` -- similar groups still 0.
- Causes: (1) the file index was already complete, so this scan re-analyzed nothing (analyzed 0); (2) A/AB never recompute unchanged files -- they display the **stored match set**; (3) that stored set is **empty**, because 0.9.4.81-0.9.4.128 never persisted live matches (the off-by-one bug), so this index's match store was never populated.
- The 0.9.4.129 fix only takes effect when files are (re)analyzed. On an all-unchanged index A/AB compute nothing, so they **cannot self-heal**. Running Stable (B) once does heal it (measured on 0.9.4.129), but upgrading users have no way to know that.
- The engine_version revalidation gate only re-checks stored pairs (a no-op on an empty set), and `revalidateMatches` stamps engine_version even for an empty set, so the existing stamp cannot prove completeness.

## 2. Previous structure

- A/AB final pass: verifies only pairs touching a changed file; unchanged-vs-unchanged pairs are trusted from the stored set.
- No persistent completeness marker: the DB could not remember "this index's stored set has completed a full-coverage verification under the current engine".

## 3. Changed structure

- New DB meta key `match_baseline` (`Database::matchBaseline()`/`setMatchBaseline()`), holding the engine version under which a **full-coverage verification** last completed for this index. It is separate from engine_version because that stamp is also written by `revalidateMatches` without a full pass and cannot prove completeness.
- At scan start, when this index has no baseline for the current engine, A/AB run this one scan as a **B-equivalent full pass**: `changedPtr=nullptr` (every pair verified), live streaming disabled (no duplicate work or stream entries), and live-owned accounting disabled. The backend log records `matchBaseline=forceFullPass engine=<v> stored=<missing|version>`.
- On completion (not cancelled/failed) the baseline is stamped with the current engine version. Cancelled or failed scans leave it untouched, so the next scan repeats the full pass. A failed stamp write is meta-only and never rolls back scan results (it simply repeats next time).
- When the engine version changes, the baseline invalidates automatically, so the next A/AB scan re-establishes it with one full pass (re-discovery under the new logic -- safer than revalidation-only).
- No file re-analysis is needed: candidates come from the existing index fingerprints (zero re-fingerprinting).
- Side fix (build): `tests/console_benchmark_cli_test.cpp` used `msf::path_from_utf8` without including `path_utils.h` directly, so the target had **not compiled** since its 0.9.4.126 commit -- it was hidden behind filtered build logs in later sessions (both trees' exes were stale binaries from the 2026-10-18 03:xx builds, and CTest kept passing on the stale exe: 32 checks in the stale binary vs 44 checks in the real one). Adding the direct include fixes it; a sweep confirmed no other test has the same omission. From this build the real 44 checks run.

## 4. What was resolved

- Exact field state reproduced (stored pairs deleted + baseline absent + all files unchanged + AB): before this fix the scan shows `pairs 0`; after it, the first scan automatically runs the full pass and displays `pairs=8, groups=8, candidates=8` (18-file real set), and the next scan returns to quick-load (`verifyCalls=0`). No manual Stable (B) scan is required.
- Combined with the 0.9.4.129 match-loss fix, upgrading users recover automatically on their **first Auto (AB) scan**.

## 6. Impact and limitations

- Verdicts, storage, protocol, engine/DB/schema/cache and the journal schema are unchanged. No new DB tables (one meta key). CTest registration count unchanged (125/126).
- For A/AB users, the **first scan** after the upgrade (or after a future engine-version bump) runs as a full verification and takes longer than usual (no file re-analysis; minutes on large datasets). Every later scan returns to the usual speed.
- Known remaining gap (out of scope here): on a fully-unchanged rescan, the left summary/detailed-log group and pair counters only count what that scan recomputed, so the numbers differ from the quick-loaded results (the group list itself displays correctly). Counter unification is a separate candidate.
