# MediaSimilarityFinder v0.9.4.110 — Wheel-speed restore after view-mode switches (List latch fix)

Baseline `0.9.4.109` -> this build `0.9.4.110`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged.

## 1. Why it was needed

User report: after visiting List/Details/Tiles and returning to any icon mode (XL/L/M/S), **mouse-wheel scrolling becomes extremely slow** — "it never returns to the icon-view wheel speed after the list view". Once List has been visited it persists in every icon mode until the app is restarted.

## 2. Previous structure (Qt item-view scroll-step mechanism)

- One wheel notch scrolls `singleStep() x wheelScrollLines(3)`. The app never sets scroll modes or singleStep, so the Qt default behavior applies as-is.
- Qt 6.11 item views **manage the scrollbar step automatically**: while `QAbstractItemViewPrivate`'s `viewMayChangeSingleStep` (initially true) is set, the view pushes the mode-appropriate step through `itemviewChangeSingleStep(...)`.
  - **Icon modes** (`QCommonListViewBase::updateVerticalScrollBar`): `itemviewChangeSingleStep(cell height + spacing)` — one notch = one cell.
  - **List mode** (`QListModeViewBase::updateVerticalScrollBar`, ScrollPerItem, TopToBottom, non-wrapping): **public** `verticalScrollBar()->setSingleStep(1)` — item-unit scrolling.
- **The defect**: `QAbstractSlider::setSingleStep(step)` **latches** `viewMayChangeSingleStep = (step < 0)`. After List mode's `setSingleStep(1)`, every automatic step update from the icon modes is ignored and the scrollbar step stays 1. Only `setSingleStep(-1)` re-enables the automatic management.
- Measured (regression test, pre-fix): XL icon-mode step = **175** (256px icon cell); after visiting List and returning to XL the step stayed **1** — one notch = 3px. This matches the user report exactly.

## 3. New structure

- **`groupViewChanged()`** (gui/mainwindow.cpp): right after the delegate/size swap and before the existing `doItemsLayout()`, call `setSingleStep(-1)` on both grid scrollbars.
  - `-1` re-enables automatic step management and immediately re-applies the value the view last pushed (`singleStepFromItemView`).
  - The following `doItemsLayout()` -> `updateGeometries()` re-pushes the step for **the mode just selected** (icon modes = cell size, List mode = item unit 1 — List behavior itself is unchanged).
- **Test**: `ui_scroll_regression_test` phase 22 — an XL->List->XL round trip must restore `verticalScrollBar()->singleStep()` to the icon-mode value. Pre-fix `xl=175 list=1 back=1` **FAIL** reproduced; post-fix `back=175` PASS (checks=88).

## 4. What is fixed

- After visiting List/Details/Tiles, any icon mode gets its one-cell-per-notch wheel back immediately, and it stays correct across every switch (the `-1` is re-applied on each switch) without an app restart.
- List mode's own wheel (3 items per notch) and the tree (Details) mode are unchanged. Scroll position, selection, the catch-up contract (0.9.4.61), and the icon re-apply fix (0.9.4.109) are unchanged.

## 6. Future impact and limits

- Display-only: verdicts, storage, protocol, engine/DB/schema/cache unchanged. No added decode or layout cost (two step resets plus the existing layout pass).
- Any new app path that sets a scrollbar step directly could re-latch the bar — the mode-switch `-1` re-apply would still revive the automatic step afterwards.
- If a Qt upgrade changes the `setSingleStep` latch semantics (`viewMayChangeSingleStep`), phase 22 detects the regression.
