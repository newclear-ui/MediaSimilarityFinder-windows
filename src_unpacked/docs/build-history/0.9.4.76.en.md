# MediaSimilarityFinder v0.9.4.76 — Crash-frontier durability (batch-entry checkpoint)

Baseline `0.9.4.75` → this build `0.9.4.76`.
CPU CTest **118/118**, GPU CTest **119/119**.
`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.4` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — all unchanged. No search-verdict change. No schema change.

## 1. Why the change was needed

- Two measured Backend crashes (`0xC0000005`) both died with zero completed
  files. The heartbeat `lastPath` stayed empty to the end, and a copied-DB
  probe showed zero `fingerprint=0` rows. The poison batch left no position
  in the DB.
- Cause: admission skeleton rows lived only inside the scan transaction.
  Existing checkpoints fire every 500 analyzed / 1000 scanned files, so death
  before finishing the first batch rolled the whole frontier back.
- Per the user request ("create dummy rows at scan time, fill them when
  indexing finishes"), the design had to be completed down to the transaction
  boundary.

## 2. Previous structure

- `processOne()` upserted fingerprint-0 skeleton rows at admission
  (`src/media_search_engine.cpp:669-677`).
- The next scan's `pendingAnalysis` rule (fingerprint 0 + not failed →
  re-analyze) already existed (`:658`) but could not reach uncommitted
  skeletons.
- `processImageBatch` / `processVideoRange` entered heavy parallel
  decode/hash work without committing anything first.

## 3. Changed structure

- `processImageBatch` now runs `checkpoint()` at entry. Admission skeletons
  commit before batch work, so a mid-batch kill/AV leaves the
  admitted-but-unanalyzed frontier committed.
- `processVideoRange` has the same entry checkpoint (failure returns
  `VideoRangeResult::Failed`).
- Added test-only `MSF_TEST_THROW_BATCH`, thrown AFTER the entry checkpoint
  to deterministically prove skeleton durability across unwind. Production
  never sets it (same pattern as `MSF_TEST_THROW_WALKER`).
- Verdict/matching/scan semantics are untouched. The checkpoint is the same
  commit+BEGIN already used, added once per batch — not frequent fsyncing.

## 4. Resolved state

- Death mid-batch now leaves the admission frontier (fingerprint 0, not
  failed) committed.
- The next scan re-analyzes those files via `pendingAnalysis` (never skips).
- The DB keeps original full paths (`files.path` PRIMARY KEY, match
  left/right paths, thumbnail paths). Dummy rows use the same path key, so
  completion fills the same row.

## 6. Future impact

- The next `0xC0000005`-class crash will leave fingerprint-0 frontier rows,
  narrowing poison-batch candidates to a concrete path list.
- Combined with the LocalDumps + PDB procedure, root-cause confirmation gets
  faster.
- No schema/engine/DB version touched, so existing indexes stay compatible.
