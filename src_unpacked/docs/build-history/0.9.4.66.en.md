# MediaSimilarityFinder v0.9.4.66 — Image overlap after view-mode switching fixed

Baseline `0.9.4.65` -> this build `0.9.4.66`.
CPU CTest **111/111**, GPU CTest **112/112** (view_mode_probe heavily extended).
`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.4` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — all unchanged.
Engine, DB, schema, cache, scheduler, and GPU backend untouched. No Test Mode.

## 1. Why the change

- Regression found during 0.9.4.63 manual acceptance (the 0.9.4.63 record
  is not edited retroactively): switching the middle similar-group list to
  another view mode and back to Extra Large (256 icons) leaves photos
  overlapped. First paint is fine; List, Grid, scrolling, scrollbar,
  Home/End all behave.
- Tracked separately from the 0.9.4.61 scroll regression.

## 2. Previous structure

- `groupViewChanged(int)`: changes viewMode, iconSize, gridSize, and the
  delegate in a row while keeping the same QListWidget items. The switch
  itself schedules layout.
- `thumbCatchUpVisible()`: per tick, regenerates visible items' thumbs at
  the current iconSize and swaps them in place. Never touching layout,
  scroll, or rebuilds is the 0.9.4.61 contract.
- Thumb cache keys are `path|WxH`, so after a mode switch catch-up delivers
  new-size thumbs.

## 3. New structure (evidence: probe measurements)

Reproduction chain (pinned by the probe's `catchup` mode, confirmed FAIL
before the fix):

1. Right after a List -> 256 switch, layout sizes cells for the previous
   (small) thumbs (probed: 254x71 cells).
2. Catch-up swaps in 256px thumbs via `setIcon()`.
3. Under `setUniformItemSizes(true)` + `Batched`, the icon swap runs no
   layout pass (still frozen after 60 event pumps; only a forced
   `doItemsLayout()` recomputes to 282x295).
4. Large art paints outside small cells and looks overlapped. The rects
   themselves never intersect, so a plain `intersects()` check misses it.

Minimal fix applied (2 spots in `gui/mainwindow.cpp` plus 1 test hook):

- `thumbCatchUpVisible()`: one `grid->doItemsLayout()` at the end, only
  when an icon actually changed. Loop, budget, in-place semantics, and
  scroll untouched. (`scheduleDelayedItemsLayout()` would be the deferred
  equivalent but is protected, so the public synchronous version is used.
  It runs only on real change, does index math only — no widget churn.)
- End of the `groupViewChanged()` grid branch: one `grid->doItemsLayout()`
  after the delegate/size swaps. No item recreation, no scroll contact.
- New public `testThumbCatchUp()` hook (same pattern as `testUiTick`).
  Never called by production; lets the probe deliver thumbnails through
  the real catch-up path instead of bypassing it.

Not done (per directive section 8): no `refreshGroupList()`/`fillPair()`
calls on mode change, scroll anchor/gate/catch-up structure/thumbnail
cache/engine/Test Mode untouched, no `processEvents()` in production code.

## 4. Resolved state

- Cells recompute when post-switch thumbs arrive, so nothing overlaps.
- The 0.9.4.61 contract enforced by the scroll regression test
  (catch-up ticks never rebuild) still passes.

- New: real MainWindow plus a 41-group fixture, driven through the viewBox.
