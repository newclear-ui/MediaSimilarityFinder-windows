# MediaSimilarityFinder v0.9.2.34 — Windows Common Compatibility Alignment

## Purpose
Preserve the official v0.9.2.32 baseline while applying CPU/CUDA-common Windows compatibility fixes discovered during CPU testing. The CUDA backend algorithms, memory path, and kernels are unchanged.

## Changes
- vcpkg `unofficial-sqlite3` CMake target handling
- Windows WIC/Qt and `NOMINMAX` handling
- `M_PI` replaced with C++20 `std::numbers::pi`
- FFmpeg 9 `av_find_best_stream()` argument compatibility
- Correct `SystemLoadMonitor` state-member placement
- UTF-8 filesystem conversion utility and major boundary integration
- `ReadDirectoryChangesW` overflow/resync and buffer bounds checks
- StableFileDetector state cleanup after successful stabilization
- MSVC test `__builtin_popcountll` replaced with `std::popcount`
- Explicit `msf::` qualification to avoid the Windows SDK `SystemLoad` collision
- Visual Studio 18 2026 CUDA build script and project-local vcpkg use

## Previous structure
Several shared paths depended on platform/compiler-specific behavior: standard CMake package naming, math constants, Windows macros, filesystem string conversion, FFmpeg API details, and GNU-only test intrinsics.

## New structure
Windows compatibility is handled at shared Core/Monitor/Scanner/Index/Decoder boundaries, and tests use standard C++20 APIs. The CUDA layer retains its existing structure.

## Rationale
CPU and CUDA builds share the same Core. Maintaining one common platform-fix baseline avoids duplicated fixes and branch-specific behavior differences.

## Validation
With CUDA OFF / GUI OFF / FFmpeg OFF on Linux, the full source compiled and all 36 test binaries were generated. Windows MSVC/Qt/CUDA execution validation will be performed in the user's Windows environment.

## Version/baseline
- Official preserved baseline: v0.9.2.32
- Windows CPU test: v0.9.2.33-test
- Shared Windows/CUDA validation line: v0.9.2.34


## Follow-up Correction — Windows Build Baseline Alignment

During the final review of the v0.9.2.34 source-ready package, the Windows build configuration was further aligned with the actual validation environment, Visual Studio 18 2026.

### Need for change
- `CMakePresets.json` still specified Visual Studio 17 2022 for both `windows-cpu` and `windows-cuda`.
- `scripts/build_windows_cpu.ps1` also used Visual Studio 17 2022.
- The CPU script did not explicitly install the GUI dependency `qtbase` and did not use the project-local `vcpkg_installed` tree.

### Old structure
- Windows CPU/CUDA Preset Generator: Visual Studio 17 2022
- CPU PowerShell: Visual Studio 17 2022 + external/classic installation path
- CPU dependency installation: `sqlite3`, `ffmpeg`
- CUDA PowerShell: Visual Studio 18 2026 + project-local `vcpkg_installed`

### New structure
- All Windows Presets: Visual Studio 18 2026
- CPU PowerShell: Visual Studio 18 2026
- Common CPU/CUDA dependency source: `vcpkg.json` with `sqlite3`, `ffmpeg`, `qtbase`
- Both CPU/CUDA use `<projectRoot>\vcpkg_installed\x64-windows`
- CPU script explicitly sets `VCPKG_INSTALLED_DIR`, `VCPKG_TARGET_TRIPLET`, `unofficial-sqlite3_DIR`, `Qt6_DIR`, and `MSF_FFMPEG_ROOT`

### Reason
The user's actual Windows validation environment is Visual Studio 18 2026. CPU and CUDA share the same Core/GUI/FFmpeg/SQLite dependencies, so the Generator and dependency installation location should be identical to make validation results reproducible and comparable.

### Resolved situation
The Generator mismatch and vcpkg path divergence between Windows CPU and CUDA builds were removed. `qtbase`, required for the CPU GUI build, is now part of the common manifest dependency set.

### Accuracy/compatibility impact
This removes the possibility of selecting the wrong VS 17 2022 Generator when configuring on the actual VS 18 2026 environment. Using the same project-local dependency tree for CPU and CUDA also reduces validation drift caused by different Qt6/SQLite/FFmpeg dependency versions. No CUDA algorithm or kernel implementation was changed.

### Validation
Static source review confirmed the Generator and vcpkg settings in both Presets and both Windows build scripts. Actual Windows Configure/Build/CTest validation will be performed in the next step.

### Future impact
All subsequent Windows CPU/CUDA builds use Visual Studio 18 2026 and project-local `vcpkg_installed` as the common baseline. The project-local vcpkg tree remains in place until the full Windows build/validation cycle is complete.
