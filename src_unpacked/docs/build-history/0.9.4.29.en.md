# MediaSimilarityFinder v0.9.4.29 — D3 Duplicate `decode` / `decodePreserveAspect` Cost Measurement

Status: **PRE-REGISTERED** (committed before any D3 instrumentation code)

D3 is a **measurement** build. It optimizes nothing.

---

## 1. Base Point

```text
base version : v0.9.4.28
base commit  : 256c41a
D2 status    : PASS
Path C       : DEFERRED (not adopted into the product)
```

D2's `CreateDecoderFromStream` + `HandleStream` path is **not adopted into the
product path**. D3 neither changes nor re-evaluates that conclusion.

## 2. Change Need

D9c measured decode as **94.90 %** of `expensive verify`. But that 94.90 % is
the **sum of two different decode calls**. The two have never been separated.

D2 narrowed the cost structure of the decoder **entry path**, and the outcome
was "the gain is too small to adopt". That judgement itself stays untouched.
D2 did settle two things:

```text
1. Decoder creation itself is on the order of tens to hundreds of microseconds
   per call, which alone does not dominate verify.
2. The remaining large question is therefore "how many times is decode called".
   Call count is cost.
```

The current structure decodes the **same file twice per verify miss**. What the
second call actually costs has never been measured by anyone.

## 3. Central Question

> What is the real wall-clock cost that `decodePreserveAspect()` incurs by
> decoding the same file again, and what percentage of `expensive verify` /
> `verify` / total scan time is that?

**No optimization is adopted before this question is answered.**

## 4. Boundary of the D2 Result — Not a D3 Baseline

```text
D1  CreateDecoderFromFilename ≈ 2.6257 ms/call  (cold, includes first codec DLL load)
D2  decoder call ≈ 0.07~0.12 ms                 (warm, per-format warm-up excluded)
D3  separated cost of decode / decodePreserveAspect
```

D1 and D2 were measured under different conditions (cold / warm), so they are
**not directly comparable**, and the gap is not a performance improvement. D3
likewise is not automatically compared against D2 or D1, and no difference is
expressed as an improvement. **Only when measurement conditions are clearly
identical are they compared directly.**

## 5. Pre-Investigation of the Code — Facts Established Before Instrumenting

The instrumentation plan below comes from the actual code. These are not
guesses.

### 5.1 The two calls accumulate into the same telemetry (the exact D3 gap)

`src/image_verify.cpp:78`

```cpp
if(!dec.decode(path, kDim, kDim, f, tel? &tel->decode : nullptr)
   || !dec.decodePreserveAspect(path, kDim, a, tel? &tel->decode : nullptr)) { ... }
```

**Both calls are handed the same `&tel->decode`.** Every timer and counter inside
`AnalyzeTelemetry::decode` (the single `DecodeTelemetry` D9d created) is therefore
the **sum** of the two calls.

```text
DecodeTelemetry::calls       → decode() + decodePreserveAspect() combined
DecodeTelemetry::aspectCalls → accumulated into that same bucket
DecodeTelemetry::totalMs     → sum of both calls
DecodeTelemetry::openMs      → sum of both calls
DecodeTelemetry::copyMs      → sum of both calls
```

In other words, **the counters that already exist cannot tell the two calls
apart.** D3 is not inventing a new concept; it is **splitting an accumulator
that already exists, per call**.

### 5.2 The call counter already increments by 2

`src/image_verify.cpp:79`

```cpp
if(tel){ tel->verifyDecodes += 2; }
```

So `verifyDecodes == 2 × verifyDecodeMisses` **already holds structurally**.
D3 does not change that meaning.

### 5.3 There are three decode call sites, and only one passes telemetry

| Call site | Call | Telemetry passed | D3 target |
|---|---|---|---|
| `image_verify.cpp:78` | `decode()` 32×32 + `decodePreserveAspect()` 32×32 | `&tel->decode` (shared) | **yes** |
| `media_pipeline.cpp:45` | `decode()` 32×32 (fingerprint) | **none** | no |
| `media_pipeline.cpp:110` | `decodePreserveAspect()` 128 (crop fingerprint) | **none** | no |

This is the factor that **will break the §9 count consistency prediction**.
`decodePreserveAspect` is also called outside the verify-miss path, so a
**global** count is **not** equal to `verifyDecodeMisses`. D3 records this in
advance rather than hiding it.

## 7. Measurement Targets

Minimum telemetry:

```text
decodeCount                  decode() invocations
decodeTotalMs                decode() wall-clock total

decodePreserveAspectCount    decodePreserveAspect() invocations
decodePreserveAspectTotalMs  decodePreserveAspect() wall-clock total
```

Where possible, the existing sub-stages are attributed to each call.

```text
open / factory / metadata / orient / resize / convert / copy / pgmFallback
```

**No new telemetry system is created.** The fields and meanings of the existing
`DecodeTelemetry` are reused first; the premise is to **split** the shared
accumulator of §5.1 per call. The real fields used as denominators:

```text
verifyMs                 AnalyzeTelemetry::verifyMs  (all of verify)
verifyDecodeMs           the D9c miss-only decode bucket
verifyKeyMs / verifyCacheStoreMs / verifyCacheCopyMs
verifyCropMs / verifyFlipMs / verifyFrameSsimMs / verifyOtherMs
analyzeMs                BenchmarkRecorder::analyzeMs_  (scan-level total)
```

## 8. Values That Must Be Produced

Per measured run, at minimum:

```text
decodeCount                       decodeTotalMs
decodePreserveAspectCount         decodePreserveAspectTotalMs
verifyMs                          verifyDecodeMs
analyzeMs                         groups
```

And these ratios are computed. The key metric is not a bare `ms/call` but **the
share of real production cost taken by the second decode**.

```text
decodePreserveAspectTotalMs / decodeTotalMs
decodePreserveAspectTotalMs / verifyDecodeMs
decodePreserveAspectTotalMs / verifyMs
decodePreserveAspectTotalMs / analyzeMs
(decodeTotalMs + decodePreserveAspectTotalMs) / verifyDecodeMs
(decodeTotalMs + decodePreserveAspectTotalMs) / verifyMs
```

`verifyDecodeMs` is used as the "expensive verify" denominator for the same
reason D9c did. D9c confirmed that the sum of the D9c stages equals `verifyMs`
exactly and normalized that sum per call to report "per expensive verify". D3
uses **the same denominator**.

## 9. Count Consistency — Predicted Values and an Expected Deviation

```text
Prediction (verify-miss path only)         Basis
decodeCount                  == verifyDecodeMisses   §5.3, one decode per miss
decodePreserveAspectCount    == verifyDecodeMisses   §5.3, one per miss
verifyDecodes                == 2 × verifyDecodeMisses  §5.2 already holds
```

**This is not treated as an established fact in advance.** If the measurement
differs, record:

```text
expected count
actual count
delta
reason
```

**Predicted deviation #1 (a structural reason already known)**

Counting globally, `decodePreserveAspectCount > verifyDecodeMisses` will hold,
because `media_pipeline.cpp:110` (§5.3) calls `decodePreserveAspect` outside
the verify path for crop fingerprints and passes no telemetry.

D3's response: report the two counts **separately**.

```text
verify-path decodePreserveAspectCount   (D3's primary metric)
calls outside the verify path           reported as N/A, never estimated
```

**The call path is not modified to make counts line up.** Changing code to
reconcile counts is not D3.

## 10. Timing Conditions

D3 measures the **real production decode path**. Within one run the same dataset
and the same file set are used.

```text
warm-up run   : 1, excluded from results
measured runs : minimum 5
```

Per measured run, record `mean / median / min / max / range`.

First-call DLL/codec initialization and similar **cold-start cost is not
interpreted as duplicate-decode cost.** If cold-start occurs it is recorded
separately and never mixed with the warm measurement. (D2 already showed the
cold/warm difference is large enough to invert the numbers.)

## 11. Production Behavior Preservation

D3 must not change:

```text
verifyCalls            verifyDecodeMisses       verifyCacheHits
verifyDecodes          ssimEvals                frameSsimEvals
groups                 final verdict            CPU/GPU parity
```

For identical input, the decode result, image dimensions and pixel output must
not differ from the existing baseline. If instrumentation changes scan results
or grouping/verdict, **the measurement is stopped and the cause recorded.**

## 12. Telemetry Correctness

The D1 cumulative double-counting bug must not recur.

### 12.1 The existing identity must hold (D9c)

```text
verifyKeyMs + verifyDecodeMs + verifyCacheStoreMs + verifyCacheCopyMs
  + verifyCropMs + verifyFlipMs + verifyFrameSsimMs + verifyOtherMs
    == verifyMs
```

### 12.2 The identity D3 adds

```text
decodeTotalMs + decodePreserveAspectTotalMs == the decode portion of verifyDecodeMs
```

If this identity breaks, **the timing results are not used**, because it means a
timer is mis-scoped. The default response to a break is not to quietly drop
instrumentation but to **record the cause and report `INCONCLUSIVE`**.

### 12.3 Value handling

```text
N/A / Not measured / unknown
```

are never replaced with invented numbers. State values (`measured` /
`not_measured` / `not_available`) are preserved alongside the JSON.
Instrumentation overhead is also **not** described as "negligible" while it has
not been measured.

## 13. Instrumentation Scope

**Allowed**

```text
counter additions           elapsed-time measurement
extending existing telemetry additive benchmark output fields
schema validation           telemetry analysis
measurement-only tests
```

**Forbidden**

```text
decode deduplication        decode result cache
decode cache restructuring  removing decodePreserveAspect
merging the two decode calls factory reuse
decoder reuse               stream reuse
HandleStream in production  CreateDecoderFromStream in production
threading changes           parallelism changes
algorithm changes           threshold changes
grouping changes            verdict changes
```

D3's code changes are **limited to instrumentation that makes the measurement
possible**.

## 14. Judgements Not Made Before Measuring

The following judgements are not made before seeing the results.

```text
"It decodes twice, so remove the second call."
"It's the same file, so cache it."
"Reuse the decode result."
"Reusing the decoder will be faster."
```

Even if D3 shows a large cost, that optimization is **not included in D3**. A
**separate optimization pre-register** is written after the results are in.

## 15. Per-Format Analysis

Where possible, per-format results are recorded.

```text
BMP / JPEG / PNG / WEBP / GIF / TIFF / ICO
```

But a per-format difference does **not** immediately trigger a per-codec
optimization. D3's first purpose is to quantify the structure of the total
duplication cost.

## 16. Core Calculations — Must Be Recorded

```text
A. Cost of the second decode itself
   decodePreserveAspectTotalMs / decodePreserveAspectCount

B. Second decode relative to the first
   decodePreserveAspectTotalMs / decodeTotalMs

C. Share of expensive verify
   decodePreserveAspectTotalMs / verifyDecodeMs

D. Share of all verify
   decodePreserveAspectTotalMs / verifyMs

E. Share of total scan
   decodePreserveAspectTotalMs / analyzeMs

F. Both decodes combined
   (decodeTotalMs + decodePreserveAspectTotalMs) / verifyDecodeMs
```

**Simple extrapolation is not recorded as a real production speedup.**

## 17. Success Conditions — Not "It Got Faster"

D3 is `PASS` only if all of the following hold.

```text
1. decode / decodePreserveAspect call counts are measured
2. The wall-clock cost of both paths is measured
3. Ratios against verifyDecodeMs / verifyMs / analyzeMs are computed
4. At least 5 repeated measurement runs complete
5. mean / median / min / max / range are recorded
6. The §12.1 and §12.2 stage identities hold
7. Existing scan results and parity are preserved
8. All existing tests still pass
9. No measured value was replaced by an estimate
```

## 18. INCONCLUSIVE Conditions

In the cases below, no conclusion is forced. The result is recorded as
`INCONCLUSIVE` together with the failure cause and revisit conditions.

```text
1. The two decode call costs cannot be separated
2. Stage totals do not reconstruct because of instrumentation
3. Run-to-run variation is too large to interpret the measurement
4. The relation between call count and verifyDecodeMisses is unexplained
5. Production results changed because of instrumentation
6. A required denominator was not actually measured
```

## 24. Expected Outcome (Judged After Recording)

Success is a measured cost structure, not a speedup.

```text

2. The share the second decode takes of verify / scan is quantified
3. The call-count relations are confirmed against actual values (§9)
4. Both the D9c identity and the new D3 identity hold
5. Verdict, grouping and parity are preserved
```

The final state is `PASS` or `INCONCLUSIVE`, judged on whether the cost
