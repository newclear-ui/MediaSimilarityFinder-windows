# MediaSimilarityFinder v0.9.4.121 — Detail-pane widening fixed (similarity-label wrap + value-row discipline + file-thumb retry)

Baseline `0.9.4.120` -> this build `0.9.4.121`.
CPU CTest **124/124**, GPU CTest **125/125** (including the new `detail_layout_probe`).
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged.

## 1. Why it was needed

Field report (0.9.4.120, group 280), three symptoms:

1. Selecting the highlighted file widens the detail pane regardless of text length, and the vertical splitter cannot shrink the right side back.
2. The group file list + detail info encroach the middle group list more than necessary. Agreement: unless the user widens it manually, the middle stays ~3 images wide.
3. Load shows every thumbnail, but after a scan start only the representative thumbnail survives and the group's other thumbnails disappear.

## 2. Previous structure and defects

Measured and reproduced with the new `detail_layout_probe` (pre-fix FAIL):

1. **The similarity tab `simLabel_` shows the full best-match path with no `wordWrap`** - the tab minimum became the path's pixel width (measured **2034px** for a 180-char path) -> `detailTabs` (2038) -> right pane (2038) forced, splitter locked (a narrow ask of 60 stayed 2038). Decisive trap: a separator-less path is a single "word", so **wrapping alone does not shrink the minimum** (still 1812 after wrap-only).
2. **The seven detail-form value rows** (size/format/modified/created/resolution/duration/similarity) demanded minimum width with no wrap, unlike the name/path rows and the stated design intent (never stretch the pane, 1115-1117).
3. **File-list thumbnails relied on the single request fired at row creation.** The middle list re-asks every tick through the catch-up pump, but the file list and preview had no retry path, so a lost answer (busy backend at scan start, restart-cleared pending map, cap refusal) stayed a permanent placeholder. The representative survives because it is also re-asked through the middle rows - hence "only the representative remains". Note the .105 comment assumed "the next visible tick retries it", but that tick only served the middle list.

## 3. New structure

- `simLabel_`: `wordWrap` + top-left align + horizontal **`Ignored`**. The displayed text gets zero-width spaces after separators for matching visual folds (stored path and tooltip keep the exact text).
- The seven value rows: unified through a `wrapVal` lambda (wrap + `Ignored`). Short values render exactly as before; long ones can no longer widen the pane.
- `thumbCatchUpVisible` extended: re-ask the file grid's visible window (+/-4 rows) + apply cache hits (same discipline as the middle) + re-ask the selected preview (220x190). In-flight duplicates are skipped, no rebuild, no scroll touch. The file grid uses the same direct `doItemsLayout` as `onThumbReady`.
- Regression probe `detail_layout_probe` (CTest-registered, **125** total): A1 wrap flag, A2 tab minimum <= 640, A3 right-pane minimum <= 700 (fixed header/toolbar/tab content only), C rebuild guard + request delta >= 4 (unreachable with the 3 middle rows alone). All three FAILs reproduced pre-fix, 5/5 PASS post-fix.

## 4. What is fixed

- tabPage2 2034 -> **129**, detailTabs 2038 -> **344**, right-pane minimum 2038 -> **592** (fixed content only). The splitter moves again, and since the right side demands nothing beyond its fixed content, the middle list regains its width.
- The file list and preview re-ask lost answers on the next tick (request delta 3 -> 6).
- The hidden `fileList` tree was measured to not contribute to the minimum (`viewStack` 70) - left untouched.
- JSON, verdicts, engine unchanged (display only).
