# MediaSimilarityFinder v0.9.4.59 — Video Cancelled/Failed split

Baseline `0.9.4.58` -> this build `0.9.4.59`.
CPU CTest **107/107**, GPU CTest **108/108** (previous 106/107 plus one new test).
`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.4` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — all unchanged. Product VERSION bump only.

## 1. Why the change was needed

0.9.4.58 fixed the image drain, but video kept a remaining bug.
`processVideoRange()` expressed Success/Cancelled/Failed with a single `bool`,
so a user Stop became `failed=true` and rolled back the whole transaction: a
fault-free Stop promoted to Failed. Completed futures were discarded too.

## 2. Previous structure

- Post-`stopSeen` completed futures discarded via `continue` in harvest
- `stopSeen` returned `false`; callers set `failed=true` -> `rollbackTransaction`
- Cancelled scans never earned the generation stamp (`r.completed` false), so
  the next scan re-analyzed every video (`videoRegrid`)

## 3. New structure

- `VideoRangeResult { Success, Cancelled, Failed }` (file scope, header/API
  untouched, no version bump needed)
- Harvest persists post-stop completions normally. Only DB errors are Failed
- `stopSeen` returns Cancelled. Callers map it to `cancelled=true` and advance
  `videoBase` (the range was fully joined and consumed)
- The generation stamp is written on cancel conditionally: only when every
  pre-existing video row was admitted (`seen`) this scan. Unreached legacy rows
  keep the next scan on regrid instead of being blessed

## 4. Resolved situation

- Stop is not Failed. No rollback, `telemetry failed:false`
- Videos complete at the stop stay in the DB and rescan reuses them unchanged
- Genuine decode failures keep failure semantics (analysisFailed recorded and
  counted, settled, scan completes)
- Conditional stamping reconciles post-cancel video reuse with legacy-row safety

## 5. Verification

### New `scan_cancel_video_test` (26 checks, PASS on CPU and GPU)

- A (cancel): 6 real ffmpeg clips, Stop from the synchronous progress hook.
  completed=false, failed==0, at least one persists, telemetry
  cancelled:true/failed:false. Post-reopen rescan reuses exactly the persisted
  ones unchanged and processes only the rest fresh
- B (failure): 2 corrupt + 2 valid clips. completed=true, failed==2,
  analyzed==2. Rescan: analyzed==0, unchanged==4 (settled)
- C (stamp condition): simulated legacy unstamped DB, then cancel after 2 of
  8 admissions -> no stamp confirmed -> rescan re-analyzes everything

### Existing drain test strengthened

`scan_cancel_drain_test` moved from lower bounds (`>=3`) to exact counts.
First scan analyzed==3/scanned==3; rescan unchanged==3/analyzed==7. It now
verifies the first scan's work was actually reused, not merely present.
