## 1. Why the Change Was Needed

E-1 measured a 89.81x waste but estimated the sparse-seek gain **arithmetically
only**, and recorded itself that this was not a measurement. E-2A's job is to
measure it, and it does not replace the production sampling policy.

## 2. Correcting an E-1 Record

E-1 marked HEVC/AV1/VP9 as `NOT_AVAILABLE_IN_CURRENT_ENVIRONMENT`. **That was a
statement about generation.** Real encoded HEVC and AV1 content exists on this
machine.

```text
original  : HEVC/AV1/VP9 = NOT_AVAILABLE_IN_CURRENT_ENVIRONMENT
cause     : the bundled FFmpeg 9.0.1 has no software ENCODER for them
            (only h264_mf actually works)
correction: generation is impossible, but real encoded content exists.
            E-2A uses it.
```

A **newly discovered, separate** constraint exists — a **decoding** constraint
rather than a generation one:

```text
AV1 = NOT DECODABLE IN THIS BUILD
  "Your platform doesn't support hardware accelerated AV1 decoding"
  "Error submitting packet to decoder: Function not implemented"
```

`-decoders` lists `av1` but the native implementation does not work. E-1 could
not have known this.

## 6. Exactness — the result that blocks production integration

Per directive §16·17 the **sample frames themselves** are compared, not the
fingerprint.

```text
sample_count_parity = 14 / 14   PASS
sample_pixel_parity =  4 / 14   FAIL
```

```text
file                                tsSame tsLater diffBytes   maxAbs frameBytes
real_h264_0648x1080_030s.mp4              2      14      7518       80     1024
real_h264_1360x0808_030s.mp4              1       8      7853      188     1024
real_h264_1920x1080_030s.mp4             12       3      2159       56     1024
real_h264_1920x1080_300s.mp4              2      33     11521       70     1024
real_hevc_1920x1080_030s.mp4             14       2      1364       31     1024
synth_ffv1_intra.mkv                      2      14      2357      157     1024
synth_mpeg4_gop15.mp4                    12       4      1056      151     1024
synth_mpeg4_gop250.mp4                   14       2       381      157     1024
synth_mpeg4_gop5.mp4                      2      14      5108      155     1024
synth_mpeg4_gop60.mp4                    14       2       343      151     1024
```

**maxAbs differences of 31 to 188 out of 255.** These are not rounding noise;
they are **different frames**.

### 6.1 Cause

Both strategies use the product's own predicate
(`frame_t + 0.05 >= target`, `video_decoder.cpp:127`). But that predicate
**permits a frame slightly earlier than the target**. 0.05 s is 1.5 frame
periods at 30 fps, so a sequential sweep may pick a frame one step early:

```text
target = 2.0 s, 30 fps
frames ... 1.9667 s, 2.0 s, 2.0333 s ...
1.9667 + 0.05 = 2.0167 >= 2.0   ->  TRUE
```

The sequential sweep picks 1.9667 s. Sparse seek lands on the keyframe at or
before the target, so it cannot reach 1.9667 s, and picks the first frame after
its landing point that satisfies the predicate. `tsLater` is the evidence.

**This is a structural difference of the strategies, not a decoder defect.**

### 6.2 Meaning for E-2B

Sparse seek is **faster but does not reproduce the current sampling result**.
Fingerprints can change and matching results can change, so a **drop-in
replacement is impossible.** The options are:

```text
(a) narrow the predicate to at-or-after the target so both strategies agree
    (changes sampling semantics)
(b) treat sparse seek as a strategy that deliberately yields different samples
    and measure the accuracy cost
(c) use sparse seek only when GOP < sample spacing, and verify results
```

**E-2A chooses none of them.** Per directive §45 it only measures.

41.7 % either way, so the conclusion does not depend on which is used.

## 9. Planner Candidate Judgement (Directive §46)

No threshold is fixed here (Directive §28); only the observed classification is
recorded.

```text
Sequential Preferred
  - when GOP >= sample spacing. Measured: sparse was 6.4…136.8 % slower in 3 cases.
  - high per-frame cost (4K) combined with a long GOP is especially risky.
  - evidence: gop250, real GOP 225, real 4K

Sparse Seek Candidate
  - when GOP is clearly below sample spacing and wasteRatio is large.
  - Measured: 35.6…99.0 % gain across 10 cases.
  - best: intra-only (-g 1) 97.2 %, GOP 30 at 270 s 99.0 %

Unsupported / Fallback
  - GopUnavailable or GopEstimated files. No sparse candidate is generated and
    the sequential path is used instead. Evidence: the 4K file (mismatch 11).

Sparse Seek Required Evidence Missing
  - under the current predicate, pixel parity fails, so "same result" cannot be
    guaranteed. Without an exactness resolution, production adoption is blocked.
```

## 10. Unresolved / Limitations

1. **Pixel parity failure is unresolved.** 10 of 14 files select a different
   frame. §6.1 identifies the cause, but **the fix belongs to E-2B** and nothing
   is chosen here.
2. **AV1 cannot be decoded** by this build. Real content was obtained but is
   unusable.
3. **The 4K file's GOP is `GopEstimated`** with an 11-packet disagreement
   between packet keys and I-frames. The cause was not investigated.
4. **The real content is 8 files, all phone-class portrait/landscape.** No
   10-minute-plus features, no multi-audio-track, no 10-bit/HDR, no VFR in the
   dataset. (VFR source candidates exist but were excluded on representativeness
   grounds.)
5. **Repeats were 1**, so the median is effectively a single sample. The trend is
   unambiguous but run-to-run variance is not characterised.
6. **The §22 sampling-spacing exploratory benchmark (96/128/192/256/384/512) was
   not run.** Those are not production plan values, they are a separate
   exploration, and they are left outside this version's scope.
7. **No measurement of the `interval = 32` bucket** (>3840 s). The longest file is
   270.5 s.
