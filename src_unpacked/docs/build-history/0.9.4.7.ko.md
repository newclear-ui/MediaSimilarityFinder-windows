# MediaSimilarityFinder v0.9.4.7 — Node B6: Resource Mode Integration

B6 검증 기준점. brief §10의 모드별 정책을 스케줄러에 연결한다.
엔진 1.5.0·DB 1.0.3·캐시 v9·schema 1 불변.

## 변경 필요성
- B5까지 스케줄러는 Resource Mode를 읽지 않았다. Maximum과 Gaming이
  같은 안정성으로 동작해서, 모드 선택이 스케줄러에 닿지 않았다.

## 기존 구조
- `SchedulerHardware`에 mode 입력이 없고, hold·floor·밴드는 전역 상수였다.

## 변경 구조
- `SchedulerHardware.mode` + `paramsForMode()`: 모드별 (cpuFloor,
  holdMs, killAt, relieveAbove). Maximum(0.10/5초/표준밴드),
  High(0.07/10초/표준), Balanced·Custom(0.05/10초/표준 = B4 검증값),
  Gaming(0.02/30초/95킬·90릴리프). Light는 Gaming 별칭(동일 enum값).
- 명시적 `setHoldMs()`가 있으면 모드 기본값을 이긴다(테스트·진단용).
  미설정(-1)이면 모드 기본값. 기존 테스트는 Balanced 기본·명시 hold라
  전부 무변경 통과한다.
- 엔진은 스캔 시작 시 `schedHw.mode = policy_.mode` 1줄로 연결한다.
  Manual의 CPU 상한은 기존대로 worker 수에서 강제되므로 스케줄러 측
  Manual == Balanced임을 명시·테스트한다.
- 모드는 안정성/반응성만 튜닝하고 shares 비례식은 손대지 않는다.

## 선택 이유
- 기존 정책 숫자(cpuPercent)를 재해석하는 대신, 스케줄러가 직접 쓰는
  4개 파라미터를 모드별로 선언했다. 숫자 출처가 한 곳이라 B6 이후
  조정(장기 관측)이 쉽다.
- Gaming의 깊은 cut·긴 hold·빠른 yield가 "보수적"의 동작 정의다.
  반대로 Maximum은 민첩+자기 우선이다. 문서가 곧 사양이다.

## 해결된 문제
- 모드 선택이 스케줄러 동작으로 이어진다. B7 게이트의 모드별 검증
  항목이 실행 가능해졌다.
