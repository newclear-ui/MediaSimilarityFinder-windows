## 1. 변경 필요성

E 노드는 "요청한 샘플보다 많은 프레임을 디코드해서 생기는 비용"을 줄이는

E-2 를 구현하려면 먼저 이 전제를 실측해야 한다.

## 3. 변경 구조 — 이번 버전은 production 코드를 바꾸지 않는다

measurement-only probe 를 `tests/` 에 추가했다. production behavior 변경 없음,
hardware decode path 연결 없음, `av_hwdevice_*` 호출 없음.

### 3.1 probe 와 왜 그것이 신뢰할 수 있는가

`tests/video_decode_planner_probe.cpp`

- sampling plan 은 **실제 production 함수** `msf::make_sample_plan` 을 호출한다.
- decode loop 은 `video_decoder.cpp:94-140` 의 계측 미러다. 같은 단일 backward
  seek, 같은 0.05 s tolerance, 같은 `SWS_BILINEAR` 96x96 gray, 같은 3x3 box mean.
- **검증**: probe 가 만든 32x32 프레임을 **진짜 production**
  `VideoDecoder::framesAt96Plus32` 출력과 byte 단위로 비교한다.

```text
probe_matches_production_frames = yes (8/8 files byte identical)
```

이 검증이 없으면 probe 는 I-2 때 문제였던 "자기 재구현만 측정하는" 상태가 된다.
불일치가 있으면 평균 내지 않고 **불일치로 보고**한다.

### 4.4 H2 — 프레임당 비용은 codec × resolution 으로 결정된다

```text
file                         codec          px   decoded  decode_ms  ms/frame
mpeg4_640x360_05fps_030s     mpeg4      230400      150       18.3     0.1221
mpeg4_640x360_25fps_005s     mpeg4      230400      125       13.9     0.1112
mpeg4_640x360_25fps_030s     mpeg4      230400      750       81.2     0.1082
mpeg4_640x360_25fps_300s     mpeg4      230400     7500      768.5     0.1025
mpeg4_640x360_60fps_030s     mpeg4      230400     1798      195.3     0.1086
mpeg4_1920x1080_25fps_030s   mpeg4     2073600      750      747.8     0.9970
h264_640x360_25fps_030s      h264      230400      750      144.0     0.1921
ffv1_640x360_25fps_030s      ffv1      230400      750     1117.6     1.4902

grouped:
  mpeg4 640x360   n=5  0.1025 ~ 0.1221  spread 19.2 %   <- fps/duration 영향이 작다
  mpeg4 1920x1080 n=1  0.9970
  h264  640x360   n=1  0.1921
  ffv1  640x360   n=1  1.4902
```

- 같은 codec·해상도에서 **fps 가 5배, duration 이 60배 달라도 프레임당 비용은
  19.2 % 안에 머문다.** → fps 와 duration 은 비용에 직접 들어가지 않는다.
- 640x360 → 1920x1080 은 픽셀 수 9.0배, 비용 9.2배. **픽셀 수에 선형.**
- codec 차이는 크다: mpeg4 0.108 → h264 0.192 (1.8배) → ffv1 1.490 (**13.8배**).
  ffv1 은 intra-only 여서 이것이 직접 반영된 결과다.

**이것이 cost model 의 실측 기반이다.**

```text
SoftwareDecodeCost ≈ framesDecoded × msPerFrame(codec, resolution)
framesDecoded     = fps × duration          (H1, 실측 일치)
msPerFrame        = f(codec, resolution)    (H2, codec·resolution 그룹별)
```

## 5. Planner input 확정 (Gate C)

지시 §9 의 후보 18개 중, §10 기준("decode time 또는 end-to-end time 을
설명하는 변수만 남긴다")으로 걸러낸 결과.

### 5.1 채택 — 5개

| input | 근거 | 상태 |
|---|---|---|
| `duration` | interval 버킷을 선택해 sample count 를 결정 | 실측 |
| `fps` | framesDecoded = fps × duration, 따라서 waste ratio 를 결정 | 실측 |
| `resolution` | msPerFrame 을 결정 (픽셀 수에 선형) | 실측 |
| `codec` | msPerFrame 을 결정 (mpeg4/h264/ffv1 에서 1.8~13.8배) | 실측 |
| `keyframe interval (GOP)` | sparse-seek 비용 계산에 필수 | **부분** — §7 한계 참조 |

### 5.2 제외 — 근거와 함께

| 제외한 후보 | 제외 근거 |
|---|---|
| `estimated frame count` | fps × duration 의 **파생값**. H1 이 증명 |
| `sampling count` | duration 의 **파생값** |
| `container` | codec·해상도가 고정된 상태에서 분리 측정 불가 (이 dataset 은 mp4/mkv 가 codec 과 함께 변함) |
| `pixel format` | dataset 전체가 yuv420p. **변이가 없어 평가 불가** → 미래 후보로 유지, 현재 입력 아님 |
| `bit depth` | 10-bit 콘텐츠 없음. **평가 불가** |
| `file size` | 5.2~6.2 MB 범위. duration/resolution/codec 과 분리 불가 |
| `seek distance` | 오늘은 항상 1회. **퇴화** |
| `CPU mode` / `CPU live load` | E-1 에서 측정 기반 없음. §10 과 지시 §3 에 따라 추측으로 넣지 않음 |
| `GPU ON/OFF` / `GPU capability` | 동일. 지시 §3 이 "GPU 가능 = GPU 선택" 을 명시적으로 금지 |
| `expected transfer cost` | F 이전에 측정 불가 |

**18개 후보 → 5개.** 지시 §10 이 요구한 축소가 그대로 실현됐다.

## 6. Planner model 설계 (Gate D)

구현하지 않고 설계만 한다. 아래 enum/구조체 이름은 E-2 구현 시 코드를
확인하고 최소화한다.

### 6.1 출력

```text
VideoDecodePlan
{
    samplingMode    SequentialSweep | SparseSeek
    backend         Software | HardwareCandidate
    expectedCostMs  추정값
    fallbackPolicy  FallbackToSoftware
    reason          아래 enum
}
```

### 6.2 판단 구조

```text
wasteRatio := fps × interval(duration)        (H1, 실측 평균 오차 6.48 %)
frameCost  := msPerFrame(codec, resolution)   (H2, 실측)
gop        := keyframe interval               (측정원 미확정 — §7)

if GPU == OFF                       -> Software / SequentialSweep / reason=GPU_OFF
if hardware capability 없음          -> Software / SamplingDecision / reason=NO_HW_CAPABILITY
if wasteRatio < 1.5                 -> SequentialSweep  (현행이 이미 최적에 가까움)
if gop < 0.5 × wasteRatio           -> SparseSeek 후보가 매우 유리, backend 와 독립
if gop ≈ wasteRatio                 -> 경계, 실측 필요
```

**중요**: `gop < 0.5 × wasteRatio` 조건은 **hardware decode 없이도**
software sampling 전략만으로 동작한다. §11 에서 후술한다.

### 6.3 reason 코드

```text
GPU_OFF / NO_HW_CAPABILITY / SHORT_VIDEO / LOW_SAMPLING_DENSITY /
SEQUENTIAL_SUFFICIENT / HIGH_TRANSFER_COST / CPU_SOFTWARE_PREFERRED /
HARDWARE_CANDIDATE
```

UI 노출 없음. 개발 telemetry 수준.

## 7. 측정 한계 — 반드시 함께 읽어야 한다

1. **dataset 이 8개 합성 lavfi 파일이다.** 실제 세계 콘텐츠가 아니다.
   bitrate 분포·화면 전환·노이즈·실제 카메라 노이즈가 없다.
2. **codec 3종뿐.** HEVC·VP9·AV1 는 이 FFmpeg 빌드에서 생성 불가(§3.3).
   현대 decode 에서 가장 큰 비용 차이가 나는 코덱군이 **빠져 있다.**
3. **GOP 입력이 신뢰할 수 없다.** ffv1 은 intra-only 인데 측정값이
   63/750 이다 (전체여야 함). `AV_PKT_FLAG_KEY` 가 ffv1-in-matroska 에서
   정확하지 않음을 뜻한다. **GOP 를 비용 모델에 쓰기 전에 다른 출처가 필요하다.**
4. **GOP 데이터점이 2개뿐** (mpeg4 ≈ 11.9, h264 = 50.0). 각각 n=1 이라
   분포를 알 수 없다.
5. **sparse-seek 절감률은 산술이지 실측이 아니다.** 아래 §8 참조.
6. 모든 파일이 ≤300초, ≤1080p. `interval = 32` 버킷(>3840초)은
   selfcheck 에서 **산술적으로만** 확인했고 실측하지 않았다.
7. cold/warm 파일 cache 를 분리하지 않았다.

## 9. E / F 경계 (Gate E)

```text
E = decision / planning     이 video 를 어떤 조건에서 어떻게 decode 할 것인가
F = implementation          선택된 hardware decode 를 실제로 어떻게 붙일 것인가
```

- E-1 은 `av_hwdevice_*` 를 **호출하지 않았다.** capability 조회(사실 확인)와
  hardware decode 사용(F)은 다르다.
- §12 에 따라 "GPU 가능 = GPU 선택" 규칙을 **만들지 않았다.**
- hardware capability·device·frame configuration 별 판단이 필요하며,
  FFmpeg 공식 API 구조상 `avcodec_get_hw_config()` 조회가 전제된다.
- hardware 값은 **만들어내지 않았다.** F 이전이므로 측정 대상이 아니다.
- fallback 계약은 E 와 F 가 동일하다.

```text
HardwareCandidate → (backend 없음) → FallbackRequired → SoftwareDecode
```

CPU fallback 은 어떤 조건에서도 제거하지 않는다.

## 10. 이번 측정에서 얻은 가장 중요한 재구성

E 노드 이름은 "Adaptive Video **Decode** Planner" 다. 측정은 **hardware
decode 없이**도 node E 가 다룰 수 있는 더 큰 항목이 있음을 보여준다.

```text
측정된 낭비 = 89.81배 (샘플 140개에 12,573프레임)
이 낭비는 sampling 전략(sparse seek) 문제이며 hardware backend 와 무관하다
```

즉 **판단은 두 개로 분리해야 한다.**

```text
(1) 몇 프레임을 디코드할 것인가   -> samplingMode, E-2, software 만으로 가능
(2) 누가 디코드할 것인가           -> backend,     F,  hardware 필요
```

현재 데이터에서는 (1) 이 (2) 보다 훨씬 크다. 이는 E-2 가 hardware 없이도
가치 있는 작업임을 뜻하며, E/F 순서를 바꾸자는 주장은 **하지 않는다**
(F 는 여전히 필요하다). 단 **E-2 의 우선순위가 (1) 이라야 한다는 근거**로
기록한다.

## 12. 다음 단계

```text
E-2  Adaptive Video Decode Planner 구현
      └─ 먼저 (1) sampling mode 결정 (Sequential vs SparseSeek) 을 구현·실측
      └─ 그 다음 (2) backend 결정 구조를 추가하되, hardware 없이 Software 로만
E-3  calibration / validation
F     Hardware Video Decode Backend
```

E-2 착수 전에 **해결이 필요한 사항**

1. **GOP 측정 원본.** `AV_PKT_FLAG_KEY` 가 ffv1 에서 부정확하다.
   `avformat` 의 index/keyframe 정보 또는 디코더 단위 측정이 필요하다.
2. **실제 콘텐츠 dataset.** 합성 lavfi 8개로는 코덱 비용 차이가 대표적이지 않다.
   codec 지원 확대(의존성 변경)를 별도로 결정하거나, 외부에서 제공된
   콘텐츠를 받아야 한다.
3. **sparse seek 실측.** §8 은 산술이다. 구현 후 실측이 필요하다.
