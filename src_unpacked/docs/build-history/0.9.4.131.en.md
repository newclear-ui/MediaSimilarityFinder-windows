# MediaSimilarityFinder v0.9.4.131 — Counters unified to the displayed result set (summary panel + detailed log)

Baseline `0.9.4.130` -> this build `0.9.4.131`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged (verdicts unchanged; CTest registration count unchanged).

## 1. Why the change was needed

- The 0.9.4.130 self-heal restores results, but one display gap remained: on a fully-unchanged rescan A/AB recompute nothing, so
  - the left summary panel's "Similar groups" row is overwritten by the finished message's `r.groups` (the pairs this scan computed) and reads **0**,
  - the detailed log reads `matches: candidates 0, pairs 0, groups 0` -- while the list displays the stored set (e.g. 9070 groups / 15135 pairs).
  The user judges results from the detailed log (consecutive field reports 0.9.4.127-130), so this mismatch keeps misleading.
- The panel also had **two different bases**: during a scan it showed `groups_.size()` (clusters in the visible list), then `refreshSummary()` replaced it with `lastStats_[3]` (a pair count) at finish -- the value's meaning changed.

## 2. Previous structure

- Finished message `r.groups` = this scan's pair count (st.groups + live-owned) -- the GUI panel displayed it as if it were a group count.
- Telemetry `matches` counters = what the engine emitted/aggregated this scan (the quick-loaded stored set was outside the accounting).

## 3. Changed structure

- `gui/mainwindow.cpp`: the summary panel's "Similar groups" row now uses `groups_.size()` (clusters of the list on screen) -- one basis during and after scans. Duplicate-file count was already list-based.
- `src/scan_worker.cpp`: right after the engine scan, it computes from the displayed stream `allMatches_` (= quick-loaded stored pairs + this scan's emissions, scope/ignore filters included):
  - the deduplicated pair count (128-bit path-pair key: two seeded FNV-1a values -- display/telemetry only, verdicts unaffected),
  - per-kind group and duplicate-file counts via a path-keyed union-find (with compression),
  then passes them through `MediaSearchEngine::applyDisplayedResultStats()` -> `TelemetryRecorder::setDisplayedResultStats()`.
- `src/benchmark.{h,cpp}`: when the displayed-set override is set, the JSON's `matches.pairs/groups` and `image*/video*` fields serialize from the displayed set. `candidates`/`reductionPct` stay scan-scoped work metrics. CLI scans never call this path, so their journal keeps the scan's own computation (the 0.9.4.126 contract is unchanged).

## 4. What was resolved

- On unchanged rescans the detailed log's `Matches` line and the summary's group/duplicate-file counts now **agree with the visible list**. Measured (18-file set, AB unchanged rescan): `pairs=8, groups=3` (0 before). The panel shows 3 as well.
- The panel's "Pair verify (total/confirmed)" row shows `candidates` (scan) / `pairs` (displayed set): fresh and self-heal scans read like `19187 / 15135`, and unchanged rescans show `-` because candidates is 0 (an intended distinction).

## 6. Impact and limitations

- Verdicts, storage, protocol, engine/DB/schema/cache and the journal schema are unchanged. CTest registration count unchanged (125/126).
- The displayed-set unification applies to the GUI (ScanWorker) path only. CLI/journal counters keep the scan-scoped basis; the difference is an intended contract (the journal is a batch measurement record, the GUI log is the user's result record).
- The 128-bit pair key is telemetry-count-only (never affects verdicts, storage or the displayed list; the list is governed by the path-based union-find regardless).
- The summary panel's "Similar groups" is now always a cluster count. Numbers in older logs/screenshots from the period when that row showed a pair count may differ (a meaning correction).
