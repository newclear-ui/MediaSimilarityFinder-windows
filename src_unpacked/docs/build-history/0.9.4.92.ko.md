# MediaSimilarityFinder v0.9.4.92 — 쌍검증 DBV-1/DBV-2 (캐시키 읽기 제거 + 캐시 확대)

기준선 `0.9.4.91` → 본 빌드 `0.9.4.92`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` 불변.

## 1. 변경 필요성

쌍매칭 검증(이미지 L2) 비용은 **decode 86.5% · 캐시키 I/O 13.4% · SSIM 0.04%**로 구성된다(0.9.4.91 로그).
`docs/architecture/database-structure.ko.md` 7절의 개선 예정 V-1(캐시키 quickHash 읽기 제거)과
V-2(검증 버퍼 캐시 확대)를 저위험 후보로 먼저 구현·실측한다.

## 2. 기존 구조

- `verifyBuffersFor`가 **매 lookup마다** 파일에서 64 KiB를 읽어 FNV 해시로 캐시키를 만든다
  (경로 stat 2회 + 64 KiB read). 고지연 드라이브에서 948 MB 읽기 → `verifyKeyMs` 170 s(합산).
- 검증 버퍼 LRU가 `kVerifyCacheMax = 32`로, 14k distinct 파일 대비 사실상 무용(히트율 9.1%).

## 3. 변경 구조

- **DBV-1**: 캐시키를 `(path, size, modified)`로 축소. **파일 읽기 0회**. (스캔 중 내용은 바뀌지 않으므로
  동일 스캔 내에서는 안전. size+modified 동일·내용 변경의 드문 경우는 전체 지문 캐시와 동일한 한계.)
  `VerifyCacheKey`/hash에서 quickHash 제거.
- **DBV-2**: `kVerifyCacheMax` 32 → **1024**(엔트리 ≈8 KB, ≈8 MB). 파일이 여러 쌍에 재등장할 때 상주한다.

## 4. 해결된 상황

- 캐시키의 64 KiB 읽기 제거 → `verifyQuickHashReads/Bytes` 0, `verifyKeyMs`에서 read 부분 제거.
- 캐시 히트율 상승 → decode miss/`verifyDecodes` 급감 → `verifyDecodeMs` 감소.

## 6. 성능 실험 기록 (AGENTS 9항)

- **Experiment**: DBV-1(캐시키 읽기 제거), DBV-2(캐시 확대)
- **Baseline**: 0.9.4.91 로직(표준 dataset before).
- **Hypothesis**: 키의 64 KiB 읽기는 중복이고, 캐시 32는 무용하다.
- **Method**: `image_verify.cpp` 수정, `msf_dataset_baseline` before/after, CTest parity.
- **Result**: 위 표. V-1 key -37.9%(read 제거), V-2 decode -93.1%(hit↑), wall -53%.
- **Status**: PASS(표준 dataset).
- **Known limitation**: size+modified 동일·내용 변경 시 캐시 재사용(전체 지문 캐시와 동일 한계).
