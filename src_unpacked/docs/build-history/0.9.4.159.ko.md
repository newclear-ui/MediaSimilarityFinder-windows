# MediaSimilarityFinder v0.9.4.159 — 비교 엔진 행 버퍼 재사용 (P2)

기준선 `0.9.4.158` → 본 빌드 `0.9.4.159`.
CPU CTest **133/133**, GPU CTest **134/134** (신규 CTest 1건: video_sim_perf_test).
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 10` / `kProtocol 1` 전부 불변.

## 1. 변경 필요성

- 외부 리뷰 P2 지적: `video_similarity()` DTW가 행마다 `hamming`/`ssim` 벡터와 GPU 게이트 통과 쌍의 packing 버퍼(`pa`/`pb`/`map`/`out`)를 새로 할당하고, `processVideoFrames()`의 pHash 스테이징(`packed`/`mirrored`/`map`)도 점진 재할당한다. kept가 길어질수록 행 단위 할당·해제가 매칭 오버헤드에 누적된다.

## 2. 기존 구조

- DTW 행 루프 안에서 행마다 벡터 생성, GPU 게이트 행마다 packing 버퍼 생성, pHash 청크마다 `normal`/`mirror` 결과 버퍼 생성.

## 3. 변경 구조

- `video_similarity()`: thread_local `VideoSimWorkspace`가 행 버퍼를 행·호출 간에 재사용한다. `scan_pipeline`이 후보 쌍을 async pool로 분산하므로 스레드별 인스턴스로 경합을 피한다. 수식·순서 불변 → 점수 불변.
- `processVideoFrames()`: pHash 스테이징 버퍼를 `keep` 개수로 1회 reserve, 청크 결과 버퍼를 루프 밖으로 이동.
- 회귀: `video_sim_perf_test` 신규 — 고정 LCG 지문 12x14의 CPU 2회 완전 동일성, GPU 존재 시 CPU·GPU 0.2 이내 일치 + submitted/completed 단언, 고정 400회 wall time 보고.

## 4. 해결된 상황

- 행 단위 힙 할당이 warmup 이후 0이 된다 (구성상 보장). 판정·텔레메트리 의미 불변.

## 5. 검증 (성능 실험 기록)

- Experiment ID: P2-WS-159. Purpose: DTW 행 할당 churn 제거의 wall-time 효과. Hypothesis: 행 할당이 매칭 오버헤드를 지배한다.
- 조건: 동일 머신·동일 바이너리 형태·동일 워크로드(12x14 고정 쌍, 400회). Baseline: 최적화 코드를 stash한 동일 트리 재빌드.
- Raw measured values (ms/400iters):
  - CPU 경로(frame_ssim fallback): baseline 486.95 / 458.73 / 465.43 / 448.43, 신규 471.90 / 445.18 / 441.53 / 455.93 / 465.72 / 451.87.
  - GPU 경로(ssimBatch, submitted=completed=308): baseline 447.13 / 400.01 / 448.03, 신규 359.48 / 322.41 / 457.73 / 435.50.
- Verdict: 속도 개선 가설은 **NOT ACCEPTED** — 양쪽 경로 모두 run-to-run 변동(±10~20%) 범위 안이며, 지배 비용은 계산(`frame_ssim`/커널)임이 확인됐다. 구조 변경 자체는 **PASS** (점수 완전 동일 `cpuScore=10.9667`, 전체 스위트 green, 할당 churn 구성상 제거, async pool 하의 allocator 압력 감소).
- 전체: `CPU Release CTest 100% tests passed out of 133`, `GPU CTest 100% tests passed out of 134`, `--version` 0.9.4.159 4종.

## 6. 향후 영향 및 한계

- 판정·저장·프로토콜·버전 전부 불변. 캐시 무효화 없음.
- GPU batch 임계값(8)·packing 순서·mutex 직렬화는 실측 근거 없이 건드리지 않았다. 진짜 매칭 가속은 디코드 상주(HW 단계) 이후에 다시 측정한다.
- 프레임 선택의 시간축 대표성은 V2/V3 gate 이후 과제이며 본 빌드에 포함하지 않는다.
