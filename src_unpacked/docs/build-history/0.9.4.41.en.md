## 1. Why the Change Was Needed

The single remaining v0.9.4.40 failure was HEVC 1080p:

```text
pixel parity = 13/14
failing file = real_hevc_1920x1080_030s.mp4
violated condition = firstDecodedPts > seekRequestPts
```

The question was singular: **is this solvable with the current seek API and
decoder interaction?** If yes, that is promotion evidence. If no, **HEVC =
SequentialPreferred is confirmed as final.** Forcing HEVC onto sparse seek was
never the goal.

## 3. Three Confirmed Facts

### 3.1 `AVSEEK_FLAG_ANY` Does Not Fix It — It Makes It Worse

```text
HEVC 1080p    : A viol=2  →  C viol=14
H.264 270.5s  : A viol=0  →  C viol=33
H.264 1080x1920: A viol=0  →  C viol=12
```

The directive's §7 diagnostic framing was justified. A non-keyframe seek lands
later rather than landing correctly, so it **increases** the violation. Keeping
it diagnostic-only was the right call.

### 3.2 `avformat_flush()` Has No Effect At All

```text
A and D are identical in viol, decoded and tsLater on all 8 files
```

Demuxer buffer disposal is not the cause. `avcodec_flush_buffers` alone suffices.

### 3.3 The Only Safe Primitive Is `av_seek_frame(..., BACKWARD)`

The narrow `avformat_seek_file` windows and `AVSEEK_FLAG_ANY` all permit
non-keyframe landings and therefore break exactness. **There is no way, among
the available APIs, to remove the two HEVC 1080p violations.**

## 6. Two Real Defects Found and Fixed During the Work

### 6.1 Verdict Logic Bug (important)

The first implementation aggregated exact results across all files and reported
`VERIFIED`. That let the **H.264 smoke group mask the HEVC failure.** The
verdict was made HEVC-specific, after which the result is `NOT VERIFIED`.
**A wrong conclusion was nearly reported.**

### 6.2 Use-After-Free Crash

`avformat_close_input(&fmt)` was followed by printf reading dangling `st`,
producing an access violation (0xC0000005). Width and height are now copied out
before closing.

Incidentally, `has_b_frames` and the `FF_PROFILE_*` constants are gone or
changed in FFmpeg 9, so the probe records only the numeric profile id rather
than reading a field that no longer exists.

## 9. What Is Left Unresolved

1. **The cause of the 2 HEVC 1080p violations is still unexplained.** What this
   version establishes is that no available API reproduces or removes them, not
   why they occur. Per §19 the investigation does not go deeper.
2. **HEVC 1360x808 is exact while 1080p is not.** The cause of that difference
   within one codec was not investigated.
3. **Only 2 HEVC files exist**, so the sample backing this conclusion is small.
4. The v0.9.4.40 4K GOP mismatch of 11 and AV1 keep their existing policies
   (Directive §20·21).
5. Planner calibration was not done (§22). It belongs to E-3B.
