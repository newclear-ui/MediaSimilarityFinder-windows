## 1. Why the change was needed

- After per-file scanning completes, candidate-pair verification takes very
  long while CPU utilization drops. Three code-confirmed structural causes:
  1. The analyze image pass is pinned to 16 workers
     (`src/scan_pipeline.cpp`, old line 284), idling cores on big machines.
  2. Shard imbalance: contiguous group ranges mean one worker grinds for tens
     of minutes on a pair-dense group while the rest idle (straggler).
  3. The report phase (`scanFinished`/`onResults`) is single GUI thread work
     with the backend already done, so no CPU can be drawn from anywhere.

## 2. Previous structure

- `consumeImageParallel`: `min(hw, groups)` workers over contiguous ranges,
  merged in part order. 16-cap.
- `flushVideo`: same 16-cap.

## 3. Changed structure

- **16-cap removed**: both follow `hardware_concurrency`.
- **Dynamic group dispenser**: workers claim whole groups via atomic
  `nextGroup`. The merge reorders segments by group index, so output order
  stays identical to the sequential pass (verdict parity, deterministic order).
- **Shard telemetry**: one `analyzeShards ...` backend-log line per analyze
  (jobs/active/pairs/max/avg shard wall), proving or disproving the straggler
  fix from logs alone, no profiler attached.
- No verdict/matching/cancel semantic change. `stop`/cancel paths,
  `LocalCancel`, and telemetry summation are untouched.

## 4. Resolved state (expected, unverified)

- Full core usage plus straggler relief shortens analyze wall time.
- Shard balance becomes measurable from logs.
