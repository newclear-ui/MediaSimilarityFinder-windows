# MediaSimilarityFinder v0.9.4.74 — merged audit, telemetry-exit fix, progress and resume

Baseline `0.9.4.73` → this build `0.9.4.74`.
CPU CTest **116/116**, GPU CTest **117/117**.
`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.4` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — all unchanged. No change to search verdicts.

## 1. Why this change

The user still sees only 1–2% GUI/Backend CPU despite heavy disk I/O, an apparent
read-complete stall on new files, and a Backend exit that restarts the process
but does not continue the scan. We compared the ChatGPT/Claude/Kimi/Grok/Meta
audits against current C++/Qt code, logs, and dumps.

Confirmed user evidence:

- The screen message is generated by the Supervisor on process exit. The user's
  log records exit code `-1073740791` = `0xC0000409`, parameter `0x7` =
  `FAST_FAIL_FATAL_APP_EXIT` (abort/terminate family). The dump RIP is
  `ucrtbase.dll+0xA527E`. No backend health-watchdog line precedes the captured
  exit.
- The 0.9.4.72 dumps had no matching PDB, so their exact caller cannot be resolved.
- Two Windows Application Event 1000 records also match the Backend image
  timestamp `0x6AC7686B`, `ucrtbase.dll`, exception `0xC0000409`, and offset
  `0xA527E` (2026-10-08 19:28:45 / 19:33:05).
- Before this build, a deterministic walker exception regression produced the
  same `0xC0000409`; its symbolized test stack was
  `TelemetryRecorder::~TelemetryRecorder` → `MediaSearchEngine` → `ScanWorker`.
  An exception bypassed `finishScan()`, leaving the telemetry sampler's
  `std::thread` joinable; destroying it calls `std::terminate()`.

## 2. Prior structure and audit comparison

- **Crash dialog/restart**: the Supervisor emits the fixed error and restarts the
  process, but did not replay `START_SCAN`. The .73 GUI auto-resume path depended
  on ordering between the failure and connection signals and did not reliably
  preserve the scan configuration.
- **Restart delay**: the unexpected-exit path emitted `failed()` (modal GUI
  handler) before `scheduleRestart()`. The direct Qt connection blocked the
  Supervisor stack in `QMessageBox::critical()` until the user dismissed it.
- **CPU/I/O**: `Scanner::scan_stream::quick()` reads the first 64 KB of **every**
  media file, including indexed files. DB size/mtime/quickHash comparison comes
  later in `processOne()`. Unchanged files skip decode/index analysis, but still
  incur quick-hash I/O. This is consistent with I/O-bound low CPU and is not by
  itself evidence of a worker-allocation defect. `Scanner::count()` also made a
  complete pre-scan directory pass without progress reporting.
- **Read counter**: the existing `ScanControl::walked` callback ran in the
  consumer's `processOne()`. A new image batch blocks that consumer in
  `processImageBatch()`, so the read row could freeze while the walker filled its
  bounded queue (up to 4096). `lastListN_` was not reset between scans.
- **Other audit hypotheses**: synchronous stdout flush is a plausible
  backpressure risk, but the captured exit was a direct abort, not a health
  watchdog termination. The Python launcher/venv/CUDA-DLL explanation does not
  match this C++/Qt repository and was not adopted.

## 3. New structure

- **Telemetry sampler RAII (`src/benchmark.h/.cpp`)**: `TelemetryRecorder`'s
  destructor always calls `stopSampler()` and joins its thread. Both
  `ScanWorker::run()` exception handlers also try `engine_.abortTelemetry()`.
- **Walker/consumer exception-safe join (`src/media_search_engine.cpp`,
  `src/scanner.*`)**: walker exceptions set `walkError`; consumer exceptions are
  held in `exception_ptr`. On failure/cancel, a local `walkAbort` and queue
  shutdown wake the producer; the walker is joined before rethrow/return.
  `ScanCallbacks::shouldStop` separates internal abort from user cancel. Walker
  exceptions become recorded failures.
- **Deterministic regression seam**: `MSF_TEST_THROW_WALKER` throws inside the
  walker thread. `scan_streaming_test` verifies join + failure reporting without
  process termination. The seam reproduced the telemetry-destructor abort before
  the fix and passes afterward.
- **Progress (`src/scanner.*`, `src/scan_worker.cpp`, `gui/mainwindow.cpp`)**:
  - `Scanner::count()` accepts an optional progress callback (every 2,000
    directory entries). ScanWorker logs `scanPhase=count begin/done` with elapsed
    time, entries, and target count.
  - New producer-side `readProgress` is separate from the existing consumer-side
    `walked` callback. In-scope, non-ignored files count as read after quick-hash
    and admission to the bounded queue. Consumer `walked` semantics (used by
    engine clients/cancellation tests) remain unchanged.
  - `scan_stream()` reports each hash batch; ScanWorker flushes the final producer
    count on return. MainWindow resets `lastListN_`, `lastPct_`, and `lastPath_` at
    each start and keeps `walkedCount` monotonic.
- **Restart/resume (`gui/mainwindow.*`, `gui/backend_supervisor.cpp`)**:
  - MainWindow stores the exact `BackendScanConfig`. A user Start resets the
    resume budget; a READY reconnect after a Backend crash reissues the saved
    config **once**. The incremental engine reuses committed rows.
  - `scanFailed()` distinguishes Backend interruption. The first pending resume
    updates status without opening a modal dialog; a repeated failure shows the
    error dialog.
  - Supervisor arms restart before emitting scan-failure signals, so a modal UI
    cannot delay the restart. The watchdog path starts terminate/escalation before
    reporting failure.
  - Unexpected-exit messages include `QProcess::ExitStatus` and exit code.

## 4. What is fixed

- The reproduced exception/unwind path no longer terminates with 0xC0000409; it
  becomes a normal failed scan with the Backend process alive.
- The UI reports pre-count enumeration and producer-side read/admission separately
  from consumer analysis; a long new-image batch is distinguishable from a dead
  walk. Heartbeat listing no longer carries a prior scan's count.
- Backend restart is scheduled before failure UI, and a READY Backend automatically
  resumes the saved scan once.
- The live read count now reflects files quick-hashed/admitted to the bounded
  queue. It can lead consumer analysis by at most the queue capacity, instead of
  freezing solely because the consumer is decoding a batch.

`scan_cancel_drain_test` and `scan_cancel_video_test` first failed when the
producer count replaced the existing consumer `walked` callback. The callbacks
were separated into `readProgress` (producer) and `walked` (consumer); exact
cancel/batch semantics were restored, and the full CPU/GPU suites passed.

**Audit confidence**:

- **Confirmed**: popup origin, previous lack of scan replay / failure-signal
  ordering, count pass without progress, quick-hash I/O on indexed files,
  consumer-count batch stall, stale listing heartbeat, and the telemetry
  sampler destructor abort path.
- **Strong matching cause**: the sampler-join omission reproduces the same code
  and offset via the deterministic seam. The old user dump lacks a PDB, so exact
  caller identity cannot be proven.
- **Unmeasured**: the user's exact .72 count/walk/batch durations and whether its
  Backend dump took the telemetry-destructor path. The .74 logs now provide
  `scanPhase=count`, `scanPhase=engine`, and producer/consumer heartbeat values.
- **Not established for this dump**: synchronous stdout pipe backpressure remains
  a separate stress-test risk, but the captured failure was a direct abort with
  no watchdog-timeout log.
- **Not applicable**: the Meta audit's Python `main.py`/venv launcher hypotheses
  do not match this C++/Qt repository.

## 6. Future impact

- On the user's next .74 run compare `scanPhase=count`, `scanPhase=engine`, and
  `alive ... walked=... listed=...` in `%TEMP%\msf_scan.log` to identify the phase.
- A new Backend dump can be symbolized using its matching .74 PDB.
- Disk I/O may remain high: unchanged files still read the first 64 KB to retain
  quickHash detection of same-size/same-mtime content changes. This audit did not
  change that correctness policy.
- New-file image/video batch processing and bounded queue backpressure remain;
  read-progress now tracks producer admission, while Index Complete tracks
  analysis.
- Supervisor `attempts_` resets when READY is proven, so its restart budget limits
  consecutive pre-READY failures. The per-scan automatic resume budget is one.
- `backend_main::send()` synchronous stdout flush remains a separate stress-test
  candidate; it was not changed without evidence tying it to this abort.
- `ExactnessPolicy::RefuseAll` stays; Node E terminal state unchanged.
