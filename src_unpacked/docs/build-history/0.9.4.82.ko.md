# MediaSimilarityFinder v0.9.4.82 — EXIF 회전 이미지 WIC FlipRotator 폭주 제거

기준선 `0.9.4.81` → 본 빌드 `0.9.4.82`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.0 → 1.5.1` / `kDatabaseVersion 1.0.5` /
`kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9`.
판정 규칙·임계·가중·게이트는 불변. 엔진 patch 상향은 **EXIF 회전 이미지의
fingerprint 바이트가 소폭(±1 LSB) 바뀌므로 기존 저장 쌍을 다음 스캔에서
재검증**하기 위한 것이다(엔진 버전 규칙 5항).

## 1. 변경 필요성

사용자가 0.9.4.79로 대규모 이미지 데이터셋(`G:\Downloads\ss_twit`, 177,120장,
고지연 드라이브)을 스캔한 리포트가 기준이다.

- 전체 177m 45.6s. 그중 이미지 stage 7037.9s(=117m), 매칭 818.2s.
- CPU 사용률 avg 20.6% / max 119.4%, GPU 듀티 0.0% → 사실상 I/O·decode 대기.
- `느린 파일 (img)` 최상위 5개가 **343~480초/장**(정상 decode 평균 77.58ms의
  약 5000배).
- 파일 자체는 정상(0.88~2.1MB, EOI 존재, GDI+ 전체 디코드 30~60ms, raw read 10ms).

프로브로 재현한 결과, 느린 5장은 모두 **EXIF orientation=6 + 12MP
(4000×3000 / 4032×3024)** 였고, 병목은 디스크도 파일도 아닌 **제품의 WIC
디코드 경로**였다.

## 2. 기존 구조

`image_decoder.cpp`의 두 WIC 경로가 EXIF orientation이 identity가 아니면
**디코더와 스케일러 사이에 `IWICBitmapFlipRotator`를 삽입**했다.

- `decodeWicBranches` (decode / decodePreserveAspect / decodeBoth 공용)
- `decodeWicFileAspectColor` (decodeColorAspect / 썸네일 color lane)

`media_pipeline.cpp`는 이미지 1장을 이 경로로 **3회**(pass1 32×32, crop
decodePreserveAspect 128, decodeColorAspect 128) 디코드한다.

`WICBitmapScaler`에 `WICBitmapInterpolationModeFant`를 걸고 그 아래가
`FlipRotator`인 경우, WIC은 회전 때문에 JPEG의 고속 축소 디코드 경로를 잃고
풀해상도 경로로 폭주한다. 프로브(회전 없는 동일 파일):
`CopyPixels` = **150,916ms (rotator→scaler) vs 22ms (scaler만)**.

## 3. 변경 구조

새 `applyOrientationPixels(px, w, h, channels, xform)` (image_decoder.cpp,
`#ifdef _WIN32` 블록)를 추가하고, orientation을 **스케일 이후**로 옮겼다.

- 정렬: WIC 합성 순서를 합성 패턴으로 실측해 확정 — **FlipHorizontal 먼저,
  그 다음 rotation(90/180/270)**. EXIF 5/7(회전+반전)도 이 순서로 일치.
- `decodeWicBranches`: `src = frame`(회전 없음). orientation이 90/270이면
  oriented w/h를 swap해 aspect 치수와 **사전 스케일 타깃**(회전 후 (w,h)가
  되도록 `(h,w)`로 스케일)을 계산. `CopyPixels` 후 `applyOrientationPixels`로
  회전. `orientApplied` 카운터는 계약대로 유지.
- `decodeWicFileAspectColor`: 동일하게 BGRA 출력에 `channels=4`로 적용.

회전은 순수 픽셀 치환이다. 따라서 **스케일된 버퍼에 적용**하는 것은 "스케일된
소스에 WICBitmapFlipRotator를 적용"과 byte-identical이고, 기존의
"풀해상도에서 회전 후 스케일"과는 **±1 LSB(88/1024 픽셀)** 차이다(Fant 보간
순서 차이).

## 6. 성능 실험 기록 (AGENTS 9항)

- **Experiment ID**: P-0.9.4.82-fliprotator-runaway, P-0.9.4.82-orient-after-scale
- **Version**: 0.9.4.82. **Date**: 2026-10-10.
- **Purpose**: 대규모 스캔에서 수백 초 걸리는 이미지의 원인 규명 및 제거.
- **Hypothesis**: 느린 파일은 디스크/파일 문제가 아니라 WIC 디코드 경로의
  회전 처리(FlipRotator) 폭주다.
- **Dataset**: `G:\Downloads\ss_twit` 산출리포트의 상위 5장(모두 orientation=6,
  12MP). 표본 500장 무작위에서 회전 이미지는 0건 → 병리 집합은 극소수.
- **Hardware/OS**: Windows, 로컬. Build: CPU/GPU Release.
- **Raw measured values**:
  - 회전 없는 12MP: CopyPixels 22ms.
  - orientation=6 12MP: rotator→scaler(기존) **150,916 / 151,563 / 156,374 ms**
    (반복 실행), scaler만 22~27ms, scaler→rotator(WIC 재정렬) 654~765ms.
  - software rotate 결과 vs 기존(rotator→scaler): 88/1024 픽셀 ±1.
  - software rotate vs WIC 재정렬: **0/1024 (byte-identical)**.
  - 수정 후 제품: 파일당 약 70~80ms.
- **Verdict / Status**: **PASS** (성능), 판정 parity는 엔진 patch 상향 + 재검증으로 처리.
- **Known limitation**: 회전 이미지의 fingerprint가 기존 대비 최대 ±1 LSB.
  Fant 보간 순서 차이이며, 방향/기하는 정확.
- **Future revisit condition**: WIC/Windows 업데이트로 FlipRotator 성능 특성이
  바뀌면 재측정. GPU/NVDEC 등 디코더 경로가 추가되면 동일 원칙(회전은 스케일
  이후) 적용 여부 재검토.
- **Related experiments**: 0.9.4.29(D3 중복 decode), 0.9.4.80(decode-once 후보).

## 7. 채택 사유와 미선택 대안 (상세 알고리즘, 차후 재검토용)

사용자 지시에 따라, 이번에 선택하지 않은 해결책을 **삭제하지 않고** 상세
알고리즘·근거·재검토 조건과 함께 남긴다. 1번(scale-first + software rotate)을
채택한 사유도 함께 기록한다.

### 7.1 채택 사유 — Option 1 (scale-first + software rotate)

1. **성능**: 회전 12MP 1건당 실측 software rotate 22ms, WIC 재정렬(B) 654~765ms,
   기존(rotator→scaler) 151s. Option 1이 가장 빠르다(기존 대비 약 6000배).
2. **정합성**: software rotate는 "스케일된 소스에 `WICBitmapFlipRotator`를 적용"(B)과
   **0/1024 byte-identical**였다(probe4). 즉 WIC 네이티브 회전과 결과가 같고 수단만
   다르다. probe7에서 7 transforms × 7 크기 × gray/BGRA **98/98 완전 일치**.
3. **구조 단순성**: `IWICBitmapFlipRotator` 객체를 아예 만들지 않으므로
   "디코더-측 회전 상호작용"이라는 문제 종류 자체가 사라진다. 상태·순서가 결정적이고
   COM 객체 수명 문제(회전 후 해제 순서 등)도 늘지 않는다.
4. **테스트 가능성**: 작은 버퍼의 순수 픽셀 치환이라 `xmp_orientation_test`
   (방향 2..8 + 조합 5/7 + geometry + quadrant)와 probe7로 직접 검증된다.
5. **적용 범위 일관성**: `decode` / `decodePreserveAspect` / `decodeBoth` /
   `decodeColorAspect` 4경로가 헬퍼 하나로 처리되고, animation이 아닌 색상 lane의
   aspect 치수(회전 시 w/h swap)까지 동일 규칙으로 처리된다.
6. **대가의 정직한 처리**: 기존 decode-시점 회전 대비 최대 ±1 LSB(Fant 보간 순서).
   `kEngineVersion` patch 상향 + 다음 스캔 재검증으로 처리했다.
7. **대안 대비**: A는 미완 + 대용량 물질화 + bytes 동일성 미검증, B는 byte-identical
   이나 약 30배 느림, C는 미측정·코덱별 불확실, D는 무관. 현재 조건에서 Option 1이
   속도·정합성·단순성을 동시에 만족하는 유일한 후보였다.

### 7.2 Option 1 알고리즘 (채택, 참조용)

1. `CoInitializeEx` → factory → `CreateDecoderFromFilename(..., WICDecodeMetadataCacheOnDemand)`
   → `GetFrame(0)`.
2. `GetMetadataQueryReader` → `/app1/ifd/{ushort=274}` → `/ifd/{ushort=274}` →
   `/xmp/tiff:Orientation` 순으로 조회해 `xform` 결정.
3. `src = frame` (회전 객체 없음).
4. `swap = (xform & 3) ∈ {1,3}`; oriented 크기 `(ow,oh) = swap ? (sh,sw) : (sw,sh)`.
5. fixed: `(pw,ph) = swap ? (fh,fw) : (fw,fh)` → `scaler.Initialize(src,pw,ph,Fant)`
   → converter 8bppGray → `CopyPixels` → `applyOrientationPixels(ch=1)`.
6. aspect: `(ow,oh)`에서 `(w,h)` 계산 → `(pw,ph) = swap ? (h,w) : (w,h)`
   → scaler/converter/CopyPixels → `applyOrientationPixels(ch=1)`(결과 dims `(w,h)`).
7. color: aspect와 동일하되 32bppBGRA, `ch=4`.
8. `applyOrientationPixels` 적용 순서: **FlipHorizontal → FlipVertical → rotation(90/180/270)**.
   각 단계는 채널 단위 픽셀 치환(회전은 버퍼 재배열 + w/h swap).

### 7.3 대안 A — byte-identical 물질화 (미선택)

**목표**: 기존의 "풀해상도 회전 → 스케일" 순서를 유지해 판정을 100% 동일하게.

**알고리즘**:
1. factory → decoder → frame → `xform` (Option 1과 동일).
2. `rotator.Initialize(frame, xform)` (풀해상도), `rotator.GetSize` → `(ow,oh)`.
3. `CreateBitmap(ow, oh, frame의 네이티브 픽셀 포맷, WICBitmapCacheOnLoad, &bmp)`.
4. `bmp.Lock(rect{0,0,ow,oh}, WICBitmapLockWrite)` → `stride`;
   `rotator.CopyPixels(nullptr, stride, stride*oh, ptr)` → `bmp.Unlock`.
   (기존 scaler가 rotator에서 당겨 쓰던 바로 그 픽셀을 캐시 비트맵에 물질화한다.)
5. `scaler.Fant(target)` 을 `bmp` 위에 걸고 converter → `CopyPixels`
   (fixed/aspect/color 각각).
6. scaler가 동일한 회전 픽셀을 캐시에서 읽으므로 출력은 기존 rotate→scale과
   byte-identical일 것으로 기대된다.

**미선택 사유**: 프로브 구현이 `hr=0x80070216`(포맷/stride 불일치 추정)로 실패해
**미완**이다. 또한 decode마다 풀해상도 비트맵 물질화 비용(12MP 24bpp≈36MB,
BGRA≈48MB)이 발생하고, 병렬 worker에서 메모리 압박이 될 수 있다. byte 동일성은
"rotator 출력이 캐시 비트맵과 bitwise 동일"에 의존하는데 원리상 참이나 실측 검증은
못 했다.

**재검토 조건**: 엔진 버전 상향이 불가/불허일 때, 또는 ±1 LSB조차 허용 불가일 때
최우선 재시도.

### 7.4 대안 B — WIC 재정렬(scaler → rotator) (미선택)

**알고리즘**:
1. factory → decoder → frame → `xform`.
2. `scaler.Initialize(frame, pw, ph, Fant)` (Option 1과 같은 pre-rotation 타깃;
   회전이 dims를 swap하므로 `(pw,ph) = swap ? (h,w) : (w,h)`).
3. `rotator.Initialize(scaler, xform)` → converter → `CopyPixels`.
4. 회전이 **작은 스케일 결과 위**에서 일어나므로 디코더-측 폭주가 없다(스케일은
   frame에서 직접, WIC 고속 JPEG 축소 경로 유지).

**실측**: 654~765ms/호출(콜드 아님, steady). software rotate와 0/1024 byte-identical.
**미선택 사유**: 가장 빠른 software rotate(22ms)보다 약 30배 느리다. 이득 대비 불필요.
**재검토 조건**: 수동 픽셀 코드를 제품에 남기지 않으려는 정책이 생기거나, WIC 회전
의미를 그대로 유지해야 할 때.

### 7.5 대안 C — 디코더 네이티브 transform (미측정)

**알고리즘**:
1. `frame->QueryInterface(IID_IWICBitmapSourceTransform, &tf)`.
2. `tf->DoesSupportTransform(xform)` 확인; 필요하면 `tf->GetClosestSize(w,h)`로
   지원 축소 크기 조회.
3. `tf->CopyPixels(prc, dstW, dstH, xform, dstFormat, stride, size, buffer)`.
4. JPEG 디코더가 **DCT 스케일 + 회전을 한 패스**로 수행해 중간 풀해상도 decode를
   회피한다.

**미측정 사유**: `IWICBitmapSourceTransform` 지원 여부와 결과 bytes가 코덱마다
다르고, 기존 Fant 보간 결과와 동일하다는 보장이 없다. 미측정 상태로 제품에 넣지 않는다.
**재검토 조건**: 코덱별 지원과 bytes parity가 확인될 때(텔레메트리 쪽수 포함).

### 7.6 대안 D — metadata cache 옵션 (미측정)

**알고리즘**: `CreateDecoderFromFilename`의 마지막 인자를
`WICDecodeMetadataCacheOnDemand` → `WICDecodeMetadataCacheOnLoad`로 변경.
**미측정 사유**: 메타데이터 파싱 시점만 바뀌고 회전 경로와 무관하다. 회전 폭주를
설명하지 못한다.
**재검토 조건**: 메타데이터 읽기 비용 문제가 별도로 재발할 때.

## 8. 향후 영향 및 한계

- orientation 대상 이미지의 fingerprint가 최대 ±1 LSB 바뀔 수 있어
  `kEngineVersion`을 patch 상향했다. 다음 스캔에서 저장 쌍이 자동 재검증된다.
- 썸네일 color lane(`decodeColorAspect`)도 같은 수정을 받아 회전 이미지 표시도
  빨라진다.
- **이번 빌드가 다루지 않은 것**: 이미지 stage의 나머지 I/O·decode 비용
  (이미지 1장당 3회 WIC decode). decode-once(3→1)는 여전히 0.9.4.80이 남긴
  후보이며, 본 수정은 회전 이미지 폭주라는 국소 원인만 제거한다.
- walk 8368s(실제로는 walk+consume 단계 wall)와 매칭 818s는 본 수정의 대상이
  아니다.
