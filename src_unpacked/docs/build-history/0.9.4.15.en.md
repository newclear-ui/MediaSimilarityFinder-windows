# v0.9.4.15 — Node D1a Image-Path Observability

## Status
Implementation complete; validation **PASS** (confirmed in 0.9.4.16).

Baseline: v0.9.4.14. Official preserved baseline v0.9.2.32 unchanged.

## Scope
Instrument the existing MediaPipeline::imageBatch() synchronous boundary using existing BenchmarkRecorder telemetry.

D1a observations:
- image batch count
- total batch items
- active batch depth
- image packing duration
- CPU hash duration
- existing GPU batch duration remains available

No new CPU/GPU execution queue is introduced.

## Guardrails
Scheduler share policy, Profile/Calibration, CUDA backend architecture, video, similarity, DB/cache, and CPU fallback semantics are unchanged.

Transfer timing remains **not_measured** until backend-internal timing hooks exist. The elapsed time of hashBatch() is not labeled as transfer time.

## Validation
CPU Release build PASS, **CTest 66/66 PASS**. GPU Release build PASS,
**CTest 67/67 PASS** (full logs kept). `--version` on both confirmed
after the 0.9.4.16 sweep, `--smoke` PASS.

Findings confirmed during validation (0.9.4.16 gate record):
- packMs is measured after decode, so decode is excluded (corrected in
  ed6f335).
- cpuHashMs is executed CPU hash work: result-determining hashes on the
  CPU path, mirror-only work included on the GPU path. A separate field,
  so no double count inside any single field.
- batchMaxDepth is structurally always 1 today (one in-flight batch per
  recorder). Recorded as an architectural fact, not a stub; the counter
  gains meaning when D3 introduces queues.
- batchItems counts attempted inputs (may include decode failures) —
  read apart from completed counts.
- transfer stays not_measured. Schema raised to v3 for the 6 added keys
  (0.9.4.16).
