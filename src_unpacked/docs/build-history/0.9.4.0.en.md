# MediaSimilarityFinder v0.9.4.0 — Node A: Foundation / Terminology / Instrumentation

Validation baseline for Node A of the 0.9.4 development line: top-level GPU
terminology cleanup, GPU ON/OFF structure, build naming cleanup, and the
shared benchmark instrumentation foundation. Engine 1.5.0, DB 1.0.3, and
video cache v9 are unchanged.

## Why the change was needed
- Through 0.9.3.19, "GPU" meant NVIDIA CUDA across the product, and users
  were exposed to a manual GPU 25/50/75/100% control. There was no
  instrumentation structure for the Adaptive Scheduler (Node B) or
  calibration (Node C) to build on.
- Unmeasured values were stored as numeric zero (`resources.samples = 0`,
  `diskAvailable: false` next to a valid volume string), so "actually zero"
  and "never measured" were indistinguishable (a Roadmap A exit violation).

## Previous structure
- Single `MSF_ENABLE_CUDA` option, `build-windows-cuda` tree, and a
  `GpuBackend` wrapping the CUDA implementation directly (no upper
  abstraction names).
- `ResourcePolicy.gpuPercent` plus a toolbar `GPU %` spinbox (direct user input).
- Benchmark JSON with no schema version, a single `completed` boolean, one
  `frames` counter, and no scheduler/calibration record structure.

## New structure
- GPU abstraction: `GpuBackendKind { Auto, Cuda, Cpu }` plus `backendName()`.
  Auto resolves to CUDA when a device exists, otherwise CPU fallback.
  Unimplemented backends (Vulkan/HIP/Level Zero) appear nowhere in code or UI.
- CMake: `MSF_ENABLE_GPU` + `MSF_GPU_BACKEND` (AUTO/CUDA/CPU) are canonical.
  `MSF_ENABLE_CUDA` stays as a deprecated compatibility alias, and
  `MSF_HAS_GPU` is defined alongside `MSF_HAS_CUDA`. New `windows-gpu`
  preset plus `scripts/build_windows_gpu.ps1`; `build-windows-gpu` is
  created by clean configure. The existing `build-windows-cuda`
  tree/preset/script are preserved untouched.
- UI: toolbar `GPU %` spinbox removed. Only the GPU ON/OFF checkbox remains.
  CPU preset values, Custom CPU input, and monitor-gate semantics are
  unchanged; the internal `gpuPercent` cap stays frozen (deprecated) until
  the Node B scheduler replaces it.
- Benchmark: independently managed `schemaVersion: 1` + `runId`.
  `measured / not_measured / not_available / partial / failed / fallback`
  states via `MeasureState`; unrecorded numbers export as `null` + state.
  Split `decodedFrames`/`sampledFrames` (a cache hit records decoded 0 as
  measured and an unknown sample plan as unmeasured), a `stages` object
  (`enumeration` … `revalidation`, unrecorded = `not_measured`),
  `scheduler`/`calibration` structures (filled by Nodes B/C, currently
  `not_measured`), `cancelled / paused / failed / failedStage /
  completionReason / files{started,completed,remaining}`, and disk
  availability latched from the sampling period. All existing keys are kept,
  so old parsers do not break.
- About text `(CPU/CUDA)` corrected to `(CPU/GPU)` (CUDA is not a generic name).

## Why this shape
- The goal is foundation, not behavior change, so verdict-touching code is
  untouched; only additive structure and instrumentation were added. The
  internal `gpuPercent` cap was deliberately not deleted yet (removal belongs
  with the Node B scheduler).
- The new GPU tree uses clean configure because reusing a renamed old tree
  risks CMake cache contamination, per the roadmap warning.

## Resolved state
- All 8 Node A exit items pass (terminology split, ON/OFF structure,
  unmeasured-zero removal, CPU fallback, regression green, build/CMake
  cleanup, version alignment).
- The `diskAvailable: false`-with-valid-volume symptom (root cause: first
  collection failure treated as fatal, fixed in 0.9.3.19) is now further
  distinguishable on recurrence via the `diskState` latch.

## Accuracy impact
- None. Fingerprint, similarity, threshold, cache, and timestamp paths are
  untouched. `benchmark_test`, `search_engine_test`, `video_scan_e2e_test`,
  `match_revalidate_test`, and `scan_pipeline_test` pass on both trees.
- Benchmark ON/OFF still cannot change verdicts; the added instrumentation
  is read-only accumulation plus JSON serialization.

## Compatibility impact
- Benchmark JSON is an additive extension. Existing keys kept, new keys
  added. `schemaVersion` starts at 1, independent of engine/DB versions.
- `MSF_ENABLE_CUDA`, the `windows-cuda` preset,
  `build_windows_cuda.ps1`, and the old `ScanWorker` constructor stay as
  deprecated compatibility paths.

## Validation
- CPU Release build PASS, **CTest 62/62 PASS**, `--version` 0.9.4.0,
  `--smoke` PASS.
- GPU (`build-windows-gpu`, clean configure) Release build PASS,
  **CTest 63/63 PASS** (including CUDA backend discovery),

- `benchmark_test` covers schemaVersion, runId, completionReason,

## Future impact
- Node B only needs the adaptive formula filling `SchedulerTelemetry`.
  Node C layers `CalibrationTelemetry` plus the INI profile on top.
- Further versions are assigned 0.9.4.1 → … as validated states emerge.
  Roadmap nodes and version numbers must not be confused.
