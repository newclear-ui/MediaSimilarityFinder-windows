## 1. 변경 필요성

v0.9.4.40(E-2B)에서 exact sparse seek 의 pixel parity 가 13/14 로 올라갔다. 남은 1건은 HEVC 1080p 이었고, v0.9.4.41(E-3A)에서 HEVC 가 sparse 로 exact 하지 않음이 확정되어 `HEVC = SequentialPreferred` 로 닫았다.

남은 의문은 하나였다. **H.264 에서 sparse seek 는 production 결과와 정말 같은가.** E-3B 는 이 질문만 다룬다.

## 2. 기존 구조

- `VideoFingerprintEngine::build()` 는 `VideoDecoder::framesAt96Plus32()` 만 호출했다. 이 함수는 파일 처음부터 순차 디코딩을 한 번 하고, 각 target 에 대해 `ft + 0.05 >= target` 을 처음 만족하는 frame 을 고른다. 두 개의 resolution(96x96, 32x32)을 **한 번의 순차 스윕**으로 얻는다(과거 2-스윕은 build 시간의 약 50%였음).
- sparse seek 는 `VideoDecoder::framesAt96Plus32ExactSparse()` 로 E-2B 에서 추가되었으나 **production 에서 호출되지 않았다**. probe 전용이었다.
- E-2A/E-2B 의 exactness 측정은 **probe 내부의 seek 기반 구현끼리** 비교했다.

`MSF_VIDEO_SAMPLING` = `off`(기본) / `adaptive` / `forced-sparse`.
`forced-sparse` 는 **진단용**이며 cost 판정만 건너뛴다. exactness policy 와 executor contract 는 건너뛰지 않는다.

## 4. 해결된 상황

### 4-1. 자기참조 exactness 측정 (핵심 발견)

E-2A 는 "bit-identical 1/1", E-2B 는 "pixel parity 13/14" 로 보고했다. 그러나 두 실험 모두 **seek 기반 구현을 다른 seek 기반 구현과 비교**했다. 두 구현 모두 `av_seek_frame` + `avcodec_flush_buffers` 를 호출하므로 **똑같은 decoder reference state 손실을 공유**했고, 따라서 **틀린 이유로 일치**했다.

E-3B 가 처음 만든 e2e 테스트는 production 의 from-zero 스윕을 포함했고, 4K H.264 1개에서 **실제 불일치**가 나타났다. 실행 로그에 `reference count overflow` / `no frame!` / `concealing ... errors` 가 동반된다. 즉 seek 경로는 from-zero 스윕과 **다른 frame을 재구성**한다.

이것은 "sparse seek 가 느려서 안 된다"가 아니라 **"sparse seek 가 정확하지 않음이 증명되었다"** 이며, 두 판정은 전혀 다른 결론이다.

### 4-2. 발견·정정한 실제 결함 3건

| # | 결함 | 정정 |
|---|---|---|
| ① | executor 가 `return !out32.empty()` 로 **truncated 결과를 성공으로 반환**. read 가 target 에 도달하기 전에 끝나면 hash 집합이 production 보다 적어진 채 성공으로 취급 → 검색 결과가 바뀜 | `out96.size()==seconds.size()` / `out32.size()==seconds.size()` contract 추가, 위반 시 폐기 후 `false` |
| ② | container-index GOP 을 `GopConfidence::Known` 으로 보고. 4K H.264 실제값은 index ≈109 vs decoded I-frame ≈120 로 **불일치** | `Estimated` 로 하향. `Known` 은 decoded I-frame 으로 교차 확인된 경우만 허용 |
| ③ | 내가 추가한 `0.5 × framesPerSample` threshold — brief 가 금지한 "단순 threshold" 이자 calibration 데이터와 **모순** (E-2A 는 5s/25fps/gop11 을 +72.7% win 으로 측정) | 제거. `sampleCount × (GOP/2) < totalFrames` 비교만 사용 |

③ 은 selfcheck 이 잡아낸 것이다. 실측 5건과 모두 일치시킨다:

| 파일 | frames/sample | sparse work vs sequential work | 실측 | 판정 |
|---|---|---|---|---|
| gop250 | 46.8 | 2000 vs 750 | 손해 | Sequential |
| gop225 | 53.1 | 1912 vs 902 | 손해 | Sequential |
| gop60 | 46.9 | 480 vs 750 | 이익 | Sparse |
| gop30 | 56.2 | 240 vs 900 | 이익 | Sparse |
| gop11 | 20.8 | 33 vs 125 | 이익 | Sparse |

### 4-3. production 판정

`ExactnessPolicy::RefuseAll` 을 기본값으로 도입했다. production-parity 증명이 있는 codec 이 하나도 없으므로 **모든 파일이 Sequential** 이고, sparse 는 production 에서 **도달 불가**다.

이것은 영구 기각이 아니라 **증거의 부재**다. 어떤 codec 에 production-parity 증명이 기록되면 `AllowVerified` 로 바꾸는 1줄 변경이다.

### End-to-end wall clock (수정 후, median of 3)

| mode | median ms | vs off |
|---|---|---|
| off | 36285 | — |
| adaptive | 36277 | **-0.02%** (중립) |
| forced-sparse | 36316 | +0.08% |

adaptive 가 중립인 것은 이제 항상 Sequential 을 고르기 때문이다. **성능 개선이 아니다.** 정확성을 지키면 남는 것이 중립이라는 점이 이 노드의 결론이다.

> **측정 잡음에 대한 주의**: 반복 실행 간 wall clock 이 34,722 ~ 46,753 ms 로 크게 흔들렸다(동일 binary, 동일 dataset). 즉 이 수치는 **noise-dominated** 이며 ±20% 수준 변동을 포함한다. 반복 재측정에서도 adaptive/off 비는 방향이 일정하지 않았다. 따라서 "이득이 정확히 0" 이 아니라 **"재현 가능한 이득이 없다"** 로 기록하는 것이 맞다. exactness 쪽(0 mismatch)은 모든 반복에서 결정적으로 일관됐으므로 이 수치와 무관하게 신뢰한다.
>
> pre-fix 의 +17.38% 역시 단일 실행이므로 **비율 자체를 확정 수치로 취급하지 않는다.** 다만 그 실행에서 exactness 위반이 동시에 발생했고, 위반은 잡음과 무관하게 재현적이므로 **기각의 근거는 정확성 쪽**이다.

## 6. 향후 영향

- **E 노드 미완료.** E-3B 는 end-to-end exactness 를 **증명하지 못했다**. sparse 를 채택할 근거가 없다.
- **production 동작은 v0.9.4.41 과 동일.** 기본값 Sequential, 결과 bit-identical.
- **재검토 조건** — 아래 중 하나가 충족되면 `AllowVerified` 로 전환을 검토한다.
  1. seek+flush 없이 decoder reference state 를 보존하는 방법이 확보될 때 (예: keyframe 에서 decoder 를 재구성하지 않는 패킷 단위 처리)
  2. `AVSEEK_FLAG_ANY` 가 H.264 exactness 를 깨뜨리지 않으면서 HEVC 문제를 풀 때 — E-3A 에서 이미 악화됨이 측정됨
  3. HEVC/H.264 외 codec 에서 production-parity 증명이 기록될 때
  - 코드·compiler·FFmpeg·dataset·build configuration 이 바뀌면 무효화된 수치다. 어느 조건에서도 **E-2A/E-2B 의 13/14 수치를 production exactness 근거로 재사용하지 않는다.** 그 비교는 자기참조였다.
- **methodology 교훈**: exactness 를 증명하려면 기준선은 반드시 **production 경로**여야 한다. 같은 계열의 재구현끼리 비교하면 공유 결함을 서로 검증하지 못한다. e2e 테스트는 A vs A control 을 항상 함께 돌린다.
- `ExactnessPolicy` 는 프로세스 전역이다. policy 가 `RefuseAll` 인 동안 `forced-sparse` 조작으로 production 결과를 바꿀 수 없다.

## 6-1. Node E 종결에 따른 E-3C / E-4 처리 (사용자 결정)

`RefuseAll` 로 sparse production path 가 도달 불가능한 현재 구조를 기준으로:

- **E-3C**: 별도 roadmap Stage 로 승격하지 않는다. F 로 이관하지 않는다. Node E 종결
  범위에서 정리한다. 향후 F architecture 에 참고가 될 수 있다는 사실만 참고사항으로
  기록하며, 작업 항목으로는 이관하지 않는다.
- **E-4**: production integration + end-to-end validation 역시 Node E 종결 범위에서
  정리한다. `RefuseAll` 하에서는 통합할 "성격의" 경로가 남아 있지 않다.
  **E-4 를 sparse 재도입 근거로 읽어서는 안 된다.**
- 본 빌드에서 `src/video_sampling_planner.h` 의 E-3C 관련 **코드 상태는 변경하지
  않았다.** 필요 여부는 별도 판단 대상이다.
