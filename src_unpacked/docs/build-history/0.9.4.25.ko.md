# MediaSimilarityFinder v0.9.4.25 — D9b Expensive Verification Cost Reduction

## 0. Status

**PRE-REGISTER.** 코드 변경 전 기록이며 아직 PASS 가 아니다.
완료 · 검증됨 · 성능 향상 확정은 모두 구현과 측정 이후에만 쓴다.

Engine 1.5.0 · DB 1.0.3 · cache v9 **불변**.
**verdict semantics · candidate generation semantics · similarity threshold ·
CPU/GPU 판정 의미 모두 변경하지 않는다.**

> 이 문서는 코드 변경 전에 작성되어 커밋 순서로 감사 가능하다.

## 0-1. Change Need (변경 필요성)

D9a 가 실측으로 확인한 사실:

```
analyze            엔진 wall 의 99.67 %
  └ verify         99.67 % 안에 99 % 이상
expensive verify   13,734 건 × 약 8.5 ms = 약 117 s
```

즉 **전체 스캔 시간의 거의 전부를 13,734 건의 expensive verification 이
소모한다.** 이 중에는 같은 원본에서 반복 계산되는 버퍼 준비가 포함되어
있으므로, 그 중복을 제거하면 판정 결과를 바꾸지 않고 비용을 줄일 수
있을 것으로 본다.

## 1-1. Scope (변경 허용 범위)

- verify 경로 내 **중복 decode 제거** (같은 verify 작업 안에서 동일 이미지

- **SSIM 입력 준비 최적화** (resize / copy / format conversion / temporary
  allocation) — **SSIM 공식 자체는 불변**

## 1-2. Non-goals (하지 않는 것)

## 2. Hypothesis

> expensive verify 경로에서 **동일한 판정에 필요한 decode/buffer/SSIM 입력을
> 재사용하거나 불필요한 중복 작업을 제거**하면, verdict semantics 를 유지하면서
> expensive verify 의 평균 처리시간을 감소시킬 수 있다.

### 가설의 코드 근거 (D9a 계측이 가리킨 지점)

`src/image_verify.cpp::verifyImagePair()` 는 호출 1건마다:

```cpp
verifyBuffersFor(pathA, fA, aA, tel)   // decode 2회 (64x64 full + aspect)
verifyBuffersFor(pathB, fB, aB, tel)   // decode 2회
ssimBuf(fA, fB)                        // 1회
fullA = centerCropResize(aA, ...)      // 1회
fullB = centerCropResize(aB, ...)      // 1회
for (asp : {4/3, 1, 9/16}) {
  rA = centerCropResize(aA, asp)       // 1회
  rB = centerCropResize(aB, asp)       // 1회
  ssimBuf(rA, rB) / ssimBuf(fullA, rB) / ssimBuf(rA, fullB)   // 3회
}
```

따라서 호출 1건당:

```
centerCropResize   2 (full) + 3 x 2 (aspect) = 8회   ← 매번 새로 계산
ssimBuf           1 + 3 x 3 = 10회
  └ flipBuf       ssimBuf 마다 1회 → 10회          ← 매번 새로 계산
  └ frame_ssim    ssimBuf 마다 2회 → 20회
```

**D9a 실측이 확인한 중복**: `ssimBuf` 10회 중 9회가 aspect 조합이며,
동일한 `GrayImage` 가 반복 재계산된다. `flipBuf` 는 `ssimBuf` 마다 새로
만들어지지만, `b` 쪽 flip 결과는 aspect 내에서 동일할 수 있다.

### 측정 가능한 예측 (pre-register)

만약 가설이 맞다면 구현 후 관측되어야 하는 변화:

```
frame_ssim 호출 수 감소   (buffer 재사용이 실제로 중복을 제거한다면)
centerCropResize 호출 감소
ms per expensive verify 감소
```

**변하지 않아야 하는 것 (이것이 성공의 핵심 조건)**

```
verifyCalls                     158,020   (동일)
expensive verify count           13,734   (동일)
verifyHitRate                     0.5286  (동일 — buffer 조회 횟수 불변)
groups                          156,152   (동일)
verdict / similarity 결과        동일 (bit-level 비교)
```

## 4. Risk (판정 로직을 안 바꾼다고 안전하다고 가정하지 않는다)

| 위험 | 설명 |
| --- | --- |
| **verdict semantics 변경** | SSIM 입력 순서/내용이 미세하게 달라지면 `0.5*hamming + 0.5*SSIM` 결과가 변해 임계값 판정이 흔들릴 수 있다 |
| **CPU/GPU parity 변화** | 해시 경로와 verify 경로의 결과 불일치 |
| **image similarity 결과 변화** | 같은 이미지가 다른 점수를 받을 수 있음 |
| **stale/incorrect buffer 사용** | 재사용 캐시가 다른 파일의 디코드 결과를 참조 |
| **decode 결과와 SSIM 입력 불일치** | full/asp 두 버퍼의 대응 관계가 깨질 수 있음 |

→ 이 위험들이 **실제로 없음을** 구현 후 측정으로 증명해야 하며,
코드 리뷰만으로 안전을 주장하지 않는다.

다음 중 하나가 발생하면 해당 optimization 을 중단한다.

```
1. verdict 또는 grouping 결과가 변경됨
2. CPU/GPU parity 가 깨짐
3. decode 결과가 달라짐
4. CUDA correctness 문제가 발생
5. 측정 신뢰성이 확보되지 않음
6. 최적화가 복잡성만 높이고 measurable benefit 이 없음
```

### 9.3 왜 실패했는가 (측정 기반 원인)

D9a 의 가설은 "`ssimBuf` 10회 중 9회가 aspect 조합이며 동일 `GrayImage` 가
반복 재계산된다"는 것이었다. 이 **관찰은 맞았으나, 관찰이 지배 비용이라는
추론이 틀렸다.**

실제 비용 구조 (호출당):

| 작업 | D9a (reference) | D9b (optimized) | 감소 |
|---|---:|---:|---:|
| `centerCropResize` | 8 | **6** | -2 |
| `ssimBuf` | 10 | 10 | 0 |
| `flipBuf` | 10 | 10 | 0 |
| `frame_ssim` | 20 | 20 | **0** |
| `frame_ssim` inner loop (4,096 ops 각) | 81,920 | **81,920** | **0** |
| `centerCropResize` 픽셀 (1,024 각) | 8,192 | 6,144 | -2,048 |

`frame_ssim` 이 64×64 입력에서 8×8 윈도우 64개 × 64픽셀 = **inner loop
4,096회**를 도는 것이 비용의 사실상 전부다. D9b 는 `centerCropResize`
8,192 → 6,144 (전체 작업의 2.3%)만 줄였고, **81,920 ops 는 그대로**다.

**즉 가설이 지목한 "중복"이 존재하지 않았다.** D9b 는 이미 `rA`/`rB` 를
루프 밖에서 한 번만 계산하고 있었고(원본 코드 기준), `verifyScorePlanImpl` 의
재사용은 그 결과를 3회 `ssimBuf` 에 넘길 뿐이었다. 원본도 이미 이 정도의
재사용을 하고 있었다.

### 9.6 다음에 배워야 할 것

이 실패는 **위험하지 않았지만 가치도 없었다.** D9b 는 성공 조건을 충족하지
못했으므로 **0.9.4.25 는 Candidate B 실패 기록으로 확정**한다.

진짜 남은 질문:

```
Q1. 8.5 ms 를 구성하는 실제 비용은 무엇인가?
    → 13,734 × 8.5 ms 의 시간은 어디에 쓰이는가

Q2. frame_ssim 자체를 줄일 수 있는가?
    → 윈도우 수/크기, 정밀도, early-exit 은 모두
      결과에 영향을 줄 수 있어 별도 pre-register 필요
```

**후보 A(candidate 도착률 감소)는 여전히 deferred** 이며, 이 실패는
A 의 우선순위를 상대적으로 올리지 않는다. A 가触及하는 것은
verdict semantics 이기 때문이다.
