# MediaSimilarityFinder v0.9.2.45 — Scan Activity Log (0% CPU Triage)

## Need for change
For the "0% CPU/GPU with only disk reads" report, an engine audit ruled out gates and deadlocks (`expensiveStageGuard` is monitor-only, never set on scan workers; `stopped()` and thread wiring correct). No remote way existed to distinguish the remaining hypotheses (23-minute walk / re-scan skip / single-file stall). A worker replica probe (3,000 files, 641,358 matches) confirmed correct behavior.

## Previous structure
In-scan UI display was purely callback-driven, so the screen looked fully frozen whenever no callback arrived (walk phase, single-file stall).

## New structure
- UI timer (600 ms) writes a heartbeat every 10 s while scanning: elapsed, last progress, last file, group count. It runs on the GUI thread independent of the worker, separating stalls from crashes
- Scan start/finish/failure appended to `%TEMP%\msf_scan.log`
- Version strings unified → 0.9.2.45

## Resolved situation
- With the user's log file: halted heartbeat = wedged/crashed process, one file stuck for tens of minutes = bottleneck file identified, advancing counter = slow but healthy

## Validation
- Core Release build: PASS, **CTest 39/39 PASS**, `--smoke` exit 0, `--version` 0.9.2.45

## Future impact
- Log stays for diagnosis. Once a stall file is identified, timeout/skip handling for its format goes in a separate version
- Reference measurements: 272k-file walk 23 min (196 files/s). Near-0% GPU is normal by design (tiny hash batches) — actual GPU use is proven by the `gpuImages` counter
