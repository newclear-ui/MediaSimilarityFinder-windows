# MediaSimilarityFinder v0.9.4.145 — Failed-file count in the summary "total" line

Baseline `0.9.4.144` → this build `0.9.4.145`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged (telemetry additive key).

## 1. Why

- 0.9.4.144 added the failed-file list/reasons, but the **summary "total" line** showed only scanned/analyzed/groups/duplicates, so the failure count was not visible at a glance.
- Request: show `total scanned: 39 analyzed: 38 dup groups: 0 dup files: 0 failed files: 1`.

## 2. Previous structure

- Telemetry `summary` had `scanned/analyzed/unchanged` only; the failure count was not stored (only the per-file list from 0.9.4.144).
- The dialog total line showed only totals/groups/duplicate files.

## 3. New structure

- `TelemetryRecorder` gains a **total failure count** (`failedCount_`), independent of the per-kind list cap (50).
- JSON `summary.failedFiles` (additive, schema 9 unchanged).
- The detailed-log total line adds `failed files: N` (key `detailLogFailedShort`).
- The per-file "Failed files (img/vid)" section (0.9.4.144) stays.

## 4. Result

- The summary line shows the failure count, and the section below names the files and reasons.
- JSON consumers can use `summary.failedFiles` (total) together with `images/videos.failedFiles` (details, max 50).

## 5. Verification

```text

```

- `analysis_failure_state_test`: `summary.failedFiles == 1` plus the path/reason.

- Field: scanning `broken.jpg` shows `failed files: 1` in the total line and `empty file — D:\...\broken.jpg` in the section.

## 6. Impact and limits

- The count increments in the per-file failure branches (independent of the list cap).
- Reasons use the same heuristic as 0.9.4.144; schema/protocol/engine versions unchanged.
