# MediaSimilarityFinder v0.9.4.3 — Node B2: Runtime Throughput Feedback

B2 검증 기준점. brief §6의 입력(CPU/GPU recent throughput과 effective
capacity)을 추가한다. 엔진 1.5.0·DB 1.0.3·캐시 v9·schema 1 불변.

## 변경 필요성
- B1의 용량은 정적 프록시라 실행 중 실제 속도와 어긋나도 배분이
  바뀌지 않았다. 관측 기반 effective capacity가 B2의 범위다.

## 기존 구조
- `SchedulerHardware`에 throughput 입력이 없고, `current*Capacity`는
  baseline을 그대로 반복했다.

## 변경 구조
- `ThroughputWindow` (30초 recent-window, 2표본 미만·전체 만료 시
  unknown 반환, smoothing 없음 — B4 범위).
- `SchedulerHardware`에 `cpuRateKnown/cpuRate/gpuRateKnown/gpuRate`
  추가(이미지 경로 images/sec, unknown은 0이 아님).
- 판단 규칙: 양쪽 실측이 있고 0 초과면 관측 비율로 배분(reason
  `observed_throughput`), 그 외 baseline 경로 유지. 한쪽 미상은 0으로
  취급하지 않고 baseline으로 폴백한다.
- 엔진: 이미지 배치마다 완료 이미지를 해시 backend별로 귀속시켜
  윈도우에 push하고, 재평가 전에 rate를 hw에 갱신한다. 비디오는
  제외한다(디코드 측은 C/E 영역임을 명시).
- `currentCapacities()`: 양쪽 실측이면 rate, 아니면 baseline을
  telemetry에 기록한다. B3의 smoothing 대상이 된다.
- 테스트는 `scheduler_test` 안에 확장(신규 바이너리 없음, 수량 불변).

## 선택 이유
- 관측 비율은 동일 단위(images/sec)라 정규화 매직이 없다. baseline과
  관측을 섞지 않고 전환하는 단순 규칙이 B2의 전부이며, 블렌딩·스무딩은
  B4에서 다룬다.
- 비디오는 파일당 수초라 recent 신호로 부적합하고, 귀속도 CPU/디코더와
  얽혀 있다. 이미지 경로로 한정한 것은 범위 준수다.

## 해결된 문제
- 스케줄러가 실행 중 관측을 입력으로 받는다. B3는 부하 신호만 얹으면 된다.

## 정확성 영향
- 없음. 게이트 위치·판정 경로 무변경. 실측 미달 구간은 B1과 동일하게
  동작한다. 양쪽 `scan_workflow_test` 동일 결과로 parity 입증.

## 호환성 영향
- Benchmark JSON 키 불변, scheduler 섹션의 current 용량이 실측 단위로
  채워질 수 있다(단위 명시는 telemetry 설계의 몫, C에서 정식화).
