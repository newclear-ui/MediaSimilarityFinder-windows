# MediaSimilarityFinder v0.9.4.82 — EXIF-rotated image WIC FlipRotator runaway removed

Baseline `0.9.4.81` -> this build `0.9.4.82`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.0 -> 1.5.1` / `kDatabaseVersion 1.0.5` /
`kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9`.
Verdict rules, thresholds, weights and gates are unchanged. The engine patch bump
exists because **fingerprints of EXIF-rotated images change by up to +/-1 LSB**, so
stored pairs must revalidate on the next scan (engine-version rule 5).

## 1. Why it was needed

The baseline is the user's report of a large scan on `G:\Downloads\ss_twit`
(177,120 images, high-latency drive) with build 0.9.4.79.

- Total 177m 45.6s. Image stage 7037.9 s (117 min), matching 818.2 s.
- CPU avg 20.6% / max 119.4%, GPU duty 0.0% -> effectively I/O and decode wait.
- `Slowest files (img)` top five are **343-480 s each** (about 5000x the 77.58 ms
  mean decode).
- The files are healthy (0.88-2.1 MB, EOI present, GDI+ full decode 30-60 ms,
  raw read ~10 ms).

Probes reproduced it: all five are **EXIF orientation=6 + 12 MP**
(4000x3000 / 4032x3024), and the bottleneck is neither the disk nor the file but
the **product WIC decode path**.

## 2. Previous structure

Both WIC paths in `image_decoder.cpp` inserted an **`IWICBitmapFlipRotator`
between the decoder and the scaler** whenever EXIF orientation was not identity:

- `decodeWicBranches` (shared by decode / decodePreserveAspect / decodeBoth)
- `decodeWicFileAspectColor` (decodeColorAspect / thumbnail color lane)

`media_pipeline.cpp` decodes each image **3 times** through this path (pass1
32x32, crop decodePreserveAspect 128, decodeColorAspect 128).

With a `WICBitmapScaler` in `WICBitmapInterpolationModeFant` sitting above a
`FlipRotator`, WIC loses the JPEG fast scaled-decode path and runs the
full-resolution path instead. Probe (same file, no rotation):
`CopyPixels` = **150,916 ms (rotator->scaler) vs 22 ms (scaler only)**.

## 3. Change

A new `applyOrientationPixels(px, w, h, channels, xform)` is added in
`image_decoder.cpp` (inside the `#ifdef _WIN32` block) and orientation is moved to
**after scaling**.

- Order: derived by measuring WIC's composition on a synthetic pattern —
  **FlipHorizontal first, then rotation (90/180/270)**. EXIF 5/7
  (rotation+flip) match this too.
- `decodeWicBranches`: `src = frame` (no rotation). When orientation is 90/270
  the oriented w/h are swapped to compute the aspect size and a **pre-rotation
  scale target** (scale to `(h,w)` so rotation yields `(w,h)`). After
  `CopyPixels`, `applyOrientationPixels` rotates. `orientApplied` is preserved
  per the existing contract.
- `decodeWicFileAspectColor`: identical, applied to the BGRA output with
  `channels=4`.

Rotation is a pure pixel permutation, so applying it to the **scaled buffer** is
byte-identical to applying a `WICBitmapFlipRotator` to the scaled source, and
differs from the old "rotate at full resolution, then scale" by **+/-1 LSB on
88/1024 pixels** (Fant interpolation ordering).

## 4. Result (measured)

The five slow files re-measured through the fixed product decoder (per call):

```text
decode32 / aspect128 / color128  = roughly 18-30 ms each (about 70-80 ms per file)
before the fix: about 450 s per file  ->  about 6000x
```

## 6. Performance experiment record (AGENTS rule 9)

- **Experiment ID**: P-0.9.4.82-fliprotator-runaway, P-0.9.4.82-orient-after-scale
- **Version**: 0.9.4.82. **Date**: 2026-10-10.
- **Purpose**: Identify and remove the cause of per-image times of hundreds of
  seconds on a large scan.
- **Hypothesis**: The slow files are not a disk/file problem but a WIC decode
  rotation (FlipRotator) runaway.
- **Dataset**: Top five files from the `G:\Downloads\ss_twit` report (all
  orientation=6, 12 MP). A random 500-file sample contained 0 rotated images, so
  the pathological set is very small.
- **Hardware/OS**: Windows, local. Build: CPU/GPU Release.
- **Raw measured values**:
  - Non-rotated 12 MP: CopyPixels 22 ms.
  - orientation=6 12 MP: rotator->scaler (old) **150,916 / 151,563 / 156,374 ms**
    (repeated runs), scaler only 22-27 ms, scaler->rotator (WIC reorder) 654-765 ms.
  - software rotate vs old (rotator->scaler): 88/1024 pixels +/-1.
  - software rotate vs WIC reorder: **0/1024 (byte-identical)**.
  - after the fix, product: about 70-80 ms per file.
- **Verdict / Status**: **PASS** (performance); verdict parity handled by the
  engine patch bump + revalidation.
- **Known limitation**: Rotated-image fingerprints differ from before by up to
  +/-1 LSB (Fant interpolation ordering); direction and geometry are exact.
- **Future revisit condition**: Re-measure if a WIC/Windows update changes the
  FlipRotator performance characteristics; review the "rotate after scale"
  principle if other decoder paths (GPU/NVDEC) are added.
- **Related experiments**: 0.9.4.29 (D3 duplicate decode), 0.9.4.80 (decode-once
  candidate).

## 7. Why option 1 was chosen + unselected alternatives (detailed algorithms)

Per the user directive, alternatives not chosen this time are **not deleted**;
they are recorded with their detailed algorithm, evidence and revisit conditions,
together with the reason option 1 (scale-first + software rotate) was chosen.

### 7.1 Why option 1 was chosen (scale-first + software rotate)

1. **Performance**: per rotated 12 MP image, measured software rotate 22 ms,
   WIC reorder (B) 654-765 ms, old (rotator->scaler) 151 s. Option 1 is the fastest
   (about 6000x over the old path).
2. **Correctness**: software rotate was **0/1024 byte-identical** to applying a
   `WICBitmapFlipRotator` to the scaled source (B) (probe4). That is, it produces
   the same result as the WIC-native rotation, only by a different means. probe7
   confirmed 7 transforms x 7 sizes x gray/BGRA **98/98 identical**.
3. **Structural simplicity**: `IWICBitmapFlipRotator` is never created, so the whole
   class of "decoder-side rotation interaction" problems disappears. State and order
   are deterministic, and COM object-lifetime hazards do not grow.
4. **Testability**: it is a pure pixel permutation on a small buffer, directly
   verified by `xmp_orientation_test` (orientations 2..8 + combined 5/7 + geometry +
   quadrants) and probe7.
5. **Consistent coverage**: one helper handles `decode` / `decodePreserveAspect` /
   `decodeBoth` / `decodeColorAspect`, including the color lane's aspect dimensions
   (w/h swap under 90/270) with the same rule.
6. **Honest handling of the cost**: up to +/-1 LSB vs the old decode-time rotation
   (Fant interpolation ordering). Handled with the `kEngineVersion` patch bump plus
   next-scan revalidation.
7. **Versus the alternatives**: A is incomplete + heavy materialization + unverified
   byte-identity; B is byte-identical but about 30x slower; C is unmeasured and
   codec-dependent; D is unrelated. Under the current conditions option 1 is the only
   candidate satisfying speed, correctness and simplicity at the same time.

### 7.2 Option 1 algorithm (chosen, for reference)

1. `CoInitializeEx` -> factory -> `CreateDecoderFromFilename(..., WICDecodeMetadataCacheOnDemand)`
   -> `GetFrame(0)`.
2. `GetMetadataQueryReader` -> `/app1/ifd/{ushort=274}` -> `/ifd/{ushort=274}` ->
   `/xmp/tiff:Orientation` to resolve `xform`.
3. `src = frame` (no rotation object).
4. `swap = (xform & 3) in {1,3}`; oriented size `(ow,oh) = swap ? (sh,sw) : (sw,sh)`.
5. fixed: `(pw,ph) = swap ? (fh,fw) : (fw,fh)` -> `scaler.Initialize(src,pw,ph,Fant)`
   -> converter 8bppGray -> `CopyPixels` -> `applyOrientationPixels(ch=1)`.
6. aspect: compute `(w,h)` from `(ow,oh)` -> `(pw,ph) = swap ? (h,w) : (w,h)`
   -> scaler/converter/CopyPixels -> `applyOrientationPixels(ch=1)` (result dims `(w,h)`).
7. color: same as aspect but 32bppBGRA, `ch=4`.
8. `applyOrientationPixels` order: **FlipHorizontal -> FlipVertical -> rotation (90/180/270)**.
   Each step is a channel-wise pixel permutation (rotation re-arranges the buffer and
   swaps w/h).

### 7.3 Alternative A — byte-identical materialization (not chosen)

**Goal**: preserve the old "rotate at full resolution -> scale" order so verdicts stay
100% identical.

**Algorithm**:
1. factory -> decoder -> frame -> `xform` (same as option 1).
2. `rotator.Initialize(frame, xform)` (full resolution), `rotator.GetSize` -> `(ow,oh)`.
3. `CreateBitmap(ow, oh, frame native pixel format, WICBitmapCacheOnLoad, &bmp)`.
4. `bmp.Lock(rect{0,0,ow,oh}, WICBitmapLockWrite)` -> `stride`;
   `rotator.CopyPixels(nullptr, stride, stride*oh, ptr)` -> `bmp.Unlock`.
   (Materializes exactly the pixels the old scaler pulled from the rotator.)
5. Put `scaler.Fant(target)` above `bmp` -> converter -> `CopyPixels` (fixed/aspect/color).
6. Because the scaler now reads the same rotated pixels from a cached bitmap, the
   output is expected to be byte-identical to the old rotate->scale order.

**Why not chosen**: the probe implementation failed with `hr=0x80070216` (likely
format/stride mismatch) and was **left incomplete**. It also pays a full-resolution
bitmap materialization per decode (12 MP 24bpp ~ 36 MB, BGRA ~ 48 MB), which can
pressure memory across parallel workers. Byte-identity relies on "the rotator output
is bitwise identical to the cached bitmap", true in principle but unverified by
measurement.

**Revisit condition**: retry first if the engine bump is not acceptable, or if even
+/-1 LSB must be avoided.

### 7.4 Alternative B — WIC reorder (scaler -> rotator) (not chosen)

**Algorithm**:
1. factory -> decoder -> frame -> `xform`.
2. `scaler.Initialize(frame, pw, ph, Fant)` (same pre-rotation target as option 1;
   rotation swaps dims so `(pw,ph) = swap ? (h,w) : (w,h)`).
3. `rotator.Initialize(scaler, xform)` -> converter -> `CopyPixels`.
4. Rotation now happens over the **small scaled result**, so there is no decoder-side
   runaway (scaling goes directly from the frame, keeping WIC's fast JPEG scale path).

**Measured**: 654-765 ms per call (steady, not cold-start). 0/1024 byte-identical to
software rotate.
**Why not chosen**: about 30x slower than the fastest software rotate (22 ms);
unnecessary given the gain.
**Revisit condition**: if a policy appears that forbids manual pixel code in the
product, or if WIC rotation semantics must be kept verbatim.

### 7.5 Alternative C — decoder-native transform (not measured)

**Algorithm**:
1. `frame->QueryInterface(IID_IWICBitmapSourceTransform, &tf)`.
2. Check `tf->DoesSupportTransform(xform)`; if needed, query `tf->GetClosestSize(w,h)`.
3. `tf->CopyPixels(prc, dstW, dstH, xform, dstFormat, stride, size, buffer)`.
4. The JPEG decoder performs **DCT scaling + rotation in a single pass**, avoiding an
   intermediate full-resolution decode.

**Why not measured**: `IWICBitmapSourceTransform` support and output bytes vary by
codec, and there is no guarantee they match the existing Fant interpolation. It is not
put into the product unmeasured.
**Revisit condition**: when per-codec support and bytes parity are confirmed (including
the telemetry side count).

### 7.6 Alternative D — metadata cache option (not measured)

**Algorithm**: change the last argument of `CreateDecoderFromFilename` from
`WICDecodeMetadataCacheOnDemand` to `WICDecodeMetadataCacheOnLoad`.
**Why not measured**: it only changes when metadata is parsed and is unrelated to the
rotation path; it cannot explain the rotation runaway.
**Revisit condition**: if a separate metadata-read cost problem reappears.

## 8. Impact and limits

- Rotated-image fingerprints may differ by up to +/-1 LSB, so `kEngineVersion`
  was patched; stored pairs auto-revalidate on the next scan.
- The thumbnail color lane (`decodeColorAspect`) receives the same fix, so
  rotated-image display is faster too.
- **Not addressed by this build**: the remaining image-stage I/O/decode cost
  (3 WIC decodes per image). decode-once (3->1) remains the candidate left by
  0.9.4.80; this change removes only the localized rotated-image runaway.
- walk 8368 s (really the walk+consume phase wall) and matching 818 s are out of
  scope here.
