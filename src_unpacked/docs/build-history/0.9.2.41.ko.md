# MediaSimilarityFinder v0.9.2.41 — 비ASCII(한글) 파일명 크래시 수정

## 변경 필요성
사용자 실미디어 폴더(`G:\Downloads\ss_twit`, 272,183개) 샘플 테스트에서 한글 파일명의 비디오 4개가 스캔 전체를 `0xC0000409`로 종료시켰다. ASCII 15개는 모두 정상이라 파일명 인코딩 경계 문제로 좁혀졌다. 프로브로 `VideoFingerprintEngine::build()` → `std::filesystem::exists()` 호출에서 크래시함을 확정했다.

## 기존 구조
`std::filesystem::exists(p, ec)`처럼 narrow UTF-8 문자열을 직접 넘겼다. Windows에서 narrow→path 변환은 프로세스 ANSI 코드페이지(CP949)를 사용하므로, 코드페이지 밖 문자(한글 등)가 있으면 **변환 자체가 throw**한다. `error_code`는 조회 오류만 막을 뿐 변환 throw는 막지 못한다. 스캔 워커의 `std::async` 태스크에서 탈출한 예외는 `terminate()`로 프로세스 전체를 죽였다. 같은 패턴이 `video_fingerprint` 2곳, `monitor` 4곳(`isStable`, `enqueuePath`, 분석 후 stat, `fileKey`), `image_decoder` PGM 폴백, `index_manager` tmp 경로, `media_search_engine` DB/제외경로, `scanner` 타임스탬프에 있었다.

## 변경 구조
- UTF-8→`fs::path` 변환은 `path_from_utf8()`로 일원화 (`video_fingerprint`, `monitor`, `image_decoder`, `index_manager`, `media_search_engine`), 반대 방향은 `path_to_utf8()` (DB/SQLite는 UTF-8을 직접 처리하므로 그대로 전달)
- `fileKey()` 시그니처를 `const fs::path&`에서 `const std::string&`(UTF-8)로 변경하고 내부 변환. 호출부 정리
- `Scanner::stamp()`에 `error_code` 추가 (스캔 중 삭제된 파일 경쟁 시 throw 방지)
- `index_manager` tmp 경로는 `fs::path` 연산으로 유지 (`.string()+".tmp"` 폐기)
- `unicode_path_test` 추가 → 총 39종. 한글 BMP 디코드, PGM 폴백, 비디오 build 무throw, 스캐너 발견, 한글 경로 SQLite를 검증. 파일명은 UTF-8 바이트 이스케이프를 써서 소스 인코딩에 무관

## 해결된 상황
- 한글 비디오 19개 전체 분석 성공 (기존 100% 중복 1쌍 + 90.6% 유사 1쌍 발견). 280개 혼합 샘플: 275 스캔·274 분석·19 그룹, GPU 이미지 255개, 재스캔 증분 정상
- 스캔되지 않은 5개는 비미디어 확장자(`.jpe`/`.part`/무확장 3개)로 정상 제외

## 검증
- Core Release 빌드 PASS, **CTest 39/39 PASS** (신규 `unicode_path_test` 포함)
- 사용자 폴더 샘플 실측 + ASCII/한글 대조 프로브. Linux 경로 동작 불변 (`path_from_utf8`는 비Windows에서 그대로 전달)

## 향후 영향
- Windows의 모든 narrow 경로 경계는 `path_from_utf8()` 사용이 규칙. 신규 파일 I/O 코드는 한글 파일명 테스트 케이스와 함께 작성
- GUI는 `QString` 기반이라 영향 없음. 테스트 픽스처의 비ASCII 이름은 바이트 이스케이프로 유지
