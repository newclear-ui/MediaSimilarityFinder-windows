## 1. Corrections

### 1-A. "Whole dataset" wording error → fixed

```text
Original record (v0.9.4.33):
  "f/a geometry and byte identity across the whole dataset, 849/849"

Cause:
  runFull() actually collected only the files under images/format plus a ~200
  file BMP stride sample. files_collected=854. So the 3,347-file standard
  dataset was never swept; the 849 comparable files formed a probe corpus that
  contains many tiny 8x8 BMPs, so its cost distribution differs from the full
  dataset too.

Corrected (v0.9.4.34):
  the whole standard dataset is collected by a recursive walk and deduplicated
  by canonicalRelativePath. Stride sampling is removed.
  files_collected=3347, unique_files=3347, duplicate_paths=0
  dataset_matches_standard=yes (3347 / 102475315 / e8f8fa6a..e2640a)

Reason:
  "whole dataset" described a wider scope than was measured.
```

### 1-B. EXIF metadata query type error → fixed (probe defect)

```text
Original record (v0.9.4.33):
  "WIC returns PROPERTYNOTFOUND for every query path probed"
  "the product EXIF path may never have executed"

Cause:
  the probe stored query paths as const char* and passed LPCWSTR(nm) to
  GetMetadataByName. That reinterprets UTF-8 bytes as UTF-16 code units, so
  every lookup addressed a garbage path. The v0.9.4.33 PROPERTYNOTFOUND was a
  false negative produced by the probe's own bug, not evidence about the
  product.

Corrected (v0.9.4.34):
  real wide literals (const wchar_t*) are used.
  product path  /app1/ifd/exif/{ushort=274} -> WINCODEC_ERR_BADPROPERTYKEY 8/8
  working path  /app1/ifd/{ushort=274}      -> S_OK + VT_UI2 + value 1..8  8/8

Reason:
  a defect in the diagnostic tool inverted the conclusion. This is the same
  family as the v0.9.4.32 mixed-pairing artifact — a flaw in the measurement
  tool made something look like a product problem.
```

### 1-C. EXIF applied counter error → fixed (probe defect)

```text
Original record (v0.9.4.33):
  exif_orientation_applied_by_product=0

Cause:
  the baseline count was incremented into `applied` while the printed value
  read `appliedBaseCount`, which was never incremented. The bug emitted exactly
  0, the same value as the real "no orientation applied" conclusion.

Corrected (v0.9.4.34):
  exif_baseline_orientation_applied and exif_candidate_orientation_applied are
  incremented independently and printed separately.

Reason:
  a measured value and its field name must agree; 0 was indistinguishable from
  an aggregation bug.
```

### 1-D. Telemetry field meaning mismatch → fixed

```text
Original record (v0.9.4.33):
  tel.orientMs = r.metaMs;

Cause:
  a field named "orient" carried metadata-reader construction time, so the name
  and the value disagreed.

Corrected (v0.9.4.34):
  metaMs   = GetMetadataQueryReader + tag query only
  orientMs = CreateBitmapFlipRotator + Initialize only (0 when no transform)
  both are timed separately and both feed the sharedMs total.

Reason:
  a production implementation brief may rely on this telemetry, so the meaning
  of each number must match its name.
```

### 3-A. The Fixtures Are Valid

```text
exif_metadata_fixtures_valid = yes (8/8 read, 8/8 value matched)
```

Eight EXIF JPEG fixtures (orientations 1–8) were built by inserting an APP1
segment into a dataset JPEG (`f0000.jpg`, 209×248) after SOI (and after any
leading APP0/JFIF). **The standard dataset was not modified**; fixtures are
written to a separate directory. WIC read all eight and the orientation values
matched 1–8 as intended. These are genuinely valid EXIF fixtures, not merely
inserted bytes.

### 3-B. The Product Query Path Is a Bad Property Key

```text
exif_product_query_path = /app1/ifd/exif/{ushort=274}  resolved=0/8  badpropertykey=8/8
exif_working_query_path  = /app1/ifd/{ushort=274}       resolved=8/8
```

The product queries `/app1/ifd/exif/{ushort=274}` at
`src/image_decoder.cpp:194` / `:267` / `:321`. WIC rejects that path with
`WINCODEC_ERR_BADPROPERTYKEY (0x88982F40)`. The Orientation tag lives in IFD0,
which WIC exposes as `/app1/ifd/`.

**This is a product-code problem, not a probe problem.** v0.9.4.33 could not
know this, and had no basis to assert the product EXIF path was broken — and in
fact it was not broken evidence (§1-B). This run confirms it with correctly
encoded wide literals, so the conclusion now has a basis.

**This task did not change production code, so the problem is not fixed.** It
is registered as a separate task (§8). → **fixed in v0.9.4.35**, see
`docs/build-history/0.9.4.35.en.md`.

Zero verdict differences and a maximum score difference of exactly 0 across all

### 6-C. The Two Corpora Are Not Comparable

```text
v0.9.4.33 probe corpus (849 files, mostly format fixtures + BMP sample):
  CPU raw 40.8-42.2 %   adjusted about 40 %
v0.9.4.34 full corpus (3,341 files, many tiny 8x8 BMPs):
  CPU raw 47.6-48.2 %   adjusted 32.0-32.6 %
```

The full corpus has a far lower median cost (0.37 ms vs 12.7 ms) because it
contains many tiny BMPs. That is a corpus-composition difference, and **the
saving percentages must not be compared as if they measured the same thing.**
Each is valid only within its own corpus.

The adjusted baseline subtracts the `CreateFileW`+`CloseHandle` **reference
probe** that the product decoder runs when a telemetry sink is present
(`src/image_decoder.cpp:69-79`). The candidate has no such probe. The lower
adjusted saving exists because of this.
