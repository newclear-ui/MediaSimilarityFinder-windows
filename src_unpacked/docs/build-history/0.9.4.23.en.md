# MediaSimilarityFinder v0.9.4.23 — D9a Analyze Internal Observability

D9 entry. **The first step of the new node is measurement, not
optimization.** D8b established by measurement that `analyze` consumes
98.7 % of a scan, and that stage has **no internal decomposition at all**,
so no optimization can have a basis. Engine 1.5.0, DB 1.0.3, cache v9
unchanged.

> This document was written **before code changes** so the ordering is
> auditable through commit order.

**D9a does not optimize anything. It makes the stage that consumes 98.7 % of
a scan observable, so a later step can decide on evidence.**

---

## Pre-register (recorded before code changes)

### Expected benefit

```
- decompose the 98.7 % into its constituent stages
- measure verifyImagePair call count / SSIM evaluation count / cache hit rate
- distinguish "too many candidate pairs" from "each pair is slow" from
  "the cache never hits"
- allow a later optimization candidate to be prioritized on evidence
```

### Not expected

```
- any performance improvement (measurement only)
- verifyImagePair optimization / cache enlargement / parallelization
- candidate pair generation changes
- SSIM algorithm changes
- threshold changes
- search-verdict semantic changes
```

### Rollback criteria

```
- instrumentation changes scan results
- existing CTest / build regression
- parity regression (group/verdict change on the same dataset)
- instrumentation overhead increases abnormally
```

## 1. Why a new node is needed

D8b (0.9.4.22) measured:

```
engine wall 109,737 ms
  analyze            108,225.6   98.62 %   ← the vast majority
  walk                 1,536.5    1.40 %
  image stage             642.3    0.59 %
  gpu batch                 48.3    0.04 %
```

Node D owns queue / transfer / overlap. `analyze` is the final
matching/grouping stage (`pipe.analyze` at `media_search_engine.cpp:702-703`),
so it is **outside the D brief**.

No amount of further D work can produce a meaningful gain on this workload.
**The real bottleneck had no owning node.** That is why D9a opens.

## 2. Why it is currently unobservable

`analyze` is recorded as a **single number**:

```cpp
// media_search_engine.cpp:702-703
const auto benchAT0=...;
st=pipe.analyze(maxDistance, ...);
bench_.addAnalyzeMs(...);
```

The benchmark JSON's `matches` section provides:

```
candidates    candidate pair count
pairs         streamed match count
retainedPairs retained pair count
groups        group count
reductionPct  candidate reduction rate
```

But there is **no internal time decomposition whatsoever.** It is therefore
impossible to tell "are there too many candidate pairs" from "is each pair's
verification slow" from "is the cache working".

## 3. Dependency relationships confirmed by code inspection

`src/scan_pipeline.cpp` `analyze()` actually does four things:

```
(A) index build     insert every file into the 8 indexes
(B) candidate scan  forEachCandidatePair → bestMatch (Hamming) per pair
(C) image verify    verifyImagePair (SSIM re-decode) for grey-zone pairs
(D) video temporal  re-decode + DTW + crop SSIM for video pairs
```

### (C) is the probable cause — a grounded hypothesis

`src/image_verify.cpp` `verifyImagePair()`:

```
kFast = 97.0        hammingSim >= 97 returns immediately (no verification)
per grey-zone pair:
  verifyBuffersFor(pathA) → decode 64x64 full + decodePreserveAspect 64x64
  verifyBuffersFor(pathB) → same, 2 decodes
  ssimBuf x1 + 3 aspects x 3 comparisons = 10 calls
  ssimBuf computes frame_ssim twice (normal + flipped)
  → up to 20 frame_ssim evaluations and 4 image decodes per pair
```

And `kVerifyCacheMax = 32`:

```
verifyCacheList is hard-capped at 32 entries.
```

With **2,700 files against a 32-entry cache**, re-decoding both files per
pair is effectively the normal case. That is the probable reason for 98.7 % —
but it is **still a hypothesis, and nothing is measured.** This step exists
to test the hypothesis, and even if it holds the code is **not** touched
until the per-stage times exist, so we can tell whether SSIM dominates or
cache misses dominate.

## 4. What to measure (telemetry design)

The following is recorded inside `analyze`. **Every one carries a
measurement state.**

### Time decomposition

| Key | Meaning |
| --- | --- |
| `analyzeIndexMs` | (A) candidate index build |
| `analyzeScanMs` | (B) candidate pair enumeration + Hamming verdicts |
| `analyzeVerifyMs` | (C) total time in image verifyImagePair |
| `analyzeVideoMs` | (D) total time in video temporal |

### Counters

| Key | Meaning |
| --- | --- |
| `verifyCalls` | verifyImagePair invocations |
| `verifyDecodeMisses` | of those, how many actually decoded (cache miss) |
| `verifyCacheHits` | cache hits |
| `ssimEvals` | ssimBuf invocations |
| `frameSsimEvals` | frame_ssim invocations |
| `videoTemporalPairs` | pairs sent to temporal re-decode |

### Derived values that must be recorded alongside

- `verifyHitRate` = verifyCacheHits / (verifyCacheHits + verifyDecodeMisses)
  — near 0 confirms the cache-size problem; high means the decode itself is
  the cost.
- `msPerVerifyCall` = analyzeVerifyMs / verifyCalls
  — separating per-pair cost is what distinguishes "many pairs" from
  "each pair is slow".

## 5. Why these keys are needed (the argument, made in advance)

```
verifyCalls large  AND msPerVerifyCall small → candidate pair count is the cause
verifyCalls small  AND msPerVerifyCall large → per-pair verification is the cause
verifyHitRate near 0                       → cache capacity (32) is the cause
ssimEvals ~10x verifyCalls                 → the aspect loop amplifies cost
analyzeScanMs large                        → candidate enumeration itself is the cause
analyzeVideoMs large                       → video temporal (0 on this dataset, no video)
```

**Right now it is impossible to tell which of these holds.** That is exactly
why measurement comes first.

## 6. Test requirements

- A. the telemetry keys exist in JSON
- B. states are correct on a recorder whose `analyze` actually ran
- C. `not_measured` when analyze did not run (never a zero standing in)
- D. sum integrity: the sum of sub-stage times does **not exceed** `analyzeMs`
  (asserted as `<=`, not exact equality — instrumentation must not invent
  time)
- E. existing verdict regression: groups / candidates / verdicts unchanged on
  the same dataset
- F. overhead judged by whole-wall-time regression, not by a separate counter

## 7. Success criterion for this step

Success is that the instrumentation **can identify the actual bottleneck
candidate.** It does not matter which one it turns out to be. "Measured, and
SSIM dominates" is a success; "Measured, and candidate enumeration dominates"
is also a success.

**It is always better than starting an optimization while unmeasured.**

## 9. Actual result

### 9.1 What was implemented (measurement only)

- `src/analyze_telemetry.h` (new, Qt-free): a plain data carrier with **no
  dependency on `BenchmarkRecorder`, `ScanPipeline`, or `image_verify`**, so
  verification code takes no new dependency upward into engine telemetry.
  `image_verify` and `scan_pipeline` fill the struct; the engine copies it
  into the recorder. **No recorder pointer ever travels downward** (the
  prompt's §16/§17 requirement).
- `image_verify.h/.cpp`: optional `AnalyzeTelemetry*` (defaults to nullptr, so
  every existing caller is unchanged). Exactly three measurement sites:
  immediately after the `isImage` pass in `verifyImagePair`, the cache
  hit/miss branches in `verifyBuffersFor`, and the actual `frame_ssim`
  execution in `ssimBuf`.
- `scan_pipeline.h/.cpp`: `ScanStats` gains `AnalyzeTelemetry analyze`
  (additive). Stage times are designed so the four slices are a partition of
  the analyze total: index is timed in its own loop, verify accumulates at
  each call site, video accumulates per flush, and **scan is the remainder**.
- `benchmark.h/.cpp`: new `"analyze"` section, **schema v8 → v9**.
- `media_search_engine.cpp`: `bench_.setAnalyzeTelemetry(st.analyze)`.

#### Why the stage sum cannot exceed analyzeMs (§20/§21)

`flushVideo()` is also called *inside* the candidate loop, so a naive nested
timer would overlap. Video time is therefore accumulated and excluded from
the scan remainder:

```
scanMs = totalMs - indexMs - verifyMs - videoMs   (clamped at 0)
```

`index + scan + verify + video == total` is then **guaranteed by
construction**. scan also honestly absorbs unattributed control overhead
(poll, callbacks, bookkeeping) instead of pretending that overhead belongs
to a stage it was never measured in.

#### Counter semantics (every one is a counted event, never an estimate)

| Counter | Definition |
| --- | --- |
| `verifyCalls` | `verifyImagePair` calls that actually entered image verification with `isImage == true`. A video pair returns above without work and is **not** counted |
| `verifyDecodeMisses` | **lookup** count that had to decode (not call count — one call performs up to two lookups) |
| `verifyCacheHits` | lookups served from cache |
| `ssimEvals` | `ssimBuf` **invocations** |
| `frameSsimEvals` | `frame_ssim` actually executed (lower than `ssimEvals` when a guard rejects the pair — that gap is itself a measurement) |
| `videoTemporalPairs` | pairs queued for temporal work |

Derived values are computed only when their denominator is real; otherwise
`null` + `not_measured`. **No 0.0 is manufactured by dividing by zero.**

### 9.2 Actual measurement

Conditions: RTX 3080 Ti, GPU tree, the D8b standard dataset
(`9b113848…4253c`, 2,700 files, 36,007,560 B, 95 dirs, version 1), **cold
index**, repeated `msf_dataset_baseline` runs.

#### Stage split (2 runs; counters identical)

```
                     run 0        run 1
  indexMs              3.2          3.7      state=measured
  scanMs             350.8        399.3      state=measured
  verifyMs        109,142.3    117,290.7      state=measured
  videoMs              0.0          0.0      state=not_measured
  --------------------------------------------
  substage sum    109,496.3    117,693.7
  analyzeMs       109,501.9    117,699.8     -> sum <= total OK
```

Share of analyze:

```
  index     0.00 %
  scan      0.32 %
  verify   99.67 %    <- dominant
  video     0.00 %    (no video in the dataset -> not_measured, not a fake 0)
```

#### Verify counters (identical across both runs = deterministic)

```
  verifyCalls          158,020
  verifyDecodeMisses    12,949
  verifyCacheHits       14,519
  verifyHitRate          0.528579    (state=measured)
  msPerVerifyCall        0.69 ~ 0.74 ms
  ssimEvals            137,340
  frameSsimEvals       274,680
  videoTemporalPairs         0
  ssimEvals/verifyCall     0.87
```

**Internal consistency of the counters** (evidence the instrumentation can
be trusted):

```
  ssimEvals / 10          = 137,340 / 10 = 13,734  (calls that ran the full SSIM loop)
  (misses + hits) / 2     =  27,468 / 2 = 13,734  (2 buffer lookups each)
```

The two agree **exactly**, so 13,734 calls performed the expensive path with
two buffer lookups and ten `ssimBuf` calls each. Direct evidence that the
counters do not contradict each other.

## 10. Hypothesis verdicts (§14 / §30)

### Hypothesis A — "verifyImagePair is the bottleneck" → **CONFIRMED**

```
verifyMs = 99.67 % of analyze
```

The pre-registered hypothesis that stage (C) dominates is confirmed by
measurement.

### Hypothesis C — "kVerifyCacheMax = 32 causes re-decodes" → **REFUTED**

```
verifyHitRate = 0.5286   (not ~0)
```

This is the most important result of the step. **A hypothesis formed by
reading code alone was refuted by measurement.** Despite a 32-entry cache,
candidate pairs arrive clustered in index order, so the real hit rate is
52.9 %. Cache enlargement therefore cannot explain 99.67 %.

### The actual dominant structure (established by measurement)

```
verifyCalls 158,020  (only 4.3 % of 3,641,700 possible pairs reach the gate)
  ├─ ~144,286 (91.3 %): kFast (>=97) short-circuit, near-zero cost
  └─ ~ 13,734 ( 8.7 %): 2 buffer lookups + 10 ssimBuf (20 frame_ssim)
       117,290 ms / 13,734 ≈ 8.5 ms per expensive verification
```

So the bottleneck is **not the cost of one expensive verification but the
number of candidate pairs that reach the verify gate**: of the 158,020 that
arrive, 8.7 % each cost ~8.5 ms, and that produces 117 seconds.

### The rest

- `analyzeScanMs` is 0.32 % — candidate enumeration / index structure is
  **not** the bottleneck
- `analyzeVideoMs` is `not_measured` because the dataset has no video (not
  faked as 0). Judging the video path needs a video dataset
- `ssimEvals/verifyCalls = 0.87` — the SSIM loop does amplify by 10×, but
  only for 8.7 % of calls, which is different from the earlier expectation
  that it amplifies across all calls

## 14. Next optimization candidates (judged, not implemented)

Directions the measurement points at:

1. **Lower the 4.3 % arrival rate at the verify gate** — but reducing pairs
   that reach verification touches verdict semantics, so it needs care.
2. **Lower the 8.5 ms cost of one expensive verification** — 4 decodes (the
   same file is decoded repeatedly per aspect) and 20 `frame_ssim` calls
   dominate it. 9 of the 10 `ssimBuf` calls are aspect combinations, and no
   `GrayImage` is reused across them.
3. **Move `ssimEvals` closer to the verify gate** — deferring aspect
   comparisons until after the full-frame SSIM could skip needless work.

**None of these were implemented here.** Which direction is right must be
settled by the next substep's pre-register first.

One caveat: the dataset's fingerprint distribution is **synthetic
deterministic patterns**, so the candidate-pair ratio on a real user library
will differ. This conclusion holds *for this dataset*.
