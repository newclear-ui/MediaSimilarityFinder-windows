D9 entry. **The first step of the new node is measurement, not
optimization.** D8b established by measurement that `analyze` consumes
98.7 % of a scan, and that stage has **no internal decomposition at all**,
so no optimization can have a basis. Engine 1.5.0, DB 1.0.3, cache v9
unchanged.

> This document was written **before code changes** so the ordering is
> auditable through commit order.

**D9a does not optimize anything. It makes the stage that consumes 98.7 % of
a scan observable, so a later step can decide on evidence.**

## 1. Why a new node is needed

D8b (0.9.4.22) measured:

```
engine wall 109,737 ms
  analyze            108,225.6   98.62 %   ← the vast majority
  walk                 1,536.5    1.40 %
  image stage             642.3    0.59 %
  gpu batch                 48.3    0.04 %
```

Node D owns queue / transfer / overlap. `analyze` is the final
matching/grouping stage (`pipe.analyze` at `media_search_engine.cpp:702-703`),
so it is **outside the D brief**.

No amount of further D work can produce a meaningful gain on this workload.
**The real bottleneck had no owning node.** That is why D9a opens.

## 2. Why it is currently unobservable

`analyze` is recorded as a **single number**:

```cpp
// media_search_engine.cpp:702-703
const auto benchAT0=...;
st=pipe.analyze(maxDistance, ...);
bench_.addAnalyzeMs(...);
```

The benchmark JSON's `matches` section provides:

```
candidates    candidate pair count
pairs         streamed match count
retainedPairs retained pair count
groups        group count
reductionPct  candidate reduction rate
```

But there is **no internal time decomposition whatsoever.** It is therefore
impossible to tell "are there too many candidate pairs" from "is each pair's
verification slow" from "is the cache working".

## 3. Dependency relationships confirmed by code inspection

`src/scan_pipeline.cpp` `analyze()` actually does four things:

```
(A) index build     insert every file into the 8 indexes
(B) candidate scan  forEachCandidatePair → bestMatch (Hamming) per pair
(C) image verify    verifyImagePair (SSIM re-decode) for grey-zone pairs
(D) video temporal  re-decode + DTW + crop SSIM for video pairs
```

### (C) is the probable cause — a grounded hypothesis

`src/image_verify.cpp` `verifyImagePair()`:

```
kFast = 97.0        hammingSim >= 97 returns immediately (no verification)
per grey-zone pair:
  verifyBuffersFor(pathA) → decode 64x64 full + decodePreserveAspect 64x64
  verifyBuffersFor(pathB) → same, 2 decodes
  ssimBuf x1 + 3 aspects x 3 comparisons = 10 calls
  ssimBuf computes frame_ssim twice (normal + flipped)
  → up to 20 frame_ssim evaluations and 4 image decodes per pair
```

And `kVerifyCacheMax = 32`:

```
verifyCacheList is hard-capped at 32 entries.
```

With **2,700 files against a 32-entry cache**, re-decoding both files per
pair is effectively the normal case. That is the probable reason for 98.7 % —
but it is **still a hypothesis, and nothing is measured.** This step exists
to test the hypothesis, and even if it holds the code is **not** touched
until the per-stage times exist, so we can tell whether SSIM dominates or
cache misses dominate.

## 4. What to measure (telemetry design)

The following is recorded inside `analyze`. **Every one carries a
measurement state.**

### Time decomposition

| Key | Meaning |
| --- | --- |
| `analyzeIndexMs` | (A) candidate index build |
| `analyzeScanMs` | (B) candidate pair enumeration + Hamming verdicts |
| `analyzeVerifyMs` | (C) total time in image verifyImagePair |
| `analyzeVideoMs` | (D) total time in video temporal |

### Counters

| Key | Meaning |
| --- | --- |
| `verifyCalls` | verifyImagePair invocations |
| `verifyDecodeMisses` | of those, how many actually decoded (cache miss) |
| `verifyCacheHits` | cache hits |
| `ssimEvals` | ssimBuf invocations |
| `frameSsimEvals` | frame_ssim invocations |
| `videoTemporalPairs` | pairs sent to temporal re-decode |

### Derived values that must be recorded alongside

- `verifyHitRate` = verifyCacheHits / (verifyCacheHits + verifyDecodeMisses)
  — near 0 confirms the cache-size problem; high means the decode itself is
  the cost.
- `msPerVerifyCall` = analyzeVerifyMs / verifyCalls
  — separating per-pair cost is what distinguishes "many pairs" from
  "each pair is slow".

## 5. Why these keys are needed (the argument, made in advance)

```
verifyCalls large  AND msPerVerifyCall small → candidate pair count is the cause
verifyCalls small  AND msPerVerifyCall large → per-pair verification is the cause
verifyHitRate near 0                       → cache capacity (32) is the cause
ssimEvals ~10x verifyCalls                 → the aspect loop amplifies cost
analyzeScanMs large                        → candidate enumeration itself is the cause
analyzeVideoMs large                       → video temporal (0 on this dataset, no video)
```

**Right now it is impossible to tell which of these holds.** That is exactly
why measurement comes first.

## 6. Test requirements

- A. the telemetry keys exist in JSON
- B. states are correct on a recorder whose `analyze` actually ran
- C. `not_measured` when analyze did not run (never a zero standing in)
- D. sum integrity: the sum of sub-stage times does **not exceed** `analyzeMs`
  (asserted as `<=`, not exact equality — instrumentation must not invent
  time)
- E. existing verdict regression: groups / candidates / verdicts unchanged on
  the same dataset
- F. overhead judged by whole-wall-time regression, not by a separate counter

## 7. Success criterion for this step

Success is that the instrumentation **can identify the actual bottleneck
candidate.** It does not matter which one it turns out to be. "Measured, and
SSIM dominates" is a success; "Measured, and candidate enumeration dominates"
is also a success.

**It is always better than starting an optimization while unmeasured.**
