# MediaSimilarityFinder v0.9.4.21 — D8a Reproducible Dataset Foundation / Dataset Fingerprint

D8a 진입. **성능 최적화가 아니다.** 코드 최적화의 선행 조건이었던
"동일 조건 end-to-end 비교"가 불가능했던 상태를 해소하는 기반 구축이다.
엔진 1.5.0·DB 1.0.3·캐시 v9 불변, benchmark schema 7→8.

> 이 문서는 **fixture / 코드 변경 전에** 작성되어 커밋 순서로 감사 가능하다.
> 실제 값(file count, total bytes, fingerprint)은 fixture를 만든 뒤에만
> 채운다. 추측값을 넣지 않는다.

**D8a does not implement transfer/compute overlap (D4b), full D3 queue
topology, or any performance optimization. It only builds the reproducible
dataset and the dataset fingerprint required to compare anything at all.**

---

## Pre-register (fixture / 코드 변경 전 기록)

### 예상 효과 (expected benefit)

```
- 동일 dataset을 반복 실행 가능 (reproducibility)
- CPU/GPU 비교의 입력 조건 고정 (input conditions pinned)
- D4b overlap 판단을 위한 실제 telemetry 확보 가능
- Full D3 queue imbalance 측정 가능
- D8 end-to-end parity 비교 가능
```

### 기대하지 않는 것

```
- 어떤 성능 향상도
- D4b overlap 구현
- Full D3 topology 구현
- Scheduler / share formula 변경
- 검색 판정语义 변경 (engine 1.5.0 / DB 1.0.3 / cache v9 불변)
```

### 롤백 기준 (하나라도 해당하면 fixture + fingerprint revert)

```
- fixture가 deterministic하지 않음
- fingerprint가 동일 dataset에서 달라짐
- 다른 absolute root에서 fingerprint가 달라짐
- benchmark JSON compatibility regression
- CPU/GPU build regression
- CTest regression
- 기존 scan result regression
```

## 1. 왜 D8a가 필요한가

D4a까지는 백엔드 내부 타이밍 경계가 생겼지만, **비교 기준이 없다.**
"같은 조건에서 다른 두 상태를 비교한다"는 말 자체가 불가능했다.
이건 코드의 문제가 아니라 근거 부재의 문제다.

## 2. 현재 fixture 부재

- `test_sample_img_vid/` 는 존재하지만 **완전히 비어 있다** (0 entries).
- `Scanner::isMediaPath` 가 `.pgm` 을 인식하지 않으므로, 포팅 가능성을
  위해 PGM을 쓸 경우 확장자는 스캔 가능한 확장자여야 한다.

## 3. D4b / Full D3 / D8이 막힌 이유

세 갈래가 **동일 dataset** 을 요구하는데 그 dataset이 없다:

- **D4b overlap 판단** → 대표 스캔의 `gpuSyncHostMs` / `gpuKernelDeviceMs`
  분포가 필요. D4a의 합성 16/256장 프로브는 대표 dataset이 아니다.
- **Full D3** → `walker.maxDepth` / `blockedTicks` / `starvedTicks` 의
  실제 queue behavior 필요.
- **D8** → 동일 dataset 반복 측정 + parity 비교 필요.

즉 다음 최적화들 전부가 동일한 근거 부족에 막혀 있다. D8a가 그 근거다.

## 4. Dataset 구성 방법 (조사 결과 기반)

### 조사 결론: 생성 스크립트 방식 채택

저장소의 확고한 관례가 **"바이너리 asset 커밋 금지"** 이다
(495개 트랙 파일 전부 텍스트). 따라서 dataset을 git에 커밋하지 않고
**결정론적 생성 스크립트**로 만든다. `test_sample_img_vid/` 는
placeholder로 유지하고 실제 산출물은 script가 결정한다.

이 선택의 이유:

- 손으로 만든 BMP는 완전히 결정론적 (encoder nondeterminism 없음)
- 66개 테스트가 이미 runtime 생성 관례를 따른다
- 바이너리가 git 히스토리에 처음 들어가는 것을 피한다
- 재생성/검증 절차가 문서로 완결된다

### Fixture 구성 (v1, image only)

기존 테스트 관례(`bmp()` 8x8 24-bit)를 따르되, end-to-end 측정의
의미를 위해 **두 구조**를 함께 둔다:

```
images/exact/dupNN.bmp      동일 콘텐츠 복제군 (중복 판정 경로)
images/varied/vNN.bmp       시드별 미세 변이 (분류/임계 경로)
```

- 확장자 `.bmp` — WIC이 실제 프로덕션 경로로 읽는다
  (PGM fallback이 아니라), 그리고 스캐너가 인식한다
- 각 파일은 header 54바이트 + 픽셀. 픽셀 값은
  `(x*2 + y*3 + seed) % 256` 형태의 **순수 정수 결정론** 생성
- 파일 크기, 이름, 상대 경로가 고정

### Video는 이번 단계에서 제외 (문서로 구분)

조사 결과 video fixture는 전부 `std::system("ffmpeg ... lavfi testsrc")`
에 의존하고, **ffmpeg 출력은 byte 재현성이 없다**
(encoder / creation-time metadata가 컨테이너에 mix됨).
현재 어떤 테스트도 `-fflags +bitexact` / `-map_metadata -1` 을 쓰지 않는다.

그래서:

```
D8a dataset foundation   = image fixture + fingerprint (이번 단계)
future video fixture expansion = 별도 단계에서 bitexact 보장 후 추가
```

를 문서에서 명확히 구분한다. video를 억지로 넣으면 fingerprint가
실행마다 흔들려 **재현성의 목적을 정면으로 파괴**한다.

## 5. Fingerprint 정의

dataset identity는 **내용**이다. 위치가 아니다.

```
manifest entry = canonical relative path + file size + content hash
sort entries by canonical relative path
canonical string = entries joined by '|' with ';' inside an entry
hash canonical string -> dataset fingerprint
```

### 절대 포함하지 않는 것

```
absolute path, timestamp, process id, GPU/CPU name, run id
```

`root` 는 이미 JSON에 있으나 이는 **location** 이며 dataset identity가
아니다. `C:\project\test_sample_img_vid` 와
`D:\other\test_sample_img_vid` 가 동일 내용이면 동일 fingerprint여야 한다.

### Relative path 규칙

`IndexManager::canonicalRoot` 의 관례를 따른다: `\` → `/`,
`lexically_normal`, trailing separator 제거. 대소문자 접기는 하지 않는다
(case-sensitive 파일시스템을 깨뜨리므로).

## 6. Canonicalization

- `msf::path_from_utf8` / `path_to_utf8` 로 모든 경계 통과 (Windows 필수)
- `fs::relative(root, file)` 후 위 규칙 적용
- entry 정렬은 byte 순서 기준 (locale 무관)
- content hash 는 **전체 파일** 을 읽는다
  (기존 `scanner.cpp` 의 `quick()` 는 첫 64 KiB 만 읽지만, 그건
  파일 동일성 용도로 쓰이므로 dataset identity 용도로 재사용하지 않는다)

## 7. Hash algorithm 선택

조사 결과 `msf_core` 에 **암호 해시가 없다.**
- SHA-256 은 `gui/mainwindow.cpp` 의 `QCryptographicHash` 뿐이며
  Qt 에만 있고 헤더로 노출되지 않는다
- `msf_core` 는 Qt 를 링크하지 않는다
- vcpkg 에 openssl 이 없다
- 사용 가능한 것은 FNV-1a 계열 뿐 (여러 파일에 복붙된 로컬 static)

따라서 새 `src/dataset_fingerprint.h/.cpp` 에 **SHA-256 을 직접 구현**한다.
요구사항:

- 순수 C++ (Qt / 외부 라이브러리 의존 없음)
- CPU / GPU 트리 공통 컴파일
- 결정론적

선례: `ProfileStore::deriveId` 가 "version 상수 + `|` 구분 canonical
문자열 → 고정폭 hex" 를 쓰므로 fingerprint 도 같은 형태를 따른다.

## 8. Fingerprint version

`datasetFingerprintVersion` = 1. dataset 내용과 별개인
**algorithm 식별자**이며, algorithm 이 바뀌면 올린다.
선례는 `PerformanceProfile::kProfileVersion`.

## 9. Benchmark JSON 변경 (schema v8)

`meta` 블록의 `root`(location) 옆에 dataset identity 를 추가한다.
additive extension 이며 기존 키는 삭제하지 않는다.

```json
"dataset":{
  "fingerprint":"<64 hex>",
  "fingerprintVersion":1,
  "fileCount":N,
  "totalBytes":M,
  "state":"measured"
}
```

`fileCount` / `totalBytes` 는 convenience metadata (fingerprint 안에 이미
포함되지만 판독 편의를 위해 별도 노출).

## 10. Measurement state

| 상황 | state |
| --- | --- |
| 계산 성공 | `measured` |
| root 가 존재하지 않음 / fixture 미설치 | `not_available` |
| 읽기 오류 발생 | `failed` |

**절대 `fingerprint: 0` 으로 missing 을 위장하지 않는다.**
미계산이면 fingerprint 는 `null` 로 기록한다.

## 11. Test 요구사항 (A~F)

- **A** 동일 fixture 2회 → 동일 fingerprint
- **B** 파일 1개 내용 변경 → fingerprint 변경
- **C** 다른 absolute root 에서 동일 dataset → 동일 fingerprint
- **D** enumeration 순서 무관 → canonical sort 로 동일 fingerprint
- **E** empty / missing dataset → 올바른 state (`not_available`)
- **F** BenchmarkRecorder JSON 에 fingerprint 기록 + state 정확성

B 는 **복사본 dataset** 을 content 변형해 비교한다 (원본 훼손 금지).
C 는 **복사본을 다른 root 로 이동**해 비교한다.

## 12. Compatibility 영향

- Windows / Linux 동일 (순수 C++, `path_utils` 경유)
- CPU-only 빌드 영향 없음 (CUDA 미사용)
- search 판정 경로 무관: dataset fingerprint 는 benchmark telemetry 뿐
  engine / DB / cache 에는 닿지 않는다
- fingerprint 계산은 **scan 결과에 영향을 주지 않는다**

## 17. 향후 D4b / Full D3 / D8에서 사용하는 방법

동일 dataset fingerprint 를 기준으로:

```
D4b   → gpuH2dDeviceMs / gpuKernelDeviceMs / gpuD2hDeviceMs /
         gpuSyncHostMs / gpuHostTotalMs 분포 + end-to-end wall time
Full D3→ walker.maxDepth / blockedTicks / starvedTicks / memory / wall time
D8    → 동일 dataset 반복 performance / stability / correctness / parity
```

**D4b overlap 구현과 Full D3 topology 구현은 아직 하지 않는다.**
