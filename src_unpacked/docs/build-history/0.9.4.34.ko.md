## 0. 이 문서의 성격

v0.9.4.33 의 I-2 결과에는 **측정 범위 표현 오류**와 **probe 결함 2건**이
있었다. 이번 문서는 그것을 정정하고, production 적용 판단에 필요한 증거를
완성한다. 과거 기록을 덮어쓰지 않는다.

```text
v0.9.4.33 의 849 파일 결과 = probe corpus 결과 (images/format 전량 + BMP stride 샘플)
v0.9.4.34 의 3,341 파일 결과 = full corpus validation 결과 (표준 dataset 전체)
```

두 결과는 같은 것이 아니며, 하나로 합치지 않는다.

```text
수정 이유:
  "전체 dataset" 이라는 표현이 실제 측정 범위보다 넓었다. 지시 요구사항.
```

### 1-B. EXIF metadata query 타입 오류 → 수정 (probe 결함)

```text
원래 기록 (v0.9.4.33):
  "WIC 가 4종 query path 전부에서 PROPERTYNOTFOUND 를 반환"
  "제품 EXIF 경로가 dataset 에서 실행된 적이 없을 가능성"

오류 원인:
  probe 가 query path 를 const char* 로 보관하고 LPCWSTR(nm) 으로 캐스팅해
  GetMetadataByName 에 넘겼다. 이는 UTF-8 바이트를 UTF-16 코드유닛으로
  재해석하는 것이므로 모든 조회가 쓰레기 경로를 가리켰다.
  따라서 v0.9.4.33 의 PROPERTYNOTFOUND 는 제품에 대한 증거가 아니라
  probe 자신의 버그가 만든 허위 음성이었다.

수정된 값 (v0.9.4.34):
  실제 wide 리터럴(const wchar_t*)로 조회.
  제품 경로  /app1/ifd/exif/{ushort=274}  -> 8/8 건 WINCODEC_ERR_BADPROPERTYKEY
  동작 경로  /app1/ifd/{ushort=274}       -> 8/8 건 S_OK + VT_UI2 + 값 1~8 일치

수정 이유:
  진단 도구의 인코딩이 잘못되어 결론이 뒤집혔다. 이는 v0.9.4.32 의
  mixed-pairing artifact 와 같은 계열 — 측정 도구 자체의 결함이
  "제품 문제" 로 보인 사례다.
```

```text
원래 기록 (v0.9.4.33):

오류 원인:

수정 이유:
  계측값과 필드 이름이 일치해야 한다. 0 이 "측정 결과 0" 인지 "집계 오류" 인지
  구분 불가 상태였다.
```

### 1-D. telemetry 필드 의미 불일치 → 수정

## 3. EXIF 결과

```text
exif_status = NOT_MEASURED  (종단간)
exif_status_reason = product_query_path_does_not_resolve_so_no_orientation_was_
                      applied_by_either_side_end_to_end
```

### 3-A. fixture 는 유효하다

```text
exif_metadata_fixtures_valid = yes (8/8 read, 8/8 value matched)
```

합성 EXIF JPEG 8개(orientation 1~8)를 dataset JPEG(`f0000.jpg`, 209x248) 의
SOI 뒤(있는 경우 APP0/JFIF 뒤)에 APP1 로 삽입했다. **표준 dataset 은 변경하지
않았고** fixture 는 별도 디렉터리에 생성했다. WIC 가 8개 모두 읽었고
orientation 값이 1~8 로 의도대로 일치했다. 즉 "바이트만 넣은 것" 이 아니라
**실제로 유효한 EXIF fixture** 다.

### 3-B. 제품 query path 는 bad property key

```text
exif_product_query_path = /app1/ifd/exif/{ushort=274}  resolved=0/8  badpropertykey=8/8
exif_working_query_path  = /app1/ifd/{ushort=274}       resolved=8/8
```

제품은 `src/image_decoder.cpp:194` / `:267` / `:321` 에서
`/app1/ifd/exif/{ushort=274}` 를 사용한다. 이 경로는 WIC 에서
`WINCODEC_ERR_BADPROPERTYKEY (0x88982F40)` 로 거부된다. Orientation 태그는
IFD0 에 있으며 WIC 는 이를 `/app1/ifd/` 로 노출한다.

**이는 이번 probe 결함이 아니라 제품 코드의 문제다.** v0.9.4.33 은 이 사실을
알 수 없었는데, 그때도 "제품 EXIF 가 동작하지 않는다" 고 단정할 근거는 없었고
실제로 근거도 없었다(위 1-B 참조). 이번에는 올바르게 인코딩된 wide 리터럴로
확인했으므로 결론의 근거가 갖춰졌다.

**이번 작업은 production 코드를 변경하지 않았으므로 이 문제는 수정되지
않았다.** 별도 과제로 등록한다(§7). → **0.9.4.35 에서 수정됨**, 상세는
`docs/build-history/0.9.4.35.ko.md`.

### 3-C. I-2 구조 자체는 회전 하에서 검증됨

```text
exif_rotation_exercised = 7   (o=2..8, o=1 은 항등 변환)
exif_shared_vs_independent_identical = 7
exif_shared_vs_independent_differs   = 0
exif_shared_source_under_rotation = PASS (7/7 identical)
```

제품 경로가 깨져 있어 종단간 비교는 불가능하므로, I-2 가 실제로 던지는 질문에
직접 답하는 형태로 검증했다. fixture 가 선언한 변환을 **강제 적용**하여
rotation 을 실제로 수행한 뒤,

```text
공유 source 1개 + 독립 scaler 2개   (후보)
   vs
완전 독립 pipeline 2개              (참조: 각각 자체 factory/decoder/frame/rotator)
```

의 출력을 f/a 모두 byte 비교했다. **7/7 동일.** 회전된 source 를 두 scaler 가
공유해도 결과가 바뀌지 않으므로, I-2 의 구조적 위험은 회전 경로에서도 없다는
것이 실측으로 확인됐다.

```text
exif_baseline_orientation_applied = 0/8
exif_candidate_orientation_applied = 0/8
```

양쪽 모두 0 인 이유는 **후보가 아니라 제품 query path** 때문이다(§3-B).
후보의 EXIF 분기 자체는 §3-C 로 검증됐다.

## 5. full-scan groups 비교

양쪽 모두 **제품의 판정 함수인 `verifyScorePlan`**
(`src/image_verify.h:30`) 으로 계산했다. `verifyImagePair` 가 내부에서 호출하는
것과 동일한 함수이며, 차이는 버퍼를 어느 파이프라인이 만들었는지뿐이다.
pairs 는 prefilter 없이 **전수** 열거했다.

```text
group_corpus_files = 3341
stride = 1 (exhaustive)
pairs_compared = 5,579,470          (= 3341*3340/2)
baseline_groups  = 457,126
candidate_groups = 457,126
group_membership_verdict_diffs = 0
max_abs_score_diff = 0.000000000
group_parity = identical
```

5,579,470 쌍 전부에서 verdict 차이 0건, 점수 최대 절대차 0. 이는 byte parity
결과와 논리적으로 일치한다(점수는 버퍼의 순수함수이므로 버퍼가 같으면 점수도
같다). 다만 **논리로만 결론내리지 않고 실제로 전수 계산했다.**

`group` 은 제품 스캔의 `s.groups` 와 같은 의미(match 개수)다. 파일 멤버십은
match 집합이 완전히 동일하므로 동일하다.

## 8. production 반영 전 남은 사항

1. **제품 EXIF query path 결정.** `/app1/ifd/exif/{ushort=274}` 는 WIC 가
   `BADPROPERTYKEY` 로 거부한다. 이 문제는 I-2 와 무관한 **제품 결함**이며,
   수정 시 후보 판정과 별개로 처리해야 한다. 수정하지 않으면 EXIF 회전 사진이
   어떤 후보에서도 적용되지 않는다.
2. **제품 경로 EXIF 종단간 검증.** 위 수정 후에 A5 를 실제로 측정해야 한다.
   그때는 후보가 제품과 동일한 경로를 쓰므로 baseline 대비 비교가 가능하다.
3. **scan 경로 통합 검증.** groups 비교는 probe 계층에서 `verifyScorePlan` 으로
   수행했다. 실제 scan 파이프라인에 후보를 연결한 경로 검증은 별도다.
