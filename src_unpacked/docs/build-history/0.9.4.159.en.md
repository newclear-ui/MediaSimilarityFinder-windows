# MediaSimilarityFinder v0.9.4.159 — Comparison Engine Row-Buffer Reuse (P2)

Baseline `0.9.4.158` → this build `0.9.4.159`.
CPU CTest **133/133**, GPU CTest **134/134** (1 new CTest: video_sim_perf_test).
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 10` / `kProtocol 1` all unchanged.

## 1. Why the change was needed

- External review P2: `video_similarity()` DTW allocates `hamming`/`ssim` vectors plus GPU-gate packing buffers (`pa`/`pb`/`map`/`out`) per row, and `processVideoFrames()` pHash staging (`packed`/`mirrored`/`map`) regrows incrementally. Row-level alloc/free accumulates into matching overhead as kept fingerprints grow.

## 2. Previous structure

- Fresh vectors per DTW row, fresh packing buffers per GPU-gated row, fresh `normal`/`mirror` result buffers per pHash chunk.

## 3. New structure

- `video_similarity()`: a thread_local `VideoSimWorkspace` reuses row buffers across rows and calls. One instance per worker thread (`scan_pipeline` fans candidate pairs over an async pool, so a shared static would race). Math and order untouched → scores unchanged.
- `processVideoFrames()`: pHash staging buffers reserved once from the `keep` count; chunk result buffers hoisted out of the loop.
- Regression pin: new `video_sim_perf_test` — fixed-LCG 12x14 fingerprints, bit-identical CPU scores across runs, CPU-vs-GPU agreement within 0.2 plus submitted/completed assertions when a GPU is present, fixed 400-iteration wall-time report.

## 4. Resolved state

- Per-row heap allocations are zero after warmup (by construction). Judgement and telemetry semantics unchanged.

## 5. Verification (performance experiment record)

- Experiment ID: P2-WS-159. Purpose: wall-time effect of removing DTW-row allocation churn. Hypothesis: row allocations dominate matching overhead.
- Conditions: same machine, same binary shape, same workload (fixed 12x14 pair, 400 iterations). Baseline: same tree rebuilt with the optimization stashed.
- Raw measured values (ms/400iters):
  - CPU path (frame_ssim fallback): baseline 486.95 / 458.73 / 465.43 / 448.43, new 471.90 / 445.18 / 441.53 / 455.93 / 465.72 / 451.87.
  - GPU path (ssimBatch, submitted=completed=308): baseline 447.13 / 400.01 / 448.03, new 359.48 / 322.41 / 457.73 / 435.50.
- Verdict: speedup hypothesis **NOT ACCEPTED** — both paths land inside run-to-run variation (±10–20%); compute (`frame_ssim`/kernels) dominates. The structural change itself is **PASS** (bit-identical scores `cpuScore=10.9667`, full suites green, churn removed by construction, less allocator pressure under the async pool).
- Full suites: `CPU Release CTest 100% tests passed out of 133`, `GPU CTest 100% tests passed out of 134`, `--version` 0.9.4.159 on all 4 binaries.

## 6. Impact and limits

- Judgement, storage, protocol, versions all unchanged. No cache invalidation.
- GPU batch threshold (8), packing order, mutex serialization untouched without measurement evidence. Real matching acceleration gets re-measured after device-resident decode (HW phase).
- Time-axis representativeness of kept-frame selection stays a post-V2/V3-gate task, not in this build.
