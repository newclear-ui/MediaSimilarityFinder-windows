# MediaSimilarityFinder v0.9.4.118 — 스캔 목록 churn 제거 (append 우선 재사용 + 대형 append 지연)

기준선 `0.9.4.117` → 본 빌드 `0.9.4.118`.
CPU CTest **123/123**, GPU CTest **124/124**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` 불변.

## 1. 변경 필요성

사용자 실기(0.9.4.117): 불러오기 점진 채우기·썸네일 속도 개선과 그룹 275 해소는 확인됐지만, **검색 중 목록 동작이 "첫 스크롤 몇 개 빠르게 → 매우 천천히 하나씩 → 어느 순간 한번에 많이"**로 보고됐다(사용자 세션 로그 2026-10-17 05:03~05:16). 로그 분석 결과 GUI가 **동일한 9,057행 전체 재구축을 반복** 수행한 것이 확인됐다:

- 불러오기 직후 05:04:46: `groupFill rows=9057 16.2s`
- 스캔 시작 05:08:38: `groupFill rows=9057 20.5s` — `beginScan`이 팬 상태를 클리어한 뒤 `refreshGroupList()`(append=false) 호출
- 스캔 종료 05:14:45: `groupFill rows=9057 19.0s`
- 이후 적용 05:16:23: `resultsApply rows=0 groups=9057` → `groupFill rows=9057 16.8s`

그룹·파일 목록이 변하지 않았는데도 전 행을 재생성하고 썸네일 캐시까지 버려 재조회했다. 사용자가 본 "한번에 많이 채워짐"은 이 반복 재구축(100행/턴 청크의 완료 burst)이었고, "쌍매칭 검증방식 차이"는 다른 원인이다(판정/엔진 로직 무관).

## 2. 기존 구조와 결함

1. 0.9.4.91의 append 재사용(`fillPair(append)`, prefix 가드)은 스캔 중 부분 도착(`refreshStreaming`)에만 적용되어 있었다. 스캔 **시작(`beginScan`)/종료(`scanFinished`)/결과 적용(`onResults`)/중단(`scanFailed`)** 경로는 모두 `refreshGroupList()`(append=false)라 그룹 목록이 그대로여도 **전 행을 재구축**했다.
2. append 경로는 대형 추가도 동기 루프 — 0.9.4.117에서 지연 채우기(`GroupFillJob`)가 전체 재구축 경로(800행 초과)에만 들어갔다.

## 3. 변경 구조

- **① 스캔 흐름 4곳 append 우선**: `beginScan`·`scanFinished`·`onResults`·`scanFailed`가 `refreshGroupList(true)`를 사용한다. 표시 목록이 현재 목록의 prefix면 신규 행만 하단에 추가(동일 목록이면 **무동작**), 병합/순서 변경 시에만 자동 전체 재구축으로 폴백한다(0.9.4.91 계약 유지).
- **② 대형 append 지연(`kDeferAppendMin=300`)**: 신규 행이 300개를 넘는 append도 `GroupFillJob`(`append=true`)으로 지연한다. 팬을 클리어하지 않고 100행/턴 추가, 완료 시 resize/`doItemsLayout`/catch-up 수행, `groupFill done rows=N ms=M append` 로그. 세대 카운터(`fillGen_`)와 지연 중 append 도착 시 전체 재구축 강등 규칙은 0.9.4.117과 동일하다.
- **③ 회귀 프로브 확장(`group_fill_probe`)**: Scenario A — 동일 데이터 재적용 시 기존 행 유지(수정 전에는 동기 클리어로 `grid->item(0)` 소멸). Scenario B — 신규 창(빈 팬) 첫 적용이 신속 반환(append 지연 없으면 동기 9,055행). **FAIL-first 2사이클 재현**: A `rowsKept=0`, B `applyMs=15,087/15,641ms`.

## 4. 해결된 상황

- 스캔 시작/종료/재적용에서 동일 목록의 9k행 churn 제거. 재적용 `applyMs=101ms rowsKept=1`(수정 전 `rowsKept=0`), 신규 창 `applyMs=77ms`(append 지연 없으면 15,641ms). 9,055행 지연 채우기 총시간은 0.9.4.117과 동일하게 100행/턴(~17s, 틱 91)로 진행된다.
- 필드에서 보이던 "천천히 하나씩 채워지다가 한번에 많이"의 주 원인(반복 재구축)이 사라진다. 스캔 중 실제 신규 발견 그룹의 1건 스트리밍(엔진 페이스)은 설계 유지다.

## 6. 향후 영향 및 한계

- 표시 전용: 판정·저장·프로토콜·engine/DB/schema/cache 불변.
- 스캔 시작 시 팬이 초기화되지 않고 스캔 종료까지 그대로 유지된다(그룹 구성이 실제로 달라진 경우에만 재구축).
- 9,055행 지연 채우기 총시간(~17초, 행당 ~2ms=tree+grid 2위젯) 한계는 0.9.4.117과 동일 — 재검토 조건도 동일(숨은 페인 지연 채우기, 모델/뷰 분리, 지속 인덱스).
- `kDeferAppendMin=300`: 소규모 append(테스트·일반 폴더)는 종전과 동일한 동기 동작을 유지한다.
