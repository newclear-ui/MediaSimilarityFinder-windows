## 1. 변경 필요성

EXIF Orientation이 없거나 EXIF 경로로 해결되지 않는 파일은 방향 정보를 읽을
수 없었다. `I-exif-orientation-path-fix`는 XMP fallback을 명시적으로 금지했으므로,
별도 계약(`I-xmp-orientation-fallback.*`)으로 승격하여 독립 production 경로를
정의했다. 기존 EXIF 계약은 소급 변경하지 않았다.

## 2. 기존 구조

- `exifOrientationToTransform()`은 EXIF 부재·조회 실패·무효값을 구분하지 않고
  모두 identity로 반환했다. XMP 조회 코드는 존재하지 않았다.

## 3. 변경 구조

- `resolveOrientationToTransform()` 신설: EXIF VT_UI2 1..8이면 EXIF 사용(XMP
  조회 금지). EXIF 부재/조회 실패/타입 불일치/범위 밖 값은 미해결로 XMP 시도.
- XMP는 `tiff:Orientation` 단일 표현만 지원. WIC 실측상 `VT_LPWSTR` 문자열로
  읽히며 정수형 VARIANT도 정규화한다. EXIF·XMP 충돌 시 EXIF 우선.
- 호출부 2곳(fingerprint decodeBoth, color display lane)은 동일 helper를
  공유하므로 transform semantics가 하나로 유지된다.
- Telemetry field 추가 없음. XMP 조회는 EXIF 미해결 때만 수행된다.

## 4. 해결된 상황

## A. `--version` 이력 판정 오류

### 1. 변경 필요성
`MediaSimilarityFinder.exe --version`이 PowerShell에서 콘솔에 아무것도 출력하지
않았다. CMD에서는 정상이었다.

### 2. 기존 구조
`gui/main.cpp::attachParentConsole()`는 GUI subsystem(`WIN32_EXECUTABLE TRUE`)
이므로 `GetConsoleWindow()==nullptr`일 때 `AttachConsole(ATTACH_PARENT_PROCESS)`
로 부모 콘솔에 붙고, 리다이렉션이 있으면 `CONOUT$` 재오픈을 건너뛴다.
판정 함수 `streamIsRedirected()`는 `fd<0`, 무효 OS 핸들, `FILE_TYPE_UNKNOWN`을
모두 `true`(리다이렉션 있음)로 돌려였다.

### 3. 변경 구조
위 세 경우를 `false`(스트림 사용 불가)로 변경했다. 리다이렉션으로 유효한
`FILE_TYPE_DISK`/`FILE_TYPE_PIPE`만 `true`로 남는다. 실제 리다이렉션은 보존되고,
출력 불가능 상태만 `AttachConsole` + `CONOUT$` 경로로 넘어간다.
`gui/main.cpp:41-49` 및 주변 주석 정정.

### 4. 해결된 상황
PowerShell 실행 시 `AttachConsole`이 건너뛰어져 `std::cout`에 쓰기 대상이 없던
경로가 제거되었다. CMD 동작은 불변이다.

### 5. 검증
- `--version` / `--help` / `cmd /c` / 잘못된 옵션(stderr, EXIT=2) 전부 정상.
- OS 수준 리다이렉션(`cmd > file`) 45바이트 정상 기록.
- `Start-Process -Wait -RedirectStandardOutput` 45바이트, EXIT=0.
- 부수 확인: PowerShell `>` 는 GUI subsystem exe를 PowerShell이 기다리지 않아
  `$LASTEXITCODE`가 비고 0바이트가 된다. **수정 전 exe에서도 동일하게 재현**되므로
  본 수정의 회귀가 아니다. OS 수준 리다이렉션은 정상이다.
- CPU CTest 102/102 PASS.

### 6. 향후 영향
콘솔 CLI 출력 경로의 판정만 바뀌었다. 검색/인덱스/비교 로직과 GUI 동작은
영향을 받지 않는다. 다음 후보: 콘솔 출력 전용 회귀 테스트 추가.

## B. CUDA host compiler 인코딩 경고 (C4819)

### 1. 변경 필요성
GPU 빌드 로그에 MSVC `warning C4819`가 CUDA 헤더(`driver_types.h`,
`cuda_runtime_api.h`)에서 반복 발생했다. 코드 페이지 949가 CUDA 헤더의 비ASCII
문자를 표현하지 못해서이며, CUDA syntax/link 오류는 없었다.

### 2. 기존 구조
`add_compile_options($<$<COMPILE_LANG_AND_ID:CXX,MSVC>:/utf-8>)`만 존재해 MSVC
C++ 컴파일에만 `/utf-8`가 들어갔다. CUDA는 host compiler가 별도라 `/utf-8`가
전달되지 않았다.

### 3. 변경 구조
nvcc는 `/utf-8`를 직접 받지 못하므로 `-Xcompiler`로 MSVC host compiler에 전달한다.
`add_compile_options($<$<AND:$<COMPILE_LANGUAGE:CUDA>,$<CXX_COMPILER_ID:MSVC>>:-Xcompiler=/utf-8>)`
추가(`CMakeLists.txt:38-41`).
첫 시도는 `COMPILE_LANG_AND_ID:CUDA,MSVC`였으나 CUDA의 compiler id가 `NVIDIA`라
매칭에 실패했다. nvcc 명령줄에 `-Xcompiler="/EHsc -Ob2 /utf-8"`가 포함되는 것을
확인했다.

### 4. 해결된 상황
C4819 발생 0건. CUDA architecture(`compute_75/86/89`)와 runtime 동작은 불변이다.

### 5. 검증
- `cuda_backend.cu` 강제 재컴파일: C4819=0 / warning=0 / error=0,
  `msf_cuda.lib` 생성 확인.
- GPU Release build + CTest 전체: **103/103 PASS**, 경고 0건.
- CPU Release build + CTest 전체: **102/102 PASS**.

### 6. 향후 영향
빌드 옵션 추가만 있고 소스/ABI 변경이 없다. 다음 후보: nvcc 자체 경고의
release gate 등록 여부 결정.
