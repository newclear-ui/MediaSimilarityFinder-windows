# MediaSimilarityFinder v0.9.4.117 — Bulk result-apply stall removed (deferred chunked fill + metadata request storm fix)

Baseline `0.9.4.116` -> this build `0.9.4.117`.
CPU CTest **123/123**, GPU CTest **124/124** (including the new `group_fill_probe`).
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged.

## 1. Why it was needed

Field observation (0.9.4.115 session): the GUI event loop stalled for a long time when a Load completed (supervisor log `health quiet 1/3` = 10 s+; later analysis suggested minutes). Adopted as "next-build candidate 1 (GUI large-list rebuild performance)".

**Measured baseline (new `group_fill_probe`, the user's exact shape: a synthetic 9,055-group / 18,110-file apply)**:
- One synchronous `onResults` = **609,668 ms (10 min 9 s)**, event-loop ticks = 1 (total freeze).
- Stage split (1,000 groups): maps 1 ms / matches 3 ms / **rebuild 65,856 ms** / fill 1,926 ms / tail 5 ms.

## 2. Previous structure and defects (multiple)

1. **Metadata request storm in `rebuildGroups()` (the dominant cause)**: for every tied group (same best%) the sort called `filePixels()`, and `filePixels -> fileResolution` **issues a backend FILE_META request on a cache miss**. The user's index has thousands of 100.0% tied groups -> one request per path per apply (synthetic 1,000 groups = 2,000 requests -> 65.9 s). On the loopback (in-process engine) the request runs synchronously and, when `dimensionsFast` fails, **falls back to an ffprobe child process per path**.
2. **Synchronous bulk fill in `fillPair()`**: two widget items per group (tree + grid, with texts/check/tooltip) created in one synchronous loop -> tens of seconds at 9,055 groups.
3. **`thumbCatchUpVisible()` full-row scan**: `visualItemRect()` called for **every row** (9,000+ calls) - another stall factor on large applies.

## 3. New structure

- **(1) `filePixels` is now cached-only** (mainwindow.cpp): the tie sort uses only already-cached resolutions and degrades to size/path order otherwise. **No backend requests and no ffprobe fallbacks during a rebuild** (per-file metadata requests still happen only on the displayed file list/detail paths).
- **(2) Deferred chunked fill**: when a `fillPair` full rebuild exceeds 800 rows it is **deferred via `GroupFillJob`**; 100 rows are added per event-loop turn (per-chunk `setUpdatesEnabled`/`blockSignals` guards) so the UI keeps responding. A **generation counter (`fillGen_`)** cancels stale jobs whenever a newer fill starts (append/rebuild/tab switch/sort/search); an append arriving while a deferred job is mid-flight is demoted to a full rebuild. On completion: anchor restore, `thumbCatchUpVisible`, and a `groupFill done rows=N ms=M` log.
- **(3) `thumbCatchUpVisible` visible-window bound**: the visible row range is derived via `itemAt` and only that window (+/- 4 rows) is checked; a full-range fallback covers the rare unresolvable case.
- **(4) Permanent stage telemetry**: `resultsApply files=... rows=... groups=... maps/matches/rebuild/fill/tail ms` plus the `groupFill done` completion line (`%TEMP%\msf_scan.log`).
- **Regression probe `group_fill_perf_probe` (CTest `group_fill_probe`)**: feeds 9,055 groups through the real `onResults` path and asserts (a) the call returns promptly (<1500 ms fails), (b) timer ticks >= 3 during the fill, (c) both panes end with 9,055 rows. **Pre-fix FAIL reproduced** (applyMs=609,668 ms, ticks=1).

## 4. What is fixed

- The synchronous block in result application is gone: applyMs **609.7 s -> 84 ms** (9,055 groups), rebuild **65.9 s -> 3 ms** (1,000 groups), and the fill proceeds **asynchronously for 18.1 s with 91 timer ticks** (UI keeps responding).
- The field's "freeze for seconds-to-minutes after Load" becomes a list that fills progressively while the window stays responsive. The same applies to large rebuilds at scan end, sort changes, and tab switches.

## 6. Future impact and limits

- Display (performance) only: verdicts/storage/protocol/engine/DB/schema/cache unchanged.
- The remaining total fill time (9,055 rows ~ 18 s, ~2 ms/row = tree+grid widgets) is acceptable as a visible, progressive fill — future candidates if needed: lazy fill of the hidden pane, model/view separation, or a persistent index. (Recorded as revisit conditions.)
- `kDeferFillMin=800`: small lists (tests, ordinary folders) keep the previous synchronous behavior.
- The resolution-first tie ordering recovers naturally once the cache is populated (the price of removing the request storm - display order only).
