`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` / `kProtocol 1` unchanged (judgement/schema unchanged).

## 1. Why the change was needed

- External re-review: the `.151` adoption code deletes from `content_hash` with a non-existent `path` column (P0). With any row to delete, the SQL fails and the whole adoption rolls back (Test 1h passed only because it had nothing to delete).
- Three P1 re-reviews: (a) does wholesale scratch `meta` adoption contaminate global state (`match_baseline`) on partial scope; (b) after a final save failure, does the GUI keep showing streamed-but-unpersisted matches; (c) does SAVEPOINT guarantee crash durability.

## 2. Previous structure

- The `.151` scoped deletes used `WHERE path IN ...` for four tables. The `content_hash` PK is `rel`.
- Meta was upserted regardless of scope. A partial scope's `match_baseline` was copied although the out-of-scope subgraph was never verified.
- On final save failure only `failed()` was emitted while the view kept the streamed accumulators (the DB kept the old set).
- In-scan checkpoints succeed inside the transaction (SAVEPOINT) but vanish on a forced kill before the outer commit.

## 3. New structure

- **P0**: explicit per-table key mapping. `content_hash` deletes use `rel` computed by `canonicalRelativePath(root, path)` — the same function the writer uses. Unmappable rows are kept (a stale cache row is harmless; a failed DELETE rolls back everything).
- **P1 meta**: meta is adopted on full scope only; partial scope keeps the main index's meta. The next A/AB scan then runs one forced full verification on a missing `match_baseline` (safe direction).
- **P1 save failure**: the failure message carries `|msfChanged=N`; with N > 0 the GUI silently reloads the last committed set (discards the temporary stream = restores the last committed view). The baseline is also invalidated so the next A/AB scan heals the file-row/match-set mismatch by full re-verification (one meta-key delete, no data delete).
- **P1 checkpoints**: code kept (SAVEPOINT = no more silent failures + in-transaction visibility). The kill-durability claim is withdrawn: matches vanish on a forced kill before the outer commit. File-row checkpoints (engine commits) stay valid. A broader transaction redesign is split off as separate design work.
- Regression pins: e2e `Test 1h` extended (deleted file's content_hash rel removed + adoption succeeds, ignored rows preserved, baseline preserved, production scan observes `forceFullPass`). New e2e `Test 1h2` (write-locked adopt → failure + full rollback verified → retry after unlock succeeds + full-scope baseline adopted). `crash_diagnostics_test` §4 kept. New `ui_persist_fail_test`: in-process loopback save failure → reason delivered + view == DB (old set) + retry succeeds. `database_test` savepoint section (nested save works, vanishes on rollback, pre-existing data kept).

## 4. Resolved state

- Adoptions with rows to delete no longer roll back on `content_hash`.
- Partial adoption no longer contaminates the global baseline. The next scan was observed performing the full verification (`matchBaseline=forceFullPass` in the backend log).
- After a save failure the view matches the DB (re-applied), and retry scans normally.
- In-scan checkpoint failures are no longer silent (logged). Kill durability is reported as unproven.
