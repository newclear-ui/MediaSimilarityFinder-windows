# MediaSimilarityFinder v0.9.4.74 — 감사 통합, telemetry 종료 크래시 수정, 진행률·재개

기준선 `0.9.4.73` → 본 빌드 `0.9.4.74`.
CPU CTest **116/116**, GPU CTest **117/117**.
`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.4` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — 전부 불변. 검색 판정 의미 변경 없음.

## 1. 변경 필요성

사용자는 CPU가 1–2%인데 디스크 I/O가 많고, 신규 파일 구간에서 읽기 완료가
멈춘 것처럼 보이며, Backend 종료 후 재시작만 되고 검색은 이어지지 않는다고
보고했다. ChatGPT/Claude/Kimi/Grok/Meta 감사 내용을 현재 C++/Qt 코드, 로그,
덤프에 대조했다.

사용자 `.72` 로그/덤프의 확정 내용:

- `backend process exited unexpectedly — scan aborted`는 Supervisor가 만드는 문구.
- exit code `-1073740791` = `0xC0000409`, parameter `0x7` =
  `FAST_FAIL_FATAL_APP_EXIT` (abort/terminate 계열), fault RIP은
  `ucrtbase.dll+0xA527E`. 로그에는 backend health watchdog 종료가 없었다.
- heartbeat에서 `walked=7340` 후 정지; 이후 새 scan의 `listed=8000`은 scan start
  때 초기화되지 않은 이전 값이었다. `.72` Backend에는 matching PDB가 없어 실제
  사용자 dump의 caller는 특정할 수 없다.
- Windows Application Event 1000 두 건도 같은 Backend image timestamp
  `0x6AC7686B`, `ucrtbase.dll`, exception `0xC0000409`, offset `0xA527E`를
  기록했다(2026-10-08 19:28:45 / 19:33:05).

별도 결정적 재현: `MSF_TEST_THROW_WALKER`로 walker 예외를 주입하자 `scan_streaming_test`
가 동일한 `0xC0000409`로 죽었다. 이 테스트 dump를 PDB로 심볼화한 결과:
`TelemetryRecorder::~TelemetryRecorder` → `MediaSearchEngine` → `ScanWorker`.
예외가 `engine.scan()`을 빠져나가면 `finishScan()`이 sampler를 stop하지 않으며,
joinable `std::thread` 소멸이 `std::terminate()` → `abort()`를 일으켰다.

## 2. 기존 구조와 감사 대조

- **크래시 문구/재시작**: Supervisor는 process exit 때 고정 실패를 내고 재시작만
  했다. scan config를 저장하거나 `START_SCAN`을 재전송하지 않았다. `.73`의
  auto-resume는 `failed`/`backendConnection(false)` 순서에 의존해 실패 플래그가
  제때 설정되지 않고, modal 오류창이 후속 처리를 막을 수 있었다.
- **재시작 지연**: unexpected-exit 경로가 `failed()`(GUI modal) 신호를 먼저 내고
  `scheduleRestart()`를 나중에 호출했다. Qt direct connection이 `QMessageBox::critical`
  안에서 기다리므로 사용자가 닫을 때까지 restart timer가 예약되지 않았다.
- **CPU/I/O**: `Scanner::scan_stream::quick()`은 인덱스된 파일도 포함해 media마다
  앞 64KB를 읽는다. `size/mtime/quickHash` 비교는 그 뒤에 있으므로 unchanged도
  quick-hash I/O를 한다. 이는 I/O-bound 저 CPU를 설명하며 worker allocation 결함의
  증거는 아니다. `Scanner::count()`는 분모를 위해 scan 전에 전체 디렉터리를 한 번 더
  훑었지만 progress callback이 없었다.
- **읽기 카운터**: 기존 `walked`는 consumer의 `processOne()`에서 증가했다. 신규 이미지
  batch의 동기 `processImageBatch()` 동안 consumer는 멈추고, walker는 bounded queue
  안에서만 앞서갈 수 있어 read count가 얼어 보였다. `lastListN_`도 새 scan에서 초기화되지 않았다.
- **다른 감사 후보**: backend `send()`의 synchronous stdout flush는 backpressure 위험
  후보지만, 수집된 종료는 health-watchdog가 아니라 direct abort였다. 이 dump의 원인으로
  확인되지 않아 이 빌드에서 전송 아키텍처는 바꾸지 않았다. Python launcher/venv/DLL
  가설은 이 C++/Qt repository와 맞지 않아 적용하지 않았다.

## 3. 변경 구조

- **Telemetry sampler RAII** (`src/benchmark.h/.cpp`): `TelemetryRecorder` destructor가
  `stopSampler()`를 호출해 sampler thread를 항상 stop/join한다. `ScanWorker::run()`의
  두 catch 경로도 `engine_.abortTelemetry()`를 try/catch로 시도한다.
- **Walker/consumer 예외 안전** (`src/media_search_engine.cpp`, `src/scanner.*`):
  walker 예외는 `walkError`로 기록된다. consumer 예외는 `exception_ptr`로 보관되고,
  내부 `walkAbort` + queue shutdown으로 producer를 깨운 뒤 walker를 join하고 재던진다.
  `ScanCallbacks::shouldStop`은 내부 abort와 사용자 cancel을 분리한다.
  `MSF_TEST_THROW_WALKER` regression seam으로 실패 경로를 검증한다.
- **병렬 quick 실패 fallback** (`src/scanner.cpp`): `std::async` fan-out 스케줄링이
  실패하면 serial `quick()` pass로 폴백한다.
- **count/walk 진행 표시** (`src/scanner.*`, `src/scan_worker.cpp`): `Scanner::count()`에
  optional progress callback(2,000 filesystem entries)을 추가하고
  `scanPhase=count begin/done`과 `scanPhase=engine begin/done`을 로그한다.
  `walked`는 기존 consumer 의미를 보존하고, 신규 `readProgress`는 quick-hash 후
  bounded queue에 들어간 in-scope/non-ignored 파일을 보고한다. UI의 read-complete는
  producer 진행을 보며, ahead 폭은 queue 용량으로 bounded다. listing callback은
  hash batch마다 나오며 `lastListN_`, `lastPct_`, `lastPath_`는 scan start에 reset한다.
- **재시작/재개** (`gui/backend_supervisor.cpp`, `gui/mainwindow.*`): Supervisor는
  restart timer를 `failed()` UI 신호보다 먼저 예약한다. MainWindow는 정확한
  `BackendScanConfig`를 저장하고 READY 재연결 후 1회 자동으로 같은 설정을 재실행한다.
  첫 backend crash는 modal dialog로 재시작을 막지 않고 상태 문구를 표시한다. 재차
  실패하면 modal error를 보인다. 종료 로그와 오류 메시지에 exit status/code를 포함한다.
- **덤프 분석 설정 문서**: runbook에 GUI와 Backend exe 각각의 WER LocalDumps 키를
  명시하고 matching PDB 보관을 요구한다.

## 4. 해결된 상황

- 예외가 scan sampler 수명보다 먼저 나도 telemetry sampler 소멸이 abort를 일으키지
  않는다. walker 예외는 기록된 scan failure로 전달된다.
- Backend 재시작이 사용자 modal 응답을 기다리지 않고 예약되며, READY 후 scan이
  checkpoint/index를 사용해 한 번 자동 재개된다.
- pre-count 동안 listing progress가 보이고, scan 간 stale heartbeat 값이 재사용되지 않는다.
- 신규 파일 batch 분석 중 read-complete는 consumer가 batch를 끝낼 때까지 멈추는 대신
  producer queue admission을 반영한다. `walked` API consumer 의미는 그대로 유지한다.

## 5. 검증 및 감사 결론

```
CPU Release CTest  100% tests passed out of 116
GPU Release CTest  100% tests passed out of 117
backend_e2e_test: forced kill -> READY -> saved-config auto-resume -> FINISHED
scan_streaming_test: count/list progress + producer read count + injected walker exception
GUI/Backend --version 0.9.4.74
CPU/GPU Release PDBs: GUI + Backend PDBs present
```

`scan_cancel_drain_test`/`scan_cancel_video_test`는 처음에 producer read count를 기존
consumer `walked` callback으로 덮어쓴 변경 때문에 exact counts가 깨졌다. callback을
분리해 기존 취소/배치 semantics를 보존한 뒤 CPU/GPU 전수 테스트 통과.

**확실도**:

- 확인: popup 경로, 이전 자동 재개 부재/실패 순서, count progress 공백, quickHash 재읽기,
  batch 중 consumer counter pause, stale listing, telemetry destructor abort path.
- 강한 원인 후보: telemetry sampler join 누락이 사용자의 `.72` abort를 일으켰을 가능성.
  결정적 seam에서 동일 코드·offset을 재현하고 수정했으나, 구 dump에 PDB가 없어 사용자의
  exact caller 동일성은 증명 불가.
- 미측정 위험: synchronous stdout backpressure stress. 이번 직접 abort의 원인으로는
  로그 증거가 없어 확정하지 않았다.

## 6. 향후 영향

- 사용자의 .74 재현에서 `scanPhase=count` elapsed, `scanPhase=engine`,
  `alive ... walked=... listed=...`로 정체 구간을 분리한다.
- 다음 Backend dump는 .74 matching PDB로 심볼 해석한다.
- 디스크 I/O는 여전히 클 수 있다. unchanged 파일도 same-size/same-mtime content
  change를 감지하기 위해 64KB quickHash를 매 scan 읽는다. 이를 생략하면 정확성 정책이
  바뀌므로 이번 감사에서는 수정하지 않았다.
- `processImageBatch`/video range의 동기 batch 처리와 queue backpressure는 유지한다.
  read counter는 queue admission까지 보이고, 실제 분석 완료는 별도 Index Complete row다.
- backend stdout pipe backpressure는 별도 stress test 대상으로 남긴다.
- `ExactnessPolicy::RefuseAll` 유지, Node E 종결 상태 불변.
