## 1. Why the change was needed

Post-0.9.4.59 review confirmed two semantic bugs. First, the generation stamp
reused the general `seen` set (deletion detection, includes ignored and
out-of-scope files) as admission evidence, and the completed path never checked
scope at all, so an image-only scan could rewrite the video generation.
Second, `finishScan(false)` inferred the terminal state from the live cancel
flag, so a DB failure followed by a Stop misreported Failed as Cancelled.
Third, the `setSamplingGeneration()` return value was ignored.

## 2. Previous structure

- Cancel-path stamp condition based on `seen`. Ignored and out-of-scope videos
  sit in `seen`, so they wrongly counted as evidence
- Completed path stamped unconditionally on `r.completed`. No video-scope check
- Terminal inferred from the live `control->cancel` value
- Stamp write failure ignored

## 3. New structure

- Split `videoScopeSeen`: recorded only past the ignored check, the media-scope
  check, at the actual video admission boundary. `seen` keeps deletion duty
- Shared stamp invariant (completed and cancelled alike): `scanVideos=false`
  never touches the generation. Written only when every pre-existing video row
  sits in `videoScopeSeen`. Ignored legacy rows hold the old value, so
  unignoring them re-analyzes instead of reusing stale fingerprints
- `ScanTerminal { Completed, Cancelled, Failed }`. Each return path passes its
  meaning explicitly. DB/checkpoint/commit failures report Failed regardless of
  a later Stop. `VideoRangeResult` semantics kept
- A failed stamp write keeps the old value (next scan safely regrids) and never
  fails or rolls back the already-committed search results. Return checked

## 4. Resolved situation

- Image-only scans (completed and cancelled) never touch the video generation
- Ignored stale rows are not promoted; unignoring re-analyzes them
- DB failure plus Stop reports telemetry failed=true, cancelled=false, with the
  transaction rollback kept
- A failed stamp leaves a valid completed scan; the next scan regrids

## 5. Verification

### New `scan_generation_scope_test` (35 checks, PASS on CPU and GPU)

- D (image-only): completed scan reuses images, admits no video, keeps "0".
  Cancelled case also keeps "0". Fails on old code (unconditional stamp)
- E (ignored): completed scan with one ignored video keeps "0". Unignored
  rescan re-analyzes everything (regrid exact). Fails on old code (seen reuse)
- F (stamp failure): meta trigger blocks the write -> scan completes, analysis
  intact, "0" kept, no failure recorded. After dropping the trigger the rescan
  regrids and the stamp recovers to "3"
- G (DB error + cancel): files trigger plus walked cancel -> completed=false,
  telemetry failed:true/cancelled:false, rollback verified directly (0 rows),
  retry completes after the fault is removed. Fails on old code (live inference)
