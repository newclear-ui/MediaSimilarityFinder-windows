# MediaSimilarityFinder v0.9.4.73 — 백엔드 크래시 방어 + PDB 활성화 + 스캔 자동 재개

기준선 `0.9.4.72` → 본 빌드 `0.9.4.73`.
CPU CTest **116/116**, GPU CTest **117/117**.
`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.4` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — 전부 불변. 검색 판정 의미·동작 변경 없음.

## 1. 변경 필요성

사용자 보고(0.9.4.72 실행 중, `G:\Downloads\ss_twit`):

- 디스크 I/O는 대량인데 GUI/백엔드 CPU가 각각 1%/2%로 낮고, 인덱스된 파일은
  빠르게 지나가나 신규 파일에서 "읽기 완료"가 진행되지 않는다.
- 검색 도중 **"backend process exited unexpectedly — scan aborted"** 팝업이 뜨고
  종료된다. supervisor가 백엔드를 재시작하지만 **검색을 이어서 하지 않아** 사용자가
  다시 시작을 눌러야 한다.

`%TEMP%\msf_scan.log`와 `%LOCALAPPDATA%\CrashDumps`의 백엔드 덤프 2건
(`MediaSimilarityFinderBackend.exe.{51136,11660}.dmp`, 2026-10-08 07:33/07:28)을
확보해 분석했다.

- 종료 코드 **`-1073740791` = `0xC0000409`**, 파라미터 **`0x7` =
  `FAST_FAIL_FATAL_APP_EXIT`**: `abort()`/`std::terminate` 계열 fail-fast.
- 덤프 fault 스레드 RIP = `ucrtbase.dll+0xA527E` (abort 내부, `int 29h`).
  이는 런북 3-1/3-2에 기록된 **동일 오프셋(결정적 abort 경로)**와 일치한다.
- 크래시 전 heartbeat는 `walked=7340`(1차)·`walked=0`(2차), `lastPct=0`으로
  walk가 완료되지 못했고, walk 단계에서 stall한 뒤 ~5분 후 사망했다.
- **Release 빌드에 PDB가 없어**(CMakeLists에 PDB 설정 부재) fault 함수를 특정할
  수 없었다. 런북은 fault 스택을 요구하므로 이는 분석 공백이다.

## 2. 기존 구조

- walker는 `std::thread walker([&]{ ... s.scan_stream(...); ... })`로 별도
  스레드에서 실행되며 **try/catch가 없다**. 0.9.4.72에서 `scan_stream`이
  `std::async`(bounded pool)를 호출하도록 바뀌어, 스케줄링 실패 시 예외가 이
  스레드 밖으로 나가면 `std::terminate -> abort`로 직행한다.
- `ScanWorker::run`은 `catch(std::exception)`/`catch(...)`로 감싸져 있으나,
  walker 스레드는 그 보호 밖이다.
- Release 빌드는 PDB를 만들지 않아 WER/덤프가 module+offset만 남긴다.
- 백엔드가 스캔 중 비정상 종료하면 supervisor는 재시작만 하고, GUI
  `onBackendConnection(false)`는 `scanFailed`(팝업 + idle)로 끝낸다. 재연결
  (`backendConnection(true,"ready")`)은 시작 버튼만 다시 활성화한다.

## 3. 변경 구조

- **walker 스레드 예외 안전 (`src/media_search_engine.cpp`)**: walker 본문을
  `try{...}catch(...){ walkError.store(true); }`로 감싸고, 소비 루프 종료 후
  `walkError`면 `failed=true`로 승격한다. 이제 walker에서 예외가 나가도
  프로세스를 종료시키지 않고 **기록된 스캔 실패**로 격하된다(런북 4항과 동일 원칙).
- **병렬 해시 fallback (`src/scanner.cpp`)**: `flushBatch`의 `std::async` 팬아웃을
  try/catch로 감싸 실패 시 **순차 quick()로 폴백**한다. 스케줄링 실패가 walker로
  전파될 경로 자체를 제거한다(항상 진행, 예외 0).
- **PDB 활성화 (`CMakeLists.txt`)**: Release에서 CXX에 `/Zi`, 링커에 `/DEBUG`를
  추가해 GUI/Backend PDB를 생성한다(`MediaSimilarityFinder.pdb` 등). nvcc에는
  `/Zi`를 넘기지 않도록 CXX 전용으로 제한한다(넘기면 MSB3721). 코드 생성은 불변.
- **스캔 자동 재개 (`gui/mainwindow.{h,cpp}`)**: `startScan()`(사용자 시작)과
  `beginScan()`(실행 본문)을 분리. 백엔드 크래시로 스캔이 중단되면
  `scanCrashed_=true`를 기록하고, supervisor가 READY 재연결을 알리면 **1회 한정**
  으로 `beginScan()`을 다시 호출해 검색을 이어간다. 엔진이 진행 상황을
  checkpoint하므로 재-walk는 인덱스된 파일을 빠르게 건너뛰고 이어서 갱신한다.
  사용자가 새로 시작하면 예산이 초기화된다.

## 4. 해결된 상황

- walker 스레드의 미처리 예외로 인한 프로세스 종료 경로를 제거했다(기록된 실패로
  전환).
- `std::async` 스케줄링 실패가 나도 walk가 순차 모드로 계속 진행한다.
- 이제 크래시가 나면 PDB로 fault 함수를 특정할 수 있다(런북 요구 충족).
- 백엔드 크래시 후 사용자가 다시 시작을 누르지 않아도 검색이 1회 자동 재개된다.

## 5. 검증

- CPU Release CTest 116/116, GPU Release CTest 117/117. 양쪽 exe --version 0.9.4.73.
- PDB 생성 확인: `MediaSimilarityFinder.pdb`(GUI) / `MediaSimilarityFinderBackend.pdb`.
- walker 예외/`async` 실패 경로는 기존 스캔 회귀 테스트(scan_streaming,
  walker_queue, backend_e2e 등) 전수 통과로 확인. 새 결정적 시드는 추가하지 않았다.
- 자동 재개는 MainWindow 경로이며 백엔드 프로세스를 요구하므로 단위 CTest 대상이
  아니다. supervisor 재시작은 `backend_e2e_test`가 계속 커버한다(통과).

## 6. 향후 영향

- **크래시 root cause는 미확정**이다. 이번 빌드는 (a) 미처리 예외를 graceful
  failure로 격하하고, (b) PDB를 켜서 다음 크래시를 심볼 해석 가능하게 만들며,
  (c) 자동 재개를 제공한다. fault 함수를 특정하려면 0.9.4.73 PDB가 있는 상태에서
  재현 덤프를 다시 확보해야 한다(런북 절차).
- stall(저 CPU·진행 정지)의 근본 원인(신규 파일 구간)은 별도 추적이 필요하다.
  0.9.4.72의 walk 병렬화는 저속 드라이브에서 5배 향상을 확인했으나 사용자
  환경의 stall을 완전히 해소하지 못했다. 다음 후보: 특정 파일의 `quick()` 64KB
  읽기 지연/행(hang), 신규 파일 분석 단계의 정체.
- HDD/네트워크 대상 walk 병렬도 재검토 조건 유지.
- `ExactnessPolicy::RefuseAll` 유지, Node E 종결 상태 불변.
