## 1. Why the change was needed

- User directive: build software decode by default but actively use hardware; assume H.264/H.265/AV1 support; bottom-bar indicator; config-file recording; enable NVDEC on this NVIDIA PC; F-2 revisit; test on temp videos; DirectX review next build.
- F-2 revisit outcome: FFmpeg D3D11VA path instead of the native CUDA/NVDEC API. On this PC D3D11VA drives the NVDEC silicon, so it equals "turning on NVDEC" in effect. The vcpkg FFmpeg has no cuvid/nvdec (verified locally), so the native path needs toolchain work and overlaps the F-1 suspension — out of this build's scope.

## 2. Previous structure

- `VideoDecoder::open()` opened software decoders only. No HW code existed.

## 3. New structure

- `open()`: tries D3D11VA first (one process-wide device); falls back to software on failure. `MSF_VIDEO_HW=off` forces software.
- Received D3D11 frames are downloaded to system memory (`av_hwframe_transfer_data`) before the existing sws path. Download failure pre-emit restarts once in software (identical fingerprint or clean failure); post-emit follows the existing sweep-failure contract.
- `VideoBuildStats.hwUsed/hwBackend/hwCodec/hwFallbacks` → `telemetry_.addVideoHw` → additive `videos.hwFiles/videos.hwFallbacks` (measured/null convention kept). `AnalyzeTelemetry.videoHwFiles/videoHwFallbacks` sums included.
- Engine cumulative counters + backend status (`hwAvailable/hwBackend/hwUsed/hwCodecs`) → IPC → GUI bottom-bar `hwLbl_` ("HW:d3d11va x12" / "SW"). QSettings records: `ui/hwDecode` (setting), `ui/hwAvailable`, `ui/hwBackend`, `ui/hwUsed`, `ui/hwCodec/<codec>`.
- Settings>General gains a "Hardware decode" checkbox. Off propagates as `MSF_VIDEO_HW=off` at the next backend (re)start (spawn-time value is sticky).
- Only native H.264-family decoders offer a HW branch in this build; the native mpeg4 decoder has none and stays software (measured).
