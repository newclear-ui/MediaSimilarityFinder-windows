# MediaSimilarityFinder v0.9.4.160 — quickIdentity 캐시 식별 신뢰성 핀 (P2)

기준선 `0.9.4.159` → 본 빌드 `0.9.4.160`.
CPU CTest **134/134**, GPU CTest **135/135** (신규 CTest 1건: video_cache_identity_test).
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 10` / `kProtocol 1` 전부 불변.

## 1. 변경 필요성

- 외부 리뷰 P2 지적: 캐시 식별이 `path + size + mtime + quick_hash(앞 64KB)` 중심이다. 앞부분 64KB 해시와 size/mtime 게이트가 실제로 동작하는지, 그리고 어디까지가 잔류 위험인지 제품 테스트로 고정한 바가 없었다.

## 2. 기존 구조

- `quickIdentity()`: 앞 64KB FNV-1a. `memoryLookup`/`loadPersistent`가 path·size·mtime·quick·version·policy 6중 키로 조회한다. 꼬리만 바뀐 파일(앞 64KB·size·mtime 동일)은 구키로 히트한다.

## 3. 변경 구조

- 제품 코드 변경 없음. 회귀: `video_cache_identity_test` 신규 — 동일 path·별도 DB로 케이스 격리, mtime 강제 복원으로 키 요소만 단독 변화:
  - control: 동일 파일 재빌드 히트 + 해시 안정.
  - (A) 앞바이트 변경(동일 size+mtime): 미스 확정. quick 게이트가 우회되면 stale true가 되어 실패한다.
  - (B) mtime 증가(동일 내용): 미스 확정.
  - (D) 64KB 이후 꼬리 변경(동일 size+mtime): stale 히트를 문서화된 잔류 위험으로 핀. 디코딩 가능한 오프셋을 캐시 없는 엔진으로 먼저 탐색하므로 디코더 관용도에 의존하지 않는다.
- 전체 파일 해시 전환은 기각 유지: 수 GB 영상에서 매번 추가 I/O가 발생하므로 현재 비용 대비 위험이 정당화되지 않는다. 재검토 조건: tail-only 변조가 실측에서 문제가 된 경우.

## 4. 해결된 상황

- 식별 게이트 3종(앞부분·mtime·control)이 테스트로 고정됐고, 잔류 위험 1종(tail-only)이 의도된 동작으로 문서화됐다.
