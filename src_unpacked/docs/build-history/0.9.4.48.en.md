# MediaSimilarityFinder v0.9.4.48 — GUI Stop unresponsiveness fix

Baseline `0.9.4.47` -> this build `0.9.4.48`.
CPU CTest **104/104**, GPU CTest **105/105** (previous 103/104 plus one new test).
`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.4` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — all unchanged.

## 1. Why the change was needed

After starting a search in the GUI, pressing Stop showed only a "stopping"
message while the actual search continued for 10+ minutes with sustained disk
read I/O.

Pressing Stop and the search actually stopping are different things. The UI
message marks only the start of the request.

## 2. Previous structure

The Stop button correctly set the flag via `MainWindow::cancelScan()` ->
`ScanWorker::cancel()` -> `control_.cancel.store(true)`. The break was after
that.

Every `MediaSearchEngine::scan()` unconditionally ran this at startup:

```cpp
telemetry_.setDatasetFingerprint(msf::computeDatasetFingerprint(root));
```

`computeDatasetFingerprint()` reads **every file from first byte to last** to
build a SHA-256 manifest. It had no cancellation parameter, so it never saw a
Stop request. On a large dataset that is hundreds of gigabytes of reads,
taking 10+ minutes.

Cancellation coverage by phase:

| Phase | Stop honored |
|---|---|
| `computeDatasetFingerprint` (scan start) | **no** — fixed here |
| `Scanner::count` pre-walk | yes (checked per file) |
| `scan_stream` walker | yes (checked per file) |
| walk consume loop / batch / video range | yes |
| inside `imageBatch` | no (but bounded by batch size) |
| single video FFmpeg decode | no (but bounded by one file) |
| final `pipe.analyze` | yes (`stopCheck` is passed) |

The 10-minute symptom is dominated by the first row. The rest are bounded or
already checked.

## 3. New structure

### Cancellation plumbed into `computeDatasetFingerprint`

```cpp
// before
DatasetFingerprint computeDatasetFingerprint(const std::string& root);
// after
DatasetFingerprint computeDatasetFingerprint(const std::string& root,
                                             const std::atomic_bool* cancel = nullptr);
```

- Checked before each file and during large file reads (every 64 KiB chunk).
- On cancel it returns immediately with `state="cancelled"` and no partial
  manifest. A partial fingerprint would be a dishonest identity.
- `"cancelled"` is a telemetry-only state. `dataset.state` is only serialized
  to JSON and no consumer branches on it (the S6 code uses the hash string).
- The default argument keeps all ~20 existing callers compiling unchanged.

### Wired from scan()

```cpp
telemetry_.setDatasetFingerprint(
    msf::computeDatasetFingerprint(root, control ? &control->cancel : nullptr));
```

When the fingerprint is cancelled the walk exits on the next file, batches and
videos have nothing in flight to drain, and post-walk runs over an empty DB.
Stop latency shrinks from minutes/10+ minutes to **seconds**.

## 4. Resolved situation

- Stop request -> fingerprint aborts immediately (`state="cancelled"`) -> walk
  exits -> worker returns -> GUI back to idle
- Normal completion and cancellation stay distinct (`completed=false`, report
  intact)
- The DB is not corrupted by a cancel, and a rescan completes normally
- `added`/`modified`/`analyzed`/`failed` meanings for normal files are unchanged

## 5. Verification

### New regression test `cancel_fingerprint_test` (11 checks, PASS on CPU and GPU)

Driven through the production path (`openIndexForRoot` + `scan`).

- With cancel pre-set the fingerprint returns `state="cancelled"`, no hash, zero
  files, immediately (0.3 ms). The old code would have read everything first
- Without cancel the same 20 files measure normally (`measured`, 64-hex)
- A pre-cancelled scan reports `completed=false` with zero analysis
- After a cancel the DB reopens and a normal scan completes (`scanned=20,
  analyzed=20`)

No timing assertions. The verdict is the state (`cancelled` vs `measured`), so
it is deterministic.

### Relationship to the existing test

`scan_cancel_test` (6 tiny files) verifies flag-set -> incomplete -> resume but
never passes through the fingerprint phase, so it could not catch this bug. The
new test fills that gap. They complement each other; neither replaces the other.

## 6. Future impact

- Stop works promptly on large datasets. A cancelled fingerprint stays in
  telemetry only and never affects scan behavior.
- Single-video FFmpeg decode and the inside of an image batch remain bounded
  waits. They cannot exceed one file's work, so they are unrelated to the
  10-minute symptom.
- The `mbstowcs` in `image_decoder.cpp:161` and the ffprobe ACP paths are out
  of this scope.
- Next gate: S4 GUI real-screen acceptance (needs user-side verification),
  `color_thumb` R1.
