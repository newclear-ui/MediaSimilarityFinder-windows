# MediaSimilarityFinder v0.9.4.28 — D2 CreateDecoderFromFilename Internal Cost / WIC Decoder Entry-Path Comparison

Status: **PRE-REGISTERED** (committed before any D2 code change)

D2 is a **measurement** build. It does not optimize.

---

## 1. Change Need

D1 closed two questions and left one open.

```text
D9d: decode ≈ 4.4654 ms/call
D1:  CreateDecoderFromFilename ≈ 2.6257 ms/call
     OS CreateFileW reference   ≈ 0.0576 ms/call
     Factory2 25,898 attempts / 25,898 successes / 0 fallbacks
```

D1 established that the `open` bucket is 97.8 % WIC-internal and that neither
the Factory2 fallback nor raw OS file I/O explains it. It could not go further
because `CreateDecoderFromFilename` is a single opaque call.

D2 therefore does **not** assume that another WIC entry point is cheaper. It
measures the alternatives.

The dangerous inference this build exists to prevent:

> "`CreateDecoderFromFilename` is slow, therefore `CreateDecoderFromFileHandle`
> or `CreateDecoderFromStream` must be faster."

That is a guess. D2 turns it into a number or leaves it refuted.

## 3. Dataset Change — This Is a Material Deviation and Is Recorded as Such

**The directive requires a per-format breakdown (§15, §16) and states the D8b
fingerprint must be maintained (§27). Those two requirements conflict, and the
conflict was resolved in favour of the format analysis, with the user
approving the dataset change.**

The D8b dataset is **100 % BMP** — verified by reading the magic bytes of all
2,700 files, not by trusting the extension. A single-format dataset cannot
support the required "JPEG ≠ BMP ≠ PNG" analysis, and generalizing
"WIC decoder costs 2.6257 ms" from BMP alone would be exactly the kind of
over-generalization this directive warns against.

With the user's explicit instruction, samples were selected from
`G:\Downloads\ss_twit`, verified by magic bytes (not by extension), stratified
by file size to avoid bias, and copied into
`C:\project\test_sample_img_vid\images\format\`:

| Format | Files | Sampling |
|---|---:|---|
| BMP (pre-existing) | 2,700 | unchanged |
| JPEG | 200 | size-stratified, <= 1 MB |
| PNG | 200 | size-stratified, <= 1 MB |
| WEBP | 200 | size-stratified, <= 1 MB |
| GIF | 20 | size-stratified, <= 4 MB |

All 620 added files were verified against their magic bytes after copying
(mismatches: 0).

**Consequences, stated up front:**

```text
fingerprint  9b113848…4253c  ->  6ef76b94…c4829c
file count   2,700          ->  3,320
total bytes  36,007,560     ->  100,579,845 (95.9 MB)
```

This means **D2 totals are not directly comparable to the D9a…D1 absolute
totals**, which were all measured on the 2,700-file BMP dataset. Per-call and
per-format figures are comparable; dataset-wide aggregates are not. The report
will state this rather than presenting a D1-vs-D2 total delta as if the dataset
were unchanged.

A first attempt sampled 800 files up to the largest sizes and added 2.16 GB,
which dominated the dataset. That was discarded and re-sampled under the size
caps above, because "an appropriate amount" must not turn a 36 MB dataset into
a multi-gigabyte one.

## 4. D2 Hypothesis

None in the optimisation sense. Three possibilities are all allowed, and the
build is designed to distinguish them:

- **Case A** — a handle or stream entry point is materially faster, implying
  filename-path-specific overhead inside WIC.
- **Case B** — all three are similar, implying decoder activation or codec
  initialisation dominates and the entry point is not the lever.
- **Case C** — the paths differ mainly by file format, implying codec-specific
  decoder initialisation.

## 5. Comparison Paths

The three WIC entry points were confirmed to exist in the Windows SDK headers
(`wincodec.h`, SDK 10.0.26100.0) before any code was written:

```text
IWICImagingFactory::CreateDecoderFromFilename(LPCWSTR, GUID*, DWORD, IWICBitmapDecoder**)
IWICImagingFactory::CreateDecoderFromFileHandle(ULONG_PTR, GUID*, DWORD, IWICBitmapDecoder**)
IWICImagingFactory::CreateDecoderFromStream(IStream*, GUID*, DWORD, IWICBitmapDecoder**)
IWICImagingFactory::CreateStream(IWICStream**)
```

`IWICStream` derives from `IStream`, so it can be passed directly to
`CreateDecoderFromStream`.

| Path | Steps | Role |
|---|---|---|
| **A** | `CreateDecoderFromFilename` | production baseline |
| **B** | `CreateFileW` → `CreateDecoderFromFileHandle` | measurement only |
| **C** | `CreateFileW` → `CreateStream` → `CreateDecoderFromStream` | measurement only |

Path A uses the **same** `metadataOptions`, `desired access` and vendor GUID as
production, so its number is directly comparable to D1's.

Paths B and C are **measurement-only**. They are not wired into `decode()` and
are never adopted as the product path by this build.

## 6. Measured Boundaries

Each metric measures exactly one call, with nothing nested inside another:

```text
fileOpenMs          CreateFileW + CloseHandle          (B and C only; A = N/A)
streamCreateMs      IWICImagingFactory::CreateStream   (C only)
streamInitMs        IWICStream::InitializeFromFilename (C only)
decoderFilenameMs   CreateDecoderFromFilename          (A)
decoderFileHandleMs CreateDecoderFromFileHandle        (B)
decoderStreamMs     CreateDecoderFromStream            (C)
combinedPathMs      A: decoderFilenameMs
                    B: fileOpenMs + decoderFileHandleMs
                    C: fileOpenMs + streamCreateMs + streamInitMs + decoderStreamMs
```

`combinedPathMs` is the sum of its own components and is reported alongside
them, never added to them. Nothing is counted twice.

## 7. Scope

Timers, counters, HRESULT recording, stage counters, profiling telemetry, and
tests validating the instrumentation. D9d's `DecodeTelemetry` is **reused and
extended**; no second telemetry system is created.

The measurement helper lives in `image_decoder.h/.cpp` as an explicit,
separately-called probe. `ImageDecoder::decode` and `decodePreserveAspect` are
**not** given a mode switch, and their behaviour is not altered.

## 8. Non-goals

Not done in D2, per the directive:

```text
switching the product path to FileHandle or Stream
factory / decoder / stream / file-handle reuse
decode deduplication
cache changes
EXIF, metadata option, resize, format conversion, copy changes
threading or parallelization changes
candidate, threshold, grouping, verdict changes
choosing a decoder CLSID from the extension (that would change format probing)
relaxing or deleting any existing test
```

§17 of the directive is respected directly: the extension is **not** used to
pick a decoder. Every path lets WIC probe the format exactly as production
does, so the comparison isolates the entry point and not a format-detection
change.

The Factory2 fallback is not re-opened as a candidate (D1: 0 fallbacks), and
cache mutex is not re-opened (D1: 71.5 ms total). Both are only checked for
regression.

## 9. Accuracy Risk

Decoder creation is instrumented; decoding is not. Requirements:

- `verifyCalls`, `verifyDecodeMisses`, `verifyCacheHits`, `ssimEvals`,
  `frameSsimEvals`, `groups`, and the final verdict unchanged.
- The probe must not alter production decode results. It is a separate entry
  point and is invoked only from the benchmark driver.
- Paths B and C are validated beyond "the call returned success": for each, the
  decoder must yield `GetFrame(0)` and a plausible pixel size. A path that
  creates a decoder but cannot produce a frame is counted as a failure and
  reported, not silently averaged in.

## 10. Compatibility Risk

Paths B and C are measurement-only and compile-guarded to Windows, so CPU-only
and non-WIC builds are unaffected. `image_decoder.cpp` already has a non-WIC
branch; the probe will report `not_available` there rather than fabricate zeros.

`Path C` may legitimately fail for some inputs (a WIC stream initialised from a
filename has different seek semantics). Failures are recorded with their
HRESULT and are **not** hidden by averaging only the successful samples.

## 11. Measurement Plan

- Same hardware, OS, GPU, build configuration and cold-index condition.
- **At least 5 runs**; mean, median, min, max, range per path and per format.
- The three paths are timed within the same run over the same files, so the
  comparison is paired and the run-to-run spread affects all three equally.
- A 1-2 % difference is **not** an improvement in a ~3.7-7.5 % spread.
- Path ordering must not be read as a simple `A < B < C` ranking; the paths do
  different internal work, and the report must discuss **where** a difference
  could arise, per §13.

## 12. Noise Consideration

The first call into a path may pay one-off costs (DLL resolution, codec load)
that later calls do not. A warm-up call per path per format will be performed
and excluded, and this is stated in the report rather than left to chance.

## 13. Stop Conditions

Reduce scope or stop, and record rather than patch around:

```text
1. instrumentation changes a verdict or grouping
2. CPU/GPU parity breaks
3. an existing test fails
4. timing overlap makes the comparison uninterpretable
5. Paths B/C cannot be validated as producing the same image
6. a value would have to be estimated rather than measured
7. the dataset change makes D1 comparison impossible to state honestly
```

Condition 7 is already partly active: the dataset changed, so the report must
decline to present dataset-wide D1-vs-D2 deltas as like-for-like.

## 14. Expected Outcome

Success is a measured cost structure, not a speedup:

```text
1. CreateDecoderFromFilename's cost is compared against two alternative entry
   points under identical metadata options and identical files
2. the result is reported per format, with success/failure and HRESULTs
3. whichever of Case A / B / C holds is identified from the numbers
4. verdict, grouping, parity preserved
5. CPU/GPU parity held, all tests pass
6. the next candidate is selectable from evidence
```

Final status will be PASS / PARTIAL / INCONCLUSIVE / FAIL, judged on whether the
cost structure was measured sufficiently. **No performance improvement is
claimed.**

## 15. Future Revisit Conditions

Recorded now, before the results, so they cannot be rationalised afterwards:

- If a handle/stream path turns out faster, the candidate is **not** adopted here.
  It needs its own pre-register, and it must account for WIC path semantics
  differing from the filename path.
- Any candidate measured as "not the bottleneck" is recorded with its share and
  a revisit condition, not deleted.
- The dataset change means a future comparison against D1 needs the same dataset
  or an explicit re-baseline.
