# MediaSimilarityFinder v0.9.4.28 — D2 CreateDecoderFromFilename Internal Cost / WIC Decoder Entry-Path Comparison

Status: **PRE-REGISTERED** (committed before any D2 code change)

D2 is a **measurement** build. It does not optimize.

---

## 1. Change Need

D1 closed two questions and left one open.

```text
D9d: decode ≈ 4.4654 ms/call
D1:  CreateDecoderFromFilename ≈ 2.6257 ms/call
     OS CreateFileW reference   ≈ 0.0576 ms/call
     Factory2 25,898 attempts / 25,898 successes / 0 fallbacks
```

D1 established that the `open` bucket is 97.8 % WIC-internal and that neither
the Factory2 fallback nor raw OS file I/O explains it. It could not go further
because `CreateDecoderFromFilename` is a single opaque call.

D2 therefore does **not** assume that another WIC entry point is cheaper. It
measures the alternatives.

The dangerous inference this build exists to prevent:

> "`CreateDecoderFromFilename` is slow, therefore `CreateDecoderFromFileHandle`
> or `CreateDecoderFromStream` must be faster."

That is a guess. D2 turns it into a number or leaves it refuted.

## 3. Dataset Change — This Is a Material Deviation and Is Recorded as Such

**The directive requires a per-format breakdown (§15, §16) and states the D8b

a multi-gigabyte one.

## 4. D2 Hypothesis

None in the optimisation sense. Three possibilities are all allowed, and the
build is designed to distinguish them:

- **Case A** — a handle or stream entry point is materially faster, implying
  filename-path-specific overhead inside WIC.
- **Case B** — all three are similar, implying decoder activation or codec
  initialisation dominates and the entry point is not the lever.
- **Case C** — the paths differ mainly by file format, implying codec-specific
  decoder initialisation.

## 5. Comparison Paths

The three WIC entry points were confirmed to exist in the Windows SDK headers
(`wincodec.h`, SDK 10.0.26100.0) before any code was written:

```text
IWICImagingFactory::CreateDecoderFromFilename(LPCWSTR, GUID*, DWORD, IWICBitmapDecoder**)
IWICImagingFactory::CreateDecoderFromFileHandle(ULONG_PTR, GUID*, DWORD, IWICBitmapDecoder**)
IWICImagingFactory::CreateDecoderFromStream(IStream*, GUID*, DWORD, IWICBitmapDecoder**)
IWICImagingFactory::CreateStream(IWICStream**)
```

`IWICStream` derives from `IStream`, so it can be passed directly to
`CreateDecoderFromStream`.

| Path | Steps | Role |
|---|---|---|
| **A** | `CreateDecoderFromFilename` | production baseline |
| **B** | `CreateFileW` → `CreateDecoderFromFileHandle` | measurement only |
| **C** | `CreateFileW` → `IStream` adapter → `CreateDecoderFromStream` | measurement only |

Path A uses the **same** `metadataOptions`, `desired access` and vendor GUID as
production, so its number is directly comparable to D1's.

Paths B and C are **measurement-only**. They are not wired into `decode()` and
are never adopted as the product path by this build.

### Path C correction against the pre-registration

The pre-registration described Path C as `CreateFileW` → `CreateStream`
(IWICStream) → `InitializeFromFilename` → `CreateDecoderFromStream`. While
implementing it, two facts forced a correction to the committed pre-register
(`3a494e7`):

1. **`IWICStream` has no `InitializeFromHandle`.** In the SDK `wincodec.h`,
   `IWICStream` offers only `InitializeFromFilename` and
   `InitializeFromIStream`. Using `InitializeFromFilename` therefore leaves the
   `CreateFileW` handle we opened **unconnected and discarded** — the path would
   have measured a thrown-away `CreateFileW` plus a second open hidden inside
   WIC, which is not a valid comparison at all.
2. **`CreateStreamOnHANDLE` does not exist.** It is absent from both `ole32.lib`
   and `ole32.dll` (verified directly, not assumed). Windows offers no
   HANDLE → IStream adapter, so the probe implements one itself
   (`HandleStream`).

Path C is therefore `CreateFileW` → `HandleStream` (hand-written IStream) →
`CreateDecoderFromStream`. The decoder now genuinely reads through the handle
we opened, which is what the experiment is meant to isolate.

**Design trade-off to carry forward**: this adapter becomes code we own and
maintain, and its cost is included in the measured numbers. Any decision to
adopt Path C has to weigh that against the saving.

## 6. Measured Boundaries

Each metric measures exactly one call, with nothing nested inside another:

```text
fileOpenMs          CreateFileW                          (B and C only; A = N/A)
streamCreateMs      unused (removed by the Path C correction) → not reported
streamInitMs        HandleStream construction (hand-written IStream) (C only)
decoderFilenameMs   CreateDecoderFromFilename          (A)
decoderFileHandleMs CreateDecoderFromFileHandle        (B)
decoderStreamMs     CreateDecoderFromStream            (C)
combinedPathMs      A: decoderFilenameMs
                    B: fileOpenMs + decoderFileHandleMs
                    C: fileOpenMs + streamInitMs + decoderStreamMs
```

`combinedPathMs` is the sum of its own components and is reported alongside
them, never added to them. Nothing is counted twice.

## 7. Scope

Timers, counters, HRESULT recording, stage counters, profiling telemetry, and
tests validating the instrumentation. D9d's `DecodeTelemetry` is **reused and
extended**; no second telemetry system is created.

The measurement helper lives in `image_decoder.h/.cpp` as an explicit,
separately-called probe. `ImageDecoder::decode` and `decodePreserveAspect` are
**not** given a mode switch, and their behaviour is not altered.

## 8. Non-goals

Not done in D2, per the directive:

```text
switching the product path to FileHandle or Stream
factory / decoder / stream / file-handle reuse
decode deduplication
cache changes
EXIF, metadata option, resize, format conversion, copy changes
threading or parallelization changes
candidate, threshold, grouping, verdict changes
choosing a decoder CLSID from the extension (that would change format probing)
relaxing or deleting any existing test
```

§17 of the directive is respected directly: the extension is **not** used to
pick a decoder. Every path lets WIC probe the format exactly as production
does, so the comparison isolates the entry point and not a format-detection
change.

The Factory2 fallback is not re-opened as a candidate (D1: 0 fallbacks), and
cache mutex is not re-opened (D1: 71.5 ms total). Both are only checked for
regression.

## 9. Accuracy Risk

Decoder creation is instrumented; decoding is not. Requirements:

- `verifyCalls`, `verifyDecodeMisses`, `verifyCacheHits`, `ssimEvals`,
  `frameSsimEvals`, `groups`, and the final verdict unchanged.
- The probe must not alter production decode results. It is a separate entry
  point and is invoked only from the benchmark driver.
- Paths B and C are validated beyond "the call returned success": for each, the
  decoder must yield `GetFrame(0)` and a plausible pixel size. A path that
  creates a decoder but cannot produce a frame is counted as a failure and
  reported, not silently averaged in.

## 10. Compatibility Risk

Paths B and C are measurement-only and compile-guarded to Windows, so CPU-only
and non-WIC builds are unaffected. `image_decoder.cpp` already has a non-WIC
branch; the probe will report `not_available` there rather than fabricate zeros.

`Path C` may legitimately fail for some inputs (a WIC stream initialised from a
filename has different seek semantics). Failures are recorded with their
HRESULT and are **not** hidden by averaging only the successful samples.

## 11. Measurement Plan

- Same hardware, OS, GPU, build configuration and cold-index condition.
- **At least 5 runs**; mean, median, min, max, range per path and per format.
- The three paths are timed within the same run over the same files, so the
  comparison is paired and the run-to-run spread affects all three equally.
- A 1-2 % difference is **not** an improvement in a ~3.7-7.5 % spread.
- Path ordering must not be read as a simple `A < B < C` ranking; the paths do
  different internal work, and the report must discuss **where** a difference
  could arise, per §13.

## 12. Noise Consideration

The first call into a path may pay one-off costs (DLL resolution, codec load)
that later calls do not. A warm-up call per path per format will be performed
and excluded, and this is stated in the report rather than left to chance.

## 13. Stop Conditions

Reduce scope or stop, and record rather than patch around:

```text
1. instrumentation changes a verdict or grouping
2. CPU/GPU parity breaks
3. an existing test fails
4. timing overlap makes the comparison uninterpretable
5. Paths B/C cannot be validated as producing the same image
6. a value would have to be estimated rather than measured
```

### Caveats that must travel with these numbers

1. **Do not use the tiff A mean (5.41).** Its median is 0.1974 but its max was
   73.2 ms — a single-file outlier caused by one TIFF container variant, not a
   property of the format. Judge tiff on the median only.
2. **First-call cost is a separate effect.** Probing a single file with no
   warm-up put A at 2.3–4.1 ms. That is the one-time codec DLL load, which
   happens once per process regardless of entry point. It is already amortised
   in a production scan, so the post-warm-up numbers are the ones that map to
   production. D1's `CreateDecoderFromFilename ≈ 2.6 ms` includes that
   cold-start, so **D1 and D2 are not directly comparable**; the gap is a
   measurement-condition difference, not a performance change.
3. **Acceptance is identical across all three paths.** The 4 ico and 1 tiff
   files that fail return `0x88982F60` (`WINCODEC_ERR_COMPONENTNOTFOUND`) for
   A, B and C alike. These are the deliberately malformed fixtures
   (`truncated_mask_32bpp.ico`, `cmyk_u8_*_case.tif`, …); switching entry
   points does not change which files are decodable. They are kept because they
   are still worth having for robustness.
4. **Path C's numbers include our own `HandleStream`.** `streamInitMs` measures
   0.0003 ms, effectively free, but adopting it means owning the adapter.
5. **The saving is small.** About 0.02 ms per file, i.e. roughly 0.5 s across
   D1's 25,898-image scan. It has to be weighed against D1's conclusion that
   open is 97.8 % WIC-internal cost.

## 15. Three Real Bugs Found While Implementing D2 (Kept Permanently)

D2 was measurement-only code, but implementing it surfaced **three defects that
actually prevented it from working**. They are recorded regardless of outcome.

### Bug 1 — Path B handle lifetime (use-after-close)

- **Cause**: `CloseHandle` was called *before* the decoder created by
  `CreateDecoderFromFileHandle` was validated with `GetFrame(0)`.
- **Problem**: the decoder still references that handle and can read from it
  inside `GetFrame`, so this was a use-after-close. It produced a real access
  violation.
- **Fix**: release the decoder and only then `CloseHandle`, after
  `validateFrame()` completes.
- **Generalised rule**: when swapping entry points, the lifetime of a
  caller-opened handle lasts until the decoder is *done being used*, not until
  it was *created*.

### Bug 2 — Path C connected the wrong stream

- **Cause**: the initial implementation used
  `IWICStream::InitializeFromFilename`.
- **Problem**: `IWICStream` has no `InitializeFromHandle`, so the `CreateFileW`
  handle we opened was **never connected to the decoder input and was
  discarded.** The path ended up measuring a thrown-away `CreateFileW` plus a
  second filename open hidden inside WIC, which made the comparison meaningless.
- **Fix**: implement a HANDLE→IStream adapter (`HandleStream`) so the decoder
  genuinely reads through the handle we opened, as described in §5.
- **Generalised rule**: before comparing "entry paths", first confirm every path
  reads **the same resource**. If it does not, discard the comparison.

### Bug 3 — COM lifetime

- **Cause**: the probe called `CoUninitialize()` itself.
- **Problem**: access violation on scope exit. While tearing the apartment
  down, `CoUninitialize` drops the last reference to a codec DLL, leaving the
  stack that is still running on top of it unusable.
- **Fix**: the probe initialises COM but never uninitialises it. Lifetime
  belongs to the owning process.
- **Note**: `src/image_decoder.cpp` lines 150–153 **already document this exact
  case** ("helpers must never touch COM lifetime themselves"). The rule existed;
  the probe simply failed to follow it.
- **Generalised rule**: **COM lifetime follows caller ownership.**

## 16. The `CreateStreamOnHANDLE` Misjudgement and Its Correction

- **Initial guess**: to fix Bug 2, `CreateStreamOnHANDLE` was used.
- **Verified result**: the symbol exists in **neither `ole32.lib` nor
  `ole32.dll`.** It was established as invalid by direct inspection, not by
  assumption.
- **Correction**: Windows provides no HANDLE→IStream adapter, so one was
  implemented directly (`HandleStream`).
- **Why recorded**: the attempt is documented transparently in both the
  pre-register and this Build History (§5). Keeping only the successful fix
  would let the next task repeat the same illusion.
- **Generalised rule**: **never guess a Windows API without checking that it
  exists.**

## 17. Parity / Equivalence Check

- The **success/failure pattern is identical** across all three paths.
- Failures are 4 ico and 1 tiff file, all returning `0x88982F60`
  (`WINCODEC_ERR_COMPONENTNOTFOUND`) for A, B and C **alike**.
- This confirms Path C did **not** selectively succeed on particular inputs to
  flatter its numbers.
- On files that succeed, all three paths return the same frame(0) and the same
  dimensions, e.g. `fax4.tiff` → 460x307 and `smile.ico` → 16x16 across all
  three paths.
- **Deliberately malformed fixtures** (`truncated_mask_32bpp.ico`,
  `cmyk_u8_*_case.tif`, …) are **not deleted**; they still have robustness value.

## 18. Final Decision on Path C = `DEFERRED`

`CreateDecoderFromStream` + `HandleStream` is **not adopted into the product
now.**

1. **The absolute expected gain is small.** There is a decoder-step improvement,
   but it is minor relative to the current bottleneck.
2. **Maintenance cost increases.** The hand-written `HandleStream` must be
   maintained long term: HANDLE lifetime, IStream semantics, Read/Seek/Stat/Clone,
   close semantics, COM interaction, Windows compatibility.
3. **There is no production full-path verification yet.** D2 is a decoder entry
   timing comparison, not a full production scan benchmark.
4. **Absolute values depend on machine load.** In the reproducibility check the
   same code produced absolute values roughly 3x apart under different load
   (§14), and the relative gap moved between 16–30 % and 63–74 %. Numbers that
   unstable cannot justify adopting a product change.

**This is `DEFERRED`, not `REJECTED`.** It is not a permanent rejection.
Revisit conditions:

```text
1. when the WIC decoder path again takes a large share of the total bottleneck
2. when a full production benchmark shows a meaningful saving
3. when HandleStream becomes reusable elsewhere
4. when the decoder architecture changes
5. when the Windows/WIC runtime changes
```

## 19. The Correct Way to State the Expected Effect

- About 0.02 ms per file of decoder-step saving is expected.
- Extrapolated naively to D1-like volume (25,898 calls) that is roughly 0.5 s,
  but **this is not a production full-path measurement.**
- Therefore do **not** record "about 0.5 s is definitively saved across a full
  scan." The accurate statement is: **"naive extrapolation of decoder-only
  timing gives a potential saving of roughly 0.5 s, but it is not yet verified on
  the production full path."**
- Against a roughly 120 s total scan that extrapolates to about 0.4 %, but that
  too is a **rough estimate.** In the production path this cost occurs together
  with file open / decoder / GetFrame / CopyPixels / conversion / resize / cache
  / verify, so it must not be treated as a whole-product improvement.

## 20. Do Not Compare D1 and D2 Directly (Restated)

```text
D1         CreateDecoderFromFilename ≈ 2.6257 ms/call
D2 warm-up about 0.07~0.12 ms
```

This gap is **not a performance improvement.** D1 includes the one-time codec
DLL load, while D2 was measured in a warm state. **The measurement conditions
differ, so the two are not directly comparable; what D2 newly establishes is the
decoder call cost after warm-up.** Do not compute this as a "95 % improvement."

## 22. Next Candidate — D3 (v0.9.4.29)

The next performance investigation is defined as
**D3 = duplicate cost of decode / decodePreserveAspect**. This task does **not**

## 24. Expected Outcome

Success is a measured cost structure, not a speedup:

```text
1. CreateDecoderFromFilename's cost is compared against two alternative entry
   points under identical metadata options and identical files
2. the result is reported per format, with success/failure and HRESULTs
3. whichever of Case A / B / C holds is identified from the numbers
4. verdict, grouping, parity preserved
5. CPU/GPU parity held, all tests pass
6. the next candidate is selectable from evidence
```

Final status will be PASS / PARTIAL / INCONCLUSIVE / FAIL, judged on whether the
cost structure was measured sufficiently. **No performance improvement is
claimed.**
