# MediaSimilarityFinder v0.9.4.47 — non-ASCII path scan failure fix

Baseline `0.9.4.46` -> this build `0.9.4.47`.
CPU CTest **103/103**, GPU CTest **104/104**.
`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.4` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — all unchanged. No DB schema change.

## 1. Why the change was needed

Clicking Search/Update in the GUI raised a `Search error` dialog:

```
No mapping for the Unicode character exists in the target multi-byte code page.
```

The failure is recorded in `%TEMP%\msf_scan.log`. The target was
`G:\Downloads\ss_twit` (272,714 entries, many Korean/Japanese file names), and it
failed **one second after start with no `lastPath`**. The same folder scanned fine
on September 25-26 and has failed on every attempt since September 28.

**This is not a "search engine under development" issue. It is a product bug.**

## 2. Previous structure

The dialog body is `e.what()` caught by `ScanWorker::run()`'s
`catch (const std::exception&)` (`gui/mainwindow.cpp:566-571`). So a C++
exception escaped the engine scan.

The message is thrown by the **MSVC standard library**, not Qt. The string was
searched across the Qt6 DLLs, the MSVC headers, and 6,240 System32/SysWOW64 DLLs,
and it exists **in none of those binaries**. Direct probes confirmed:

```cpp
std::filesystem::u8path(valid UTF-8)        -> ok
std::filesystem::u8path(CP949 bytes)       -> THROW: No mapping ...
std::filesystem::u8path(truncated UTF-8)   -> THROW
std::filesystem::path(UTF-8 Korean narrow) -> THREW (same message)
```

`fs::u8path()` and the narrow `fs::path(string)` constructor interpret input as
the **ANSI code page (949)**, not UTF-8, so they throw on non-ASCII names.

## 3. New structure

### Cause

`canonicalRelativePath()` in `src/dataset_fingerprint.cpp:118`.

```cpp
// before
fs::path rel = fs::relative(fs::path(file), fs::path(root), ec);
// after
fs::path rel = fs::relative(path_from_utf8(file), path_from_utf8(root), ec);
```

`file` and `root` are UTF-8 strings by product convention. Constructing a narrow
`fs::path(string)` reinterprets them as ACP and throws on non-ASCII names. This
function came in with the dataset fingerprint for the S6 measurement gate
(D8a/D8b) and runs at every scan start (telemetry setup, before any file is
processed) — hence "in one second, with no file processed".

The timeline matches. The same folder scanned fine before the dataset fingerprint
landed around September 26-28, and every non-ASCII folder scan has failed since.

### Same-pattern audit

Every `fs::path(narrow string)` construction in the product was audited.

| Location | Verdict |
|---|---|
| `dataset_fingerprint.cpp:118` | **fixed** (the only dangerous site) |
| `monitor.cpp:129,130,240` | safe (`fs::path("..")`, `fs::path(".")` ASCII literals) |
| `monitor.cpp:226` | safe (wide `std::wstring` construction) |
| everything via `path_from_utf8` | safe (explicit UTF-8) |

### Candidates ruled out by verification

- Qt6 `QString::toStdString()` / `fromStdString()` are UTF-8 based, confirmed by
  header and probe. `toLocal8Bit()` silently substitutes `?` and never throws
- every `path_from_utf8` path receives valid UTF-8
- `Scanner().count/scan`, `MediaPipeline.image/imageBatch`, `db_.upsert`,
  `compareFingerprint`, the GPU getters, `detectCpuModel`, and `ProfileStore`
  were each verified working by stepwise probes
- the index databases were audited read-only for corrupt paths; none found

## 4. Resolved situation

- One non-ASCII file: `exit=-1073740791` (0xC0000409, no output) ->
  `exit=0, analyzed=1`
- Four mixed files (Korean, Japanese, accented, ASCII):
  `scanned=4 analyzed=4 candidates=6 groups=6`
- The CLI silent crash and the GUI `Search error` dialog were two faces of the
  same exception. CLI `runHeadlessScan` has no `catch`, so it terminated ->
  abort -> fail-fast; the GUI `ScanWorker` catches it and shows the dialog.

## 6. Future impact

- The scan-start dataset fingerprint now works on non-ASCII folders. The full
  272k-entry `G:\Downloads\ss_twit` scan was not run to completion in this build
  because of its size; verification used single-file and small mixed
  reproductions.
- Narrow `fs::path(string)` construction is a forbidden pattern in the product.
  UTF-8 strings must go through `path_from_utf8()`. The audit confirmed no other
  instances.
- `image_decoder.cpp:161`'s `std::mbstowcs` (C-locale dependent, XMP `VT_LPSTR`
  path) and the ffprobe `toLocal8Bit`/`fromLocal8Bit` in `mainwindow.cpp` remain
  ACP-dependent but were not this failure's path, so they were left alone. They
  stay as separate tasks.
- Next gate: S4 GUI real-screen acceptance (needs user-side verification),
  `color_thumb` R1.
