## 2. 기존 구조와 결함 (0.9.4.113 B1 수정의 회귀)

- 0.9.4.113에서 `MediaSearchEngine::loadMatches()`(빠른 로드 경로)에 전체 내용 확인을 추가하며, 파일 해시 메모를 **맵 내부 참조 반환**으로 구현했다:
  ```cpp
  const auto fullHex=[&](const std::string& p)->const std::string&{
    ...
    return fullMemo.emplace(p,std::move(hex)).first->second;  // 맵 내부 참조
  };
  ...
  const std::string& ha=fullHex(m.left); const std::string& hb=fullHex(m.right);
  if(!ha.empty()&&ha==hb) ...   // 두 번째 호출의 emplace/리해시가 ha를 무효화 → UAF
  ```
- **원인**: `std::unordered_map`은 삽입으로 리해시되면 **모든 참조를 무효화**한다. 두 번째 `fullHex` 호출이 새 키를 삽입하며 리해시 → `ha`가 해제된 버킷 메모리를 가리킴 → 댕글링 비교(use-after-free) → 힙 손상/크래시.
- **두 증상의 공통 원인**: `loadMatches`는 불러오기(`backend_session.cpp:347`)와 스캔 quick-load(`scan_worker.cpp:135`) 양쪽에서 호출된다.
- **CI가 놓친 이유(잠복)**: 소규모 테스트 데이터(수백 쌍)에서는 리해시 후에도 해제된 버킷 배열이 재사용되지 않아 댕글링 참조가 우연히 유효한 값을 읽는다. 사용자 데이터(후보 5,296파일·3,493쌍, 긴 경로, 잦은 힙 재사용)에서만 결정적으로 터진다.

## 3. 변경 구조

- **`fullHex`가 값(std::string)으로 반환**하고 `ha`/`hb`도 값으로 받는다(`media_search_engine.cpp`). 참조 수명 문제가 원천 제거된다. 비용: 문자열 복사(수 KB, 무시 가능).
- **회귀 테스트**(`search_engine_test`): **필드 규모** 케이스 — 서로 구별되는 노이즈 BMP 3,000쌍(6,000파일) 생성 → 스캔 → `saveMatches` → `loadMatches` → 모든 저장 쌍이 `contentIdentical=true` 단언(맵 6,000 삽입으로 다수 리해시 유도). 반환 코드 20~24.
- 정직 기록: 무력화(참조 반환) 버전으로 이 테스트를 돌려도 **통과**했다 — 합성 환경에서는 해제 메모리가 재사용되지 않아 UAF가 비결정적이다. 필드 크래시(62097)가 재현 증거이며, 본 테스트는 계약(대규모 로드 무결성)을 고정한다.

## 4. 해결된 상황

- 댕글링 참조가 제거되어 불러오기·검색 시작의 백엔드 크래시가 해소된다(원인-수정 일치: 두 경로 모두 이 함수).
- 배지 계약(전체 내용 SHA-256 동일성)과 0.9.4.113의 다른 수정(스캔 파이프라인 메모는 값 반환이라 무영향)은 그대로 유지된다.
- 사용자 인덱스 DB는 SQLite 크래시 안전성으로 손상 없음(크래시는 로드 처리 중 발생, 쓰기 없음).
