# MediaSimilarityFinder v0.9.4.89 — incremental dataset fingerprint (per-file content-hash cache)

Baseline `0.9.4.88` -> this build `0.9.4.89`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged.
**`kDatabaseVersion 1.0.5 -> 1.0.6`** (additive `content_hash` table; old code ignores it).

## 1. Why it was needed

The 0.9.4.86 dataset-fingerprint cache reuses a value only when the file-set key is
**exactly equal**. In the 0.9.4.87 run (`detailed-log-2026-10-11T013805`), with only
**20 files changed**:
- fingerprint **1533.2 s (61.4 % of 2495.5 s wall)**, `bytesRead = 68.9 GB` = a full re-hash.
- i.e. "any file changed -> 25 min full re-read" remained.

## 2. Previous structure

- `computeDatasetFingerprint` read every in-scope file fully and SHA-256'd it into a manifest.
- The cache was **whole-fingerprint only** (hit only when the file-set key matched).

## 3. Change

- **DB `content_hash` table** (1.0.6, additive): `rel TEXT PRIMARY KEY, size, modified, sha256`.
  `Database::contentHashGet/Put`.
- **`computeDatasetFingerprint` gains a `DatasetHashCache` (get/put) hook**: per file, when
  `(rel,size,modified)` match, **reuse the stored SHA-256** (no read); otherwise read+hash and
  store. New `DatasetFingerprint.cachedFiles` counter; `bytesRead` is what was actually read.
- The engine passes `db_`-backed callbacks.

## 4. Result

- A rescan with a few changed files now **re-hashes only the changed/new files** -> 25 min -> seconds.
- When nothing changed, the existing whole-fingerprint cache still returns instantly (0 reads).

## 6. Performance experiment record (AGENTS rule 9)

- **Experiment**: P-0.9.4.89-incremental-fingerprint
- **Baseline**: 0.9.4.87 (20-file change -> fingerprint 1533 s / 68.9 GB full re-read).
- **Hypothesis**: storing per-file content hashes lets only changed files be re-hashed.
- **Method**: `content_hash` table + `DatasetHashCache`; `dataset_e2e_test` third scan.
- **Result**: with 1 change, 59/60 files reused (`cachedFiles=59`), identity exact.
- **Status**: PASS (fixture). Real large-scale re-measurement is a user run.
- **Known limitation**: a change that keeps `(size,modified)` but alters content is reused (same limitation as the whole-fingerprint cache).

## 7. Impact and limits

- DB version 1.0.6 (additive table). Existing DBs create it via `CREATE TABLE IF NOT EXISTS` on open.
- `content_hash` rows are updated per file each scan; orphan rows for deleted files may remain
  (harmless; a prune candidate later).
- Each file's content hash is computed once on the first scan, then reused.
