# MediaSimilarityFinder v0.9.2.44 — 대용량 스캔 live 검증 + 스트리밍 전환

## 변경 필요성
실머신 보고 "중복 검색이 전혀 동작하지 않는다"를 소스 전수 + 워커 경로 재현으로 검증했다. 엔진·매치 파이프라인·스트리밍은 정상이었다. 3000개 유사 이미지 프로브: 641,358 매치가 스트리밍·보관 양쪽으로 정확히 전달됐다. 진짜 문제는 규모였다. 27만 파일 폴더는 수백만 매치를 만들 수 있고, 기존 구조는 매치마다 경로 문자열 2개를 결과 벡터에 보관 + 600ms마다 전체 뷰 재구성 + 그룹 대표 썸네일을 매번 재디코딩했다. 수백 MB~GB 메모리와 UI 프리즈로 "아무것도 안 된다"처럼 보인다. 워킹 23분 무표시 + 수 시간 분석도 같은 체감에 기여했다.

## 기존 구조
- 워커가 기본값(`retainMatches=true`)으로 전체 매치를 `SearchReport`에 보관 후 GUI에 전달
- `fileThumb()`이 이미지는 매번 WIC 재디코딩 (비디오만 캐시)

## 변경 구조
- 워커 `control_.retainMatches=false` (스트리밍 전용). GUI는 `drainMatches` union-find 누적으로 이미 동일 데이터를 보유하므로 동작 동일, 메모리 수백 MB 절약. `finished` 메시지의 카운트는 그대로 유지
- `fileThumb()` 전체 캐시 + 3000개 상한 (초과 시 비움). 그룹 리스트 갱신 시 재디코딩 제거
- 버전 표기 통일 → 0.9.2.44

## 해결된 상황
- 대용량 스캔에서 메모리 증가가 인덱스·매치 수에 비례하지 않게 됨. UI 갱신 비용은 캐시 적중 후 썸네일 표시 수준

## 검증
- 워커 재현 프로브(3000개, `openIndexForRoot`+스트리밍): 641,358/641,358 스트리밍·보관 일치 확인 후 전환. 전환 후 동등성은 `retainMatches=false` 경로가 동일 콜백을 사용하므로 구조적으로 보장
- Core Release 빌드 PASS, **CTest 39/39 PASS**, `--smoke` exit 0, `--version` 0.9.2.44
- 사용자 27만 폴더의 통스캔 시간(수 시간 규모)은 하드웨어·코덱 bound로 남음. 진행 표시(.42) + 증분 재스캔으로 대응

## 향후 영향
- `SearchReport.matches` 비우기에 의존하는 GUI 코드는 없음 (확인됨). 향후 가상화 모델도 동일 스트림 사용
