## 1. Why the Change Was Needed

v0.9.4.36 integrated I-2 into production and confirmed a 36.72 % reduction at the
decoder level. That value came from a decoder microbenchmark, though, and decode
is only part of a MediaSimilarityFinder scan — it does not run at all on a cache
hit. This version measures how much of that gain actually reaches the full
production scan, so the I node can be closed on evidence.

## 2. Previous Structure

`MediaSimilarityFinder.exe` is a GUI-subsystem binary that accepts only
`--version`, `--help` and `--smoke`. **There is no CLI flag that starts a scan.**
Scanning is reachable only through the GUI's Scan button (`ScanWorker::run`).

However, a measurement driver that fits the purpose already exists:

```text
tests/dataset_baseline.cpp
  msf_dataset_baseline <dataset-root> <app-dir> [runs]
```

It calls `MediaSearchEngine::scan(root, 8, &control)`, so it runs the **same**
`scan_pipeline.cpp` + `image_verify.cpp` + `MediaPipeline` path as the GUI. It
reports host wall clock (`run=N wall_ms=`), the full D9a/D9c/D9d/D1/D3 telemetry,
and the raw JSON through the `MSF_DUMP_JSON` environment variable.

**All required telemetry already existed.** The minimum telemetry the directive
permitted was **not needed, and not one line of production code was changed.**
This commit contains only a version bump, the measurement harness, and documents.

## 3. Method

### 3.1 Obtaining the baseline binary

A separate git worktree was created so the working tree was never checked out or
overwritten:

```text
C:\project\validation\v0.9.4.35\src_unpacked\   (worktree, detached at 6c981f7)
```

To avoid rebuilding 2.2 GB of vcpkg dependencies, the existing
`C:\project\src_unpacked\vcpkg_installed` tree was reused:

```text

-DVCPKG_MANIFEST_INSTALL=OFF
-DMSF_ENABLE_GPU=OFF   (CPU tree)   /  -DMSF_ENABLE_GPU=ON (GPU tree)
```

The CPU build switches were matched to the v0.9.4.36 CPU tree
(`MSF_ENABLE_GPU=OFF`, `MSF_GPU_BACKEND=AUTO`, `MSF_CUDA_ARCHITECTURES=75;86;89`,
VS 18 2026 x64, Release).

### 3.2 Condition A — decode-active (cold process)

`verifyCacheList` is a **process-global** 32-entry LRU in `image_verify.cpp`
(`constexpr std::size_t kVerifyCacheMax = 32;`, file-static). There is no API to
reset it. Therefore **one scan per process** is the only way to guarantee a cold
verify cache — and that is also what actually happens when the app is launched
fresh and scans.

```text
msf_dataset_baseline <root> <appdir> 1     # one measurement = one process
```

Baseline and candidate were interleaved **BCBCBCBCBC** to remove time-axis bias.
One warm-up execution of each binary was performed and discarded.

### 3.3 Condition B — normal production (warm / repeat scan)

Reproduces clicking Scan more than once in a GUI session. Runs 5 scans in one
process and **discards run 0 as warm-up**, using runs 1–4, matching the project's
existing convention (the D3 block in `dataset_baseline.cpp` starts at index 1 for
the same reason).

### 3.4 Fixed conditions

Same dataset, same Release build, same CPU/GPU switches, same search parameters,
same app-dir layout (separate prefix per version so the two can never share an
index), and no artificial manipulation of the Windows file cache.

The dataset was **not modified**:

```text

fingerprint e8f8fa6ab0257f1e2b7d839b73ec14b1cc726695dac2efe79b55a13a13e2640a
```

## 5. Results — Condition B (warm / repeat scan)

GPU, 3 processes × 4 repeat runs = 12 rows per version.

```text
baseline  median  31,005.3 ms  [23,797.1 – 31,136.3]
candidate median  22,718.9 ms  [16,643.0 – 24,231.3]
delta            -8,286.4 ms   (-26.73 %)
```

The work done is identical across all 24 executions (`scanned=3334`,
`analyzed=3333`, `groups=156211`, `verifyDecodeMisses=12962`,
`verifyCacheHits=14524`), and the candidate is faster in 24/24.

However, **the absolute times in this condition are abnormal.** Within a process,
run 1 is fast and both versions slow down sharply from run 2 onward:

```text
v0.9.4.35  run1 23,930 → run2 31,036 → run3 31,136 → run4 31,058
v0.9.4.36  run1 16,643 → run2 23,082 → run3 22,745 → run4 24,231
```

The cause was isolated through telemetry. Comparing per-miss decode cost across
conditions:

```text
v0.9.4.35  cold 0.7203 ms/miss  →  warm 1.1546 ms/miss   (+60 %)
v0.9.4.36  cold 0.5522 ms/miss  →  warm 0.6196 ms/miss   (+12 %)
```

**v0.9.4.35's decode gets 60 % slower on a repeat scan, while v0.9.4.36 slows by
only 12 %.** `openMs` is essentially unchanged between the conditions for both
versions, so the difference sits in `copyMs`. WIC's lazy decode plausibly caches
differently depending on the decoder-instance structure, but **this is a
hypothesis, not a settled conclusion.**

`MSF_DUMP_JSON` only records the last run's JSON, so per-repeat-run telemetry
could not be captured. That is why condition B is not used as the headline.

## 6. Decomposition — What Actually Got Cheaper

The decode-stage saving was broken down by bucket (condition A, medians).

### GPU

| bucket | v0.9.4.35 | v0.9.4.36 | delta | per miss |
|---|---|---|---|---|
| verifyDecodeMs | 9,335.9 | 7,158.0 | **-2,177.9** | -0.1680 |
| decodeTotalMs | 9,329.5 | 7,153.5 | -2,176.0 | -0.1679 |
| open (WIC decoder creation) | 1,945.1 | 963.0 | **-982.1** | -0.0758 |
| osFileOpenProbeMs | 1,229.4 | 586.9 | **-642.4** | -0.0496 |
| metadata | 25.9 | 13.4 | -12.5 | -0.0010 |
| comInit | 17.2 | 11.5 | -5.8 | -0.0004 |
| resize | 114.9 | 102.1 | -12.8 | -0.0010 |
| convert | 77.7 | 61.6 | -16.1 | -0.0012 |
| **copy (real pixel decode)** | 5,034.9 | 4,939.6 | **-95.4** | -0.0074 |
| osFileOpenProbeCount | 25,924 | 12,962 | -12,962 | |

### CPU

| bucket | v0.9.4.35 | v0.9.4.36 | delta | per miss |
|---|---|---|---|---|
| verifyDecodeMs | 8,379.6 | 6,418.8 | **-1,960.8** | -0.1513 |
| open | 1,696.1 | 855.1 | -841.0 | -0.0649 |
| osFileOpenProbeMs | 1,076.1 | 525.1 | **-551.0** | -0.0425 |
| copy | 4,575.5 | 4,433.5 | -142.0 | -0.0110 |

### The fact that must be stated

**Roughly 28–30 % of the saving is removed measurement overhead.**

```text
GPU  of the 2,177.9 ms saving, 642.4 ms (29.5 %)
CPU                             551.0 ms (28.1 %)
```

`probeOsFileOpen` is at `src/image_decoder.cpp:69` and its source comment says:

> Opens and immediately closes a handle; it does not touch the decode path, the
> image bytes, or any result, and its outcome never gates the decode.

It is therefore **pure measurement cost** and returns immediately when
`tel == nullptr`. v0.9.4.35 ran it 25,924 times per scan; v0.9.4.36 runs it
12,962 times. Part of what v0.9.4.36 removes is not product work but duplicated
instrumentation. The 36.72 % microbenchmark in v0.9.4.36 was likewise measured in a
telemetry-enabled build and is subject to the same correction.

### The real product gain

The largest **genuine** saving is the `open` bucket: WIC decoder object creation
went from 25,924 calls to exactly half, 12,962. That is the substance of the I-2
integration.

The `copy` bucket (real pixel decompression) barely moved, at -95 ms on GPU. WIC
was already sharing the expensive decompression internally, so the duplication was
in **object creation and setup**, not in the decode itself.

## 7. Consistency Between Full Scan and Decoder Figures

```text
GPU condition A:
  decode share of baseline wall   9,335.9 / 18,399.7 = 50.7 %
  decode stage reduction                       22.3 %
  50.7 % × 22.3 %                                = 11.3 %
  observed paired full-scan reduction            11.13 %
```

Prediction and measurement agree within 0.2 %p. The full-scan improvement is
simply the decode-stage saving propagating through, with no new cost appearing
elsewhere.

The gap between the 36.72 % decoder microbenchmark and the 10–11 % full scan has a
simple explanation:

```text
1. decode is only ~50 % of scan wall time
2. 28–30 % of the saving is measurement overhead
3. every other stage (walk, image stage, verify key/hash, DB) is unchanged
```

## 10. Limitations and Open Items

### Unexplained (does not block the I node)

1. **Process-level slowdown in condition B.** From the second scan in the same
   process onward, both versions get 30–60 % slower. v0.9.4.36 is still faster in
   24/24 runs there, so **this is not a regression introduced by I-2.** It sits in
   the decode `copyMs`; WIC lazy-decode caching may depend on the decoder-instance
   structure, but **this is a hypothesis.**
2. **No per-run telemetry in condition B.** `MSF_DUMP_JSON` records only the last
   run, so per-repeat-run counters could not be obtained. This is why condition B
   is not used as the headline.
3. **CPU wall-clock noise.** Runs 3, 5 and 6 disturbed it enough that the ranges
   overlap. The GPU measurement is the representative figure.

### Other

- `vcpkg.json` `version-string` is still `0.9.4.35` (v0.9.4.36 did not bump it
  either). Changing it would alter the manifest hash and trigger a full 2.2 GB
  vcpkg dependency rebuild, so it was **deliberately left alone in this
  measurement-only version.** It belongs to a separate maintenance version.
- It was reconfirmed that the product executable has no scan CLI flag. This
  validation used the existing `msf_dataset_baseline` driver, which calls the
  production `MediaSearchEngine::scan()` directly. **No additional code change was
  required.**

## 11. Future Revisit Condition

Re-measure condition B if any of the following changes:

- `verifyCacheList` gains a reset API (cold/warm becomes code-separable)
- `msf_dataset_baseline` gains per-run JSON dump
- the WIC or Windows version changes (decode caching behaviour may change)
- the ~60 % `copyMs` increase in condition B reproduces again, in which case the
  WIC instance-structure dependence should be isolated as its own experiment
