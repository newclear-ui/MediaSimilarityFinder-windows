## 1. 변경 필요성

두 증상이 보고됐다.

1. 읽기 완료 카운터가 오르다가 0으로 리셋된 뒤 다시 진행됨
2. 정지 후 카운터가 최종 0으로 표시됨

## 2. 원인 1: phase handoff 리셋

fingerprint와 walk는 분모가 다른 별개 시퀀스다. `onFingerprintProgress`가
`sumValDone_`에 해시 수를 쓰고, walk 시작 후 `updateStatusCounts`가
`lastTotalN_`(0부터 시작)으로 덮어썼다. 카운터가 올라가다 0으로 떨어지는
것처럼 보였다.

## 3. 원인 2: 취소 후 0 표시

`scanFinished` CANCELLED 분기는 `lastStats_`를 갱신하지 않는다. 이어지는
`refreshSummary()`는 리포트 없음으로 전행 블랭크(`"-"`), `updateStatusCounts()`는
`lastTotalN_=0`을 쓴다. fingerprint에서 4519개를 해시해도 최종 표시는 0이었다.

## 4. 변경 구조

- `lastReadN_` 멤버 신설. 스캔 시작 시 리셋, fingerprint·walk 중 max로 갱신.
  phase가 달라도 단조 증가하므로 리셋이 보이지 않는다. "지금까지 touched된
  파일 수"로서 정직하다 (fingerprint와 walk는 같은 dataset을 순차 처리).
- `refreshSummary` 무보고 분기는 `lastReadN_ > 0`이면 블랭크하지 않고 live
  값을 보존한다. 실제 0인 경우에만 `"-"`.
- `indexed` 행은 기존 live analyzed 경로 그대로 (0.9.4.54).

## 6. 인덱스가 안 되는 이유 (코드 변경 없음, 설명)

첨부 로그는 fingerprint 단계에서 취소된 실행이다
(`cancelledDuring=fingerprint`, 71초, 11GB, scanned=0).
walk/분석/인덱싱에 도달하기 전에 멈췄으므로 인덱싱이 없는 게 정상이다.
고장이 아니다. fingerprint가 전체를 먼저 해시하는 구조상 대용량에서는
이 구간이 길다 (별도 과제: streaming fingerprint 검토).
