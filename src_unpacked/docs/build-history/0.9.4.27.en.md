# MediaSimilarityFinder v0.9.4.27 — D1 File Open / WIC Factory Root-Cause Measurement

Status: **PRE-REGISTERED** (committed before any D1 code change)

D1 is a **root-cause measurement build**. It is not "let us reuse the factory".
It is "prove why file open and WIC factory construction are expensive".

---

## 1. Change Need

D9d decomposed the decode region and left a narrow, unanswered question:

```text
decode 4.4654 ms/call
  open     2.7749 ms  62.15 %
  factory  1.2230 ms  27.39 %
  copy     0.2300 ms   5.15 %   (the real decompression)
  rest               1.20 %
```

`open + factory` is **89.55 %** of decode and **84.93 %** of total verify time
(103,539.7 / 115,628.4 and 103,539.7 / 121,906.2). The 84.9 % figure quoted in the
D9d documents is confirmed correct. The D9d documents additionally state 89.54 %,
which is the truncation of 89.5452 %; D1 records the correctly rounded 89.55 %.

Two questions remain, and neither can be answered by reading the code:

- **A.** Where inside the 2.7749 ms of `open` does the time go?
- **B.** Does `CLSID_WICImagingFactory2` actually succeed, or is every call
  paying for a failed attempt plus a fallback?

Question B is the one this project has the strongest reason to ask. The source
attempts Factory2 and falls back on failure. If the fallback is universal, then
the measured 1.2230 ms is not "one factory creation" but **two** COM activations,
and the first is pure waste. That is a different optimization target from
"factory is slow", and the two must not be confused.

## 3. Source Facts Established Before Instrumenting

Read from `src/image_decoder.cpp`, not inferred from names:

1. `CLSID_WICImagingFactory2` is attempted and falls back to
   `CLSID_WICImagingFactory` on failure, in **three** places: `decodeWicFile`
   (line 109), `decodeWicFileAspect` (line 186), and
   `decodeWicFileAspectColor` (line 243). The fallback HRESULT is currently
   discarded, so **the project does not know whether it ever fires**.
2. `open` is a single call: `factory->CreateDecoderFromFilename(...)`. There is
   **no** `CreateStream` / `CreateDecoderFromStream` anywhere in the file. WIC
   therefore opens the file, probes the format, and instantiates the decoder
   inside one opaque call.
3. Each of `decode` and `decodePreserveAspect` independently constructs its own
   factory and its own decoder, so each cache miss pays both twice.
4. `decodeColorAspect` is the GUI preview lane and is **not** instrumented, for
   the same reason as in D9d: it is not the fingerprint path.

## 4. Primary Target — file open internals

`CreateDecoderFromFilename` cannot be split without changing how WIC is used,
which D1 forbids. So D1 measures what can be measured without changing it:

```text
openTotalMs                 the existing D9d bucket
openHrFailCount             how often it returns a failure HRESULT
openHrFirstFailCode         first failure code seen, for diagnosis
osFileOpenProbeMs           reference: plain CreateFileW + CloseHandle on the
                            same path, timed OUTSIDE the open bucket
```

`osFileOpenProbeMs` is a **reference measurement, not part of the decode path**.
Its purpose is to separate "the OS cost of opening a file" from "WIC's decoder
instantiation and format probe", which the single opaque call otherwise hides.
It is reported separately and is explicitly excluded from `openTotalMs`; the
difference between the two is the WIC-specific part of `open`.

The probe is additive: it opens and immediately closes a handle. It does not
alter the decode path, the image bytes, or any result, and it is the only way to
answer question A without rewriting the WIC usage.

## 5. Secondary Target — WIC factory and the Factory2 fallback

This is question B, and it is answered by counting, not by timing:

```text
factory2Attempts       CoCreateInstance(CLSID_WICImagingFactory2) calls
factory2Successes      those that returned a success HRESULT
factory2Fallbacks      those that failed and went to the fallback
factory2FirstFailHr    the first failure HRESULT observed (0 if none)
factoryFallbackType    which factory actually got used
factory2Ms             time inside the Factory2 attempt
factoryFallbackMs      time inside the fallback attempt
factoryTotalMs         factory2Ms + factoryFallbackMs (the D9d factoryMs)
```

`factory2Ms` and `factoryFallbackMs` are exclusive and together reconstruct
`factoryMs`, so the existing D9d number stays comparable.

The HRESULT is recorded as the raw `HRESULT` value and decoded to a symbolic
name, so the result is diagnosable ("why does it fail") rather than merely
counted ("does it fail").

## 6. Scope

Timers, counters, HRESULT logging/aggregation, stage counters, profiling
telemetry, and tests validating the instrumentation. D9d's `DecodeTelemetry`
and analyze telemetry are **reused and extended**; no second telemetry system is
introduced.

`kBenchmarkSchemaVersion` stays at **9**. D9d established that the schema is
additive-read by test (`benchmark_schema_test`, 29 checks), and the only
structured reader is the GUI's `QJsonDocument` key-lookup path. D1 adds fields of
the same kind, and the same test is re-run.

## 8. Factory2 / Fallback Hypothesis

Stated so it can be falsified, and explicitly *not* assumed:

- If `factory2Successes` is high and `factory2Fallbacks` near zero, the fallback
  is irrelevant and the correct next question is only about making factory
  construction cheap (reuse), not about removing a wasted attempt.
- If `factory2Fallbacks` is 100 %, then the measured 1.2230 ms is two COM
  activations, the first of which is wasted on every single decode, and that is
  a structural problem distinct from "COM is slow".
- A partial rate is itself a finding and will be reported as such.

No new external dependency is introduced, and nothing is forced onto Factory2.

## 9. Accuracy Risk

Instrumentation must not change any result. Requirements, all to be verified:

- `verifyCalls`, `verifyDecodeMisses`, `verifyCacheHits`, `ssimEvals`,
  `frameSsimEvals`, `groups`, and the final verdict identical to D9d and to the
  D9a reference.
- `verify_parity_test` unchanged and passing.
- `ui_translation_keys_test` still passing (the D9d GUI fix must not regress).
- `benchmark_schema_test` still passing.
- WIC success/failure counts must be identical with and without the probe.

## 10. Compatibility Risk

Low, but not assumed away. The probe adds a `CreateFileW`/`CloseHandle` pair per
decode; if a dataset entry were unreadable in a way the probe surfaces but WIC
tolerates, the probe must not be allowed to change the decode result. The probe
therefore records its own failure count separately and never gates the decode.

HRESULT logging is a read of a value the code already had. No COM lifetime is
touched: every `ComPtr` still dies before `CoUninitialize`, as the comment at
the top of the anonymous namespace requires.

## 11. Measurement Plan

- Same dataset, fingerprint, hardware, GPU, configuration, cold-index condition.
- **At least 5 identical runs**; report mean, median, min, max, range.
- Wall-clock differences of 1-2 % are **not** improvements in a 6.3 % spread.
- Stage shares and per-call costs are the signal; absolute totals from an
  instrumented build are not a performance claim.

## 12. Noise Consideration

D9d measured 6.3 % wall spread over 5 runs. Call counts are deterministic, so
ratios and per-call costs are the reliable comparison. The probe adds I/O and
will slightly perturb absolute timings; that perturbation is measured and
reported rather than assumed negligible.

## 13. Stop Conditions

Reduce scope or stop, and record rather than patch around:

```text
1. instrumentation changes a verdict or grouping
2. CPU/GPU parity breaks
3. an existing test fails or is relaxed
4. the probe changes any decode result
5. factory2Ms + factoryFallbackMs does not reconstruct factoryMs
6. timing overlap makes the split uninterpretable
7. a value would have to be estimated rather than measured
8. schema compatibility is contradicted
```

## 14. Expected Outcome

Success is root-cause identification, not a speedup:

```text
1. open's composition answered, or its non-separability proven and recorded
2. Factory2 success/fallback answered with real counts and a real HRESULT
3. factory split into Factory2 attempt vs fallback, reconstructing factoryMs
4. decode vs decodePreserveAspect reported separately
5. mutex state re-confirmed
6. verdict, grouping, parity preserved
7. CPU/GPU parity held, all tests pass
8. dataset reproduced, >= 5 runs
9. the next candidate selectable from evidence
```

Final status will be PASS / PARTIAL / INCONCLUSIVE / FAIL, judged on whether the
root cause was identified. No performance change is claimed.

# MediaSimilarityFinder v0.9.4.27 — D1 Result: File Open / WIC Factory Root Cause

Status: **PASS** (root-cause measurement completed — no optimization, no
performance claim)

---

## 1. Question B answered: Factory2 works, the fallback never fires

```text
Factory2 attempts     25,898
Factory2 successes    25,898   100.00 %
Factory2 fallbacks         0     0.00 %
first Factory2 fail HRESULT  (none observed)
```

`CLSID_WICImagingFactory2` succeeds on **every single call** on this machine.
The fallback to `CLSID_WICImagingFactory` is dead code in practice, and the
1.2230 ms D9d attributed to "factory" is **one** COM activation, not two.

This closes a structural suspicion and removes a candidate. The pre-register
asked whether the measured cost might be "two activations, the first wasted".
It is not. There is no wasted first attempt to remove, and any optimization
framed as "eliminate the failed Factory2 attempt" targets a problem this
environment does not have.

The fallback is still left in the code, deliberately: it is a portability guard
for systems where Factory2 is unavailable, and D1 does not remove it.

## 2. Question A answered: `open` is 97.8 % WIC-internal, not OS file I/O

```text
CreateDecoderFromFilename total   68,000.8 ms   2.6257 ms/call
OS CreateFileW reference           1,490.5 ms   0.0576 ms/call
WIC-specific remainder            66,510.3 ms   2.5682 ms/call   = 97.8 % of open
probe count 25,898, probe failures 0
open HRESULT failures 0
```

The actual OS cost of opening the file is **0.0576 ms**, about **2.2 %** of the
`open` bucket. The remaining 97.8 % is WIC's own work inside the single
`CreateDecoderFromFilename` call: opening the file, probing the format, and
instantiating the decoder.

So the name "file open" is misleading. The cost is not file I/O in the ordinary
sense; it is WIC decoder construction. The plain `CreateFileW` reference probe
is what makes this visible — without it, 2.6 ms of COM work would have been
attributed to "opening a file", and an optimization targeting file handle
management would have looked reasonable and done nothing.

`open` cannot be split further without switching to
`CreateStream` + `CreateDecoderFromStream`, which changes how WIC is used and is
a Non-goal for D1.

## 3. factory split, and the identity check

```text
Factory2 attemptMs   17,769.0 ms   0.6861 ms/attempt
fallback attemptMs        0.0 ms   0.0000 ms/attempt
split              17,769.0 vs factoryMs 17,769.0 -> OK (<=)   over 0.0000
```

`factory2Ms + factoryFallbackMs` reconstructs `factoryMs` exactly.

### A bug this caught

The first implementation of this split reported `factoryMs = 235,023,895 ms` —
absurd for a ~2 minute workload. The cause: the shared `createWicFactory` helper
accumulates into **running totals**, and the call site then added
`tel->factory2Ms + tel->factoryFallbackMs` to `factoryMs` on every call. The
first attempt was therefore counted once, the second twice, the third three
times, and the sum grew quadratically with the call count.

This is exactly the failure the pre-register's stop condition 5 anticipated
("`factory2Ms + factoryFallbackMs` does not reconstruct `factoryMs`"). The fix
takes the per-call **delta** at each site. The bug is recorded here rather than
quietly corrected, because a quadratic double-count would have produced
plausible-looking but wrong percentages if the buckets had been less obviously
broken.

## 4. Timing Semantics

Exclusive. `factory2Ms` and `factoryFallbackMs` are disjoint and sum to
`factoryMs`; the identity is published as `factorySplitOverMs` so a consumer can
check it rather than trust it.

`osFileOpenProbeMs` is **deliberately excluded** from `openMs` and from the
decode stage sum. It is a reference measurement on the same path, not part of
the decode path. It does add I/O, which is why D1's absolute `open` is slightly
lower than D9d's (2.6257 vs 2.7749 ms/call): the probe warms the OS file cache
for the subsequent WIC open. The stage *shares* are the signal.

No timer is inside any inner loop. D9d's instrumentation was kept, and its
exclusive verify identity still holds exactly.

## 10. Limitations

- `CreateDecoderFromFilename` is not separable without changing WIC usage, so
  the split is "OS file open" vs "everything WIC does internally", and the
  latter is not further subdivided.
- The OS probe warms the file cache, so D1's `open` is lower than D9d's. The
  reference figure is still valid as a *lower bound* on the OS cost.
- `factory` figures are not directly comparable to D9d for the reasons in §5.
- The D9d 4.1 % unmeasured gap between `decodeSubSumMs` and `decodeTotalMs`
  remains unmeasured; it is inter-call code (allocation, `GetSize`, HRESULT
  checks).
- Single host, single dataset, one configuration, 5 runs, one machine.
- Factory2 succeeding 100 % is a fact about **this** Windows configuration. A
  machine without it would see the fallback fire, so the 0 % must not be
  generalized.

## 11. Next Candidate

**Not implemented here.** Both questions are answered, and the answers point
somewhere different from where D9d left off.

> **The next candidate is WIC decoder construction, not file I/O and not the
> Factory2 fallback.** `open` is 97.8 % WIC-internal and `factory` is a single
> working activation. The candidates that survive measurement are: (a) not
> constructing a decoder per call, (b) not decoding the same file twice per miss,
> and (c) whether a single larger decode could produce both the 64x64 and the
> aspect-preserving buffer that the current two-pass design requires.

Explicitly ruled out by measurement, with the numbers:

- **Removing the Factory2 fallback** — 0 fallbacks in 25,898 calls. Nothing to
  remove on this machine.
- **Optimizing file handle / stream management** — the OS cost is 0.0576 ms,
  2.2 % of `open`.
- **`WICBitmapInterpolationModeFant`** — 0.32 % (D9d).
- **EXIF skip** — 0.17 % (D9d).
- **`frame_ssim`** — 0.54 % of the verify (D9d).
- **Cache mutex contention** — 0.07 % of decode (D9d), reconfirmed at 71.5 ms
  total in D1.

The next pre-register must first decompose the 2.5682 ms WIC-internal portion,
because `CreateDecoderFromFilename` still hides at least three things (file
open, format probe, decoder instantiation) behind one call, and D1 has shown
that guessing between them is unreliable.

Candidate A (candidate arrival reduction) stays deferred: it touches candidate
recall, false positive/negative risk, and verdict semantics.
