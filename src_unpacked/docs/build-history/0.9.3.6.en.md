# MediaSimilarityFinder v0.9.3.6 — Thumbnail DB Contention Fix + Stall Fills

## Need for change
- The direct cause of mid-scan preview stalls is identified. The GUI `thumbDb_`
  and the worker engine `db_` share one `index.sqlite`, and the worker holds a
  write transaction open for most of the scan. Every freshly decoded thumbnail
  called `putThumb()` on the GUI thread, blocking up to 5s waiting for the lock.
- Match-less phases (video analysis, listing) never opened a fill, freezing the list.

## Previous structure
- Synchronous `putThumb()` per decode. `refreshStreaming` filled only on new matches.

## New structure
- Persistence is deferred mid-scan. JPEG bytes queue up (capped at 1000) and flush
  once at scan end (after worker records commit) and before the next scan starts
  (before worker launch). Memory/disk reads stay live; only the blocking is gone.
- `thumbStarved_` joins the `refreshStreaming` gate so match-less phases still fill
  progressively within the existing adaptive cadence (600ms-3s).
- Thumbnail-source counters (memory/disk/engine/shell/decode/placeholder/fail) are
  logged to `scanLog` at scan end. Render tracing gap closed.
- Version strings unified → 0.9.3.6.

## Resolved situation
- The direct GUI-freeze cause during scans is removed.
- Stalled phases fill progressively.
- Thumbnail provenance is visible in logs.

## Validation
- Core+GUI Release build: PASS, **CTest 59/59 PASS**.
- GUI-thread visual behavior has no automated test; verified by code review.
- Portable `--smoke` exit 0, `MediaSimilarityFinder-v0.9.3.6-Portable-Windows-x64.zip` produced.

## Future impact
- Scan-time entries persist in one post-scan batch, so a force-quit loses only that
  batch from the disk cache (recovered via engine LRU/re-decode next scan).
