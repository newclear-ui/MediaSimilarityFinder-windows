# MediaSimilarityFinder v0.9.4.107 — A/AB 타깃 열거 (변경 파일 한정 후보 탐색)

기준선 `0.9.4.106` → 본 빌드 `0.9.4.107`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` 불변.

## 1. 변경 필요성

0.9.4.106 사용자 실측(§7.3)에서 A/AB 모드는 최종 패스 검증을 0~1회만 수행하는데도 analyze가 **170.2~185.8초** 걸렸다. 그 구성은 index 1.2~1.4 s + **열거 168.8~184.4 s**(verify 0)였다 — 변경 파일이 0~64개뿐이어도 전체 dataset(177k)의 index seed + 크롭(4:3/1:1/9:16) 열거를 전량 수행한 뒤 `included()`로 버리는 구조였다. worklog 후보 `P-0.9.4.106-A-targeted-enum`(PROPOSED)으로 기록된 이 고정비를 제거한다.

## 2. 기존 구조

- A/AB(`changedFiles != nullptr`)는 B와 동일한 열거 경로를 탄다: 병렬 이미지 전체 패스 → 비디오 윈도우 패스 → (미완결 시) seed + 크롭 윈도우 패스(`consumeWindowed`, 순차). `process()`가 `included()`로 "변경 파일에 닿은 쌍"만 남긴다.
- 비용은 dataset 크기에 비례(177k 기준 ~170-186 s)하고, 변경 수와 무관하게 고정이다.

## 3. 변경 구조

- **`ScanPipeline::analyze`에 `consumeTargeted` 추가** (`src/scan_pipeline.cpp`): `changedFiles != nullptr`이면 전체/크롭 열거 대신, **변경 파일마다 자신의 해시로 동일 index를 질의**한다.
  - 이미지: `imageIdx_`(fingerprint, mirrorFingerprint), `c4_`(crop4x3), `c1_`(crop1x1), `c916_`(crop9x16) — `indexFile`이 crop index에 **일반 크롭만** 넣으므로 질의도 일반 크롭만 사용(미러 크롭 질의를 추가하면 기존에 없던 쌍이 생겨 parity가 깨진다).
  - 비디오: `videoIdx_`(fingerprint, mirrorFingerprint, **anchors 전부**), `vc4_`/`vc1_`/`vc916_`.
  - 발견된 쌍은 기존 `dedupCrop`/`seen` 집합으로 중복 제거되고 **동일한 `process()`** 로 처리된다(bestMatch → verifyImagePair/시간축 → `included()` 필터 → 방출). 발견 집합·필터·방출이 동일하므로 판정 불변.
- **`candidates` 의미 변경(A/AB 한정)**: 이제 "이 패스가 실제로 고려한 쌍"(= 변경 파일에 닿은 후보 쌍)을 센다. 리포트/텔레메트리의 `candidates`·`reduction`이 A/AB에서 작아진다(B는 불변).
- **B 모드 무변경**: 전체 열거·B 슬라이스·`analyzeCheckpoint` 전부 그대로.
- **parity 고정**: `analyze_mode_test`에 (3b) 추가 — A 부분(변경 2) candidates=3, AB 부분 candidates=3, A 콜드 candidates=B와 동일, B candidates 불변. 총 22 checks.

## 4. 해결된 상황

- A/AB의 analyze 고정비가 dataset 크기에서 **변경 파일 수**로 이동한다: index(1.2~1.4 s) + 변경 수 × 해시 질의(수백 µs~ms). 177k dataset, 변경 0~64 기준 기대 analyze ≈ **2~4초**(기존 170~186초). B 모드는 종전 비용 유지(전 쌍 재검증이 설계).
- 판정·그룹·저장 쌍은 불변(동일 `process()` 경로 + parity 테스트).

## 6. 향후 영향 및 한계

- engine/DB/schema/cache·`kProtocol` 불변(성능 전용, 판정 불변).
- `candidates` 의미가 모드별로 달라진다(A/AB = 변경 접촉 쌍, B = 전체 후보 쌍) — 문서/리포트 해석 주의.
- AB 콜드(전체 변경)는 여전히 전 파일 질의를 수행한다(기존과 동급 비용). "전부 변경 + AB"에서 included()가 전부 거르는 것을 이용한 조기 스킵은 별도 후보(비디오 예외 처리 필요).
- **Future revisit condition**: 실측에서 변경 수가 매우 큰(수만) 경우 질의 비용이 커질 수 있음 — 그때는 변경 파일 측 해시만 담은 임시 index 또는 파티션 스캔 하이브리드 검토.
