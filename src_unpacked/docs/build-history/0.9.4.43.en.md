## 1. Why the change was needed

The F preflight established that NVDEC genuinely runs on the RTX 3080 Ti (`Runtime PASS` /
`Decode PASS`), and produced a `Pixel-exact FAIL` on a 4K H.264 fixture. This stage is not an
NVDEC implementation; it establishes the **safety contract that must hold before NVDEC is used**.

Central principle (directive §44):

> Separate "GPU decode is possible" from "GPU decode is still exact".

## 2. Previous structure

- All production video decode is software FFmpeg. There is no NVDEC/CUDA path.
- Node E covers **sampling strategy** (Sequential/Sparse) and does not cover the **decode backend**.
- E-3B refused sparse seek for lack of exactness proof, and `ExactnessPolicy::RefuseAll` is the default.

## 3. New structure

The addition is **probe/test only**. No production decode decision changed.

- `tests/f_random_access_safety_test.cpp` — contract definition + 20-check selfcheck, registered
  with CTest. `msf_core` does not include it and no production path reads it.
- `CMakeLists.txt` — version `0.9.4.43`, test registration.

### 3-1. Contract structure (directive §6, §28)

```text
Video → Codec capability → Decoder availability
      → Random-access safety → Exactness compatibility → NVDEC candidate
Any step not established → CPU software fallback
```

Target defence in depth:

```text
E Planner → Sparse/Sequential → F Backend Selector
                               → Random-Access Safety
                                  ├─ SAFE → NVDEC
                                  └─ UNSAFE/UNKNOWN → CPU
```

### 3-2. Three states and policy (directive §7, §24, §25)

```text
RandomAccessSafe / RandomAccessUnsafe / RandomAccessUnknown
Unsafe → CPU,  Unknown → CPU
```

`Unsafe` and `Unknown` are **deliberately collapsed**. A stream whose safety is merely unproven
must not be sent to the hardware path, so there is no optimistic branch anywhere.

### 3-3. Decision order (must not be reordered)

```text
1. no hardwareCapability    → Unknown (moot, treated as CPU)
2. startIsKeyFrame false   → Unsafe
3. firstDecodedPts > request → Unsafe
4. predicate not reproducible → Unknown
5. exactnessVerified false → Unknown   ← forced by measurement
6. otherwise                → Safe
```

## 4. What was resolved

### 4-1. Core reversal — "starting at an IDR is safe" is false

The assumption at F-1 kickoff was `mid-GOP start = unsafe`. A survey of the whole dataset showed
that assumption is **insufficient**.

| file | file-start | mismatch | exact |
|---|---|---|---|
| h264_0648x1080_30fps_030s | IDR(0) | 0/20 | YES |
| h264_1080x1920_30fps_030s | IDR(0) | **1/20** | **NO** |
| h264_1360x0808_30fps_030s | IDR(0) | **20/20** | **NO** |
| h264_1920x1080_30fps_300s | IDR(0) | 0/20 | YES |
| h264_3840x2160_30fps_020s | **P(23)** | 20/20 | NO |

**13 of 14 dataset files are IDR-start** (key=1 at index 0). mid-GOP is that one 4K file.

However **1360x0808 is IDR-start yet mismatched 20/20**, and it **still mismatched 20/20 when
decoding was restarted from a confirmed IDR (ss 2.0)**. So mid-GOP is **only one** failure mode,
and NVDEC exactness does not hold at 4K either, nor merely because a stream is IDR-start.

→ The contract therefore makes `exactnessVerified` a **necessary** condition for `Safe`.
Structure is necessary but not sufficient.

### 4-2. 1360x0808 characterisation (INCIDENT-F1-1)

- 98.6 % of bytes differ, `maxAbs=185`, `meanSigned=0`
- Persists when both paths stop at nv12 (Y maxAbs 143, chroma maxAbs 169) → **not format conversion**
- **Chroma is affected more than luma**
- 1360x808 has a **height 808 that is not 16-aligned** (chroma plane height 404). This looks like a
  decode mismatch at non-aligned chroma placement, but **the root cause is not confirmed in this
  stage** (parser forbidden, new fixtures forbidden).

### 4-3. Eliminated hypotheses

| hypothesis | evidence | status |
|---|---|---|
| 4K resolution itself | 4K is exact from a confirmed IDR | weakened |
| mid-GOP start | 1360x808 is IDR-start yet mismatches | **explains only part** |
| format conversion | persists with both paths at nv12 | weakened |
| software threading | default == `-threads 1` | eliminated |
| corrupted decode | 0 warnings on both paths | not supported |
| frame-rate mismatch | r=60 vs avg=59.95, but frame identity matches | weakened |

|---|---|---|---|---|
| mid-GOP start (4K) | baseline | differ | **NO** | CPU fallback |
| Confirmed IDR onwards (4K) | baseline | same | YES | NVDEC candidate |
| **File-start IDR fixture (1360x808)** | baseline | differ | **NO** | **CPU fallback** |
| **File-start IDR fixture (1080x1920)** | baseline | 1/20 differ | **NO** | **CPU fallback** |
| File-start IDR fixture (0648x1080) | baseline | same | YES | NVDEC candidate |
| File-start IDR fixture (1920x1080 300s) | baseline | same | YES | NVDEC candidate |
| Unknown safety | baseline | n/a | n/a | CPU fallback |

Control: software A vs A byte-identical (all files); `default == -threads 1` byte-identical.

### 5-2. Fallback (Gate C)

By contract, mid-GOP **and unproven IDR-start** both take `CPU fallback`. The fallback uses the CPU
baseline directly, so the result cannot change, and the selfcheck verifies that neither `Unsafe`
nor `Unknown` selects the hardware path.

### 5-3. Performance preflight (Gate D)

Measured on a **confirmed exact-condition file** (`real_h264_1920x1080_30fps_300s.mp4`, 0/20 exact),
3 runs, median. The `bench: total` field does not exist in this build, so PowerShell wall clock was used.

| case | 100 frames | full 870 frames |
|---|---|---|
| CPU software decode + output | **0.112 s** | **4.438 s** |
| NVDEC + transfer + output | 0.337 s | 9.397 s |
| NVDEC decode only (GPU-resident) | 0.342 s | — |

Marginal cost (the extra 770 frames): CPU ≈ 5.62 ms/frame, NVDEC ≈ 11.77 ms/frame.
**NVDEC is 2.1× slower per frame.** This is not a fixed-overhead story.

**Measurement limitation (recorded honestly)**: this run downloads **every** frame through
`hwdownload`. Production samples roughly 12 frames per video, so real transfer cost may be smaller.
Even so, for the production usage pattern (sparse decode is not available, so a full decode plus
selective download is required) **there is no performance case for NVDEC**. At 100 frames NVDEC
was already 3× slower.

## 6. Future impact

- **PRODUCTION ADOPTION = NO.** F-2 production integration is **forbidden** (directive §41).
- **There is no evidence that NVDEC exactness holds generally for H.264.** 2 of 4 IDR-start
  H.264 files mismatched.
- The core contract rule is "structure is necessary, a recorded exactness proof is sufficient".
- **Additional fixture required (directive §42)**
  - Reason: the dataset has no 4K IDR-start H.264, and it is impossible to tell whether the
    1360x808 non-aligned chroma problem is a root cause or merely a size effect.
  - Expected information gain: (a) whether exactness holds for 4K IDR-start; (b) whether the
    problem reproduces on H.264 with non-16-aligned height, which decides whether 1360x808 is a
    structural issue.
  - **Not generated in this stage** (directive §16/§13/§42). Awaiting a separate instruction.
- The 1360x808 root cause remains `INCONCLUSIVE`. Narrowing it via direct SPS/PPS parsing is not
  permitted under the parser prohibition.
