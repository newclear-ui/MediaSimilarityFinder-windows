# MediaSimilarityFinder v0.9.4.9 — Node C1: Profile Foundation

C1 검증 기준점. calibration 없이 profile 데이터 모델·INI 저장소·
판정·initial-estimate 전달 구조를 만든다. 엔진 1.5.0·DB 1.0.3·캐시
v9·schema 1 불변.

## 변경 필요성
- 스케줄러는 매 스캔을 하드웨어 프록시에서 시작했다. 장기 baseline을
  저장할 구조가 없어 C2 calibration이 올라갈 곳이 없었다.

## 기존 구조
- 성능 프로파일 영속화 없음. `CalibrationTelemetry`는 구조만 있었다.
- 스케줄러 baseline = 하드웨어 프록시 직결.

## 변경 구조
- 신규 `src/profile.h/.cpp` (Qt-free, `msf_core` 편입):
  `PerformanceProfile`(id·identity·confidence·timestamps·6개 metric),
  `ProfileMatch`(Missing/Exact/Soft/Hard/Stale),
  `ProfileStore`(load/save/classify/initialEstimate).
- id는 identity FNV-1a hex(재시작에도 안정, 판정은 필드로 수행).
- 판정 순서 Missing→Hard→Stale→Soft→Exact. Stale은 호출자가 준
  maxAge로만 발화(C1은 기본 age 정책 없음, C3 몫).
- initialEstimate는 Exact/Soft + 양쪽 throughput 실측일 때만 pair로
  반환한다. 한쪽만 덮어쓰면 비율이 깨지므로, CPU-only 머신은 estimate
  불가(CPU 경로는 원래 fallback이라 정상).
- INI 수동 codec(escape·forward-compat 무시 규칙·strict 수치).
  저장은 같은 디렉토리 temp+rename(실패 시 remove+rename 폴백).
  프로파일은 재생성 가능 캐시라 원자성 창고 crash는 문서화된 한계다.
- QSettings 미재사용: 비원자 + 문자열 상태라 Node A 측정 원칙과
  맞지 않는다.
- Brief §5 개념 구조와의 대응: 섹션·키 철자는 C1 코드가 고정한다.
  `gpuBatchThroughput`·`transferBandwidthMBps`(cost 대신 brief 개념인
  bandwidth)·`driver`·`benchmarkSchemaVersion` provenance를 포함하고,
  `[lastUpdate]`는 C3 업데이트 정책과 함께 온다. `profileVersion` 정수
  1과 brief의 "1.0"은 동일 세대 표기다.
- 스케줄러 우선순위: live rate → profile baseline → hardware proxy.
  `profile_baseline` reason 신설. 정책(share/hold/band/binding) 불변.
- 엔진 후크: 머신 전역 `<appDir>/Index/PerformanceProfile.ini` 로드,
  usable estimate면 baseline 대입. C1 live에서는 writer가 없어 항상
  하드웨어 값(동작 동일).

## 선택 이유
- live>profile>hardware 우선순위를 C1에서 고정해야 C2가 writer만
  얹으면 된다. 판정·단위·원자성 규칙을 먼저 굳히는 게 C1의 전부다.
- C2/C3 수치(calibration 시간·confidence 조정·stale 기본 age·
  재측정 임계)는 아직 정하지 않았다. 메커니즘만 있고 정책은 없다.

## 해결된 문제
- C2 진입 조건(저장소·판정·전달 API) 충족.

## 정확성 영향
