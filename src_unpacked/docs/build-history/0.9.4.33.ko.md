## 1. 목적

I-1 은 중간 8-bit GrayImage 를 공유했기 때문에 2단계 Fant 체인이 생겼고,
그 결과 f/a byte parity 가 깨졌다. 이번 후보는 **중간 GrayImage 를 만들지
않는다.** factory · decoder · frame · EXIF orientation source 만 공유하고,
최종 scaler/converter/`CopyPixels` 는 두 개를 독립적으로 만든다.

핵심 질문은 **속도가 아니라 exact output parity** 였다.

## 2. 후보 구조

```text
파일
 ↓  CoInitializeEx                      1회
 ↓  WIC factory                         1회
 ↓  CreateDecoderFromFilename           1회
 ↓  GetFrame(0)                         1회
 ↓  EXIF orientation (FlipRotator)      1회
 ↓  공유 src (IWICBitmapSource)
      ├── scaler A -> 64x64    -> converter A -> CopyPixels A -> f
      └── scaler B -> aspect64 -> converter B -> CopyPixels B -> a
 ↓  모든 COM object release
 ↓  CoUninitialize                      1회
```

제품 경로(`decodeWicFile` / `decodeWicFileAspect`,
`src/image_decoder.cpp:154` / `:238`)는 두 번씩 factory·decoder·frame·
metadata·orientation 을 수행한다. 후보는 그 앞부분만 한 번으로 줄인다.

**생산 코드는 변경하지 않았다.** 측정은 전부 별도 실행파일
`tests/shared_wic_source_probe.cpp` 안의 자체 WIC 파이프라인으로 수행했고,
baseline 은 제품 함수를 **호출**했다.

### 3.1 검증 중 실제로 발생한 결함 2건 (자기 정합성 검사로는 잡히지 않음)

probe 작성 중 두 가지 실제 결함이 발생했고, 둘 다 문서화된 위험과 정확히
일치했다. 이 실험의 가치가 여기에 일부 있다.

1. **COM lifetime 순서 위반 → access violation.** `(C)` 검증 블록이
   factory/decoder/frame/rotator/converter 가 **살아 있는 상태에서**
   `CoUninitialize()` 를 호출했고, 스코프 종료 시 접근 위반으로 프로세스가
   죽었다(0xC0000005). 제품 소스가 경고하는 바로 그 실패다
   (`src/image_decoder.cpp:150-153`).
   → 해결: WIC 객체를 **전부 헬퍼 함수가 소유**하게 하고, 호출자가 헬퍼
   반환 **이후에** `CoUninitialize` 하도록 구조를 바꿨다. 실패 경로까지
   자동으로 안전해진다. 후보 본체도 같은 구조다.
2. **실패 집계가 상쇄되고 있었다.** 측정 루프가
   `if (!okCand) continue;` 를 `if (!okBase)` 검사보다 먼저 두어, 후보가
   실패한 5개 파일에서 **baseline 실패가 세어지지 않았다.** `baseFail=0` 이
   보이기에 "baseline 은 5개를 성공하고 후보만 실패했다" 고 오판할 뻔했다.
   → 수정: 양쪽을 독립적으로 기록하고, baseline 만 성공하고 후보가 실패하는
   `candOnlyFail` 를 별도 카운트로 추가했다. 실제로는 **양쪽 모두 같은 5개를
   실패**했다(§5).

## 4. COM lifetime 최종 구조

```text
candidateSharedSource()
  CoInitializeEx
  runSharedPipeline()      <- 모든 WIC ComPtr 를 이 함수가 소유
  CoUninitialize           <- 반환 후이므로 반드시 살아 있는 객체가 없다
```

`runSharedPipeline` 이 반환하면 factory·decoder·frame·rotator·scaler A/B·
converter A/B 가 전부 해제된 상태이고, 그 다음에만 `CoUninitialize` 가
실행된다. 모든 return 경로(성공·실패)에 대해 성립한다.

## 7. Q4 — WIC 는 실제 decode workload 를 공유하는가

**공유한다.** 이게 후보의 실체다. CPU run 1 (n=849):

| CopyPixels | baseline mean | candidate mean | 비율 |
|---|---:|---:|---:|
| f (첫 번째) | 3.9224 ms | 3.8801 ms | 1.01× |
| a (두 번째) | 3.8833 ms | **1.0917 ms** | **0.28×** |

- baseline 은 두 파이프라인이므로 **둘 다** 풀 decode 비용을 낸다.
- 후보는 첫 `CopyPixels` 가 풀 decode 비용을 내고, 두 번째는 그
  ~1/3.6 로 내려간다.
- 즉 factory/decoder/frame 생성만 줄고 `CopyPixels` 는 그대로 비싸다면
  비용이 줄지 않았을 것이다. 실제로 줄었으므로 H3 이 확인되고,
  반대 가설 H4 는 **기각**된다.

## 8. EXIF — PARTIAL / not_measured

```text
exif_status = not_measured
```

- 표준 dataset 은 `orient_applied_files = 0` 이므로 EXIF 분기가 본 측정에서
  실행되지 않는다. 이는 I-1 부터 이어지는 기존 사실이다.
- 표준 dataset 은 변경하지 않았다. dataset 안 JPEG(`f0000.jpg`, 209x248) 의
  SOI 뒤(있는 경우 APP0/JFIF 뒤)에 EXIF APP1 orientation 1~8 을 삽입한
  fixture 8개를 별도 디렉터리에 생성해 baseline/후보 byte parity 를
  비교했다. **8/8 byte 동일.**
- 그러나 **제품이 적용한 orientation 이 0건**이었다. 즉 이 fixture 는
  EXIF 분기를 실행하지 못했다. WIC metadata reader 는
  `WINCODEC_ERR_PROPERTYNOTFOUND (0x88982F41)` 를 반환했고, 시도한
  query path 는 아래 4종이었다.

```text
/app1/ifd/exif/{ushort=274}    (제품이 쓰는 경로)
/app1/ifd0/exif/{ushort=274}
/app1/ifd/{ushort=274}
/app1/exif/{ushort=274}
```

- 원인 규명은 **이 실험의 범위를 넘어선다.** 후보와 baseline 은 orientation
  태그를 **똑같은 코드로** 읽는다. 확인된 것은 EXIF fixture 가 이
  환경에서 WIC 에게 보이지 않는다는 사실이며, 이는 후보만의 문제가 아니라
  **제품 EXIF 경로 자체가 dataset 에서 한 번도 실행되지 않았을 가능성**을
  함께 시사한다. 이 항목은 별도 후속 과제로 등록한다(§12).
- 따라서 **A5(EXIF parity)는 PASS 로 기록하지 않는다.** 후보의 EXIF 관련
  위험은 다만 구조적으로 낮다. FlipRotator source 를 두 scaler 가 공유하는
  경로는 selfcheck 에서 byte 동일으로 PASS 했고(§3 C), 메타데이터 검출
  코드는 양쪽이 동일하다. 그래도 **종단간 검증은 미측정**이다.

## 9. PGM — PASS

```text
후보 PGM 구조: readPgmFile 1회 → 원본 buffer 공유 → scaleGray 2회
```

- 제품 `decode()` 가 WIC 실패 후 P5 fallback 으로 처리하는 결과와
  후보의 read-once/scale-twice 구조가 **f/a 모두 byte 동일**하다
  (selfcheck).
- `readPgmFile` 은 P5 전용·`maxv` 정규화 없음이라는 제품 동작을 그대로
  유지했다. 헤더 파싱도 제품과 동일하게 토큰 스캔 + 공백 1바이트 소비다.
- 표준 dataset 에 PGM 이 없어 본체 dataset 측정에는 포함되지 않는다.
  fixture 기반 검증이다.

범위가 3,341/3,341 로 확대되고 full-scan groups 전수 비교까지 추가되었다.
바뀌는 것은 측정 범위의 표현, EXIF 진단의 근거, telemetry 의 의미다.
