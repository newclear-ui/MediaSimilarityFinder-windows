# MediaSimilarityFinder v0.9.4.144 — Failed-file names and reasons in the detailed log

Baseline `0.9.4.143` → this build `0.9.4.144`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged (telemetry additive keys).

## 1. Why

- In the S-3 field check, `broken.jpg` (a text file renamed to .jpg) was counted as an analysis failure, but the detailed log showed **only the count** - not which file failed or why.
- Request: list the failed files with their reasons, like the slowest-files section.

## 2. Previous structure

- On analysis failure the engine only stored the `analysis_failed` state and incremented `failed`.
- The telemetry JSON had `images/videos.slowest` only; the detailed-log dialog rendered just those lists.

## 3. New structure

- `TelemetryRecorder` gains a `FailedFile{path, reason, ms}` list (up to **50 per kind**).
- Image/video failure branches record a reason:
  - read failure -> `read failed`
  - 0 bytes -> `empty file`
  - otherwise -> `decode/analysis failed`
  - videos add the range processing time (ms).
- Telemetry JSON (additive keys, schema v9 unchanged):
  - `images.failedFiles[] = {path, reason, ms}`
  - `videos.failedFiles[] = {path, reason, ms}`
- The detailed-log dialog shows a **"Failed files (img/vid)"** section with up to 10 entries per kind as `reason — path` (the JSON keeps up to 50).

## 4. Result

- The detailed log alone explains which file was not indexed and why (e.g., `empty file — D:\...\broken.jpg`).
- CLI/JSON consumers get the same data from `failedFiles`.

## 6. Impact and limits

- The reason is a heuristic (read / 0-byte / generic decode failure). Decoder-specific HRESULT/FFmpeg error codes are not recorded.
- The list is capped at 50 per kind (log-size protection on mass failures).
- The telemetry schema version stays 9 per the additive-key rule.
