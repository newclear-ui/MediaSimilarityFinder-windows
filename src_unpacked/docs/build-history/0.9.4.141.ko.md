# MediaSimilarityFinder v0.9.4.141 — 검색 중 불러온 목록·선택·미리보기 유지 (결과는 완료 시 적용)

기준선 `0.9.4.140` → 본 빌드 `0.9.4.141`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` 불변 (표시 전용).

## 1. 변경 필요성

- 0.9.4.140에서 썸네일 캐시는 유지했지만, 검색 시작 시 **오른쪽 미리보기와 상세 정보가 "—"로 바뀌고 파일 그리드가 비워지는 현상**이 남았다(실기 보고).
- 원인은 캐시가 아니라 `beginScan()`의 뷰 초기화였다: `currentGroup_ = -1`, `currentFile_.clear()` 후 `refreshFileViews()`/`refreshDetail()`를 호출해 선택과 미리보기를 의도적으로 지웠다.
- 사용자 제안: 업데이트 중에는 불러온 목록·미리보기를 그대로 두고, 완료 시 갱신하며, 변경이 없으면 그대로 유지.

## 2. 기존 구조

- `beginScan()`이 썸네일 캐시 외에도 `bestPct_`/`resCache_`/`pathKind_`/`fileMetaAsked_`/`contentFlag_`/`allPaths_`/`matchRows_`/`fileSize_` 등을 시작 시 비우고, 선택을 해제한 뒤 두 패널을 다시 그렸다.
- 결과는 `onResults()`에서 적용되며, 그 전까지 화면은 검색 시작 시 초기화된 상태였다.

## 3. 변경 구조

- **검색 시작(`beginScan`)**: 진행 상태(`hasReport_`)와 매치 누적(`bestPct_`/`pathKind_`/`contentFlag_`)만 초기화한다. 목록·선택(`currentGroup_`/`currentFile_`)·미리보기·썸네일 캐시·파일 크기/경로 맵은 **그대로 유지**하고, 패널을 다시 그리지 않는다.
  - 매치 누적을 시작 시 비우는 이유: 빠른 로드가 저장 쌍을 즉시 재전송해 값을 다시 채우고, 변경된 쌍은 새 값을 받아야 하기 때문(이전 값과 max 병합 시 오래된 높은 %가 남음).
- **결과 적용(`onResults`)**: 최종 결과를 그대로 적용하고 `rebuildGroups()`가 대표 경로로 선택을 복원한다. 매치 상태는 여기서 리셋하지 않는다 — 하이브리드(AB)의 라이브 쌍은 `onMatch`로만 전달되고 최종 행에는 없으므로, 리셋하면 그 쌍의 유사도·배지가 사라진다.
  - 변경 없음(`analyzed == 0`): 목록은 append-first로 동일 → 화면 변화 없음. 미리보기·해상도 등 표시 값도 그대로 유지(메타데이터 캐시 유지).
  - 변경 있음(`analyzed > 0`): 검색 종료 시 썸네일·메타데이터 캐시를 무효화하고 가시 영역만 다시 요청/표시한다.
- 검색 중 스트리밍되는 신규 그룹은 기존처럼 하단에 추가된다(기존 동작 유지).

## 4. 해결된 상황

- 검색 시작 버튼을 눌러도 불러오기(Load)로 보이던 목록과 오른쪽 미리보기가 사라지지 않는다.
- 변경이 없는 재검색은 로드 상태 그대로 유지되고, 변경이 있으면 완료 시에만 갱신된다.

## 6. 향후 영향 및 한계

- 표시 전용(판정·저장·프로토콜·engine/DB/schema/cache 불변).
- 검색 중 파일을 삭제/이동하면 완료 시 선택 그룹이 사라질 수 있으며, 이때는 기존처럼 선택이 해제된다.
- 매치 union-find(`pathParent_`)는 기존과 동일하게 검색 시작 시 비우지 않는다(결과 적용 시 매치·메타 상태만 리셋). 이는 0.9.4.81 이후의 기존 동작을 유지한 것이다.
