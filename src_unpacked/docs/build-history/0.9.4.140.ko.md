# MediaSimilarityFinder v0.9.4.140 — 스캔 시작 시 미리보기(썸네일) 유지 (변경된 파일만 종료 후 갱신)

기준선 `0.9.4.139` → 본 빌드 `0.9.4.140`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` 불변 (표시 전용).

## 1. 변경 필요성

- 실기 확인(0.9.4.139 S-1): 불러오기(Load)로 미리보기가 보이던 상태에서 검색을 시작하면 **미리보기가 전부 사라지고 검색이 끝날 때까지 빈칸**으로 남았다.
- 이는 기능 결함은 아니지만 체감 품질 문제다. 검색 중에는 백엔드가 바쁘므로 썸네일 재요청이 검색 뒤로 밀린다.

## 2. 기존 구조

- `beginScan()`이 검색 시작 시 메모리 표시용 썸네일 캐시를 통째로 비웠다(`thumbCache_.clear()`).
- 목록 행이 다시 채워지면 캐시가 비어 있어 자리표시자로 시작하고, 화면에 보이는 행부터 백엔드에 썸네일을 다시 요청한다. 검색 중에는 이 요청이 처리되지 않아 검색 내내 빈칸이었다.
- 백엔드 썸네일 저장소는 `(경로, mtime, size)` 신원으로 디스크 캐시를 조회하므로, 파일이 바뀌면 새 요청에서 최신 아트를 준다. 그러나 GUI 캐시 적중 시에는 요청 자체가 없어 낡은 아트가 남을 수 있었다.

## 3. 변경 구조

- **검색 시작**: `thumbCache_.clear()` 제거. 행이 유지/재생성되어도 기존 아트를 즉시 재사용한다. `scanLog("thumbCache kept=N")`로 상태를 남긴다.
- **검색 종료**: 완료·중단 메시지의 `analyzed`가 1 이상일 때만(실제로 파일을 다시 읽은 경우) 캐시를 무효화하고, 백엔드가 한가한 시점에 `thumbCatchUpVisible()`로 **보이는 행/파일 그리드/선택 미리보기만** 다시 요청한다.
  - 도착 전까지 행은 기존 아이콘을 계속 그리므로 빈칸이 생기지 않고, 변경된 파일은 새 아트로 교체된다.
  - `analyzed == 0`(전부 unchanged)이면 캐시를 그대로 유지한다. 이 경우 파일 내용이 바뀌지 않았으므로 재요청 자체가 불필요하다.
- `scanLog("thumbCache invalidated analyzed>0")`로 무효화 시점을 기록한다.

## 4. 해결된 상황

- 이미 인덱스된 폴더를 다시 검색할 때 미리보기가 사라지지 않고 유지된다.
- 실제로 수정된 파일이 있으면 검색 종료 직후 보이는 화면부터 새 미리보기로 갱신된다(검색 중 빈칸 없음).

## 6. 향후 영향 및 한계

- 표시 전용(판정·저장·프로토콜·engine/DB/schema/cache 불변).
- GUI 메모리 캐시 상한(3000개)과 표시 크기별 키(path|WxH)는 그대로다.
- 검색 중 파일이 바뀌어도 종료 전까지는 이전 아트가 보일 수 있다(종료 시 analyzed>0이면 갱신). 검색 중 실시간 교체는 하지 않는다.
- Load/재검증은 기존처럼 뷰를 새로 구성하며 캐시를 비운다(대상 세트가 바뀌는 경로).
