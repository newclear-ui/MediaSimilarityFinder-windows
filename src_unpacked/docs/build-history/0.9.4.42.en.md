# 0.9.4.42 — E-3B Adaptive Sampling Planner Calibration and End-to-End Validation

- **Verdict**: `NOT ACCEPTED`
- **Summary**: `EXACTNESS = DISPROVEN` / `SPARSE_SEEK_PRODUCTION_ADOPTION = NO` / `E_NODE = NOT COMPLETE`
- **Production default**: Sequential, unchanged
- **Commit order**: brief alone (`b3ee35e`) → implementation/measurement
- **Date**: 2026-09-29

---

## 1. Why the change was needed

In v0.9.4.40 (E-2B) exact sparse seek pixel parity rose to 13/14. The one remaining failure was HEVC 1080p, and v0.9.4.41 (E-3A) established that HEVC is not exact under sparse seek, closing it as `HEVC = SequentialPreferred`.

One question remained. **Is sparse seek on H.264 genuinely identical to the production result?** E-3B addresses only that.

## 2. Previous structure

- `VideoFingerprintEngine::build()` called only `VideoDecoder::framesAt96Plus32()`. That function makes a single sequential pass from the start of the file and, for each target, takes the first frame satisfying `ft + 0.05 >= target`. Both resolutions (96x96 and 32x32) come from **that one sequential sweep** (a second full sweep previously cost about 50% of build time).
- The exact sparse seek path, `VideoDecoder::framesAt96Plus32ExactSparse()`, was added in E-2B but **was never called from production**. It was probe-only.
- The E-2A/E-2B exactness measurements **compared seek-based implementations inside the probe with each other**.

## 3. New structure

### Added

- `src/video_sampling_planner.{h,cpp}` — classification only. No decoding, no FFmpeg calls, no I/O. It answers from inputs alone (codec, duration, fps, resolution, GOP confidence, sample count).
- `VideoDecoder::codecName()` / `gopFramesFromIndex()` — cheap facts taken from the already-open format context, so the file is not opened twice. `gopFramesFromIndex()` reads the container **index**; it does not scan packets.
- `VideoDecoder::framesAt96Plus32ExactSparse()` — wired into the production path.
- `ExactnessPolicy` — `RefuseAll` (default) / `AllowVerified`.
- Telemetry: plan fields in `VideoBuildStats`, `BenchmarkRecorder::addVideoPlan()`, and a `videos.sampling` object in the benchmark JSON.
- `tests/video_sampling_planner_test.cpp` — 31 classification selfchecks, registered with CTest.
- `tests/video_sampling_e2e_test.cpp` — end-to-end A/B/C validation driving the **real `MediaSearchEngine::scan()`**. Deliberately not registered with CTest: it needs a dataset and it measures wall clock, so putting a timing test in the regression suite would create a flaky test rather than a useful one.

### Run switch

`MSF_VIDEO_SAMPLING` = `off` (default) / `adaptive` / `forced-sparse`.
`forced-sparse` is a **diagnostic** that skips only the cost decision. It does not skip the exactness policy or the executor contract.

## 4. What was resolved

### 4-1. Self-referential exactness measurement (central finding)

E-2A reported "bit-identical 1/1" and E-2B reported "pixel parity 13/14". But both compared one seek-based implementation against *another* seek-based implementation, and both call `av_seek_frame` + `avcodec_flush_buffers`. They therefore **shared the same decoder reference-state loss** and agreed for the wrong reason.

The e2e test built in E-3B is the first to include the production from-zero sweep, and there one 4K H.264 file **genuinely diverged**, with `reference count overflow` / `no frame!` / `concealing ... errors` in the log. The seek path reconstructs frames the from-zero sweep does not.

This is not "sparse seek is too slow". It is **"sparse seek is demonstrably inexact"**, and those are entirely different conclusions.

### 4-2. Three real defects found and corrected

| # | Defect | Fix |
|---|---|---|
| ① | The executor returned a **truncated result as success** via `return !out32.empty()`. If reads ran out before a target was reached, a smaller hash set was treated as success, which would change search results | Added `out96.size()==seconds.size()` / `out32.size()==seconds.size()` contracts; violations discard and return `false` |
| ② | Container-index GOP was reported as `GopConfidence::Known`. For the 4K H.264 file the measured index implied ≈109 while decoded I-frames implied ≈120 — a disagreement | Downgraded to `Estimated`. `Known` is reserved for values corroborated against decoded I-frames |
| ③ | A `0.5 × framesPerSample` threshold I had added is a brief-forbidden "simple threshold" and **contradicts the calibration data** (E-2A measured 5s/25fps/gop11 as a 72.7 % win) | Removed. Only the `sampleCount × (GOP/2) < totalFrames` comparison remains |

③ was caught by the selfcheck. With it, all five measured cases resolve correctly:

| file | frames/sample | sparse work vs sequential work | measured | decision |
|---|---|---|---|---|
| gop250 | 46.8 | 2000 vs 750 | loss | Sequential |
| gop225 | 53.1 | 1912 vs 902 | loss | Sequential |
| gop60 | 46.9 | 480 vs 750 | win | Sparse |
| gop30 | 56.2 | 240 vs 900 | win | Sparse |
| gop11 | 20.8 | 33 vs 125 | win | Sparse |

### 4-3. Production decision

`ExactnessPolicy::RefuseAll` is the default. Since no codec holds a production-parity proof, **every file is Sequential** and sparse is **unreachable in production**.

This is not a permanent rejection; it is the **absence of evidence**. Flipping to `AllowVerified` is a one-line change once a codec has a recorded production-parity proof.

**An exactness violation and a 17 % regression at the same time.** Exactness broke, and there was no performance gain to trade against it.

### End-to-end wall clock (post-fix, median of 3)

| mode | median ms | vs off |
|---|---|---|
| off | 36285 | — |
| adaptive | 36277 | **-0.02 %** (neutral) |
| forced-sparse | 36316 | +0.08 % |

adaptive is neutral because it now always chooses Sequential. **That is not a performance win.** The honest conclusion of this node is that preserving exactness leaves nothing but neutrality.

> **Measurement noise caveat**: wall clock varied between 34,722 and 46,753 ms across repeats (identical binary, identical dataset), so these numbers are **noise-dominated** and carry roughly ±20 % swing. On repeat measurement the adaptive/off ratio was not directionally consistent. The accurate statement is therefore **"no reproducible gain"**, not "the gain is exactly zero". The exactness side (0 mismatches) was deterministically consistent in every repeat, so it stands independently of this noise.
>
> The pre-fix +17.38 % is likewise a single run, so **the ratio itself should not be treated as a settled figure**. What matters is that an exactness violation occurred in that same run, and the violation reproduces independently of noise, so **the basis for rejection is the exactness side**.

## 6. Future impact

- **The E node is not complete.** E-3B did not prove end-to-end exactness. There is no basis for adopting sparse.
- **Production behaviour is identical to v0.9.4.41.** Default Sequential, bit-identical results.
- **Revisit conditions** — reconsider `AllowVerified` when any of the following holds:
  1. A way to preserve decoder reference state without seek+flush becomes available (for example, packet-level handling that does not rebuild the decoder from a keyframe)
  2. `AVSEEK_FLAG_ANY` solves the HEVC problem without breaking H.264 exactness — E-3A already measured it as making things worse
  3. A codec other than HEVC/H.264 obtains a recorded production-parity proof
  - These figures are invalidated by changes to code, compiler, FFmpeg, dataset or build configuration. Under **no** condition should the E-2A/E-2B 13/14 figure be reused as production exactness evidence: that comparison was self-referential.
- **Methodology lesson**: to prove exactness, the baseline must be the **production path**. Two reimplementations of the same family cannot validate each other, because a shared defect passes. The e2e test always runs an A vs A control alongside.
- `ExactnessPolicy` is process-wide. While it is `RefuseAll`, no `forced-sparse` manipulation can change production results.

## 6-1. E-3C / E-4 handling for Node E closure (user decision)

Based on the current structure where `RefuseAll` makes the sparse production path unreachable:

- **E-3C** is not promoted to a separate roadmap Stage and not migrated to F. It is
  closed within Node E's scope. Only the fact that it may inform F's architecture in
  future is recorded as a note; it is not migrated as a work item.
- **E-4** (production integration + end-to-end validation) is likewise closed within
  Node E's scope. Under `RefuseAll` no "qualitative" path is left to integrate.
  **E-4 must not be read as grounds for reintroducing sparse.**
- The **code state** for E-3C in `src/video_sampling_planner.h` was **not changed** in
  this build. Whether a change is needed is a separate judgement.
