# MediaSimilarityFinder v0.9.4.130 — 매치 세트 완전성 베이스라인 (A/AB 자가치유)

기준선 `0.9.4.129` → 본 빌드 `0.9.4.130`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` 불변 (판정 불변, CTest 등록 수 불변).

## 1. 변경 필요성

- 0.9.4.129 업그레이드 후 실기 로그(`detailed-log-2026-10-19T053207.json`): 자동(AB) 스캔이 `scanned 177887, analyzed 0, unchanged 177887`, 매치 `candidates 0, pairs 0, groups 0` — 유사그룹이 여전히 0.
- 원인: ① 파일 인덱스는 이미 완성되어 이번 스캔이 아무것도 재분석하지 않음(analyzed 0) ② A/AB는 무변경 파일을 재계산하지 않고 **저장된 매치 세트**를 표시하는 설계 ③ 그 저장 세트가 **비어 있음** — 0.9.4.81~0.9.4.128은 라이브 매치를 저장한 적이 없으므로(off-by-one 버그) 이 인덱스의 매치 저장소는 한 번도 채워진 적이 없다.
- 0.9.4.129 수정은 파일이 (재)분석될 때만 발동한다. 전부 무변경인 인덱스에서는 A/AB가 아무것도 계산하지 않으므로 **스스로 회복할 수 없다**. 안정(B) 1회 스캔이 전체 패스로 회복시킨다는 것은 0.9.4.129에서 실측했지만, 업그레이드한 사용자가 그것을 알 방법이 없다.
- engine_version 재검증 게이트는 "저장된 쌍"만 재검증하며(빈 세트에는 무동작), `revalidateMatches`가 빈 세트에도 engine_version을 스탬프하므로 기존 스탬프로는 완전성을 판별할 수 없다.

## 2. 기존 구조

- A/AB 최종 패스: `changedPtr` 필터로 changed에 닿는 쌍만 검증. 무변경 쌍은 저장 세트를 신뢰.
- 완전성(completeness)에 대한 영속 마커가 없음: "이 인덱스의 저장 세트가 현재 엔진에서 전체 커버리지 검증을 마쳤다"는 사실을 DB가 기억하지 않는다.

## 3. 변경 구조

- DB meta에 `match_baseline` 신설(`Database::matchBaseline()`/`setMatchBaseline()`). 값 = 마지막 **전체 커버리지 검증이 완료된** engine 버전. engine_version과 분리한 이유: 그 스탬프는 `revalidateMatches`가 전체 패스 없이도 기록하므로 완전성 증거가 될 수 없다.
- 스캔 시작 시 이 인덱스의 베이스라인이 현재 엔진과 다르거나 없으면, A/AB라도 이번 스캔 1회를 **B 등가 전체 패스**로 수행한다: `changedPtr=nullptr`(전 쌍 검증), 라이브 스트리밍 비활성(중복 작업·중복 방출 방지), 라이브 소유 집계도 비활성. 백엔드 로그에 `matchBaseline=forceFullPass engine=<v> stored=<missing|버전>`를 남긴다.
- 완료(취소/실패 아님) 시 `match_baseline`을 현재 engine 버전으로 스탬프. 취소·실패면 미스탬프 → 다음 스캔이 전체 패스를 반복한다. 스탬프 실패는 메타 전용이며 스캔 결과를 되돌리지 않는다(다음 스캔에서 재시도).
- 엔진 버전이 바뀌면 베이스라인도 자동으로 무효화되어 A/AB의 다음 스캔이 1회 전체 패스로 재수립한다(판정 로직 변경 시 새 로직 기준으로 재발견 — 기존 "저장 쌍 재검증"보다 안전).
- 파일 재분석이 전혀 필요 없다: 후보는 기존 인덱스의 지문에서 나온다(재지문화 0).
- 부수 수정(빌드): `tests/console_benchmark_cli_test.cpp`가 `msf::path_from_utf8`를 쓰면서 `path_utils.h`를 직접 include하지 않아, 0.9.4.126 커밋 이후 이 타깃이 **컴파일되지 않은 채** 세션들의 필터된 빌드 로그 뒤에 숨어 있었다(두 트리의 exe가 10-18 03시 빌드의 스테일 바이너리였고, CTest는 그 스테일 exe를 통과시켰다 — 스테일 exe 32 checks vs 실제 44 checks). 직접 include를 추가해 해소했고, 같은 누락이 다른 테스트에 없음을 전수 확인했다. 이번 빌드부터 실제 44 checks가 실행된다.

## 4. 해결된 상황

- 실기와 동일한 상태 재현(저장 세트 삭제 + 베이스라인 없음 + 전부 무변경 + AB): 수정 전 스캔 `pairs 0` → 수정 후 첫 스캔이 자동으로 전체 패스를 수행해 `pairs=8, groups=8, candidates=8` 표시(18건 실파일 세트 실측), 두 번째 스캔부터는 기존처럼 quick-load(재계산 `verifyCalls=0`)로 복귀. 안정(B) 수동 1회 스캔 없이 해결된다.
- 0.9.4.129의 매치 유실 수정과 합쳐져, 업그레이드 사용자는 **다음 자동(AB) 스캔 1회로 자동 회복**한다.

## 6. 향후 영향 및 한계

- 판정·저장·프로토콜·engine/DB/schema/cache·journal schema 불변. CTest 등록 수 불변(125/126). DB 테이블 추가 없음(meta 키 1개).
- A/AB 사용자는 업그레이드(또는 이후 엔진 버전 상향) 후 **첫 스캔 1회**가 전체 검증으로 수행되어 평소보다 오래 걸린다(파일 재분석은 없음; 대형 데이터셋에서 수 분). 이후 모든 스캔은 기존 속도로 복귀.
- 알려진 남은 공백(이번 범위 밖): 완전 무변경 재스캔에서 좌측 요약/상세 로그의 그룹·쌍 카운터는 그 스캔이 재계산한 것만 세므로 quick-load로 표시된 결과와 숫자가 다르다(그룹 목록 자체는 정상 표시). 카운터 통일은 별도 후보.
