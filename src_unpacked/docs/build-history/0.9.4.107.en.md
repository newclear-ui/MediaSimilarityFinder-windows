# MediaSimilarityFinder v0.9.4.107 — A/AB targeted enumeration (changed-file candidate discovery)

Baseline `0.9.4.106` -> this build `0.9.4.107`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged.

## 1. Why the change was needed

In the 0.9.4.106 user measurements (§7.3), A/AB modes verified only 0-1 pairs in the final pass yet still spent **170.2-185.8 s** in analyze: index 1.2-1.4 s + **enumeration 168.8-184.4 s** (verify 0). With 0-64 changed files the pass still enumerated the whole 177k-file dataset (index seed + crop 4:3/1:1/9:16 passes) and then discarded everything through `included()`. This build removes that fixed cost, recorded as candidate `P-0.9.4.106-A-targeted-enum` (PROPOSED) in the work log.

## 2. Previous structure

- A/AB (`changedFiles != nullptr`) took the same enumeration path as B: parallel image full pass -> video windowed pass -> (when incomplete) seed + sequential crop windowed passes (`consumeWindowed`). `process()` kept only pairs touching a changed file via `included()`.
- The cost scaled with the dataset size (~170-186 s at 177k files) and was independent of the change count.

## 3. New structure

- **`consumeTargeted` added to `ScanPipeline::analyze`** (`src/scan_pipeline.cpp`): when `changedFiles != nullptr`, instead of the full/crop enumeration, **each changed file queries the same indexes with its own hashes**.
  - Images: `imageIdx_` (fingerprint, mirrorFingerprint), `c4_` (crop4x3), `c1_` (crop1x1), `c916_` (crop9x16) — `indexFile` stores **normal crops only** in the crop indexes, so the queries use normal crops only (adding mirror-crop queries would discover pairs the previous pass never found and break parity).
  - Videos: `videoIdx_` (fingerprint, mirrorFingerprint, **all anchors**), `vc4_`/`vc1_`/`vc916_`.
  - Discovered pairs are deduplicated through the existing `dedupCrop`/`seen` set and processed by the **identical `process()`** (bestMatch -> verifyImagePair/temporal -> `included()` filter -> emission). Discovery, filtering and emission are identical, so verdicts do not change.
- **`candidates` semantics change (A/AB only)**: it now counts the pairs this pass actually considered (pairs touching a changed file). Report/telemetry `candidates`/`reduction` shrink for A/AB; B is unchanged.
- **B mode unchanged**: full enumeration, B slices and `analyzeCheckpoint` stay as they were.
- **Parity pinned**: `analyze_mode_test` gains (3b) — A partial (2 changed) candidates=3, AB partial candidates=3, A cold candidates == B, B candidates unchanged. 22 checks total.

## 4. Resolved state

- A/AB's analyze fixed cost moves from dataset size to the changed-file count: index (1.2-1.4 s) + changed-count x hash queries (hundreds of us to ms each). At 177k files with 0-64 changed, expected analyze ~= **2-4 s** (was 170-186 s). B keeps its cost by design (full re-verification).
- Verdicts, groups and stored pairs are unchanged (same `process()` path + parity test).

## 6. Future impact and limits

- engine/DB/schema/cache and `kProtocol` unchanged (performance-only, verdict-neutral).
- `candidates` now means different things per mode (A/AB = changed-touching pairs, B = all candidate pairs) — take care when reading reports/docs.
- AB cold (all files changed) still queries every file (same class as before). Early-skip for "all changed + AB" (where `included()` rejects everything) is a separate candidate (needs the video exception).
- **Future revisit condition**: if the changed count becomes very large (tens of thousands), the query cost could grow — consider a temporary index holding only changed-file hashes or a partition-scan hybrid.
