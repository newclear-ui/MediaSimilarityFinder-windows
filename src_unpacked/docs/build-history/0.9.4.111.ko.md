# MediaSimilarityFinder v0.9.4.111 — G4 IPC backpressure + G6 Job Object/GUI 종료 검증 (프로세스 분리 release gate)

기준선 `0.9.4.110` → 본 빌드 `0.9.4.111`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` 불변.

## 1. 변경 필요성

Active Build Queue 우선순위 2~3의 프로세스 분리 release gate 2건이 `OPENCODE REVIEW REQUIRED / DEFECT NOT CONFIRMED(미검증)` 상태였다.

- **G4 (IPC backpressure)**: `send/flush` 동기 경로와 유계 outgoing queue, 느린 소비자 스트레스에서 결과 무손실·coalescing·메모리 상한의 증거가 없었다.
- **G6 (Job Object / GUI 종료)**: Win32 API 반환값 처리 검토와 GUI 부모 종료 후 Backend PID 종료 E2E 증거가 없었다.

## 2. 기존 구조와 검토 결과

**G4 (결함 미확정 — 설계 검토 + 스트레스 검증 필요)**
- GUI→Backend 명령은 소수·소형이고 GUI pending 상한(0.9.4.105 D)으로 요청량이 유계다. `QProcess::write` 버퍼는 이론상 무계지만 생산량이 유계라 실질 위험 없음.
- Backend→GUI MATCHES는 500개 단위 청크로 무손실(드롭 없음), 진행 이벤트는 도착 기준 최신 우선(coalescing)이다. 느린 소비자에서는 파이프가 차서 백엔드 이벤트 스레드가 `flush()`에서 대기하고 이벤트 큐가 쌓이지만, 총량은 스캔 산출물 크기(=결과 자체)로 유계다.
- 감독자의 stdout 파서는 줄 상한(64 MiB) + runaway 가드로 유계이며, 시퀀스 갭 로그가 유실을 검출한다.
- **결함 미확정**: 위 설계가 실제로 무손실·무교착·유계임을 보이는 증거가 없었으므로 스트레스 테스트를 추가한다.

**G6 (실결함 2건 확인)**
- **실결함 1 — 종료 지연 3초 고정**: `BackendSupervisor::shutdown()`이 `proc_->state()` 폴링으로 종료를 기다렸다. Qt는 `QWinEventNotifier`의 `WinEventAct`를 **이벤트 루프 디스패치에서만** 처리하므로(qwineventnotifier.cpp), 이벤트 루프 없이 도는 폴링 루프는 종료를 절대 관측하지 못한다. 결과: 백엔드가 50 ms 만에 종료해도 **매 앱 종료마다 `shutdownWaitMs`(기본 3 s) 전액을 소모**한다. 실측(수정 전): `shutdown elapsed=3049 ms`.
- **실결함 2 — Win32 반환값 3곳 무시**: `assignJobObject()`에서 `SetInformationJobObject`(실패 시 KILL_ON_JOB_CLOSE 미설정), `OpenProcess`, `AssignProcessToJobObject`의 반환값을 검사하지 않았다. 실패해도 조용히 넘어가 고아 보호가 무력화될 수 있는데 로그 증거조차 없었다. (CreateJobObjectW 실패도 무로그.)
- 할당 전 창(window): `QProcess::started` 직후 할당까지의 미소 구간은 백엔드의 stdin-EOF self-exit가 커버한다(문서화).

## 3. 변경 구조

- **`BackendSupervisor::shutdown()`** (gui/backend_supervisor.cpp): 폴링 대신 `proc_->disconnect(this)` 후 `waitForFinished(shutdownWaitMs)`로 **프로세스 핸들을 직접 대기**한다. disconnect는 블로킹 드레인이 readyRead를 동기 발화해 GUI 핸들러로 재진입하는 것을 막는다("이벤트 펌핑 없음" 보장 유지). 타임아웃 시에만 `terminate()`, 중복 호출은 즉시 반환(이중 대기 방지). Job Object KILL_ON_JOB_CLOSE는 최종 백스톱으로 유지.
- **`assignJobObject()`**: `CreateJobObjectW` / `SetInformationJobObject` / `OpenProcess` / `AssignProcessToJobObject` 전부 반환값 검사 + `GetLastError` 로그. `PROCESS_ALL_ACCESS` → `PROCESS_SET_QUOTA|PROCESS_TERMINATE|PROCESS_QUERY_LIMITED_INFORMATION`(문서화된 권한). 실패 시 "고아 보호 = 채널-손실 self-exit만" 명시 로그. 테스트 전용 `SupervisorOptions::jobObjectEnabled`(기본 true) 추가.
- **`src/backend_main.cpp`**: 테스트 시임 `MSF_TEST_BACKEND_WEDGE` — stdin 리더는 시작하되 이벤트 루프에 진입하지 않아 SHUTDOWN·stdin-EOF self-exit이 모두 막힌다(Job Object만이 죽일 수 있는 상태; G6 E2E 대조군용).
- **`tests/backend_e2e_test.cpp`** (checks 37, 데이터셋 30→300 그룹):
  - Test 4 (G4): 스캔 중 3초 소비자 정지(이벤트 펌프 중단 → 파이프 충만 → 백엔드 flush 대기) 후 드레인 — 시퀀스 갭 0, 매치 600건 전달, 그룹 수 동일, 무교착, RSS 상한.
  - Test 5 (G6): 정상 종료가 유계이면서 신속한지 — `delete supervisor` 시간 실측(수정 전 3049 ms FAIL 재현 → 수정 후 6 ms PASS), 종료 후 PID 소멸 확인.
  - Test 6 (G6): 부모(GUI) 급사 E2E — 헬퍼 프로세스가 웨지 백엔드를 띄우고 PID를 보고하면 부모가 `TerminateProcess`(크래시 시뮬레이션). Job이 백엔드를 회수하는지 확인 + `--no-job` 대조군은 고아 생존(→ Job이 실제 사망 원인임을 입증) 후 명시 정리.

## 4. 해결된 상황

- **G4**: 느린 소비자 스트레스에서 무손실(갭 0, 600건 전달)·무교착·유계(수정 전후 RSS 20/20/21 MB) 입증. 설계 검토 결론: GUI→Backend는 pending 상한으로 유계, Backend→GUI는 무손실이며 백로그는 스캔 산출물 크기로 유계.
- **G6**: 앱 종료 체감 지연 제거(3049 ms → 6 ms). Win32 실패 시 로그로 증거 확보(조용한 무력화 금지). 부모 급사 시 웨지 백엔드도 Job이 확실히 회수함을 E2E로 증명(대조군으로 Job의 필수성 입증).

## 6. 향후 영향 및 한계

- 판정·저장·프로토콜(`kProtocol`)·engine/DB/schema/cache 불변. `--backend` 외 인터페이스 변화 없음.
- **한계(문서화)**: 소비자가 영구히 정지하면 백엔드 이벤트 큐 백로그는 스캔 산출물 크기까지 증가한다(무손실 설계의 내재 비용). GUI 모달은 중첩 이벤트 루프라 QProcess 드레인이 계속되므로 실사용 경로는 없음 — **재검토 조건**: 이벤트 루프를 멈추는 새 소비 경로(비모달 동기 블로킹 등)가 생기면 coalescing/상한 도입을 검토한다.
- Job 할당 실패 시 고아 보호는 stdin-EOF self-exit로 강등되며 로그로 남는다. `MSF_TEST_BACKEND_WEDGE`는 테스트 전용(프로덕션 경로 무영향).
