# 0.9.2.31 — 대용량 Match 결과 스트리밍/메모리 제한

## 중요 변경
실제 유사 매치가 수십만~수백만 건 발생할 때 `SearchReport.matches`가 전체 결과를 메모리에 유지하는 문제를 완화했다.

## 필요성
0.9.2.29에서 candidate pair 임시 벡터를 제거하고 0.9.2.30에서 중복 Match 보관을 줄였지만, 최종 Match 자체가 매우 많으면 결과 벡터가 메모리를 지배할 수 있었다.

## 기존 구조
`ScanPipeline` → `MediaSearchEngine::scan()` → `SearchReport.matches` 전체 materialization.

## 새 구조
`ScanPipeline` → `ScanControl::onMatch` 즉시 전달 → 필요할 때만 `SearchReport.matches` 보관.

`retainMatches=false`로 전체 결과의 report 보관을 끌 수 있으며, `maxRetainedMatches`로 report에 보관하는 최대 건수를 제한할 수 있다. 스트리밍 콜백은 제한과 무관하게 모든 Match를 받을 수 있다.

## 설계 이유
기존 API와 기본 동작은 유지하면서 GUI/Monitor가 향후 페이지 단위 저장·표시 또는 DB 기반 결과 소비로 확장할 수 있는 경계를 먼저 마련한다.

## 해결 상황
대량 Match 결과를 반드시 `SearchReport` 벡터에 전부 materialize하지 않아도 된다. 기존 호출자는 아무 설정을 하지 않으면 이전과 동일하게 전체 결과를 받는다.
