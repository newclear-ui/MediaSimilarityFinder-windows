# MediaSimilarityFinder v0.9.4.109 — View-mode overlap recurrence fix (warm-cache icon re-apply)

Baseline `0.9.4.108` -> this build `0.9.4.109`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged.

## 1. Why the change was needed

User report: switching the similar-groups view mode (List/Details/Tiles -> Extra Large/Large) makes images overlap each other or overlap another view mode. A recurrence of the 0.9.4.66 overlap that was never fully closed and re-opened after P3.

## 2. Previous structure (0.9.4.66 -> P3)

- The 0.9.4.66 fix's core: `thumbCatchUpVisible()` actually **replaced icons** (cache hit or fresh decode via `setIcon`) and forced `doItemsLayout()` when anything changed. Under `uniformItemSizes`, a bare icon swap runs no layout pass, so this path prevented the small-cell/big-art overlap (the 0.9.4.66 root cause).
- **P3 (0.9.4.69-.71) async migration**: GUI decoding moved to the backend, and `thumbCatchUpVisible()` became a "request pump" — it **ignores `fileThumb()`'s return value** and icon application moved to `onThumbReady` (backend arrivals) only.
- **The missed part**: on a memory-cache hit, `fileThumb()` returns the stored icon and creates **no backend request**. A cache-hit item therefore never receives an arrival and keeps its old-size pixmap. After a mode switch, `groupViewChanged`'s `doItemsLayout()` recomputes only the cells, so a warm-cache round trip (XL -> L -> XL) leaves the item holding the 128px pixmap while the cells are recomputed for 256 — the overlap reappears (partially, since only uncached items heal via arrivals).
- Why the probe missed it: `view_mode_probe`'s catchup scenarios call `testDropThumbCache()` first, so they only exercised the all-miss -> arrival -> heal path. The warm-cache (cache-hit) path had no test.

## 3. New structure

- **`thumbCatchUpVisible()`** (gui/mainwindow.cpp): cache-hit items are applied in place.
  - Look up `thumbCache_` directly with the current `iconSize` key (`path|WxH`); on a hit, `setIcon` when `item->icon().cacheKey()` differs (a pure memory write — no decode, request or rebuild).
  - Misses keep calling `fileThumb()` **only to request** (the returned placeholder is deliberately not applied, so a real icon is never clobbered by a placeholder).
  - When anything changed, the same **coalesced layout pass** arrivals use is scheduled (`thumbLayoutPending_` + `singleShot(0) flushThumbLayout`) — the scroll-gate contract (defer/retry during gestures) is unchanged.
- **`groupViewChanged()`**: after the delegate/size swap and the existing `doItemsLayout()`, it calls `thumbCatchUpVisible()` — warm-cache icons re-apply immediately on a mode switch and misses are requested (no next-tick wait).
- **Test**: `ui_scroll_regression_test` phase 21 (warm-cache round trip) + hook `testCachedThumb(path,size)`. It warms XL(256) and L(128) through the real arrival path, then asserts the XL->L->XL round trip restores the item icon to the **exact cached icon (cacheKey)**. Pre-fix `XL icon restored=0` **FAIL** reproduced; post-fix PASS.

## 4. Resolved state

- Every warm-cache view switch (List/Details/Tiles <-> XL/L/M/S) restores the item icons to the current size immediately, and a layout pass follows the swaps, so cells and art sizes match — no overlap.
- The 0.9.4.61 scroll contract (catch-up never rebuilds, scroll untouched) holds: the fix only swaps icons; layout stays on the coalesced/gated path.

## 6. Future impact and limits

- Display-only: verdicts, storage, protocol and engine/DB/schema/cache unchanged. No added decodes (cache-hit re-apply only).
- Off-viewport items behave as before: catch-up applies them when they scroll into view.
- This class of "async migration dropped a synchronous guarantee" is handled by this pattern (apply cache hits immediately + coalesced layout). New surfaces must explicitly check the same contract.
