# MediaSimilarityFinder v0.9.4.118 — Scan list churn removed (append-first reuse + deferred large appends)

Baseline `0.9.4.117` -> this build `0.9.4.118`.
CPU CTest **123/123**, GPU CTest **124/124**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged.

## 1. Why it was needed

Field feedback (0.9.4.117): the Load progressive fill, faster thumbnails, and the group-275 resolution were confirmed, but **the list behavior during a scan was reported as "a few images fast in the first scroll -> then very slowly one by one -> then suddenly a big burst"** (user session log, 2026-10-17 05:03-05:16). Log analysis showed the GUI performing **the same 9,057-row full rebuild repeatedly**:

- Right after Load, 05:04:46: `groupFill rows=9057 16.2s`
- Scan start, 05:08:38: `groupFill rows=9057 20.5s` - `beginScan` cleared the pane state and then called `refreshGroupList()` (append=false)
- Scan end, 05:14:45: `groupFill rows=9057 19.0s`
- A later apply, 05:16:23: `resultsApply rows=0 groups=9057` -> `groupFill rows=9057 16.8s`

The group/file lists had not changed, yet every row was re-created and the thumbnail cache was dropped (forcing re-requests). The user's "big burst" was these repeated rebuilds (the completion burst of the 100-rows-per-turn chunks); the "pair-verification mode difference" was not the cause (verdict/engine logic is unrelated).

## 2. Previous structure and defects

1. The 0.9.4.91 append reuse (`fillPair(append)`, prefix guard) was only used for partial arrivals during a scan (`refreshStreaming`). The scan **start (`beginScan`) / end (`scanFinished`) / result apply (`onResults`) / abort (`scanFailed`)** paths all called `refreshGroupList()` (append=false), so they **rebuilt every row even when the group list was unchanged**.
2. The append path filled large additions synchronously too - the 0.9.4.117 deferred fill (`GroupFillJob`, above 800 rows) covered only the full-rebuild path.

## 3. New structure

- **(1) Append-first on the four scan paths**: `beginScan`, `scanFinished`, `onResults`, and `scanFailed` now use `refreshGroupList(true)`. When the shown list is a prefix of the current list only the new rows are appended (an identical list is a **no-op**); a merge/order change falls back to the automatic full rebuild (the 0.9.4.91 contract is unchanged).
- **(2) Deferred large appends (`kDeferAppendMin=300`)**: an append of more than 300 new rows is also deferred via `GroupFillJob` (`append=true`). The pane is not cleared; 100 rows are added per event-loop turn, completion does resize/`doItemsLayout`/catch-up and logs `groupFill done rows=N ms=M append`. The generation counter (`fillGen_`) and the append-arriving-mid-flight demotion rule are the same as 0.9.4.117.
- **(3) Regression probe extended (`group_fill_probe`)**: Scenario A - a repeat apply of identical data keeps the existing rows (pre-fix the synchronous clear destroyed `grid->item(0)`). Scenario B - a fresh window (empty pane) returns promptly on the first apply (without append deferral it fills 9,055 rows synchronously). **FAIL-first reproductions (2 cycles)**: A `rowsKept=0`, B `applyMs=15,087/15,641 ms`.

## 4. What is fixed

- The 9k-row churn at scan start/end/apply is gone for unchanged lists. Repeat apply `applyMs=101 ms rowsKept=1` (previously `rowsKept=0`), fresh window `applyMs=77 ms` (15,641 ms without append deferral). The 9,055-row deferred fill still proceeds at 100 rows/turn (~17 s, 91 ticks) exactly as in 0.9.4.117.
- The field's "slowly one by one, then a big burst" is removed at its dominant cause (the repeated rebuilds). The one-by-one streaming of genuinely new groups discovered during a scan (engine pace) is unchanged by design.

## 6. Future impact and limits

- Display only: verdicts/storage/protocol/engine/DB/schema/cache unchanged.
- At scan start the pane is no longer reset and stays as-is until the scan ends (a rebuild happens only when the group composition actually changed).
- The total deferred-fill time (9,055 rows ~ 17 s, ~2 ms/row = tree+grid widgets) remains the 0.9.4.117 limit - same revisit conditions (lazy hidden-pane fill, model/view separation, persistent index).
- `kDeferAppendMin=300`: small appends (tests, ordinary folders) keep the previous synchronous behavior.
