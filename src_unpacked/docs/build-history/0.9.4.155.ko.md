# MediaSimilarityFinder v0.9.4.155 — decodedFrames 정직화 (실제 디코드 수 계측)

기준선 `0.9.4.154` → 본 빌드 `0.9.4.155`.
CPU CTest **128/128**, GPU CTest **129/129** (신규 CTest 등록 없음; 기존 `video_real_test`에 회귀 단언 1건 추가).
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` / `kProtocol 1` 불변 (판정·스키마·버전 상향 없음).

## 1. 변경 필요성

- `VideoBuildStats.decodedFrames` 주석은 "실제 디코드된 프레임 수"라고 설명하지만, `VideoFingerprintEngine::build()`는 이 값을 `frames32.size()`(유지된 샘플 수)로 설정했다.
- `VideoDecoder::framesAt()`은 선택된 샘플만 결과 배열에 저장하므로, 현재 값으로는 디코더가 중간에 실제로 몇 프레임을 처리했는지 알 수 없다.
- 이 상태에서는 GPU 디코드가 CPU 작업을 얼마나 대체했는지, 프레임 다운로드를 얼마나 줄였는지 정확하게 측정할 수 없다.

## 2. 기존 구조

- 디코드 카운트는 ExactSparse 경로에만 있었다(`SparseSeekStats.decoded/emitted` 분리). 정식 sequential sweep에는 카운트가 없었다.
- `video_decode_planner_probe`가 이 간극을 문서로 기록했다("decodedFrames는 frames32.size()이며 FFmpeg 실제 생산량이 아니다").

## 3. 변경 구조

- `VideoDecoder::framesAt()`/`framesAt96Plus32()`에 선택적 `decodedOut` 추가: `avcodec_receive_frame` 성공마다 계수(선택·폐기 불문). no-FFmpeg 폴백은 성공 push마다 1 계수. 32px 유도는 디코딩이 없으므로 96px sweep 값을 그대로 전달.
- `VideoFingerprintEngine::build()`: sequential 경로는 sweep 계수, sparse 경로는 `SparseSeekStats.decoded`(동일 receive_frame 기준)를 사용. `sampledFrames`(플랜 타깃 수)·`keptFrames`(최종 해시 수)는 불변.
- 회귀: `video_real_test`에 `decodedFrames >= keptFrames && decodedFrames >= sampledFrames` 단언. 실측 8s 테스트 영상: kept=8, decoded=80, sampled=9 (CPU·GPU 양 트리 동일, GPU 경로 `gpuUsed=yes`).
- 주석 정합: `VideoBuildStats` 주석에 중간 폐기 프레임 포함을 명시, probe의 간극 기록을 "0.9.4.155에서 해소"로 갱신.

## 4. 해결된 상황

- `decodedFrames`는 이제 실제 디코드 수를 보고한다. telemetry/benchmark JSON 형태 불변(값만 정직해짐).
- GPU 디코드 도입 시 대체율·다운로드 절감 측정의 분모가 확보됐다.
