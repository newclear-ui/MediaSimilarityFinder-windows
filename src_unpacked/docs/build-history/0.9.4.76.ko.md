# MediaSimilarityFinder v0.9.4.76 — 크래시 프론티어 확정 (batch 진입 checkpoint)

기준선 `0.9.4.75` → 본 빌드 `0.9.4.76`.
CPU CTest **118/118**, GPU CTest **119/119**.
`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.4` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — 전부 불변. 검색 판정 의미 변경 없음. 스키마 변경 없음.

## 1. 변경 필요성

- 실측 Backend 크래시(`0xC0000005`) 2건은 모두 “분석 완료 0건” 상태에서 죽었다.
  heartbeat의 `lastPath`가 끝까지 비었고, 복사본 DB 조회에서도
  `fingerprint=0` 행이 0건이었다. 즉 poison 배치의 위치가 DB에 남지 않았다.
- 원인은 admission 스켈레톤 행이 스캔 트랜잭션 안에만 있었기 때문이다.
  기존 checkpoint는 500 analyzed / 1000 scanned 단위라, 첫 배치를 마치기
  전의 죽음은 롤백으로 프론티어를 통째로 지웠다.
- 사용자 요청대로 “스캔 시점에 더미 행을 먼저 만들고 인덱싱이 끝나면 채운다”는
  방향을, 트랜잭션 경계까지 포함해 완성해야 했다.

## 2. 기존 구조

- `processOne()`은 admission 시점에 fingerprint 0 스켈레톤 행을 upsert했다
  (`src/media_search_engine.cpp:669-677`).
- 다음 스캔의 `pendingAnalysis` 규칙(fingerprint 0 + 미실패 → 재분석)은
  이미 있었으나 (`:658`), 커밋되지 않은 스켈레톤에는 닿지 않았다.
- `processImageBatch` / `processVideoRange`는 작업 시작 전에 아무것도
  확정하지 않고 바로 병렬 디코드/해시로 들어갔다.

## 3. 변경 구조

- `processImageBatch` 진입 시점에 `checkpoint()`를 먼저 수행한다. admission
  스켈레톤이 그 배치 작업 전에 커밋되므로, 배치 중 kill/AV가 나도
  admitted-but-unanalyzed 프론티어가 남는다.
- `processVideoRange` 진입 시점에도 같은 checkpoint를 둔다 (실패 시
  `VideoRangeResult::Failed`).
- 테스트용 `MSF_TEST_THROW_BATCH` seam을 추가했다. 진입 checkpoint **이후**에
  던지므로, unwind across durability를 결정적으로 검증한다. 제품 코드는 이
  변수를 절대 설정하지 않는다 (`MSF_TEST_THROW_WALKER`와 같은 패턴).
- 판정·매칭·스캔 의미는 그대로다. checkpoint는 기존에도 쓰던 commit+BEGIN
  이며, 배치당 1회 추가되는 수준이라 빈번한 fsync가 아니다.

## 4. 해결된 상황

- 배치 중 죽어도 admission 프론티어(fingerprint 0, 미실패)가 커밋되어 남는다.
- 다음 스캔은 `pendingAnalysis` 규칙으로 그 파일들을 재분석한다 (스킵하지 않음).
- DB에는 원본 전체 경로가 그대로 들어간다 (`files.path` PRIMARY KEY,
  `matches` 좌우 경로, `thumbs` 경로). 더미 행도 같은 경로 키를 쓰므로
  완료 시 같은 행이 채워진다.

## 6. 향후 영향

- 다음 `0xC0000005`급 충돌이 나면 DB에 fingerprint-0 프론티어가 남아
  poison 배치 후보를 경로 목록으로 직접 좁힐 수 있다.
- poison 파일 특정 절차(LocalDumps + PDB)와 병행하면 원인 확정이 빨라진다.
- 스키마·엔진·DB 버전을 건드리지 않았으므로 기존 인덱스와 호환된다.
