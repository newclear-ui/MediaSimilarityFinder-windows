# MediaSimilarityFinder v0.9.4.105 — Thumbnail-storm root fix + detail ping-pong fix + immediate index reflection + background file I/O

Baseline `0.9.4.104` -> this build `0.9.4.105`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged.

## 1. Why the change was needed

User report (0.9.4.104 field): preview loss after delete/move persists even after the batched build. "Loading time slightly reduced, same problem" -> **fix the root cause** plus finish every deferred item (D/E/F/C/detail-text).

Root-cause analysis (structure established in the 0.9.4.104 report):

1. **Thumbnail request storm (D)**: `prunePaths()` rebuilds the whole middle list, and every rebuilt row (`addGroupItems`) calls `fileThumb()`, firing one backend request per group (thousands). The pending-map cap 2000 used `erase(begin())`, which dropped the tracking row of an in-flight request; the late answer arrived as "unknown" and was discarded, leaving the cell a permanent placeholder. Combined with `thumbCache_` (3000) this produces "only reference files survive" (the middle list caches the reference thumbnail under the same size key, so the right pane hits it).
2. **Detail-text blanking (deferred item)**: `requestFileMeta` deduped only while in flight. A duration-less answer (every image file) left the duration unknown, so `refreshDetail` asked **again** -> answer -> rebuild -> ask again: an endless ping-pong. Each round deleted and recreated the form rows (+ re-parsed EXIF), so the text appeared and vanished. 0.9.4.102's `activate()` (geometry commit) does not address this separate cause.
3. **Index not updated (F)**: after delete/move the stored index (files rows, match pairs, thumbs rows) stayed until the next scan, so a later Load/report showed ghost rows/pairs.
4. **GUI blocking (C)**: file operations ran on the GUI thread, so large checked-set recycle/move froze the window with no progress (0.9.4.104 deferral C).

## 2. Previous structure

- `fileThumb()` on every cache miss did (dedup loop -> cap handling -> request). On cap overflow it **erased the oldest entry** = lost tracking of an in-flight request.
- `addGroupItems()` called `fileThumb(rep, grid->iconSize())` for every row, for both full rebuilds and appends.
- `onBackendConnection(false)` changed UI state only; in-flight thumbnail/meta tracking survived into the reconnect as ghost ids.
- `requestFileMeta()` deduped against `fileMetaPending_` (in-flight) only; nothing prevented a re-request after the answer. `onFileMetaReady` rebuilt the detail on any ok answer.
- `BackendSession` had no index-row deletion path (only `loadIndex`/`startScan`), and `Database` had no multi-path delete API.
- `deleteSelected`/`moveSelected` ran the batch shell call / per-file loop synchronously on the GUI thread.

## 3. New structure

- **(D) Storm root fix** (`gui/mainwindow.cpp`, `gui/mainwindow.h`):
  - `thumbBulkFill_` flag: during a bulk fill (`addGroupItems`) `fileThumb` serves cache hits/placeholders only and never requests. When the fill completes, `fillPair` (both append and full rebuild) calls `thumbCatchUpVisible()` so **only visible rows** are requested; the idle-tick pump stays as before.
  - Pending cap: on overflow, **refuse the new request** (erase-oldest removed). A refused cell is still a cache miss, so the next visible pump retries once the backlog drains; the unknown-drop path no longer exists.
  - `onBackendConnection(false)`: clears `thumbPendingReq_`/`fileMetaPending_`/`fileMetaAsked_`. Answers after a restart cannot match stale ids, and the visible pump re-requests once READY returns.
- **(detail-text) metadata ping-pong removed**:
  - `fileMetaAsked_` (one request per path) + `fileMetaRequestCount_` (instrumentation); cleared with `resCache_` at scan/load start.
  - `onFileMetaReady` rebuilds the detail **only when displayed content actually changed** (new dimensions and/or new duration). List rows keep their in-place refresh (`refreshFileMetaRow`).
- **(E) wider backend duplicate absorption**: `ThumbnailStore::kMemMax` 256 -> 1024. The disk table is authoritative; the memory LRU absorbs repeat requests (middle representative, right pane, preview) before SQLite. Worst case ~40 MB.
- **(F) immediate index reflection**: new `Database::forget(paths)` (files + matches both sides + thumbs, one transaction, rollback on failure). IPC `FORGET_PATHS` + `BackendSession::forgetPaths` (refused while a scan owns the index; the next scan reconciles) + supervisor/loopback wiring. The GUI passes only paths that actually left the filesystem, after delete/move/rename/cut-paste. The shared `prunePaths` path (e.g. the ignore list) is deliberately excluded to avoid deleting rows for ignored files.
- **(C) background file I/O + progress**: recycle runs the batch `SHFileOperationW` on a worker thread (`CoInitializeEx(APARTMENTTHREADED)` + COM cleanup); move runs the per-file rename/copy loop (cross-volume fallback included) on a worker thread with between-file cancel. A shared dialog helper (`newFileOpDialog`: indeterminate when total<=0, optional cancel button). Only the actually-moved set returns to the GUI thread, which runs `prunePaths` + `forgetPaths` + timing logs. The move log gains `cancelled=`.
- **Regression tests**: `ui_scroll_regression_test` phase 17 (a bulk rebuild must not request every row: `pending=2 items=120`, visible rows still fill) + phase 18 (metadata requests settle after selection: `m1=240 m2=240`, detail text stable). `database_test` forget section (files/matches/thumbs removed, unrelated rows kept, empty input no-op). New hooks `testRefreshGroupList`/`testFileMetaRequestCount`.

## 4. Resolved state

- One full rebuild now costs visible-row requests (tens) instead of one per row (thousands), and the pending cap can no longer destroy in-flight tracking (refuse mode), so late answers are never lost.
- Selecting an image costs exactly one metadata request plus one display refresh (endless rebuild gone); the detail text is stable.
- Delete/move/rename immediately drop file + pair + thumbnail rows from the index, so a later Load/report matches the filesystem (operations during a scan recover on the next scan).
- The GUI stays responsive during large recycle/move with visible progress (indeterminate/determinate bar + cancel).

## 6. Future impact and limits

- `kProtocol` unchanged (new `FORGET_PATHS` command). The portable ships GUI/backend at the same version, so mixing cannot occur.
- engine/DB/schema/cache unchanged; `forget()` deletes rows of existing tables, not a schema change.
- FORGET_PATHS is refused while a scan owns the index. A moved file's **new location** indexes on the next scan (immediate re-analysis is out of scope by cost).
- A background file operation overlapping app exit can be cut short (no worse than the previous blocking behavior; the worker dies with the process).
- The E LRU increase costs at most ~40 MB (1024 x average JPEG).
- **Future revisit condition**: if field logs still show `rebuildMs` dominating, move to true per-row incremental updates; if `recycleMs` keeps dominating, switch to `IFileOperation`+progress. If detail blanking reappears via another path, introduce a state machine for request tracking.
