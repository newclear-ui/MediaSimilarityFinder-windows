# MediaSimilarityFinder v0.9.4.27 — D1 File Open / WIC Factory 원인 계측

Status: **PRE-REGISTERED** (D1 코드 변경 전에 커밋된다)

D1 은 **원인 계측 빌드**다. "factory 를 재사용하자"가 아니다. "file open 과
WIC factory 생성이 왜 비싼지 증명하는 단계"다.

---

## 1. 변경 필요성

D9d 가 decode 영역을 분해하고 좁고 미해결인 질문을 남겼다.

```text
decode 4.4654 ms/call
  open     2.7749 ms  62.15 %
  factory  1.2230 ms  27.39 %
  copy     0.2300 ms   5.15 %   (실제 압축 해제)
  나머지               1.20 %
```

`open + factory` 는 decode 의 **89.55 %**, 전체 verify 시간의 **84.93 %** 다
(103,539.7 / 115,628.4, 103,539.7 / 121,906.2). D9d 문서에 적힌 84.9 % 는
정확함이 확인되었다. D9d 문서는 89.54 % 도 쓰는데 이는 89.5452 % 의 절삭값이며,
D1 은 반올림한 89.55 % 로 기록한다.

두 질문이 남았고 둘 다 코드를 읽어서는 답할 수 없다.

- **A.** 2.7749 ms 의 `open` 은 내부 어디에서 발생하는가?
- **B.** `CLSID_WICImagingFactory2` 는 실제로 성공하는가, 아니면 매번 실패한
  시도와 fallback 을 함께 치르고 있는가?

B 는 이 프로젝트가 가장 강하게 물어야 할 질문이다. 소스는 Factory2 를 시도하고
실패 시 fallback 한다. fallback 이 보편적이라면 측정된 1.2230 ms 는 "factory
생성 1회"가 아니라 **COM 활성화 2회** 이고, 그 첫 번째는 매번 순수한 낭비다.
이는 "factory 가 느리다"는 것과 **다른** 최적화 대상이며, 둘을 혼동하면 안 된다.

## 3. 계측 전에 확정한 소스 사실

`src/image_decoder.cpp` 에서 읽은 것이며 이름에서 추론한 것이 아니다.

1. `CLSID_WICImagingFactory2` 를 시도하고 실패 시
   `CLSID_WICImagingFactory` 로 fallback 한다. **세 곳**:
   `decodeWicFile`(109행), `decodeWicFileAspect`(186행),
   `decodeWicFileAspectColor`(243행). fallback HRESULT 는 현재 버려지므로
   **이 프로젝트는 이것이 실제로 발생하는지 모른다.**
2. `open` 은 단일 호출이다: `factory->CreateDecoderFromFilename(...)`.
   파일 안에 `CreateStream` / `CreateDecoderFromStream` 가 **전혀 없다.** 즉
   WIC 이 파일 open, 형식 탐지, decoder 생성을 하나의 불투명한 호출 안에서 한다.
3. `decode` 와 `decodePreserveAspect` 는 각각 자기 factory 와 자기 decoder 를
   독립적으로 만들므로, cache miss 1건은 둘 다 두 번씩 지불한다.
4. `decodeColorAspect` 는 GUI preview 경로이며 D9d 와 동일하게 계측하지 않는다
   (fingerprint 경로가 아니다).

## 4. 주요 대상 — file open 내부

`CreateDecoderFromFilename` 은 WIC 사용 방식을 바꾸지 않고는 분해할 수 없고,
D1 은 그것을 금지한다. 따라서 변경 없이 측정 가능한 것을 측정한다.

```text
openTotalMs                 기존 D9d 버킷
openHrFailCount             실패 HRESULT 를 돌려주는 횟수
openHrFirstFailCode         진단용, 처음 관측한 실패 코드
osFileOpenProbeMs           참조 측정: 같은 path 에 대한 단순
                            CreateFileW + CloseHandle, open 버킷 바깥에서 계측
```

`osFileOpenProbeMs` 는 **decode 경로의 일부가 아닌 참조 측정**이다. 목적은
"파일을 여는 OS 비용"과 "WIC 의 decoder 생성 및 형식 탐지"를 분리하는 것으로,
불투명한 단일 호출이 감추고 있는 부분이다. `openTotalMs` 에 포함하지 않고
별도로 보고하며, 둘의 차이가 `open` 의 WIC 고유 부분이다.

이 probe 는 추가적 성격이다. 핸들을 열고 즉시 닫는다. decode 경로, 이미지
바이트, 어떤 결과도 바꾸지 않으며, WIC 사용을 다시 쓰지 않고서는 질문 A 에
답할 수 있는 유일한 방법이다.

## 5. 보조 대상 — WIC factory 와 Factory2 fallback

질문 B 이며, 시간이 아니라 **카운트로** 답한다.

```text
factory2Attempts       CoCreateInstance(CLSID_WICImagingFactory2) 호출
factory2Successes      성공 HRESULT 를 반환한 것
factory2Fallbacks      실패하여 fallback 한 것
factory2FirstFailHr    관측된 첫 실패 HRESULT (없으면 0)
factoryFallbackType    실제로 쓰인 factory
factory2Ms             Factory2 시도 시간
factoryFallbackMs      fallback 시도 시간
factoryTotalMs         factory2Ms + factoryFallbackMs (기존 D9d factoryMs)
```

`factory2Ms` 와 `factoryFallbackMs` 는 exclusive 이며 합쳐서 `factoryMs` 를
재구성하므로 기존 D9d 수치와 비교 가능하다.

HRESULT 는 원시 값으로 기록하고 기호 이름으로 해독해, 단순히 "실패했는가"가
아니라 **"왜 실패했는가"** 까지 진단 가능하게 한다.

## 6. Scope

timer, counter, HRESULT 로깅/집계, 단계 counter, profiling telemetry,
instrumentation 을 검증하는 test. D9d 의 `DecodeTelemetry` 와 analyze telemetry
는 **재사용·확장**하며, 두 번째 telemetry 체계를 만들지 않는다.

`kBenchmarkSchemaVersion` 은 **9 유지**다. D9d 가 스키마가 additive-read 임을
테스트로 확정했고(`benchmark_schema_test` 29 checks), 유일한 구조화 reader 는
GUI 의 `QJsonDocument` key-lookup 경로다. D1 은 같은 종류의 필드를 추가하며
동일 테스트를 다시 실행한다.

## 7. Non-goals

지시에 따라 D1 에서 하지 않는다.

```text
file open 최적화
factory 재사용, static/thread_local/pool/singleton factory
decoder 재사용
stream 재사용
중복 decode 제거 (12,949 x 2 구조 유지)
Factory2 강제 사용
fallback 제거
EXIF 제거, Fant 변경, format conversion 변경, copy 제거
cache 변경, mutex 변경
frame_ssim 변경
candidate, threshold, grouping, verdict 변경
```

12,949 x 2 중복 decode 는 실제 후보이지만 **여기서 다루지 않는다.** D1 은 먼저
`decode` 와 `decodePreserveAspect` 를 별도로 측정해 그 중복의 크기를 알아낸다.

## 8. Factory2 / Fallback 가설

반증될 수 있게 서술하며 **가정하지 않는다.**

- `factory2Successes` 가 높고 `factory2Fallbacks` 가 거의 0 이면 fallback 은
  무관하며, 올바른 다음 질문은 factory 생성을 싸게 만드는 것(재사용)이지
  낭비된 시도를 없애는 것이 아니다.
- `factory2Fallbacks` 가 100 % 이면 측정된 1.2230 ms 는 COM 활성화 2회이며
  첫 번째는 매 decode 마다 낭비다. 이는 "COM 이 느리다"와 **구별되는** 구조적
  문제다.
- 부분 비율 자체가 발견이며 그대로 보고한다.

새로운 외부 의존성을 추가하지 않고, Factory2 를 강제하지 않는다.

## 9. 정확성 위험

instrumentation 은 어떤 결과도 바꾸지 않아야 한다. 전부 검증한다.

- `verifyCalls`, `verifyDecodeMisses`, `verifyCacheHits`, `ssimEvals`,
  `frameSsimEvals`, `groups`, 최종 verdict 가 D9d 및 D9a 기준과 동일.
- `verify_parity_test` 변경 없이 통과.
- `ui_translation_keys_test` 계속 통과 (D9d GUI fix 회귀 없음).
- `benchmark_schema_test` 계속 통과.
- probe 유무에 따라 WIC 성공/실패 카운터가 동일해야 한다.

## 10. 호환성 위험

낮지만 없애지 않는다. probe 가 decode 마다 `CreateFileW`/`CloseHandle` 한 쌍을
추가한다. dataset 항목 중 WIC 가 관대하게 처리하지만 probe 에서는 드러나는 경우가
있으면, probe 가 decode 결과를 바꾸어서는 안 된다. 따라서 probe 는 자체 실패
카운터를 별도로 기록하고 decode 를 게이트하지 않는다.

HRESULT 로깅은 코드가 이미 가지고 있던 값의 읽기다. COM lifetime 은 건드리지
않는다. 익명 namespace 맨 위 주석이 요구하듯 모든 `ComPtr` 은 여전히
`CoUninitialize` 이전에 소멸한다.

## 11. 측정 계획

- 동일 dataset, fingerprint, 하드웨어, GPU, 설정, cold-index 조건.
- **동일 조건 최소 5회**, mean/median/min/max/range 보고.
- wall clock 1~2 % 차이는 6.3 % 편차 환경에서 개선으로 선언하지 않는다.
- 단계 비중과 per-call 비용이 신호이며, instrumented 빌드의 절대 합계는 성능
  주장이 아니다.

## 12. noise 고려

D9d 가 5회에서 6.3 % wall 편차를 측정했다. 호출 횟수는 결정적이므로 비율과
per-call 비용이 신뢰할 비교다. probe 가 I/O 를 추가하므로 절대 시간이 소폭
왜곡될 수 있으며, 그 왜곡은 무시하지 않고 측정·보고한다.

## 13. 중단 조건

범위를 줄이거나 중단하고, 고쳐 돌리지 않고 기록한다.

```text
1. instrumentation 이 verdict 또는 grouping 을 변경
2. CPU/GPU parity 파괴
3. 기존 test 실패 또는 완화
4. probe 가 어떤 decode 결과를 변경
5. factory2Ms + factoryFallbackMs 가 factoryMs 를 재구성하지 못함
6. timing 중복으로 분해가 해석 불가
7. 값을 추정해야만 채울 수 있는 상황
8. schema 호환성 결론과 모순
```

## 14. 기대 결과

성공은 속도 개선이 아니라 원인 식별이다.

```text
1. open 의 구성이 답해지거나, 분리 불가함이 증명·기록됨
2. Factory2 성공/fallback 이 실제 카운트와 실제 HRESULT 로 답해짐
3. factory 가 Factory2 시도 / fallback 로 분해되어 factoryMs 재구성
4. decode 와 decodePreserveAspect 가 별도로 보고됨
5. mutex 상태 재확인
6. verdict, grouping, parity 보존
7. CPU/GPU parity 유지, 전체 test PASS
8. dataset 재현, 5회 이상
9. 다음 후보를 증거로 선정 가능
```

최종 상태는 PASS / PARTIAL / INCONCLUSIVE / FAIL 중 하나이며, 원인 식별 여부로
판정한다. 성능 변화는 주장하지 않는다.

## 15. 여기서 결정하지 않는 것

어떤 최적화가 뒤따르는가. 순서는 고정이다.

```text
D1 measurement
  -> 실제 원인
  -> 후보 선정
  -> 별도 pre-register
  -> 새 build version
  -> optimization
```

후보 A(candidate 도착률 감소)는 계속 deferred 다. candidate recall,
false positive/negative 위험, verdict semantics 를 접촉한다.
