# 0.9.2.29 — ScanPipeline Candidate Streaming and Complete-Coverage Short-Circuit

## IMPORTANT CHANGE
**IMPORTANT:** ScanPipeline no longer materializes all candidate-pair vectors returned by the eight CandidateIndex instances.

### Why the change was needed
Although 0.9.2.28 optimized `candidatePairs()` internally and introduced the basis for streaming consumption, ScanPipeline still materialized every index result before merging them. Bucket-heavy datasets can produce millions of candidate pairs, creating very large transient memory usage.

### Previous structure
- Call `candidatePairs()` for eight indexes.
- Keep all result vectors simultaneously.
- Deduplicate through a global `seen` set.
- Build another final pair vector.

### New structure
- Added `CandidateIndex::forEachCandidatePair()`.
- ScanPipeline consumes candidate pairs immediately through a callback.
- No complete candidate-pair vector is materialized.
- If the full index already covers every possible pair for a media kind, crop indexes for that kind are skipped.
- Crop deduplication state is enabled only when needed.

### Resolution
The transient candidate-pair vectors have been removed from the ScanPipeline path. In worst-case identical-hash datasets, once the full index covers all possible pairs, redundant crop-index generation is skipped entirely.

## Accuracy / Compatibility
- Existing `candidatePairs()` API and ordering remain unchanged.
- `forEachCandidatePair()` uses the same exact Hamming semantics.
- ScanPipeline candidate deduplication semantics are preserved.
- Image/video separation remains unchanged.
- SimilarityEngine, mirror/crop similarity, and video temporal refinement are unchanged.
