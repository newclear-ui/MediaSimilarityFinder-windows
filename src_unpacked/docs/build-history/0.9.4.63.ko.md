## 2. splitter 가운데 우선 정책 (0.9.4.63)

- 원인: stretch `(0,0,1)` — 창 증가분이 전부 오른쪽 상세 pane으로 갔다.
  기본 `{200,330,950}`도 오른쪽이 과대했다.
- 변경: stretch `(0,1,0)` — 증가분은 가운데 유사그룹 pane이 흡수.
  기본값 `{200,720,560}` (오른쪽은 미리보기 4개 ≈ 4×128 기준).
- 저장된 state는 삭제하지 않음. 복원 후 가운데가 320 미만이면 오른쪽
  (최소 360), 왼쪽 (최소 140) 순으로 빌려 최소폭만 보정.
- 실측 (offscreen 1500→1850→2200): `200/720/560` → `200/1070/560` →
  `200/1420/560`. 오른쪽 증가 0, 가운데가 전부 흡수.

## 4. Test Mode 설계 검토 결과 — DEFERRED

- 명칭 확정: KO `테스트 모드` / EN `Test Mode` (사용 가능).
- 구 GUI benchmark worker/storage는 S4 reset으로 삭제된 것
  (`docs/architecture/legacy/S4_GUI_BENCHMARK_REMOVAL.ko.md`).
  되살리지 않는다.
- 현 S2/S5 `BenchmarkRunner`는 suite·journal·mode 실행 모델이라 단일
  사용자 검색 비교에 잘못된 추상화다. GUI에서 재사용하면 S4가 금지한
  "GUI benchmark runner" 부활과 같다. 재사용하지 않는다.
- 정직한 최소형은 scratch-AppDir 실스캔이다 (별도 인덱스 디렉토리로
  실제 엔진을 돌려 실제 인덱스를 건드리지 않음 + telemetry·시간 기록).
  `TelemetryPurpose`区分 수단은 존재한다.
- 이번 빌드에서 강행하지 않은 이유: UI 표면(버튼/대화상자), scratch
  수명주기(정리 정책), telemetry 구분 결정, acceptance 테스트가 필요해
  "작고 확실한" 범위를 초과한다.
- 재개 조건: 위 4개 결정 + 별도 버전. Settings 위치는 새 표시 설정
  대화상자 계열로 follow-up에서 결정.

## 5. visible-range traversal 검토 결과 — DEFERRED

- 현 구조: 전체 순회하며 rect 교차 검사 (decode는 보이는 것만).
  11k groups 기준으로도 tick당 수 ms 수준이라 correctness blocker 아님.
- indexAt 기반 범위 계산은 Batched 비동기 layout·3종 view mode·미layout
  viewport에서 실패 시 조용히 스킵(영구 placeholder)한다.
  실패가 조용해서 테스트로 안전을 증명할 수 없다.
- 따라서 전체 순회를 유지한다. 위험은 성능 비용으로 worklog에 기록.
  대규모 dataset 실측 후 후속 빌드에서 재검토.
