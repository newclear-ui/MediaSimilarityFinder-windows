# MediaSimilarityFinder v0.9.2.49 — 선택 검색 + 실시간 매칭 + 멀티코어

## 변경 필요성
대용량 실사용 보고: (1) 이미지/비디오 선택 검색 옵션 부재, (2) 목록 작성과 매칭이 분리되어 결과가 끝에서야 나타남, (3) 진행률이 오르내림, (4) 99% 장시간 정체, (5) GPU 0%, (6) 카운터 없이 체감 불가, (7) 일부 코어에만 부하 집중. 원인별로 대응했다.

## 기존 구조
스캔 종류 필터 없음. `pipe.analyze`는 분석 완료 후 일괄 실행. 진행률 분모가 스트리밍 중 증가하는 walked 수라 감소 표시. 이미지 디코드는 단일 스레드 직렬. 장시간 단일 파일 정체 시 화면 갱신 없음.

## 변경 구조
- **선택 검색**: `ScanControl::scanImages/scanVideos`(기본 true). 제외 종류는 seen 집합에만 넣어 삭제 방지, 카운트 제외. GUI `검색 대상 ▾` 드롭다운(체크 유지, `ui/kindMask` 저장). 워커 전달
- **증분 live 매칭**: `ScanPipeline::addAndMatch()` 신설. 실행 인덱스를 멤버로 승격하고 `best()`를 공용 static으로 추출. 분석 완료 파일마다 기존 항목과 즉시 비교해 `onMatch` 스트리밍. 최종 `analyze()`는 그대로 실행(시간차 temporal 2차 판정 + 미변경 파일 쌍 + 보관 벡터 담당). 스트림 중복은 GUI union-find에서 idempotent 처리
- **단조 진행률**: 바는 감소하지 않고, 메시지에 `분석D / 목록W (P%)` 실수 표시
- **이미지 병렬 디코드**: `imageBatch` 디코드 + 크롭 패스를 하드웨어 스레드 상한(4~16) fan-out. 순서 보장이라 결과 결정적, 예외 격리. GPU 해시 배치는 그대로
- **스톨 가시성**: 600ms 타이머가 경과 포함 메시지를 재구성. 장시간 파일은 파일명 고정 + 시간 증가로 "작업 중"과 "멈춤" 구분
- 오픈소스 대조: DCT pHash 방식이 `aetilius/pHash`의 `ph_dct_imagehash`와 동일 계열임을 확인 (D<=8 임계값은 pHash 가이드 ≤10과 일치). `Pengfei-Kou/viddup`의 3단 파이프라인(정확 해시→duration 프리필터→pHash), `akamhy/videohash`의 콜라주 접근, `commonsmachinery/blockhash`를 향후 후보로 기록
- 버전 표기 통일 → 0.9.2.49

## 해결된 상황
- 이미지/비디오 단독 스캔 가능. 매치는 분석되는 대로 실시간 표시 (최종 패스가 temporal·미변경 쌍 보완)
- 진행률 역행 소멸. 이미지 단계 멀티코어 사용. 정체 파일 특정 가능

## 검증
- Core Release 빌드 PASS, **CTest 40/40 PASS** (스캔 경로 전부 녹색)
- 동등성 프로브(280개 실미디어): live 19 = final 19, fully identical (정수 %까지). `--smoke` exit 0, `--version` 0.9.2.49
- GPU 사용률 상시 표시에 대한 답변: 해시 커널이 수 ms 단위라 nvidia-smi에 안 잡히는 게 정상. 실제 사용은 `gpuImages` 카운터로 확인 (프로브 255/255). NVDEC/nvJPEG급 하드웨어 디코드는 별도 프로젝트 규모라 미포함

## 향후 영향
- `addAndMatch`는 temporal 2차를 생략 (최종 패스가 담당). 완전 점진 매칭으로 가려면 temporal 스트리밍 설계가 별도 필요
- 정확-복제 fast path(xxHash류, viddup L1 착안), duration 프리필터(L2), 저분산 프레임 제외를 다음 효율화 후보로 기록. 셋 다 현재 구조 위에 additive로 추가 가능
- `ScanControl` kind 플래그는 테스트 기본값 true라 기존 호출 무영향
