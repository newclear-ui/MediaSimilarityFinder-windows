# MediaSimilarityFinder v0.9.4.137 — Preview gauge: 0.05-step snapping + two-decimal ratio bubble

Baseline `0.9.4.136` -> this build `0.9.4.137`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged (display-only).

## 1. Why the change was needed

- Field feedback (0.9.4.136): (1) show **two decimals** in the drag bubble, (2) the preview size changes too finely between 0.9 and 1.0 (thirteen 1-px steps). The user suggested 0.1-unit movement.
- Judgment: 0.1 units (12.8 px) make 0.9 -> 1.0 a single 13 px jump with only 17 stops overall -- too coarse. **0.05 units (6.4 px, 33 stops)** removes the "too many changes" problem while keeping the second decimal meaningful (0.95 -> 1.00 -> 1.05). Applied on that basis.

## 2. Previous structure

- The 0.9.4.136 `ZoomSlider` moved in 1 px steps (48..256, 208 stops), the bubble showed one decimal, and consumers connected to the raw `QSlider::valueChanged`.

## 3. Changed structure

- **0.05-ratio snapping**: `ZoomSlider::snapValueFor(v, reference)` computes `round(round((v/128)/0.05) * 0.05 * 128)` (0.40..2.00, 33 stops). `onValueChanged` re-sets the slider to the snapped value (QSignalBlocker prevents re-entry) and emits **`previewSizeChanged(px)` with the snapped value only**. `MainWindow` connects that signal to `zoomChanged` (the raw `valueChanged` is no longer used). Keyboard/wheel: `singleStep=6 px`, `pageStep=26 px`.
- **Two-decimal bubble**: `round(ratio*100)/100` rendered with `'f', 2` (0.50 / 0.95 / 1.00 / 1.25 ...).
- The 1.0 reference (128 px) coincides exactly with a snap stop.

## 4. What was resolved

- A 0.9 -> 1.0 move is now 0.90 -> 0.95 -> 1.00 (two steps) instead of thirteen size changes, and the bubble shows the 0.05 granularity with two decimals.
