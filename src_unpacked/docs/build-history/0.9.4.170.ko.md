# MediaSimilarityFinder v0.9.4.170 — D3D11VA 하드웨어 디코드 (F-2 부분 재개)

기준선 `0.9.4.169` → 본 빌드 `0.9.4.170`.
CPU CTest **139/139**, GPU CTest **140/140** (신규 CTest 1건: video_hw_decode_test).
`kEngineVersion 1.5.2` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 11` / `kProtocol 1` (모두 불변).

## 1. 변경 필요성

- 사용자 지시: 소프트웨어 디코드를 기본으로 빌드하되 하드웨어를 적극 사용, H.264/H.265/AV1 가정 빌드, 하단 상태 표시, 설정 파일 기록, 이 PC(NVIDIA)에서 NVDEC 켜기, F-2 재검토, 임시 폴더 비디오로 테스트, 다음 빌드 DirectX 검토.
- F-2 재검토 결과: 네이티브 CUDA/NVDEC API가 아니라 FFmpeg D3D11VA 경로를 채택. 이 PC에서는 D3D11VA가 NVDEC 실리콘을 그대로 구동하므로 "NVDEC 켜기"와 실효가 같다. vcpkg FFmpeg에 cuvid/nvdec이 없어 (로컬 확인) 네이티브 경로는 툴체인 공사가 필요하고, F-1 중단 범위와도 겹치므로 이번 빌드 범위 밖이다.

## 2. 기존 구조

- `VideoDecoder::open()`은 소프트웨어 디코더만 열었다. HW 코드가 없었다.

## 3. 변경 구조

- `open()`: D3D11VA 장치(프로세스 공용 1개)가 있으면 HW 우선으로 열고, 실패하면 소프트웨어로 재시도한다. `MSF_VIDEO_HW=off`는 소프트웨어 강제.
- 프레임 수신 후 D3D11이면 시스템 메모리로 다운로드(`av_hwframe_transfer_data`)한 뒤 기존 sws 경로로 간다. 다운로드 실패는 pre-emit이면 소프트웨어로 1회 재시작(지문 불일치 불가), post-emit이면 기존 sweep 실패 계약을 따른다.
- `VideoBuildStats.hwUsed/hwBackend/hwCodec/hwFallbacks` → `telemetry_.addVideoHw` → `videos.hwFiles/videos.hwFallbacks` (가산, measured/null 규약 준수). `AnalyzeTelemetry.videoHwFiles/videoHwFallbacks` 합산 포함.
- 엔진 누적 카운터 + backend 상태(`hwAvailable/hwBackend/hwUsed/hwCodecs`) → IPC → GUI 하단 `hwLbl_` ("HW:d3d11va x12" / "SW"). QSettings 기록: `ui/hwDecode`(설정), `ui/hwAvailable`, `ui/hwBackend`, `ui/hwUsed`, `ui/hwCodec/<코덱>`.
- Settings>일반에 "하드웨어 디코드" 체크박스. 끄면 백엔드 재시작 후 `MSF_VIDEO_HW=off`로 전파된다 (스폰 시점 고정값이므로).
- 네이티브 H.264 디코더에만 HW 분기가 있다. 이 빌드의 mpeg4 네이티브 디코더는 HW 경로가 없어 소프트웨어로만 간다 (측정으로 확인).

## 4. 해결된 상황

- H.264 파일은 D3D11VA(NVDEC 실리콘)로 디코드되고, 소프트웨어와 동일한 지문이거나 깨끗이 실패한다.
- 현장 50개: HW 사용 50/50, 속도 1.26x (474.3s → 375.2s).
- 지문 drift: 50개 중 1개 파일(f07) 1프레임 2비트 해시 차이 (HW 결정적, hwHwDiff=0). 교차쌍 1225개 score 완전 동일, 반전 0 (50/87.5 모두). f07 혼합경로 중복쌍 Δ≤0.47, 판정 경계와 무관.
