# MediaSimilarityFinder v0.9.4.86 — dataset fingerprint 캐시 + 후보 결정성 진단

기준선 `0.9.4.85` → 본 빌드 `0.9.4.86`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.5` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — 전부 불변. 판정·스키마·디코드 변경 없음.
(DB `meta` 테이블에 키 1개(`dataset_fp_cache`) 추가 — 가산 키, 구코드 무시.)

## 1. 변경 필요성

사용자 풀 검색 로그 2건 분석 결과:
- run1(08:27): 총 2047.5s 중 **dataset fingerprint 1387.7s(67.8%)**, 68.9GB 전체 재해시.
- run2(09:13): 총 2199.8s 중 **dataset fingerprint 1436.6s(65.3%)**, 동일 68.9GB 재해시.
- 두 실행의 dataset fingerprint 값이 **동일**(`1bf86a74…`) → 데이터셋 불변인데 매 스캔마다 전체를 다시 읽는다.
- 이 단계는 **telemetry 전용**(JSON의 dataset identity)이며 결과(groups/pairs)에 영향 없음.
- 추가로, 동일 fingerprint인데 run1 groups 1976 vs run2 4734로 달라 **결정성 확인 필요**.

## 2. 기존 구조

- `computeDatasetFingerprint`(`dataset_fingerprint.cpp`)가 in-scope 모든 파일을 **전체 읽어 SHA-256**하고 매니페스트 해시를 만든다.
- 호출 조건(`media_search_engine.cpp`): `telemetryOn && walkCompleted && !cancelled` (상세 로그 ON이면 매 스캔).
- 캐시가 없어 매 스캔마다 전체 재해시 → 대규모에서 23분.

## 3. 변경 구조

**(1) 파일셋 키 캐시 (핵심)**
- 스캔 완료 후 DB rows의 `(path,size,modified,quickHash)`(walk가 변경 감지에 쓰는 바로 그 값)로
  정렬 매니페스트를 만들고 SHA-256 → **파일셋 키**.
- 지문·fileCount·totalBytes를 `keyHash|fingerprint|fileCount|totalBytes`로 DB `meta`
  (`dataset_fp_cache`)에 저장.
- 다음 스캔에서 키가 같으면 **재해시를 생략하고 저장값을 재사용**(`bytesRead=0`).
  키가 다르면(변경·신규·삭제) 전체 재계산 후 갱신.
- fingerprintVersion·scope(images/videos)도 키에 포함해 알고리즘/스코프 변경 시 무효화.

**(2) 후보 결정성 진단**
- `ScanPipeline::analyze`가 `scanIndex files= indexed= withCrops= imageIdx= c4= c1= c916=`
  로그 1줄을 남긴다. 후보 집합은 `files_`(지문+crop)의 **순수 함수**이므로, 두 실행의 이
  수치가 다르면 DB의 crop 컬럼 완성도가 다르다는 뜻이다(코드 비결정성이 아님).

## 4. 해결된 상황

- 변경 없는 재스캔에서 dataset fingerprint 23분 → **0(캐시 히트)**.
- 판정·결과·인덱스·썸네일은 불변(캐시는 telemetry 값만 재사용).

## 6. 향후 영향 및 한계

- **파일이 하나라도 바뀌면 전체 재해시**(현재와 동일). 파일별 전체 해시를 저장하는 진증분
  캐시는 후속 후보.
- 캐시 키는 size/mtime/quickHash(앞 64KiB) 기반이라, mtime을 보존하면서 64KiB 이후만
  바뀌는 드문 경우는 감지하지 못한다(telemetry 값 한정, 결과 불변).
- **결정성 이상(run1 1976 vs run2 4734)은 미규명**: 후보 집합은 코드상 결정적이므로 두 실행의
  DB crop 데이터가 달랐을 가능성이 크다. 이번 빌드의 `scanIndex … withCrops= …` 로그로 다음
  실행에서 확인한다.
