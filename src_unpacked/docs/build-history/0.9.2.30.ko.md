# 0.9.2.30 — Scan 결과 전달 경로의 이중 Match 저장 제거

**중요 변경 (IMPORTANT)**

## 변경 필요성
0.9.2.29에서 후보 pair 생성은 스트리밍 방식으로 전환되었지만, 실제 유사 매치가 확정된 뒤에는 `ScanPipeline::ScanStats::matches`에 `MediaMatch`를 저장한 다음 `MediaSearchEngine::scan()`에서 다시 `SearchMatch`로 복사하고 있었다. 대규모 결과에서는 동일한 매치 집합이 일시적으로 두 개의 컨테이너에 존재하여 불필요한 피크 메모리를 만들 수 있었다.

## 이전 구조
`ScanPipeline` → `ScanStats.matches` → `MediaSearchEngine`에서 `SearchReport.matches`로 복사

## 새 구조
`ScanPipeline` → `MatchCallback` → `SearchReport.matches`

기존 `analyze(maxDistance)` 호출은 호환성을 위해 그대로 유지되며, callback을 지정하지 않으면 기존처럼 `ScanStats.matches`에 저장한다.

## 해결된 상황
`MediaSearchEngine::scan()`은 이제 매치가 확정되는 즉시 `SearchReport.matches`로 전달한다. 따라서 일반 검색 경로에서 `MediaMatch` 전체 배열과 `SearchMatch` 전체 배열을 동시에 유지하는 이중 저장을 제거했다.

## 정확성 / 호환성
- 매치 판정 로직, threshold, mirror/crop/temporal refinement는 변경하지 않았다.
- `ScanPipeline::analyze(maxDistance)` 기존 API와 반환 형식은 유지된다.
- callback API는 추가 API이며 기존 호출자를 깨뜨리지 않는다.
- 매치 순서도 기존 `ScanPipeline` 처리 순서를 그대로 따른다.

## 검증
- 기존 전체 테스트와 신규 callback 경로를 함께 검증한다.
- 0.9.2.29의 CandidateIndex streaming 및 complete-index short-circuit 설계를 그대로 유지한다.

## 향후 영향
다음 단계에서는 `SearchReport.matches` 자체가 수백만 건으로 커지는 경우를 대비해 결과 저장/페이지네이션 구조를 검토할 수 있다. 이번 변경은 그 전 단계로서 불필요한 중복 메모리를 먼저 제거한다.
