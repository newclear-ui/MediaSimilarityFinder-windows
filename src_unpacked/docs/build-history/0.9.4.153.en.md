## 1. Why the change was needed

- P1-A: the `.152` partial adoption preserved the baseline. With a currently valid baseline, a partial adoption leaves unverified out-of-scope pairs behind while the next A/AB skips full verification. Invalidation is the safe behavior.
- P1-B: on cancel/exception/engine-reported failure with applied changes, a still-valid baseline would vouch for an incomplete match set. The final-save-failure path (`.151`/`.152`) already invalidates; the remaining exit paths follow the same rule.

## 2. Previous structure

- Partial adoption: keep all meta (`.152`). Cancel: pruned persist + GUI re-apply existed, baseline kept. Exception catches: persist + failed existed, baseline kept. Engine failure report (`!r.completed`, no throw): reported as "Scan complete".

## 3. New structure

- **P1-A**: delete the `match_baseline` key inside the partial-adopt transaction (full-scope adoption still upserts all scratch meta). Rollback covers the delete (existing atomicity). The next A/AB runs one forced full verification and restamps.
- **P1-B**: invalidate the baseline on cancel / std::exception / non-std paths whenever `changedFiles_` is non-empty (guarded try/catch, existing no-throw contract kept). Engine-reported failure (`!r.completed`, not cancelled) emits `failed|msfChanged=N` with no results (append-only contract kept, positional indices unchanged). A user cancel is never classified as failure (cancel branch first).
- Regression pins: new e2e `Test 1h3` (valid baseline + partial adopt → invalidated → observed forced full verification → restamped + pairs preserved/dropped). `crash_diagnostics_test` §5 (new: cancel after change approval → CANCELLED + invalidated + forced full pass + pair consistency), §6 (new: exception-path invalidation), §4 extended (save-failure invalidation asserted). New `ui_cancel_consistency_test`: in-process loopback cancel on first progress signal → exact GUI==DB set equality → forced full verification → restamped. `MSF_TEST_ENGINE_FAIL` (new seam, deterministic engine-failure report).

## 4. Resolved state

- A partial adoption on a valid baseline no longer lets the next scan skip full verification.
- Cancelled/failed scans cannot leave an incomplete set trusted as complete. The GUI matches the DB through the existing re-apply paths.
- Genuine DB/engine failures are never reported as success.
