# MediaSimilarityFinder v0.9.4.133 — System CPU metric corrected (GetSystemTimes idle-in-denominator)

Baseline `0.9.4.132` -> this build `0.9.4.133`.
CPU CTest **125/125**, GPU CTest **126/126**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 9` unchanged (verdicts unchanged; CTest registration count unchanged).

## 1. Why the change was needed

- Field report: "CPU usage very different" (Maximum setting, nothing else running). The detailed log's `system avg 66.7%` disagreed with Task Manager's total CPU (35-50%) and looked contradictory next to the app's own 1.7%.
- Root cause: `TelemetryRecorder::sampleOnce` ignored that GetSystemTimes kernel time **includes idle** and added idle to the denominator:
  - Old formula: `sys = 1 - idle/(idle+kernel+user)` -- mathematically always `1/(2-u)` for a true busy fraction u, so **a fully idle machine reads 50%**.
  - Measured proof (near-idle 5 s window, compared side by side): old formula **55.8%**, corrected formula 20.6%, Windows performance counter 17.1-23.8%.
  - Field log correction: 66.7% -> true u = 2 - 1/0.667 = **~50%**.
- `monitor.cpp` (SystemLoadMonitor) always used the correct formula (`(dk+du-di)/(dk+du)`); a sweep confirmed the telemetry recorder was the only wrong site.

## 2. Previous structure

- `sampleOnce` computed `tot = idle+kernel+user; cpuSys = 100*(1 - idle/tot)` per sample -- a different result from the same-kind calculation in `monitor.cpp`.

## 3. Changed structure

- New header-inline `msf::systemBusyPercent(dIdle, dKernel, dUser)` = `(kernel+user - idle)/(kernel+user)`, 0 for an empty interval, clamping an inverted idle delta. `sampleOnce` calls it.
- Moving the formula into the header makes it **unit-testable**: `benchmark_test` gains five checks (empty / fully idle = 0% / fully busy = 100% / mixed 40.909% / clamp = 0%).

## 4. What was resolved

- System CPU now reports the true value. Concurrent probe (20 s window): telemetry `cpuSysMean 17.5%` vs performance counter average 15.4% (max 24.5) -- they agree.
- The app's process metric (process tree) was always correct: a walk-only measurement showed 1.66% (= the field log's 1.7%, matching Task Manager's 2%).

  - Interpretation: the field log's ~50% system CPU (corrected) comes from **consumers outside the app (antivirus)**; it is not that "Maximum uses no CPU" -- the app metric is accurate and the walk phase is I/O-latency bound.

## 6. Historical record correction (AGENTS 9 rule)

- `resources.cpuSysMean` in logs from 0.9.4.88 to 0.9.4.132 and the summary dialog's "system avg" value are **inflated** (see the root cause above). Field example: 66.7% -> true ~50%.
- The original records are kept; this entry records the error cause, the corrected formula and the reason. Logs from this build onward carry true values.

## 7. Impact and limitations

- Verdicts, storage, protocol, engine/DB/schema/cache and the journal schema are unchanged. CTest registration count unchanged (125/126). JSON keys unchanged (only the value definition was corrected).
- Field follow-ups (separate candidates): (1) adding the scan root to Defender exclusions reduces AV involvement in walk/verify I/O (user action). (2) A no-change rescan still reads a 64 KiB quick hash per file every time (21.2 GB per scan) -- skipping the read when (size, modified) match is a candidate (the same principle as the 0.9.4.89 fingerprint cache). Both are out of scope here and are recorded as measurements.
