# MediaSimilarityFinder v0.9.4.165 — Cancelled Video Builds Never Become Settled Failures (P1 Regression Fix)

Baseline `0.9.4.164` → this build `0.9.4.165`.
CPU CTest **134/134**, GPU CTest **135/135** (no new executables; deterministic scenario D added to `scan_cancel_video_test`).
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.6` / `kBenchmarkSchemaVersion 9` / `kCacheFormatVersion 10` / `kProtocol 1` all unchanged.

## 1. Why the change was needed

- `scan_cancel_video_test` scenario A flaked intermittently in the 0.9.4.163/164 GPU suites (identical binaries always green standalone). Root-causing showed a real product defect behind the flake, not just timing.
- Defect: when a user stops a scan, in-flight video builds were recorded with `analysisFailed=true` (settled failures). Under the `pendingAnalysis` rule (fingerprint==0 && !analysisFailed) those rows are skipped forever — cancelled videos vanish from the index until their bytes change. The 0.9.4.158 P0 fix stopped storing forged fingerprints but left the failure count and settled marking in place, so "cancelled" masqueraded as "failed".
- The test's exact-count assertions (`failed==0`, full rescan reuse) broke exactly when the defect bit, depending on timing. Fixing the defect makes them hold unconditionally.

## 2. Previous structure

- Video range harvest: any failed build was stored as `fingerprint=0, analysisFailed=true` + counted as failed + reported as a failed file, with no cancel distinction.
- `stopped(control)` also waits out pauses, so it cannot select the cancel path.

## 3. New structure

- At harvest time, check `control->cancel` directly (non-blocking, pause-insensitive): a cancel-aborted build keeps its admission skeleton (fp=0, not failed) so the next scan retries it via `pendingAnalysis`. Excluded from the failed count and the failed-file telemetry. Trace outcome is `"cancelled"` per the `file_trace` contract (settled without analysis, not `"failed"`).
- Genuine failures (no cancel) keep the settled path unchanged.
- Regression pin: scenario D (tiny clip + 4K-noise clip, ~40x sweep-time gap for a deterministic mid-sweep abort). Verified FAIL-first on the old code (`failed==1`, rescan skips the aborted file), then green after the fix.
- The adhoc query path and image batches have no cancel-abort path (batches run to completion, reverify rolls back), so they are unchanged.

## 4. Resolved state

- Cancelled scans leave no settled-failure rows. Completed work is stored and reused, aborted work is retried next scan, only genuine failures settle.
- Scenario A's exact-count assertions are deterministic again (`failed==0`, `unchanged==analyzed`, `analyzed+unchanged==kClips` under every interleaving).

## 6. Impact and limits

- Judgement, storage, protocol, versions, engine unchanged. No cache invalidation. No engine bump (a cancel-path recording correction, not a judgement change — no re-verification needed).
- A cancelled scan's `failed` count now means genuine failures only; past cancelled scans overcounted failures.
