# MediaSimilarityFinder v0.9.4.26 — D9c Expensive Verify 내부 비용 계측

Status: **PRE-REGISTERED** (이 문서는 코드 변경 **전에** 커밋된다)

이번 빌드는 **instrumentation / profiling 빌드**다. 성능 향상이 목표가 아니다.

---

## 1. 변경 필요성

v0.9.4.25 D9b는 후보 B(expensive verify 1건 비용 감소)를 검증했고 기각됐다.

```text
v0.9.4.25 D9b
후보 B
expensive verify 1건 비용 감소
→ NOT ACCEPTED
```

정확성과 호환성은 보존됐으나 성능 목표를 달성하지 못했다. 따라서 D9b는
성능 baseline으로 승격하지 않으며, 이후 모든 비교 기준은 계속
**D9a(0.9.4.24)** 다.

D9b가 답하지 못한 질문이 D9c의 주제다.

> expensive verify 약 8.5 ms는 실제로 어디에 쓰이는가?

D9a 자체의 run 간 편차(약 7.5%)가 D9b 관측값과 같은 크기이므로 감소로
간주할 수 없다.

**D9b가 확정한 구조적 사실 — 반복하지 않도록 기록한다.**
D9b가 가정한 중복은 존재하지 않았다. 원본도 이미 aspect buffer(`rA`, `rB`)를
루프 바깥에서 한 번만 계산하고 재사용하고 있었다. D9b는 이미 재사용되고 있던
값을 더 넓은 스코프로 옮겼을 뿐이다. 이것이 **"원본이 완벽하게 최적화되어
있다"는 뜻은 아니다.** 해당 가설 하나가 무효였다는 뜻일 뿐이다.

## 4. D9c 가설

최적화 가설 없음. D9c는 어떤 단계가 지배적인지 가정하지 않고 각 단계를
따로 측정한다. 이유는 D9b의 교훈 때문이다.

```text
관찰된 연산량 ≠ 실제 병목
```

D9b는 약 2,048회 픽셀 연산(proxy 기준 2.3%)을 제거했고 변화가 없었으며,
같은 함수 안의 다른 단계는 아예 후보에 오르지 않았다.

## 5. 계측 범위

`src/image_verify.cpp` 의 실제 call path를 추적해 분리한다
(`verifyImagePair` → `verifyBuffersFor` ×2 → `verifyScorePlan` →
`verifyScorePlanImpl` → `ssimBuf` ×10 → `frame_ssim` ×20):

| 단계 | 코드 위치 | 계측 경계 |
|---|---|---|
| buffer key / stat / quick-hash read | `verifyBuffersFor` 앞부분 | `file_size` + `last_write_time` + 64KB read + FNV 루프 timer |
| decode | `verifyBuffersFor` | `ImageDecoder::decode` ×2 + dimension 검증 timer |
| cache 저장 / hit 시 복사 | `verifyBuffersFor` | map insert/evict timer, hit 시 buffer 복사 별도 timer |
| crop / aspect 준비 | `verifyScorePlan` | `centerCropResize` 8회 timer |
| mirror flip | `ssimBuf` | `flipBuf` timer |
| frame_ssim | `ssimBuf` | `frame_ssim` 2회 timer |
| other | — | verify total 의 나머지 |

코드가 resize 와 crop 을 분리하지 않으면 억지로 나누지 않는다. 보고서에는
**실제로 계측한 경계**를 명시한다.

**`frame_ssim` 내부는 계측하지 않는다.** `src/video_fingerprint.cpp:398` 의
단일 함수이며, 내부 루프에 timer 를 넣어야만 분리되는데 이는 금지된다
(Non-goals 참조). 따라서 preparation/window/accumulation 분해는
**측정되지 않은 상태로 보고**해야 하며 추정으로 채우지 않는다.

## 6. instrumentation 범위

D9c에서 허용되는 것은 아래뿐이다.

```text
timing instrumentation
counter instrumentation
profiling telemetry
benchmark reporting
instrumentation 검증에 필요한 test coverage
```

기존 구조를 확장한다. 중복 체계는 만들지 않는다.

- `src/analyze_telemetry.h` — 기존 단순 데이터 운반체.
  `BenchmarkRecorder`·`ScanPipeline`에 대한 의존이 없고, recorder 포인터가
  검증 코드에 전달되지 않는 것이 의도된 설계다. D9c도 이 성질을 유지한다.
  `image_verify` 는 이 struct 만 채운다.
- `src/benchmark.cpp` — analyze telemetry 을 렌더링하는 곳
  (현재 `verifyMs`, `verifyCalls`, `msPerVerifyCall`). 새 필드를 나란히 출력한다.
- schema version — analyze telemetry 블록은 schema v9다. 필드 추가는
  additive이며, 기존 additive-read 계약이 요구할 때만 버전을 올리고 그 판단
  근거를 명시한다.

## 7. Non-goals

D9c에서는 어떤 이유로도 다음을 하지 않는다.

```text
SSIM 공식 / window 크기 / precision 변경
early-exit 추가
SSIM 평가 횟수 변경
frame sampling, threshold, candidate filtering,
candidate semantics, grouping, verdict semantics 변경
cache semantics 변경
decode, resize, crop, mirror semantics 변경
CPU fallback semantics 변경
CUDA correctness 변경
"timer 넣는 김에 조금 최적화" 류의 작업
vcpkg 구조 정리
```

window size, precision, early-exit 은 별도 pre-register 대상이다.

## 8. 정확성 / verdict 위험

위험은 수치가 아니라 **행동**이다. instrumentation 이 아래를 바꾸면 안 된다.

```text
verify 결과
verdict
그룹 수와 구성
similarity 판정
```

대응:

- 기존 `verify_parity_test` 가 보존된 pre-D9b `verifyScorePlanReference` 와
  `verifyScorePlan` 을 double 동일 비교한다. 이 테스트를 반드시 통과시킨다.
- instrumented 실행과 uninstrumented 실행(`tel == nullptr`)을 같은 입력으로
  비교해 결과가 동일한지 검증하는 assertion 을 추가한다.
- sub-stage 시간 합이 계측된 verify total 이하인지 검증하는 assertion 을
  추가한다. timer 범위가 겹치면 조용히 틀린 분포를 내는 대신 실패한다.
- 동일 dataset 에서 `groups` == 156,152 여야 한다.

## 9. 호환성 위험

기대 없음. struct 는 additive 이고 core 가 채우며 Qt 무관하다. 검증은 공유
CPU 코드이므로 CPU fallback 과 GPU 경로 어느 쪽도 건드리지 않는다. 이것이
사실이 아니라면 그것은 중단 조건이지 우회 대상이 아니다.

## 10. 측정 계획

- D9a 와 동일 dataset, 하드웨어, GPU, 설정, cold-index 조건. 측정 전
  fingerprint 를 확인한다.
- 기존 `msf_dataset_baseline` harness, 3 runs. 단일 run 결론은 유효하지 않다.
- 단계 시간을 합계와 expensive-verify 1건 평균, 그리고 비율로 보고한다.
- instrumentation 자체가 시간을 쓰므로, D9c timing 결과는
  **production performance 주장이 아니다.** 상대적 내부 분포만 범위다.

## 11. timer 의미와 비중복

시간은 **exclusive** 이며 서로 배타적으로 구성한다.

```text
verifyTotal = keyMs + decodeMs + cacheStoreMs + cacheCopyMs
            + cropMs + flipMs + frameSsimMs + otherMs
```

`otherMs` 는 D9a 가 `scanMs` 를 정의한 방식과 동일하게, 계측된 단계들을
뺀 verify total 의 나머지다. 단계들이 서로 겹치지 않는 코드 영역이므로 합이
total 을 넘을 수 없고, 테스트가 이를 검증한다.

inclusive 시간을 중첩해 더하지 않는다. 필드별 의미를 보고서에 명시한다.

overhead 예산: expensive verify 1건당 대략 48회 timer read
(`verifyBuffersFor` 2회 × 약 20회, crop 1회, `ssimBuf` 10회 × 4회),
전체 실행 기준 약 660,000회 규모다. timer 를 4,096회 inner loop 안에 넣지
않는다. 측정된 overhead 는 가정으로 없애지 않고 보고한다.

## 12. 중단 조건

다음 중 하나면 계측 범위를 줄이거나 중단하고, 문제를 임의로 고치지 않고
기록한다.

```text
1. instrumentation 이 verdict 를 변경
2. instrumentation 이 candidate semantics 를 변경
3. CPU/GPU parity 파괴
4. 기존 test 실패
5. timer overhead 과도
6. 단계 시간이 중복되어 해석 불가
7. 실제 expensive verify path 를 정확히 계측할 수 없음
8. 기존 test 를 삭제하거나 조건을 완화
9. 측정값을 추정해야만 채울 수 있는 상황
```

## 13. pre-register 기준선 결정

현재 working tree 에는 D9b 코드가 있다(D9a 커밋 `f46658e` 대비
`src/image_verify.cpp` / `.h` 에 103줄 추가). 되돌리지 않는다.

이유:

- 되돌릴 필요가 없다. D9b 는 모든 카운터와 그룹 수를 D9a 와 동일하게
  유지함이 측정되었고, `verify_parity_test` 가 채점 경로가 pre-D9b
  reference 와 double 동일함을 증명한다. 따라서 코드는 달라도 **행동은
  D9a 와 동등**하다.
- `git reset --hard`, `git clean -fd`, `git restore .` 은 금지되어 있고,
  보존할 로컬 사용자 변경사항이 없다(HEAD `0f75c2d` 기준 트리 clean).

D9c 는 현재 트리에 계측을 적용하고, 보고서에서 이 동등성을 명시해 D9a 와
비교 가능하게 유지한다.

## 14. 기대 결과

성공의 정의는 다음이며, 다음이 아니다.

```text
성공:
  expensive verify 경로의 안정적인 내부 timing
  verdict / grouping / candidate behaviour 보존
  CPU/GPU parity 유지
  기존 test 전부 PASS
  D9a 기준과 비교 가능한 telemetry
  다음 후보를 고를 수 있는 증거 확보

성공 아님 (성능이 기준이 아님):
  어떤 wall-clock 개선
  D9a 보다 큰 ms/verify 수치
```

산출물은 8.5 ms의 측정된 비용 분포와, 다음 후보를 선정하기 위한 증거다.
다음 후보는 **D9c 에서 구현하지 않는다.** 별도 pre-register, 별도 version,
별도 hypothesis, 별도 정확성 위험, 별도 측정 계획으로 진행한다.
