# MediaSimilarityFinder v0.9.4.26 — D9c Expensive Verify 내부 비용 계측

Status: **PASS** (instrumentation 빌드 — 목표는 비용 분포의 측정이지 속도 개선이 아니다)

## 1. D9c 질문에 대한 답

> expensive verify 약 8.5 ms는 어디에 쓰이는가?

**94.90 %는 이미지 decode 다.** D9b 가 최적화한 `frame_ssim` 은
**0.55 %** 다.

D8b dataset, cold index, 3 runs, 평균:

| 단계 | 합계 ms | 비중 | expensive verify 1건당 |
|---|---:|---:|---:|
| **decode** | 111,621.7 | **94.90 %** | **8.1274** |
| key (stat 2회 + 64KB quick-hash read) | 4,421.9 | 3.76 % | 0.3220 |
| other (나머지) | 481.4 | 0.41 % | 0.0351 |
| **frame_ssim** | 645.2 | **0.55 %** | **0.0470** |
| crop / aspect (crop+resize 합계) | 201.9 | 0.17 % | 0.0147 |
| mirror flip | 188.7 | 0.16 % | 0.0137 |
| cache store | 42.9 | 0.04 % | 0.0031 |
| cache copy (hit) | 11.0 | 0.01 % | 0.0008 |
| **합계** | **117,614.6** | 100 % | **8.564** |

`sum == verifyMs` 가 정확히 성립한다(초과 0.0000 ms). 따라서 분해는 완전하고
중복이 없다.

```text
expensive verify 1건당 8.564 ms
│
├─ decode             94.90 %   8.1274 ms
├─ key (stat + hash)   3.76 %   0.3220 ms
├─ other               0.41 %   0.0351 ms
├─ frame_ssim          0.55 %   0.0470 ms
├─ crop/aspect         0.17 %   0.0147 ms
└─ mirror flip         0.16 %   0.0137 ms
```

## 2. 무엇이 뒤집혔는가

D9b 는 비용이 채점 경로에 있다고 가정하고 그쪽의 buffer 재계산을 제거했다.
그 단계는 지금 전체의 **0.55 %** 로 측정된다 — 8.564 ms 중 0.047 ms 다.
D9b 의 변경은 결과 동일한 올바른 정리였지만, 애초에 병목이 아니었던 단계를
정리한 것이므로 아무것도 움직이지 않은 것이 설명된다.

비율을 분명히 적어 둔다. 이 경로에서 decode 는 `frame_ssim` 의 약
**173배** 비용이다. decode 를 건드리지 않는 후보는 남은 5.1 % 보다 큰 것을
다룰 수 없다.

## 3. 무엇을 측정했고, 무엇을 측정하지 않았는가

측정 경계 — 모두 서로 겹치지 않는 코드 영역:

- **key** — `verifyBuffersFor` 의 cache 조회 이전 구간. `file_size` +
  `last_write_time` + 64KB read + FNV 루프. **hit / miss 무관하게 매 buffer
  lookup마다** 실행된다.
- **decode** — `ImageDecoder::decode` ×2 + dimension 검증.
- **cache store** — map insert 와 LRU eviction.
- **cache copy** — hit 시 cache 에서 `GrayImage` 를 복사하는 2회.
- **crop/aspect** — `centerCropResize` 8회. `resize` 는 crop 과 **분리하지
  않았다.** `centerCropResize` 가 한 함수에서 둘 다 수행하므로, 분리하려면
  측정 대상 코드를 바꾸어야 하기 때문이다.
- **mirror flip** — `flipBuf` 10회.
- **frame_ssim** — `frame_ssim` 20회, 호출 바깥에서 계측.
- **other** — `verifyMs` 의 나머지. D9a 가 `scanMs` 를 정의한 방식과 동일.

**측정하지 않았고, 추정하지도 않은 것:**

- `frame_ssim` 내부(preparation / window / accumulation). `src/video_fingerprint.cpp:398`
  의 단일 함수이며, 4,096회 inner loop 안에 timer 를 넣어야만 분리되는데 이는
  금지다. **미측정으로 보고한다.**
- decode 내부의 분해(파일 open, EXIF read, WIC scale, format conversion,
  pixel copy). D9c 는 decode 를 한 영역으로 계측했다. 이것이 다음 분해
  수준이며, 다음 후보는 여기서 찾아야 한다.

## 5. timing 의미

**exclusive, 비중복.** 7개 측정 단계는 서로 겹치지 않는 코드 영역이고 `other`
는 나머지이므로, 합계는 `verifyMs` 를 정확히 재구성한다. 소비자가 이 등식을
신뢰하지 않고 확인할 수 있도록 `verifySumMs` 와 `verifyBreakdownOverMs` 를
함께 공개한다. 이번 실행에서 초과량은 0.0000 ms 다.

timer overhead: expensive verify 1건당 대략 48회 read(`verifyBuffersFor` 2회 ×
약 20회, crop 1회, `ssimBuf` 10회 × 4회), 전체 실행 기준 약 660,000회.
inner loop 안에는 어떤 timer 도 없다. 이 빌드는 자기 timer 비용을 치르므로
**이 수치는 상대적 분포이지 production 성능 주장이 아니다.** `verifyMs` 117,614.6 ms
가 D9a/D9b run 간 범위(109,142–117,291 ms) 안에 있는 점이 그 한계와 일관된다.

## 7. 단계 카운터

```text
verifyBufferLookups    27,468   (= miss 12,949 + hit 14,519)
verifyQuickHashReads   27,468   lookup 당 1회, hit 포함
verifyQuickHashBytes   380,999,408  (363.3 MB, verify 1건당 평균 27,741 B)
verifyDecodes          25,898   (= 2 x 12,949 miss)
verifyCacheCopies      14,519   (= hit)
verifyCropCalls       109,872   (= 8 x 13,734)
verifyFlipCalls       137,340   (= 10 x 13,734)
```

이 카운터에서 두 구조적 사실이 나온다.

1. **cache hit 에도 64KB 를 읽고 해시한다.** 실제 decode 12,949회에 대해
   quick-hash read 가 27,468회다. 즉 key 가 hit 에서도 매번 재구성된다.
   14,519회의 cache hit 을 처리하기 위해 363 MB 를 읽고 해시했다. 비용의
   3.76 % 이므로 실제로는 존재하지만 병목은 아니다.
2. **miss 하나당 같은 파일을 두 번 디코드한다.** `verifyDecodes` 25,898 = 2 ×
   12,949. `verifyBuffersFor` 가 같은 path 에 대해 `decode(path,64,64,f)` 와
   `decodePreserveAspect(path,64,a)` 를 둘 다 호출한다. decode 1회당 4.31 ms
   × 2 가 8.127 ms 다.

## 8. decode 가 4.31 ms 인 이유

D9c 조사 중 `src/image_decoder.cpp` 를 읽은 결과다(보고만, 변경 없음).

- `decodeWicFile` / `decodeWicFileAspect` 는 호출마다
  `CoCreateInstance(CLSID_WICImagingFactory2)` 와 `CreateDecoderFromFilename`
  을 **수행한다.** factory 도, decoder 도, decode 된 frame 도 같은 파일의 두
  호출 사이에 재사용되지 않는다.
- scaler 가 `WICBitmapInterpolationModeFant` 을 쓴다(143행, `decodeWicFileAspect`
  도 동일). 고품질 다운샘플링 모드다.
- EXIF orientation 을 매 decode 마다 조회한다(120행, 168행).
- `IWICBitmapFormatConverter` 로 8bpp gray 변환 후 `CopyPixels`.

64×64 grayscale thumbnail 하나를 이 방식으로 만드는 데 4.31 ms 가 들고,
파일당 두 번 수행된다. D9c 는 이 내부를 더 잘게 측정하지 않았고, 이 코드
독해는 **다음 측정이 어디로 가야 하는지**를 알려준다.

## 10. 한계

- instrumented 빌드이므로 절대 시간에는 timer overhead 가 포함된다. 분포로 쓸 것.
- `frame_ssim` 내부와 `decode` 내부는 분해하지 않았다.
- key 단계는 stat 2회 + 64KB read + FNV 루프가 섞여 있으며, 더 나누지 않았다.
- 한 대의 기계, 한 dataset, 한 실행 구성. 3회 실행이지만 단일 호스트다.
- `8.564 ms/verify` 의 분모는 `verifyBufferLookups / 2`, 즉 buffer 단계까지
  도달한 호출로 유추한 expensive verify 다. D9a 의 13,734 와 정확히 일치한다.

## 11. 다음 후보

**D9c 에서 구현하지 않는다.** 지시대로 decode 가 지배적이라는 사실을
확인했다고 그걸 고쳐도 되는 것은 아니다. 증거가 가리키는 방향:

> **후보 D — 이미지 decode 비용.** 다음 pre-register 는 먼저 4.31 ms decode 를
> 분해해야 한다(factory/decoder 설정, file open, EXIF, Fant scale, format
> conversion, copy). D9c 는 decode 를 한 영역으로만 측정했기 때문이다.

모두 측정 카운터 또는 코드 독해에서 나온 관찰이며, 어떤 것도 제안이 아니다.

1. miss 하나당 같은 파일이 **두 번** 디코드된다(12,949 파일에 25,898회).
2. 64KB quick-hash key 가 **hit 14,519회까지** 매 lookup마다 재구성되어
   363 MB 를 읽고 해시한다.
3. WIC factory 와 decoder 가 호출마다 생성되고, scaler 가
   `WICBitmapInterpolationModeFant` 로 동작한다.

후보 A(candidate 도착률 감소)는 계속 deferred 다. verdict semantics 를 접촉한다.
`frame_ssim` 최적화는 0.55 % 로 측정되었으므로 단독 pre-register 를 받을
가치가 없다.
