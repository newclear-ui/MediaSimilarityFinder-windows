## 1. D9c 질문에 대한 답

> expensive verify 약 8.5 ms는 어디에 쓰이는가?

**94.90 %는 이미지 decode 다.** D9b 가 최적화한 `frame_ssim` 은
**0.55 %** 다.

D8b dataset, cold index, 3 runs, 평균:

|---|---:|---:|---:|
| **decode** | 111,621.7 | **94.90 %** | **8.1274** |
| key (stat 2회 + 64KB quick-hash read) | 4,421.9 | 3.76 % | 0.3220 |
| other (나머지) | 481.4 | 0.41 % | 0.0351 |
| **frame_ssim** | 645.2 | **0.55 %** | **0.0470** |

## 2. 무엇이 뒤집혔는가

D9b 는 비용이 채점 경로에 있다고 가정하고 그쪽의 buffer 재계산을 제거했다.
그 단계는 지금 전체의 **0.55 %** 로 측정된다 — 8.564 ms 중 0.047 ms 다.
D9b 의 변경은 결과 동일한 올바른 정리였지만, 애초에 병목이 아니었던 단계를
정리한 것이므로 아무것도 움직이지 않은 것이 설명된다.

비율을 분명히 적어 둔다. 이 경로에서 decode 는 `frame_ssim` 의 약
**173배** 비용이다. decode 를 건드리지 않는 후보는 남은 5.1 % 보다 큰 것을
다룰 수 없다.

## 3. 무엇을 측정했고, 무엇을 측정하지 않았는가

측정 경계 — 모두 서로 겹치지 않는 코드 영역:

- **key** — `verifyBuffersFor` 의 cache 조회 이전 구간. `file_size` +
  `last_write_time` + 64KB read + FNV 루프. **hit / miss 무관하게 매 buffer
  lookup마다** 실행된다.
- **decode** — `ImageDecoder::decode` ×2 + dimension 검증.
- **cache store** — map insert 와 LRU eviction.
- **cache copy** — hit 시 cache 에서 `GrayImage` 를 복사하는 2회.
- **crop/aspect** — `centerCropResize` 8회. `resize` 는 crop 과 **분리하지
  않았다.** `centerCropResize` 가 한 함수에서 둘 다 수행하므로, 분리하려면
  측정 대상 코드를 바꾸어야 하기 때문이다.
- **mirror flip** — `flipBuf` 10회.
- **frame_ssim** — `frame_ssim` 20회, 호출 바깥에서 계측.
- **other** — `verifyMs` 의 나머지. D9a 가 `scanMs` 를 정의한 방식과 동일.

**측정하지 않았고, 추정하지도 않은 것:**

- `frame_ssim` 내부(preparation / window / accumulation). `src/video_fingerprint.cpp:398`
  의 단일 함수이며, 4,096회 inner loop 안에 timer 를 넣어야만 분리되는데 이는
  금지다. **미측정으로 보고한다.**
- decode 내부의 분해(파일 open, EXIF read, WIC scale, format conversion,
  pixel copy). D9c 는 decode 를 한 영역으로 계측했다. 이것이 다음 분해
  수준이며, 다음 후보는 여기서 찾아야 한다.

## 5. timing 의미

**exclusive, 비중복.** 7개 측정 단계는 서로 겹치지 않는 코드 영역이고 `other`
는 나머지이므로, 합계는 `verifyMs` 를 정확히 재구성한다. 소비자가 이 등식을
신뢰하지 않고 확인할 수 있도록 `verifySumMs` 와 `verifyBreakdownOverMs` 를
함께 공개한다. 이번 실행에서 초과량은 0.0000 ms 다.

timer overhead: expensive verify 1건당 대략 48회 read(`verifyBuffersFor` 2회 ×
약 20회, crop 1회, `ssimBuf` 10회 × 4회), 전체 실행 기준 약 660,000회.
inner loop 안에는 어떤 timer 도 없다. 이 빌드는 자기 timer 비용을 치르므로
**이 수치는 상대적 분포이지 production 성능 주장이 아니다.** `verifyMs` 117,614.6 ms
가 D9a/D9b run 간 범위(109,142–117,291 ms) 안에 있는 점이 그 한계와 일관된다.

## 7. 단계 카운터

```text
verifyBufferLookups    27,468   (= miss 12,949 + hit 14,519)
verifyQuickHashReads   27,468   lookup 당 1회, hit 포함
verifyQuickHashBytes   380,999,408  (363.3 MB, verify 1건당 평균 27,741 B)
verifyDecodes          25,898   (= 2 x 12,949 miss)
verifyCacheCopies      14,519   (= hit)
verifyCropCalls       109,872   (= 8 x 13,734)
verifyFlipCalls       137,340   (= 10 x 13,734)
```

이 카운터에서 두 구조적 사실이 나온다.

1. **cache hit 에도 64KB 를 읽고 해시한다.** 실제 decode 12,949회에 대해
   quick-hash read 가 27,468회다. 즉 key 가 hit 에서도 매번 재구성된다.
   14,519회의 cache hit 을 처리하기 위해 363 MB 를 읽고 해시했다. 비용의
   3.76 % 이므로 실제로는 존재하지만 병목은 아니다.
2. **miss 하나당 같은 파일을 두 번 디코드한다.** `verifyDecodes` 25,898 = 2 ×
   12,949. `verifyBuffersFor` 가 같은 path 에 대해 `decode(path,64,64,f)` 와
   `decodePreserveAspect(path,64,a)` 를 둘 다 호출한다. decode 1회당 4.31 ms
   × 2 가 8.127 ms 다.

## 8. decode 가 4.31 ms 인 이유

D9c 조사 중 `src/image_decoder.cpp` 를 읽은 결과다(보고만, 변경 없음).

- `decodeWicFile` / `decodeWicFileAspect` 는 호출마다
  `CoCreateInstance(CLSID_WICImagingFactory2)` 와 `CreateDecoderFromFilename`
  을 **수행한다.** factory 도, decoder 도, decode 된 frame 도 같은 파일의 두
  호출 사이에 재사용되지 않는다.
- scaler 가 `WICBitmapInterpolationModeFant` 을 쓴다(143행, `decodeWicFileAspect`
  도 동일). 고품질 다운샘플링 모드다.
- EXIF orientation 을 매 decode 마다 조회한다(120행, 168행).
- `IWICBitmapFormatConverter` 로 8bpp gray 변환 후 `CopyPixels`.

64×64 grayscale thumbnail 하나를 이 방식으로 만드는 데 4.31 ms 가 들고,
파일당 두 번 수행된다. D9c 는 이 내부를 더 잘게 측정하지 않았고, 이 코드
독해는 **다음 측정이 어디로 가야 하는지**를 알려준다.

## 10. 한계

- instrumented 빌드이므로 절대 시간에는 timer overhead 가 포함된다. 분포로 쓸 것.
- `frame_ssim` 내부와 `decode` 내부는 분해하지 않았다.
- key 단계는 stat 2회 + 64KB read + FNV 루프가 섞여 있으며, 더 나누지 않았다.
- 한 대의 기계, 한 dataset, 한 실행 구성. 3회 실행이지만 단일 호스트다.
- `8.564 ms/verify` 의 분모는 `verifyBufferLookups / 2`, 즉 buffer 단계까지
  도달한 호출로 유추한 expensive verify 다. D9a 의 13,734 와 정확히 일치한다.

## 1. 변경 필요성

D9c 가 "expensive verify 의 어느 단계가 지배적인가"에 답했고, 그 결과는 이었다.

```text
expensive verify = 8.564 ms
  decode             94.90 %   8.1274 ms/verify
  frame_ssim          0.55 %   0.0470 ms/verify
```

그런데 decode 는 **8.1274 ms 라는 하나의 영역**으로 측정되었다. 이것은
"병목이 decode 다"라는 사실은 알려주지만, 행동하기에는 부족하다. 8.1274 ms 가
decode 2회에 걸린 값이라 1회당 4.31 ms 인데, 코드는 1회당 최소 6개의 분리
가능한 단계를 수행한다.

D9b 의 실패는 "시간이 어디에 쓰이는지 측정하지 않고 단계를 최적화한 것"이었다.
decode 안에서 같은 실수를 반복하는 것이 D9d 가 피하려는 구체적 위험이다.

D9c 는 답하지 못한 두 번째 질문도 남겼다. verify buffer cache 는 프로세스
전역 `std::mutex` 로 보호되는 LRU 인데, D9c 는 lock 대기 시간을 전혀 측정하지
않았다. 여러 스레드가 그 mutex 에 직렬화된다면, per-call 비용이나
`verifyOtherMs`의 일부가 wall-clock 분해에서는 보이지 않는 contention 일 수 있다.

D9c 카운터가 드러낸 구조적 사실 두 가지:

- `verifyDecodes` 25,898 = 2 x 12,949 miss. `verifyBuffersFor` 가 같은 path 에
  대해 `decode(path,64,64,f)` 와 `decodePreserveAspect(path,64,a)` 를 둘 다
  호출한다.
- 64KB quick-hash key 가 **hit 14,519회까지** 매 lookup마다 재구성된다:
  27,468회, 363.3 MB. D9c 는 이를 **낭비라고 단정하지 않았다.** 관찰이며,
  D9c 는 3.76 % 로 측정했다.

## 5. D9d 가설

최적화 관점의 가설은 없다. D9d 는 어느 decode sub-step이 지배적인지 가정하지
않고 각각을 독립적으로 측정한다.

가능한 형태이며, 모두 반증될 수 있습니다.

- WIC factory + decoder COM 생성이 호출마다 이뤄지고, 같은 파일이 miss 마다
  처음부터 두 번 열린다 — 둘 다 큰 비중일 수 있다.
- `WICBitmapInterpolationModeFant` 다운스케일이 유의미할 수도, 아닐 수도 있다.
- EXIF metadata 조회는 작을 수 있다.
- cache mutex contention 이 0 근처라면, 모호하게 두지 않고 **명시적으로
  우선순위를 낮춘다** 고 기록한다.

## 6. 주요 계측 대상 — decode 내부

실제 call path 는 이름에서 추론하지 않고 소스에서 읽었다.

```text
ImageDecoder::decode(path,w,h,out)                     (image_decoder.cpp:241)
  MultiByteToWideChar
  CoInitializeEx
  decodeWicFile(wpath,w,h,out)                          (:90-154)
    CoCreateInstance(CLSID_WICImagingFactory2)
    CreateDecoderFromFilename                          <- file open + decoder
    GetFrame(0) + GetMetadataQueryReader
    GetMetadataByName(/app1/ifd/exif/{ushort=274})      <- EXIF orientation
    CreateBitmapFlipRotator + Initialize                (xform != 0 일 때만)
    CreateBitmapScaler + Initialize(..., Fant)          <- Fant
    CreateBitmapFormatConverter + Initialize(8bppGray)  <- format conversion
    CopyPixels                                         <- pixel copy
  decodePgm fallback (WIC 실패 시에만)

ImageDecoder::decodePreserveAspect(path,maxDim,out)    (:254)
  decodeWicFileAspect(wpath,maxDim,out)                 (:155-195)
    동일한 여섯 WIC 단계, GetSize 기반 aspect 계산
  decodePgmAspect fallback
```

위 코드 구조를 기준으로 계측할 경계:

```text
decodeTotalMs / decodeCount                      (decode)
decodePreserveAspectTotalMs / ...Count           (decodePreserveAspect)
  ├─ comInitMs         CoInitializeEx
  ├─ factoryMs         CoCreateInstance(WIC factory)
  ├─ openMs            CreateDecoderFromFilename
  ├─ metadataMs        GetFrame + GetMetadataQueryReader + GetMetadataByName
  ├─ orientMs          CreateBitmapFlipRotator + Initialize
  ├─ resizeMs          CreateBitmapScaler + Initialize (Fant)
  ├─ convertMs         CreateBitmapFormatConverter + Initialize
  ├─ copyMs            CopyPixels
  └─ otherMs           WIC 함수 내부의 나머지
```

두 WIC 본문이 거의 같더라도 `decode` 와 `decodePreserveAspect` 는 **항상** 별도로
보고한다.

**분리 불가하며 그렇게 보고한다:** 실제 lazy decode. WIC 는 `CopyPixels` 중에
디코딩하므로 "decode" 와 "copy" 는 측정 대상 코드를 바꾸지 않고는 나눌 수 없다.
따라서 `copyMs` 버킷 안에 실제 이미지 decode 가 들어 있다. 숫자를 잘못 읽지
않도록 이 사실을 기록한다.

PGM fallback 은 카운트만 하고 분해하지 않는다. WIC 실패 시에만 실행된다.

## 7. 보조 계측 대상 — cache mutex

```text
cacheMutexAcquires
cacheMutexWaitMs      lock 획득 전 대기 시간
cacheMutexHoldMs      lock 보유 시간
```

`verifyBuffersFor` 의 기존 lock 지점 두 곳에서 측정한다(조회 경로, insert/evict
경로). wait 와 hold 는 판정이 비율에 의존하므로 별도로 보고한다.

```text
hold 작고 wait 큼  -> contention 이 실제 후보
hold 작고 wait 작음 -> mutex 는 병목 아님
```

mutex 구현은 **변경하지 않으며**, lock scope 도 옮기지 않는다.

## 8. Scope

다음을 허용한다.

```text
timing instrumentation
counter instrumentation
profiling telemetry
benchmark reporting
instrumentation 을 검증하는 test
```

timer 는 측정하는 호출 바깥에 둔다. `AnalyzeTelemetry` 와 `BenchmarkRecorder`
는 D9c 패턴대로 제자리 확장한다. core 가 채우는 단순 데이터 운반체를 유지하고,
recorder 포인터가 decode 코드로 들어오지 않게 한다.

## 9. Non-goals

D9d 에서 **하지 않는다.**

```text
같은 파일의 중복 decode 제거
decode cache 추가
decoder / WIC factory 재사용
EXIF skip 또는 지연
Fant 를 다른 interpolation 으로 변경
resize 또는 그 quality 변경
format conversion / pixel copy 제거
decode 안의 buffer reuse
cache mutex 의 구조/scope/존재 여부 변경
quick-hash 변경
frame_ssim 최적화, early exit, window, precision 변경
parallelization 또는 thread scheduling 변경
candidate, threshold, grouping, verdict 변경
```

window size, precision, early-exit, sampling 은 별도로 관리하는 저우선순위
후보다.

## 10. 정확성 / verdict 위험

instrumentation 은 어떤 결과도 바꾸지 않아야 한다.

- `verifyCalls`, expensive verify count, `verifyDecodeMisses`,
  `verifyCacheHits`, `ssimEvals`, `frameSsimEvals`, `groups`, 최종 verdict 가
  동일 dataset 에서 D9a 기준과 동일해야 한다.
- `verify_parity_test` 계속 통과 (25 checks, 보존된 pre-D9b reference 와
  double 동일).
- 추가 assertion: instrumented / uninstrumented decode 가 동일한 `GrayImage`
  를 낼 것, decode sub-stage 시간 합이 계측 total 이하일 것.
- 새 필드를 추가한 뒤에도 D9c 의 exclusive 합계 등식이 유지될 것.

## 11. 호환성 위험

analyze 블록에 필드가 더 늘어난다. 이것은 가정하지 않고 D9d 전에 이미 결론을
내렸다. `kBenchmarkSchemaVersion` 은 **9 유지**다. 스키마가 additive 임이
`msf_benchmark_schema_test` (29 checks, `additive-read-confirmed`) 로 증명되기
때문이다. 그 테스트는 실제 record 를 GUI 와 동일한 `QJsonDocument` 접근
패턴으로 파싱해, 새 필드가 있어도/없어도 pre-D9c 필드가 동일하게 읽힌다��
확인한다. D9d 는 같은 종류의 필드를 더 추가하며 상수는 바꾸지 않는다.

## 12. 측정 계획

- D9a/D9b/D9c 와 동일한 dataset, fingerprint, 하드웨어, GPU, 설정, cold-index
  조건.
- **동일 조건 최소 5회** 실행 (D9a 는 2회, D9b/D9c 는 3회). 단계별로
  **median, min, max, range** 를 보고한다. 평균만 내면 7.5 % 편차가 가려지므로.
- 분포에 중점: decode sub-step 별 호출당 비용, mutex wait/hold 비율, 내부
  비중. 절대 합계는 2순위다. 빌드가 자기 timer 비용을 치르므로.
- 7.5 % noise 환경에서 1~2 % 차이는 개선으로 선언하지 않는다.

## 13. timer 의미

exclusive 이며 비중복. D9c 와 동일하다.

```text
decodeTotal = comInit + factory + open + metadata + orient
            + resize + convert + copy + other
```

`otherMs` 는 WIC 함수 내부의 나머지이며, D9a 의 `scanMs` 와 D9c 의
`verifyOtherMs` 와 같은 정의다. timer 범위가 잘못되면 그럴듯한 잘못된 분해가
아니라 음수 또는 과도한 나머지로 나타난다.

mutex wait/hold 는 decode 합계의 일부가 아니다. lock 은 decode 가 아니라 map
조회 중에 보유되므로 별도로 보고한다.

어떤 inner loop 안에도 timer 를 넣지 않는다. `frame_ssim` 의 4,096회 반복
body 는 건드리지 않는다.

## 14. noise 고려

D9a 에서 약 7.5 % run 간 편차가 관측됐다. 따라서 D9d 는:

- 5회 이상 실행하고 median/min/max/range 를 보고한다;
- 두 단계의 median 차이가 관측 range 안에 있으면 순위를 매기지 않고
  **동률로 보고**한다;
- 절대 ms 보다 호출 횟수가 결정적이므로 per-call 비중을 우선한다.

## 15. 중단 조건

다음이면 범위를 줄이거나 중단하고, 고쳐 돌리지 않고 기록한다.

```text
1. instrumentation 이 verdict 또는 grouping 을 변경
2. CPU/GPU parity 파괴
3. 기존 test 실패
4. timer overhead 과도
5. 단계 시간이 중복되어 해석 불가
6. decode path 를 정확히 분리할 수 없음
7. 새 필드가 schema 호환성 결론과 모순
8. 기존 test 를 삭제하거나 완화
9. 값을 추정해야만 채울 수 있는 상황
```

## 16. D9c 에서 유지하는 것

D9c instrumentation 은 이 빌드에 **유지**한다. D9b 시대의
`verifyScorePlan` / `verifyScorePlanReference` / `verifyImagePairReference`
역시 의도적으로 유지한다. 계측 격리, 이력 추적성, 실험 재현성을 위해서다.
profiling timer 를 최종적으로 production path 에 남길지는 D9d 와 별개인
housekeeping 결정이다.

## 17. 기대 결과

성공은 speedup 이 아니다.

```text
1. decode 내부 비용이 의미 있게 분해됨
2. decode / decodePreserveAspect 가 별도로 보고됨
3. mutex wait/hold 가 측정되거나 측정 불가 사유가 기록됨
4. verdict 보존
5. grouping 보존
6. CPU/GPU parity 유지
7. 기존 test 전부 PASS
8. dataset 조건 재현
9. timing semantics 문서화
10. 다음 후보를 증거로 선정 가능
```

최종 상태는 PASS / PARTIAL / INCONCLUSIVE / FAIL 중 하나이며, 기준은
instrumentation 목적 달성 여부다. 성능 변화가 없는 빌드가 FAIL 은 아니다.

## 18. 여기서 결정하지 않는 것

D9d 이후 어떤 최적화를 할 것인가. 별도 pre-register, 별도 version, hypothesis,
정확성 위험, 측정 계획이 필요하며, **D9d 가 실제로 측정한 비용만 근거로**
선정한다. "이 코드가 느려 보인다"는 이유로 선정하지 않는다.

후보 A(candidate 도착률 감소)는 계속 deferred 다. candidate recall,
false positive/negative 위험, verdict semantics 를 접촉한다.
