## 1. Why the Change Was Needed

Node E exists to reduce "the cost of decoding more frames than requested". But
**that premise has never actually been measured.** The telemetry the roadmap
requires (requested sample frames, seek count/latency, keyframe/GOP cost, decode
throughput) **does not exist as fields.** Before E-2 can be implemented, the
premise must be measured.

## 3. New Structure — this version changes no production code

A measurement-only probe is added under `tests/`. No production behaviour
change, no hardware decode path wired up, no `av_hwdevice_*` call.

### 3.1 The probe, and why it can be trusted

`tests/video_decode_planner_probe.cpp`

- The sampling plan calls the **real production function** `msf::make_sample_plan`.
- The decode loop is an instrumented mirror of `video_decoder.cpp:94-140`: same
  single backward seek, same 0.05 s tolerance, same `SWS_BILINEAR` 96x96 gray,
  same 3x3 box mean.
- **Verification**: the 32x32 frames the probe produces are compared **byte for
  byte** against the output of the real production
  `VideoDecoder::framesAt96Plus32`.

```text
probe_matches_production_frames = yes (8/8 files byte identical)
```

Without that check the probe would be measuring only a re-implementation, which
is exactly the defect the I-2 probe was corrected for. A mismatch is reported as
a mismatch, never averaged away.

### 3.2 Dataset

The standard dataset was **not modified**. A separate reference dataset was
created (`C:\project\validation\video_dataset`, gitignored):

```text
mpeg4  640x360   25fps   5s / 30s / 300s   software, inter-frame
mpeg4  1920x1080 25fps   30s
mpeg4  640x360    5fps   30s
mpeg4  640x360   60fps   30s
h264   640x360   25fps   30s   (h264_mf, MediaFoundation hardware encoder)
ffv1   640x360   25fps   30s   (intra-only → every frame is a key frame)
```

### 3.3 Dataset constraint — recorded as a constraint, not a result

The bundled FFmpeg 9.0.1 has **no software encoder for H.264, HEVC, VP9 or AV1**:

```text
available : mpeg4, ffv1 (software), h264_mf (hardware, verified working)
absent    : libx264 libx265 libvpx-vp9 libaom-av1  ← not in this build
failed    : hevc_mf, av1_d3d12va, av1_mf, hevc_d3d12va
```

Per directive §8, HEVC/VP9/AV1 are **not force-included**; their absence is
recorded as a constraint. Resolving it requires a dependency change, which §31
forbids.

## 4. What Was Resolved — measurement results

### 4.1 Headline: 12,573 frames decoded to produce 140 samples

```text
total_frames_actually_decoded   = 12,573
total_frames_emitted_at_samples =    140
decoded_over_emitted_ratio      = 89.81x
```

| file | codec | fps | dur | planN | decoded | emitted | ratio | keys |
|---|---|---|---|---|---|---|---|---|
| mpeg4_640x360_05fps_030s | mpeg4 | 5 | 30s | 16 | 150 | 15 | 10.0x | 13 |
| mpeg4_640x360_25fps_005s | mpeg4 | 25 | 5s | 6 | 125 | 6 | 20.8x | 11 |
| mpeg4_640x360_25fps_030s | mpeg4 | 25 | 30s | 16 | 750 | 16 | 46.9x | 63 |
| mpeg4_640x360_25fps_300s | mpeg4 | 25 | 300s | 39 | 7500 | 39 | **192.3x** | 625 |
| mpeg4_640x360_60fps_030s | mpeg4 | 60 | 30s | 16 | 1798 | 16 | 112.4x | 150 |
| mpeg4_1920x1080_25fps_030s | mpeg4 | 25 | 30s | 16 | 750 | 16 | 46.9x | 63 |
| h264_640x360_25fps_030s | h264 | 25 | 30s | 16 | 750 | 16 | 46.9x | 15 |
| ffv1_640x360_25fps_030s | ffv1 | 25 | 30s | 16 | 750 | 16 | 46.9x | 63 |

**Node E's premise is confirmed by measurement.** One 300 s 25 fps file decodes
7,500 frames to obtain 39 samples — a factor of 192.3.

### 4.2 Time decomposition — what is worth optimising

```text
decode     3,086.7 ms   97.57 % of sweep
convert       29.8 ms    0.94 %
open           7.9 ms    0.25 %
seek           0.1 ms    0.003 %   (one per sweep, by construction)
decode share of (open + decode) = 99.75 %
```

**Decode is 97.6 % of the cost.** Conversion, open and seek are not worth
planning against at this scale. This follows the directive's §12 instruction not
to invent stages that do not exist.

### 4.3 H1 — the ratio is not an independent variable; it is fps × interval(duration)

```text
file                              fps interval      pred  measured     err%
mpeg4_640x360_05fps_030s          5.0        2      10.0      10.0      0.0 %
mpeg4_640x360_25fps_005s         25.0        1      25.0      20.8    -16.7 %
mpeg4_640x360_25fps_030s         25.0        2      50.0      46.9     -6.3 %
mpeg4_640x360_25fps_300s         25.0        8     200.0     192.3     -3.8 %
mpeg4_640x360_60fps_030s         60.0        2     120.0     112.4     -6.4 %
mpeg4_1920x1080_25fps_030s       25.0        2      50.0      46.9     -6.3 %
h264_640x360_25fps_030s          25.0        2      50.0      46.9     -6.3 %
ffv1_640x360_25fps_030s          25.0        2      50.0      46.9     -6.3 %

mean |error| = 6.48 %
```

`decoded_over_emitted` is not a measurement target but a **function of fps and
duration**. The §9 candidate list's "estimated frame count" and "sampling count"
are **derived values, not independent inputs.**

### 4.4 H2 — per-frame cost is determined by codec × resolution

```text
file                         codec          px   decoded  decode_ms  ms/frame
mpeg4_640x360_05fps_030s     mpeg4      230400      150       18.3     0.1221
mpeg4_640x360_25fps_005s     mpeg4      230400      125       13.9     0.1112
mpeg4_640x360_25fps_030s     mpeg4      230400      750       81.2     0.1082
mpeg4_640x360_25fps_300s     mpeg4      230400     7500      768.5     0.1025
mpeg4_640x360_60fps_030s     mpeg4      230400     1798      195.3     0.1086
mpeg4_1920x1080_25fps_030s   mpeg4     2073600      750      747.8     0.9970
h264_640x360_25fps_030s      h264      230400      750      144.0     0.1921
ffv1_640x360_25fps_030s      ffv1      230400      750     1117.6     1.4902

grouped:
  mpeg4 640x360   n=5  0.1025 ~ 0.1221  spread 19.2 %   <- fps/duration barely matter
  mpeg4 1920x1080 n=1  0.9970
  h264  640x360   n=1  0.1921
  ffv1  640x360   n=1  1.4902
```

- At the same codec and resolution, even with **5× the fps and 60× the
  duration**, the per-frame cost stays within **19.2 %** → fps and duration do
  not enter the cost directly.
- 640x360 → 1920x1080 is 9.0× the pixels and **9.2×** the cost. **Linear in
  pixel count.**
- Codec differences are large: mpeg4 0.108 → h264 0.192 (1.8×) → ffv1 1.490
  (**13.8×**). ffv1 is intra-only, which is reflected directly.

This is the measured basis of the cost model:

```text
SoftwareDecodeCost ≈ framesDecoded × msPerFrame(codec, resolution)
framesDecoded     = fps × duration          (H1, matches measurement)
msPerFrame        = f(codec, resolution)    (H2, per codec·resolution group)
```

## 5. Planner Inputs Fixed (Gate C)

Of the 18 §9 candidates, applying the §10 rule ("keep only variables that
explain decode time or end-to-end time").

### 5.1 Adopted — 5

| input | Evidence | State |
|---|---|---|
| `duration` | selects the interval bucket, hence the sample count | measured |
| `fps` | framesDecoded = fps × duration, hence the waste ratio | measured |
| `resolution` | determines msPerFrame (linear in pixels) | measured |
| `codec` | determines msPerFrame (1.8–13.8× across mpeg4/h264/ffv1) | measured |
| `keyframe interval (GOP)` | required for the sparse-seek cost | **partial** — see §7 |

### 5.2 Excluded — with reasons

| Excluded candidate | Reason |
|---|---|
| `estimated frame count` | **derived** from fps × duration. Proven by H1 |
| `sampling count` | **derived** from duration |
| `container` | not separable at fixed codec and resolution in this dataset (mp4/mkv vary together with codec) |
| `pixel format` | the whole dataset is yuv420p. **No variation, so unevaluable** → retained as a future candidate, not a current input |
| `bit depth` | no 10-bit content. **unevaluable** |
| `file size` | 5.2–6.2 MB range; not separable from duration/resolution/codec |
| `seek distance` | always 1 today. **degenerate** |
| `CPU mode` / `CPU live load` | no measurement basis in E-1. §10 and directive §3 forbid adding them by guesswork |
| `GPU ON/OFF` / `GPU capability` | same. Directive §3 explicitly forbids a "GPU available = choose GPU" rule |
| `expected transfer cost` | not measurable before F |

**18 candidates → 5.** The reduction §10 called for is realised.

## 6. Planner Model Design (Gate D)

Design only; not implemented. The enum and struct names below are to be
minimised against the real code at E-2 implementation time.

### 6.1 Output

```text
VideoDecodePlan
{
    samplingMode    SequentialSweep | SparseSeek
    backend         Software | HardwareCandidate
    expectedCostMs  estimate
    fallbackPolicy  FallbackToSoftware
    reason          enum below
}
```

### 6.2 Decision structure

```text
wasteRatio := fps × interval(duration)        (H1, mean error 6.48 %)
frameCost  := msPerFrame(codec, resolution)   (H2, measured)
gop        := keyframe interval               (source unconfirmed — §7)

if GPU == OFF                -> Software / SequentialSweep / reason=GPU_OFF
if no hardware capability    -> Software / SamplingDecision / reason=NO_HW_CAPABILITY
if wasteRatio < 1.5          -> SequentialSweep  (current behaviour already near optimal)
if gop < 0.5 × wasteRatio    -> SparseSeek strongly favourable, independent of backend
if gop ≈ wasteRatio          -> boundary case, needs measurement
```

**Important**: the `gop < 0.5 × wasteRatio` branch works **with no hardware
decoder at all** — it is a pure software sampling-strategy change. See §10.

### 6.3 Reason codes

```text
GPU_OFF / NO_HW_CAPABILITY / SHORT_VIDEO / LOW_SAMPLING_DENSITY /
SEQUENTIAL_SUFFICIENT / HIGH_TRANSFER_COST / CPU_SOFTWARE_PREFERRED /
HARDWARE_CANDIDATE
```

No UI exposure; development telemetry level is sufficient.

## 7. Measurement Limitations — must be read alongside the above

1. **The dataset is 8 synthetic lavfi files.** Not real-world content. No
   bitrate distribution, scene cuts, noise or real camera noise.
2. **Only 3 codecs.** HEVC, VP9 and AV1 cannot be generated in this FFmpeg build
   (§3.3). **The codec family where modern decode differs most is missing.**
3. **The GOP input is not trustworthy.** ffv1 is intra-only, yet the measurement
   reports 63/750 (it should be all of them). `AV_PKT_FLAG_KEY` is therefore
   inaccurate for ffv1-in-matroska. **A different source is needed before GOP can
   drive a cost model.**
4. **Only 2 GOP data points** (mpeg4 ≈ 11.9, h264 = 50.0), each n=1, so the
   distribution is unknown.
5. **The sparse-seek saving is arithmetic, not measurement.** See §8.
6. Every file is ≤300 s and ≤1080p. The `interval = 32` bucket (>3840 s) was
   verified **only arithmetically** in the selfcheck, never measured.
7. Cold and warm file cache were not separated.

## 8. Sparse-Seek Model — Arithmetic, Not Measurement

The following is **arithmetic over measured inputs, not a measured result.**

Assumption: seeking to a target requires decoding from the previous key frame,
so the expected extra frames per sample is `GOP/2`. **This assumption is not
verified here.**

| file | seqFrm | smp | gop | sparseFrm | model saving |
|---|---|---|---|---|---|
| mpeg4_640x360_05fps_030s | 150 | 15 | 11.5 | 87 | 42.3 % |
| mpeg4_640x360_25fps_005s | 125 | 6 | 11.4 | 34 | 72.7 % |
| mpeg4_640x360_25fps_030s | 750 | 16 | 11.9 | 95 | 87.3 % |
| mpeg4_640x360_25fps_300s | 7500 | 39 | 12.0 | 234 | 96.9 % |
| mpeg4_640x360_60fps_030s | 1798 | 16 | 12.0 | 96 | 94.7 % |
| h264_640x360_25fps_030s | 750 | 16 | 50.0 | 400 | 46.7 % |
| ffv1_640x360_25fps_030s | 750 | 16 | 11.9 | 95 | 87.3 % |

The condition is `GOP < 2 × fps × interval`, and all eight cases satisfy it.

## 9. E / F Boundary (Gate E)

```text
E = decision / planning     how this video should be decoded under these conditions
F = implementation          how the chosen hardware decode is actually wired up
```

- E-1 **never called** `av_hwdevice_*`. Querying capability (a fact) and using
  hardware decode (F) are different things.
- Per §12, **no "GPU available = choose GPU" rule was created.**
- Hardware capability, device and frame configuration each need their own
  decision, and FFmpeg's official API makes `avcodec_get_hw_config()` a
  prerequisite.
- **No hardware values were fabricated.** F has not happened, so they are not
  measurement targets.
- The fallback contract is identical in E and F:

```text
HardwareCandidate → (no backend) → FallbackRequired → SoftwareDecode
```

The CPU fallback is never removed under any condition.

## 10. The Most Important Finding: a Reframing

Node E is named "Adaptive Video **Decode** Planner". The measurement shows there
is a **larger** issue inside node E that has nothing to do with hardware decode:

```text
measured waste = 89.81x  (12,573 frames decoded for 140 samples)
that waste is a SAMPLING-STRATEGY problem, independent of any hardware backend
```

So the decision must be split in two:

```text
(1) how many frames to decode   -> samplingMode, E-2, achievable with software alone
(2) who decodes them            -> backend,     F,    requires hardware
```

On the current data (1) is far larger than (2). This means E-2 has value without
hardware. It does **not** argue for reordering E and F — F is still needed — but
it is recorded as the **evidence that (1) should be E-2's first priority.**

## 12. Next Steps

```text
E-2  Adaptive Video Decode Planner implementation
      └─ implement and measure (1) sampling mode first (Sequential vs SparseSeek)
      └─ then add the (2) backend decision structure, software only
E-3  calibration / validation
F     Hardware Video Decode Backend
```

Before starting E-2, three things need resolving:

1. **A trustworthy GOP source.** `AV_PKT_FLAG_KEY` is inaccurate for ffv1.
   Container index information or a decoder-level measurement is needed.
2. **A real-content dataset.** Eight synthetic lavfi files do not make codec
   cost differences representative. Either expanding codec support (a dependency
   change) or obtaining externally supplied content.
3. **A measured sparse seek.** §8 is arithmetic. It must be implemented and
   measured.
