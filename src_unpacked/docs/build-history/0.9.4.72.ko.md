# MediaSimilarityFinder v0.9.4.72 — 스캔 정체 수정(walk/analyze 병렬화) + 표시/ETR 결함

기준선 `0.9.4.71` → 본 빌드 `0.9.4.72`.
CPU CTest **116/116**, GPU CTest **117/117**.
`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.4` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — 전부 불변. 검색 판정 의미·동작 변경 없음.

## 1. 변경 필요성

사용자 보고: 스캔 중 프론트엔드/백엔드 CPU 점유율이 **<1%**, ETR이 **7000분+**,
화면이 **0%에서 멈추고 "읽기 완료"가 정지**. "스케줄러 CPU 할당"을 의심.

headless `--scan`으로 **실제 정체를 재현**했다(표시 문제가 아님):

- dataset A(`G:\Downloads\ss_twit`, 273k 파일, 지연 큰 드라이브): walk 단계에서
  ~105–166 파일/s, `done=0`, CPU ~6%, 150초 동안 analyze 도달 실패.
- dataset B(`D:`, 16×16 근접-중복 이미지 20,000장, SSD): walk 6.3초로 빠르지만
  **analyze가 126.5초**(분해: `cand=199,990,000`, `scanMs=101.7s`,
  `verifyMs=4.9s`).

두 정체 모두 **단일 스레드(~1코어)** 구간이다. `CpuGpuScheduler`는 배치 단계의
이미지 해싱 CPU/GPU 분배만 담당하므로 스케줄러를 봐도 정상으로 보인다.
별도로 표시/공식 결함 2건(백엔드 CPU/RSS가 0으로 덮임, ETR 순수 선형 외삽)도
함께 수정한다.

## 2. 기존 구조

- **walk**: `Scanner::scan_stream`이 모든 미디어 파일마다 `quick()`(앞 64KB를
  FNV 해시)을 **단일 스레드**로 계산한다(초기 커밋 `3b3e096`부터). 파일당
  open+read 지연이 지배해 저속/대량 트리에서 walk 전체가 1코어에 직렬화된다.
- **analyze**: `ScanPipeline::analyze`의 후보 쌍 루프(`consume`→`process`)가
  **단일 스레드**다. 후보가 많은(근접-중복) 데이터에서 `bestMatch` 재계산이
  한 코어에 몰린다. video temporal 단계만 이미 병렬(flushVideo)이었다.
- **표시**: `BackendSupervisor::dispatchEvent`의 `kStatus`(~5Hz, match 도착)가
  `BackendStatus st;`를 새로 만들어 `backendCpu/backendRssMB`를 0으로 덮었다.
  실제 CPU/RSS는 `kHealth`(1Hz)만 전달하므로 표시가 대부분 0%로 진동했다.
- **ETR**: `MainWindow::scanStatusText`가 `elapsedMs*(total-done)/done` 순수
  선형 외삽. 초반 `done`이 수 개일 때 7000분대가 산출됐다.

## 3. 변경 구조

- **walk 병렬화 (`src/scanner.cpp`)**: `scan_stream`이 열거·메타데이터는 이
  스레드에서 유지하되, `quick()` 64KB 읽기만 **bounded pool(≤8)**로 배치(256)
  단위 팬아웃한다. 배치는 **열거 순서대로 flush**되어 발행 순서(따라서 결과·
  진행·결정성)가 불변이다. worker는 예외로 종료되지 않는다(실패는 빈 해시).
- **analyze 병렬화 (`src/scan_pipeline.cpp`, `src/candidate_index.*`)**:
  `CandidateIndex::groupBoundaries()` + `forEachCandidatePairInRange()`를 추가해
  외부 엔트리 범위를 **그룹(파일) 경계**에서 분할한다. 각 unordered pair는 더
  작은 엔트리가 한 번만 방출하므로 경계 정렬 샤드는 쌍 집합을 중복·누락 없이
  분할한다. worker는 thread-local 카운터·텔레메트리·match 버퍼를 갖고, 샤드를
  **순서대로 병합**해 방출 match 순서·카운터·텔레메트리 합이 순차 실행과
  동일하다(판정 패리티·결정적 순서).
- **텔레메트리 병합 (`src/analyze_telemetry.h`, `src/image_decoder.h`)**:
  thread-local 텔레메트리를 더하는 `addAnalyzeTelemetry`/`addDecodeTelemetry`
  추가. D9a 불변식(`index+scan+verify+video == total`)을 유지하기 위해 병렬
  verify 벽시계 합을 잔여 예산으로 **cap**한다(초과 시 scan=0).
- **표시 수정 (`gui/backend_supervisor.cpp`)**: `kStatus` 분기가 `BackendStatus
  st = lastStatus_;`로 Health 샘플 CPU/RSS를 승계한다.
- **loopback 표시 (`gui/backend_loopback.cpp`)**: statusSnapshot 람다가
  `msf::sampleOwnProcess`로 GUI 프로세스 CPU/RSS를 채운다(loopback에 Health
  ticker가 없음).
- **ETR 가드 (`gui/mainwindow.cpp`)**: `elapsedMs<3000 || done==0 || total<=done`
  또는 `done < max(20, total/50)`이면 ETR을 숨긴다.

## 4. 해결된 상황

- 지연 큰 드라이브/대량 트리에서 walk가 1코어에 직렬화되지 않는다.
  실측: G: 읽기 처리량 **~10.6MB/s → ~55MB/s(약 5배)**, ~166 → ~880 파일/s.
- 근접-중복 데이터에서 analyze의 `bestMatch`/verify가 여러 코어로 분산된다.
  실측(ds2, 2억 쌍): analyze 101.7s → 87.9s(이 케이스는 match 방출이 지배).
  후보는 많고 match는 적은 실제 데이터에서 병렬 이득이 더 크다.
- 스캔 중 CPU/RAM 표시가 실제 작업 프로세스 값을 유지한다(0% 진동 제거).
- 초반 ETR 폭주(7000분대)가 사라진다.

## 5. 검증

### 재현 계측 (0.9.4.72)

- dataset A(G:, 지연 드라이브, 이미지 전용 재스캔): walk 읽기 처리량
  수정 전 ~10.6MB/s → 수정 후 ~55MB/s. 프로세스 CPU는 I/O-bound로 여전히 낮으나
  완료 시간이 크게 단축된다.
- dataset B(D:, 16×16 근접-중복 20,000장): phase 계측에서 walk 0.1→1.0s,
  analyze 1.1→89.0s(수정 전 101.7s), `cand=199,990,000`.
- D9a 불변식: `index+scan+verify+video`가 analyze total을 넘지 않도록 verify를
  cap. `analyze_telemetry_test`의 `substage sum <= analyzeMs` 검사 통과.

### 성능 실험 색인 (AGENTS 9항)

- **Experiment ID**: P-0.9.4.72-walk-parallel, P-0.9.4.72-analyze-parallel
- **Version**: 0.9.4.72. **Date**: 2026-10-08.
- **Purpose**: 스캔 정체(저 CPU·장시간)의 실제 원인 규명 및 완화.
- **Hypothesis**: walk의 파일별 64KB 읽기와 analyze의 후보 쌍 루프가 단일
  스레드라 코어를 쓰지 못하고 완료가 지연된다.
- **Baseline**: 미수정 0.9.4.72(=0.9.4.71 walk/analyze 경로).
- **Dataset**: A `G:\Downloads\ss_twit`(273k 파일, 평평한 구조), B
  `D:\Temp\OpenCodeWork\ds2`(16×16 근접-중복 20,000장).
- **Hardware/OS**: Windows, 로컬. Build configuration: CPU/GPU Release.
- **Run count**: 각 조건 반복 계측(3초 샘플). 단일 실행 대표값.
- **Raw measured**: A walk 읽기 ~10.6MB/s(미수정, 166 files/s) → ~55MB/s
  (수정, 880 files/s). B analyze 101.7s(미수정) → 87.9s(수정).
- **Verdict / Status**: PASS(walk), PASS(analyze, 병리적 match 폭증 케이스는
  개선폭 제한). Accuracy/verdict parity: CTest 전수 통과로 확인.
- **Known limitation**: 병렬 벽시계 합을 verifyMs에서 cap하므로 병렬 포화 시
  D9c 분해 정합은 근사다. HDD에서는 8-way 병렬 읽기의 seek 비용으로 이득이
  줄 수 있다(SSD/NVMe 기준).
- **Future revisit condition**: HDD/네트워크 공유 대상 walk 병렬도 재조정,
  match 방출 경로(engine onMatch)의 병목화 시 그쪽 병렬화.

## 6. 향후 영향

- 실제 GUI 육안 acceptance는 여전히 필요하다(미리보기, selection, Tiles/List,
  대규모 dataset traversal).
- analyze 병렬화는 `ScanPipeline::analyze`를 쓰는 모든 경로(revalidate, monitor
  compare 포함)에 적용된다. 순차 경로와 판정·순서가 동일함을 CTest가 보장한다.
- headless `--scan`은 `retainMatches` 기본값으로 2억 match 같은 병리적 데이터에서
  메모리가 폭증할 수 있다(GUI `ScanWorker`는 `retainMatches=false`). 별도 항목.
- HDD 대상 walk 병렬도는 재검토 조건으로 남긴다.
- `ExactnessPolicy::RefuseAll` 유지, Node E 종결 상태 불변.
