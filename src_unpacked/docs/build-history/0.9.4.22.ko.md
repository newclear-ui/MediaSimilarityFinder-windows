# MediaSimilarityFinder v0.9.4.22 — D8b Scaled Dataset / Walker Queue Evidence

D8b 진입. **성능 최적화가 아니다.** D8a가 만든 재현성 기반 위에서
"실제 규모에서 walker queue가 어떻게 behave하는가"를 **측정**해
D4b / Full D3 판단의 근거를 얻는 단계다.
엔진 1.5.0·DB 1.0.3·캐시 v9 불변, benchmark schema 8 유지(키 추가 없음).

> 이 문서는 **fixture 변경 전에** 작성되어 커밋 순서로 감사 가능하다.
> 실제 수치(fileCount / totalBytes / fingerprint / queue 관측)는 fixture를
> 만든 뒤에만 채운다.

**D8b implements no optimization. It measures the existing structure at a
realistic scale so the D4b / Full D3 decisions rest on evidence instead of on
a 60-file extrapolation.**

## 1. 왜 D8b가 필요한가

0.9.4.21(D8a)의 dataset 은 **재현성/parity 용 최소 fixture** 로 의도적으로
작다: 8×8 24-bit BMP **60개, 총 14,760 바이트, 디렉토리 2개**.

이 dataset 으로 5회 반복 측정한 결과(v0.9.4.21 상태):

```
walker_queued/dequeued   60 / 60      손실 0
walker_max_depth         1            capacity 4096 의 0.024%
blocked_ticks            0
starved_ticks            0
gpu_batch_share_of_wall  0.34%        (gpuBatchMs 0.469ms / wall 136.1ms)
```

이 수치는 **"D4b / Full D3 불필요"의 증거로 쓸 수 없다.** 이유는
dataset 이 파이프라인의 실제做任何 일도 하지 않기 때문이다:

- 8×8 이미지는 decode·crop·thumbnail 비용이 사실상 0
- 디렉토리가 2개뿐이라 directory walk 비용이 사실상 0
- 그 결과 producer 와 consumer 가 둘 다 즉시 끝나서
  queue depth 1 이라는 **구조적 결론이 아니라 dataset 크기 탓**

즉 "이득 없다"는 판정이 **측정 대상 부재**에서 온 것이다.
D8b 는 그 대상을 만든다.

## 2. 현재 구조에서 확인된 사실 (코드 근거)

`src/media_search_engine.cpp` 604-634 행:

- **producer** = 별도 walker thread. `Scanner::scan_stream` 이 `onFile` 로
  push 만 한다 (622 행 이전).
- **consumer** = **단일 스레드**. `while(...) { queue.waitForData(50);
  queue.tryPop(x); processOne(std::move(x)); }` — 한 번에 **1개만** pop 하고
  동기적으로 `processOne` 을 수행한다.
- `processOne` 은 `imageBatch` 에 누적하고 `size() >= gpuBatch` 일 때만
  `processImageBatch` 로 flush 한다.

이 구조상 consumer 가 file 단위 동기 처리이므로, **consumer 처리 비용이
producer walk 비용보다 크면 queue 가 깊어진다.** D8a dataset 은 양쪽 비용이
모두 0 에 가까워서 depth 1 이었다.

따라서 D8b dataset 은 **두 축**으로 deliberately 비대칭을 만든다:

1. **walk 축** (`tree/`) — 여러 디렉토리에 분산된 다수 파일.
   producer(disk enumeration) 비용을 실제로 발생시킨다.
2. **decode 축** (`bulk/`) — 현실 크기 이미지.
   consumer(decode + crop + color thumbnail) 비용을 실제로 발생시킨다.

## 3. Dataset 구성 (v2)

기존 `images/exact` 48 + `images/varied` 12 는 **그대로 유지**한다
(D8a 에서 기록한 fingerprint 와의 연속성·parity 회귀 기준 보존).

추가:

| 경로 | 개수 | 크기 | 목적 |
| --- | --- | --- | --- |
| `tree/lN/MM/lNNN.bmp` | 2400 | 8×8 (246 B) | 디렉토리 spread → walk 비용, queue depth |
| `bulk/bNNNN.bmp` | 240 | 256×192 (147,510 B) | decode/crop/thumbnail 비용, GPU batch share |

합계: 60 (기존) + 2400 + 240 = **2700 files**

근거:

- 2400 을 여러 하위 디렉토리에 분산시켜 한 디렉토리의 entry 수가 작게
  유지되도록 한다. 그래야 walk 가 "한 번의 큰 read" 가 아니라
  "많은 작은 enumeration" 으로 실제 비용을 낸다.
- 240 장의 256×192 로 crop pass(128×128 재decode)와 color thumbnail 이
  파일마다 실제 비용을 갖게 하여 consumer 를 느리게 만든다.
- 147,510 B 는 BMP 24-bit + 4바이트 row padding 없는 크기
  (256×3 = 768, 768 % 4 == 0).

**기존 D8a 8×8 fixture 도 유지**하므로, 60 파일만 스캔했을 때의
parity 결과가 그대로 재현된다 (regression anchor).

## 4. Fingerprint 정의 변경 여부

**알고리즘은 바꾸지 않는다.** canonical manifest + SHA-256 v1 을 그대로
쓴다. 바뀌는 것은 dataset **내용** 이므로 fingerprint 값이 의도적으로
달라진다.

```
fingerprintVersion = 1   (변경 없음)
fingerprint        = 새 값 (실측 후 기록)
```

이것이 올바른 이유: `fingerprintVersion` 은 algorithm 식별자이고,
`fingerprint` 는 content 식별자다. content 가 바뀌면 fingerprint 가 바뀌는
것이 정의상 맞다.

## 5. Measurement state / schema

- benchmark schema **8 유지**. 새 telemetry 키를 추가하지 않는다
  (D8b 는 관측이 아니라 dataset扩充).
- `meta.dataset` 는 D8a 와 동일 구조로 자동 기록된다.
- dataset 을 못 만들면 `not_available`, 읽기 실패면 `failed`.

## 6. Test 요구사항

기존 D8a 테스트(`dataset_fingerprint_test` A~F, `dataset_e2e_test`)는
그대로 통과해야 한다. D8b 추가로:

- 확장 dataset 에서도 E2E 가 동일 fingerprint 를 기록/검증한다
- `images/exact` 48 + `images/varied` 12 가 **그대로 존재**하고
  동일 fingerprint 부분집합을 갖는지 (regression anchor)
- walker telemetry 이 스캔 후 `measured` 이고
  queued == dequeued (손실 0) 임을 단언

## 7. D4b / Full D3 재판정 방법

확장 dataset 으로 다수 회 반복 측정한 뒤:

**D4b (overlap)**
```
gpu_batch_share_of_wall 이 여전히 1% 미만이면 → D4b 보류 (근거 확보)
kernel device time 이 device 합에서 지배적이면 → overlap 후보 아님
host_side_share 가 크고 gpu_batch share 도 크면 → D4b 실험 설계
```

**Full D3 (queue)**
```
maxDepth 가 capacity 대비 유의미하게 크고 blockedTicks > 0 이면
  → producer 가 실제로 block 된다 → topology 변경 후보
blockedTicks == 0 이고 maxDepth 작으면 → topology 변경 근거 없음
starvedTicks > 0 이면 consumer idle 존재 → 별도 분석
```

판정은 **실측 후에만** 한다. 이번 단계에서 topology 를 바꾸지 않는다.
