# MediaSimilarityFinder v0.9.2.52 — Incremental Match Checkpointing During Scan (Resume Guarantee)

## Need for change
The v0.9.2.50 match persistence (quick load) saved **only once, at scan end**. Groups visible on screen mid-scan were not yet in the DB, so closing the app before completion — or a kill, crash, or scan exception — discarded everything that scan had found. If the very first scan never finished, the DB stayed empty and re-scanning the same folder restored nothing. Letting users resume unfinished file work required saving matches as soon as they are found.

## Previous structure
- `ScanWorker::run()` called `engine_.saveMatches(allMatches_)` exactly once, just before finishing. `allMatches_` = quick-loaded stored pairs + this scan's new pairs
- The exception path (`catch`) emitted `failed` without saving — partial results of a failed scan were lost too
- `saveMatches` is wholesale replacement (upsert + DELETE of rows absent from the saved set), so saving a partial set would wipe existing history — a footgun for any incremental approach

## New structure
- **Incremental checkpointing during scan**: `control_.onMatch` calls `persistMatchesSnapshot()` every 25 new matches AND at least 5 seconds after the previous save. The saved set is always the full accumulation (`allMatches_`), so it never conflicts with the wholesale-DELETE semantics. Count+time dual throttle keeps million-match scans fast
- **`persistMatchesSnapshot()` helper**: `ScanWorker` member. Converts `allMatches_` to a `SearchMatch` vector, then `engine_.saveMatches`. Worker-thread only, no lock needed (kept separate from the `pending_` GUI-delivery queue). The `onMatch` critical section shrinks to the `pending_` push
- **Exception-path save**: `catch` checkpoints before emitting `failed`, so the next scan of the same folder quick-loads the partial results. Safe when the DB never opened (`saveMatches` early-returns) and no partial wipe is possible (transaction ROLLBACK on error)
- **Comment correction**: the old "keeps deleted files out of stored results" contradicted the actual behavior (loaded rows are re-saved); now documents the union semantics (every pair ever found is kept, including pairs whose files are currently missing from disk)
- Verified no existence filtering on the load/group paths — missing-file pairs restore as-is. Mark persistence explicitly out of scope
- Version strings unified → 0.9.2.52

## Resolved situation
- However a scan ends (complete, cancelled, failed, or killed after the last checkpoint), every same-file pair found so far stays in the DB
- Re-scanning the same folder quick-loads the previous group list immediately, so unfinished work on those files can resume
- The saved set is always the full accumulation, so wholesale DELETE can never drop existing history

## Future impact
- Checkpoint cadence (25 matches / 5 s) is tunable per scan scale; raise only the time interval if saving ever burdens huge scans
- "Restore on folder open" (show stored groups without pressing scan) is possible as separate work (currently restores on scan)
- Monitor-path matches could reuse the same snapshot persistence
