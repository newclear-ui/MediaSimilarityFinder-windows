## 1. Why D4a entry is needed

D1a established that `addImageTransferMs()` / `addImageExecMs()` /
`addImageGpuQueueMs()` exist as telemetry fields with **zero callers**.
So `gpuTransferState` / `gpuExecState` / `gpuQueueWaitState` being
`not_measured` is correct today — not a zero standing in for missing data.

The cause sits at the abstraction boundary: there is no CUDA device-side
timer inside the backend, and wrapping the call from above necessarily
bundles transfer with kernel execution. The D4 brief's D4 evaluation
items (separate transfer time / GPU execution time / synchronization
time) are **impossible to measure at all** without internal timing points.

D4a is therefore a "make measurement possible" gate, not an optimization.

## 2. Current hashBatch structure

`src/cuda_backend.cu` `msf_cuda_backend_hash_batch()`:

```
ensure_capacity
    ↓
cudaMemcpyAsync(H2D)
    ↓
msf_phash_kernel<<<>>>
    ↓
cudaMemcpyAsync(D2H)
    ↓
cudaStreamSynchronize
```

`src/media_pipeline.cpp` records the whole thing as a single
`addGpuBatchMs()`. So `gpuBatchMs` = H2D + kernel + D2H + synchronization
with no way to tell which element dominates.

`cudaEvent_t` does not appear anywhere in the file.

## 3. Limits of existing telemetry

- `gpuBatchMs`: single value with no internal boundary
- `gpuTransferMs` / `gpuExecMs` / `gpuQueueWaitMs`: defined but uncalled
  (state = `not_measured`)
- The "never encode missing telemetry as 0" rule is being honored, yet
  **no measurement is possible**, so D4 has no evidence to reason from.
- B5's historical ≈86 ns/image transfer describes that run's conditions
  and cannot substitute for the current workload's dominant factor.

## 4. Why CUDA internal timing

The D4 brief's D1b transfer-observability clause requires "timing points
implemented under the backend abstraction". Placing them inside
`cuda_backend.cu` satisfies that without spreading CUDA anywhere else:
`GpuBackend` is the only boundary between upper layers and the `.cu`, so
only plain values reach the engine / pipeline / recorder.

## 5. Timing point definitions

Recorded in order on the same CUDA stream (so real execution order is
reflected):

```
event  h2dStart   recorded
        cudaMemcpyAsync(H2D)
event  h2dEnd     recorded
event  kernelStart recorded
        kernel launch
event  kernelEnd   recorded
event  d2hStart   recorded
        cudaMemcpyAsync(D2H)
event  d2hEnd     recorded
        cudaStreamSynchronize   ← host wait point
```

Events are created once at backend creation and reused; creating them per
call would add overhead that pollutes the very numbers being measured.

## 6. Meaning of each metric

| metric | definition |
| --- | --- |
| `h2dDeviceMs` | device event delta. **Device** execution time of the H2D copy on the stream |
| `kernelDeviceMs` | device event delta. **Device** execution time of the pHash kernel |
| `d2hDeviceMs` | device event delta. **Device** execution time of the D2H copy on the stream |
| `syncHostMs` | **host wall time** spent inside the backend's `cudaStreamSynchronize()` call |
| `hostTotalMs` | **host wall time** of the whole backend call |

`sync = hostTotal - h2d - kernel - d2h` is **not** computed. That value
mixes host enqueue overhead and host scheduling effects, so it cannot be
claimed as exact CUDA synchronization time. `syncHostMs` is a directly
measured host-side value and is a different definition.

## 7. Unmeasured handling

- event create / record / elapsed failure → `measured = false`
- In that case the hash result is returned **exactly as before**.
  `measurement failure != GPU processing failure`
- Callers do **not** touch the recorder when `measured == false`, so JSON
  keeps `not_measured` and never becomes 0.

## 8. Protection of existing GPU / CPU semantics

- `hashBatch()` argument behavior, return value, and hash results unchanged
- `addGpuBatchMs()` key and meaning preserved (pipeline-side host elapsed)
- CPU build / GPU OFF / GPU unavailable / GPU fallback all behave as before
- New measurement code is not compiled at all in a non-CUDA build
- On CUDA runtime error, measurement turns off and the existing error path
  is used unchanged

## 9. D4b items NOT implemented here

```
double buffering / triple buffering
pinned memory
new stream topology / stream pool
producer-consumer overlap
D5 batching, D6 starvation, D7 dispatch
Scheduler / share formula
```

## 10. Accuracy impact

Measurement only. Hash arithmetic, thresholds, and verdict logic are
untouched. Validation uses the CPU↔GPU hash parity test.

## 11. Windows / GPU / Linux compatibility impact

- `cudaEvent_t` is standard CUDA runtime API; identical on Windows and Linux
- No impact on CPU-only builds
- Other backends (HIP / Level Zero) do not exist yet, so they take the
  existing "cannot measure → not_measured" path

## 14. How the D4b decision will be made

From the measured JSON:

- If `gpuKernelMs` far exceeds `gpuH2dMs + gpuD2hMs + gpuSyncHostMs`,
  the kernel dominates → overlap is not a gain candidate.
- If the kernel is short while `gpuSyncHostMs` / host enqueue is a large
  share, the host wait structure dominates wall time → design a separate
  D4b overlap experiment.
- Either way the call is made **only after measurement**.
