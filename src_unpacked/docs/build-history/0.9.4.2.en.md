# MediaSimilarityFinder v0.9.4.2 — Node B1: Minimal Adaptive Allocation

First-validation baseline for B1: the brief's B1 table (GPU OFF → CPU
100%, valid GPU → shares, slow GPU → CPU-lean possible, unavailable →
fallback, parity). Engine 1.5.0, DB 1.0.3, cache v9, benchmark schema 1
unchanged.

## Why the change was needed
- Through 0.9.4.1, GPU use was decided by a single `policy_.gpuEnabled`
  boolean. Shares, decision reasons, and re-evaluation did not exist as
  concepts, so the rest of Node B (B2–B6) had no structure to build on.

## Previous structure
- Image batches and video builds referenced `policy_.gpuEnabled` directly.
- `SchedulerTelemetry` existed as structure only, always `not_measured`.

## New structure
- New `src/scheduler.h/.cpp` — `CpuGpuScheduler`: inputs (CPU thread
  count, GPU ON/OFF, availability, SM count) and outputs (CPU/GPU shares,
  backend, reason, gpuUsed). Capacity units are relative; only the ratio
  feeds shares. Reason codes: `gpu_off` / `gpu_unavailable` /
  `no_gpu_capacity` / `proportional_baseline`. No fixed split — a weak GPU
  converges CPU-heavy by construction.
- Re-evaluation: `maybeReevaluate(hw, tick)` with a 2000 ms default
  cadence, called at the existing image-batch and video-range entries (no
  structural change). Stable inputs never raise the adjustment counter.
- Engine wiring: one `decide()` at scan start; both gates now read
  `schedUseGpu`. ON + available uses GPU exactly as before; OFF or
  unavailable goes CPU — verdict behavior unchanged.
- Telemetry: `finishScan` records the scheduler section as `measured`
  (initial == current capacities, shares, backend, adjustment count,
  image + video fallback sum). One added getter,
  `BenchmarkRecorder::videoGpuFallbacks()`.
- `GpuBackend::computeUnits()` (CUDA SM count, additive) plus a one-line
  `MediaPipeline::gpuComputeUnits()` forward.
- B2+ items (moving average, hysteresis, transfer/workload cost, external
  load) and Node D pipeline/queue changes are untouched.

## Why this shape
- B1 stays thin: existing gate positions kept, decision structure layered
  on top. Verdict paths untouched, so parity is preserved structurally.
- SM-vs-thread ratio is documented in code and history as the B1 starting
  proxy. Measured throughput (B2) and calibration (C) replace it.

## Resolved state
- Scheduler decisions exist as structure + tests + telemetry. B2 only
  needs wider inputs.

## Accuracy impact
- None. Gate replacement maps ON + available → GPU, everything else →
  CPU, identical to before. `scan_workflow_test` proves it with the same
  1-group result on both trees. `search_engine_test`,
  `video_scan_e2e_test`, `match_revalidate_test`, `fingerprint_fast_test`,
  `video_decode_parity_test`, and `scan_pipeline_test` pass on both.

## Compatibility impact
- Benchmark JSON keeps existing keys; the scheduler section is now
  measured. Existing compat paths (`MSF_ENABLE_CUDA` alias, old
  `ScanWorker` ctor) kept.

## Validation
- CPU Release build PASS, **CTest 64/64 PASS** (incl. new
  `scheduler_test`; one `reveal_window_test` flake re-ran green —
  Explorer foreground contention, unrelated to code).
- GPU Release build PASS, **CTest 65/65 PASS**.
- `scheduler_test`: OFF → 100/0, unavailable → fallback, proportional sum
  100, slow-GPU CPU-lean, zero capacity, cadence hold/fire/adjust, and
  telemetry JSON pass on both trees.
- `--version` 0.9.4.2 and `--smoke` PASS on both.

## Future impact
- B2 enters by widening inputs plus `SchedulerHardware` extension.
- B1 capacity proxies are provisional; B2/C replace them. The sum-100
  rule and reason codes stay.
