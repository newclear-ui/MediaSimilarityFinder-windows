- **Base**: `v0.9.4.44` / `1564b87`
- **date**: 2026-10-04
- **Verdict**: baseline PASS (S4 not CLOSED, S5 not complete)

## 1. Why the change was needed

Files without EXIF Orientation, or with an unresolvable EXIF path, had no
readable orientation. `I-exif-orientation-path-fix` explicitly forbade an XMP
fallback, so XMP was promoted to a standalone contract
(`I-xmp-orientation-fallback.*`) with its own production path. The existing
EXIF contract was not retroactively changed.

## 2. Previous structure

- `exifOrientationToTransform()` returned identity for EXIF absent, query
  failure, and invalid values alike, with no distinction. No XMP query code
  existed.

## 3. Changed structure

- New `resolveOrientationToTransform()`: a usable EXIF VT_UI2 value (1..8)
  wins and XMP is never queried. EXIF absent / query failed / wrong type /
  out-of-range value all count as unresolved and fall through to XMP.
- XMP supports exactly one representation, `tiff:Orientation`. Measured WIC
  behavior surfaces it as a `VT_LPWSTR` string; integer VARIANTs are
  normalized too. EXIF wins on conflict.
- Both call sites (fingerprint decodeBoth, color display lane) share the same
  helper, so transform semantics stay unified.
- No telemetry field added. XMP is queried only when EXIF is unresolved.

## 4. Resolved situation

- All 7 fixtures (A–G) PASS: identity/90/180/270 applied, EXIF precedence,
  invalid ignored, absent keeps the existing default.
- Existing EXIF path behavior unchanged (EXIF fixture regression kept).

## 5. Verification

# Two follow-up fixes (same 0.9.4.45 build, no version bump)

## A. `--version` redirection misdetection

### 1. Why the change was needed
`MediaSimilarityFinder.exe --version` printed nothing to the console when
launched from PowerShell, while CMD worked correctly.

### 2. Previous structure
Because the executable is GUI subsystem (`WIN32_EXECUTABLE TRUE`),
`gui/main.cpp::attachParentConsole()` calls
`AttachConsole(ATTACH_PARENT_PROCESS)` when `GetConsoleWindow()` is null and
skips the `CONOUT$` reopen when the streams are considered redirected. The
predicate `streamIsRedirected()` returned `true` for `fd<0`, an invalid OS
handle, and `FILE_TYPE_UNKNOWN`, so all unusable streams were misreported as
"redirected".

### 3. New structure
Those three cases now return `false` (stream unusable). Only genuinely usable
`FILE_TYPE_DISK`/`FILE_TYPE_PIPE` count as redirected, so real redirection is
still preserved and only unusable streams fall through to
`AttachConsole` + `CONOUT$`. Comment corrected alongside
(`gui/main.cpp:41-49`).

### 4. Resolved situation
The path where a PowerShell launch skipped `AttachConsole` and left `std::cout`
with nowhere to write is gone. CMD behavior is unchanged.

### 5. Verification
- `--version`, `--help`, `cmd /c`, and a bad option (stderr, EXIT=2) all correct.
- OS-level redirection (`cmd > file`) records 45 bytes.
- `Start-Process -Wait -RedirectStandardOutput`: 45 bytes, EXIT=0.
- Side finding: PowerShell `>` yields 0 bytes with an empty `$LASTEXITCODE`
  because PowerShell does not wait for GUI-subsystem executables. This
  **reproduces identically on the pre-fix binary**, so it is not a regression of
  this change. OS-level redirection works.
- CPU CTest 102/102 PASS.

### 6. Future impact
Only the console CLI stream decision changed. Search/index/comparison logic and
GUI behavior are unaffected. Next candidate: a dedicated console-output
regression test.

## B. CUDA host compiler encoding warning (C4819)

### 1. Why the change was needed
GPU build logs repeatedly emitted MSVC `warning C4819` from the CUDA headers
(`driver_types.h`, `cuda_runtime_api.h`). Code page 949 cannot represent
non-ASCII characters in those headers; there was no CUDA syntax/link error.

### 2. Previous structure
Only `add_compile_options($<$<COMPILE_LANG_AND_ID:CXX,MSVC>:/utf-8>)` existed,
so `/utf-8` reached MSVC C++ compilation only. CUDA uses a separate host
compiler and never received the flag.

### 3. New structure
nvcc does not accept `/utf-8` directly, so it is forwarded to the MSVC host
compiler through `-Xcompiler`:
`add_compile_options($<$<AND:$<COMPILE_LANGUAGE:CUDA>,$<CXX_COMPILER_ID:MSVC>>:-Xcompiler=/utf-8>)`
(`CMakeLists.txt:38-41`). The first attempt used
`COMPILE_LANG_AND_ID:CUDA,MSVC`, which failed to match because CUDA reports
compiler id `NVIDIA`. The nvcc command line now shows
`-Xcompiler="/EHsc -Ob2 /utf-8"`.

### 4. Resolved situation
Zero C4819 occurrences. CUDA architectures (`compute_75/86/89`) and runtime
behavior are unchanged.

### 5. Verification
- Forced recompile of `cuda_backend.cu`: C4819=0 / warning=0 / error=0 and
  `msf_cuda.lib` produced.
- GPU Release build + full CTest: **103/103 PASS**, zero warnings.
- CPU Release build + full CTest: **102/102 PASS**.

### 6. Future impact
Build-option only; no source or ABI change. Next candidate: decide whether nvcc
warnings join the release gate.
