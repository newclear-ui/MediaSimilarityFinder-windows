# MediaSimilarityFinder v0.9.4.83 — Index-first display (show existing results first)

Baseline `0.9.4.82` -> this build `0.9.4.83`.
CPU CTest **122/122**, GPU CTest **123/123**.
`kEngineVersion 1.5.1` / `kDatabaseVersion 1.0.5` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — all unchanged. No verdict, schema or decode change.

## 1. Why it was needed

User report: on a folder whose **index is already complete**, pressing "Search
Update" shows **no existing results at all** until the rescan finishes (over two
hours on a large dataset). User request: "read the already-indexed files first,
show their thumbnails in the GUI first, then move on to the remaining files."

## 2. Previous structure

`ScanWorker::run()` order:

1. `openIndexForRoot`
2. **count prepass** (full directory enumeration) -> `targetCount`
3. **engine-version gate** (`revalidateMatches`) -> persists survivors only
4. **quick-load** (restore stored matches) -> `quickLoaded` + `matchesArrived`
5. walk + analyze

Because quick-load came after count and revalidate, the stored groups reached the
GUI only well into the scan. On large folders that delay is minutes long.

## 3. Change

Reordered `ScanWorker::run()` so the **engine-version gate and quick-load run
before the count prepass**:

1. `openIndexForRoot`
2. **engine-version gate** (`revalidateMatches`) — a no-op when the version matches
3. **quick-load** -> stored groups/files reach the GUI right after scan start
4. count prepass -> `targetCount`
5. walk + analyze

Thumbnails are served from `ThumbnailStore` (disk-persistent), so they display
**without re-decoding**. Once the GUI has the groups/files it requests visible
items via `fileThumb()` and paints arrivals via `onThumbReady` (unchanged path).

The gate must run before quick-load because `revalidateMatches` persists only the
survivors with `saveMatches`; calling `loadMatches` afterwards is what keeps false
positives off the screen.

## 4. Result

- Rescanning an indexed folder now shows **existing similar/duplicate groups,
  files and thumbnails immediately** at scan start.
- Count and walk then proceed, new results stream in, and the final results
  replace the snapshot on completion.

## 6. Tried and rejected (experiment record, AGENTS rule 9)

- **Attempt A (rejected)**: add a `preliminary` flag to the `results` message and
  pre-send the indexed file list into `allPaths_` at scan start.
  - **Rejected because**: the GUI file view (`refreshFileViews`) renders only the
    **selected group**; `allPaths_` is written but never consumed for display. Also
    `revalidateMatches` persists survivors only, so showing stored matches before
    revalidation leaves false positives on screen.
  - It added IPC signature churn without reaching the goal, so it was reverted.
- **Chosen**: move quick-load before count (an ordering change only). No IPC or
  signature change.
- **Future revisit**: if a separate full-file-list view is ever wanted, consider a
  file-list snapshot path distinct from `results`.

## 7. Impact and limits

- The reorder does not affect walk/analyze verdicts or aggregation (display timing
  only).
- **Not fixed (follow-up)**: the live "Index complete" counter is
  `analyzed`+`unchanged`, and `BackendSession::pushStatusSnapshot()` pushes that
  state **only when matches arrive**. On an incremental rescan with no changed
  files it stays 0 (a separate defect, next build).
- Test Mode, profile and thumbnail DB bytes are unaffected.
