## 1. 변경 필요성

0.9.4.59 사후 검토에서 두 의미 버그가 확인됐다.
첫째, generation 스탬프가 일반 `seen`(deletion detection용, ignored·
out-of-scope 포함)을 admission 증거로 재사용했고, 정상 완료 경로는 scope를
전혀 확인하지 않아 이미지 전용 스캔이 video generation을 갱신할 수 있었다.
둘째, `finishScan(false)`가 live cancel flag로 terminal을 추론해서 DB 실패
뒤 Stop이 들어오면 Failed를 Cancelled로 잘못 보고했다.
셋째, `setSamplingGeneration()` 반환값을 무시했다.

## 2. 기존 구조

- 취소 스탬프 조건이 `seen` 기준. ignored·out-of-scope video도 `seen`에
  있으므로 스탬프 근거로 잘못 쓰였다
- 완료 경로는 `if(r.completed)` 무조건 스탬프. video scope 미확인
- terminal은 `control->cancel` live 값으로 추론
- stamp write 실패 무시

## 3. 변경 구조

- `videoScopeSeen` 분리: ignored·scope 검사 통과 + 실제 video admission
  경계에서만 기록. `seen`은 deletion detection 그대로
- 스탬프 공통 invariant (완료·취소 동일): `scanVideos=false`면 절대 변경
  없음. 모든 기존 video row가 `videoScopeSeen`에 있을 때만 기록. ignored
  旧 row가 있으면 보수적으로 유지 → unignore 시 regrid
- `ScanTerminal { Completed, Cancelled, Failed }` 도입. 각 return 경로가
  명시 전달. DB error/checkpoint/commit 실패 → Failed (이후 Stop과 무관).
  `VideoRangeResult` 의미는 유지
- stamp write 실패는 반환값 확인 후 old 유지 (다음 스캔 안전 regrid).
  이미 commit된 검색 결과를 Failed/rollback으로 바꾸지 않는다

## 4. 해결된 상황

- 이미지 전용 스캔(완료·취소 모두)이 video generation을 건드리지 않는다
- ignored stale row는 승격되지 않고, unignore하면 재분석된다
- DB 실패 + Stop 동시 상황에서 telemetry failed=true, cancelled=false.
  transaction rollback 유지
- stamp 실패해도 스캔은 유효·완료, 다음 스캔이 regrid한다

## 5. 검증

### 신규 `scan_generation_scope_test` (35 checks, CPU·GPU PASS)

- D (image-only): 완료 스캔이 이미지 재사용 + video 미admission + gen "0"
  유지. 취소 케이스도 gen 불변. 구 코드(D2 완료 무조건 스탬프)에서는 실패
- E (ignored): 무시 1개 포함 완료 스캔이 gen "0" 유지. unignore 후 전체
  재분석 (regrid exact). 구 코드(seen 재사용)에서는 실패
- F (stamp 실패): meta trigger로 write 차단 → 스캔 완료·analyzed 정상·
  gen "0" 유지·failed 없음. trigger 제거 후 rescan regrid + gen "3" 회복
- G (DB error + cancel): files trigger + walked 취소 → completed=false,
  telemetry failed:true/cancelled:false, rollback 직접 확인(0 rows),
  trigger 제거 후 재시도 완료. 구 코드(live 추론)에서는 실패
