## 1. Why D8b is needed

The 0.9.4.21 (D8a) dataset is a **minimal fixture for reproducibility and
parity** by design: 8×8 24-bit BMP, **60 files, 14,760 bytes total, 2
directories**.

Five repeated runs against it (at 0.9.4.21) produced:

```
walker_queued/dequeued   60 / 60      no loss
walker_max_depth         1            0.024% of capacity 4096
blocked_ticks            0
starved_ticks            0
gpu_batch_share_of_wall  0.34%        (gpuBatchMs 0.469ms / wall 136.1ms)
```

Those numbers **cannot be used as evidence that "D4b / Full D3 are
unnecessary"**, because the dataset does not make the pipeline do any real
work:

- 8×8 images cost essentially nothing to decode, crop, or thumbnail
- 2 directories cost essentially nothing to walk
- therefore both producer and consumer finish instantly, and
  `maxDepth = 1` reflects **the dataset's size**, not the architecture

In other words, "no gain" came from **an absent measurement subject**. D8b
creates that subject.

## 2. Facts confirmed in the current structure (code evidence)

`src/media_search_engine.cpp` lines 604–634:

- **producer** = a separate walker thread. `Scanner::scan_stream` only
  pushes via `onFile`.
- **consumer** = **a single thread**. `while(...) { queue.waitForData(50);
  queue.tryPop(x); processOne(std::move(x)); }` — it pops **one** file at a
  time and runs `processOne` synchronously.
- `processOne` accumulates into `imageBatch` and only flushes through
  `processImageBatch` when `size() >= gpuBatch`.

Given that the consumer processes files synchronously one at a time, the
queue grows whenever **consumer cost exceeds producer walk cost**. The D8a
dataset made both costs ~0, hence depth 1.

So the D8b dataset deliberately creates asymmetry along two axes:

1. **walk axis** (`tree/`) — many files spread across many directories, so
   disk enumeration costs something real.
2. **decode axis** (`bulk/`) — realistically sized images, so
   decode + crop + color thumbnail cost something real.

## 3. Dataset composition (v2)

The existing `images/exact` (48) and `images/varied` (12) are **kept
unchanged** to preserve continuity with the fingerprint recorded in D8a and
to keep a parity regression anchor.

Added:

| Path | Count | Size | Purpose |
| --- | --- | --- | --- |
| `tree/lN/MM/lNNN.bmp` | 2400 | 8×8 (246 B) | directory spread → walk cost, queue depth |
| `bulk/bNNNN.bmp` | 240 | 256×192 (147,510 B) | decode/crop/thumbnail cost, GPU batch share |

Total: 60 (existing) + 2400 + 240 = **2700 files**

Rationale:

- 2400 files are spread over many subdirectories so no single directory has a
  large entry count. The walk then costs "many small enumerations" rather
  than "one big read".
- 240 images at 256×192 make the crop pass (a second decode at 128×128) and
  the color thumbnail cost real per-file work, slowing the consumer.
- 147,510 B is a 24-bit BMP with no row padding (256×3 = 768, and
  768 % 4 == 0).

**The existing D8a 8×8 fixture is also retained**, so a 60-file-only scan
still reproduces the same parity result — a regression anchor.

## 4. Does the fingerprint definition change?

**The algorithm does not change.** The canonical manifest + SHA-256 v1 is
used as-is. What changes is the dataset **content**, so the fingerprint value
changes on purpose:

```
fingerprintVersion = 1   (unchanged)
fingerprint        = new value (recorded after measurement)
```

This is correct: `fingerprintVersion` identifies the *algorithm* and
`fingerprint` identifies the *content*. A content change must change the
fingerprint by definition.

## 7. How D4b / Full D3 get re-decided

After repeated measurement on the expanded dataset:

**D4b (overlap)**
```
if gpu_batch_share_of_wall is still < 1%        -> defer D4b (evidence secured)
if kernel device time dominates the device sum  -> overlap is not a candidate
if host_side_share is high AND gpu_batch share
   is also significant                          -> design a D4b experiment
```

**Full D3 (queue)**
```
if maxDepth is meaningfully large vs capacity AND blockedTicks > 0
                                                 -> the producer really blocks
                                                    -> topology change candidate
if blockedTicks == 0 and maxDepth is small       -> no basis for a change
if starvedTicks > 0                              -> consumer idle exists,
                                                    separate analysis
```

The call is made **only after measurement**. No topology change in this step.

## 10. Actual measurement

RTX 3080 Ti, GPU tree, 3 runs, **cold index** each run.
Dataset fingerprint `9b113848…4253c` fixed.

### Walker queue (the Full D3 question)

| Metric | D8a (60 files) | **D8b (2700 files)** |
| --- | --- | --- |
| queued / dequeued | 60 / 60 | **2700 / 2700** (no loss) |
| maxDepth | **1** | **964 mean / 1076 max** |
| share of capacity | 0.024 % | **23.5 %** |
| blocked_ticks | 0 | **0** |
| starved_ticks | 0 | **0** |

D8a's depth of 1 is now **shown to have been a dataset-size artifact.** In
reality the queue does build depth (mean 964, max 1076).

But `blocked_ticks` is **still 0** — the producer never actually blocked,
because depth 1076 is 3.8× below the capacity of 4096.

### GPU batch internal timing (the D4b question)

| Metric | mean | max |
| --- | --- | --- |
| gpu_host_total_ms | 28.413 | 48.233 |
| kernel device | 17.123 | 30.110 |
| d2h device | 2.264 | 3.790 |
| h2d device | 1.082 | 1.107 |
| syncHost | 1.823 | 3.219 |
| host-side share | 28.0 % | — |
| timed batches | 18 | — |

### Stage breakdown — the actual bottleneck

```
summary_wall_ms      109737.1
  walk                 1536.5   1.40 %
  image stage           642.3   0.59 %
  analyze            108225.6  98.62 %   ← the real bottleneck
  (of which gpu batch)   48.3   0.04 %
```

`analyze` is `MediaPipeline::analyze()` — the **final matching/grouping
stage** (`pipe.analyze` at `media_search_engine.cpp:702-703`) — and it is
**outside** the queue/transfer/overlap scope that Node D owns.

## 11. D4b / Full D3 re-decision

### Full D3 — **deferred (evidence secured)**

```
blocked_ticks = 0   → the producer never actually blocked
maxDepth 964/4096  → capacity never acted as the bottleneck
```

There is **no observed loss for a topology change to recover.** Capacity only
becomes a problem at roughly 4× the current file count (about 11,000 files at
the same density).

### D4b overlap — **deferred (evidence secured)**

```
gpu_batch_share_of_wall = 0.0257 %
D3+D4 addressable ceiling = 0.044 % of engine wall
```

The entire GPU hash path is 0.026 % of the scan. Perfect transfer/compute
overlap could return less than 0.044 % of wall time, and realistically only a
fraction of that. The kernel (17.1 ms) already accounts for 84 % of the device
sum (20.5 ms), so there is little to hide in the first place.

### The conclusion this stage actually produced

```
what Node D owns (queue + GPU batch)  = 0.044 % of engine wall
outside Node D (analyze: matching)    = 98.62 % of engine wall
```

**Continuing pipeline optimization (D) yields no meaningful gain on this
workload.** The real bottleneck is `analyze`, which is outside the D brief.

Honest scoping of that claim:

- these numbers are a conclusion **for this dataset's density and composition**
- the `bulk` 256×192 images make crop + color thumbnail expensive, which slows
  the consumer and raises queue depth — so this dataset was **deliberately
  built to favour observing the queue**
- even so, GPU share was 0.026 %. For the GPU path to matter, images would
  have to be far larger (no crop/thumbnail cost) or hash batches far more
  numerous.
