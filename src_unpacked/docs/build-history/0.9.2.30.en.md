# 0.9.2.30 — Remove duplicate match-result storage in the scan path

**IMPORTANT CHANGE**

## Why this change was needed
0.9.2.29 converted candidate-pair generation to streaming, but confirmed matches were still stored in `ScanStats::matches` and then copied into `MediaSearchEngine::SearchReport::matches`. On large result sets, the same match set temporarily existed in two containers, creating avoidable peak memory usage.

## Previous structure
`ScanPipeline` → `ScanStats.matches` → copy into `SearchReport.matches`

## New structure
`ScanPipeline` → `MatchCallback` → `SearchReport.matches`

The existing `analyze(maxDistance)` API remains compatible; when no callback is supplied, it retains the previous `ScanStats.matches` behavior.

## Resolved situation
`MediaSearchEngine::scan()` now receives each confirmed match immediately through the callback and appends it directly to `SearchReport.matches`. The normal search path therefore no longer holds two complete match arrays simultaneously.

## Accuracy / compatibility
- Match decision logic, thresholds, mirror/crop handling, and temporal refinement are unchanged.
- Existing `ScanPipeline::analyze(maxDistance)` remains available.
- The callback is additive and does not break existing callers.
- Match processing order is preserved.

## Verification
The existing regression suite is retained and the callback path is exercised in the search pipeline tests.

## Future impact
A later stage can address cases where `SearchReport.matches` itself reaches millions of entries through persistent result storage and pagination. This release removes the preceding avoidable duplication first.
