# MediaSimilarityFinder v0.9.4.81 — 매칭 검증 모드 선택 (안정형/고속형/자동)

기준선 `0.9.4.80` → 본 빌드 `0.9.4.81`.

`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.5` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — 전부 불변(의도). 판정(임계·SSIM·temporal)은 세 모드 모두 동일.

## 1. 변경 필요성

- 파일이 1만~10만 개를 넘으면 후작업(쌍매칭 검증)이 오래 걸린다. 검증을 "언제·어떤
  단위로" 수행할지 사용자가 골라 최종 테스트에서 비교할 수 있어야 한다.
- 지금까지는 스캔 후 전역 `analyze()` 1회가 유일한 경로였고, 어떤 방식으로
  동작했는지 로그로 구분할 수단이 없었다.

## 2. 기존 구조

- walk 중 스트리밍 매칭(`livePipe.addAndMatch`, 이미지 정본) 후, walk 종료 시
  `db_.all()`로 전체 파일을 다시 모아 별도 `ScanPipeline::analyze()`를 1회 수행.
- 어떤 모드인지 로그/telemetry에 남지 않았다.

## 3. 변경 구조

- **설정 옵션 `매칭 검증 방식`** (설정 → 일반 탭, QSettings `ui/analyzeMode`):
  1. **안정형 (스캔 후 검증)** = `B` (기본) — 스캔 후 전역 검증(기존 동작).
  2. **고속형 (스캔 중 검증)** = `A` — 최종 검증을 "이번 스캔에서 변경된 파일이 낀 쌍"으로 제한.
  3. **자동 (혼합 검증)** = `A+B` — A에 더해, 양쪽 모두 변경된 이미지 쌍은 라이브 스트리밍이
     이미 방출했으므로 최종 패스에서 생략.
- 새 `src/analyze_mode.h`(`msf::AnalyzeMode`, `analyzeModeKey` = `B`/`A`/`AB`).
- 배선: GUI 설정 → `BackendScanConfig.analyzeMode` → `START_SCAN`(JSON `analyzeMode`) →
  `BackendSession::startScan` → `ScanWorker::setAnalyzeMode` → `ScanControl.analyzeMode`
  → `MediaSearchEngine::scan`.
- `ScanPipeline::analyze(...)`에 선택 인자 `changedFiles`(파일별 변경 플래그)와
  `skipBothChangedImages` 추가. null이면 전부 검증(=B). 판정 로직 자체는 손대지 않음.
- **로그 식별**: 스캔 시작 시 `msf_scan.log`에 `scanAnalyzeMode=<B|A|AB>` 1줄, 그리고
  상세 로그 JSON의 `analyze.mode`에 같은 키. `finished`/`results` 메시지 형태는 불변.

## 4. 해결된 상황

- 사용자가 세 방식을 선택할 수 있고, 최종 테스트가 로그의 `scanAnalyzeMode=`(또는
  `analyze.mode`)만 보고 어떤 모드였는지 기계적으로 구분한다.
- A/AB는 변경 파일이 낀 쌍만 재검증하므로 증분 스캔에서 불필요한 재계산을 줄인다.
- 콜드 스캔(전부 변경)에서 A는 B와 동일한 쌍 집합을 검증한다(`analyze_mode_test`가 고정).

## 5. 검증

```text
CPU CTest: 122/122 PASS (0.9.4.81, CPU 트리)
GPU CTest: 123/123 PASS (0.9.4.81, GPU 트리)
신규 analyze_mode_test: 12 checks PASS (콜드 A==B, 부분 dirty, AB skip 양쪽변경)
```

- parity: A/AB는 판정 코드를 바꾸지 않으며, 콜드 스캔에서 A==B임을 테스트로 고정.
- 스키마: `analyze.mode`는 가산적(additive) 키이므로 `kBenchmarkSchemaVersion`은
  **9 유지**(`benchmark_schema_test`가 가산 계약을 고정).

## 6. 향후 영향 및 한계 (명시)

- **B는 이번 빌드에서 기존 전역 검증 그대로다.** "1000 파일 슬라이스 + 프론티어 영속
  + 재개"는 아직 배선하지 않았다(후속 버전). B의 화면 표기는 "스캔 후 검증"이므로
  동작과 일치한다.
- **A/AB의 증분 정확성은 persisted match 집합에 의존**한다: unchanged-vs-unchanged
  쌍은 이전 완료 스캔이 저장한 쌍을 신뢰한다(엔진 버전 상향 시 `revalidateMatches`가
  재검증). 이전 스캔이 중단되어 저장이 불완전하면 그 쌍을 놓칠 수 있다. 콜드 스캔과
  완료된 증분 스캔에서는 B와 동일하다.
- AB의 "양쪽 변경 이미지 생략"은 **라이브 스트리밍이 실행되었을 때만** 사용한다
  (`liveMatch` 가드). 스트리밍 소비자가 없으면(예: CLI) 자동으로 A처럼 동작한다.
- 다음 단계 후보: B의 슬라이스/프론티어 재개, A/AB의 요약 카운트 정합(현재 `pairs`
  요약 수는 재검증한 쌍 기준이라 B와 다를 수 있음; GUI가 표시하는 그룹은 라이브+최종
  합집합이므로 동일).
