# MediaSimilarityFinder v0.9.4.81 — Selectable matching-verification mode (Stable/Fast/Auto)

Baseline `0.9.4.80` → this build `0.9.4.81`.

`kEngineVersion 1.5.0` / `kDatabaseVersion 1.0.5` / `kBenchmarkSchemaVersion 9` /
`kCacheFormatVersion 9` — all unchanged (intended). Verdicts (thresholds, SSIM,
temporal) are identical across all three modes.

## 1. Why the change was needed

- Beyond 10k-100k files, post-processing (candidate-pair verification) takes too
  long. The user must be able to choose when/in what units verification runs and
  compare the choices in a final test.
- Until now the only path was one global `analyze()` after the scan, and nothing
  recorded which scheduling was used.

## 2. Previous structure

- Streaming match during the walk (`livePipe.addAndMatch`, authoritative for
  images), then a single `ScanPipeline::analyze()` over all files rebuilt from
  `db_.all()` after the walk.
- The active mode was not recorded anywhere.

## 3. Changed structure

- **Settings option "Matching verification"** (Settings → General, QSettings
  `ui/analyzeMode`):
  1. **Stable (verify after scan)** = `B` (default) — post-scan global pass (the
     existing behavior).
  2. **Fast (verify during scan)** = `A` — restrict the final verification to
     pairs touching a file changed this scan.
  3. **Auto (hybrid)** = `A+B` — like A, plus image pairs where BOTH sides
     changed are dropped from the final pass because the live streaming pass
     already emitted them.
- New `src/analyze_mode.h` (`msf::AnalyzeMode`, `analyzeModeKey` = `B`/`A`/`AB`).
- Wiring: GUI settings → `BackendScanConfig.analyzeMode` → `START_SCAN` (JSON
  `analyzeMode`) → `BackendSession::startScan` → `ScanWorker::setAnalyzeMode` →
  `ScanControl.analyzeMode` → `MediaSearchEngine::scan`.
- `ScanPipeline::analyze(...)` gains optional `changedFiles` (per-file changed
  flags) and `skipBothChangedImages`. Null means verify everything (=B). The
  verdict code itself is untouched.
- **Log identity**: one `scanAnalyzeMode=<B|A|AB>` line in `msf_scan.log` at scan
  start, plus the same key in the detailed-log JSON at `analyze.mode`. The
  `finished`/`results` message shapes are unchanged.

## 4. Resolved state

- The user can pick any of the three schemes; a final test can tell which ran
  from `scanAnalyzeMode=` (or `analyze.mode`) alone, mechanically.
- A/AB re-verify only pairs touching a changed file, cutting redundant recompute
  on incremental scans.
- On a cold scan (everything changed) A verifies the same pair set as B
  (pinned by `analyze_mode_test`).

- Schema: `analyze.mode` is an additive key, so `kBenchmarkSchemaVersion` stays
  **9** (`benchmark_schema_test` pins the additive contract).

## 6. Future impact and limits (explicit)

- **B is the unchanged global pass in this build.** The "1000-file slice +
  persisted frontier + resume" is not wired yet (follow-up version). B's display
  label "verify after scan" matches its behavior.
- **A/AB incremental correctness depends on the persisted match set**:
  unchanged-vs-unchanged pairs trust the pairs a prior completed scan saved
  (`revalidateMatches` re-checks them after an engine bump). If a prior scan was
  interrupted so its save is incomplete, those pairs can be missed. Cold scans
  and completed incremental scans match B.
- AB's "skip both-changed images" is used **only when the live streaming pass
  ran** (`liveMatch` guard). With no streaming consumer (e.g. CLI) it degrades to
  A automatically.
- Next candidates: B slice/frontier resume; A/AB summary-count reconciliation
  (the `pairs` summary currently counts re-verified pairs and may differ from B;
  the GUI's displayed groups are the live+final union and stay identical).
