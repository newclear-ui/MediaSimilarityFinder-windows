## 1. Why it was needed

- Follow-up to the right-click-path I/O removal (.124): menu construction is I/O-free now, but the QuickLook action's pipe send (`quickLookSendMessage`) was still a **synchronous `WriteFile`**. A wedged server (connected but never reading) would block the GUI thread forever. No field report, but the hole in the responsiveness contract needed closing.
- The color_thumb production correction decision has been pending since .113 (R1: no-FFmpeg SKIP). Re-examined the current test and production path for new evidence.

## 2. Previous structure

- `quickLookSendMessage`: synchronous `CreateFileW` + synchronous `WriteFile` + immediate close. Tiny messages return at once against a healthy server, so the hazard never showed.
- The test covered only the healthy-server path (exact-bytes assertion, `quicklook_pipe=ok`).

## 3. New structure

- The send is now overlapped I/O + a 5 s wait. On timeout the pending write is cancelled via `CancelIo` and the send fails, which callers already handle (status message). The open stays synchronous (no server / all instances busy fail immediately).
- Regression test gains a wedged-server case: connected, never reads, 64 B inbound buffer, 4 MB payload. Pre-fix the test binary **hung for 60 s** (killed externally = FAIL confirmed); post-fix it **fails in 5.0 s**.
- color_thumb: no code change. Ruling (awaiting confirmation; recommended: keep as is) - the test guards exactly the production decode functions (`decodeColorAspect`, `frameAtColor`) and passes across the full suite; the production path (`ThumbnailStore::wicArt/ffmpegArt`) uses those same functions, and gray engine art is never persisted to disk (memory-only fallback). No defect evidence.

## 4. What is fixed

- The pipe-loss scenario is bounded (fails within ~5 s). Reproduced (old hangs) -> fixed -> verified (5.0 s fail).
- color_thumb: "decision pending" -> "keep-as-is recommended, awaiting confirmation", with the rationale on record.
