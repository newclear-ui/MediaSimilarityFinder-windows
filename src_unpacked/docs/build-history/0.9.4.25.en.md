## 0-1. Change Need

What D9a established by measurement:

```
analyze            99.67 % of engine wall
  +-- verify       over 99 % of that
expensive verify   13,734 calls x ~8.5 ms = ~117 s
```

So **almost the entire scan time is spent in 13,734 expensive
verifications.** Those include buffer preparation recomputed from the same
source repeatedly, so removing that duplication should reduce cost without
changing any verdict.

## 1. Direction decision — Primary Candidate / Deferred Candidate

| Candidate | Decision | Reason |
| --- | --- | --- |
| **B. Reduce the cost of one expensive verification** | **Primary (this D9b)** | verdict logic untouched, directly targets the measured 117 s |
| A. Reduce candidate pair arrival rate | **Deferred** | candidate gate semantics risk (candidate recall, false positives/negatives) |

A has the potential to cut the 158,020 verify calls, but it is **not
implemented in this D9b.** Revisiting A requires a separate pre-register
that first defines candidate semantics change, FP/FN risk, verdict parity,
candidate recall impact, and the accuracy validation method.

## 1-1. Scope

- Remove **duplicate decodes** inside the verify path (check whether the same
  image is decoded repeatedly in one verification, reuse already-decoded data)
- Reduce **repeated buffer creation/copy** (the duplicate flow of
  temporary buffer -> copy -> resize -> copy again)
- Reduce **duplicated aspect buffer preparation** — but **crop semantics
  itself stay unchanged**
- Optimize **SSIM input preparation** (resize / copy / format conversion /
  temporary allocation) — but the **SSIM formula itself stays unchanged**

## 1-2. Non-goals

- changing the similarity threshold
- changing verdict / candidate / grouping semantics
- changing Engine / DB semantics
- changing cache semantics themselves
- changing CPU fallback semantics
- changing CUDA correctness semantics
- **changing the SSIM formula itself**
- changing mirror matching / crop matching meaning
- adding threads, adding a worker pool, adding GPU parallelism
- "just make the cache bigger"
- "just reduce SSIM calls unconditionally"
- "arbitrarily drop candidates"

## 2. Hypothesis

> In the expensive verify path, **reusing the decode/buffer/SSIM inputs that
> the same verdict needs, or removing duplicated work**, can reduce the
> average expensive-verification time while keeping verdict semantics
> unchanged.

### Code basis for the hypothesis (the point D9a measurement pointed at)

`src/image_verify.cpp::verifyImagePair()` per call:

```cpp
verifyBuffersFor(pathA, fA, aA, tel)   // 2 decodes (64x64 full + aspect)
verifyBuffersFor(pathB, fB, aB, tel)   // 2 decodes
ssimBuf(fA, fB)                        // 1 call
fullA = centerCropResize(aA, ...)      // 1
fullB = centerCropResize(aB, ...)      // 1
for (asp : {4/3, 1, 9/16}) {
  rA = centerCropResize(aA, asp)       // 1
  rB = centerCropResize(aB, asp)       // 1
  ssimBuf(rA, rB) / ssimBuf(fullA, rB) / ssimBuf(rA, fullB)   // 3
}
```

So per call:

```
centerCropResize   2 (full) + 3 x 2 (aspect) = 8     recomputed every call
ssimBuf            1 + 3 x 3 = 10
  +-- flipBuf      1 per ssimBuf -> 10              recomputed every call
  +-- frame_ssim   2 per ssimBuf -> 20
```

**The duplication D9a measured**: 9 of the 10 `ssimBuf` calls are aspect
combinations, and the same `GrayImage` is recomputed repeatedly. `flipBuf` is
rebuilt inside every `ssimBuf`, although the flipped `b` can be identical
within an aspect.

### Measurable prediction (pre-registered)

If the hypothesis holds, these must change after implementation:

```
frame_ssim call count decreases    (buffer reuse actually removes duplication)
centerCropResize call count decreases
ms per expensive verify decreases
```

**What must NOT change (this is the core success condition)**

```
verifyCalls                     158,020   identical
expensive verify count          13,734   identical
verifyHitRate                     0.5286  identical (lookup count unchanged)
groups                          156,152   identical
verdict / similarity results    identical (bit-level comparison)
```

## 4. Risk (not assuming safety just because the verdict logic is untouched)

| Risk | Description |
| --- | --- |
| **Verdict semantics change** | A subtle difference in SSIM input order/content can shift `0.5*hamming + 0.5*SSIM` and move the threshold verdict |
| **CPU/GPU parity change** | Divergence between the hash path and the verify path |
| **Image similarity result change** | The same image could receive a different score |
| **Stale/incorrect buffer use** | A reused cache could reference another file's decode result |
| **Decode result vs SSIM input mismatch** | The correspondence between the full and aspect buffers could break |

→ These risks must be **proven absent by measurement** after implementation;
code review alone is not a safety claim.

## 5-1. Compatibility Risk

| Target | Risk | Handling |
| --- | --- | --- |
| Windows CPU | the verify path is shared, so CPU results could change | CPU CTest + parity verification required |
| Windows GPU (CUDA) | divergence between the hash path and the verify path | GPU CTest + `cuda_backend_test` + CPU/GPU parity |
| Linux | pure C++ path, so the same verification target | separate parity check |
| benchmark JSON | adding telemetry requires a schema bump | additive only, existing keys kept |
| DB / cache format | must not change | regression check |
| Future GPU backends | no CUDA-specific code may spread upward | handled only inside the backend abstraction |

## 5-2. Expected Outcome

Success requires **all** of:

```
- per-expensive-verify cost actually decreases
- total verify time actually decreases
- measurable under identical conditions
- final verdict parity preserved
- group parity preserved (groups 156,152)
- CPU/GPU parity preserved
- all existing tests PASS (none deleted or relaxed)
- complexity growth is reasonable
```

**A shorter total runtime alone is not recorded as PASS.** If the dataset
changed, the result is not described as a direct improvement over D9a. A cost
reduction at the level of measurement noise trips stop condition 7.

## 6. Stop Conditions

Abort the optimization if any of the following occurs:

1. **Verdict or grouping results change**
2. **CPU/GPU parity breaks**
3. **Decode results differ**
4. **A CUDA correctness problem appears**
5. **Measurement reliability cannot be established**
6. **The optimization only adds complexity with no measurable benefit**
7. **The cost reduction is at the level of measurement noise**
8. **Evidence appears that Candidate B is not the real bottleneck**

The failure is not hidden; it is recorded as the D9b measurement result. On
abort, telemetry/hooks stay isolated so they can be reverted cleanly.
