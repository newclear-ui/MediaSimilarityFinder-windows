# 작업 내역 — 0.9.4 개발선

구현 기준: `ffd64e8` (0.9.4.24 코드 상태) · 문서 등록 HEAD: `374dbaf`
범위: Node D 잔여 정리 → Dataset 기반 구축 → 병목 실측 → 병목 규명 → settings identity

English version: `docs/worklog/0.9.4.en.md`

## 1. 한 줄 요약

파이프라인 최적화(Node D)를 **측정 근거로 종료**하고, 비교가 불가능했던 상태를
해소한 뒤, 진짜 병목인 매칭 단계를 계측해 **원인을 규명**했다.
마지막으로 배포물의 개인 식별자를 제품명으로 교체하고 기존 사용자 설정을
안전하게 이관했다.

```
"성능이 좋아졌다"가 아니라
"이 workload 에서 D 는 못 한다"를 증명하고,
진짜 병목이 어디인지 measurements 로 규명했다.
```

## 2-1. Performance / Tuning Experiment Index

> **이 표는 영구 삭제 대상이 아니다.** `NOT ACCEPTED` / `REJECTED` / `DEFERRED` /
> `LOW PRIORITY` 는 **현재 조건에서의 판정**이며, 아래 "재검토 조건"이
> 충족되면 다시 유효해질 수 있다. 성공한 최적화뿐 아니라 **기각된 가설과 그
> 근거**를 남기는 것이 이 인덱스의 존재 이유다.
>
> 상세 수치와 실행 조건은 각 Build History 에 있고, 이 표는 실험 간 관계와
> 판단 흐름만 연결한다. 같은 가설을 반복 실험하지 않기 위한 색인이다.

| ID | Version | Target | Hypothesis / Question | Result | Key Evidence | Status |
| --- | --- | --- | --- | --- | --- | --- |
| D9a | 0.9.4.23 | verify stage | verify 가 전체 병목인가 | confirmed | verify ≈ analyze 의 99.67 % | **BASELINE** |
| D9b | 0.9.4.25 | aspect/buffer | 중복 준비 비용이 크다 | no measurable gain | 전 카운터 D9a 와 동일 | **NOT ACCEPTED** |
| D9c | 0.9.4.26 | expensive verify | 8.5 ms 가 어디에 쓰이는가 | measured | decode 94.90 % / frame_ssim 0.55 % | **PASS** |
| D9d | 0.9.4.26 | decode | decode 내부의 병목은 | measured | open 62.15 % + factory 27.39 % | **PASS** |
| D1 | 0.9.4.27 | open / factory | 왜 비싼가 | WIC decoder 경로 | fallback 0 %, OS open 0.0576 ms | **PASS** |

### 계보

```text
D9a  verify 가 병목임을 확인
 ↓
D9b  후보 B(expensive verify 비용 감소) → NOT ACCEPTED
 ↓   비관측: aspect buffer "중복" 은 원본에서도 이미 재사용되고 있었다
D9c  expensive verify 내부 계측 → decode 94.90 %
 ↓
D9d  decode 내부 계측 → open 62.15 % + factory 27.39 %
 ↓
D1   open/factory 원인 계측
     → Factory2 fallback 기각 (25,898회 중 0회)
     → raw OS file open 기각 (0.0576 ms, open 의 2.2 %)
     → WIC decoder creation 으로 수렴
```

### 측정 방법론에서 얻은 교훈 (실험 인프라)

- **Profiling telemetry 자체가 검증 대상이다.** D1 첫 구현은 누적 합계를 다시
  합산해 `factoryMs = 235,023,895 ms` 를 냈다. 그럴듯한 수치라는 이유로
  자동 신뢰하지 않고, pre-register 의 "분해가 원래 총합을 재구성해야 한다"는
  조건이 즉시 잡았다. 이 bug 와 D9d↔D1 factory 수치 차이는 **제품 성능 변화가
  아니라 measurement implementation 차이**이며, 0.9.4.27 build history 에
  원인과 수정값이 함께 남아 있다.
- **관찰된 연산량 ≠ 실제 병목.** 이 개발선에서 코드 독해로 세운 병목 가설이
  다섯 차례 측정에서 뒤집혔다(캐시 32, scoring 중복, decode 내부, Fant/EXIF,
  Factory2 fallback). 연산량 proxy 로 병목을 추정하는 방식은 반복해서
  실패했다.
- **측정은 후보를 삭제하는 일이 더 많다.** 삭제된 후보는 되돌아오지 않지만
  잘못된 채 살아남은 후보는 반복해서 비용을 낸다.
- **측정 오차 안의 차이는 개선이 아니다.** run 간 편차 3.7~7.5 % 환경에서
  1~2 % 차이를 개선으로 선언하지 않는다.

## 3. 핵심 흐름

### 3.1 측정 없이는 판단할 수 없었다 (0.9.4.19 → 0.9.4.20)

D3-Minimal 과 D4a 를 통과했지만 **비교 기준이 없었다.**
"같은 조건에서 두 상태를 비교한다"는 말 자체가 성립하지 않았다.

D4a 실측(합성 16/256장)에서 kernel device time 이 배치 크기에
**비례해 증가하지 않는다**는 것까지 확인했고, 동시에 이건 대표
dataset 이 아니므로 **D4b 결론으로 쓸 수 없다**고 명시했다.

### 3.2 결론: 코드 문제가 아니라 근거 부재 (0.9.4.21)

> "가장 큰 병목은 코드가 아니라, 동일 조건의 end-to-end 비교를 수행할 수
> 있는 재현 가능한 대표 데이터셋이 없다는 것이다."

D8a 는 성능 최적화가 아니라 **비교 재현성 기반**을 만들었다.
조사 결과에 따라 세 가지를 결정했다.

- **binary asset 미커밋** 관례(트랙 495개 전부 텍스트) → 생성 스크립트 방식
- **`msf_core` 에 암호 해시 없음** (Qt `QCryptographicHash` 는 GUI 전용,
  openssl 없음) → SHA-256 직접 구현 (NIST 벡터 4종 검증)
- **ffmpeg 출력이 byte 비재현적** → video 는 제외하고 별도 과제로 문서화

dataset identity 는 절대경로·timestamp·하드웨어명을 **포함하지 않으므로**
동일 내용 복사본은 다른 root 에서도 동일 fingerprint 다.

### 3.3 D8a 의 판정이 무효였음을 스스로 증명 (0.9.4.22)

60개 8×8 파일 dataset 으로는 "이득 없다"가 **근거가 되지 못했다.**
pipeline 이 아무 일도 하지 않으므로 `maxDepth = 1` 은 구조가 아니라
**dataset 크기**를 기술한 것이었다.

그래서 dataset 을 의도적으로 비대칭으로 확장했다.

| 축 | 구성 | 목적 |
| --- | --- | --- |
| walk 축 | `tree/` 2,400개, 240 디렉토리 | producer enumeration 비용 |
| decode 축 | `bulk/` 240장 256×192 | consumer decode+crop+thumbnail 비용 |

queue 는 consumer 비용이 producer 비용보다 클 때만 깊어지므로
**양쪽 축을 독립적으로 조절**해야 했다.

결과:

```
walker maxDepth   1 → 964 mean / 1076 max  (capacity 23.5 %)
blocked_ticks     0  (producer 는 한 번도 block 되지 않음)
gpu_batch share   0.34 % → 0.026 %
analyze           엔진 wall 의 98.62 %
D3+D4 상한        0.044 %
```

→ **D4b overlap 과 Full D3 topology 를 근거로 보류.** 그리고 병목이
D brief 범위 밖이라 **Node I 를 신설**했다 (변경 관리 5단계 기록).

### 3.4 가설이 측정으로 뒤집혔다 (0.9.4.23)

코드만 읽고 세운 가장 유력한 가설:

> `kVerifyCacheMax = 32` 라서 2,700 파일 기준 캐시가 거의 안 맞고
> 재디코드 비용이 98 % 를 설명한다.

**결과: 적중률 0.5286 — 기각.** 후보 쌍이 인덱스 순으로 집중 방문해서
32-entry 캐시도 절반은 맞는다. 캐시 용량 확대는 99.67 % 를 설명하지 못한다.

실제 지배 구조:

```
verifyCalls 158,020  (가능 쌍 3,641,700 의 4.3 %)
  ├─ ~144,286 (91.3 %)  kFast 단축, 거의 무비용
  └─ ~ 13,734 ( 8.7 %)  buffer 조회 2회 + ssimBuf 10회 (frame_ssim 20회)
                        각 ~8.5 ms → 117 초
```

→ 병목은 **건당 비용이 아니라 verify 게이트에 도달하는 후보 쌍의 수.**

카운터 정합성으로 계측 자체를 신뢰성 검증:
`ssimEvals/10 == (misses+hits)/2 == 13,734` **정확히 일치.**

### 3.5 배포물의 개인 식별자 (0.9.4.24)

QSettings organization 이름이 곧 설정 폴더명이므로, GitHub 계정명
`newclear-ui` 가 그대로 배포물에 나가 있었다.

단순 rename 은 기존 사용자의 UI 상태를 초기화처럼 보이게 하므로,
삭제를 **엄격한 순서**로만 수행하도록 만들었다.

```
복사 → 실제 QSettings 로 새 INI open → status()==NoError
     → 핵심 key 존재 확인 → 그때만 legacy 제거
     → 디렉터리는 비었을 때만 rmdir
```

어떤 실패 경로에서도 legacy 가 보존된다. 새 위치가 있으면 그쪽이 승리하고
legacy 는 그대로 두므로 **idempotent** 하다.

## 4. 이 작업에서 지키 못한 / 남은 것

### 근거로 보류한 최적화 (구현하지 않음)

| 항목 | 보류 근거 |
| --- | --- |
| D4b transfer/compute overlap | GPU hash 전체가 스캔의 0.026 %. 상한 0.044 % |
| Full D3 queue topology | `blocked_ticks = 0`. 되돌릴 **관측된 손실이 없음** |
| D5 batching / D6 worker / D7 dispatch | D3+D4 가 0.044 % 라 선행 근거 없음 |
| verify cache 용량 확대 | **측정으로 기각** (적중률 0.53) |

### D9a 가 식별했지만 구현하지 않은 다음 후보

1. verify 게이트 도착률 4.3 % 낮추기 — 단 verdict semantics 를 건드릴 수 있음
2. 비싼 검증 1건의 8.5 ms 낮추기 — 디코드 4회 + `frame_ssim` 20회,
   `ssimBuf` 10회 중 9회가 aspect 조합이며 buffer 재사용 없음

**어느 방향이 옳은지는 다음 substep 의 pre-register 를 먼저 써야 결정 가능.**

### 명시적 한계

- dataset 이 **합성 deterministic fingerprint** 이므로 실사용 라이브러리의
  후보 쌍 비율은 다를 수 있다. 모든 결론은 **"이 dataset 에서"** 의 결론.
- video 는 여전히 dataset 에 없다 (`analyzeVideoMs` = `not_measured`).
  video 경로 판단은 video dataset 확보 후 별도 과제.
- ffmpeg 비결정성으로 video fixture 는 아직 없다.

## 5. 이 작업에서 학습한 방식 (재사용 가치)

### 5.1 pre-register 를 코드 변경 **전** 커밋

```
0fc3344  D9a pre-register      (코드 변경 전)
f46658e  D9a implementation    (검증 후)
```

커밋 순서만으로 "약속을 먼저 세웠는지"가 감사된다. 이 순서를
D4a · D8a · D8b · D9a 네 번 반복했다.

### 5.2 가설을 코드에서 세우고 측정으로 깬다

가장 크게 배운 지점이다.

```
가설: 캐시 32 가 재디코드 원인
결과: verifyHitRate 0.5286 → 기각

기각된 가설 덕분에 캐시 확대 작업(시간 낭비)을 하지 않았다.
```

"가설 ≠ 측정된 병목"을 문서와 코드 주석 양쪽에 명시했다.

### 5.3 계측이 자기 자신을 검증하게 만들기

```
ssimEvals / 10          = 13,734
(misses + hits) / 2     = 13,734   ← 서로 독립 경로
```

두 값이 일치한다는 사실이 계측이 서로 모순되지 않다는 증거다.

### 5.4 무관한 것을 건드리지 않기

- QuickLook 레지스트리 조회(`NativeFormat` + 명시 path) — organization 과 무관
- `Index` 저장 구조, DB schema, Engine version — 전부 불변
- CUDA / Scheduler / threshold / verdict — 계측 단계에서 미변경

### 5.5 cross-process 테스트로 진짜 디스크를 검증

같은 프로세스 read-back 은 QSettings 인메모리 캐시로 인해 **디스크
영속성이 깨져도 통과**한다. migration 테스트를 5개 phase 로 프로세스를
분리해 이 함정을 피했다.

## 0.9.4.25 — D9b (Candidate B) 실패 기록

**성공이 아니라 실패로 기록한다.** 근거 기반 기각의 연속이 이어졌다.

가설: expensive verify 의 중복 buffer/SSIM 준비를 제거하면 비용이 준다.
결과: **카운터가 하나도 변하지 않았고 시간도 줄지 않았다.**

원인은 측정으로 확정되었다. 호출당 작업량:

```
frame_ssim        20회 x 4,096 inner loop = 81,920 ops   <- 전부의 지배
centerCropResize   8회 x 1,024 픽셀     =  8,192 ops   <- D9b 가 2,048 만 제거
```

D9b 는 전체 작업의 **2.3%** 만 건드렸고, `frame_ssim` 의 81,920 ops 는
한 번도 줄이지 못했다. 더 나아가 **가설이 지목한 중복이 원본에 없었음**이
밝혀졌다 — 원본도 이미 aspect 버퍼를 루프 밖에서 1회만 계산하고 있었다.

### 이 세션에서 다시 확인된 것

- **가설은測정해야 한다.** D9a 는 캐시 32 가설을 기각했고,
  D9b 는 "중복 제거" 가설을 기각했다. 두 번 연속 코드 리뷰만으로는
  병목을 못 짚었다.
- **관찰과 추론을 구분해야 한다.** "9/10 이 aspect 조합" 은 **관찰**로
  맞았지만 "그것이 병목" 은 **잘못된 추론**이었다. 관찰이 비용이라는
  결론이 뒤따르지 않는다.
- **안전하지만 쓸모없는 변경도 실패다.** parity 는 지켰고 테스트도 모두
  통과했지만, 성공 조건(비용 감소)을 충족하지 못했으므로 NOT ACCEPTED.

### 남은 방향

- `frame_ssim` 자체 감소는 결과에 영향을 줄 수 있어 **별도 pre-register 필요**
- 후보 A 는 계속 deferred — verdict semantics 접촉 위험

## 0.9.4.26 — D9c 내부 비용 계측 (instrumentation)

**D9b 실패의 원인이 측정으로 확정됐다.**

D9b 는 "채점 경로의 buffer 재계산이 병목"이라는 가설로 실패했다. D9c 는
가설이 아니라 계측으로 답을 냈다.

```text
expensive verify 1건 = 8.564 ms

decode             94.90 %   <- 진짜 병목
frame_ssim          0.55 %   <- D9b 가 최적화한 곳
```

`frame_ssim` 은 D9b 가 "거의 전부"라고 추정한 그 단계였고, 실제로는
0.047 ms 였다. decode 는 그보다 173배 비싸다.

### 세 번째 반복에서 얻은 교훈

이 development 선에서 측정이 기각시킨 가설이 이제 세 번이다.

```text
D9a  "verify cache 32 가 병목"      -> 기각
D9b  "채점 경로의 중복 계산이 병목"   -> 기각
D9c  계측 -> decode 가 94.90 %       -> 확정
```

D9a 와 D9b 는 둘 다 **코드 독해로 병목을 추정**했다. D9b 는 심지어 이미
재사용되고 있던 코드를 다시 재사용하는 구조로 바꿨다. 두 번 다 관찰은
맞았는데("9/10 이 aspect 조합", "동일 buffer 반복") 그 관찰이 비용이라는
추론이 틀렸다.

**반복되는 패턴: "관찰된 작업량 ≠ 실제 병목."** 연산량 proxy 로 병목을
추측하는 방식은 이 코드베이스에서 세 번 연속 실패했다. 다음부터 병목 가정은
**pre-register 에 관측 계측을 포함**해야 한다.

### 이번 빌드가 남긴 것

- 정답: expensive verify 비용의 94.90 % 는 이미지 decode 다.
- D9a 가 유도한 "약 8.5 ms" 가 8.564 ms 로 직접 측정됐다.
- 미측정으로 남긴 것(추정하지 않음): `frame_ssim` 내부, decode 내부.
- 카운터가 드러낸 구조: 같은 파일을 miss 마다 2번 디코드, cache hit 에도
  64KB quick-hash 를 읽고 해시(363.3 MB).
- 정합성: 전 카운터와 groups 156,152 가 D9a 와 동일. parity 25 + instrumentation PASS.

### 다음

**후보 D — 이미지 decode 비용.** 단 먼저 4.31 ms decode 를 factory/decoder

## 0.9.4.26 — D9d decode 내부 분해 (measurement)

D9c 가 decode 를 94.90 % 라는 **하나의 영역**으로 측정했다. 그 안에 무엇이
있는지 이번에 분해했다.

```text
decode 4.4654 ms/call
  open    62.15 %   파일 열기 + decoder 생성
  factory 27.39 %   호출마다 WIC factory COM 생성
  copy     5.15 %   실제 이미지 압축 해제
  나머지   5.31 %
```

**이 측정이 기각시킨 것들.** 이 개발선에서 네 번째이다.

```text
D9a  "cache 32 가 병목"                  -> 기각
D9b  "채점 경로 중복이 병목"               -> 기각
D9c  "decode 가 병목"                     -> 확정 (94.90%)
D9d  "Fant / EXIF 가 decode 안의 병목"      -> 기각 (0.32% / 0.17%)
```

`WICBitmapInterpolationModeFant` 는 이름부터 고품질 보간이라 비싸 보이지만
0.32 % 다. EXIF metadata 조회도 0.17 % 다. 반대로 이름에서 드러나지 않는 쪽,
즉 파일 열기와 COM factory 생성이 89.55 % 였다.

그리고 "decode 가 비싸다"는 직관이 가리키는 실제 압축 해제(`copy`)는 5.15 %,
비용의 20분의 1 이었다.

### mutex 에 대한 두 번째 기각

D9c 는 "verify cache 의 전역 mutex contention 이 있을 수 있다"고 남겨뒀다.
D9d 가 측정했다.

```text
wait 0.0002 ms/acquire    hold 0.0018 ms/acquire
lock 총시간 = decode 의 0.07 %
```

병목이 아니다. 추측이 아니라 측정으로 종결했다. 이에 따라 D9c 의 `other`
버킷(0.42 %)에 숨은 contention 이 없다는 것도 함께 확인된다.

### 이 개발선의 누적 교훈

네 번 연속, 코드 독해로 세운 병목 가설이 측정에서 무너졌다. D9d 는 그 반복을
끝내는 것이 아니라 **그 반복을 근거로 잘라내는 일**을 했다. Fant 와 EXIF 는
이제 지식이 아니라 측정값으로 배제되었고, "다음에는 이것을 보자"가 아니라
"다음에는 2.77 ms open 과 1.22 ms factory 부터 분해하라"로 narrowed 됐다.

좋은 흐름의 계측은 답을 주는 것만이 아니라 **답을 지우는 것도** 한다.
이전에는 없던 질문("mutex 가 문제인가")이 measurement 로 닫혔고,
있던 질문("decode 안의 무엇인가")이 두 개로 좁혀졌다.

## 0.9.4.27 — D1: 왜 file open 과 factory 가 비싼가

D9d 는 `open + factory` 가 decode 의 89.55 %, verify 전체의 84.93 % 라고
측정했다. 그 안이 무엇인지는 몰랐다. 이번에 두 질문에 답했다.

```text
질문 B: Factory2 는 성공하는가?
  attempts 25,898 / successes 25,898 (100%) / fallbacks 0

질문 A: open 2.6 ms 는 어디에서인가?
  OS CreateFileW        0.0576 ms  (2.2%)
  WIC 내부             2.5682 ms  (97.8%)
```

### 두 가지가 삭제되었다

이 빌드의 가장 큰 산출은 "무엇을 최적화할 것인가"가 아니라 **무엇을 하지
않을 것인가**다.

1. **Factory2 fallback 제거** — 25,898회 중 fallback 이 **0회**다. 이 머신에
   제거할 낭비가 없다. "첫 시도가 낭비다"는 가설이measurement로 기각됐다.
2. **파일 핸들 / 스트림 관리 최적화** — 실제 OS 비용은 0.0576 ms, `open` 의
   2.2 %. 파일을 여는 비용이 아니라 WIC 가 decoder 를 만드는 비용이었다.
   `open` 이라는 이름이 오해를 만들고 있었다.

이 두 개는 이름과 직관이 자연스럽게 끌어들이는 후보였다. 어느 것도 측정되지
않았다면 그대로 구현되었을 것이고, 어느 것도 효과为零였을 것이다.

### 측정이 계측 버그를 잡았다

첫 구현이 `factoryMs = 235,023,895 ms` 를 냈다. 약 2분 작업에 터무논할 수 없는
값이었다. 공통 헬퍼가 **누적 합계**에 기록하는데 호출 지점이 그 합계를 매번
다시 더해 제곱으로 증가한 것이었다.

pre-register 에 "분해가 `factoryMs` 를 재구성하지 못하면 중단"이라고 적어둔
것이 이 버그를 정확히 잡았다. 만약 그 등식 검사가 없었다면, 버킷이 덜 눈에
띄었을 것이고, 그럴듯해 보이지만 틀린 비율이 보고되었을 것이다.

**accounting 은 측정값의 전제조건이지 마무리 장식이 아니다.**
