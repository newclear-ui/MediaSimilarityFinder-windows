## 1. 한 줄 요약

파이프라인 최적화(Node D)를 **측정 근거로 종료**하고, 비교가 불가능했던 상태를
해소한 뒤, 진짜 병목인 매칭 단계를 계측해 **원인을 규명**했다.
마지막으로 배포물의 개인 식별자를 제품명으로 교체하고 기존 사용자 설정을
안전하게 이관했다.

```
"성능이 좋아졌다"가 아니라
"이 workload 에서 D 는 못 한다"를 증명하고,
진짜 병목이 어디인지 measurements 로 규명했다.
```

## 2-1. Performance / Tuning Experiment Index

> **이 표는 영구 삭제 대상이 아니다.** `NOT ACCEPTED` / `REJECTED` / `DEFERRED` /
> `LOW PRIORITY` 는 **현재 조건에서의 판정**이며, 아래 "재검토 조건"이
> 충족되면 다시 유효해질 수 있다. 성공한 최적화뿐 아니라 **기각된 가설과 그
> 근거**를 남기는 것이 이 인덱스의 존재 이유다.
>
> 상세 수치와 실행 조건은 각 Build History 에 있고, 이 표는 실험 간 관계와
> 판단 흐름만 연결한다. 같은 가설을 반복 실험하지 않기 위한 색인이다.

- **Profiling telemetry 자체가 검증 대상이다.** D1 첫 구현은 누적 합계를 다시
  합산해 `factoryMs = 235,023,895 ms` 를 냈다. 그럴듯한 수치라는 이유로
  자동 신뢰하지 않고, pre-register 의 "분해가 원래 총합을 재구성해야 한다"는
  조건이 즉시 잡았다. 이 bug 와 D9d↔D1 factory 수치 차이는 **제품 성능 변화가
  아니라 measurement implementation 차이**이며, 0.9.4.27 build history 에
  원인과 수정값이 함께 남아 있다.
- **관찰된 연산량 ≠ 실제 병목.** 이 개발선에서 코드 독해로 세운 병목 가설이
  다섯 차례 측정에서 뒤집혔다(캐시 32, scoring 중복, decode 내부, Fant/EXIF,
  Factory2 fallback). 연산량 proxy 로 병목을 추정하는 방식은 반복해서
  실패했다.
- **측정은 후보를 삭제하는 일이 더 많다.** 삭제된 후보는 되돌아오지 않지만
  잘못된 채 살아남은 후보는 반복해서 비용을 낸다.
- **측정 오차 안의 차이는 개선이 아니다.** run 간 편차 3.7~7.5 % 환경에서
  1~2 % 차이를 개선으로 선언하지 않는다.
- **판정의 대조 쌍은 반드시 같은 세계여야 한다 (0.9.4.32).** 0.9.4.31 probe
  의 "기준선" 점수에 이전 파일의 **후보** 버퍼가 섞여 있었다. 결과는 flip 2건과
  "R 증가 → delta 증가(2.63→9.19)"처럼 지우간한 단조 경향으로 나왔고, 5회
  재현이라 재현성은 충분했다. 재현성은 정확성을 보장하지 않는다 — **재현된
  artifact 다.** D1 의 factoryMs 합계 오류와 같은 계열의 결함이며, 두 경우 모두
  "자체 정합성 검사" 가 아니라 "쌍 구성 자체의 정의" 를 의심하는 단계에서
  발견됐다. 점수 분해의 `verifyScorePlan` 합 일치는 통과했으므로, 분해가 맞아도
  쌍이 틀리면 무의미하다는 뜻이다.
- **지우간한 결과는 defect 신호로 읽어야 한다 (0.9.4.32).** 같은 족쇄로
  나온 두 가지 신호가 함께 나타났다. 하나는 R 이 커질수록 delta 가 단조 증가
  (2.63→9.19)했고, 다른 하나는 "오래된 TIFF 근사중복 쌍에서만" flip 이
  났다. 둘 다 설명 가능한 서사가었고, 그래서 오류가 아니라 발견처럼 보였다.
  측정값이 예상과 잘 맞는 순간 그 서사를 의심하는 것이 필요하다.
- **인식된 원인과 채택 여부는 분리한다 (0.9.4.32).** flip 이 artifact 라고
  규명된 뒤에도 후보는 `DEFERRED` 를 유지했다. 판정 근거가 하나 사라졌다고
  나머지 근거(byte parity 미유지, geometry 차이, pixel divergence, full-scan
  groups 미측정, EXIF/PGM 미검증)가 함께 사라지지는 않는다. 조사로 판정을
  뒤집지 않고, 판정을 지지하는 근거의 구성만 고치는 것이 맞다.

## 3. 핵심 흐름

### 3.1 측정 없이는 판단할 수 없었다 (0.9.4.19 → 0.9.4.20)

D3-Minimal 과 D4a 를 통과했지만 **비교 기준이 없었다.**
"같은 조건에서 두 상태를 비교한다"는 말 자체가 성립하지 않았다.

D4a 실측(합성 16/256장)에서 kernel device time 이 배치 크기에
**비례해 증가하지 않는다**는 것까지 확인했고, 동시에 이건 대표
dataset 이 아니므로 **D4b 결론으로 쓸 수 없다**고 명시했다.

### 3.2 결론: 코드 문제가 아니라 근거 부재 (0.9.4.21)

> "가장 큰 병목은 코드가 아니라, 동일 조건의 end-to-end 비교를 수행할 수
> 있는 재현 가능한 대표 데이터셋이 없다는 것이다."

D8a 는 성능 최적화가 아니라 **비교 재현성 기반**을 만들었다.
조사 결과에 따라 세 가지를 결정했다.

- **binary asset 미커밋** 관례(트랙 495개 전부 텍스트) → 생성 스크립트 방식
- **`msf_core` 에 암호 해시 없음** (Qt `QCryptographicHash` 는 GUI 전용,
  openssl 없음) → SHA-256 직접 구현 (NIST 벡터 4종 검증)
- **ffmpeg 출력이 byte 비재현적** → video 는 제외하고 별도 과제로 문서화

dataset identity 는 절대경로·timestamp·하드웨어명을 **포함하지 않으므로**
동일 내용 복사본은 다른 root 에서도 동일 fingerprint 다.

### 3.3 D8a 의 판정이 무효였음을 스스로 증명 (0.9.4.22)

60개 8×8 파일 dataset 으로는 "이득 없다"가 **근거가 되지 못했다.**
pipeline 이 아무 일도 하지 않으므로 `maxDepth = 1` 은 구조가 아니라
**dataset 크기**를 기술한 것이었다.

그래서 dataset 을 의도적으로 비대칭으로 확장했다.

| 축 | 구성 | 목적 |
| --- | --- | --- |
| walk 축 | `tree/` 2,400개, 240 디렉토리 | producer enumeration 비용 |
| decode 축 | `bulk/` 240장 256×192 | consumer decode+crop+thumbnail 비용 |

queue 는 consumer 비용이 producer 비용보다 클 때만 깊어지므로
**양쪽 축을 독립적으로 조절**해야 했다.

결과:

```
walker maxDepth   1 → 964 mean / 1076 max  (capacity 23.5 %)
blocked_ticks     0  (producer 는 한 번도 block 되지 않음)
gpu_batch share   0.34 % → 0.026 %
analyze           엔진 wall 의 98.62 %
D3+D4 상한        0.044 %
```

→ **D4b overlap 과 Full D3 topology 를 근거로 보류.** 그리고 병목이
D brief 범위 밖이라 **Node I 를 신설**했다 (변경 관리 5단계 기록).

### 3.4 가설이 측정으로 뒤집혔다 (0.9.4.23)

코드만 읽고 세운 가장 유력한 가설:

> `kVerifyCacheMax = 32` 라서 2,700 파일 기준 캐시가 거의 안 맞고
> 재디코드 비용이 98 % 를 설명한다.

**결과: 적중률 0.5286 — 기각.** 후보 쌍이 인덱스 순으로 집중 방문해서
32-entry 캐시도 절반은 맞는다. 캐시 용량 확대는 99.67 % 를 설명하지 못한다.

실제 지배 구조:

```
verifyCalls 158,020  (가능 쌍 3,641,700 의 4.3 %)
  ├─ ~144,286 (91.3 %)  kFast 단축, 거의 무비용
  └─ ~ 13,734 ( 8.7 %)  buffer 조회 2회 + ssimBuf 10회 (frame_ssim 20회)
                        각 ~8.5 ms → 117 초
```

→ 병목은 **건당 비용이 아니라 verify 게이트에 도달하는 후보 쌍의 수.**

카운터 정합성으로 계측 자체를 신뢰성 검증:
`ssimEvals/10 == (misses+hits)/2 == 13,734` **정확히 일치.**

### 3.5 배포물의 개인 식별자 (0.9.4.24)

QSettings organization 이름이 곧 설정 폴더명이므로, GitHub 계정명
`newclear-ui` 가 그대로 배포물에 나가 있었다.

단순 rename 은 기존 사용자의 UI 상태를 초기화처럼 보이게 하므로,
삭제를 **엄격한 순서**로만 수행하도록 만들었다.

```
복사 → 실제 QSettings 로 새 INI open → status()==NoError
     → 핵심 key 존재 확인 → 그때만 legacy 제거
     → 디렉터리는 비었을 때만 rmdir
```

어떤 실패 경로에서도 legacy 가 보존된다. 새 위치가 있으면 그쪽이 승리하고
legacy 는 그대로 두므로 **idempotent** 하다.

## 8. D9b 비교 기준과 후보 우선순위 고정

**0.9.4.24 D9a를 향후 관련 빌드의 비교 baseline으로 고정한다.**

- D8b dataset: 2,700 files, fingerprint `9b113848…4253c`
- verifyCalls: 158,020
- verifyHitRate: 0.5286
- expensive verify: 13,734
- expensive verify: 약 8.5 ms/call, aggregate 약 117 s
- groups: 156,152

D9b의 primary는 **B — expensive verify 1건 비용 감소**다. 구현 후에는 성능뿐 아니라 `groups`, 최종 match/verdict, CPU/GPU parity를 baseline과 비교한다.

**A — candidate pair 도착률 감소**는 verdict semantics에 접촉할 위험이 있으므로 D9b에서는 구현하지 않는다. A는 폐기하지 않고 **deferred candidate**로 유지하며, 향후 별도 pre-register와 정확성 검증을 거친다.

향후 0.9.4.x 빌드에서는 가능한 경우 새 수치와 함께 **0.9.4.24 D9a baseline 대비 증감**을 기록한다. dataset / hardware / cold-index 조건이 다르면 차이를 명시하고 직접적인 성능 개선으로 단정하지 않는다.

다음 순서는 유지한다.

```
D9a baseline
→ D9b pre-register
→ commit
→ B implementation
→ build/test/measurement
→ baseline comparison
```

## 0.9.4.25 — D9b (Candidate B) 실패 기록

**성공이 아니라 실패로 기록한다.** 근거 기반 기각의 연속이 이어졌다.

가설: expensive verify 의 중복 buffer/SSIM 준비를 제거하면 비용이 준다.
결과: **카운터가 하나도 변하지 않았고 시간도 줄지 않았다.**

원인은 측정으로 확정되었다. 호출당 작업량:

```
frame_ssim        20회 x 4,096 inner loop = 81,920 ops   <- 전부의 지배
centerCropResize   8회 x 1,024 픽셀     =  8,192 ops   <- D9b 가 2,048 만 제거
```

D9b 는 전체 작업의 **2.3%** 만 건드렸고, `frame_ssim` 의 81,920 ops 는
한 번도 줄이지 못했다. 더 나아가 **가설이 지목한 중복이 원본에 없었음**이
밝혀졌다 — 원본도 이미 aspect 버퍼를 루프 밖에서 1회만 계산하고 있었다.

### 이 세션에서 다시 확인된 것

- **가설은 측정해야 한다.** D9a 는 캐시 32 가설을 기각했고,
  D9b 는 "중복 제거" 가설을 기각했다. 두 번 연속 코드 리뷰만으로는
  병목을 못 짚었다.
- **관찰과 추론을 구분해야 한다.** "9/10 이 aspect 조합" 은 **관찰**로
  맞았지만 "그것이 병목" 은 **잘못된 추론**이었다. 관찰이 비용이라는
  결론이 뒤따르지 않는다.
- **안전하지만 쓸모없는 변경도 실패다.** parity 는 지켰고 테스트도 모두
  통과했지만, 성공 조건(비용 감소)을 충족하지 못했으므로 NOT ACCEPTED.

### 남은 방향

- `frame_ssim` 자체 감소는 결과에 영향을 줄 수 있어 **별도 pre-register 필요**
- 후보 A 는 계속 deferred — verdict semantics 접촉 위험

## 0.9.4.26 — D9c 내부 비용 계측 (instrumentation)

**D9b 실패의 원인이 측정으로 확정됐다.**

D9b 는 "채점 경로의 buffer 재계산이 병목"이라는 가설로 실패했다. D9c 는
가설이 아니라 계측으로 답을 냈다.

```text
expensive verify 1건 = 8.564 ms

decode             94.90 %   <- 진짜 병목
frame_ssim          0.55 %   <- D9b 가 최적화한 곳
```

`frame_ssim` 은 D9b 가 "거의 전부"라고 추정한 그 단계였고, 실제로는
0.047 ms 였다. decode 는 그보다 173배 비싸다.

### 세 번째 반복에서 얻은 교훈

이 development 선에서 측정이 기각시킨 가설이 이제 세 번이다.

```text
D9a  "verify cache 32 가 병목"      -> 기각
D9b  "채점 경로의 중복 계산이 병목"   -> 기각
D9c  계측 -> decode 가 94.90 %       -> 확정
```

D9a 와 D9b 는 둘 다 **코드 독해로 병목을 추정**했다. D9b 는 심지어 이미
재사용되고 있던 코드를 다시 재사용하는 구조로 바꿨다. 두 번 다 관찰은
맞았는데("9/10 이 aspect 조합", "동일 buffer 반복") 그 관찰이 비용이라는
추론이 틀렸다.

**반복되는 패턴: "관찰된 작업량 ≠ 실제 병목."** 연산량 proxy 로 병목을
추측하는 방식은 이 코드베이스에서 세 번 연속 실패했다. 다음부터 병목 가정은
**pre-register 에 관측 계측을 포함**해야 한다.

### 이번 빌드가 남긴 것

- 정답: expensive verify 비용의 94.90 % 는 이미지 decode 다.
- D9a 가 유도한 "약 8.5 ms" 가 8.564 ms 로 직접 측정됐다.
- 미측정으로 남긴 것(추정하지 않음): `frame_ssim` 내부, decode 내부.
- 카운터가 드러낸 구조: 같은 파일을 miss 마다 2번 디코드, cache hit 에도
  64KB quick-hash 를 읽고 해시(363.3 MB).
- 정합성: 전 카운터와 groups 156,152 가 D9a 와 동일. parity 25 + instrumentation PASS.

### 다음

**후보 D — 이미지 decode 비용.** 단 먼저 4.31 ms decode 를 factory/decoder
설정, file open, EXIF, Fant scale, format conversion, copy 로 분해해야 한다.
D9c 는 decode 를 한 영역으로만 측정했기 때문이다. 계측 없이 최적화하지 않는다 —
D9b 가 그렇게 했다가 실패했다.

## 0.9.4.26 — D9d decode 내부 분해 (measurement)

D9c 가 decode 를 94.90 % 라는 **하나의 영역**으로 측정했다. 그 안에 무엇이
있는지 이번에 분해했다.

```text
decode 4.4654 ms/call
  open    62.15 %   파일 열기 + decoder 생성
  factory 27.39 %   호출마다 WIC factory COM 생성
  copy     5.15 %   실제 이미지 압축 해제
  나머지   5.31 %
```

**이 측정이 기각시킨 것들.** 이 개발선에서 네 번째이다.

```text
D9a  "cache 32 가 병목"                  -> 기각
D9b  "채점 경로 중복이 병목"               -> 기각
D9c  "decode 가 병목"                     -> 확정 (94.90%)
D9d  "Fant / EXIF 가 decode 안의 병목"      -> 기각 (0.32% / 0.17%)
```

`WICBitmapInterpolationModeFant` 는 이름부터 고품질 보간이라 비싸 보이지만
0.32 % 다. EXIF metadata 조회도 0.17 % 다. 반대로 이름에서 드러나지 않는 쪽,
즉 파일 열기와 COM factory 생성이 89.55 % 였다.

그리고 "decode 가 비싸다"는 직관이 가리키는 실제 압축 해제(`copy`)는 5.15 %,
비용의 20분의 1 이었다.

### mutex 에 대한 두 번째 기각

D9c 는 "verify cache 의 전역 mutex contention 이 있을 수 있다"고 남겨뒀다.
D9d 가 측정했다.

```text
wait 0.0002 ms/acquire    hold 0.0018 ms/acquire
lock 총시간 = decode 의 0.07 %
```

병목이 아니다. 추측이 아니라 측정으로 종결했다. 이에 따라 D9c 의 `other`
버킷(0.42 %)에 숨은 contention 이 없다는 것도 함께 확인된다.

### 이 개발선의 누적 교훈

네 번 연속, 코드 독해로 세운 병목 가설이 측정에서 무너졌다. D9d 는 그 반복을
끝내는 것이 아니라 **그 반복을 근거로 잘라내는 일**을 했다. Fant 와 EXIF 는
이제 지식이 아니라 측정값으로 배제되었고, "다음에는 이것을 보자"가 아니라
"다음에는 2.77 ms open 과 1.22 ms factory 부터 분해하라"로 narrowed 됐다.

좋은 흐름의 계측은 답을 주는 것만이 아니라 **답을 지우는 것도** 한다.
이전에는 없던 질문("mutex 가 문제인가")이 measurement 로 닫혔고,
있던 질문("decode 안의 무엇인가")이 두 개로 좁혀졌다.

### 다음

후보 D1 — image decoder 생성과 file open. 먼저 `open` 과 `factory` 내부를
분해해야 한다. 그리고 `CLSID_WICImagingFactory2` 시도가 실패한 뒤 fallback
하는지 확인해야 한다. fallback 이 있다면 빠른 경로가 아예 타지 않는다는
뜻이므로 그게 우선이다.

여기서 구현하지 않는다. 측정 없이 최적화하는 것이 이 개발선에서 반복된
실패의 원인이었다.

## 0.9.4.27 — D1: 왜 file open 과 factory 가 비싼가

D9d 는 `open + factory` 가 decode 의 89.55 %, verify 전체의 84.93 % 라고
측정했다. 그 안이 무엇인지는 몰랐다. 이번에 두 질문에 답했다.

```text
질문 B: Factory2 는 성공하는가?
  attempts 25,898 / successes 25,898 (100%) / fallbacks 0

질문 A: open 2.6 ms 는 어디에서인가?
  OS CreateFileW        0.0576 ms  (2.2%)
  WIC 내부             2.5682 ms  (97.8%)
```

### 두 가지가 삭제되었다

이 빌드의 가장 큰 산출은 "무엇을 최적화할 것인가"가 아니라 **무엇을 하지
않을 것인가**다.

1. **Factory2 fallback 제거** — 25,898회 중 fallback 이 **0회**다. 이 머신에
   제거할 낭비가 없다. "첫 시도가 낭비다"는 가설이measurement로 기각됐다.
2. **파일 핸들 / 스트림 관리 최적화** — 실제 OS 비용은 0.0576 ms, `open` 의
   2.2 %. 파일을 여는 비용이 아니라 WIC 가 decoder 를 만드는 비용이었다.
   `open` 이라는 이름이 오해를 만들고 있었다.

이 두 개는 이름과 직관이 자연스럽게 끌어들이는 후보였다. 어느 것도 측정되지
않았다면 그대로 구현되었을 것이고, 어느 것도 효과가 0이었을 것이다.

### 측정이 계측 버그를 잡았다

첫 구현이 `factoryMs = 235,023,895 ms` 를 냈다. 약 2분 작업에 터무논할 수 없는
값이었다. 공통 헬퍼가 **누적 합계**에 기록하는데 호출 지점이 그 합계를 매번
다시 더해 제곱으로 증가한 것이었다.

pre-register 에 "분해가 `factoryMs` 를 재구성하지 못하면 중단"이라고 적어둔
것이 이 버그를 정확히 잡았다. 만약 그 등식 검사가 없었다면, 버킷이 덜 눈에
띄었을 것이고, 그럴듯해 보이지만 틀린 비율이 보고되었을 것이다.

**accounting 은 측정값의 전제조건이지 마무리 장식이 아니다.**

### 누적 교훈 (5회째)

```text
D9a  "cache 32"           -> 기각
D9b  "채점 경로 중복"       -> 기각
D9c  decode 발견           -> 확정
D9d  Fant/EXIF            -> 기각
D1   "Factory2 fallback"   -> 기각 (0회)
D1   "파일 open"            -> 부분 기각 (OS 는 2.2%)
```

여섯 번째 build history인데, 이 접근 방식은 계속 새 후보를 **생성**하기도
하지만 더 자주 기존 후보를 **삭제**한다. 삭제가 더 값지다. 삭제된 후보는 다시
돌아오지 않지만, 잘못된 채 살아남은 후보는 반복해서 비용을 낸다.

## 2026-09-30 — Benchmark Console UI / 실행 모델 최종 결정

이번 설계에서 benchmark 실행 단위와 Console 표시 구조를 최종 확정했다.

### 결정 사항

1. **파일 단위 mode 실행**
   - 한 파일에 대해 AUTO → CPU → GPU-max를 순차 실행한다.
   - 파일별 결과를 즉시 journal에 기록한 뒤 다음 파일로 이동한다.
   - 파일 식별/입력 준비는 공유할 수 있지만 분석/디코드/intermediate 결과는 공유하지 않는다.

2. **중단 안전성**
   - Ctrl+C는 cancellation request로 취급한다.
   - 완료된 file/mode 결과는 이미 저장되어야 하며, 중단 후에도 partial Suite를 사용할 수 있어야 한다.

3. **CPU Resource Policy**
   - 기존 Maximum/High/Balanced/Gaming/Manual 10–90 정책을 그대로 사용한다.
   - 기본 Console benchmark 권장값은 Balanced 55%다.
   - Balanced 실행 결과의 선형 extrapolation으로 Maximum 실제 benchmark 결과를 만들지 않는다.

4. **Terminal UI**
   - 상단 고정영역은 3개 정보 행으로 압축한다.
   - Target/Scope/IMG·VID progress, Mode/CPU/GPU, Distance/Suite ID/Build/Git를 좌우 배치한다.
   - 자동 줄바꿈을 금지하고 긴 Target은 middle ellipsis로 화면에서만 축약한다.
   - 하단 CURRENT FILE에는 파일명과 mode별 상세 상태/시간/backend/fallback 정보를 충분히 표시한다.
   - 완료 이력은 파일당 한 줄로 누적한다.

5. **데이터와 화면 분리**
   - terminal은 view이고 journal/summary가 canonical data다.
   - Interactive와 non-interactive는 렌더러만 다르고 데이터 모델은 같다.

### 보존 원칙

## 2026-10-01 — S6 Grouping 설계 결정

### 단일 composite grouping key 를 채택하지 않은 이유

가장 고려한 설계안은 `datasetFingerprint + mediaScope + buildVersion + gitCommit +
requestedMode + effectiveMode` 을 하나로 묶는 것이었다. 구현이 가장 단순하고
report 출력도 짧아진다. **그러나 이 key 는 모든 run 을 자기 고유 그룹에 가두고,
build 간 비교를 구조적으로 불가능하게 만든다.** dataset 과 scope 는 같지만
build 가 다른 두 run 이 서로 다른 그룹에 들어가므로, 나중에 "같은 조건에서 무엇이
바뀌었나" 를 물어도 cohort 가 비어 있다.

겉으로는 정돈된 설계처럼 보이지만 실제로는 비교를 삭제하는 설계이므로 기각했다.
차후 계층이 "여러 build 를 함께 보겠다" 고 요구할 때 되돌리기 아주 어려운 결정이라
여기에 근거를 남긴다.

채택한 구조는 **분석 축별 typed key 분리**다. 각 축이 자기 질문에만 답하고,
호출부가 필요한 view 를 고른다. 두 key 를 합치는 것은 호출부의 몫이며 데이터 계층의
responsibility 이 아니다.

| view | key | 답하는 질문 |
| --- | --- | --- |
| `DatasetCohortKey` | `datasetFingerprint` | 한 dataset 을 build/mode 를 넘어 관찰 |
| `ScopeCohortKey` | fingerprint + `mediaScope` | build 간 관찰의 기준 모집단 |
| `BuildCohortKey` | `buildVersion` + `gitCommitState` + `gitCommit` | 같은 build 의 run |
| `ModeCohortKey` | `requestedMode` + `effectiveMode` | fallback/capability 관찰 |
| `CaseCohortKey` | fingerprint + `caseId` | 파일 단위 비교 |

### `caseId` 는 run-scoped 가 아니다 (실측)

S2 는 `caseId = IndexManager::folderId(file.path)` 로 canonical path 를 FNV-1a 두 번
해시한다. brief 는 이 값을 "run-scoped" 로 가정했으나 **실측 결과 run 간 동일 파일은
동일 `caseId`** 다(같은 파일을 실행한 두 run 이 동일 값을 냈다). 따라서 case 를
run 간 비교하는 것이 원래 가능했다. 그래도 단독 신뢰하지 않고 dataset fingerprint 와
짝을 이루는 key 로 쓴다. 절대경로 해시이므로 같은 값이 다른 dataset 에서 나올 수 있고,
새 hash 를 만들지 않는다는 brief 의 조건도 지켰다.

### Legacy / Unknown provenance 를 그룹으로 합치지 않는다

`gitCommit` 이 journal 에 있다는 사실과 commit 으로 비교할 수 있다는 것은 다르다.
`BuildCohortKey` 는 commit 값과 **provenance 상태를 함께** key 에 담아
Known/Unknown/Legacy cohort 를 구조적으로 분리하고, `commitComparable` 은 Known 에서만
true 로 둔다. 두 Unknown run 이 같은 binary 라는 증거는 없으므로 이 flag 로
commit 수준 비교에서 제외할 수 있게 했다. Legacy 는 필드 자체가 없으므로 현재 HEAD 로
채우지 않는다. `commitComparable` 은 **provenance 품질** 표시이며 비교 가능성 판정이
아니다.

### 실제 journal 에서 나온 확인 사항

- **`requested=CUDA` 인데 `effective=CPU` 인 record 가 실측 60건** 존재한다.
  `status=SKIPPED`, `errorMessage="mode unavailable in this environment"` 로
  GPU 미지원 환경의 fallback 이었다. requested/effective 를 합쳤다면 CUDA 실행
  60건이 CPU 실행으로 위장되어 capability 관찰이 통째로 사라진다. brief §9 가
  두 값을 분리하라고 규정한 이유가 실제 데이터에서도 확인되었다.
- **scope 는 `all` 이 실제 최댓값**이다(21/31 run). `all` 을 images+videos 로
  분해하지 않는 것이 맞다.
- **build diversity 는 부족**하다(2 cohort, 1 commit). brief §23 에 따라 부족함을
  정상으로 기록하며 다양성을 만들어내지 않았다.
- **`suite-ORDER-A/B/C` 는 S2/S5 ordering 테스트가 실제 benchmark store 에 남긴
  fixture** 이다. 각 journal 에 동일 `runId` 의 `run_started` 가 3개씩 있고
  `mode_result` 가 중복 기록되어 있다. S6-3 의 `ModeCohort` 는 (run, case, mode)
  를 **집합**으로 세므로 중복 기록을 1회로 센다(486 vs raw 494). 이 fixture 는
  S6 이전부터 있던 것이며 S6-3 가 만든 것이 아니다. 후속 단계에서 실제 store 와
  분리된 fixture 관리가 필요할 수 있다.

### 범위

이번 단계는 membership / count / provenance 만 계산한다. mean·median·p95·delta·

## 2026-10-01 — S6 Aggregation 설계 결정

### `all` 을 images/videos 로 분해하지 않는다

실제 저장소에서 `all` 이 31 run 중 22 run 이다. `all = images + videos` 로 환산하면
집계가 훨씬гля아 보이지만 **journal 이 한 `all` run 이 각 scope 에서 몇 case 를 실제로
덮었는지 기록하지 않는다.** 분배 비율을 알 수 없으므로 분배하면 그 값은 추측이 된다.
`all` 은 독립 scope 로 유지하고, elapsed 를 나눠 주지 않는다. 후속 단계에서 사용자가
`images-only` / `videos-only` / `all` 중 무엇을 원하는지 명시적으로 고르게 한다.

### SKIPPED / FAILED / CANCELLED 를 performance 모집단에서 제외한다

실측 `requested=CUDA` / `effective=CPU` / `SKIPPED` /
`mode unavailable in this environment` 60건은 **CPU 성능 관찰이 아니다.** 이를
평균에 넣으면 GPU 를 못 쓰는 환경의 기록이 CPU 속도로 위장되어 capability 관찰이
반대로 왜곡된다. `SKIPPED` 를 0 ms 로 바꾸는 것은 더 나쁘다. 0 은 "측정했다가 0" 이라는
주장이 되어 데이터에 없는 값을 만들어 넣는 것이다.

따라서 세 상태 모두 **성능 통계에서는 제외**하고 **status 집계에는 반드시 보존**한다.
제외 시 사유(`skipped`/`failed`/`cancelled`/`missingElapsed`/`invalid`)를 함께 남긴다.
사유 없는 제외 개수만 남기면 bug 와 구분되지 않는다.

level 별 포함 규칙은 서로 다르다. mode 는 `elapsedMs` 가 optional 이라
`Success` 인데 duration 이 없는 `missingElapsed` 가 가능하다. case 는 non-optional
`double` 이라 그 경우가 **존재할 수 없고** status 만으로 판정한다. run 은 terminal record
가 없으면 status 가 없으므로 Success 로 가정하지 않고 `invalid` 로 제외한다.

### raw journal duplicate 대신 logical entity 를 집계한다

실제 store 의 `suite-ORDER-A/B/C` 는 동일 journal 을 여러 번 썼다. raw line 수를 평균
모집단으로 쓰면 **여러 번 쓴 suite 가 한 번 쓴 suite 보다 무게게** 잡힌다. S6-1/2 가
복구·정규화한 logical entity 를 쓴다.

> **이 과정에서 실제 결함을 하나 발견했다.** `suite-ORDER-A/B/C` 가 **같은 `runId`**
> 를 공유한다. 즉 **accepted 31 run 에 대해 distinct runId 는 29 개**다. `runId` 만으로
> 파일 단위 집계를 하면 세 run 중 하나만 남고 나머지 두 run 의 case 가 사라진다
> (실제로 case 관측이 314 → 324 로 늘어났다). dedupe 로 처리하면 반대 방향으로
> 측정을 버린다. **journal 은 "같은 측정이 3번 기록된 것" 인지 "별개 측정 3건" 인지를
> 답해 주지 않으므로 어느 쪽으로든 임의 처리하지 않고**, `(sourceJournalPath, runId)`
> 로 keying 하고 충돌 건수만 `runsWithCollidingIdentity` 로 보고한다.
>
> 이건 S6-1 이 "31 accepted" 라고 보고할 때 드러나지 않았던 사실이므로, **runId 가
> store 유일성이라는 가정**을 S6 어느 층도 신뢰하면 안 된다는 점을 남긴다.

### run / mode / case metric 을 서로 합치지 않는다

세 값은 측정 대상이 다르다. `case_complete.elapsedMs` 는 S2 정의상 그 case 의 mode
elapsed 합이고 discovery 를 포함하지 않으며, `run wall duration` 은 1초 해상도
timestamp 파생값이다. run wall duration 에 mode 합이나 case 합으로 **보정하지 않는다**,
0 ms 를 missing 으로 재분류하지도 않고, 소수 millisecond 를 추정하지도 않는다.

이를 구조적으로 강제하기 위해 `MetricLevel` 과 `MetricResolution` 을 모든 통계 블록이
가진다. `run wall duration` 은 반드시 `OneSecond` 이고, 그 값이 0 이라는 것은
"1초 안에 시작과 완료를 마쳤다"는 뜻이지 "시간이 없었다"가 아니다.

### 각 level 이 자기 sample 을 직접 누적한다

dataset → scope → build 계층의 rollup 을 **통계값을 합쳐서** 만들면 mean of mean 이
되어 의미가 없다. 각 level 이 `SampleAccumulator` 를 갖고 최종적으로 한 번에 정렬·요약한다.

### rounding 규칙

double 합산은 순서에 따라 미세하게 달라질 수 있으므로 보고값은 소수점 6자리로 반올림한다
(`aggregationRoundMs`). 입력은 건드리지 않고 출력 형태만 고정한다.

p95 는 nearest rank 로 `n = 1`, `n = 2` 에도 **숨기지 않고** 계산하며 sample count 를
함께 보낸다. 통계 해석과 "이 표본 수로 말해도 되는가" 는 후속 단계 몫이다.
eligible sample 이 0 이면 statistic 은 존재하지 않으며(0 이 아님), 0 은 실측값이다.

### 범위

regression percentage, threshold, anomaly 판정, statistical confidence, winner 순위,
resourcePolicy/distance/gpuBackend 추론, CLI, GUI, CSV/Markdown report,
journal schema 변경은 **전부 미구현**이다.
## 2026-10-01 — S6 Comparison Eligibility 설계 결정

### `runId` 대신 `(sourceJournalPath, runId)` 를 run reference 로 사용

S6-4 에서 `accepted 31 run / distinct runId 29` 를 발견했다. `suite-ORDER-A/B/C` 가 같은
`runId` 를 공유한다. **`runId` 만으로 run 을 식별하면 세 run 중 하나만 남고 나머지가
사라진다.** 실제로 S6-5 초안에서 case 단위 집계를 `runId` 로 조회했을 때 case 관측이
잘못 누락되었다(같은 문제가 S6-4 에서 314 → 324 로 드러났다).

정식 run reference 는 `RunReference { sourceJournalPath, runId }` typed 구조체다.
같은 `(journal, runId)` 의 logical duplicate 는 S3 recovery semantics 가 이미 처리하므로
이 단계가 다시 판단하지 않는다.

### candidate 는 pairwise run 이 아니라 population-vs-population

동일 조건 반복 실행이 N 개 있으면 **run 1 대 run 1 을 짝짓지 않는다.** 그런 짝짓기는
나머지 표본을 버리고, 데이터에 없는 대응 관계를 만들어낸다. 각 side 는 자기 표본 수를
갖는 aggregate 전체이며, 그 뒤의 `RunReference` 목록은 추적 가능성만 위해 남는다.

`left < right` 가 typed key 순서로 고정되므로 어떤 쌍이든 한 번만 나오고 좌우가 매 실행
같다.

### Legacy / Unknown provenance 는 known commit comparison 에서 제외

`gitCommitState` 를 `gitCommit` 값과 **함께** 비교하므로 Known · Unknown · Legacy cohort 가
구조적으로 분리된다. commit 수준 비교는 **양쪽 모두 Known** 일 때만 가능하다.

- **Legacy**: 필드 자체가 필드 도입 이전 journal 에 없다.
- **Unknown**: writer 가 필드를 갖고 있었지만 채우지 않았다.
- **Legacy + Legacy** 를 "같은 binary" 로 간주하지 않는다. 동일 build 라는 증거가 없다.

한 가지 주의: `buildVersion` 만으로 동일 build 를 확정하지 않는다. S6-3 이 git provenance
를 추가한 목적 자체가 "같은 app version 의 다른 commit 구분" 이므로, Known commit 이 있으면
commit 이 우선한다. 같은 `0.9.4.43` 에서 `commitA` vs `commitZ` 는 정상적인 비교 후보다.

### unavailable metadata 를 "동일 조건" 으로 간주하지 않음

`distance` · `resourcePolicy` · `gpuBackend` 는 journal 에 없다. **부재는 "조건이 같다"가
아니다.** 기록이 없다는 것이지 일치했다는 뜻이 아니다.

그래서 candidate 마다 `ComparisonLimitations` 를 **9개** 함께 실어 보낸다: distance /
resourcePolicy / gpuBackend unavailable, controlled env 미정의, process isolation 비통제,
OS filesystem cache 비통제, 반복 run 부족, run wall 1초 해상도, cancellation 미관측.
`comparable=true` 만 남기고 이 제약을 버리지 않는다.

### candidate 생성과 regression 판정을 분리

이번 단계는 "비교 가능한가" 까지만 판정한다. regression %, speedup %, confidence
interval, p-value, threshold pass/fail, winner, better/worse 를 **계산하지 않는다.**
threshold 도 정하지 않는다(OS cache · process isolation · 반복 run · controlled env 문제
미해소).

### `all` 은 독립 scope 유지

`all vs all` 만 후보가 되고 `all` 을 images/videos 로 환산하지 않는다. §3-2 에서 이미
집계 단계에서 분배하지 않았으므로 비교 단계도 같은 결정을 따른다.

### CaseElapsed 은 build/mode 로 쪼갤 수 없다 (구조적 한계)

S6-4 의 `AggregatedScope`/`AggregatedDataset` 에 `caseElapsed` 가 있고
`AggregatedBuild` 에는 **없다.** 즉 case elapsed 는 dataset+scope 단위일 뿐 build 별·
mode 별로 쪼개진 값이 존재하지 않는다. 그래서 case elapsed 의 build 비교와 mode 비교는
**수치가 존재하지 않는 candidate** 가 아니라 `InsufficientData` 로 기록된다.

실제 저장소에서 `images` scope 에 이미 build 별 run wall 표본이 **1 과 5** 존재한다.
Legacy 인 쪽에만 `gitCommit` 이 있었다면 지금 바로 build-vs-build 후보가 되었을 데이터다.
**provenance 부재가 데이터 부족의 원인** 이라는 실측 근거다.

### 상태명에 대한 주의

S6-5 의 eligibility 는 benchmark execution status 가 아니라 **분석 비교 가능성 상태** 다.
S2 의 `BenchmarkStatus` 와 어휘를 공유하지 않으므로, 취소된 run 과 비교 불가능한
비교가 서로 다르게 보인다. 상태는 9종:
`Eligible` / `MismatchedDataset` / `MismatchedScope` / `MismatchedMetric` /
`MismatchedMode` / `MissingProvenance` / `SameProvenance` / `NoComparableSamples` /
`InsufficientData`.

판정 순서도 의도적이다. dataset 동일성을 가장 먼저 확인한다 — "다른 dataset" 이 더 근본적인
이유이므로, 호출자가 그것을 알기 위해 다른 조건까지 살펴볼 필요가 없어야 한다.

regression percentage, speedup, anomaly, threshold, confidence, p-value,

## 2026-10-01 — CaseElapsed 의 Build / Mode 축 보완 (S6-4 구조적 보완)

### 무엇이 빠졌는가

S6-4 는 `caseElapsed` 를 `AggregatedScope` / `AggregatedDataset` 에만aggregating했다.
`AggregatedBuild` 와 `AggregatedMode` 에는 없었다. 그래서 S6-5 는

```text
same dataset + same scope + build A  vs  build B
```

의 case-level 비교를 **제시할 수 없었다.** 측정이 없는 것이 아니라 **축이 없는** 상태였다.
S6-5 는 그때 `InsufficientData` 로 거절했고, 그 기록이 오히려 문제를 드러냈다.

### 새 측정이 아니라 추가 projection

이번 보완은 **새 측정을 만들지 않는다.** S6-2 가 이미 정규화해 둔
`case_complete.elapsedMs` 를 Build / Mode 축에서도 집계해 보존할 뿐이다.
S1 의 normalized 의미도, S6-4 의 기존 Run/Case/Mode semantics 도 그대로 유지했다.

Build 축은 거의 공짜였다. `placeRun()` 이 이미 dataset · scope · build 세 cell 모두에
case 를 넣고 있었는데 **내보내지 않았을 뿐**이었다. Mode 축만 새로 계산했다.

### Mode 축은 "분배"가 아니라 "필터" 다 (가장 중요한 결정)

`case_complete.elapsedMs` 는 S2 정의상 **그 case 의 모든 mode elapsed 합**이고, journal 은
그 분할을 기록하지 않는다. 그래서 case 합을 mode 사이에 나누면 **측정되지 않은 계수를
발명**하는 것이 된다. 금지했다.

대신 mode cohort 마다 그 mode semantics 가 **실제로 실행된 case 만** 필터한다.

```text
CPU/CPU   는 CPU가 성공한 case 2개  -> 100, 200  (mean 150)
AUTO/CPU  는 AUTO가 성공한 case 1개 -> 100        (mean 100)
```

두 모집단은 **의도적으로 겹친다.** 두 mode 가 모두 성공한 case 는 양쪽에 모두 들어간다.
따라서 이 두 통계는 **더할 수 없고**, case 별 비교는 기존 per-file view 가 담당한다.
겹침은 숨기지 않고 `caseAccounting.observed` 로 각 cohort 가 스스로 밝힌다.

**SKIPPED 는 아무것도 넣지 않는다.** `requested=CUDA / effective=CPU / SKIPPED` case 는
그 cohort 의 case 모집단에서 제외된다. CPU case performance sample 로 만들지 않는다는
S6-4 규칙을 case 축에도 그대로 적용했다.

### Build 축은 같은 build 의 scope 합과 같다

`AggregatedBuild.caseElapsed` 와 `AggregatedScope.caseElapsed` 는 **같은 표본을 두 단계로
본 것**이다. 합산 대상이 아니며, 어느 쪽을 써도 값은 동일하다. build 별로 쪼개야 할 때
build 축을 쓴다.

## 2026-10-01 — S6 Comparison Metrics: 수치 계산은 판정이 아니다

### left/right deterministic ordering ≠ baseline/target

S6-5 의 `left < right` 는 typed key 순서이며, 쌍을 재현 가능하게 만드는 것이 전부다.
**baseline 이 아니다.** `left = old`, `right = new` 로 읽지 않는다.
`left = better`, `right = worse` 로도 읽지 않는다.

순서가 방향을 암시하도록 만들면, **그 순서가 조용히 방향을 선택**하게 된다. 그래서
ComparisonMetrics 는 orientation 을 **결정적 순서**로만 유지하고 public 의미를 부여하지
않는다. baseline 을 명시적으로 지정하는 단계가 올 때 그때 역할을 부여하면 된다.

### raw comparison ≠ regression judgement

```text
absoluteDelta        = right - left                       (ms)
relativeDeltaPercent = ((right - left) / left) * 100
ratio                = right / left
```

`relativeDeltaPercent = +50%` 는 **+50% 로 보고한다.** regression 도 improvement 도
better/worse 도 winner 도 아니다. 그것이 회귀인지 판단하는 것은 이후 decision layer 의
책임이며, 그 layer 는 아직 없다. **threshold 를 정의하지 않았으므로 여기서 pass/fail 도
구조상 불가능하다.**

이 layer 의 어휘에 방향을 나타내는 항목이 없다는 것을 테스트로 확인한다.

### zero reference → relative/ratio unavailable

`left == 0` 이면:

```text
absoluteDelta        = 존재 (계산한다)
relativeDeltaPercent = unavailable
ratio                = unavailable
```

**0 으로 대체하지 않고, NaN/inf 문자열도 output contract 에 넣지 않는다.** 0, NaN, inf
문자열은 각각 발명한 값이기 때문이다.

`leftValueIsZero` 플래그와 `ZeroLeftReference` 사유로 **사유를 남긴다.** 그래야
"ratio 가 없는 이유가 값이 없어서인가, 나누는 기준이 0 이라서인가" 를 구분할 수 있다.
이 구분이 없으면 missing 과 0 이 같은 코드로 보이며, S6-4 가 0 을 missing 으로 재분류하지
않던 계약이 여기서 깨진다.

특히 `RunWallDuration` 의 0 ms 는 **두 timestamp 가 같은 초**라는 실제 derived 값이다.
absent 가 아니라 측정값이다.

### Known/Unknown/Legacy provenance 가 metric 계산을 제한한다

ComparisonMetrics 는 candidate 가 eligibility 를 통과했다는 전제에서 동작한다. 따라서
실제 commit-level candidate 는 Known vs Known 다. Legacy/Unknown 을 known 으로 변환하지
않으며, 그런 candidate 는 애초에 생성되지 않으므로 **해당 metrics 도 없다.** 테스트로
확인한다.

### aggregate 를 소비하고 다시 계산하지 않는다

`resolveSide()` 는 `BenchmarkAggregation` 안의 값을 **포인터로 빌려** 사용한다. 값을 복사해
다시 계산하지 않으므로, metric 이 자신이 파생된 aggregate 와 disagrees 할 수 없다.
journal 을 읽지 않고, grouping 을 다시 하지 않고, aggregation 을 다시 하지 않는다.

nesting level 은 dimension 이 아니라 **무엇을 주소하는가** 로 정한다. ModeSemantics 비교와
ModeElapsed metric 은 mode cohort 를 주소하고, CaseElapsed 와 RunWallDuration 는 build 를
주소한다. (BuildProvenance + ModeElapsed 후보는 S6-5 가 mode semantics 별로 생성하므로
dimension 이 build 라고 해도 mode cohort 를 가리킨다.)

### 방어적 검증

S6-5 가 이미 metric level / resolution 불일치 후보를 거절하지만, ComparisonMetrics 층에서
**다시 검증한다.** 서로 다른 metric 의 숫자를 빼는 것은 delta 가 감춰버리는 바로 그
실수이기 때문이다. 불일치 시 어떤 숫자도 계산하지 않고 사유만 남긴다.

### statistic 은 독립적으로 비교한다

`Min / Max / Mean / Median / P95` 를 각각 독립 비교한다. 한 statistic 이 unavailable 이면
다른 statistic 의 비교까지 삭제하지 않는다. `p95` 는 mean 을 반복하지 않음을 테스트로
확인한다(left 110/120 → p95 120).

## 2026-10-04 — `--version` 이력 판정 오류 수정 + CUDA C4819 제거

버전 `0.9.4.45` 유지(bump 없음). 상세: `docs/build-history/0.9.4.45.ko.md`

### `--version` 이력 판정 오류

사용자 제보로 시작. `MediaSimilarityFinder.exe --version`이 PowerShell에서 콘솔
출력이 없고, CMD에서는 정상이었다.

판정 경로: GUI subsystem(`WIN32_EXECUTABLE TRUE`)이므로 `GetConsoleWindow()`가
null이면 `AttachConsole(ATTACH_PARENT_PROCESS)`를 시도한다. 이때
`streamIsRedirected()`가 리다이렉션 여부를 판정하는데, 이 함수가 **스트림 사용
불가**(`fd<0`, `_get_osfhandle`이 `-1`/`0`, `FILE_TYPE_UNKNOWN`)를 전부
`true`(리다이렉션 있음)로 돌려였다.

그 결과 PowerShell 실행 시 `stdout`/`stderr`가 실제 출력 대상이 아닌데도
리다이렉션으로 판정되어 `AttachConsole`이 건너뛰어지고, `std::cout`에 쓰기 대상이
없어 `--version` 출력이 사라졌다. CMD는 콘솔 핸들 경로라 정상 동작했다.

수정은 세 반환값을 `false`로 바꾸는 것이었다. 유효한 `FILE_TYPE_DISK`/`FILE_TYPE_PIPE`
만 리다이렉션으로 남기므로 **실제 리다이렉션 보존이라는 기존 설계 의도는 유지**되고
판정 오류만 제거된다. `gui/main.cpp:41-49`.

### 검증 중 발견한 별개 제약 (회귀 아님)

PowerShell에서 `--version > file`이 0바이트가 되는 현상을 함께 확인했다.
다만 **수정 전 exe에서도 동일하게 재현**되며 `$LASTEXITCODE`가 비어 있다.
원인은 PowerShell이 GUI subsystem exe를 기다리지 않는다는 점이며, 본 수정이 만든
회귀가 아니다. OS 수준 리다이렉션(`cmd /c "exe --version > file"`)과
`Start-Process -Wait -RedirectStandardOutput` 은 모두 정상 기록된다.
앞으로 콘솔 출력 검증은 OS 수준 리다이렉션을 기준으로 한다.

### CUDA C4819

GPU 빌드 로그의 `warning C4819`는 CUDA 문법 오류가 아니라 코드 페이지 949가 CUDA
헤더의 비ASCII 문자를 표현하지 못해서 나는 인코딩 경고였다. 원인: `/utf-8`가
`CXX`에만 적용되어 CUDA host compiler에 전달되지 않았다.

`nvcc`는 `/utf-8`를 직접 받지 못하므로 `-Xcompiler`로 MSVC host compiler에 전달한다.
첫 시도는 `COMPILE_LANG_AND_ID:CUDA,MSVC`였으나 **CUDA 의 compiler id 가 `NVIDIA`
라 매칭에 실패**했다. `COMPILE_LANGUAGE:CUDA` + `CXX_COMPILER_ID:MSVC` 조합으로
바꿔 nvcc 명령줄에 `-Xcompiler="/EHsc -Ob2 /utf-8"`가 포함되는 것을 확인했다.
강제 재컴파일 결과 C4819=0, warning=0, error=0.

## 2026-10-05 — 0.9.4.46 DEFECT-A/B 수정 (Queue 0·1 완료)

| != 0 | 0 | 분석 완료 | 불필요 |

| 0 | 1 | 분석 시도했으나 fingerprint 산출 실패 | **불필요**(내용 불변 시) |

## 2026-10-05 — 0.9.4.49 Detailed Logs 사용자 요약 추가

상세: `docs/build-history/0.9.4.49.ko.md`

### 요구와 설계 공백

Detailed Logs 에는 내부 계측이 많지만 일반 사용자용 요약이 없고, 특히
**중복 파일 총개수가 어디에도 없었다.** 실제 GUI 로그 검증에서 발견해야 할
설계 공백이다.

요구된 한눈 요약: Duration(`12m 34.5s` 형식), 이미지/비디오별
scanned/analyzed/throughput, duplicate groups/files/pairs 분리, 합계 행,
시간 배분 Total/Image/Video/Matching.

### 의미 고정

- `SearchReport.groups` 는 매치된 **쌍 수**를 세고 있었다. 클러스터 수가 아니다.
- telemetry `matches.groups` 는 union-find distinct root 수 (**클러스터 수**)다.
- duplicate pairs = threshold 이상 verified match (종류별)
- duplicate groups = distinct cluster (종류별)
- duplicate files = pair 참여 파일, 즉 멤버 수 (종류별)
- 클러스터는 종류를 넘지 않는다 (인덱스 분리). 종류별 groups 는 전체를 분할한다.

### 구현

엔진 `SearchReport` 10개 필드 + telemetry `matches`/`images`/`videos` 확장 +

## 2026-10-06 — S4 telemetry 보강 타당성·순위 리포트 (나머지 항목)

1·2순위(finishedAt, cancellation phase, fingerprint 계측, totalScannedBytes,
series 시각)는 착수 확정. 여기서는 나머지(3순위·GUI·제외분)의 타당성 조사와
작업 순위를 기록한다. **이 항목들은 이번에 구현하지 않는다.**

### A. process I/O rate — 타당, 3순위 선두

**타당성 근거.** 요구(`평균 io 읽기 속도 실측`)와 현 상태의 격차가 실측으로
확인됐다. `sampleOnce()` 는 PDH LogicalDisk(`ioReadBps`)와
`GetProcessIoCounters` 누적치(`procIoReadBytes`)를 모두 읽는다. 그러나 첨부
로그에서 `diskAvailable=false`, `samples=1` 이라 속도가 전부 0이었다.
누적치는 있어도 속도가 없는 상태다.

**설계 제약 (구현 전 문서 확정 필요).**
- PDH(볼륨 전체)와 procIo(프로세스 귀속)는 성질이 다르므로 같은 필드로
  덮어쓰지 않는다. 별도 필드로 둔다.
- 속도는 샘플 구간 델타 ÷ 실제 interval 로만 계산한다. `bytes÷wall` 식 파생 금지.
- 최소 샘플 수 규칙을 명시한다. 1개 이하에서는 평균을 계산하지 않고
  `not_measured` 로 남긴다. `0 B/s` 실측과 미측정을 구분한다.
- `series` 7필드에 procIo 누적치를 추가해야 샘플당 delta 가 복원된다.

**순위 이유.** 명시적 요구사항이나 규칙 문서가 선행되어야 해서 1·2순위 뒤다.
규칙 없이 계수부터 하면 0 위장 버그가 재발한다.

### B. DB upsert/remove 카운터 — 조건부 타당, 3순위

**타당성 근거.** 호출이 전부 `media_search_engine.cpp` 9곳(upsert 6, remove 3)에
집중되어 있고, 주석상 "Single DB connection: only this thread touches db_" 라서
단일 스레드다. atomic 불필요, 단순 카운터로 충분하다.

**설계 제약 (정의 문서 선행).** rollback 지점이 4곳(L488,700,707,716) 존재한다.
`upsert()` 성공 직후 계수하면 이후 rollback 시 영속 행보다 커진다. 따라서
"DB 반영 횟수"가 아니라 **"시도 횟수"로 정의**하고 문서화한다. 취소 증거
(어디까지 진행됐는가) 용도로는 시도 횟수가 오히려 맞는 의미다.

**순위 이유.** 정의 1줄이 코드보다 먼저다. A 와 묶어 같은 phase 에서 처리한다.

### C. GUI 표시 — 타당, 마지막

**타당성 근거.** 데이터 7종이 있어야 렌더링이 가능하다. tr 키 + gate 등록이
필수이며, `scan_detailed_log_acceptance_test` 패턴으로 JSON→표시 일치를
검증한다. 측정 안 된 값은 `N/A` 계열로 표시하고 0으로 두지 않는다.

**순위 이유.** 표시할 데이터가 없으면 빈 칸 투성이 대화창이 된다. A·B 완료 후.

### D. 제외 항목과 이유

**D-1. media-type match 6종 — 제외 (완료됨).** 0.9.4.49 에서
`imagePairs/Groups/DuplicateFiles` + video 3종을 이미 구현·검증했다
(`summary_breakdown_test` 21 checks). 재구현하면 중복이다. 검증만으로 충분하다.

**D-2. §9 MediaKind 재구현 — 제외 (완료됨).** 0.9.4.49 가 `files_[].kind` 실측을

## 2026-10-06 — 0.9.4.59 사후 코드 검토: 1차 semantic 보정 + 2차 GUI 회귀 분리
상세 기준: `0.9.4.59` / `18f101f` · CPU CTest 107/107 · GPU CTest 108/108

### 1차 검토에서 확인된 명확한 semantic bug

**Video sampling generation의 scope 오판**을 확정했다.

현재 구현은 `processOne()`에서 다음 두 상황도 일반 `seen` 집합에 넣는다.

- `scanVideos=false`인 비디오: 사용자가 요청하지 않은 out-of-scope 파일
- ignored 파일: 현재 스캔에서 분석하지 않는 파일

그런데 0.9.4.59는 취소 시 `allOldVideosSeen`을 일반 `seen`으로 판정하고, 정상 완료 시에는 `r.completed`만으로 `setSamplingGeneration()`을 수행한다. 따라서 **이미지 전용 스캔도 비디오 sampling generation을 갱신할 수 있다.** 이는 `seen = discovered/present`와 `admitted/in-scope processed`를 동일시한 semantic bug다.

요구되는 invariant:

- `scanVideos=false`이면 `sampling_generation`을 절대 변경하지 않는다.
- generation stamp는 in-scope video admission/processing 경계를 만족했을 때만 갱신한다.
- 삭제 탐지 등에 사용하는 일반 `seen`의 의미는 그대로 보존하고, 별도의 video-scope admission 상태를 사용한다.

### 진단 semantic 보강점

`finishScan(false)`가 실제 terminal reason 대신 live `control->cancel` flag를 읽는다. DB 오류로 `failed=true`가 된 직후 Stop이 들어오면 transaction은 실패/rollback했어도 telemetry가 Cancelled로 기록될 수 있다. 따라서 `Completed / Cancelled / Failed`를 명시적 terminal state로 전달하여 **실패는 늦은 Stop에 의해 Cancelled로 재분류되지 않도록** 한다.

### 검증 보강점

1. image-only (`scanVideos=false`) complete/cancel scan이 stale video generation stamp를 바꾸지 않는 회귀.
2. deterministic DB-error가 rollback + `failed=true` telemetry로 남고, 뒤늦은 Stop이 있어도 Cancelled로 바뀌지 않는 회귀.
3. `setSamplingGeneration()` 실패 반환값을 무시하지 않고 보수적으로 처리하는 계약 확인 및 테스트.

### 실제 GUI 측정에서 얻은 성능 관찰

사용자 실제 GUI 실행 (`0.9.4.59`, 32,494 images)에서 GPU image path는 32,494건 모두 사용됐지만 GPU duty는 **약 0.2%**에 불과했다. image stage는 567.7s였고 verify decode 25.43s, WIC copy 약 25.07s에 비해 GPU H2D/kernel/D2H 합계는 약 0.31s였다. 이는 GPU backend가 동작하지 않는다는 증거가 아니라 **CPU/WIC decode·crop/I/O와 짧은 GPU hashing 구간 사이의 pipeline overlap/starvation이 큰 후보**라는 의미다.

CPU는 Maximum(90%)에서도 장시간 구간에서 약 20~70%로 널뛰었고 평균 30.8%였다. 드라이브 I/O도 관찰상 약 15~40% 수준으로 변동했다. 이 항목은 correctness defect가 아니라 **1.0 이후 scheduler/pipeline 고도화 과제**로 분류한다.

### 1.0 이후 개선 목표로 기록

이미지 검색 엔진은 **1차적으로 제품 경로가 완성**되었다. 1.0 이후 다음을 별도 개선 트랙으로 다룬다.

- CPU worker occupancy ↔ CPU policy의 실제 효과 정밀화
- read/decode concurrency 및 I/O backpressure 조정
- decode/crop/hash pipeline overlap과 GPU batch 지속성 향상
- GPU queue starvation 및 host↔device overlap 개선
- scheduler가 aggregate CPU/GPU load 외에 stage bottleneck, 자기 사용량, I/O wait를 구분
- Balanced의 초기 과소활용과 Maximum의 장주기 oscillation을 worker 수 증가만으로 해결하지 않고 admission/backpressure 문제로 재설계

GPU utilization 자체를 목표로 하지 않고 end-to-end throughput과 시스템 안정성을 목표로 한다. 이 작업들은 0.9.4.59 correctness 수정과 섞지 않는다.

### 2차 GUI-UI 회귀 과제

실제 GUI에서 유사그룹 목록을 아래로 스크롤할 때 마우스 드래그, 세로 scrollbar, End 등의 키보드 navigation을 사용하면 어느 지점 이후 느려지고 최상단으로 되돌아가는 회귀가 재현되었다.

과거 `0.9.3.10`은 `fillPair()`의 단순 pixel-offset 복원을 **semantic top-item scroll anchor + `PositionAtTop`** 방식으로 수정한 기록이 있다. 현재 0.9.4에도 anchor 복원 코드는 존재하지만, 현재 GUI는 검색 종료 후에도 `uiTimer_`를 유지하고 `thumbStarved_`가 남아 있으면 `refreshStreaming()` → `refreshGroupList()` → `fillPair()` 전체 rebuild를 반복한다. 이 destructive rebuild/catch-up 경로가 과거 scroll fix와 충돌하는 것이 현재의 우선 root-cause 후보이다.

2차 단계에서는 과거 commit `4c059177efca54463dec62bc0da79cd66fe6507e`와 현재 `uiTimer_`/`thumbStarved_`/`fillPair()`를 대조하고, 스크롤 조작 중 전체 rebuild를 피하거나 visible-item thumbnail만 갱신하는 방향으로 수정한다. mouse drag, scrollbar drag, End/PageDown/Home 등의 회귀 검증을 별도 acceptance로 만든다.

### GUI 회귀의 중요한 정정

`0.9.3.10`의 `itemAt(QPoint(2,2))` 기반 semantic anchor 자체는 현재까지 보존되어 있다. 따라서 '예전 수정이 코드에서 사라졌다'는 설명은 틀리다.

오히려 현재 0.9.4는 `0.9.3.8`에서 도입된 scan 종료 후 지속 timer 정책을 유지하면서, `thumbStarved_`가 발생하면 `refreshStreaming()`이 `thumbStarved_` 하나만 보고 full rebuild를 수행한다. tick당 fresh thumbnail budget이 4라서 대규모 group list에서는 이 조건이 오래 살아 있을 수 있다.

결과적으로 사용자 scroll 중 `fillPair()`가 tree/grid를 `clear()`하고 전체 widget을 재생성할 수 있다. anchor 복원은 재생성 후 위치를 되찾는 fallback이지만, scrollbar drag 상태·keyboard navigation·layout/paint 진행 중에 widget hierarchy 자체를 파괴하는 것을 방지하지 않는다.

따라서 2차 작업의 1순위는 **anchor 재작성보다 full rebuild 제거/지연**이다.

### 권장 수정 구조

- group membership/sort/search가 실제로 바뀐 경우에만 `rebuildGroups() + fillPair()`를 수행한다.
- thumbnail-only catch-up은 기존 item을 유지하고 현재 viewport의 item icon만 교체하는 별도 경로로 분리한다.
- scrollbar slider interaction 및 recent wheel/key scroll에 대한 cooldown을 두어 rebuild와 user navigation을 서로 배타적으로 만든다.
- 0.9.3.10 anchor는 실제 full rebuild가 필요한 경우의 안전장치로 그대로 둔다.

실제 Qt 내부에서 scroll value가 최종적으로 0으로 clamp되는 정확한 한 지점은 아직 runtime instrumentation으로 입증하지 않았다. 이를 추측하여 Qt workaround를 넣지 않는다.

### 회귀 acceptance 후보

- tree view: End → timer tick → top item/scroll value 유지
- tree view: vertical scrollbar drag 중 timer tick → drag가 끊기지 않고 위치 유지
- grid view: End/PageDown/Home + timer tick → anchor 유지
- mouse wheel 연속 입력 중 timer tick → full rebuild 없음
- scan 직후 thumbnail catch-up 중에도 사용자가 스크롤하면 right pane/detail refresh가 과도하게 발생하지 않음.
