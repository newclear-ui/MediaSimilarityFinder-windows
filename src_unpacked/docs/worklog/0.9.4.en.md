# Work Log — 0.9.4 Development Line

Implementation baseline: `ffd64e8` (0.9.4.24 code state) · Documentation registration HEAD: `374dbaf`
Scope: Node D cleanup → dataset foundation → bottleneck measurement → bottleneck identification → settings identity

Korean version: `docs/worklog/0.9.4.ko.md`

---

## 1. One-line summary

Node D (pipeline optimization) was **closed on measured evidence**, the
state that made comparison impossible was removed, the real bottleneck
(the matching stage) was instrumented, and the cause was **identified**.
Finally, a personal identifier in the distribution was replaced with a
product-based name, and existing user settings were migrated safely.

```
This is not "performance got better".
It is proving that D cannot help on this workload, and then
identifying where the real bottleneck is through measurement.
```

### Lessons about method (experiment infrastructure)

- **Profiling telemetry is itself a verification target.** D1's first
  implementation re-summed a running total and reported
  `factoryMs = 235,023,895 ms`. Rather than trusting it because it looked
  plausible, the pre-register's rule "the split must reconstruct the original
  total" caught it on the first run. That bug, and the D9d↔D1 factory
  difference, are a **measurement implementation** change and not a product
  performance change; the cause and the corrected value are both preserved in
  the 0.9.4.27 build history.
- **Observed operation count ≠ actual bottleneck.** On this line, five
  bottleneck hypotheses built by reading code were overturned by measurement
  (cache 32, scoring duplication, inside decode, Fant/EXIF, the Factory2
  fallback). Inferring a bottleneck from an operation-count proxy failed
  repeatedly.
- **Measurement deletes candidates more often than it adds them.** A deleted
  candidate does not come back; a wrong one that survives keeps costing.
- **A difference inside measurement noise is not an improvement.** In a 3.7-7.5 %
  run-variation environment, a 1-2 % delta is not declared an improvement.
- **A verdict comparison pair must come from one world (0.9.4.32).** The
  v0.9.4.31 probe's "baseline" score carried the previous file's **candidate**
  buffers. The output was 2 flips and a tidy monotone trend ("delta grows with
  R", 2.63→9.19), reproduced 5×. Reproducibility did not imply correctness — it
  was a **reproduced artifact**. Same defect family as the D1 `factoryMs` sum
  error; both were caught only by questioning the definition of the pair
  construction itself, not by self-consistency checks. The score decomposition
  matched `verifyScorePlan` exactly, which proves that a correct decomposition
  of a wrong pair is still meaningless.
- **A tidy result is a defect signal (0.9.4.32).** Two signals arrived from the
  same defect. One was a monotone "delta grows with R" (2.63→9.19); the other
  was flips confined to "old TIFF near-duplicate pairs". Both had a plausible
  narrative, which is exactly why the error looked like a finding. The moment
  measurements fit the expectation is when the narrative should be doubted.
- **Separate the identified cause from the adoption decision (0.9.4.32).**
  Even after the flip was corrected to an artifact, the candidate stayed
  `DEFERRED`. One line of evidence disappearing does not remove the others
  (byte parity not maintained, geometry differences, pixel divergence, no
  full-scan groups measurement, no EXIF/PGM coverage). The right move is to
  correct the composition of the supporting evidence, not to flip the verdict.

## 3. Core flow

### 3.1 Without measurement, no judgment was possible (0.9.4.19 → 0.9.4.20)

D3-Minimal and D4a passed, but there was **no comparison baseline.** The
statement "compare two states under identical conditions" was not even
expressible.

D4a measured (synthetic 16/256 images) that kernel device time **does not
grow proportionally with batch size**, while also recording explicitly that
this **cannot** serve as a D4b verdict because it is not a representative
dataset.

### 3.2 The conclusion: not a code problem, an evidence problem (0.9.4.21)

> The largest bottleneck is not the code, but the absence of a reproducible
> representative dataset that allows an end-to-end comparison under identical
> conditions.

D8a was not a performance optimization; it built the **comparison
reproducibility foundation**. Three decisions followed from the
investigation:

- **No committed binary assets** (all 495 tracked files are text) → a
  generation script instead
- **No cryptographic hash in `msf_core`** (Qt `QCryptographicHash` is
  GUI-only, no openssl) → SHA-256 implemented directly, validated against
  4 NIST vectors
- **ffmpeg output is not byte-reproducible** → video excluded and documented
  as separate future work

Dataset identity deliberately contains **no absolute path, timestamp, or
hardware name**, so two copies of the same content share a fingerprint even
under different roots.

### 3.3 D8a's own verdict was proven invalid (0.9.4.22)

A 60-file 8×8 dataset could not support a "no gain" claim: the pipeline does
no real work, so `maxDepth = 1` described **the dataset size**, not the
architecture.

The dataset was therefore expanded along deliberately asymmetric axes:

| Axis | Composition | Purpose |
| --- | --- | --- |
| walk axis | `tree/` 2,400 files, 240 directories | producer enumeration cost |
| decode axis | `bulk/` 240 images at 256×192 | consumer decode + crop + thumbnail cost |

The queue only grows when consumer cost exceeds producer cost, so **both
axes had to be tuned independently.**

Result:

```
walker maxDepth   1 → 964 mean / 1076 max  (23.5 % of capacity)
blocked_ticks     0  (the producer never actually blocked)
gpu_batch share   0.34 % → 0.026 %
analyze           98.62 % of engine wall
D3+D4 ceiling     0.044 %
```

→ **D4b overlap and Full D3 topology deferred on evidence.** And because the
bottleneck sat outside the D brief, **Node I was opened** (with the full
5-step change-management record).

### 3.4 A hypothesis was overturned by measurement (0.9.4.23)

The most plausible hypothesis, formed by reading code alone:

> Because `kVerifyCacheMax = 32`, the cache almost never hits across 2,700
> files, and re-decode cost explains the 98 %.

**Result: hit rate 0.5286 — refuted.** Candidate pairs arrive clustered in
index order, so even a 32-entry cache hits about half the time. Cache
enlargement cannot explain 99.67 %.

The actual dominant structure:

```
verifyCalls 158,020  (4.3 % of 3,641,700 possible pairs)
  ├─ ~144,286 (91.3 %)  kFast short-circuit, near-zero cost
  └─ ~ 13,734 ( 8.7 %)  2 buffer lookups + 10 ssimBuf (20 frame_ssim)
                        ~8.5 ms each → 117 s
```

→ The bottleneck is **candidate-pair volume reaching the verify gate**, not
per-call cost.

Counter coherence was used to validate the instrumentation itself:
`ssimEvals/10 == (misses+hits)/2 == 13,734` **exactly**.

### 3.5 A personal identifier in the distribution (0.9.4.24)

The QSettings organization name becomes the settings folder name, so the
GitHub account name `newclear-ui` was shipping in the product.

A plain rename would make existing users' UI state look reset, so deletion
was made to happen in a **strict order** only:

```
copy → open the new INI through a real QSettings → status() == NoError
     → confirm the key presence → only then remove legacy
     → remove the directory only if it is empty
```

No failure path can lose the legacy file. When the new location already
exists it wins and legacy is left alone, which also makes the migration
**idempotent**.

## 5. Ways of working learned here (reusable value)

### 5.1 Commit the pre-register **before** any code change

```
0fc3344  D9a pre-register      (before code)
f46658e  D9a implementation    (after validation)
```

Commit order alone makes "was the promise made first?" auditable. This
order was repeated four times: D4a, D8a, D8b, D9a.

### 5.2 Form a hypothesis from code, then break it with measurement

This was the single biggest lesson.

```
hypothesis: cache size 32 causes re-decodes
result:     verifyHitRate 0.5286 → refuted
```

Because the hypothesis was refuted, the cache-enlargement work (a waste of
time) was never done. "Hypothesis ≠ measured bottleneck" was written
explicitly in both the documents and the code comments.

### 5.3 Make the instrumentation validate itself

```
ssimEvals / 10      = 13,734
(misses + hits) / 2 = 13,734   ← independent paths
```

The two agreeing is evidence that the counters do not contradict each other.

### 5.4 Do not touch unrelated things

- The QuickLook registry lookup (`NativeFormat` + explicit path) is
  unrelated to the organization name
- `Index` storage, DB schema, Engine version — all unchanged
- CUDA / Scheduler / threshold / verdict — untouched during measurement

### 5.5 Verify real disk with cross-process tests

A same-process read-back would pass from QSettings' in-memory cache **even
if disk persistence were broken.** The migration tests were split into 5
process phases to avoid that trap.

`WICBitmapInterpolationModeFant` sounds expensive because it is the

### A second refutation, about the mutex

D9c left open the possibility that the verify cache's global mutex causes

```text
wait 0.0002 ms/acquire    hold 0.0018 ms/acquire

```

It is not a bottleneck, and that is now settled by measurement rather than
assumption. It also confirms there is no hidden contention inside D9c's `other`
bucket (0.42 %).

Four times in a row, a bottleneck hypothesis built by reading code has been
overturned by measurement. D9d's contribution is not to stop that repetition
but to **cut it short with evidence.** Fant and EXIF are now excluded by

Good measurement does not only answer questions. It also **deletes** them. The
question that did not exist before, "is the mutex a problem," is now closed by
measurement, and the question that did exist, "which part of decode," narrowed
from one region to two.

## 0.9.4.27 — D1: why file open and factory are expensive

D9d measured `open + factory` at 89.55 % of decode and 84.93 % of the verify,
but not what was inside. This answered two questions.

```text
Question B: does Factory2 work?
  attempts 25,898 / successes 25,898 (100%) / fallbacks 0

Question A: where does the 2.6 ms of open go?
  OS CreateFileW        0.0576 ms  (2.2%)
  WIC internal          2.5682 ms  (97.8%)
```

### Two things were deleted

The largest output of this build is not "what to optimize" but **what not to.**

1. **Removing the Factory2 fallback** — **zero** fallbacks in 25,898 calls.
   There is nothing to remove on this machine. The "the first attempt is
   wasted" hypothesis was refuted by measurement.
2. **File handle / stream management optimization** — the real OS cost is
   0.0576 ms, 2.2 % of `open`. The cost was not opening the file; it was WIC
   constructing a decoder. The name "file open" was misleading.

Both are candidates that names and intuition pull in naturally. Had either gone
unmeasured, both would have been implemented, and both would have done nothing.

### Measurement caught a measurement bug

The first implementation reported `factoryMs = 235,023,895 ms` -- an impossible
figure for a ~2 minute workload. The shared helper accumulates into **running
totals**, and the call site added those totals again on every call, so the sum
grew quadratically.

The pre-register's "stop if the split does not reconstruct factoryMs" caught it
exactly. Without that identity check, and with buckets less obviously broken, a
plausible-looking but wrong set of percentages would have been reported.

**Accounting is a precondition of a measurement, not a finishing touch.**

### The cumulative pattern (sixth build on this line)

```text
D9a  "cache 32"          -> refuted
D9b  "duplicated scoring" -> refuted
D9c  decode found        -> established
D9d  Fant / EXIF         -> refuted
D1   "Factory2 fallback"  -> refuted (0 occurrences)
D1   "file open"          -> partly refuted (OS is 2.2 %)
```

This approach keeps producing new candidates, but more often it **deletes**
existing ones. Deleting is the more valuable half. A deleted candidate does not
come back; a surviving wrong one keeps costing.

   - Keep completed history compact, one line per file.

5. **Data vs view**
   - The terminal is a view; journal/summary is canonical data.
   - Interactive and non-interactive outputs differ only in rendering and use the same data model.
