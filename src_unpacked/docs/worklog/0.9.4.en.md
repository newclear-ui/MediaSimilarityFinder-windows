## 1. One-line summary

Node D (pipeline optimization) was **closed on measured evidence**, the
state that made comparison impossible was removed, the real bottleneck
(the matching stage) was instrumented, and the cause was **identified**.
Finally, a personal identifier in the distribution was replaced with a
product-based name, and existing user settings were migrated safely.

```
This is not "performance got better".
It is proving that D cannot help on this workload, and then
identifying where the real bottleneck is through measurement.
```

### Lessons about method (experiment infrastructure)

- **Profiling telemetry is itself a verification target.** D1's first
  implementation re-summed a running total and reported
  `factoryMs = 235,023,895 ms`. Rather than trusting it because it looked
  plausible, the pre-register's rule "the split must reconstruct the original
  total" caught it on the first run. That bug, and the D9d↔D1 factory
  difference, are a **measurement implementation** change and not a product
  performance change; the cause and the corrected value are both preserved in
  the 0.9.4.27 build history.
- **Observed operation count ≠ actual bottleneck.** On this line, five
  bottleneck hypotheses built by reading code were overturned by measurement
  (cache 32, scoring duplication, inside decode, Fant/EXIF, the Factory2
  fallback). Inferring a bottleneck from an operation-count proxy failed
  repeatedly.
- **Measurement deletes candidates more often than it adds them.** A deleted
  candidate does not come back; a wrong one that survives keeps costing.
- **A difference inside measurement noise is not an improvement.** In a 3.7-7.5 %
  run-variation environment, a 1-2 % delta is not declared an improvement.
- **A verdict comparison pair must come from one world (0.9.4.32).** The
  v0.9.4.31 probe's "baseline" score carried the previous file's **candidate**
  buffers. The output was 2 flips and a tidy monotone trend ("delta grows with
  R", 2.63→9.19), reproduced 5×. Reproducibility did not imply correctness — it
  was a **reproduced artifact**. Same defect family as the D1 `factoryMs` sum
  error; both were caught only by questioning the definition of the pair
  construction itself, not by self-consistency checks. The score decomposition
  matched `verifyScorePlan` exactly, which proves that a correct decomposition
  of a wrong pair is still meaningless.
- **A tidy result is a defect signal (0.9.4.32).** Two signals arrived from the
  same defect. One was a monotone "delta grows with R" (2.63→9.19); the other
  was flips confined to "old TIFF near-duplicate pairs". Both had a plausible
  narrative, which is exactly why the error looked like a finding. The moment
  measurements fit the expectation is when the narrative should be doubted.
- **Separate the identified cause from the adoption decision (0.9.4.32).**
  Even after the flip was corrected to an artifact, the candidate stayed
  `DEFERRED`. One line of evidence disappearing does not remove the others
  (byte parity not maintained, geometry differences, pixel divergence, no
  full-scan groups measurement, no EXIF/PGM coverage). The right move is to
  correct the composition of the supporting evidence, not to flip the verdict.

## 3. Core flow

### 3.1 Without measurement, no judgment was possible (0.9.4.19 → 0.9.4.20)

D3-Minimal and D4a passed, but there was **no comparison baseline.** The
statement "compare two states under identical conditions" was not even
expressible.

D4a measured (synthetic 16/256 images) that kernel device time **does not
grow proportionally with batch size**, while also recording explicitly that
this **cannot** serve as a D4b verdict because it is not a representative
dataset.

### 3.2 The conclusion: not a code problem, an evidence problem (0.9.4.21)

> The largest bottleneck is not the code, but the absence of a reproducible
> representative dataset that allows an end-to-end comparison under identical
> conditions.

D8a was not a performance optimization; it built the **comparison
reproducibility foundation**. Three decisions followed from the
investigation:

- **No committed binary assets** (all 495 tracked files are text) → a
  generation script instead
- **No cryptographic hash in `msf_core`** (Qt `QCryptographicHash` is
  GUI-only, no openssl) → SHA-256 implemented directly, validated against
  4 NIST vectors
- **ffmpeg output is not byte-reproducible** → video excluded and documented
  as separate future work

Dataset identity deliberately contains **no absolute path, timestamp, or
hardware name**, so two copies of the same content share a fingerprint even
under different roots.

### 3.3 D8a's own verdict was proven invalid (0.9.4.22)

A 60-file 8×8 dataset could not support a "no gain" claim: the pipeline does
no real work, so `maxDepth = 1` described **the dataset size**, not the
architecture.

The dataset was therefore expanded along deliberately asymmetric axes:

| Axis | Composition | Purpose |
| --- | --- | --- |
| walk axis | `tree/` 2,400 files, 240 directories | producer enumeration cost |
| decode axis | `bulk/` 240 images at 256×192 | consumer decode + crop + thumbnail cost |

The queue only grows when consumer cost exceeds producer cost, so **both
axes had to be tuned independently.**

Result:

```
walker maxDepth   1 → 964 mean / 1076 max  (23.5 % of capacity)
blocked_ticks     0  (the producer never actually blocked)
gpu_batch share   0.34 % → 0.026 %
analyze           98.62 % of engine wall
D3+D4 ceiling     0.044 %
```

→ **D4b overlap and Full D3 topology deferred on evidence.** And because the
bottleneck sat outside the D brief, **Node I was opened** (with the full
5-step change-management record).

### 3.4 A hypothesis was overturned by measurement (0.9.4.23)

The most plausible hypothesis, formed by reading code alone:

> Because `kVerifyCacheMax = 32`, the cache almost never hits across 2,700
> files, and re-decode cost explains the 98 %.

**Result: hit rate 0.5286 — refuted.** Candidate pairs arrive clustered in
index order, so even a 32-entry cache hits about half the time. Cache
enlargement cannot explain 99.67 %.

The actual dominant structure:

```
verifyCalls 158,020  (4.3 % of 3,641,700 possible pairs)
  ├─ ~144,286 (91.3 %)  kFast short-circuit, near-zero cost
  └─ ~ 13,734 ( 8.7 %)  2 buffer lookups + 10 ssimBuf (20 frame_ssim)
                        ~8.5 ms each → 117 s
```

→ The bottleneck is **candidate-pair volume reaching the verify gate**, not
per-call cost.

Counter coherence was used to validate the instrumentation itself:
`ssimEvals/10 == (misses+hits)/2 == 13,734` **exactly**.

### 3.5 A personal identifier in the distribution (0.9.4.24)

The QSettings organization name becomes the settings folder name, so the
GitHub account name `newclear-ui` was shipping in the product.

A plain rename would make existing users' UI state look reset, so deletion
was made to happen in a **strict order** only:

```
copy → open the new INI through a real QSettings → status() == NoError
     → confirm the key presence → only then remove legacy
     → remove the directory only if it is empty
```

No failure path can lose the legacy file. When the new location already
exists it wins and legacy is left alone, which also makes the migration
**idempotent**.

## 5. Ways of working learned here (reusable value)

### 5.1 Commit the pre-register **before** any code change

```
0fc3344  D9a pre-register      (before code)
f46658e  D9a implementation    (after validation)
```

Commit order alone makes "was the promise made first?" auditable. This
order was repeated four times: D4a, D8a, D8b, D9a.

### 5.2 Form a hypothesis from code, then break it with measurement

This was the single biggest lesson.

```
hypothesis: cache size 32 causes re-decodes
result:     verifyHitRate 0.5286 → refuted
```

Because the hypothesis was refuted, the cache-enlargement work (a waste of
time) was never done. "Hypothesis ≠ measured bottleneck" was written
explicitly in both the documents and the code comments.

### 5.3 Make the instrumentation validate itself

```
ssimEvals / 10      = 13,734
(misses + hits) / 2 = 13,734   ← independent paths
```

The two agreeing is evidence that the counters do not contradict each other.

### 5.4 Do not touch unrelated things

- The QuickLook registry lookup (`NativeFormat` + explicit path) is
  unrelated to the organization name
- `Index` storage, DB schema, Engine version — all unchanged
- CUDA / Scheduler / threshold / verdict — untouched during measurement

### 5.5 Verify real disk with cross-process tests

A same-process read-back would pass from QSettings' in-memory cache **even
if disk persistence were broken.** The migration tests were split into 5
process phases to avoid that trap.

## 0.9.4.27 — D1: why file open and factory are expensive

D9d measured `open + factory` at 89.55 % of decode and 84.93 % of the verify,

```text
  attempts 25,898 / successes 25,898 (100%) / fallbacks 0

  OS CreateFileW        0.0576 ms  (2.2%)
```

### Two things were deleted

The largest output of this build is not "what to optimize" but **what not to.**

1. **Removing the Factory2 fallback** — **zero** fallbacks in 25,898 calls.
   There is nothing to remove on this machine. The "the first attempt is
   wasted" hypothesis was refuted by measurement.
2. **File handle / stream management optimization** — the real OS cost is
   0.0576 ms, 2.2 % of `open`. The cost was not opening the file; it was WIC
   constructing a decoder. The name "file open" was misleading.

Both are candidates that names and intuition pull in naturally. Had either gone
unmeasured, both would have been implemented, and both would have done nothing.

### Measurement caught a measurement bug

The first implementation reported `factoryMs = 235,023,895 ms` -- an impossible
figure for a ~2 minute workload. The shared helper accumulates into **running
totals**, and the call site added those totals again on every call, so the sum
grew quadratically.

The pre-register's "stop if the split does not reconstruct factoryMs" caught it
exactly. Without that identity check, and with buckets less obviously broken, a
plausible-looking but wrong set of percentages would have been reported.

**Accounting is a precondition of a measurement, not a finishing touch.**

### The cumulative pattern (sixth build on this line)

```text

D9b  "duplicated scoring" -> refuted
D9c  decode found        -> established
D9d  Fant / EXIF         -> refuted

D1   "file open"          -> partly refuted (OS is 2.2 %)
```

existing ones. Deleting is the more valuable half. A deleted candidate does not
come back; a surviving wrong one keeps costing.

## 2026-10-01 — S6 Grouping design decision

### Why a single composite grouping key was not adopted

The leading candidate was one key combining `datasetFingerprint + mediaScope +
buildVersion + gitCommit + requestedMode + effectiveMode`. It is the simplest thing
to implement and produces a very short report. **It also puts every run in a cohort
of its own and makes cross-build comparison structurally impossible.** Two runs over
the same dataset and scope but different builds land in different cohorts, so a
later question of "what changed under the same conditions" finds an empty population.

It looks tidier than it is, and what it actually does is delete the comparison, so it
was rejected. This is expensive to reverse once a later stage depends on it, which is
why the reasoning is recorded here.

What was adopted instead is **separate typed keys per analysis axis**. Each axis
answers only its own question, and the caller selects the view it needs. Combining two
keys is the caller's business, not the data layer's.

| View | Key | Question it answers |
| --- | --- | --- |
| `DatasetCohortKey` | `datasetFingerprint` | Observing one dataset across builds and modes |
| `ScopeCohortKey` | fingerprint + `mediaScope` | The baseline population for cross-build observation |
| `BuildCohortKey` | `buildVersion` + `gitCommitState` + `gitCommit` | Which runs came from the same build |
| `ModeCohortKey` | `requestedMode` + `effectiveMode` | Fallback and capability observations |
| `CaseCohortKey` | fingerprint + `caseId` | Per-file comparison |

### `caseId` is not run-scoped (measured)

S2 derives `caseId` as `IndexManager::folderId(file.path)`, a double FNV-1a hash of the
canonical path. The brief assumed this value was run-scoped, but **measurement shows
the same file in two runs yields the same `caseId`** — two runs over one file produced
the same value. Per-file comparison across runs was therefore always possible. It is
still not trusted alone: it is paired with the dataset fingerprint, because it hashes
an absolute path and could in principle collide across datasets. No new hash was
invented, honouring the brief.

### Legacy / Unknown provenance is never merged into one group

`gitCommit` existing in the journal is not the same as being comparable by commit.
`BuildCohortKey` carries the commit value **and** the provenance state, so Known,
Unknown and Legacy cohorts are separated structurally, and `commitComparable` is true
only for Known. Two Unknown runs are not evidence of the same binary, so the flag
makes them excludable from commit-level comparison. Legacy has no field at all and is
never filled in with the current HEAD. `commitComparable` states **provenance
quality** and is not a comparability verdict.

### What the real journals showed

- **60 records have `requested=CUDA` but `effective=CPU`.** They carry
  `status=SKIPPED` and `errorMessage="mode unavailable in this environment"` — a
  fallback on a machine without GPU support. Had requested and effective been merged,
  60 CUDA observations would have been disguised as CPU runs and the entire
  capability observation would have vanished. Brief §9's reason for keeping them apart
  is confirmed by real data.
- **`all` is the dominant scope** (21 of 31 runs). Not decomposing it into
  images+videos is correct.
- **Build diversity is insufficient** (2 cohorts, 1 commit). Per brief §23 this is
  recorded as normal, and no diversity was fabricated.
- **`suite-ORDER-A/B/C` are fixtures** left in the real benchmark store by S2/S5
  ordering tests. Each journal holds three `run_started` records with the same
  `runId` and duplicated `mode_result` lines. `ModeCohort` counts (run, case, mode)
  as a **set**, so a duplicated record counts once (486 against 494 raw lines). These
  fixtures predate S6 and were not created by it. Separating fixture management from
  the real store may be needed at a later stage.

### Scope

This stage computes membership, counts and provenance only. mean, median, p95, delta,
speedup, failure rate, thresholds, anomalies, final comparability judgement, CLI and
GUI are all **not implemented**, and the journal schema is unchanged. Statistics were
deliberately left out: adding them now would let a later threshold design inherit
unmeasured assumptions.
## 2026-10-01 — S6 Aggregation design decision

### `all` is never decomposed into images/videos

In the real store `all` is 22 of 31 runs. Converting it to `images + videos` would make
the aggregates look tidier, but **the journal does not record how many cases of each
scope an `all` run actually covered.** Distributing the elapsed time therefore requires
inventing a ratio. `all` stays an independent scope and donates no elapsed time to the
others. A later stage makes the user pick `images-only`, `videos-only` or `all`
explicitly.

### SKIPPED / FAILED / CANCELLED are excluded from the performance population

The 60 real `requested=CUDA` / `effective=CPU` / `SKIPPED` /
`mode unavailable in this environment` records are **not CPU performance
observations.** Averaging them would disguise a machine that cannot use the GPU as CPU
speed and would actively distort the capability observation. Rewriting `SKIPPED` as 0 ms
is worse still: it asserts "measured, and the value was zero", inventing a value the
data does not contain.

So all three are **excluded from performance statistics** and **always kept in the
status tally**. Every exclusion carries its reason
(`skipped`/`failed`/`cancelled`/`missingElapsed`/`invalid`). A bare excluded count is
not acceptable, because it cannot be told apart from a bug.

The per-level rules differ, because the model does. mode `elapsedMs` is optional, so a
`Success` with no duration is possible and becomes `missingElapsed`. case `elapsedMs` is
a non-optional `double`, so that case **cannot occur** there and status alone decides. A
run with no terminal record has no status at all, so it is excluded as `invalid` rather
than assumed Success.

### Logical entities, not raw journal duplicates, are aggregated

The real store's `suite-ORDER-A/B/C` wrote the same journal more than once. Averaging raw
lines would weight a repeatedly-written suite above an identical one written once, so
aggregation uses the logical entities S6-1/S6-2 recovered.

> **This surfaced a real defect.** `suite-ORDER-A/B/C` share one `runId`, so **31
> accepted runs carry only 29 distinct runIds.** Keying per-file aggregation on `runId`
> alone kept one of the three and silently dropped the other two runs' cases (case
> observations rose from 314 to 324 once fixed). Deduplicating instead would discard
> measurements in the opposite direction. **The journal cannot say whether these are one
> measurement written three times or three separate measurements**, so neither is applied
> silently: per-file populations are keyed on `(sourceJournalPath, runId)` and the
> collision is only reported through `runsWithCollidingIdentity`.
>
> S6-1 reported "31 accepted" without this being visible, so the point is recorded here:
> **no S6 layer may assume runId is unique in a store.**

### Run, mode and case metrics are never combined

The three measure different things. `case_complete.elapsedMs` is by S2 definition the sum
of that case's mode elapsed values and excludes discovery; run wall duration is derived
from one-second-resolution stamps. The run wall duration is **not corrected** by summing
modes or cases, a 0 ms value is **not reclassified** as missing, and fractional
milliseconds are never estimated.

To enforce that structurally, every statistics block carries `MetricLevel` and
`MetricResolution`. Run wall duration is always `OneSecond`, and its 0 means "started and
completed within the same second", not "no time passed".

### Each level accumulates its own samples

Rolling dataset → scope → build up by **combining statistics** would produce a mean of
means, which is meaningless. Each level owns a `SampleAccumulator` and sorts and
summarises once at the end.

### Rounding rule

Double summation can vary slightly with order, so reported values are rounded to 6
decimal places (`aggregationRoundMs`). Inputs are untouched; only the printed form is
fixed.

p95 uses nearest rank and is computed and **not hidden** for `n = 1` and `n = 2`, with
its sample count alongside. Whether a sample count justifies a statement is a later
stage's job. With zero eligible samples the statistic **does not exist** (rather than
being 0), and a 0 is a measurement.

### Scope

Regression percentage, thresholds, anomaly judgement, statistical confidence, winner
ranking, resourcePolicy/distance/gpuBackend inference, CLI, GUI, CSV/Markdown reports and
journal schema changes are **all not implemented**.
## 2026-10-01 — S6 Comparison Eligibility design decision

### `(sourceJournalPath, runId)` is the run reference, not runId

S6-4 found `31 accepted runs / 29 distinct runIds`: `suite-ORDER-A/B/C` share one `runId`.
**Identifying a run by `runId` alone keeps one of the three and loses the rest.** That
actually bit while writing S6-5: per-case lookup by `runId` dropped observations, the same
defect that surfaced in S6-4 as 314 -> 324.

The formal run reference is the typed `RunReference { sourceJournalPath, runId }`. A
duplicate of the same `(journal, runId)` is a different question and is already resolved
by S3 recovery semantics; this stage does not re-decide it.

### A candidate is population-versus-population, not a run pairing

When the same condition was repeated N times, **run 1 is not paired against run 1.** Such a
pairing discards the rest of the samples and invents a correspondence the data does not
contain. Each side is a whole aggregate with its own sample count, and the `RunReference`
list behind it exists only for traceability.

`left < right` is fixed by typed key order, so any pair appears once and its sides are the
same on every run.

### Legacy / Unknown provenance is excluded from commit-level comparison

`gitCommitState` is compared **alongside** the `gitCommit` value, so Known, Unknown and
Legacy cohorts are separated structurally. Commit-level comparison requires Known on both
sides.

- **Legacy**: the field does not exist in journals written before it was added.
- **Unknown**: the writer had the field and did not fill it in.
- **Legacy + Legacy** is not treated as the same binary. There is no evidence for it.

One caution: `buildVersion` alone must not settle "same build". The entire point of adding
git provenance in S6-3 was to distinguish different commits under the same app version, so
a Known commit takes precedence. `commitA` vs `commitZ` on the same `0.9.4.43` is a
legitimate pair.

### Unavailable metadata is not treated as "the same conditions"

`distance`, `resourcePolicy` and `gpuBackend` are not in the journal. **Absence is not
agreement.** Not recorded is not the same as matching.

So every candidate carries **nine** `ComparisonLimitations`: distance, resourcePolicy and
gpuBackend unavailable; controlled environment undefined; process isolation uncontrolled;
OS filesystem cache uncontrolled; repeated runs insufficient; run wall one-second
resolution; cancellation unobserved. A bare `comparable=true` with these dropped would be a
claim the data cannot support.

### Candidate generation and regression judgement are separate

This stage decides "may these be compared" and stops there. Regression percentage, speedup
percentage, confidence interval, p-value, threshold pass/fail, winner and better/worse are
**not computed**, and no threshold is chosen, because the OS cache, process isolation,
repeated runs and controlled environment problems remain unsolved.

### `all` stays an independent scope

Only `all vs all` is a candidate, and `all` is never converted to images/videos. §3-2 already
refused to distribute it during aggregation, so comparison follows the same decision.

### CaseElapsed cannot be split by build or mode (structural limit)

S6-4 puts `caseElapsed` on `AggregatedScope` and `AggregatedDataset` but **not** on
`AggregatedBuild`. Case elapsed exists only per dataset+scope; there is no per-build or
per-mode breakdown of it. So a case-elapsed build comparison and a case-elapsed mode
comparison are recorded as `InsufficientData` rather than emitted as candidates whose
numbers do not exist.

The real store already has per-build run wall samples of **1 and 5** in the `images` scope.
Had the Legacy side carried a `gitCommit`, a build-vs-build candidate would exist today.
**Missing provenance is the measured cause of the missing data.**

### A note on state naming

S6-5 eligibility is an **analysis comparability state**, not a benchmark execution status.
It shares no vocabulary with S2's `BenchmarkStatus`, so a cancelled run and an impossible
comparison never look alike. There are nine states: `Eligible` / `MismatchedDataset` /
`MismatchedScope` / `MismatchedMetric` / `MismatchedMode` / `MissingProvenance` /
`SameProvenance` / `NoComparableSamples` / `InsufficientData`.

The order of checks is deliberate too. Dataset identity is verified first, because "a
different dataset" is the more fundamental reason and a caller should not have to satisfy
itself about the other conditions before learning it.

### Scope

Regression percentage, speedup, anomaly, thresholds, confidence, p-value,
winner/better ranking, final reports, CLI, GUI, journal schema changes,
resourcePolicy/distance/gpuBackend inference and timestamp correction are **all not
implemented**.
## 2026-10-01 — CaseElapsed on the build and mode axes (S6-4 structural completion)

### What was missing

S6-4 aggregated `caseElapsed` only onto `AggregatedScope` and `AggregatedDataset`. It was
absent from `AggregatedBuild` and `AggregatedMode`. So S6-5 could not state

```text
same dataset + same scope + build A  vs  build B
```

at case level. The measurement did not exist on that axis; the **axis** did not exist. S6-5
refused with `InsufficientData`, and that record is what exposed the problem.

### A projection, not a new measurement

This completion **creates no new measurement.** It aggregates and preserves the
`case_complete.elapsedMs` values S6-2 had already normalized, along the build and mode axes.
The S6-1/S6-2 normalized meaning is untouched and the existing S6-4 Run/Case/Mode semantics
are unchanged.

The build axis was nearly free: `placeRun()` already fed every case into the dataset, scope
and build cells, and the result was simply **never exposed**. Only the mode axis was new.

### The mode axis is a FILTER, not an allocation (the important decision)

`case_complete.elapsedMs` is by S2 definition the **sum of all of that case's modes**, and
the journal records no split of it. Dividing that total between modes would therefore mean
**inventing a factor that was never measured.** That was refused.

Instead, each mode cohort **filters** to the cases where that mode semantics actually ran.

```text
CPU/CPU   covers the 2 cases where CPU succeeded  -> 100, 200  (mean 150)
AUTO/CPU  covers the 1 case where AUTO succeeded  -> 100         (mean 100)
```

The two populations **overlap by design.** A case where both modes succeeded appears in
both. So these two statistics must **never be added**, and per-file comparison stays the job
of the existing per-file view. The overlap is not hidden: each cohort states it in
`caseAccounting.observed`.

**Skipped contributes nothing.** A `requested=CUDA / effective=CPU / SKIPPED` case is
excluded from that cohort's case population. The S6-4 rule that such a record must not
become a CPU case performance sample is applied unchanged on the case axis.

### The build axis is the sum of that build's scopes

`AggregatedBuild.caseElapsed` and `AggregatedScope.caseElapsed` are **the same samples seen
from two levels.** They are not additive and both hold the same values. The build axis is
used when the question needs them separated by build.

## 2026-10-01 — S6 Comparison Metrics: a computed number is not a verdict

### left/right ordering is not baseline/target

`left < right` from S6-5 is a typed key order, and its whole job is to make the pair
reproducible. **It is not a baseline.** It is not read as `left = old` / `right = new`, and
it is not read as `left = better` / `right = worse`.

An ordering that also implied a direction would quietly **choose** that direction. So
ComparisonMetrics keeps the orientation as a **deterministic order only** and attaches no
public meaning to it. Roles can be assigned later, when a stage lets a user name a baseline
build explicitly.

### A raw comparison is not a regression judgement

```text
absoluteDelta        = right - left                       (ms)
relativeDeltaPercent = ((right - left) / left) * 100
ratio                = right / left
```

`relativeDeltaPercent = +50%` is reported as **+50%**. It is not a regression, an
improvement, better, worse or a winner. Deciding whether a difference matters belongs to a
later decision layer, which does not exist yet. **No threshold is defined here, so pass/fail
is structurally impossible here.**

A test asserts that the layer's vocabulary contains no directional term at all.

### A zero reference makes the ratio and relative delta unavailable

When `left == 0`:

```text
absoluteDelta        = present (computed)
relativeDeltaPercent = unavailable
ratio                = unavailable
```

Neither is replaced with 0, and **no NaN or infinity string is put in the output contract**,
because each of those would be an invented value.

The reason is recorded through the `leftValueIsZero` flag and a `ZeroLeftReference` entry,
so "the ratio is absent because a value was missing" can be told from "the ratio is absent
because the reference was a measured zero". Without that distinction missing and zero look
alike, and the S6-4 rule that a zero is never reclassified as missing would break here.

A `RunWallDuration` of 0 ms in particular is a **real derived value** meaning the two
timestamps fell in the same second. It is an absence of nothing.

### Provenance restricts the calculation

ComparisonMetrics works on the premise that the candidate already passed eligibility, so a
real commit-level candidate is Known against Known. Legacy and Unknown are never converted
to Known, and such a candidate is never generated in the first place, so **there are no
metrics for it either.** A test asserts that.

### The aggregate is consumed, never recomputed

`resolveSide()` borrows the values inside `BenchmarkAggregation` **by pointer**. It copies
nothing and recomputes nothing, so a metric cannot disagree with the aggregate it came from.
It reads no journal, performs no grouping and performs no aggregation.

The nesting level is decided by what is addressed rather than by the dimension alone. A
ModeSemantics comparison and a ModeElapsed metric address a mode cohort; CaseElapsed and
RunWallDuration address the build. A BuildProvenance candidate over ModeElapsed addresses a
mode cohort inside each build, because S6-5 generates it per mode semantics, even though the
dimension says "build".

### Defence in depth

S6-5 already refuses a candidate whose sides disagree on metric level or resolution, and
ComparisonMetrics **re-checks rather than trusting it**, because subtracting numbers from
different metrics is exactly the mistake a delta would hide. On a mismatch nothing is
computed and only the reasons are recorded.

### Statistics are compared independently

`Min / Max / Mean / Median / P95` are each compared on their own. One statistic being
unavailable never removes another statistic's comparison. A test confirms that p95 is not
just the mean repeated: with left values 110 and 120 the p95 is 120.

### Limitations are carried through unchanged

The nine `ComparisonLimitations` from S6-5 are passed through as they are. No second
limitation system was created, and a test pins the count at nine. Nothing is reduced to a
bare `comparable=true`.

### Scope

Thresholds, regression classification, winners, better/worse, confidence intervals,
p-values, statistical significance, anomalies, controlled-environment scores, CLI, GUI,
report formatters, journal schema changes and S2/S3 changes are **all not implemented**.

## 2026-10-04 — `--version` redirection misdetection fix + CUDA C4819 removal

Version stays `0.9.4.45` (no bump). Details: `docs/build-history/0.9.4.45.en.md`

### `--version` redirection misdetection

Reported by the user: `MediaSimilarityFinder.exe --version` printed nothing to the
console from PowerShell, while CMD worked.

Decision path: because the executable is GUI subsystem (`WIN32_EXECUTABLE TRUE`),
`GetConsoleWindow()` being null leads to `AttachConsole(ATTACH_PARENT_PROCESS)`.
That path consults `streamIsRedirected()` to decide whether to skip the `CONOUT$`
reopen. The predicate returned `true` for every **unusable** stream: `fd<0`, an
invalid `_get_osfhandle` result (`-1`/`0`), and `FILE_TYPE_UNKNOWN`.

So a PowerShell launch whose `stdout`/`stderr` were not real output targets was
classified as redirected, `AttachConsole` was skipped, and `std::cout` had
nowhere to write — hence no `--version` output. CMD took the console-handle path
and was unaffected.

The fix was to return `false` for those three cases. Only a genuinely usable
`FILE_TYPE_DISK`/`FILE_TYPE_PIPE` counts as redirected, so the original design
intent — preserve real redirection — is kept and only the misdetection is
removed (`gui/main.cpp:41-49`).

### A separate constraint found during verification (not a regression)

`--version > file` yields 0 bytes from PowerShell. It **reproduces identically on
the pre-fix binary** and leaves `$LASTEXITCODE` empty. The cause is that PowerShell
does not wait for GUI-subsystem executables; this change did not introduce it. OS
level redirection (`cmd /c "exe --version > file"`) and
`Start-Process -Wait -RedirectStandardOutput` both record correctly. Console
output verification should therefore use OS level redirection as the criterion.

### CUDA C4819

The `warning C4819` in the GPU build log was not a CUDA syntax error but an
encoding warning: code page 949 cannot represent non-ASCII characters in the
CUDA headers. Cause: `/utf-8` was applied to `CXX` only and never reached the
CUDA host compiler.

`nvcc` does not accept `/utf-8` directly, so it is forwarded to the MSVC host
compiler via `-Xcompiler`. The first attempt used `COMPILE_LANG_AND_ID:CUDA,MSVC`
and **failed to match, because CUDA reports compiler id `NVIDIA`**. Switching to
the `COMPILE_LANGUAGE:CUDA` + `CXX_COMPILER_ID:MSVC` combination puts
`-Xcompiler="/EHsc -Ob2 /utf-8"` on the nvcc command line. A forced recompile
reported C4819=0, warning=0, error=0.

## 2026-10-05 — 0.9.4.46 DEFECT-A/B fix (queue 0 and 1 complete)

Detail: `docs/build-history/0.9.4.46.en.md`

### Cause: the two defects were not independent bugs

They were judged to be two symptoms of a single missing failure state model.

`processOne()` in `MediaSearchEngine::scan()` used `fingerprint==0` to express
both **"analysis not completed (retry needed)"** and **"analysis failed (no retry
needed)"**, and no field separated them.

- **DEFECT-A**: `added`/`modified` were counted **before** analysis, so a file
  with no fingerprint was reported as successfully indexed
- **DEFECT-B**: `fingerprint==0` made `changed` unconditionally true, so a failed
  file was reported as `modified=1` on every scan while no reanalysis actually
  happened (leaving `analyzed=0`)

-> Fixed as one state transition.

### State model adopted

A `files.analysis_failed` column (default 0) separates the two meanings of
`fingerprint==0`.

| fingerprint | analysis_failed | meaning | retry |
|---|---|---|---|
| != 0 | 0 | analysis completed | not needed |
| 0 | 0 | skeleton (cancel/crash/not reached) | **needed** |
| 0 | 1 | attempted, no fingerprint produced | **not needed** while content is unchanged |

`added`/`modified` moved to analysis **outcome** time and a `failed` counter was
introduced. Failures are surfaced through the CLI, the GUI, telemetry, and the
benchmark journal, and telemetry `pending` became `scanned - analyzed - failed` so
a failed file is no longer misread as outstanding work.

### Fixture decision

As directed, it was judged first whether the real TIFF is strictly required. It is
**not**. The defect is a state transition, not a format, so a single 64x64 BMP
header carrying no pixel data reproduces it deterministically. Nothing hardcodes
a file name or a TIFF subtype.

### Confirmed the regression test actually catches the defect

Removing `&& !analysisFailed` from `pendingAnalysis` to restore DEFECT-B behavior
makes the new test **exit 1** (three convergence checks fail). After restoring, all
pass.

> **Reusable rule**: after restoring a source file, always raise its mtime to force
> recompilation. `Copy-Item` preserves the source `LastWriteTime`, so make skips the
> rebuild, the `.obj` stays at the previous state, and tests fail for no real reason.
> This actually happened during this task.

> **Reusable rule (test design)**: a regression test must verify **invariants**, not
> "the file that triggered the bug". Here it is anchored on the accounting identity
> `scanned == added + modified + unchanged + failed` plus identical reports from the
> third and fourth scans. Pinning individual counter values would break whenever a
> legitimate improvement lands on the normal path.

## 2026-10-05 — 0.9.4.47 non-ASCII path scan failure fix

Detail: `docs/build-history/0.9.4.47.en.md`

### Symptom

`%TEMP%\msf_scan.log` recorded `start folder=G:\Downloads\ss_twit` followed one
second later by `failed No mapping ...`. The same folder scanned fine on

the same exception goes uncaught -> terminate -> abort -> 0xC0000409, so it dies

### Cause confirmation (verified, not guessed)

The message string was searched across the Qt6 DLLs, the MSVC headers, and 6,240

confirmed:

- `fs::u8path(valid UTF-8)` -> ok
- `fs::u8path(CP949 bytes)` -> THROW (exactly this message)
- `fs::path(UTF-8 Korean narrow)` -> THREW (same message)

the **ANSI code page (949)**, not UTF-8.

`fs::path(file)` and `fs::path(root)` in `canonicalRelativePath()`
(`dataset_fingerprint.cpp:118`) reinterpreted UTF-8 as ACP. It came in with the
dataset fingerprint for the S6 measurement gate (D8a/D8b) and runs at every scan
start, so scans failed "in one second with no file processed". The timeline
matches.

> **Reusable rule**: narrow `fs::path(string)` construction is a forbidden pattern
> in the product. UTF-8 strings must go through `path_from_utf8()`.

Qt6 `toStdString`/`fromStdString` are UTF-8 based (header + probe confirmed).
`toLocal8Bit()` silently substitutes `?` and never throws.
`Scanner().count/scan`, `MediaPipeline.image/imageBatch`, `db_.upsert`,
`compareFingerprint`, the GPU getters, `detectCpuModel`, and `ProfileStore` were
each verified working by stepwise probes. The index databases were audited
read-only for corrupt paths; none found.

### Fix

One line: `fs::relative(path_from_utf8(file), path_from_utf8(root), ec)`.
The whole product was audited for the same pattern. The `".."`/`"."` ASCII
literals and the `wstring` wide construction in `monitor.cpp` are safe. No other
dangerous site.

### Regression

The existing `unicode_path_test` covered decode, scanner, and DB but not the
dataset fingerprint path, which is how this bug passed. A sixth check was added
in the same file and fixture style.

## 2026-10-05 — 0.9.4.48 GUI Stop unresponsiveness fix

Detail: `docs/build-history/0.9.4.48.en.md`

### Symptom and verdict

After starting a search in the GUI, pressing Stop showed only a "stopping"
message while the actual search continued 10+ minutes with sustained disk reads.

Pressing Stop and the search actually stopping are different things. The message
marks only the start of the request.

### Cause: the fingerprint phase never saw cancellation

The Stop button -> `cancelScan()` -> `worker_->cancel()` ->
`control_.cancel=true` chain was correct. The break was at the start of
`MediaSearchEngine::scan()`:

```cpp
telemetry_.setDatasetFingerprint(msf::computeDatasetFingerprint(root));
```

That function reads every file from first byte to last to build a SHA-256
manifest. It had no cancellation parameter, so it never saw Stop.

Every phase's Stop coverage was verified in code. This was the only gap.
`Scanner::count`, the walker, the consume loop, batches, video ranges, and the
final analyze either check or are bounded, and the inside of `imageBatch` plus a
single FFmpeg decode are bounded by one file.

### Fix

`computeDatasetFingerprint(root, cancel=nullptr)` plumbs the path, checked per
file and during large reads (every 64 KiB chunk). On cancel it returns
immediately with `state="cancelled"` and no partial fingerprint. `"cancelled"`
is telemetry-only with no branching consumer, so it is safe. The default
argument keeps all ~20 existing callers compiling unchanged.

scan() passes `control ? &control->cancel : nullptr`.

`scan_cancel_test` (6 tiny files) verifies flag-set -> incomplete -> resume but
never passes through the fingerprint phase, so it could not catch this bug. The
new `cancel_fingerprint_test` (11 checks) verifies on the production path:

- with cancel pre-set the fingerprint returns `state="cancelled"`, no hash,
  zero files, immediately
- without cancel the same 20 files measure normally
- a pre-cancelled scan reports `completed=false` with zero analysis
- after a cancel the DB reopens and a normal scan completes

No timing assertions. The verdict is the state, so it is deterministic.

## 2026-10-06 — 0.9.4.59 post-build review: phase-1 semantics and phase-2 GUI regression separated
Reference: `0.9.4.59` / `18f101f` · CPU CTest 107/107 · GPU CTest 108/108

### Confirmed semantic bug in phase 1

A **video sampling-generation scope error** is confirmed.

Current `processOne()` inserts both of the following into the general `seen` set:

- videos when `scanVideos=false` (explicitly out of the requested scan scope)
- ignored files (intentionally not analyzed in the current scan)

But 0.9.4.59 uses that general `seen` set for the cancelled-scan `allOldVideosSeen` condition, and its successful-scan branch can call `setSamplingGeneration()` from `r.completed` without checking video scope. Therefore **an image-only scan can advance video sampling generation**. This is a semantic bug caused by treating `seen = discovered/present` as equivalent to `admitted/in-scope processed`.

Required invariant:

- `scanVideos=false` must never mutate `sampling_generation`.
- The generation stamp may advance only after the in-scope video admission/processing boundary is satisfied.
- Keep the general `seen` meaning for deletion detection; introduce a separate video-scope admission state.

### Diagnostic semantic hardening

`finishScan(false)` infers the terminal reason from the live `control->cancel` flag. If a DB error sets `failed=true` and a Stop arrives immediately afterward, the transaction still fails/rolls back but telemetry can be mislabeled Cancelled. Pass an explicit terminal state (`Completed / Cancelled / Failed`) so **a late Stop can never relabel a real failure**.

### Verification additions

1. Complete/cancel an image-only (`scanVideos=false`) scan against a stale generation and prove the video generation stamp is unchanged.
2. Inject a deterministic DB error and prove rollback + `failed=true` telemetry; then prove a late Stop cannot change it to Cancelled.
3. Do not ignore the return value of `setSamplingGeneration()`; verify and document the conservative failure behavior.

### Performance observations from the real GUI run

In the real 0.9.4.59 GUI run with 32,494 images, all images used the GPU image path but reported GPU duty was only **about 0.2%**. The image stage was 567.7 s; verify decode was 25.43 s and WIC copy about 25.07 s, while GPU H2D/kernel/D2H combined was only about 0.31 s. This is not evidence of a broken GPU backend; it points more strongly to **pipeline overlap/starvation between CPU/WIC decode, crop, I/O, and short GPU hashing bursts**.

Even under Maximum (90%), CPU usage oscillated around 20–70% for long intervals and averaged 30.8%. Observed drive I/O also varied around 15–40%. These are classified as **post-1.0 scheduler/pipeline work**, not correctness defects.

### Explicit post-1.0 improvement targets

The image-search engine is **first-pass complete as a product path**. After 1.0, treat the following as a separate performance track:

- refine the real effect of CPU worker occupancy versus the CPU policy
- tune read/decode concurrency and I/O backpressure
- improve decode/crop/hash pipeline overlap and GPU batch persistence
- reduce GPU queue starvation and improve host<->device overlap
- distinguish stage bottlenecks, self-attributed usage, and I/O wait in scheduler decisions
- treat Balanced's initial under-utilization and Maximum's long-period oscillation as a worker-admission/backpressure problem rather than just adding workers

GPU utilization itself is not the objective; end-to-end throughput and system stability are. These tasks stay out of the 0.9.4.59 correctness repair.

### Phase 2 GUI regression

The real GUI reproduced a similar-group list regression: when moving downward with mouse dragging, the vertical scrollbar, or keyboard navigation such as End, the list becomes slow after some distance and eventually returns to the top.

Historical `0.9.3.10` fixed an earlier version of this problem by replacing a simple pixel-offset restore with a **semantic top-item scroll anchor + `PositionAtTop`**. The current 0.9.4 code still contains anchor restoration, but after scans the GUI intentionally keeps `uiTimer_` alive, and `thumbStarved_` can repeatedly trigger `refreshStreaming()` -> `refreshGroupList()` -> `fillPair()` full widget rebuilds. That destructive catch-up path is the leading root-cause candidate for the recurrence.

Phase 2 should compare commit `4c059177efca54463dec62bc0da79cd66fe6507e` with the current `uiTimer_`/`thumbStarved_`/`fillPair()` flow, then avoid destructive full rebuilds during active scrolling or update visible item thumbnails in place. Mouse drag, scrollbar drag, End/PageDown/Home acceptance should be explicit regression checks.
